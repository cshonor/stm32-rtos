## 这一篇讲什么

收发 API 各只有一个，但 `xTicksToWait` 参数让它们的语义裂成三种。
本篇把这三种语义、返回值、以及"谁被唤醒"的选择逻辑讲清楚。

## 先用人话说一遍（新手铺垫）

`xTicksToWait` 这个参数，本质是排队办业务时的**三种耐心程度**：

- 写 `0`：**看一眼人多扭头就走**——办不成立刻返回失败，适合
  "这事不办也行"的场景；
- 写 `pdMS_TO_TICKS(N)`：**等 N 分钟，过号就走**——有截止时间的活；
- 写 `portMAX_DELAY`：**今天不办成我就住这儿**——死等，适合
  "必须成功"的关键路径。

注意一个反直觉点：耐心参数只在**暂时办不了**时才生效。窗口空着，
你写"死等"也是立刻办完就走——阻塞从来不是目的，是兜底。

还有"先叫醒谁"的规矩：一个空位腾出来、三个人在排队想写——
**VIP（高优先级）先醒，同级按先来后到**。所以低优先级任务可能
永远排不上号，这是设计时就要想的事。

| 术语 | 一句话解释 |
|---|---|
| 生产者-消费者 | 经典分工模式：一方只往队列放数据，另一方只取；队列就是中间的缓冲 |
| `portMAX_DELAY` | "无限等"的特殊取值：一直阻塞到操作能完成为止（受 INCLUDE_vTaskSuspend 影响） |
| `pdPASS` / `pdFAIL` | FreeRTOS 的统一返回值：成功 / 失败；队列 API 里失败=超时或满/空 |

## 收发 API 的签名（函数原型：名字 + 参数 + 返回值的合称）

```c
/* 发送（尾部插入） */
BaseType_t xQueueSend( QueueHandle_t xQueue,
                       const void * pvItemToQueue,
                       TickType_t xTicksToWait );
/* xQueueSendToBack 是它的宏别名，同一件事 */

/* 接收（头部取出） */
BaseType_t xQueueReceive( QueueHandle_t xQueue,
                          void * pvBuffer,
                          TickType_t xTicksToWait );
```

返回值只有两种：
- `pdPASS`（=1）：成功
- `pdFAIL`（=0）：失败（超时 or 满/空）

## xTicksToWait 的三态语义

| 取值 | 语义 | 适用 |
|---|---|---|
| `0` | **不阻塞**：满/空就立刻返回失败 | 轮询式消费者、非关键路径 |
| `pdMS_TO_TICKS(N)` | **超时阻塞**：等 N tick，超时返回失败 | 有 deadline 的操作 |
| `portMAX_DELAY` | **死等**：一直阻塞到能操作为止 | 必须成功的关键路径 |

**核心规则**：超时参数只在"暂时做不了"时生效。
如果队列有空间/有数据，参数是 `portMAX_DELAY` 也**立刻返回**——
阻塞不是目的，是兜底。

## 阻塞时的任务状态

发送方发现队列满 → 进 Blocked 态，挂到 `xTasksWaitingToSend` 名单，
同时记录超时时刻。接收方发现队列空 → 同理挂到
`xTasksWaitingToReceive`。超时到了没轮到 → 内核把它从名单摘除，
改为 Ready，函数返回 `pdFAIL`。

```c
/* 生产者：满了最多等 100ms */
if( xQueueSend( q, &data, pdMS_TO_TICKS(100) ) != pdPASS )
{
    /* 超时——下游消费不过来，是丢数据还是报警？ */
}

/* 消费者：空了就睡，数据来了被唤醒 */
if( xQueueReceive( q, &data, portMAX_DELAY ) == pdPASS )
{
    process( data );
}
```

## 唤醒谁：优先级优先，同优先级 FIFO

队列满时有三个任务挂着想写，一个位置空出来了——**唤醒谁？**

FreeRTOS 的规则：**优先级最高的等待者先醒**；同优先级按等待先后（FIFO（先进先出））。
这与调度器选 Ready 任务的逻辑完全一致——队列唤醒本质就是
"把一个任务从 Blocked 名单挪到 Ready 名单"，调度器随即按
[3.3 优先级与调度](../03-task-management/3.3-优先级与调度.md) 的规则接手。

**推论**：低优先级任务可能饿死。三个高优先级生产者抢一个消费者，
低优先级的永远排不上。解法是 ch07 讲的互斥量/优先级继承，
或者干脆给生产者分级（高优先级走 SendToFront 插队）。

## 超时精度：±1 tick

`pdMS_TO_TICKS(100)` 不是精确的 100ms。内核在 tick（系统心跳中断，默认 1ms 一次，见 1.3）中断里检查超时，
而调用发生在 tick 的任意相位——实际等待时间在 **99~100ms** 之间
（最多差 1 tick）。这与 [3.4 两种延时](../03-task-management/3.4-两种延时.md)
的量化误差同源：所有 tick 级超时都有这个 ±1 边界。

## 一个完整的生产者-消费者骨架

```c
QueueHandle_t q;

void producer( void *p )
{
    uint32_t n = 0;
    for( ;; )
    {
        xQueueSend( q, &n, portMAX_DELAY );  /* 死等，必须送出去 */
        n++;
        vTaskDelay( pdMS_TO_TICKS(10) );
    }
}

void consumer( void *p )
{
    uint32_t val;
    for( ;; )
    {
        if( xQueueReceive( q, &val, portMAX_DELAY ) == pdPASS )
        {
            /* 拿到 val，干活 */
        }
    }
}
```

## 要点回顾

1. `xTicksToWait` 三态：0=不阻塞、N=超时、portMAX_DELAY=死等。
2. 阻塞 = 任务挂到等待名单 + 记录超时时刻；超时自动转 Ready 返回失败。
3. 唤醒顺序：优先级优先，同级 FIFO——低优先级可能饿死。
4. 所有 tick 级超时有 ±1 tick 量化误差。

<details>
<summary>Q1：portMAX_DELAY 真的会永远等吗？</summary>

看 `INCLUDE_vTaskSuspend` 配置：为 1 时 `portMAX_DELAY` 是无限等；
为 0 时它退化成一个很大的 tick 数（约 49 天，实际等于无限）。
**建议**：除非确定 `INCLUDE_vTaskSuspend=1`，否则关键路径用
`pdMS_TO_TICKS(大数值)` 明确超时，比 `portMAX_DELAY` 更可控。

</details>

<details>
<summary>Q2：阻塞时被 vTaskDelete 删了会怎样？</summary>

被删的任务从等待名单移除，函数不会返回——任务已经不存在了。
队列本身不受影响，等待名单只是引用任务句柄，不是所有权。
这正是 [3.6 句柄删除](../03-task-management/3.6-句柄删除与动态优先级.md)
里"删别人的任务要慎重"的原因之一：你不知道它正阻塞在哪。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| 写了 `portMAX_DELAY` 就会阻塞 | 以为死等 = 一定先睡一会儿 | 队列有空位 / 有数据时立刻返回，超时参数只在"暂时办不了"时生效 |
| `portMAX_DELAY` 永远等于无限等 | 名字就叫 MAX_DELAY | 依赖 `INCLUDE_vTaskSuspend=1`；为 0 时退化成约 49 天的大数，关键路径建议用 `pdMS_TO_TICKS(大数值)` |
| 等待名单按先来后到唤醒 | 直觉 FIFO 公平 | 优先级最高者先醒，同级才 FIFO——低优先级任务可能饿死 |
| `pdMS_TO_TICKS(100)` 就是精确 100ms | 名字写着 ms 转 tick | 有 ±1 tick 量化误差，实际 99~100ms |
| 阻塞中的任务随时可删，函数会报错返回 | 以为删除后 API 返回错误码 | 任务没了函数永不返回；等待名单只是引用句柄，队列本身不受影响 |

## 代码自测

_注：本节代码按 FreeRTOS API 语义编写，未在本仓库环境实跑，上板验证见「验证路径」。_

```c
QueueHandle_t q;

void vProducer( void *p )          /* 快生产者：10ms 一条，队列很快满 */
{
    uint32_t n = 0;
    for( ;; )
    {
        if( xQueueSend( q, &n, pdMS_TO_TICKS(100) ) != pdPASS )
        {
            printf( "drop %lu (timeout)\r\n", n );   /* 超时兜底 */
        }
        n++;
        vTaskDelay( pdMS_TO_TICKS(10) );
    }
}

void vConsumer( void *p )          /* 慢消费者：500ms 消化一条 */
{
    uint32_t val;
    for( ;; )
    {
        if( xQueueReceive( q, &val, portMAX_DELAY ) == pdPASS )
        {
            printf( "eat %lu\r\n", val );
            vTaskDelay( pdMS_TO_TICKS(500) );
        }
    }
}

void app_init( void )
{
    q = xQueueCreate( 5, sizeof( uint32_t ) );   /* 深度只有 5 */
    xTaskCreate( vProducer, "prod", 256, NULL, 2, NULL );
    xTaskCreate( vConsumer, "cons", 256, NULL, 3, NULL );
}
```

**预期现象**：
- 队列先被灌满 5 条，之后生产者每 100ms 超时一次，打印 `drop ... (timeout)`
- 消费者每 500ms 打印一行 `eat N`，N 严格递增但大量跳号（被丢的就是跳掉的号）
- 消费者打印不会因 `portMAX_DELAY` 而延迟——有数据时它立刻返回

**验证路径**：F103 实机 + USART printf；观察 drop 与 eat 的比例 ≈ 生产/消费速率比。

**常见翻车点**：
- 把 `pdFAIL` 当系统错误处理而停机——它只是"超时了"，是正常兜底分支
- 以为 `portMAX_DELAY` 的消费者会拖慢系统——它在空队列时零 CPU
