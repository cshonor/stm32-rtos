## 这一篇讲什么

8.1 是"一个任务等多件事"。本篇升级成**多个任务互相等**：三个采集任务各自
就位，谁最后到谁触发全员放行——教科书叫 rendezvous（会合点），`xEventGroupSync` 一行搞定。

## 先用人话说一遍（新手铺垫）

8.1 是店长一个人等白板。这篇是**对等的多人互相等**：
三个采集任务，谁快谁慢不一定，但规矩是**三个人都干完这一轮，
才一起开始下一轮**——谁也不许抢跑，谁也不掉队。

画面：三个人拼车上班，约定都到齐了才发车。每个人到集合点做
两件事：签个到，然后看人到齐没。坑就出在这两步分开做：
你签完到转身接了个电话，这期间另外两人已到齐、车开走了，
你挂电话回来看签到板——信息已经过时。**"签到"和"查人齐没齐"
之间只要留缝，就会有人拿着过期的现场做决定。**

xEventGroupSync 的解法：把"签到 + 查齐"焊死成一步，中间
谁也插不进来（原子）。最后到的那位签完到发现人齐了，
顺手擦板、招呼全员上车——所以他叫"开门人"。
映射：签到 = 置自己的位，人齐 = all_bits 全置 1，
擦板 = 最后到达者统一清位。

| 术语 | 一句话解释 |
|---|---|
| 会合点（rendezvous） | 并发术语：N 个执行体必须全部到达某一点，才允许任何一个继续前进 |
| 原子操作 | 不可被打断的一串动作：要么全做完，要么没开始，中间状态对外不可见 |
| 竞态窗口 | 两步操作之间允许抢占插入的缝隙，别的执行体在缝里改状态就会出错 |
| 开门人 / 最后到达者 | Sync 里最后一个置位的任务：负责清位并唤醒所有先到者，自己不阻塞 |
| all_bits | 所有参与者"各自的位"按位或起来的并集，即"全员到齐"的判定掩码 |

## 为什么"各自 WaitBits"做不到

朴素想法：每个任务先 SetBits 自己的位，再 WaitBits 等全部位：

```c
xEventGroupSetBits( eg, MY_BIT );
xEventGroupWaitBits( eg, ALL_BITS, pdTRUE, pdTRUE, portMAX_DELAY );
```

坑在两步之间：**两次 API 调用不是原子的。**A 置完位还没开始等，B 已把位凑齐
并放行、甚至位已被清掉——A 带着过时现场进场，这一轮会合就错位了。两拍之间塞得进任意次抢占，精度没法保证。

## xEventGroupSync = "置我的位 + 等全员的位"一步到位

```c
#define BIT_A ( 1 << 0 )
#define BIT_B ( 1 << 1 )
#define BIT_C ( 1 << 2 )
#define ALL_BITS ( BIT_A | BIT_B | BIT_C )

void vTaskX( void *p )   /* A/B/C 三个任务同构 */
{
    for( ;; )
    {
        do_my_work();                    /* 各自干活 */
        xEventGroupSync( eg, BIT_A,      /* 我要置的位（我是A） */
                         ALL_BITS,       /* 我要等齐的位 */
                         portMAX_DELAY );
        /* 走到这里：三人都干完这一轮，同步点开始下一轮 */
    }
}
```

内部语义（概念级）：

```
Sync( my_bit, all_bits ) = 关中断保护下：
    1. 置上 my_bit
    2. all_bits 齐了吗？
       ├─ 齐（我最后到）：清 all_bits，唤醒所有等待者，自己不阻塞
       └─ 没齐：进 Blocked，等"最后到的人"来唤醒
```

**原子性是全部价值**：置位 + 检查 + 阻塞绑成一次内核操作，抢占插不进来。
最后到达者当"开门人"，一次放行全员。

## 一个经典用途：分帧流水线

```
帧 N：  [采集A] [采集B] [采集C]   ← 三任务并行，速度不一
              Sync 会合点          ← 全部完成才进入帧 N+1
帧 N+1：[融合处理] 各自再采集 ...
```

没有 Sync 就得用 3 个计数信号量（能数"还剩几次"的信号量，Give/Take 对应计数增/减） + 1 个互斥量手搓，"最后一个到"的判定
也得自己写——Sync 把这个模式收进了一个 API。

## 和 WaitBits 的对照

| | WaitBits | Sync |
|---|---|---|
| 参与者 | 1 个等待者，N 个无关置位者 | N 个任务**互相**等 |
| 操作 | 只等，不置 | 置 + 等，原子绑定 |
| 谁清位 | ClearOnExit，等待者自己定 | 最后到达者统一清 all_bits |
| 语义 | 状态布告栏 | 周期性会合点 |

**选择标准**：单向"等别人"用 WaitBits；循环里"每轮互相等"用 Sync。用 WaitBits
手搓 Sync 错在原子性；反用 Sync 干 WaitBits 的活，你置的位会污染别人的会合判定。

## 注意事项

- 每个参与者的"我的位"必须**互不相同**，all_bits 是并集；位分错（两人
  同一位）会合点直接失效。
- 参与者数量/位号变了要全组同步改宏——位分配手工管理，没有登记处。
- 有参与者中途退出（被删、被挂起）时 all_bits 永远凑不齐，剩余任务卡死——
  要么给超时，要么设计上禁止中途离场。
- 超时返回时位可能只齐一部分，需按位判定"真会合还是超时"。超时路径待实验验证。

## 要点回顾

1. 会合点 = N 个任务循环里互相等，最后到达者放行全员。
2. 手写"SetBits + WaitBits"两步有原子性漏洞，Sync 把两步并成一步。
3. Sync 内部分工：先到者阻塞，最后到者清位 + 广播唤醒。
4. 位分配手工管、参与者不许中途离场，是会合点模式的两条纪律。

<details>
<summary>Q1：三个任务优先级不同，会合放行顺序怎么算？</summary>

最后到达者唤醒全体后，调度器按老规矩办：**优先级最高的就绪者先跑**。
会合点只保证"全员都已就位"这个事实，不保证放行后的顺序——
顺序归调度器管，别指望 Sync 当公平锁（严格按"先来后到"顺序分配资源的锁）用。

</details>

<details>
<summary>Q2：Sync 和用 N 个二值信号量两两互等，差在哪？</summary>

信号量方案要 N 个信号量加协调逻辑，"最后到达判定"还得自己写计数；
Sync 是一个内核对象 + 一个 API。更要命的是正确性：手搓方案的竞态
窗口和"各自 WaitBits"同款。**模式被收进内核那天起，手搓就是负债。**

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| "各自 SetBits 再 WaitBits" 就能手搓会合点 | 两步合起来不就是 Sync | 两次调用之间不是原子的，竞态窗口里位可能已被凑齐又清掉，会合错位 |
| Sync 放行后按"先到先走"的顺序跑 | 排队嘛，先来后到 | 只保证"全员就位"，放行顺序归调度器：优先级最高的就绪者先跑 |
| 参与者中途删掉/挂起无妨 | 少一个人剩下继续 | all_bits 永远凑不齐，剩余任务全部卡死；要么给超时，要么禁止离场 |
| Sync 超时返回 = 会合成功 | 返回了就是齐了 | 超时也返回，位可能只齐一部分，必须按位判定"真会合还是超时" |
| 位号分配内核会帮我查重 | 建对象时应该登记 | 位分配纯手工管理，两人同一位，会合点静默失效 |

## 代码自测

_注：本节代码按 FreeRTOS API 语义编写，未在本仓库环境实跑，上板验证见「验证路径」。_

```c
/* 三任务会合点：每轮全部干完才一起进下一轮 */
static EventGroupHandle_t eg;

#define BIT_A ( 1 << 0 )
#define BIT_B ( 1 << 1 )
#define BIT_C ( 1 << 2 )
#define ALL_BITS ( BIT_A | BIT_B | BIT_C )

static void vWorker( void *pv )    /* A/B/C 同构，仅位号、干活时长不同 */
{
    const EventBits_t my_bit = ( EventBits_t ) pv;
    const char *pc = ( my_bit == BIT_A ) ? "A" :
                     ( my_bit == BIT_B ) ? "B" : "C";
    for( ;; )
    {
        vTaskDelay( pdMS_TO_TICKS( 100 + ( my_bit * 200 ) ) );  /* 各干各的，速度不同 */
        printf( "%s: arrive\r\n", pc );
        xEventGroupSync( eg, my_bit, ALL_BITS, portMAX_DELAY );
        printf( "%s: go next round\r\n", pc );
    }
}

void app_init( void )
{
    eg = xEventGroupCreate();
    xTaskCreate( vWorker, "A", 256, ( void * ) BIT_A, 2, NULL );
    xTaskCreate( vWorker, "B", 256, ( void * ) BIT_B, 2, NULL );
    xTaskCreate( vWorker, "C", 256, ( void * ) BIT_C, 2, NULL );
}
```

**预期现象**：
- 每轮三个 "arrive" 打印完之后，三个 "go next round" 才成批出现——谁都不抢跑。
- 最快的 A（300ms）到达后要等最慢的 C（900ms），轮次节奏由最慢者决定。
- 同优先级下放行顺序不固定；把 C 的优先级调到 4，"C: go next round" 总是第一个打印。
- 把 Sync 换成"SetBits + WaitBits"两步手搓版重跑：偶发某任务多用一轮前的旧现场，日志轮次错位。

**验证路径**：F103 实机 + USART printf，数每轮 arrive/go 的分组是否整齐。

**常见翻车点**：
- 用 `(void*)BIT_x` 传参时把位号写成十进制 0/1/2，ALL_BITS 判不齐直接卡死。
- 某任务被 vTaskDelete 删掉，剩余任务在 Sync 里永久阻塞，无超时无报错。
- 优先级不同导致打印交织，误以为是会合失败——看分组边界别看顺序。
