## 这一篇讲什么

[4.3](../04-queue-management/4.3-FromISR家族.md) 已经用队列讲过 FromISR 家族；
本篇把规则提炼成**通用清单**（信号量/通知/定时器全都适用），
并讲透一个常被敷衍的问题：**yield 为什么不能在 API 内部自动做，
非要 ISR 尾部手动调。**

## FromISR 家族的通用规则

1. ISR 里**只能**调名字带 `FromISR` 的 API；普通版 = 未定义行为
2. FromISR 版**永不阻塞**：没有 `xTicksToWait`，做不到就立刻返回失败
3. 大多数带一个输出参数 `pxHigherPriorityTaskWoken`
   （不想用这个机制可传 NULL）
4. 中断优先级必须在红线**之下**（数值 ≥ configMAX_SYSCALL_INTERRUPT_PRIORITY），
   详见 [6.3](6.3-中断优先级红线.md)

## xHigherPriorityTaskWoken：内核的"建议"，不是"执行"

```c
BaseType_t xHigherPriorityTaskWoken = pdFALSE;   /* ① 必须初始化 */
xSemaphoreGiveFromISR( sem, &xHigherPriorityTaskWoken );
portYIELD_FROM_ISR( xHigherPriorityTaskWoken );  /* ② ISR 尾部统一 yield */
```

- give 唤醒了一个**比当前被中断任务优先级更高**的任务 → 内核写 `pdTRUE`
- 被唤醒任务优先级不够高 → 保持 `pdFALSE`（不用切，回原任务更划算）
- **注意方向**：这个变量只被"置真"，API 不会帮你置假——所以必须
  每次自己初始化为 `pdFALSE`，且一个 ISR 里多次调 FromISR API
  可以**共用同一个变量**（任何一次置真都值得切）

## 为什么 yield 要手动，API 不能自动切

三个理由：

1. **一个 ISR 里常调多次 API**（收多个字节 give 多次）。
   每次 API 内部都切换 = 现场反复保存/恢复，纯属浪费；
   统一在尾部切一次，只切到"最终赢家"
2. **切换时机必须是"ISR 收尾之后"**：硬件标志清完、数据搬完再走。
   API 内部切走，剩下的 ISR 代码会以"错误任务的上下文"继续跑
3. **把决定权留给应用**：极少数场景你就是想处理完一整批再切，
   手动 yield 让这成为可能（先攒着，最后统一 yield）

Cortex-M 上 `portYIELD_FROM_ISR(pdTRUE)` 的本质：把 PendSV 挂起位
置 1，ISR 退出、所有更高优先级中断退净后，PendSV 以最低优先级
执行真正的上下文切换（port 层职责，见 [1.2](../01-distribution/1.2-portable层是什么.md)）。

## 不 yield 会怎样

不是错误，只是**延迟**：被唤醒的高优先级任务要等下一个 tick 中断
才接手。1ms tick 下最多白等 1ms——对串口协议可能无感，
对微秒级响应的电机控制就是事故。**养成"give 完必 yield"的肌肉记忆。**

## 嵌套中断下的行为

高优先级 ISR 可以抢占低优先级 ISR（Cortex-M 原生支持嵌套）。
`xHigherPriorityTaskWoken` 是栈上局部变量，**每个 ISR 各有一份**，
互不干扰；PendSV 最低优先级保证所有嵌套退净后才切换一次——
嵌套越深，这个设计越划算。

## 要点回顾

1. ISR 里只碰 FromISR API；永不阻塞；红线之下才能调。
2. `xHigherPriorityTaskWoken` 是内核建议：pdTRUE = "有更急的人醒了"。
3. yield 手动且放 ISR 尾部：一批 API 只切一次，切在收尾之后。
4. 不 yield 不算错，但响应延迟最多一个 tick。

<details>
<summary>Q1：pxHigherPriorityTaskWoken 传 NULL 行不行？</summary>

行，语义等于"我不要建议"。那也就不该调 portYIELD_FROM_ISR——
被唤醒的任务等下个 tick 才跑。只在对延迟完全无所谓的场景这么干；
否则老老实实接变量 + yield。

</details>

<details>
<summary>Q2：portYIELD_FROM_ISR 和 taskYIELD 是一回事吗？</summary>

不是。`taskYIELD` 用在任务上下文，立刻触发 PendSV；
`portYIELD_FROM_ISR` 用在 ISR 尾部，带一个条件参数
（pdFALSE 时什么都不做）。混用场景调错版本，
轻则语义不对，重则在中断里做了任务级的调度动作——未定义行为。

</details>
