# 6.1 二值信号量做中断同步：延迟中断处理的标准范式

## 这一篇讲什么

RTOS 中断设计的第一范式：**ISR 只做"记下来 + 通知"两件快事，
真正的处理交给一个被信号量唤醒的任务。**这叫延迟中断处理
（deferred interrupt processing），二值信号量是它的标准载体。

## 为什么不能让 ISR 干完所有活

ISR 跑的时候，同级和更低级中断全被压着。ISR 里干慢活
（解析协议、写 flash、打印日志）的代价：

- 其他中断延迟暴涨，串口丢字节、定时器漂移
- 高优先级任务也被拖——中断优先于一切任务

裸机篇 [ch10](../../../01-stm32/book-notes/10-interrupts/README.md) 的"上半部/
下半部"说的就是这件事；FreeRTOS 里下半部 = 一个普通任务。

## 标准范式：三段式

```c
static SemaphoreHandle_t xUartRxSem;

/* ① 初始化：建信号量，任务先 take（此时为空 → 任务 Blocked） */
void app_init( void )
{
    xUartRxSem = xSemaphoreCreateBinary();
    xTaskCreate( vHandlerTask, "rx", 256, NULL, 3, NULL );
}

/* ② 下半部任务：take 不到就睡，睡到 ISR 来叫 */
void vHandlerTask( void * p )
{
    for( ;; )
    {
        xSemaphoreTake( xUartRxSem, portMAX_DELAY );   /* 阻塞在这 */
        process_rx_data();                              /* 慢活随便干 */
    }
}

/* ③ ISR（上半部）：清标志 + give，立刻走人 */
void USART1_IRQHandler( void )
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;
    USART1->SR = 0;                    /* 清中断标志（硬件义务） */
    xSemaphoreGiveFromISR( xUartRxSem, &xHigherPriorityTaskWoken );
    portYIELD_FROM_ISR( xHigherPriorityTaskWoken );
}
```

**时序**：中断来 → ISR give → 信号量"满" → ISR 退出时
portYIELD_FROM_ISR 直接切到下半部任务 → 任务 take 到"空"，干活，
回到 take 继续睡。**整个慢处理在任务上下文完成**，中断系统
只被 ISR 占用了几微秒。

## 二值信号量在这里就是"事件旗标 + 阻塞点"

| 角色 | 队列 | 二值信号量 |
|---|---|---|
| 存什么 | 数据（值拷贝，见 [4.1](../04-queue-management/4.1-队列是什么.md)） | 不存数据，只有"满/空"两个状态 |
| 中断同步适用场景 | ISR 要把**数据**递给任务（如收到的字节） | ISR 只报"出事了"，数据在别处（DMA 缓冲、寄存器） |
| 实现 | queue.c | queue.c（长度 1、项大小 0 的特例） |

选型口诀：**要带数据用队列，只报信用二值信号量。**

## 先 take 再用的初始化细节

任务创建后第一件事是 `xSemaphoreTake`——此时信号量是空的
（CreateBinary 出来就是空），任务立刻 Blocked，**不占 CPU**。
这是"事件驱动任务"的标准开机姿势：
不开机自旋、不用标志位轮询，Blocked 态即"等中断"态
（[3.2 任务状态机](../03-task-management/3.2-任务状态机.md) 里
Blocked 的又一燃料）。

## 中断来了两次、任务还没处理完怎么办

二值信号量只有满/空：ISR 在任务处理期间再 give，**第二次 give 丢失**
（还是满）。对"事件可以合并"的场景（按键、DMA 半满/全满）无所谓；
对"次数就是信息"的场景（数脉冲）会**丢事件**——
那要用计数信号量，见 [6.4 计数信号量](6.4-计数信号量.md)。

## 要点回顾

1. 范式一句话：ISR 清标志 + give + yield，任务 take + 干活。
2. 只报信用二值信号量，要带数据走队列。
3. 任务开机即 take（空 → Blocked），零轮询零自旋。
4. 事件合并没问题，事件计数会丢——后者转 6.4。

<details>
<summary>Q1：为什么 ISR 里能调 xSemaphoreGiveFromISR 却不能调普通 give？</summary>

普通 `xSemaphoreGive` 可能触发调度相关的内部操作，
且没有"我是中断"的标注，内核无法按 ISR 规则保护临界区。
FromISR 版内部用中断屏蔽（而非调度器挂起）保护，且绝不阻塞——
设计细节见 [6.2](6.2-FromISR规则与yield.md) 与 [6.3](6.3-中断优先级红线.md)。

</details>

<details>
<summary>Q2：延迟处理任务优先级怎么定？</summary>

它顶替了"本来要在 ISR 里干的活"，所以优先级应体现该中断的
紧迫度：串口协议解析 > LED 刷新。一般给应用任务里的高档，
**但别高过其他更急的延迟处理任务**。F103 实验里的具体档位
待实验验证。

</details>
