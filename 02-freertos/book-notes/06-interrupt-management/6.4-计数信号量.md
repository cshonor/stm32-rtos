## 这一篇讲什么

二值信号量只有满/空；计数信号量把"满"扩展成 **0..N 的计数器**。
这一个改动支撑两种完全不同的用法：**数资源**（池子里还剩几个）
和**数事件**（攒了几次没处理）。后者正是 [6.1](6.1-二值信号量中断同步.md)
"丢事件"问题的解药。

## 先用人话说一遍（新手铺垫）

二值信号量像**只有一个车位的私人车库**：满/空两个状态。快递来了
两次你还没回家？第二次"送到"的信息直接丢了——车库没法告诉你
"积了两件"。

计数信号量把车库换成**带剩余车位显示屏的停车场**，一个数（0..N）
撑起两种生意：

- **数资源**：显示屏初始 = 总车位（max）。进一辆车数字 -1
  （take=借一个资源），出一辆 +1（give=归还）。归零时想进的车
  排队（阻塞）。三个相同的 DMA 通道就这么管。
- **数事件**：显示屏初始 = 0。ISR 每来一次 +1，任务每处理一件
  -1。**积压多少次都记得**，峰值不超 max 就一次不丢——6.1 的
  丢事件问题就此解决。

选型口诀不变：事件能合并用二值，**次数本身就是信息用计数**。

| 术语 | 一句话解释 |
|---|---|
| 计数信号量 | 取值 0..N 的信号量；二值信号量是 N=1 的特例，底层同为队列特例 |
| 资源池 | N 个可互换的同质资源（如 3 个 DMA 通道）；计数信号量的计数=剩余可借数 |
| 积压深度 | 数事件用法里"攒了几次没处理"；max 是积压上限，超出照样丢 |
| `uxSemaphoreGetCount` | 读当前计数值的 API，调试时用来看积压水位 |

## 创建与语义

```c
/* 数资源：max=3，初值=3（池子满） */
SemaphoreHandle_t xPool = xSemaphoreCreateCounting( 3, 3 );

/* 数事件：max=10，初值=0（从"没攒事件"开始） */
SemaphoreHandle_t xEvents = xSemaphoreCreateCounting( 10, 0 );
```

| 用法 | max | 初值 | take 含义 | give 含义 |
|---|---|---|---|---|
| 数资源 | 池子容量 | = max（全可用） | 借一个资源（计数-1，空则阻塞） | 还一个（计数+1） |
| 数事件 | 最多攒几个 | 0 | 消费一个事件（计数-1，无则阻塞） | 记录一次事件（计数+1） |

实现上仍是 queue.c 的特例（长度 max、项大小 0），
`configUSE_COUNTING_SEMAPHORES` 要在
[FreeRTOSConfig.h](../01-distribution/1.3-FreeRTOSConfig逐项过一遍.md) 里置 1。

## 数事件：解决 6.1 的丢事件问题

场景回放：ISR 给二值信号量，任务还没 take 完第二个中断来了——
再 give 还是"满"，**第二次事件被吞**。

换计数信号量（max=10, 初值 0）：

```
中断1：give → 计数 1      中断2（任务还在忙）：give → 计数 2
任务 take → 计数 1        任务 take → 计数 0，处理两次，一次不丢
```

**计数就是积压深度**：事件可以"攒着"，峰值积压不超过 max 就一次不丢；
超 max 再 give 依旧失败——max 是缓冲，不是解药
（同 [4.3](../04-queue-management/4.3-FromISR家族.md) 队列深度的结论）。

二值信号量在此显形为 **max=1 的特例**：积压上限 1，超出即丢。
选型即"能合并 → 二值；次数是信息 → 计数"。

## 数资源：另一种经典用法

```c
/* 三个相同的 DMA 通道，谁先空谁用 */
if( xSemaphoreTake( xPool, pdMS_TO_TICKS(50) ) == pdPASS )
{
    use_one_dma_channel();              /* 用哪个由通道自己的逻辑选 */
    xSemaphoreGive( xPool );            /* 用完归还 */
}
```

take/give 天然完成"借还配平"，计数永远等于"还剩几个"。
注意这**不是互斥**：它管的是 N 个同质资源的分配，
保护单个共享资源要用互斥量（保护共享资源的锁，带优先级继承），那是
[ch07](../07-resource-management/README.md) 的地盘。

## 边界与失败语义

| 情况 | 结果 |
|---|---|
| take 时计数为 0 | 按 xTicksToWait 阻塞（任务睡着等、不占 CPU）/超时/立即失败（三态同 [4.2](../04-queue-management/4.2-阻塞语义与超时.md)） |
| give 时计数已达 max | 返回 pdFAIL，计数不变（数事件 = 丢事件；数资源 = 程序有 bug，还多了） |
| ISR 里 give | `xSemaphoreGiveFromISR`，规则同 [6.2](6.2-FromISR规则与yield.md) |
| ISR 里 take | **没有这个 API**——ISR 永不阻塞，也没有"借资源"的合理场景 |

"数资源时 give 失败"值得单独警觉：正常借还绝不会多还，
出现 pdFAIL = 有人 give 了两次或 take 后忘还前的代码路径错乱，
开发期建议断言（条件不成立就当场停车报错的检查，如 `configASSERT`）。

## 与任务通知的关系

ch09 会讲：任务通知也能当"轻量计数信号量"用
（`ulTaskNotifyTake` 的计数值），更快更省 RAM，但只能
一对一（通知固定属于某个任务）。多对一的事件汇聚
（多个 ISR 通知同一个任务）才必须用真信号量。
先用信号量把语义写对，性能敏感再迁通知。

## 要点回顾

1. 计数信号量 = 0..N 计数器：数资源（初值=max）与数事件（初值=0）两种用法。
2. 数事件攒积压：max 内一次不丢，超出照样丢——缓冲不是解药。
3. 二值信号量 = max=1 的特例；选型看"事件能否合并"。
4. 数资源 ≠ 互斥；give 达 max 返回失败多半是代码 bug。

<details>
<summary>Q1：数事件的 max 怎么定？</summary>

按"最坏突发积压"定：事件处理时长 × 中断最大频率，再加裕量。
拍脑袋给 10 起步，真实水位（uxSemaphoreGetCount 峰值）待实验验证。

</details>

<details>
<summary>Q2：数资源时 take 到 0 后任务阻塞，资源还了谁先醒？</summary>

等待名单按优先级排队（同队列的两个名单机制）：
归还资源时唤醒**优先级最高**的等待任务，同级按先来后到。
低优先级任务可能因高优先级反复借还而等较久——
设计资源池大小时要考虑这点。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| 数资源和数事件创建参数一样 | 反正都是计数信号量 | 数资源 `max=N, 初值=N`（池子满）；数事件 `max=N, 初值=0`（从零攒），写反语义全错 |
| max 给大点就万事大吉 | 深度够就不会丢 | max 是缓冲不是解药；积压超 max 照样丢，治本靠消费端更快 |
| give 返回 `pdFAIL` 无所谓 | 失败就失败呗 | 数资源时 give 失败 = 借还配平代码有 bug（多还 / 忘还），开发期断言当场抓 |
| ISR 里可以 take 一下试试 | give 有 FromISR 版，take 应该也有 | `xSemaphoreTakeFromISR` 不存在——ISR 永不阻塞，也没有借资源的合理场景 |
| 计数信号量可以当互斥锁用 | 都是信号量 | 数资源 ≠ 互斥；保护单个共享资源用互斥量（带优先级继承），是 ch07 的地盘 |

## 代码自测

_注：本节代码按 FreeRTOS API 语义编写，未在本仓库环境实跑，上板验证见「验证路径」。_

```c
static SemaphoreHandle_t xEvents;   /* 数事件：max=10, 初值=0 */

void EXTI0_IRQHandler( void )       /* 按键中断，可能连按 */
{
    BaseType_t xWoken = pdFALSE;
    xSemaphoreGiveFromISR( xEvents, &xWoken );   /* 每按一次 +1 */
    EXTI->PR = ( 1 << 0 );                       /* 清挂起标志 */
    portYIELD_FROM_ISR( xWoken );
}

void vHandlerTask( void *p )
{
    for( ;; )
    {
        xSemaphoreTake( xEvents, portMAX_DELAY );
        printf( "key handled, backlog=%lu\r\n",
                uxSemaphoreGetCount( xEvents ) );  /* 看积压水位 */
        vTaskDelay( pdMS_TO_TICKS(300) );          /* 模拟慢处理 */
    }
}

void app_init( void )
{
    /* configUSE_COUNTING_SEMAPHORES 须置 1 */
    xEvents = xSemaphoreCreateCounting( 10, 0 );
    xTaskCreate( vHandlerTask, "key", 256, NULL, 3, NULL );
}
```

**预期现象**：
- 连按 5 次按键，任务慢速打印 5 行——换成二值信号量只会处理 1~2 次
- 处理期间 `backlog` 峰值可见（如 3），随 take 逐步归零，一次不丢
- 连按超过 10 次再观察：超出 max 的 give 失败，事件开始丢——缓冲不是解药

**验证路径**：F103 实机 + 按键 EXTI + USART printf，对照实验 `02-freertos/03-semaphore`。

**常见翻车点**：
- `xSemaphoreCreateCounting(10, 10)` 当数事件用——初值写反，开机就"攒了 10 个假事件"
- 忘开 `configUSE_COUNTING_SEMAPHORES`，创建函数链接/运行直接不可用
