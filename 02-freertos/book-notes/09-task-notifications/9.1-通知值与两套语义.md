## 这一篇讲什么

任务通知（task notification）是 FreeRTOS 里**最快、最省 RAM** 的
任务间通信方式：每个任务的 TCB 里**天生自带**一个 32 位通知值
（`ulNotifiedValue`）和一个通知状态（`ucNotifyState`），
发通知就是**直接改对方 TCB 里的这两个字段**——没有中间对象。
本篇讲清这个结构和它为什么比队列/信号量快，以及两套接收语义的分工。

## 结构：TCB 里多出的两个字段

```
┌─ TCB ─────────────────────────────┐
│  栈指针、优先级、名单项 ...         │
│  ulNotifiedValue  ← 32 位通知值     │
│  ucNotifyState    ← 通知状态        │
└───────────────────────────────────┘
```

通知状态只有三种：未等待通知 / 等待通知（接收方已阻塞）/ 通知已挂起
（值已到、接收方还没来取）。内核靠这个状态决定
"发通知时要不要唤醒接收任务"。

**前提**：`configUSE_TASK_NOTIFICATIONS` 置 1（默认就是 1）。
置 0 可以省掉每个 TCB 里的这几个字节，但一般不值得。

## 为什么比队列快、比信号量省 RAM

队列/信号量/事件组都是**独立内核对象**：要先 `xQueueCreate`
从 heap 切一块结构体 + 存储区，收发时还要操作对象上的
两个等待名单（见 [4.1](../04-queue-management/4.1-队列是什么.md)）。
任务通知把这些全省了：

| 对比项 | 队列/信号量 | 任务通知 |
|---|---|---|
| 对象创建 | 需要（heap 分配） | 不需要，TCB 自带 |
| RAM 开销 | 结构体 + 存储区 + 两个名单 | 每个 TCB 固定几个字节 |
| 发送动作 | 拷贝数据 + 操作名单 + 可能切换 | 改 TCB 两个字段 + 可能切换 |
| 官方口径 | 基准 | 快约 45%（书里的实测数字） |

"快约 45%、RAM 更省"是官方书给出的口径，本仓未做实测——
骨架实验建起来后值得在 F103 上复核。

## 两套 API 的分工：Take 还是 Wait

任务通知有两组收发搭配，**语义不同，别混用**：

| 用途 | 发送 | 接收 | 语义 |
|---|---|---|---|
| 计数信号量替身 | `xTaskNotifyGive()` | `ulTaskNotifyTake()` | 通知值当**计数器**：发一次 +1，取一次 -1 |
| 事件组 / 轻量邮箱替身 | `xTaskNotify()` | `xTaskNotifyWait()` | 通知值当**32 位数据**：按 `eNotifyAction` 覆写/置位/累加 |

```c
/* 路线一：Give/Take —— 计数语义 */
xTaskNotifyGive( xTask );            /* 对方通知值 +1，并唤醒 */
ulTaskNotifyTake( pdTRUE,            /* pdTRUE：取走时清零（二值用法） */
                  portMAX_DELAY );   /* 返回取走前的计数 */

/* 路线二：Notify/Wait —— 数据语义 */
xTaskNotify( xTask, 0x01, eSetBits );/* 按位或进对方通知值 */
uint32_t val;
xTaskNotifyWait( 0,           /* 进入时不清任何位 */
                 0xFFFFFFFF,  /* 退出时清掉全部位 */
                 &val, portMAX_DELAY );
```

**怎么选**：只要"发生了一次"的信号 → Give/Take（信号量替身）；
要带数据或要传多个事件位 → Notify/Wait（事件组/邮箱替身）。
下两篇分别展开。

## 要点回顾

1. 任务通知 = TCB 自带的 32 位通知值 + 通知状态，无中间对象。
2. 省掉对象创建和名单操作 → 比队列快、比信号量省 RAM（官方口径快约 45%）。
3. Give/Take 是计数语义（信号量替身）；Notify/Wait 是数据语义（事件组/邮箱替身）。

<details>
<summary>Q1：通知值只有一个 32 位，多个发送方同时发会不会打架？</summary>

会——这正是通知"只能一对一"的根源之一。通知值没有队列那样的
多格缓冲，两个发送方对同一个值做读改写，没有互斥保护就互相覆盖。
所以官方定位是 **一个接收任务配一个发送源**（ISR→任务 或 任务→任务），
详见 [9.3 通知的边界](9.3-通知的边界.md)。

</details>

<details>
<summary>Q2：通知状态 ucNotifyState 我需要手动管吗？</summary>

不需要，内核自动维护。它的作用是区分"接收方正在阻塞等通知"
（发送时要唤醒它）和"通知先到了人还没来"（接收方下次调 Take/Wait
时立即拿到、不阻塞）。理解它有助于看懂"先发后收也不丢"的行为。

</details>
