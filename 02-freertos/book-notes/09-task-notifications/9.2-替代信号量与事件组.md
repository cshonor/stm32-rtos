## 这一篇讲什么

任务通知的官方卖点是"一个顶四个"：二值信号量、计数信号量、
事件组、长度 1 的队列，都能用它顶替。本篇把三种替身写法和
`xTaskNotify` 的五种 `eNotifyAction` 讲透。

## 先用人话说一遍（新手铺垫）

接着上一篇的工牌便签栏。这篇回答的问题是：这块 32 位的便签栏，
具体能怎么写？答案是五种写法，对应 `eNotifyAction` 的五个取值：

- **只拍肩膀不写字**（eNoAction）：只点灯唤醒，内容走别的渠道；
- **按格打勾**（eSetBits）：便签栏上 32 个格子，你点名的格子勾上，
  已有的勾不动——这是事件组的玩法；
- **正字加一笔**（eIncrement）：计数加一——这是信号量的玩法；
- **擦掉重写**（eSetValueWithOverwrite）：管他原来写了什么，
  整栏换成新内容——"只关心最新值"的邮箱玩法；
- **有字就不写**（eSetValueWithoutOverwrite）：上一条还没被取走？
  那我宁可报失败也不覆盖——"一条都不许丢"的玩法。

前四种丢了上一条不心疼（计数可叠加、最新值即正义），第五种是
全家族**唯一**会主动报错的写法。正文按"顶替哪个正主"组织，
看到每个替身时回这张清单对一下"用的是哪种写法"即可。

| 术语 | 一句话解释 |
|---|---|
| `eNotifyAction` | `xTaskNotify` 的第三个参数：规定这次发送对通知值做哪种操作 |
| 轻量邮箱 | 长度 1、只留最新值的数据通道：新值直接盖掉旧值 |
| 覆写（overwrite） | 无条件用新值替换旧值；旧值丢了就丢了 |
| `eSetValueWithoutOverwrite` | 唯一不覆写的动作：对方没取走上一条就发送失败（返回 pdFAIL） |
| 进入清位 / 退出清位 | `xTaskNotifyWait` 的两个参数：开始等之前 / 拿到值之后，分别清掉哪些位 |

## 替身一：信号量（Give/Take）

[ch06 中断管理](../06-interrupt-management/README.md) 的标准模式是
"ISR 给信号量，任务拿信号量做下半部（ISR 里只做最急的事，剩下的活儿交给任务慢慢干的分工）"。通知版把对象省了：

```c
/* 正主：二值信号量 */
xSemaphoreGiveFromISR( xSem, &xWoken );        /* ISR 侧 */
xSemaphoreTake( xSem, portMAX_DELAY );         /* 任务侧 */

/* 替身：任务通知，xSem 这个对象整个消失 */
vTaskNotifyGiveFromISR( xTask, &xWoken );      /* ISR 侧：对方计数 +1 */
ulTaskNotifyTake( pdTRUE, portMAX_DELAY );     /* 任务侧：取走并清零 */
```

`ulTaskNotifyTake` 第一个参数是**清法**：

| 取值 | 效果 | 对应正主 |
|---|---|---|
| `pdTRUE`（FreeRTOS 的"真"常量，就是 1；"假"是 pdFALSE = 0） | 取走时通知值**清零** | 二值信号量（攒多了也只算一次） |
| `pdFALSE` | 取走时通知值**减一** | 计数信号量（来几次处理几次） |

计数信号量场景（比如"来了 N 个数据，逐个处理"）就用 `pdFALSE`，
返回值是减一前的计数——通知值本身就是计数器，
不需要 `uxSemaphoreGetCount` 之类的辅助查询。

## 替身二：事件组（eSetBits + Wait）

[ch08 事件组](../08-event-groups/README.md) 用 24 个事件位表达
"哪几件事发生了"。通知值是 32 位，**全都能当事件位用**：

```c
/* ISR 里置第 0 位："收到一帧" */
xTaskNotifyFromISR( xTask, 0x01, eSetBits, &xWoken );

/* 任务侧：等到后读出全部位，退出时清掉 */
uint32_t val;
xTaskNotifyWait( 0,                  /* 进入时不预清 */
                 0xFFFFFFFF,         /* 成功返回时清掉全部 32 位 */
                 &val, portMAX_DELAY );
if( val & 0x01 ) { /* 处理收到的一帧 */ }
```

和事件组的差别：事件组支持**多任务同等单位**和"等位 A 或位 B"的 OR 语义；
通知只支持一对一，位语义一样，组合能力弱。

## 替身三：轻量邮箱（eSetValueWithOverwrite）

长度 1 队列 + `xQueueOverwrite` 的"最新值邮箱"（见 [4.4](../04-queue-management/4.4-传指针的代价与规矩.md)），通知版：

```c
/* 发送：直接覆写对方通知值 */
xTaskNotify( xTask, sensor_value, eSetValueWithOverwrite );

/* 接收：读出整个 32 位 */
xTaskNotifyWait( 0, 0, &val, portMAX_DELAY );
```

适合"只关心最新值"的单生产者场景（传感器采样、状态字广播给唯一消费者）。

## 五种 eNotifyAction 总表

| eAction | 对通知值的操作 | 典型用途 |
|---|---|---|
| `eNoAction` | 不改值，只更新通知状态 | 纯"拍一下"唤醒，值由别的途径传 |
| `eSetBits` | 按位或（`val |= bits`） | 事件组替身 |
| `eIncrement` | 值 +1 | 计数信号量替身（Give 就是它的封装） |
| `eSetValueWithOverwrite` | 无条件覆写 | 轻量邮箱（最新值） |
| `eSetValueWithoutOverwrite` | 对方还没取走就**失败返回** | 轻量队列（不丢数据，发重了报错） |

注意最后一行：`eSetValueWithoutOverwrite` 是唯一会"发送失败"的动作——
对方上一次的通知还没被 `xTaskNotifyWait` 取走时，返回 `pdFAIL`，
值保持不变。这是通知家族里**唯一的"不覆盖"保证**，
想要"一条都不能丢"就用它并检查返回值。

## 要点回顾

1. Give/Take 顶替信号量：`pdTRUE` 清零 = 二值，`pdFALSE` 减一 = 计数。
2. `eSetBits` + `xTaskNotifyWait` 顶替事件组，32 位全可用。
3. `eSetValueWithOverwrite` 顶替长度 1 的覆写队列（轻量邮箱）。
4. 要"不丢数据"用 `eSetValueWithoutOverwrite` 并检查返回值。

<details>
<summary>Q1：xTaskNotifyWait 的两个清位参数怎么配合？</summary>

第一个 `ulBitsToClearOnEntry`：进入等待**前**清哪些位——
用于丢弃历史残留，常用 0（保留）或全 1（每次从干净状态等）。
第二个 `ulBitsToClearOnExit`：成功返回**后**清哪些位——
常用全 1（读走即清，下次等全新事件），也可以只清已处理的位、
留下没处理的位下次继续看。

</details>

<details>
<summary>Q2：通知能替代所有信号量场景吗？</summary>

不能。互斥锁（mutex）不行——互斥锁有**优先级继承**（持锁的低优先级任务临时借用等待者的高优先级）机制
（见 ch07 资源管理），通知没有。多对一、一对多也不行，
那是通知的结构性限制，下一篇专门讲。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| `eSetValueWithOverwrite` 能保数据不丢 | 发了总会被看到 | 无条件覆写，上一条没取走就直接盖掉；"不能丢"要用 `eSetValueWithoutOverwrite` |
| `eSetValueWithoutOverwrite` 失败时会等对方取走 | 跟队列满了阻塞一样 | 通知没有发送方阻塞，直接返回 `pdFAIL`，补救（重试/计数丢弃）自己来 |
| `ulTaskNotifyTake` 取走就是清零 | 跟二值信号量 Take 一样 | 第一个参数决定：`pdTRUE` 清零（二值），`pdFALSE` 减一（计数信号量） |
| 通知能把所有信号量场景都顶替 | "一个顶四个" | 互斥锁不行：互斥锁有优先级继承，通知没有 |
| 通知当事件组用，也能多人同等一位 | 位语义一样 | 通知只支持一对一，没有广播、没有多人等同位 |

## 代码自测

_注：本节代码按 FreeRTOS API 语义编写，未在本仓库环境实跑，上板验证见「验证路径」。_

```c
/* eSetBits 顶替事件组 + eSetValueWithoutOverwrite 的"不丢"保证 */
static TaskHandle_t xRxTask;
#define BIT_FRAME_RX  ( 1u << 0 )
#define BIT_ERROR     ( 1u << 1 )

static void vTx( void *pv )
{
    uint32_t tick = 0;
    for( ;; )
    {
        tick++;
        xTaskNotify( xRxTask, BIT_FRAME_RX, eSetBits );   /* 按位或进去 */
        if( ( tick % 5 ) == 0 )
        {
            xTaskNotify( xRxTask, BIT_ERROR, eSetBits );  /* 每 5 次报一次错 */
        }
        vTaskDelay( pdMS_TO_TICKS( 200 ) );
    }
}

static void vRx( void *pv )
{
    uint32_t val;
    for( ;; )
    {
        xTaskNotifyWait( 0,            /* 进入时不清历史位 */
                         0xFFFFFFFF,   /* 退出时清掉全部 32 位 */
                         &val, portMAX_DELAY );
        if( val & BIT_FRAME_RX ) { printf( "frame\r\n" ); }
        if( val & BIT_ERROR )    { printf( "error!\r\n" ); }
    }
}

void app_init( void )
{
    xTaskCreate( vRx, "RX", 256, NULL, 3, &xRxTask );
    xTaskCreate( vTx, "TX", 256, NULL, 2, NULL );
}
```

**预期现象**：
- 每 200ms 打印一行 "frame"；大约每秒额外插一行 "error!"。
- RX 优先级高于 TX，置位即被唤醒，两个 if 可能同轮都命中（val 里多位同时置 1）。
- 把 TX 换成连发两次 `eSetValueWithoutOverwrite` 且中间不让 RX 跑：第二次返回 `pdFAIL`，旧值原样保留——这是全家唯一会失败的写法。

**验证路径**：F103 实机 + USART printf，看 frame/error 打印节奏；用调试器或打印检查第二次覆写的返回值。

**常见翻车点**：
- `xTaskNotifyWait` 第二参数写 0：位永不清，每次唤醒都看到全部历史位，事件被"重播"。
- 同一个通知值别处又用了 `xTaskNotifyGive`（+1），位语义被计数污染。
- 把 `eSetBits` 写成 `eSetValueWithOverwrite`：不是按位或，是整值覆写，BIT_ERROR 会把 BIT_FRAME_RX 冲掉。
