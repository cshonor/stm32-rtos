# ch09 · 任务通知 —— 章节导航

> 书第 9 章 · 对应实验：后续追加（骨架未建）
> 章导航：本篇

## 本章讲什么

**任务通知 = "直接发给某个任务的轻量事件"，每个任务自带一个 32 位通知值，
不需要单独创建队列/信号量对象。**官方定位：在"一对一"场景下，
任务通知可以替代二值信号量、计数信号量、事件组、甚至长度 1 的队列——
**快约 45%、RAM 更省**（书里的实测口径）。

代价是限制：只能一对一（ISR→任务 或 任务→任务），不能一对多；
只有接收方能阻塞（发送方不能等"对方收走"）。

## 只看这一页（速览）

**主线一句话**：一对一通信为什么要先建个中间对象？9.1 讲通知直达 TCB 的结构和两套语义，9.2 给出顶替信号量/事件组/邮箱的具体写法，9.3 划清边界：什么场景必须退回队列等正主。

| 小节 | 一句话结论 |
|---|---|
| 9.1 通知值与两套语义 | 通知 = 直接改对方 TCB 自带的 32 位通知值 + 状态，无中间对象所以快约 45%、RAM 近零；Give/Take 是计数语义，Notify/Wait 是数据语义。 |
| 9.2 替代信号量与事件组 | 三种替身写法对应五种 eNotifyAction；唯一会"发送失败"的是 eSetValueWithoutOverwrite，要"一条不丢"就用它并查返回值。 |
| 9.3 通知的边界 | 只能一对一、发送方不能阻塞、值是无类型 32 位；要互斥继承、广播、可靠排队就退回正主；FromISR 规则和队列家族完全一致。 |

**本章最容易踩的坑**：

- 同一个任务混用 Give（+1）和 eSetBits（按位或）两套语义，互相污染通知值（9.3）。
- 多个发送方并发改同一通知值，读改写无互斥保护会丢更新——官方定位一个通道一个发送源（9.1/9.3）。
- 拿通知当互斥锁用——通知没有优先级继承机制（9.2/9.3）。
- 用 eSetValueWithOverwrite 传"不能丢"的数据——上一条没取走就被直接盖掉（9.2）。

## API 速查卡

| API / 命令 | 一句话作用 | 易错点 |
|---|---|---|
| `configUSE_TASK_NOTIFICATIONS` | 开关任务通知功能 | 默认 1，无需手动开 |
| `xTaskNotifyGive` | 对方通知值 +1 并唤醒 | 计数语义，别和 eSetBits 混用污染同一个值 |
| `ulTaskNotifyTake` | 取走通知值 | `pdTRUE` 清零（二值）/ `pdFALSE` 减一（计数），别用反 |
| `xTaskNotify` | 按 `eNotifyAction` 改写对方通知值 | 五种动作语义不同，覆写类会丢旧值 |
| `xTaskNotifyWait` | 等通知并读出值 | 两个清位参数（进入/退出）别配错，退出清 0 会重播历史位 |
| `eSetValueWithoutOverwrite` | 对方没取走就发送失败 | 唯一返回 `pdFAIL` 的动作，要查返回值 |
| `vTaskNotifyGiveFromISR` | ISR 里 Give 通知 | 返回 void；记得 `portYIELD_FROM_ISR` |
| `xTaskNotifyFromISR` | ISR 里发数据语义通知 | 多一个 `pxHigherPriorityTaskWoken` 参数 |
