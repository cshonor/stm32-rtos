# 4.2 xQueueSend / xQueueReceive 的阻塞语义与超时

## 这一篇讲什么

收发 API 各只有一个，但 `xTicksToWait` 参数让它们的语义裂成三种。
本篇把这三种语义、返回值、以及"谁被唤醒"的选择逻辑讲清楚。

## 收发 API 的签名

```c
/* 发送（尾部插入） */
BaseType_t xQueueSend( QueueHandle_t xQueue,
                       const void * pvItemToQueue,
                       TickType_t xTicksToWait );
/* xQueueSendToBack 是它的宏别名，同一件事 */

/* 接收（头部取出） */
BaseType_t xQueueReceive( QueueHandle_t xQueue,
                          void * pvBuffer,
                          TickType_t xTicksToWait );
```

返回值只有两种：
- `pdPASS`（=1）：成功
- `pdFAIL`（=0）：失败（超时 or 满/空）

## xTicksToWait 的三态语义

| 取值 | 语义 | 适用 |
|---|---|---|
| `0` | **不阻塞**：满/空就立刻返回失败 | 轮询式消费者、非关键路径 |
| `pdMS_TO_TICKS(N)` | **超时阻塞**：等 N tick，超时返回失败 | 有 deadline 的操作 |
| `portMAX_DELAY` | **死等**：一直阻塞到能操作为止 | 必须成功的关键路径 |

**核心规则**：超时参数只在"暂时做不了"时生效。
如果队列有空间/有数据，参数是 `portMAX_DELAY` 也**立刻返回**——
阻塞不是目的，是兜底。

## 阻塞时的任务状态

发送方发现队列满 → 进 Blocked 态，挂到 `xTasksWaitingToSend` 名单，
同时记录超时时刻。接收方发现队列空 → 同理挂到
`xTasksWaitingToReceive`。超时到了没轮到 → 内核把它从名单摘除，
改为 Ready，函数返回 `pdFAIL`。

```c
/* 生产者：满了最多等 100ms */
if( xQueueSend( q, &data, pdMS_TO_TICKS(100) ) != pdPASS )
{
    /* 超时——下游消费不过来，是丢数据还是报警？ */
}

/* 消费者：空了就睡，数据来了被唤醒 */
if( xQueueReceive( q, &data, portMAX_DELAY ) == pdPASS )
{
    process( data );
}
```

## 唤醒谁：优先级优先，同优先级 FIFO

队列满时有三个任务挂着想写，一个位置空出来了——**唤醒谁？**

FreeRTOS 的规则：**优先级最高的等待者先醒**；同优先级按等待先后（FIFO）。
这与调度器选 Ready 任务的逻辑完全一致——队列唤醒本质就是
"把一个任务从 Blocked 名单挪到 Ready 名单"，调度器随即按
[3.3 优先级与调度](../03-task-management/3.3-优先级与调度.md) 的规则接手。

**推论**：低优先级任务可能饿死。三个高优先级生产者抢一个消费者，
低优先级的永远排不上。解法是 ch07 讲的互斥量/优先级继承，
或者干脆给生产者分级（高优先级走 SendToFront 插队）。

## 超时精度：±1 tick

`pdMS_TO_TICKS(100)` 不是精确的 100ms。内核在 tick 中断里检查超时，
而调用发生在 tick 的任意相位——实际等待时间在 **99~100ms** 之间
（最多差 1 tick）。这与 [3.4 两种延时](../03-task-management/3.4-两种延时.md)
的量化误差同源：所有 tick 级超时都有这个 ±1 边界。

## 一个完整的生产者-消费者骨架

```c
QueueHandle_t q;

void producer( void *p )
{
    uint32_t n = 0;
    for( ;; )
    {
        xQueueSend( q, &n, portMAX_DELAY );  /* 死等，必须送出去 */
        n++;
        vTaskDelay( pdMS_TO_TICKS(10) );
    }
}

void consumer( void *p )
{
    uint32_t val;
    for( ;; )
    {
        if( xQueueReceive( q, &val, portMAX_DELAY ) == pdPASS )
        {
            /* 拿到 val，干活 */
        }
    }
}
```

## 要点回顾

1. `xTicksToWait` 三态：0=不阻塞、N=超时、portMAX_DELAY=死等。
2. 阻塞 = 任务挂到等待名单 + 记录超时时刻；超时自动转 Ready 返回失败。
3. 唤醒顺序：优先级优先，同级 FIFO——低优先级可能饿死。
4. 所有 tick 级超时有 ±1 tick 量化误差。

<details>
<summary>Q1：portMAX_DELAY 真的会永远等吗？</summary>

看 `INCLUDE_vTaskSuspend` 配置：为 1 时 `portMAX_DELAY` 是无限等；
为 0 时它退化成一个很大的 tick 数（约 49 天，实际等于无限）。
**建议**：除非确定 `INCLUDE_vTaskSuspend=1`，否则关键路径用
`pdMS_TO_TICKS(大数值)` 明确超时，比 `portMAX_DELAY` 更可控。

</details>

<details>
<summary>Q2：阻塞时被 vTaskDelete 删了会怎样？</summary>

被删的任务从等待名单移除，函数不会返回——任务已经不存在了。
队列本身不受影响，等待名单只是引用任务句柄，不是所有权。
这正是 [3.6 句柄删除](../03-task-management/3.6-句柄删除与动态优先级.md)
里"删别人的任务要慎重"的原因之一：你不知道它正阻塞在哪。

</details>
