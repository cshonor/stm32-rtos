## 这一篇讲什么

队列单项大小创建时锁死。传 `uint32_t` 没问题，
传一个 200 字节的传感器帧呢？直接传值 = 每次收发各拷贝 200 字节。
本篇讲清**什么时候该传指针，以及传指针必须遵守的三条规矩**。

## 先用人话说一遍（新手铺垫）

队列默认传值，像**复印文件给对方**：你留原件随便改，对方拿复印件，
互不干扰。但文件厚了（200 字节的日志帧）复印又慢又费纸——这时
改传指针，等于**告诉对方"唯一原件锁在哪个柜子里"**，只递一把钥匙。

钥匙方案省了拷贝，但责任全转到设计上，三条规矩都是血的教训：

1. **柜子不能是你自己的抽屉**（栈上的局部变量）——你一下班
   桌子就被清空，对方拿钥匙开出来的是垃圾；
2. **钥匙给出去后你不能再碰原件**——对方正读着你改，读到一半
   新一半旧，就是数据竞争；
3. **原件最后谁销毁，事先写死**——没人销毁就是内存泄漏，
   两个人都销毁就是 double free（同一块内存被释放两次，堆管理器会被搞乱）。

本篇还附送一个特化工具：**只要最新值**的场景（"当前温度"），
用长度 1 的队列 + 覆盖写，旧值直接丢，不用排队不用决策。

| 术语 | 一句话解释 |
|---|---|
| 所有权（ownership） | "这块内存现在归谁写、归谁释放"的设计约定；传指针时必须显式规定 |
| 野指针 | 指向已被销毁/释放内存的指针；栈上传指针是经典制造法 |
| 数据竞争 | 两方同时摸同一块内存且至少一方在写，读到半新半旧的值 |
| `xQueueOverwrite` | 覆盖式写：队满也不失败，直接挤掉旧值——"只要最新"场景专用 |
| `xQueuePeek` | 读一份但不从队列移除；配 Overwrite 就是线程安全的"全局变量"（邮箱模式） |
| 内存池 / 双缓冲 | 静态数组轮换当数据源：零分配零碎片，代价是池深有限、消费慢会被覆写 |

## 传值 vs 传指针：一笔账

```c
typedef struct {
    uint32_t timestamp;
    int16_t  accel[3];
    int16_t  gyro[3];
    float    temperature;
    uint8_t  flags;
    uint8_t  reserved[7];
} sensor_frame_t;   /* ≈ 32 字节 */
```

| 方案 | 队列单项大小 | 每次收发拷贝 | 问题 |
|---|---|---|---|
| **传值** | `sizeof(sensor_frame_t)` = 32B | 进 32B + 出 32B | 大结构体拷贝慢；队列深度深时占 RAM 多 |
| **传指针** | `sizeof(void*)` = 4B | 进 4B + 出 4B | 指针指向的内存谁管？野指针？ |

32 字节传值还行——Cortex-M3 拷贝 32B 是 8 次 word 操作，纳秒级。
但 200 字节的日志帧、1KB 的网络包，传值就是浪费。
**经验法则：单项 > 16~32 字节时认真考虑传指针。**

## 传指针的三条铁律

```c
QueueHandle_t q = xQueueCreate( 5, sizeof( sensor_frame_t * ) );
```

传指针 = 队列里存的是**地址**，不是数据。
数据本体在别处——发送方和接收方都能摸到它。规矩：

### 规矩一：指针指向的必须是长寿命存储

```c
void sender( void )
{
    sensor_frame_t frame;           /* 栈上！ */
    frame.timestamp = 1234;
    sensor_frame_t *p = &frame;
    xQueueSend( q, &p, 0 );         /* ❌ 发送成功，但 frame 马上要销毁 */
}   /* ← frame 死了，队列里的指针是野指针 */
```

合法指向：**全局变量、静态变量（static 修饰：函数跑完也不销毁、一直占着内存）、堆分配**。

### 规矩二：发送后发送方不能再碰

```c
static sensor_frame_t frame;        /* 静态，长寿命 ✅ */
sensor_frame_t *p = &frame;
xQueueSend( q, &p, 0 );             /* 发出去 */
frame.timestamp = 5678;             /* ❌ 改了！接收方读到的是改后的值 */
```

发送后数据的**所有权**转移给接收方。发送方再写就是数据竞争。
要么发完后不再碰，要么用双缓冲/内存池轮换。

### 规矩三：谁负责释放，必须写死在设计里

```c
/* 方案 A：静态数组轮换（零分配，适合固定速率） */
static sensor_frame_t pool[4];
static int idx = 0;
sensor_frame_t *p = &pool[idx];
idx = (idx + 1) % 4;                /* 下次用下一格 */
/* 风险：消费慢了，pool 被覆写——需要流控 */

/* 方案 B：堆分配 + 接收方释放（灵活，但有碎片风险） */
sensor_frame_t *p = pvPortMalloc( sizeof( sensor_frame_t ) );
/* ...填数据... */
xQueueSend( q, &p, 0 );
/* 接收方用完后必须 vPortFree(p)，否则内存泄漏 */
```

**没有"自动管理"这回事**。C++ 的 shared_ptr（智能指针：自动计数、没人用就自动释放）在 FreeRTOS 的 C API 里
不存在——所有权是你的设计决策。

## 覆盖式队列：长度 1 + xQueueOverwrite

特殊场景：**只关心最新值**，旧值可以丢。
比如"当前温度"——读第 3 次温度时，前 2 次的值已经没意义了。

```c
QueueHandle_t q = xQueueCreate( 1, sizeof( float ) );  /* 长度 1 */
xQueueOverwrite( q, &temperature );  /* 满了不失败，直接覆盖 */
```

- 长度 1 + `xQueueOverwrite` = 永远成功，旧值被丢弃
- 接收方用 `xQueuePeek`（读了不删）配合，反复读最新值
- ISR 版本：`xQueueOverwriteFromISR`

**vs 普通队列（长度 N）**：普通队列满了发送方要决策（等/丢/超时），
覆盖式队列**不决策，直接丢旧的**——语义完全不同，选错了就是丢数据。

## 长度 1 的另一种用法：邮箱模式

```c
/* "最新配置"邮箱：永远只有一份，新配置来了就覆盖 */
QueueHandle_t cfg_mbox = xQueueCreate( 1, sizeof( config_t ) );

/* 配置更新方 */
xQueueOverwrite( cfg_mbox, &new_cfg );

/* 使用方：peek 读当前配置，不移除 */
xQueuePeek( cfg_mbox, &current_cfg, 0 );
```

`xQueuePeek` 读数据但**不从队列移除**——下次还能再读同一份。
配合 `xQueueOverwrite`，就是一个线程安全的"全局变量"。

## 要点回顾

1. 单项 > 16~32B 时考虑传指针；队列存地址不存数据。
2. 传指针三铁律：长寿命存储、发送后不碰、释放责任写死。
3. `xQueueOverwrite`（长度 1）= 只留最新值，旧值丢弃——"当前状态"场景专用。
4. `xQueuePeek` 读不删，配合覆盖式队列实现线程安全邮箱。

<details>
<summary>Q1：双缓冲轮换池 pool[4] 怎么防覆写？</summary>

核心是**消费速度必须快于生产速度 × 池深度**。pool[N] 意味着
最多容忍 N 条积压；第 N+1 条生产时第 1 条还没被消费就覆写了。
防御做法：发送前检查 `uxQueueSpacesAvailable` 或直接监控丢帧计数器，
超阈值就报警——这与 [4.3 FromISR](4.3-FromISR家族.md) 里 ISR 丢字节的
思路一致：**缓冲是缓冲，不是解药**。

</details>

<details>
<summary>Q2：能不能用 xQueueSend 传指向堆的指针，接收方 vPortFree？</summary>

可以，而且这是常见模式。但要确认 heap 方案支持 free
（heap_1 不支持！），本仓选 heap_4（见
[2.3 本仓选型 heap_4](../02-heap-memory/2.3-本仓选型heap_4.md)），
支持 alloc/free，可以做。风险：碎片 + 泄漏（接收方忘 free）。
高可靠性场景优先用静态池。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| 队列里存指针 = 存数据本体 | 以为 `xQueueSend` 会把指向的结构体一起拷进去 | 队列只拷 4 字节地址；数据本体必须活在静态 / 堆 / 全局存储里 |
| 发送完接着改发送缓冲区 | 静态变量长寿命，改了没关系 | 所有权已转移给接收方，再写就是数据竞争，对方读到半新半旧 |
| 内存释放有人自动管 | 习惯了带 GC / 智能指针的环境 | FreeRTOS C API 没有 shared_ptr；谁释放必须写死在设计里，且 heap_1 根本不支持 free |
| `xQueueOverwrite` 是"更可靠的 send" | 名字像普通发送的增强版 | 队满时不失败、直接丢旧值——"只要最新"场景专用，拿它传必须逐条送达的数据就是丢数据 |

## 代码自测

_注：本节代码按 FreeRTOS API 语义编写，未在本仓库环境实跑，上板验证见「验证路径」。_

```c
static QueueHandle_t temp_mbox;    /* 长度 1 邮箱：只留最新温度 */

void vSensorTask( void *p )
{
    float t = 20.0f;
    for( ;; )
    {
        t += 0.5f;                              /* 假装采样 */
        xQueueOverwrite( temp_mbox, &t );       /* 永远成功，旧值直接丢 */
        vTaskDelay( pdMS_TO_TICKS(100) );
    }
}

void vDisplayTask( void *p )
{
    float cur;
    for( ;; )
    {
        if( xQueuePeek( temp_mbox, &cur, 0 ) == pdPASS )  /* 读不删 */
        {
            printf( "temp %.1f\r\n", cur );
        }
        vTaskDelay( pdMS_TO_TICKS(1000) );      /* 慢 10 倍也无所谓 */
    }
}

void app_init( void )
{
    temp_mbox = xQueueCreate( 1, sizeof( float ) );
    xTaskCreate( vSensorTask, "sen", 256, NULL, 2, NULL );
    xTaskCreate( vDisplayTask, "disp", 256, NULL, 2, NULL );
}
```

**预期现象**：
- 显示任务每秒打印一次 `temp X.X`，数值每秒跳 5.0（采样 10 次只留最后一次）
- `xQueueOverwrite` 从不返回失败；旧温度被静默丢弃，这正是"只要最新"语义
- `xQueuePeek` 用 0 超时也几乎总成功——邮箱里永远有值可读

**验证路径**：F103 实机 + USART printf；对照实验 `02-freertos/02-queue`。

**常见翻车点**：
- 把邮箱模式用在"每条都要处理"的数据上——Overwrite 静默丢旧值，丢了无告警
- `xQueuePeek` 写成 `xQueueReceive`：值被取走，下一个读者读到旧数据或阻塞
