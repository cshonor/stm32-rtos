## 这一篇讲什么

ISR 里用普通 `xQueueSend` 是**未定义行为**。FreeRTOS 给中断上下文
准备了全套 `FromISR` 变体。本篇讲清两件事：
**为什么不能混用，以及 `pxHigherPriorityTaskWoken` 的正确用法。**

## 为什么 ISR 里不能用普通 API

普通 `xQueueSend` 在队列满时会**阻塞**——把当前任务挂到等待名单，
触发调度。但 ISR 上下文里**没有"当前任务"这个概念**：

- 中断是硬件抢来的执行流，不属于任何任务
- 阻塞一个 ISR = 阻塞整个中断系统 = 系统冻结
- 而且 ISR 里不能主动让出 CPU（PendSV 不能在中断里再触发调度）

所以 `FromISR` 版本的设计原则是：**绝不阻塞，只做数据搬运，
然后告诉调用者"刚才的操作有没有吵醒一个更高优先级的任务"。**

## API 对照表

| 任务上下文 | ISR 上下文 | 区别 |
|---|---|---|
| `xQueueSend` / `xQueueSendToBack` | `xQueueSendFromISR` / `xQueueSendToBackFromISR` | 无超时参数，多一个 `pxHigherPriorityTaskWoken` |
| `xQueueReceive` | `xQueueReceiveFromISR` | 同上 |
| `xQueueSendToFront` | `xQueueSendToFrontFromISR` | 同上 |
| `xQueueOverwrite` | `xQueueOverwriteFromISR` | 覆盖式，见 4.4 |

签名变化的核心：

```c
BaseType_t xQueueSendFromISR( QueueHandle_t xQueue,
                              const void * pvItemToQueue,
                              BaseType_t * pxHigherPriorityTaskWoken );
/* 没有 xTicksToWait——不能等，满就立刻返回 errQUEUE_FULL */
```

## pxHigherPriorityTaskWoken：醒来的人可能比你急

场景：UART 接收中断，ISR 把字节塞进队列。队列那头的消费者任务
（优先级 5）正在 Blocked 等数据。ISR 一塞，消费者变 Ready。

问题来了：**ISR 返回后，应该立刻切到那个优先级 5 的消费者吗？**

如果不切，CPU 回到被中断的低优先级任务（优先级 2），
消费者要等下一个 tick 才能跑——**数据已经到了，人还没醒，白等**。

`pxHigherPriorityTaskWoken` 就是内核给你的提示：

```c
void USART1_IRQHandler( void )
{
    uint8_t byte = USART1->DR;
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    xQueueSendFromISR( rx_queue, &byte, &xHigherPriorityTaskWoken );

    /* 如果唤醒了一个更高优先级任务，请求在 ISR 退出时切换 */
    portYIELD_FROM_ISR( xHigherPriorityTaskWoken );
}
```

- 初始化为 `pdFALSE`
- 内核在唤醒了更高优先级任务时把它置为 `pdTRUE`
- `portYIELD_FROM_ISR(pdTRUE)` → 触发 PendSV，ISR 返回时**直接切到高优先级任务**，不回到被中断的那个

**如果被唤醒的任务优先级不高于当前运行的任务**，
内核不会动这个变量——不用切，回了再说。

## FromISR 里满了怎么办

队列满，`xQueueSendFromISR` 返回 `errQUEUE_FULL`。
ISR 里不能等，所以**数据就丢了**——这是 ISR 设计的硬约束：

```c
if( xQueueSendFromISR( rx_queue, &byte, &pxHigherPriorityTaskWoken ) != pdPASS )
{
    /* 丢了。计数器++，上层定期看丢了多少 */
    dropped_bytes++;
}
```

**对策不是加大队列，是让消费端更快**（提高优先级、用 DMA、
减少中断频率）。队列深度是缓冲，不是解药。

## 中断优先级与 configMAX_SYSCALL_INTERRUPT_PRIORITY

FreeRTOS 把中断分成两档（Cortex-M 上）：

| 优先级 | 能调 FromISR API？ | 说明 |
|---|---|---|
| **高于** `configMAX_SYSCALL_INTERRUPT_PRIORITY`（数值更小） | ❌ 不能 | 完全不受内核管理，裸跑 |
| **等于或低于**它（数值更大） | ✅ 能 | 受内核管理，可以安全调 FromISR |

F103 上 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 默认 5（0~15 数值制），
即**优先级数值 ≥5 的中断才能调 FromISR API**。
更快的中断（0~4）彻底裸奔，不能碰任何内核对象。

裸机篇 [ch10.3 NVIC 优先级分组](../../../01-stm32/book-notes/10-interrupts/README.md)
讲过 Cortex-M 的优先级数值制——数值小 = 硬件优先级高，这个反直觉
在 FreeRTOS 里再次踩人。

## 要点回顾

1. ISR 里用普通队列 API = 未定义行为；必须用 FromISR 变体。
2. FromISR 无超时参数，满就立刻返回失败——ISR 不能等。
3. `pxHigherPriorityTaskWoken` + `portYIELD_FROM_ISR`：让被唤醒的高优先级任务在 ISR 退出时立即接手。
4. 中断优先级数值 ≥ `configMAX_SYSCALL_INTERRUPT_PRIORITY` 才能调 FromISR。

<details>
<summary>Q1：为什么 FromISR 里也要拷贝数据，不能直接存指针？</summary>

可以存指针——队列的单项大小设为 `sizeof(void*)` 就行，
见 [4.4 传指针的代价与规矩](4.4-传指针的代价与规矩.md)。
但 ISR 里**不能**存指向 ISR 局部变量的指针：ISR 返回后栈帧就没了，
指针变野指针。要传指针，指向的必须是静态/堆/全局存储。

</details>

<details>
<summary>Q2：portYIELD_FROM_ISR 在所有移植层都一样吗？</summary>

不一样。Cortex-M 上它是 `portEND_SWITCHING_ISR` 的别名，
本质是触发 PendSV。某些移植层（如某些 ARM7）需要显式调用
`vTaskSwitchContext()`。用的时候查对应 port 的 `portmacro.h`，
但 Cortex-M（F103/F4/H7）统一用 `portYIELD_FROM_ISR`。

</details>
