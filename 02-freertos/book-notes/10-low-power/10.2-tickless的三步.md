# 10.2 tickless 的三步：算睡眠时间 → 停 tick 睡觉 → 醒来补 tick

## 这一篇讲什么

`portSUPPRESS_TICKS_AND_SLEEP(xExpectedIdleTime)` 是 tickless 的全部。
内核算出"预期空闲 xExpectedIdleTime 个 tick"后调用它，
它分三步走完一轮睡眠。本篇逐步拆开，并讲清**补 tick** 这个
最容易被忽略的环节。

## 第一步：算睡眠时间

进函数前内核已经给出 `xExpectedIdleTime`：
所有阻塞任务/定时器里**最近的到期时刻**距现在的 tick 数。
port 实现先做两道防护：

```c
/* 伪代码，对应官方 Cortex-M port 的实现逻辑 */
if( xExpectedIdleTime < 最小阈值 )   /* 睡太短不值当：进出睡眠本身耗时耗电 */
    return;                          /* 放弃本次睡眠，正常走 tick */

把唤醒定时器编程到 xExpectedIdleTime tick 之后;
```

F103 官方参考实现的做法：**停掉 SysTick，改用 SysTick 自己
重装成"长定时器"**（把重装载值从 1ms 拉长到 N ms）——
不用额外定时器。想睡更久或更深（Stop 模式）时可换成 RTC 闹钟。

## 第二步：停 tick 睡觉

```c
__disable_irq();          /* 临界区：防止刚编程完就被打断 */
检查一遍"是否真的还空闲";  /* 可能有 ISR 刚唤醒了任务，那就放弃 */
__WFI();                  /* 或更深的睡眠（下篇） */
__enable_irq();
```

睡眠期间**没有周期 tick 中断**，内核的 tick 计数原地不动——
这就是"tickless"（无 tick）的字面意思。

## 第三步：醒来补 tick

唤醒有两种情形，补偿方式不同：

| 唤醒来源 | 实际睡了多久 | 补偿方式 |
|---|---|---|
| 定时唤醒（就是编程的那个唤醒源） | = xExpectedIdleTime | 直接从定时器计数读出来，补相应 tick |
| **提前唤醒**（别的中断，如按键/UART） | < 预期值 | 从定时器剩余值反推实际睡了多少，**按实际补** |

补偿调用：

```c
vTaskStepTick( xActualTicks );   /* 把 tick 计数一次性推进 xActualTicks */
```

`vTaskStepTick` 和正常 tick 中断里的 `xTaskIncrementTick` 干一样的事
（推进计数、唤醒到期任务），只是**一次推进 N 格**；补完之后逻辑时间
严丝合缝——`vTaskDelay(100)` 不会因中间睡一觉而多等或少等。

**不补会怎样**：tick 计数停在入睡前，所有基于 tick 的超时、延时、
软件定时器全部"时间变慢"——这是自写 tickless port 的头号坑。

## 全流程一图

```
空闲任务
  └→ eTaskConfirmSleepModeStatus()：确认能睡（无就绪任务、
  │    无"禁睡"的调度器挂起状态）→ 得到 xExpectedIdleTime
  └→ portSUPPRESS_TICKS_AND_SLEEP( N )
       ① N 太小 → 直接返回（正常 tick）
       ② 停 SysTick / 重编程唤醒源到 N tick 后
       ③ 关中断 → 复查空闲 → WFI 睡下
       ④ 被唤醒（到点 or 提前）
       ⑤ 读定时器算实际睡眠 T、恢复 SysTick 周期配置
       ⑥ vTaskStepTick( T )  ← 补 tick
  └→ 调度恢复，到期的任务变 Ready
```

## 谁负责实现

- 官方 Cortex-M port 自带 `portSUPPRESS_TICKS_AND_SLEEP` 的
  **弱符号参考实现**（睡 Sleep 模式，SysTick 拉长）。
- 想睡 Stop/Standby、换 RTC 做唤醒源 → **自己覆写这个宏/函数**，
  三步骨架不变，改的是"哪个定时器、睡多深"（下篇）。

## 要点回顾

1. 三步：算 N → 停 tick 睡 N → 醒后 `vTaskStepTick` 补 N。
2. 提前唤醒按**实际**睡眠时长补，不是按预期补。
3. 不补 tick = 全系统时间变慢，这是自写 port 的头号坑。
4. 睡眠太短不值得，port 实现里有最小阈值直接放弃。

<details>
<summary>Q1：补 tick 时一口气唤醒多个到期任务，顺序乱吗？</summary>

不乱。`vTaskStepTick` 内部就是循环调用推进逻辑，
到期任务按 tick 顺序逐个从延时名单移到就绪名单，
同优先级的相对顺序保持 FIFO。补一格和补 N 格语义一致。

</details>

<details>
<summary>Q2：睡眠期间来的 UART 数据会丢吗？</summary>

睡 Sleep 模式不会——外设时钟还在，UART 中断正常唤醒 CPU，
ISR 照常跑（FromISR API 收数据），只是这次唤醒算"提前唤醒"，
补 tick 按实际时长算。睡 Stop 模式时高速外设时钟停了，
要先醒时钟才能收——这是下篇选档位的核心权衡。

</details>
