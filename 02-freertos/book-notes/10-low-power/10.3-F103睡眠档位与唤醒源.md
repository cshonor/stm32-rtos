## 这一篇讲什么

tickless 的三步骨架不变，但"睡多深、用什么叫醒"是 STM32 平台决策。
本篇对照 F103 的三档睡眠各关了什么、能被什么唤醒，
以及和 tickless 配对时的取舍。最后说清**谁不该开 tickless**。

## F103 三档睡眠速查

| 档位 | 关了什么 | 保留什么 | 唤醒源 | 唤醒后时钟 |
|---|---|---|---|---|
| **Sleep** | CPU 时钟（HCLK） | 所有外设时钟、SRAM、寄存器 | 任意中断 | 不变，立即续跑 |
| **Stop** | CPU + 大部分外设时钟（HSE/HSI 停） | SRAM、寄存器、RTC、低速时钟 | EXTI 线（含 RTC 闹钟、EXTI 引脚） | 回 HSI，要重新切 PLL |
| **Standby** | 几乎全断（1.8V 域断电） | 仅备份域、RTC、WKUP 引脚 | RTC 闹钟、WKUP 上升沿、NRST | **复位重启**（SRAM 全丢） |

裸机篇 [ch19 SysTick](../../../01-stm32/book-notes/19-systick-and-timer/README.md)
讲过 SysTick 挂在 CPU 时钟域——Sleep 下 SysTick 也停了，
Stop 下更是整个停。所以 tickless 里"停 tick"在硬件上是自然结果，
关键是**另找一个还活着的钟来定时唤醒**。

## 与 tickless 的配对

| 档位 | 唤醒定时器选型 | 与 tickless 的配合 |
|---|---|---|
| Sleep | SysTick 自己（拉长重装载） | 官方参考实现的默认做法，改动最小 |
| Stop | RTC 闹钟（32.768kHz LSE 还在走） | 自写 `portSUPPRESS_TICKS_AND_SLEEP`：停 SysTick、编程 RTC、WFI 进 Stop、醒后重配时钟再补 tick |
| Standby | RTC 闹钟 / WKUP | 不适合 tickless——唤醒即复位，RTOS 现场全无，属于"关机"语义 |

**Stop 档的两个额外动作**（自写 port 时必须处理）：

1. **唤醒后时钟重建**：Stop 醒来回 HSI 8MHz，要重新使能 HSE+PLL
   回 72MHz，这期间别补 tick——先把系统时钟扶正再算时间。
2. **唤醒源先接 EXTI**：RTC 闹钟、UART 唤醒线都要映射到 EXTI，
   Stop 只认 EXTI/NRST。

```c
/* Stop 版 portSUPPRESS_TICKS_AND_SLEEP 骨架（概念伪代码） */
停 SysTick;
编程 RTC 闹钟 = 现在 + N tick;
进入 Stop（PWR 寄存器 + __WFI）;
/* ---- 醒来 ---- */
重配系统时钟回 72MHz;
读 RTC 算实际睡了 T;
恢复 SysTick;
vTaskStepTick( T );
```

## 谁不该开 tickless

| 场合 | 原因 |
|---|---|
| 微秒级精度的周期任务 | tickless 的睡眠粒度是 tick（通常 1ms），且进/出睡眠有不可忽略的执行开销，µs 级时序会被抖坏 |
| 高吞吐 ISR 流（如高速串口无 DMA） | Stop 档下外设时钟停，头几个字节可能在时钟重建期间丢掉 |
| 调试阶段 | 睡着后 SWD 连接常断（下详），开发期建议关掉 |
| 任务几乎不空闲的系统 | 每次算出来 N 都小于阈值，纯白忙 |

**调试器问题**：F103 默认进低功耗后调试域断电，OpenOCD 会丢连接。
置 `DBGMCU->CR` 的 `DBG_SLEEP` / `DBG_STOP` / `DBG_STANDBY` 位，
让调试时钟在睡眠中保持——**代价是省电效果打折**，所以这是
调试期开关，量产固件别开。

## 要点回顾

1. Sleep 配 SysTick 拉长（官方默认）；Stop 配 RTC 闹钟（自写 port）；Standby 不配对 tickless。
2. Stop 唤醒后先重建时钟，再补 tick。
3. µs 级精度、密集 ISR 流、调试期——别开 tickless。
4. 调低功耗时记得 `DBGMCU` 的 DBG_* 位，否则调试器一睡就断。

<details>
<summary>Q1：tick 是 1ms，RTC 是 32.768kHz，补 tick 的精度够吗？</summary>

RTC 分辨率约 30.5µs，远细于 1ms tick，换算回 tick 时取整
误差不足 1 tick。注意 RTC 与 SysTick 是**两个独立时钟源**，
长期运行会有 ppm 级漂移——对 tick 级超时可忽略，
做日历级计时才需要另行校准。

</details>

<details>
<summary>Q2：用了 HAL 库，HAL 的 1ms 时基和 FreeRTOS tick 冲突吗？</summary>

CubeMX 生成的工程通常把 HAL 时基从 SysTick 挪到某个 TIM
（正因为 SysTick 归 FreeRTOS 用）。tickless 睡眠期间如果那个
TIM 也停了，HAL_GetTick 会停走——HAL 侧超时逻辑会受影响。
方案：HAL 时基也改挂 RTC 唤醒，或在 port 层同步补偿 HAL 计数。

</details>
