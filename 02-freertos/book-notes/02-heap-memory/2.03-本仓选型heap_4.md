## 这一篇讲什么

选型结论一句话：**本仓选 heap_4**。这一篇把理由钉死，
再解决真正的工程问题：F103 只有 20K RAM，`configTOTAL_HEAP_SIZE` 该写多大？

## 为什么是 heap_4

| 候选 | 排除/入选理由 |
|---|---|
| heap_1 | ❌ 学习阶段要反复创建/删除任务做实验，"只分不还"会把 heap 耗光 |
| heap_2 | ❌ 过时，不合并碎片 |
| heap_3 | ❌ 继承 libc malloc 的不确定性（2.01 四宗罪） |
| **heap_4** | ✅ 动态创建/删除 + 碎片缓解，官方默认，实验全够 |
| heap_5 | ⏸ F103 单段 20K SRAM 用不上多段堆；**F407 阶段再议**（128K SRAM + 64K CCM） |

## configTOTAL_HEAP_SIZE：20K RAM 的预算案

F103RB：20K SRAM。花钱的项目：

```
SRAM 总账（20K = 20480 B）
├── .data + .bss（你的全局变量）        实测：blink 只有 16 B，随应用涨
├── 中断栈（MSP）                       链接脚本里 _estack 定顶，向下长；预算 1K
├── ucHeap[configTOTAL_HEAP_SIZE]       ← 本章主角，heap_4 的全部本钱
│     ├── 每个任务：TCB（约 100+ B）+ 任务栈（xTaskCreate 第三个参数 ×4 字节）
│     ├── 每个队列：结构体 + 存储区（长度 × 项大小）
│     └── 内核对象（信号量/定时器……）
└── （裸机 newlib 的 _sbrk 堆：进了 RTOS 就该让它失业，见 2.1）
```

01-hello-task 的最小预算（两个 LED 任务 + 空闲任务 + 定时器守护任务）：

| 对象 | 估算 | 备注 |
|---|---|---|
| 2 个 LED 任务栈 | 2 × 128 字 × 4 B = **1024 B** | 128 字是书中最小任务的常见起点 |
| 2 个任务 TCB | ~2 × 120 B ≈ **240 B** | TCB 结构体随配置略有浮动 |
| 空闲任务（栈+TCB） | 栈=configMINIMAL_STACK_SIZE（一般 130 字）≈ **640 B** | 内核自动建 |
| 定时器守护任务 | 类似空闲 ≈ **640 B**（若启用软件定时器） | configUSE_TIMERS=1 才有 |
| 队列等预留 | **1~2K** | 02-queue 马上要用 |

合计约 4~5K → **`configTOTAL_HEAP_SIZE` 取 8K（8192）宽松起步**，
剩下 ~11K 给 MSP 栈余量、.bss 增长和调试期的 printf 缓冲。

**定大小的方法论**：先按上表算理论值 → 上调一档取整 →
实验里用 `xPortGetFreeHeapSize()` 和 `uxTaskGetStackHighWaterMark()`
把真实水位读出来，**再向下收紧**。这才是最终值；拍脑袋的值只是开工值。

## 分配失败怎么抓（配置清单）

```c
/* FreeRTOSConfig.h 关键三行 */
#define configTOTAL_HEAP_SIZE        ( ( size_t ) ( 8 * 1024 ) )
#define configCHECK_FOR_STACK_OVERFLOW   2   /* ch11 详解，方法二 */
/* malloc 失败钩子：创建对象失败时内核回调这里 */
void vApplicationMallocFailedHook( void )
{
    taskDISABLE_INTERRUPTS();
    for( ;; );   /* 卡死在这——调试器里一眼看到调用栈 */
}
```

配上钩子之后，`xTaskCreate` 返回 `pdFAIL` 就不是"静默失败"，
而是**在分配现场当场停车**——2.1 说的第四宗罪被彻底拆掉。

## 要点回顾

1. 本仓选 heap_4：动态实验 + 碎片缓解；heap_5 留给 F407 阶段。
2. `configTOTAL_HEAP_SIZE` 先算后拍（8K 起步），再用水位 API 收紧。
3. `vApplicationMallocFailedHook` + `configCHECK_FOR_STACK_OVERFLOW=2`
   是开车前的安全带，01 实验落地当天就配。

<details>
<summary>Q1：任务栈在 ucHeap 里，MSP（中断栈）在哪？</summary>

MSP 栈**不在** ucHeap 里——它就是链接脚本里 `_estack` 往下那片"什么都没占用"的 RAM。
所以 SRAM 预算里要给 MSP 留够（ISR 嵌套最深时的用量），
这部分不参与 heap 分配，超了就是栈溢出去踩 .bss/ucHeap，
死相会很难看（数据被悄悄改写而不是立刻 HardFault）。

</details>

<details>
<summary>Q2：heap 用不完的部分浪费了怎么办？</summary>

不浪费——`configTOTAL_HEAP_SIZE` 本来就是你自己拍的数，
实验中用 `xPortGetFreeHeapSize()` 读到"历史最低剩余"
（`xPortGetMinimumEverFreeHeapSize()`）后把它收紧即可。
**先宽后紧**是标准流程，反着来（先紧后爆）才难受。

</details>
