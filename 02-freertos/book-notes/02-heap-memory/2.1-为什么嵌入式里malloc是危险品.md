## 这一篇讲什么

PC 上 `malloc/free` 是日常；裸机篇 [ch13](../../../01-stm32/book-notes/13-dynamic-memory/README.md)
也见过 `_sbrk` 怎么从链接脚本给的堆里切内存。那为什么 FreeRTOS 要自带分配器，
还一口气给了五个？因为 **malloc 在嵌入式实时语境下有四个硬伤**。

## 先用人话说一遍（新手铺垫）

`malloc` 在 PC 上好用，是因为 PC 内存以 GB 计、程序慢几微秒没人
在乎。单片机 RAM 只有 20K、电机控制环一拍都不能晚，这时候 malloc
就像一家**不挂牌价的裁缝店**：这次裁布花多久没准（耗时不定）、
裁多了剩一堆用不上的边角料（碎片）、店里一次只接待一位客人
（中断里不能进）、裁错了还不吱声（返回 NULL 等你踩雷）。

FreeRTOS 的回答很干脆：**不用这家店，自己砌一个尺寸固定的布柜**
（`ucHeap` 静态数组，编译时大小就定死），再配五种不同脾气
的管理员（heap_1~heap_5，下一篇选型）。柜子的边界是编译期画死的，
所以裸机时代"堆长过头踩到栈"这个老大难，在结构上就不存在了。

| 术语 | 一句话解释 |
|---|---|
| TCB | 任务控制块：内核给每个任务建的"档案卡"（栈指针、优先级、状态），约一百多字节 |
| 碎片化 | 堆里空闲总量够、但都是不相邻的小块，申请大块时失败的现场 |
| 可重入 / 线程安全 | 函数被多个任务（或中断）同时调用也不出错的性质；malloc 靠加锁硬凑出来 |
| 挂起调度器 | 暂时禁止任务切换（比关中断温和，中断照常响应），`pvPortMalloc` 用它做保护 |
| malloc failed hook | 分配失败时内核回调的函数，在里面卡死=当场抓住案发现场 |

## malloc 的四宗罪

| # | 毛病 | 后果 |
|---|---|---|
| 1 | **不确定耗时** | glibc 的 malloc 要遍历空闲链表、可能合并/分裂块，耗时随堆状态变化——实时系统里"这次调用花多久"必须是已知数 |
| 2 | **碎片化** | 长期分配/释放不同大小的块，堆被切成筛子：总空闲很多、单块都不够，分配开始莫名失败 |
| 3 | **不可重入 / 线程不安全的代价** | newlib（嵌入式常用的 C 标准库实现）的 malloc 靠锁保证多任务安全，ISR（中断服务函数）里调 = 未定义行为（C 标准不保证结果，可能崩也可能"看着正常"） |
| 4 | **失败难察觉** | 返回 NULL 没人检查 → 解引用（跟着指针去读写它指向的内存）→ HardFault（Cortex-M 的致命错误异常，多为访问非法内存），现场离事故原点十万八千里 |

## FreeRTOS 的回答：内核不碰你的 malloc

FreeRTOS 内核分配 TCB、栈、队列时**不调用 C 库 malloc**，
而是调用自己的 `pvPortMalloc()`——这个函数由你选编的 `heap_x.c` 提供：

```
xTaskCreate()
   → pvPortMalloc(TCB) + pvPortMalloc(栈)     ← 走 heap_x.c，不走 _sbrk
```

于是四个毛病被逐个拆解：

- **耗时确定**：heap_4 用首次适配（沿空闲块从头找，第一个够大的就用）+ 相邻块合并，行为简单可分析（不是 O(1)，但可上界）；
- **碎片可控**：选合适的 heap_x（下一篇），或者干脆禁释放（heap_1）；
- **重入安全**：`pvPortMalloc` 内部挂起调度器做临界保护，任务侧随便调；
  （ISR 侧规矩不变：内存分配本来就不是 ISR 该干的活）
- **失败显式**：返回 NULL + 可配 `malloc failed hook`，在钩子函数里 `configASSERT(0)` 当场抓住。

## 与裸机篇 ch13 的对照

| | 裸机（ch13） | FreeRTOS（本章） |
|---|---|---|
| 分配器 | newlib malloc + `_sbrk` | `pvPortMalloc` + heap_x.c |
| 堆从哪来 | 链接脚本 `_end` ~ 栈底之间 | `configTOTAL_HEAP_SIZE` 定死的静态数组 `ucHeap[]` |
| 栈/堆碰撞检查 | 靠自己量 | heap 是编译期定长数组，**物理上不可能撞任务栈** |
| 释放 | free（碎片风险） | 看选哪个 heap_x（下篇） |

注意第三行那个区别：裸机的堆和栈是**同一片 RAM 两头长**，
堆长过头就踩栈；FreeRTOS 的 `ucHeap` 是一个**定长静态数组**，
链接时大小就定死——堆永远长不出数组边界。这是结构性的安全提升。

## 要点回顾

1. malloc 四宗罪：耗时不定、碎片、重入代价、失败难察。
2. FreeRTOS 内核全走 `pvPortMalloc`，由 heap_x.c 提供，与 C 库 malloc 完全脱钩。
3. `ucHeap` 是定长静态数组，堆撞栈这个裸机老大难在结构上消失。

<details>
<summary>Q1：那应用程序里还能用 malloc 吗？</summary>

能，但不推荐混用。混用的坑：malloc 从 `_sbrk` 的区域拿内存，
而链接脚本给不给它留地方、留多少，是你自己的责任；
FreeRTOS 的 ucHeap 又是另一块。两片"堆"都要预算，总量很容易超 RAM。
**规矩：进了 RTOS 的世界，一律 `pvPortMalloc/vPortFree`，让 malloc 失业。**

</details>

<details>
<summary>Q2：heap_x.c 五个文件能一起编进工程吗？</summary>

不能——它们定义同名函数（`pvPortMalloc/vPortFree`），一起编链接冲突。
**五选一**，写在 Makefile 的源文件清单里，选错了换要重编。
选型见下一篇。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| 应用里 malloc 和 pvPortMalloc 混着用 | "都是分配内存，顺手就行" | malloc 从 `_sbrk` 区域拿、ucHeap 是另一块，两片堆都要预算，总量很容易超 RAM；进了 RTOS 一律 `pvPortMalloc/vPortFree` |
| heap_1~heap_5 全编进工程慢慢挑 | "都编上，运行时选" | 五个文件定义同名函数 `pvPortMalloc/vPortFree`，一起编直接链接冲突；只能五选一，写在 Makefile 源清单里 |
| `pvPortMalloc` 在中断里也能调 | 它内部有保护，ISR 应该也行 | 保护方式是挂起调度器，只保证任务侧安全；ISR 里分配内存本来就不是该干的活 |
| 堆长过头会踩任务栈 | 裸机经验：堆栈同一片 RAM 两头长 | FreeRTOS 的 `ucHeap` 是编译期定长静态数组，物理上长不出边界——堆撞栈在结构上不存在 |

## 衔接

## 代码自测

_注：本节代码按 FreeRTOS API 语义编写，未在本仓库环境实跑，上板验证见「验证路径」。_

```c
/* 演示：内核风格的动态分配——pvPortMalloc/vPortFree，失败要显式抓 */
static void vAllocTask( void *pv )
{
    uint8_t *p = pvPortMalloc( 256 );       /* 走 heap_4，不走 _sbrk */
    if ( p == NULL )
    {
        /* 不查 NULL 就解引用 = HardFault，现场离事故原点很远 */
        for ( ;; );
    }
    p[0] = 0xAA;                            /* 正常使用 */
    vPortFree( p );                         /* 用完就还 */
    p = NULL;                               /* 防悬空指针 */

    for ( ;; )
    {
        vTaskDelay( 100 );
    }
}

int main( void )
{
    xTaskCreate( vAllocTask, "alloc", 128, NULL, 1, NULL );
    vTaskStartScheduler();
    for ( ;; );
}
```

**预期现象**：
- 正常跑：任务每 100ms 空转一次，分配/释放无异常。
- 把申请量改成超过 `configTOTAL_HEAP_SIZE`：`pvPortMalloc` 返回 NULL，停在自己的死循环里（若配了 malloc failed hook 则停在钩子里）。
- 注释掉 NULL 检查：解引用空指针 → HardFault，错误现场指向 `p[0]=` 那行而非分配点。

**验证路径**：F103 实机 + USART printf 打印返回值；heap 选 heap_4。

**常见翻车点**：
- 工程里同时编了两个 heap_x.c → 链接报同名符号冲突。
- 老代码里的 `malloc` 没换干净 → `_sbrk` 区域和 ucHeap 双重占 RAM。
- ISR 里调 `pvPortMalloc` → 行为未定义。
