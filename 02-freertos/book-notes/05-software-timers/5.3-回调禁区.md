# 5.3 回调禁区：为什么不能阻塞、阻塞了会拖死谁

> 书 5.3–5.4 节 · 对应实验：后续追加（骨架未建）
> 章导航：[README](README.md) ｜ 上一篇：[5.2 定时器命令队列](5.2-定时器命令队列.md)
>

## 这一篇讲什么

定时器回调函数只有一条纪律，但违反的代价是系统级的：
**回调里绝对不能进入 Blocked 态。**本篇讲清为什么、
哪些 API 暗藏阻塞、以及"回调里确实要干重活"的正规出路。

## 为什么阻塞是灾难

所有定时器回调**串行跑在同一个守护任务里**（[5.1](5.1-单次与周期定时器.md)）。
回调 = 守护任务代码的一部分。所以：

```c
void vBadCallback( TimerHandle_t t )
{
    vTaskDelay( pdMS_TO_TICKS(1000) );   /* 守护任务 Blocked 1 秒！ */
}
```

这 1 秒内：守护任务挂着 → 其他所有到点定时器的回调**全部排不上**
→ 命令队列也**没人消费**（[5.2](5.2-定时器命令队列.md)），
应用任务的 `xTimerStart` 开始返回 pdFAIL。

**一个回调阻塞 = 拖死全部定时器 + 定时器 API 开始失败。**
这不是一个定时器变慢，是整个定时器子系统停摆。

## 暗藏阻塞的 API 清单

回调里禁用的不是一个函数，是一类——**任何 xTicksToWait ≠ 0 的调用**：

| API | 陷阱形态 |
|---|---|
| `vTaskDelay` / `vTaskDelayUntil` | 明文阻塞 |
| `xQueueReceive(q, portMAX_DELAY)` | 等数据 = 阻塞 |
| `xQueueSend(q, 非0等待)` | 队列满时等空位 = 阻塞 |
| `xSemaphoreTake(sem, 非0等待)` | 等信号量 = 阻塞 |
| `xTaskNotifyWait(... 非0等待)` | 等通知 = 阻塞 |
| 定时器 API 自身带非零等待 | 队列满时等 = 阻塞 |

**允许**的等价物：把等待参数全改成 `0`（"试一把，不行就走"）。
例如 `xQueueSend(q, &x, 0)` 在回调里完全合法——发不进就丢弃/计数，
下次再说。

## 重活的正规出路：defer to task

回调里确实要干慢活（写 flash、打印长日志、复杂计算），
标准模式是**回调只做通知，活交给专用任务**：

```c
void vGoodCallback( TimerHandle_t t )
{
    /* 只发通知，零阻塞；处理任务自己在 Blocked 态等着 */
    xTaskNotifyGive( xWorkerTask );
}

void vWorkerTask( void * p )
{
    for( ;; )
    {
        ulTaskNotifyTake( pdTRUE, portMAX_DELAY );  /* 这里阻塞没问题 */
        do_the_slow_work();                          /* 慢活随便干 */
    }
}
```

这正是 [6.1](../06-interrupt-management/6.1-二值信号量中断同步.md)
"延迟中断处理"的同款模式，只是触发源从 ISR 换成了定时器回调。
队列（[4.3](../04-queue-management/4.3-FromISR家族.md)）也能当这个通道，
按"要不要传数据"选：只报信用通知，要传参数用队列。

## 与 ISR 纪律的对照

| | ISR | 定时器回调 |
|---|---|---|
| 能否阻塞 | 绝对不能（没有任务上下文） | 绝对不能（会拖死守护任务） |
| 能调什么 API | 只能 FromISR 家族 | 普通 API 可以，但等待参数必须为 0 |
| 优先级红线 | 受 configMAX_SYSCALL_INTERRUPT_PRIORITY 管 | 不受（它是任务上下文） |
| 重活出路 | 延迟处理（信号量/队列唤醒任务） | 同款：通知/队列唤醒任务 |

注意第二行：回调是任务上下文，所以**可以用普通 API**，
只是等待时间必须为 0——这是和 ISR 最容易混淆的点。

## 要点回顾

1. 回调 = 守护任务的代码；一个回调阻塞 = 定时器子系统整体停摆。
2. 禁区不是某个函数，是"任何非零等待"——等待参数一律写 0。
3. 重活出路：回调里 xTaskNotifyGive / xQueueSend(...,0)，慢活交给专用任务。
4. 回调是任务上下文：普通 API 可用、无中断红线，但纪律比照 ISR。

<details>
<summary>Q1：回调里打印调试信息（printf/UART）行不行？</summary>

阻塞式 UART 发送本质是"等发送完成"，违反纪律。
行得通的做法：把格式化好的字符串 `xQueueSend(...,0)` 给日志任务，
由它慢慢发（裸机篇 [ch09](../../../01-stm32/book-notes/09-uart-serial/README.md)
的 DMA 发送思路在此直接复用）。发不进就丢日志保系统。

</details>

<details>
<summary>Q2：怎么查出"哪个回调在捣乱"？</summary>

给每个回调首尾打 tick 计数（`xTaskGetTickCount` 差值），
耗时超预期的回调就是它；或开 `configUSE_TICK_HOOK` 观察守护任务
心跳是否停摆。具体手段与数据待实验验证。

</details>
