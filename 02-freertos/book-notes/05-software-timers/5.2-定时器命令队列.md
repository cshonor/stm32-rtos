# 5.2 定时器命令队列：start/stop/reset 都是"发消息"

## 这一篇讲什么

`xTimerStart()` 并不直接"启动定时器"——它往一条队列里
**发一条命令**，由守护任务取出来执行。理解这条命令队列，
定时器 API 的所有怪行为（返回值、FromISR 变体、阻塞参数）全都顺了。

## 机制全景

```
你的任务/ISR                     内核                         守护任务
─────────────                  ──────────                    ──────────
xTimerStart(t, wait)  ──►  往命令队列塞一条                取出命令：
  {cmd=START, t}      ──►  {START, 定时器t, 时刻}   ──►    把 t 挂进"活跃名单"
                                                            到点后执行回调
```

- 命令队列就是一条普通队列（[ch04](../04-queue-management/README.md) 的机制），
  深度 = `configTIMER_QUEUE_LENGTH`，由内核自动创建，你拿不到句柄
- **所有定时器 API 都是"发命令"**：start、stop、reset、
  change period、delete——无一例外
- 真正操作定时器数据结构的只有守护任务一个执行者
  → **天然免锁**：没有多任务并发改名单的问题

## 为什么这样设计

定时器的活跃名单若允许任意任务直接改，就要全套临界区保护；
改成"单写者（守护任务）+ 消息队列"后：

1. 定时器内部数据结构零锁，逻辑简单；
2. ISR 里也能安全操作定时器——发消息不需要碰名单；
3. 所有操作天然排序：命令按到达顺序执行，语义确定。

## API 对照：为什么每个都有 FromISR 版

| 任务上下文 | ISR 上下文 |
|---|---|
| `xTimerStart` | `xTimerStartFromISR` |
| `xTimerStop` | `xTimerStopFromISR` |
| `xTimerReset` | `xTimerResetFromISR` |
| `xTimerChangePeriod` | `xTimerChangePeriodFromISR` |
| `xTimerDelete` | （无 FromISR 版，删除请避开 ISR） |

FromISR 版存在的原因和 [4.3 FromISR 家族](../04-queue-management/4.3-FromISR家族.md)
完全一样：ISR 里不能阻塞，而普通版的 `xTicksToWait` 参数意味着
"队列满时可以等"——ISR 里不允许等。

## xTicksToWait 参数：等的是"队列空位"

```c
/* 命令队列若满，最多等 100ms 腾位置；仍满则放弃，返回 pdFAIL */
if( xTimerStart( t, pdMS_TO_TICKS(100) ) == pdFAIL )
{
    /* 命令没发出去——定时器状态没变，不是"启动失败"，是"没排上队" */
}
```

两个易错点：

- **返回值 pdPASS 只代表"命令进队列了"**，不代表回调已执行——
  执行是守护任务稍后的事
- 调度器启动前调定时器 API，`xTicksToWait` 被忽略（此时不能阻塞），
  队列满了就直接失败

## 队列深度配多少

`configTIMER_QUEUE_LENGTH` 决定能积压多少条未处理命令。
突发的多路 start/reset（比如中断密集期用 FromISR 版）会快速占满。
配 10 是常见起点；够不够看应用并发度，待实验验证。
队列满且等不到位置时的失败计数，可用 `xTimerGetTimerDaemonTaskHandle`
拿到守护任务后配合队列查询调试（进阶，用到再查书）。

## reset 的语义细节

`xTimerReset` = "把到期时刻重设为 now + 周期"。
对休眠中的定时器等效于 start；对活跃的等效于"重新计时"。
**超时看门狗场景全靠它**：每次收到心跳包就 reset，
一直收不到 → 到期 → 回调报错。这是单次定时器的第一用例。

## 要点回顾

1. 定时器 API 全是"往命令队列发消息"，守护任务是唯一执行者。
2. 单写者设计 → 定时器名单零锁，ISR 也安全（FromISR 版）。
3. pdPASS = 命令入队，≠ 回调已执行。
4. `xTicksToWait` 等的是队列空位；调度器启动前它无效。

<details>
<summary>Q1：命令队列和普通队列是同一条吗？</summary>

不是。命令队列由内核在 `vTaskStartScheduler` 时专门创建，
与应用队列完全隔离，句柄不暴露。它只是**复用队列机制**
（queue.c 的代码），逻辑上是定时器子系统的私有传输层。

</details>

<details>
<summary>Q2：xTimerDelete 为什么没有 FromISR 版？</summary>

删除要释放定时器内存（动态创建时），ISR 里做内存释放既慢又危险；
而且删除语义在"中断随时可能再来"的场景里本身就矛盾。
官方干脆不提供——设计上把"销毁"留给任务上下文做。
想停中断源的定时器，用 `xTimerStopFromISR`。

</details>

## 衔接

命令都汇总到守护任务执行，意味着**所有定时器回调共享同一个任务
上下文**——一个回调阻塞，后面所有定时器全陪葬。
这条"回调禁区"的纪律与后果，下一篇 [5.3 回调禁区](5.3-回调禁区.md)。
