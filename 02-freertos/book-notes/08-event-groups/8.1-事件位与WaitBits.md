# 8.1 事件位与事件组：WaitBits 的 AND/OR 与退出清位

> 章导航：[README](README.md) ｜ 下一篇：[8.2 xEventGroupSync 会合点](8.2-xEventGroupSync会合点.md)

## 这一篇讲什么

队列传数据，信号量传"发生了一次"——但如果要等的是
**"A 或 B 发生了"**、**"A、B、C 全都发生了"**呢？
事件组就是干这个的：**一个变量里的一堆标志位**，按位等待，AND/OR 可选。

## 事件组 = 一个字 + 一堆约定

```c
EventGroupHandle_t eg = xEventGroupCreate();   /* 一个事件组 */

#define BIT_UART_READY   ( 1 << 0 )
#define BIT_SENSOR_READY ( 1 << 1 )
#define BIT_NET_UP       ( 1 << 2 )
```

- 事件组本体就是**一个无符号整数**，每一位是一个独立标志。
- 可用位数由 `configUSE_16_BIT_TICKS` 决定：16 位 tick 时 8 位、
  32 位 tick 时 24 位（高位被内核占用）。F103 一律 32 位 tick → 24 位。
- 每位**没有预定义含义**——BIT0 是"串口就绪"还是"电池低"全靠宏约定，
  内核只认位，不认语义。

## 置位：SetBits / ClearBits

```c
xEventGroupSetBits( eg, BIT_SENSOR_READY );     /* 置位（可一次置多位） */
xEventGroupClearBits( eg, BIT_NET_UP );         /* 清位 */
```

**SetBits 是广播**：一次置位唤醒**所有**等这几位的任务——
和信号量"Give 一次只救一个人"完全不同，这是事件组的标志性语义。

ISR 侧有 `xEventGroupSetBitsFromISR`，但有个坑：置位动作
**不在 ISR 里直接执行**，而是发消息给**定时器守护任务**代办——
SetBits 可能唤醒多个任务，这工作量不适合呆在中断里。
所以 ISR 置位有 **tick 级额外延迟**，强实时场景要心里有数。

## 等待：xEventGroupWaitBits 四参数

```c
EventBits_t bits = xEventGroupWaitBits(
    eg,                                  /* ① 哪个事件组 */
    BIT_UART_READY | BIT_SENSOR_READY,   /* ② 等哪几位 */
    pdTRUE,                              /* ③ xClearOnExit：满足后清这几位？ */
    pdFALSE,                             /* ④ xWaitForAllBits：AND 还是 OR */
    portMAX_DELAY );                     /* ⑤ 超时；返回值=退出时刻的快照 */
```

| ③ ClearOnExit | ④ WaitForAll | 语义 | 典型场景 |
|---|---|---|---|
| pdFALSE | pdFALSE | **等任意位**（OR），不清位 | "任一外设就绪就开跑"，位留给别人看 |
| pdTRUE | pdFALSE | 等任意位，出来**清等待的位** | 消费型事件：处理过就不再算数 |
| pdFALSE | pdTRUE | **等全部位**（AND），不清位 | "所有子系统自检通过"，状态常驻 |
| pdTRUE | pdTRUE | 等全部位，出来清掉 | 一次性集结：凑齐即发，发完翻篇 |

**返回值是快照不是"哪几位满足了"**——要判断得自己按位与：

```c
if( ( bits & BIT_UART_READY ) != 0 ) { /* UART 这边好了 */ }
```

注意：OR 模式返回时可能**多位同时满足**；快照只对退出那一刻诚实，
时序细节待实验验证。

## 最小完整例子

```c
/* 两个生产者 */
void vUartTask( void *p )    { init_uart();   xEventGroupSetBits( eg, BIT_UART_READY );   /*...*/ }
void vSensorTask( void *p )  { init_sensor(); xEventGroupSetBits( eg, BIT_SENSOR_READY ); /*...*/ }

/* 消费者：两个都好了才开工 */
void vMainTask( void *p )
{
    xEventGroupWaitBits( eg, BIT_UART_READY | BIT_SENSOR_READY,
                         pdTRUE, pdTRUE, portMAX_DELAY );
    /* 全员就绪，开始主业务 */
}
```

换信号量要两把锁加计数，换队列语义不对（队列是数据通道不是状态
布告栏）——这就是事件组的生态位。

## 要点回顾

1. 事件组 = 一个字里的 8/24 个标志位，位的含义全靠自己约定。
2. SetBits 是广播：一次置位唤醒所有等待者。
3. WaitBits 四参数定语义：等哪几位、AND/OR、退出清不清位、超时。
4. SetBitsFromISR 经守护任务中转，有 tick 级延迟。

<details>
<summary>Q1：xClearOnExit=TRUE 时，清的是"我等的位"还是"整组位"？</summary>

只清**你在参数 ② 里点名等待的那些位**，别的位不动。但另一位
任务若同时在等同一批位且不清位，两个等待者可能都满足——谁清
谁不清要提前设计好，否则"先出门的清了位，后出门的白等"。

</details>

<details>
<summary>Q2：为什么高 8 位（32 位 tick 时的 bit24~31）不能用？</summary>

事件组内部要用同一个变量存内核控制信息（比如"位正被清除"这类
状态），高 8 位被征用，24 位是应用上限。位不够用见
[8.3](8.3-事件组的局限.md)。

</details>

## 衔接

WaitBits 解决"一个人等多件事"；更进一步是**多个任务互相等**——
各自就位、最后到的人触发全员放行，即 xEventGroupSync 的"会合点"。
