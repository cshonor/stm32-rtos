## 这一篇讲什么

8.1 是"一个任务等多件事"。本篇升级成**多个任务互相等**：三个采集任务各自
就位，谁最后到谁触发全员放行——教科书叫 rendezvous（会合点），`xEventGroupSync` 一行搞定。

## 为什么"各自 WaitBits"做不到

朴素想法：每个任务先 SetBits 自己的位，再 WaitBits 等全部位：

```c
xEventGroupSetBits( eg, MY_BIT );
xEventGroupWaitBits( eg, ALL_BITS, pdTRUE, pdTRUE, portMAX_DELAY );
```

坑在两步之间：**两次 API 调用不是原子的。**A 置完位还没开始等，B 已把位凑齐
并放行、甚至位已被清掉——A 带着过时现场进场，这一轮会合就错位了。两拍之间塞得进任意次抢占，精度没法保证。

## xEventGroupSync = "置我的位 + 等全员的位"一步到位

```c
#define BIT_A ( 1 << 0 )
#define BIT_B ( 1 << 1 )
#define BIT_C ( 1 << 2 )
#define ALL_BITS ( BIT_A | BIT_B | BIT_C )

void vTaskX( void *p )   /* A/B/C 三个任务同构 */
{
    for( ;; )
    {
        do_my_work();                    /* 各自干活 */
        xEventGroupSync( eg, BIT_A,      /* 我要置的位（我是A） */
                         ALL_BITS,       /* 我要等齐的位 */
                         portMAX_DELAY );
        /* 走到这里：三人都干完这一轮，同步点开始下一轮 */
    }
}
```

内部语义（概念级）：

```
Sync( my_bit, all_bits ) = 关中断保护下：
    1. 置上 my_bit
    2. all_bits 齐了吗？
       ├─ 齐（我最后到）：清 all_bits，唤醒所有等待者，自己不阻塞
       └─ 没齐：进 Blocked，等"最后到的人"来唤醒
```

**原子性是全部价值**：置位 + 检查 + 阻塞绑成一次内核操作，抢占插不进来。
最后到达者当"开门人"，一次放行全员。

## 一个经典用途：分帧流水线

```
帧 N：  [采集A] [采集B] [采集C]   ← 三任务并行，速度不一
              Sync 会合点          ← 全部完成才进入帧 N+1
帧 N+1：[融合处理] 各自再采集 ...
```

没有 Sync 就得用 3 个计数信号量 + 1 个互斥量手搓，"最后一个到"的判定
也得自己写——Sync 把这个模式收进了一个 API。

## 和 WaitBits 的对照

| | WaitBits | Sync |
|---|---|---|
| 参与者 | 1 个等待者，N 个无关置位者 | N 个任务**互相**等 |
| 操作 | 只等，不置 | 置 + 等，原子绑定 |
| 谁清位 | ClearOnExit，等待者自己定 | 最后到达者统一清 all_bits |
| 语义 | 状态布告栏 | 周期性会合点 |

**选择标准**：单向"等别人"用 WaitBits；循环里"每轮互相等"用 Sync。用 WaitBits
手搓 Sync 错在原子性；反用 Sync 干 WaitBits 的活，你置的位会污染别人的会合判定。

## 注意事项

- 每个参与者的"我的位"必须**互不相同**，all_bits 是并集；位分错（两人
  同一位）会合点直接失效。
- 参与者数量/位号变了要全组同步改宏——位分配手工管理，没有登记处。
- 有参与者中途退出（被删、被挂起）时 all_bits 永远凑不齐，剩余任务卡死——
  要么给超时，要么设计上禁止中途离场。
- 超时返回时位可能只齐一部分，需按位判定"真会合还是超时"。超时路径待实验验证。

## 要点回顾

1. 会合点 = N 个任务循环里互相等，最后到达者放行全员。
2. 手写"SetBits + WaitBits"两步有原子性漏洞，Sync 把两步并成一步。
3. Sync 内部分工：先到者阻塞，最后到者清位 + 广播唤醒。
4. 位分配手工管、参与者不许中途离场，是会合点模式的两条纪律。

<details>
<summary>Q1：三个任务优先级不同，会合放行顺序怎么算？</summary>

最后到达者唤醒全体后，调度器按老规矩办：**优先级最高的就绪者先跑**。
会合点只保证"全员都已就位"这个事实，不保证放行后的顺序——
顺序归调度器管，别指望 Sync 当公平锁用。

</details>

<details>
<summary>Q2：Sync 和用 N 个二值信号量两两互等，差在哪？</summary>

信号量方案要 N 个信号量加协调逻辑，"最后到达判定"还得自己写计数；
Sync 是一个内核对象 + 一个 API。更要命的是正确性：手搓方案的竞态
窗口和"各自 WaitBits"同款。**模式被收进内核那天起，手搓就是负债。**

</details>
