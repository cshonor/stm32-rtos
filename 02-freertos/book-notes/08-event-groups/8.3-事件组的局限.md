# 8.3 事件组的局限与替代选型对照表

> 上一篇：[8.2 xEventGroupSync 会合点](8.2-xEventGroupSync会合点.md) ｜ 章导航：[README](README.md)

## 这一篇讲什么

事件组轻巧好用，但有几个结构性短板：**位没有所有权、
广播语义会误伤、位数有上限、从位上看不出"谁干的"**。
本篇把坑列清楚，再给一张"事件组 vs 信号量 vs 队列 vs
任务通知"的选型对照表。

## 坑一：位没有所有权

```c
/* 任务A 置位 */
xEventGroupSetBits( eg, BIT_X );
/* 任务B 也置同一个位——内核不管，位还是那个位 */
xEventGroupSetBits( eg, BIT_X );
```

位是**匿名**的：谁都能置、谁都能清、置了几次不可数。
- 想知道"事件发生了 3 次"？做不到——位只有 0/1，没有计数。
  要计数用**计数信号量**。
- 想知道"是谁置的"？做不到——位不带来源。
  要带来源用**队列**（消息体里写发送者 ID）。
- 误清别人的位？没人拦你——ClearBits 不查户口。
  位的置/清权限全靠团队纪律（对照 [7.4](../07-resource-management/7.4-递归互斥与ISR禁令.md)
  互斥量的"谁拿谁还"，事件组**什么所有权机制都没有**）。

## 坑二：广播语义是把双刃剑

SetBits 唤醒**所有**满足条件的等待者。多数时候这是卖点，
但两种场景会咬人：

1. **多位消费同一事件**：两个任务都等 BIT_X，本意"谁抢到谁处理"，
   实际两个都醒了都去处理——事件被消费两次。
   事件组**没有**"只唤醒一个"的选项；要独占消费用队列
   （数据只有一份，Receive 天然抢单）。
2. **清位竞态**：A 满足条件、ClearOnExit 清位出门；
   B 慢半拍醒来，位没了——同一事件，A 吃到 B 饿死。
   设计多人等同一位时，清位策略要全组统一想清楚。

## 坑三：位数天花板与 ISR 延迟

- **8/24 位封顶**（见 [8.1](8.1-事件位与WaitBits.md)）。
  24 个事件不够时，可以建多个事件组——但 WaitBits **一次只能等一组**，
  "等 A 组的位或 B 组的位"这种跨组条件原生做不到，
  只能轮询/拆任务，基本等于宣告该换方案。
- **SetBitsFromISR 经守护任务中转**（8.1 已讲），
  中断到任务醒来的延迟比任务通知长。硬实时链路
  （ISR → 单个高优先级任务）请用**任务通知**。

## 选型对照表

| 需求 | 信号量 | 队列 | 事件组 | 任务通知 |
|---|---|---|---|---|
| "发生了一次"唤醒一人 | ✅ 二值 | 可 | 可（杀鸡用牛刀） | ✅ 更快更省 |
| 计数（还剩几次/几个） | ✅ 计数型 | 可（深度近似） | 不能（位不可数） | ✅（通知值） |
| 传数据 + 顺序 | 不能 | ✅ 唯一正解 | 不能 | 只有 32 位值 |
| 等"多件事任一/全部" | 不能（无 OR/AND） | 不能 | ✅ 主场 | 不能 |
| N 个任务会合点 | 手搓且错 | 手搓且错 | ✅ Sync | 不能 |
| 广播给多人 | 不能 | 不能（队列集另有用途） | ✅ | 不能（一对一） |
| ISR 里触发，延迟敏感 | 可 | 可 | 中转，慢一档 | ✅ 最快 |
| RAM 开销 | 中 | 高（存储区） | 低 | **零**（TCB 内置） |

**一句话分工**：数据走队列、次数走信号量、
一人一事走任务通知、**多人多事按位组合走事件组**。
任务通知（[ch09](../09-task-notifications/README.md)）出现后，
"二值信号量唤醒一个固定任务"这个场景基本被它接管——
事件组受影响不大，因为它的主场（OR/AND/广播/会合）别人进不来。

## 位不够用/语义不够的逃生舱

| 症状 | 换什么 |
|---|---|
| 24 位不够 | 多个事件组 + 拆分等待任务；或重新抽象事件层级 |
| 要"事件 + 数据" | 事件组发"有数据了"，数据本体走队列/全局缓冲（配 ch07 保护） |
| 要数次数 | 计数信号量 |
| 要追来源 | 队列，消息体带 sender 字段 |
| 要独占消费 | 队列（Receive 抢单语义） |

## 要点回顾

1. 位匿名无所有权：不可计数、不带来源、谁都能清——纪律兜底。
2. 广播语义：多人等同位可能重复消费或清位饿死，策略要全组统一。
3. 8/24 位封顶、跨组等待做不到、ISR 置位有中转延迟。
4. 选型口诀：数据→队列，次数→信号量，一人一事→任务通知，多人多事→事件组。

<details>
<summary>Q1：事件组 + 队列混用（事件组通知、队列传数据）会不会竞态？</summary>

标准姿势，但要保证**先备好数据再置位**：发送方先 Send 到队列
（数据落地），再 SetBits；接收方等到位后 Receive 必有数据。
顺序反了（先置位后送队列）就有"位到了数据没到"的窗口。
先数据后信号，是多对象协作的通用安全序。待实验验证。

</details>

<details>
<summary>Q2：为什么跨事件组的 OR 等待内核不做？</summary>

WaitBits 的阻塞挂接点是**事件组自己的等待名单**，一个任务
同一时刻只能挂在一个名单上（TCB 里只有一个事件列表项）。
要跨组等，内核得允许一个任务挂多个名单——事件列表项就要变成
复数结构，整个阻塞/唤醒机制的复杂度和 RAM 开销翻倍。
这是个刻意的剪裁：常用场景 90% 被单组覆盖，
剩下 10% 由你拆任务消化。（队列集是个特例，那是另一套名单机制，
见 [4.5](../04-queue-management/4.5-队列集.md)。）

</details>
