## 这一篇讲什么

每个任务的栈是创建时从 heap 切的一小块（单位是字，见
[3.1](../03-task-management/3.1-任务函数与创建.md)）。
写爆了不会有人拦你——栈下方是别的任务的 TCB 或数据，被静默踩平。
`configCHECK_FOR_STACK_OVERFLOW` 提供两档检测，本篇讲原理、开销和选型。

## 为什么栈溢出是 RTOS 头号杀手

heap_4 连续分配时，任务 A 的栈下方很可能就是任务 B 的 TCB 或栈。
栈向下生长，爆了就踩到邻居地盘。
被踩的数据不会立刻发作：B 的栈里存着它的"寄存器现场"，
下次切换到 B 时弹出一堆垃圾——PC 指到火星，HardFault。
**死的地方和作案的地方隔着十万八千里**，这就是必须当场检测的原因。

## 方法一：查栈指针（configCHECK_FOR_STACK_OVERFLOW = 1）

每次**任务切换时**（PendSV 里）检查：当前任务的 SP 是否仍在自己栈的边界内。

| 项 | 说明 |
|---|---|
| 时机 | 每次上下文切换，开销固定 |
| 能查出 | 切换那一刻 SP 已越界 |
| 漏检 | 溢出后又缩回来、且没踩坏现场的情况（极少但存在） |
| 判定 | 快——一次比较 |

## 方法二：查填充模式（= 2，推荐）

任务创建时，内核把整个栈填成固定模式（`0xA5`）。
每次切换时检查**栈底最后 16 字节的填充模式是否还在**：
还在 = 没溢出过；被改写 = **历史上**溢出过（填充被踩不可逆），抓！

| 项 | 说明 |
|---|---|
| 时机 | 每次上下文切换 |
| 能查出 | 曾经溢出过的历史（痕迹，不是现状） |
| 漏检 | 一次写得极远、跳过栈底直接踩别人地盘的"飞跃式"溢出 |
| 判定 | 比对 16 字节，比方法一略慢 |

**方法二更严**。调试期一律方法二；RAM/CPU 极限紧张且已充分验证才退方法一；
发布固件资源允许就留着，钩子改"记录后复位"。

## 溢出钩子：检测到之后干什么

```c
/* FreeRTOSConfig.h */
#define configCHECK_FOR_STACK_OVERFLOW   2

/* 你的代码里实现（原型固定） */
void vApplicationStackOverflowHook( TaskHandle_t xTask,
                                    char * pcTaskName )
{
    ( void ) xTask;
    taskDISABLE_INTERRUPTS();
    for( ;; );  /* pcTaskName 里有肇事任务的名字，调试器直接看 */
}
```

注意：钩子里**别 printf、别调任何内核 API**——栈都爆了，
环境已经不可信，只能停车等调试器。
定位套路见 [12.3](../12-troubleshooting/12.3-栈问题与HardFault定位.md)。

## 主动量水位：uxTaskGetStackHighWaterMark

检测是"出事后抓"，水位是"出事前量"：

```c
/* 返回该任务栈的"历史最小剩余量"，单位：字（4 字节） */
UBaseType_t uxLeft = uxTaskGetStackHighWaterMark( NULL );  /* NULL = 自己 */

if( uxLeft < 32 )  /* 剩不到 128 字节，该加栈了 */
{
    /* 预警 */
}
```

"高水位"是**剩多少**（历史最小剩余），不是用了多少。
数字越小越危险，接近 0 = 曾经离爆栈只差一层函数调用。
调栈大小的正确姿势：跑到功能最全的负载，读水位，留 30% 余量定栈深。

## 要点回顾

1. 栈溢出踩的是邻居的地盘，**死相离现场极远**，必须当场抓。
2. 方法一查 SP 现状，方法二查 0xA5 填充痕迹——方法二更严，调试期标配。
3. 溢出钩子里只停车，不干别的。
4. `uxTaskGetStackHighWaterMark` 返回历史最小剩余（单位字），用来科学定栈深。

<details>
<summary>Q1：方法二会不会误报？</summary>

不会。填充写在栈最底部，正常执行永远到不了（到了就是溢出），
0xA5 被改写只有一个原因：栈生长越过了它。
反过来，完好也不能 100% 证明安全（飞跃式写入会跳过它）——
所以叫"检测"不叫"证明"。

</details>

<details>
<summary>Q2：中断用哪个栈？会被这个机制检测到吗？</summary>

中断跑在 MSP 上，不走任务栈（见
[20.1](../../../01-stm32/book-notes/20-towards-freertos/20.1-任务与调度的硬件落点.md)），
**不在这两档检测范围内**。深层中断嵌套把 MSP 写爆，
得靠链接时静态核算 + 调试器看 MSP 值。

</details>

## 衔接

栈水位是"单个任务"的视角。想看**全局**——所有任务各吃多少 CPU、
heap 还剩多少、每个任务水位排一排——要靠运行时统计和系统状态 API。
