## 这一篇讲什么

每个任务的栈是创建时从 heap（堆：FreeRTOS 自己管理的一块内存池，创建任务/队列都从这里切）切的一小块（单位是字，见
[3.1](../03-task-management/3.1-任务函数与创建.md)）。
写爆了不会有人拦你——栈下方是别的任务的 TCB 或数据，被静默踩平。
`configCHECK_FOR_STACK_OVERFLOW` 提供两档检测，本篇讲原理、开销和选型。

## 先用人话说一遍（新手铺垫）

每个任务的栈是合租房里隔出来的一间小屋，屋子之间没有墙，
只有约定俗成的地界。你的东西（局部变量、函数调用层数）越堆
越多，堆过地界就进了隔壁房间——**隔壁当下毫无察觉**，等
主人回来开灯（下次任务切换恢复现场），屋里全是垃圾，
灯一开就是 HardFault（Cortex-M 的总故障异常：踩了非法内存等严重错误都会掉进来）。惨案现场在隔壁，凶手是你。

两档检测对应两种查房方式。**方法一像宿管突击查寝**：每次
换班的瞬间看一眼你现在站在哪——越界立刻抓，但你越完界又
缩回去就可能漏掉。**方法二在边界撒一层石灰粉**（栈底预填的
`0xA5`）：粉被踩出脚印就证明**有人越界过**，缩回去也销不了
赃。所以方法二更严，调试期无脑选它。

映射：地界 = 栈边界，查房时机 = 每次任务切换（PendSV：Cortex-M 的一种异常，FreeRTOS 在它里面执行任务切换），
石灰粉脚印 = 被改写的填充模式。正文最后还有主动量房深的
办法（水位 API），别等抓到凶手才想起量。

| 术语 | 一句话解释 |
|---|---|
| 栈向下生长 | Cortex-M 的栈从高地址往低地址堆：溢出时踩的是"下方"邻居的数据 |
| 填充模式（`0xA5`） | 任务创建时内核预填进整个栈的固定字节图案，被改写即证明溢出发生过 |
| 上下文切换 | 调度器把 CPU 从任务 A 换给任务 B 的瞬间；两档检测都挂在这个时机 |
| 飞跃式溢出 | 一次写穿整个栈底、直接踩到别人地盘的溢出，方法二的石灰粉会被跳过 |
| 栈高水位 | `uxTaskGetStackHighWaterMark` 的返回值：该任务历史上最少还剩多少栈（单位：字） |

## 为什么栈溢出是 RTOS 头号杀手

heap_4 连续分配时，任务 A 的栈下方很可能就是任务 B 的 TCB 或栈。
栈向下生长，爆了就踩到邻居地盘。
被踩的数据不会立刻发作：B 的栈里存着它的"寄存器现场"，
下次切换到 B 时弹出一堆垃圾——PC 指到火星，HardFault。
**死的地方和作案的地方隔着十万八千里**，这就是必须当场检测的原因。

## 方法一：查栈指针（configCHECK_FOR_STACK_OVERFLOW = 1）

每次**任务切换时**（PendSV 里）检查：当前任务的 SP 是否仍在自己栈的边界内。

| 项 | 说明 |
|---|---|
| 时机 | 每次上下文切换，开销固定 |
| 能查出 | 切换那一刻 SP 已越界 |
| 漏检 | 溢出后又缩回来、且没踩坏现场的情况（极少但存在） |
| 判定 | 快——一次比较 |

## 方法二：查填充模式（= 2，推荐）

任务创建时，内核把整个栈填成固定模式（`0xA5`）。
每次切换时检查**栈底最后 16 字节的填充模式是否还在**：
还在 = 没溢出过；被改写 = **历史上**溢出过（填充被踩不可逆），抓！

| 项 | 说明 |
|---|---|
| 时机 | 每次上下文切换 |
| 能查出 | 曾经溢出过的历史（痕迹，不是现状） |
| 漏检 | 一次写得极远、跳过栈底直接踩别人地盘的"飞跃式"溢出 |
| 判定 | 比对 16 字节，比方法一略慢 |

**方法二更严**。调试期一律方法二；RAM/CPU 极限紧张且已充分验证才退方法一；
发布固件资源允许就留着，钩子改"记录后复位"。

## 溢出钩子：检测到之后干什么

```c
/* FreeRTOSConfig.h */
#define configCHECK_FOR_STACK_OVERFLOW   2

/* 你的代码里实现（原型固定） */
void vApplicationStackOverflowHook( TaskHandle_t xTask,
                                    char * pcTaskName )
{
    ( void ) xTask;
    taskDISABLE_INTERRUPTS();
    for( ;; );  /* pcTaskName 里有肇事任务的名字，调试器直接看 */
}
```

注意：钩子里**别 printf、别调任何内核 API**——栈都爆了，
环境已经不可信，只能停车等调试器。
定位套路见 [12.3](../12-troubleshooting/12.3-栈问题与HardFault定位.md)。

## 主动量水位：uxTaskGetStackHighWaterMark

检测是"出事后抓"，水位是"出事前量"：

```c
/* 返回该任务栈的"历史最小剩余量"，单位：字（4 字节） */
UBaseType_t uxLeft = uxTaskGetStackHighWaterMark( NULL );  /* NULL = 自己 */

if( uxLeft < 32 )  /* 剩不到 128 字节，该加栈了 */
{
    /* 预警 */
}
```

"高水位"是**剩多少**（历史最小剩余），不是用了多少。
数字越小越危险，接近 0 = 曾经离爆栈只差一层函数调用。
调栈大小的正确姿势：跑到功能最全的负载，读水位，留 30% 余量定栈深。

## 要点回顾

1. 栈溢出踩的是邻居的地盘，**死相离现场极远**，必须当场抓。
2. 方法一查 SP 现状，方法二查 0xA5 填充痕迹——方法二更严，调试期标配。
3. 溢出钩子里只停车，不干别的。
4. `uxTaskGetStackHighWaterMark` 返回历史最小剩余（单位字），用来科学定栈深。

<details>
<summary>Q1：方法二会不会误报？</summary>

不会。填充写在栈最底部，正常执行永远到不了（到了就是溢出），
0xA5 被改写只有一个原因：栈生长越过了它。
反过来，完好也不能 100% 证明安全（飞跃式写入会跳过它）——
所以叫"检测"不叫"证明"。

</details>

<details>
<summary>Q2：中断用哪个栈？会被这个机制检测到吗？</summary>

中断跑在 MSP（主栈指针：Cortex-M 两根栈指针之一，启动代码和中断专用；任务用的是另一根 PSP）上，不走任务栈（见
[20.1](../../../01-stm32/book-notes/20-towards-freertos/20.1-任务与调度的硬件落点.md)），
**不在这两档检测范围内**。深层中断嵌套把 MSP 写爆，
得靠链接时静态核算 + 调试器看 MSP 值。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| 方法一（查 SP）和方法二差不多 | 都是溢出检测 | 方法二查 `0xA5` 填充痕迹，抓"历史上溢出过"，越完界缩回去也销不了赃——更严，调试期标配 |
| 方法二填充完好 = 证明没溢出过 | 石灰粉没脚印就是没人来 | "飞跃式"溢出一次写穿栈底、跳过填充直接踩别人地盘——是"检测"不是"证明"（Q1） |
| 中断深层嵌套爆栈也能被这两档抓到 | 检测覆盖所有栈 | 中断走 MSP，不走任务栈，**不在检测范围内**；要静态核算 + 调试器看 MSP（Q2） |
| 溢出钩子里赶紧 printf 出任务名 | 出事要先打日志 | 栈都爆了，环境不可信——钩子里只许关中断停车，`pcTaskName` 留给调试器看 |
| "高水位"是历史最大用量 | 水位高 = 用得多 | `uxTaskGetStackHighWaterMark` 返回**历史最小剩余**（单位：字），数字越小越危险 |

## 衔接

栈水位是"单个任务"的视角。想看**全局**——所有任务各吃多少 CPU、
heap 还剩多少、每个任务水位排一排——要靠运行时统计和系统状态 API。

## 代码自测

_注：本节代码按 FreeRTOS API 语义编写，未在本仓库环境实跑，上板验证见「验证路径」。_

```c
/* FreeRTOSConfig.h */
#define configCHECK_FOR_STACK_OVERFLOW  2

void vApplicationStackOverflowHook( TaskHandle_t xTask, char *pcTaskName )
{
    ( void ) xTask;
    taskDISABLE_INTERRUPTS();
    for( ;; );   /* 调试器里看 pcTaskName，应为 "fat" */
}

void vFatTask( void *pv )       /* 创建时栈只给 128 字（512 字节） */
{
    char buf[ 600 ];            /* 局部数组远超栈深 */
    ( void ) pv;
    memset( buf, 0xAA, sizeof( buf ) );  /* 必须真写，否则被优化掉 */
    for( ;; ) vTaskDelay( 10 );
}

void vGaugeTask( void *pv )     /* 正常任务：量自己的水位 */
{
    ( void ) pv;
    for( ;; )
    {
        vTaskDelay( pdMS_TO_TICKS( 2000 ) );
        printf( "gauge stack left: %u words\r\n",
                ( unsigned ) uxTaskGetStackHighWaterMark( NULL ) );
    }
}
```

**预期现象**：
- `vFatTask` 一切换出去，方法二查到栈底 `0xA5` 被踩 → 停车进溢出钩子。
- 调试器里 `pcTaskName` 指向 `"fat"`，肇事任务直接点名。
- `vGaugeTask` 每 2 秒报水位；数字稳定且 >32 字即健康。
- 换成方法一（=1）：若溢出后 SP 恰好在切回前缩回边界内，可能漏检。

**验证路径**：F103 实机 + ST-Link 调试器（看钩子停车现场）+ USART printf（看水位）。

**常见翻车点**：
- 大数组声明了但没用，被编译器优化掉，溢出复现不了——必须 `memset` 真写。
- 钩子原型写错（参数必须是 `TaskHandle_t, char *`），链接报未定义或检测静默失效。
- 以为方法二能抓 MSP 爆栈——中断栈不归它管。
