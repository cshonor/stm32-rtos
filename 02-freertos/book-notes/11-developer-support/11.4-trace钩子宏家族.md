## 这一篇讲什么

FreeRTOS 内核源码在几十个关键位置预留了 `traceXXX()` 宏——
默认全是空，**你在 FreeRTOSConfig.h 里定义它，它就在内核内部替你埋点**。
这是 FreeRTOS+Trace / Percepio Tracealyzer 这类可视化工具的底层机制，
也是你自己写轻量调度日志的正规入口。

## 先用人话说一遍（新手铺垫）

上一篇的报告单是"你问才答"的快照。但有一类 bug 快照抓不到：
死锁（多个任务互相持有对方要的锁、谁都不放，全体永久卡住）、优先级反转（高优先级任务被低优先级任务间接卡住的现象，ch07 详解）、偶发超时——**病在"顺序"里**，你得知道过去
几百毫秒每件事发生的先后。要这个就得连续录像。

trace 钩子宏像流水线出厂时就打好的**摄像头安装孔**：内核源码
在几十个最关键的位置（每次任务切换、每次队列收发、进出中断）
留好了孔位。不装摄像头，孔位不占一分钱（默认空宏，编译器
删光）；装上摄像头——也就是你在 FreeRTOSConfig.h 里把宏定义
成自己的记录代码——你就在**全场视野最好的位置**开始录像，
而且没拆机器（不动内核源码，升级 FreeRTOS 不丢补丁）。

录下来的东西怎么用？最低配是录个切换计数；高配是 Tracealyzer
那套：事件压缩进 RAM 环形缓冲，事后倒到 PC 上按时间线回放，
谁跑了多久、谁抢了谁一目了然。代价只有一条军规要记死：
**摄像头本身不能拖慢流水线**——钩子跑在内核肚子里，阻塞或
printf 都是灾难。

| 术语 | 一句话解释 |
|---|---|
| trace 钩子宏 | 内核源码里预留的空宏插槽（`traceTASK_SWITCHED_IN` 等），你定义它就在该位置执行你的代码 |
| 埋点 | 在代码关键位置插入观测记录的动作；"埋"强调位置是预先选好的 |
| 环形缓冲 | 写满回头覆盖最旧数据的定长缓冲区，适合"只留最近 N 条事件"的录像 |
| Tracealyzer | Percepio 的可视化工具：把 trace 记录重放成调度时间线图 |
| 观察者效应 | 观测本身扰动被观测对象：钩子越重，系统时序变得越多，可能把 bug 吓跑 |

## 钩子宏是什么：内核留的回调插槽

```c
/* 内核源码里（tasks.c 概念示意）：每次任务切换都会经过 */
traceTASK_SWITCHED_IN();

/* 默认定义（FreeRTOS.h 里）：空 */
#ifndef traceTASK_SWITCHED_IN
    #define traceTASK_SWITCHED_IN()
#endif
```

你不定义 = 零开销（编译器直接删）；
你定义了 = 在**内核最精准的位置**插了自己的代码——
想观测的事件一个不漏，且不用改内核源码（升级 FreeRTOS 不丢补丁）。

## 常用宏速查

| 宏 | 触发时机 |
|---|---|
| `traceTASK_SWITCHED_IN` / `_OUT` | 任务切入 / 切出 |
| `traceTASK_CREATE` / `_DELETE` | 任务创建 / 删除 |
| `traceTASK_DELAY` / `_SUSPEND` / `_RESUME` | 延时 / 挂起 / 恢复 |
| `traceQUEUE_SEND` / `_RECEIVE` | 队列收发（含信号量） |
| `traceISR_ENTER` / `_EXIT` | 进出 ISR（port 层（FreeRTOS 里适配具体芯片架构的那层代码，不同内核各有一份）埋点） |
| `traceMALLOC` / `traceFREE` | heap 分配释放 |

## 最小可用示例：切换计数器

```c
/* FreeRTOSConfig.h */
extern volatile uint32_t ulSwitchCount;
#define traceTASK_SWITCHED_IN()  ulSwitchCount++
```

跑一分钟看计数，和预期心跳/事件频率对不上 = 调度行为异常
（比如有个任务在空转抢时间片——结合
[11.3 运行时统计](11.3-任务与堆水位观测.md) 能直接点名是谁）。

## FreeRTOS+Trace / Tracealyzer 的概念

Percepio Tracealyzer 的工作方式（概念，本仓未实测）：
钩子宏定义成"往 RAM 环形缓冲写事件记录"（谁、何时、干了什么，
压缩编码每条几字节）→ 调试器/串口倒出缓冲 →
PC 端重放成时间线图：任务条带、ISR 穿插、队列事件连线。

它回答的是快照 API 回答不了的问题：
**"过去 200 ms 里调度的完整顺序是什么？"**
——死锁、优先级反转、偶发超时这类**时序病**只有连续录像能抓。

书里的定位：trace 工具是"调试核武器"，平时不配，遇到时序型 bug 再上；
真到那一步直接接 Tracealyzer 的 recorder 库，别手写全套。

## 三条军规

1. **钩子里不许阻塞、不许调可能阻塞的 API**——你人在内核肚子里。
2. **钩子里越快越好**——`traceTASK_SWITCHED_IN` 在每次切换都跑，
   里面放个 printf 等于给调度器挂铅球（printf 本身的坑见
   [12.1](../12-troubleshooting/12.1-症状病因对照表.md)）。
3. **观察会改变被观察对象**——记录越细扰动越大，
   时序病抓不到时先减采样率，别把病人治死在手术台上。

## 与其他观测手段的分工

| 手段 | 粒度 | 开销 | 回答什么 |
|---|---|---|---|
| configASSERT（[11.1](11.1-configASSERT总开关.md)） | 事件点 | 极低 | 参数/状态错没错 |
| vTaskList 等快照（[11.3](11.3-任务与堆水位观测.md)） | 单时刻全览 | 一次性 | 现在健不健康 |
| trace 钩子 | 连续事件流 | 持续低开销 | 刚才发生了什么顺序 |
| 调试器断点 | 任意 | 停车 | 此刻的精确现场 |

## 要点回顾

1. trace 宏 = 内核预留的空插槽，定义即埋点，不改内核源码。
2. `traceTASK_SWITCHED_IN` 是观测调度的黄金位置。
3. Tracealyzer = 钩子宏 + RAM 环形缓冲 + PC 端重放，专抓时序病。
4. 钩子三军规：不阻塞、要极快、警惕观察者效应。

<details>
<summary>Q1：trace 钩子和 idle 钩子、tick 钩子是一类东西吗？</summary>

不是。idle/tick/malloc-failed/stack-overflow 钩子是**完整的回调函数**
（见 [3.5](../03-task-management/3.5-空闲任务与钩子.md)）；
trace 宏是**内联插槽**，插在内核函数中间的几十个点上。
前者是"内核请你干活"，后者是"内核让你看它干活"。

</details>

<details>
<summary>Q2：不用 Tracealyzer，自己能做简易 trace 吗？</summary>

能：定义 `traceTASK_SWITCHED_IN` 把 `(任务ID, 时基读数)` 压进
RAM 环形缓冲（复用 [11.3](11.3-任务与堆水位观测.md) 的 TIM2 时基），
事后调试器 dump 出来人工分析，够抓"切换顺序异常"。
要做队列事件追踪和图形化就别造轮子，直接上 Tracealyzer recorder。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| trace 钩子和 idle/tick 钩子是一类东西 | 都是"内核调的钩子" | idle 钩子是完整回调函数；trace 宏是插在内核函数中间几十个点上的**内联插槽**（Q1） |
| 钩子里顺手 printf 一条日志 | 调试嘛，打印最直观 | `traceTASK_SWITCHED_IN` 每次切换都跑，放 printf = 给调度器挂铅球 |
| 加观测不影响被观测系统 | 只是记录一下 | 观察者效应：记录越细扰动越大，时序病抓不到时先减采样率，别把病人治死在手术台上 |
| 不接 Tracealyzer 就没法用 trace | 那是专业工具的配套 | 最小可用就是把宏定义成计数器/写环形缓冲，几行代码抓切换顺序异常（Q2） |
| 用 trace 得改内核源码 | 埋点当然要改代码 | 宏在 `FreeRTOSConfig.h` 里定义即埋点，不动内核源码，升级 FreeRTOS 不丢补丁 |

## 代码自测

_注：本节代码按 FreeRTOS API 语义编写，未在本仓库环境实跑，上板验证见「验证路径」。_

```c
/* FreeRTOSConfig.h */
extern volatile uint32_t ulSwitchCount;
#define traceTASK_SWITCHED_IN()  ulSwitchCount++

/* main.c */
volatile uint32_t ulSwitchCount = 0;

void vReportTask( void *pv )    /* 1s 周期 */
{
    ( void ) pv;
    for( ;; )
    {
        vTaskDelay( pdMS_TO_TICKS( 10000 ) );
        printf( "context switches in 10s: %lu\r\n",
                ( unsigned long ) ulSwitchCount );
        ulSwitchCount = 0;
    }
}

void vIdle1s( void *pv )        /* 另一个 1s 周期任务，做基线 */
{
    ( void ) pv;
    for( ;; ) vTaskDelay( pdMS_TO_TICKS( 1000 ) );
}
```

**预期现象**：
- 基线：两个 1s 级周期任务 + 空闲任务，10 秒切换次数是一个可预期的稳定值（约 20 次量级，加上 tick 引起的进出空闲）。
- 加入一个死循环不阻塞的任务后，计数暴涨（时间片轮转每次 tick 都切）——调度异常被点名。
- 把宏定义改回空，计数停、系统零额外开销。

**验证路径**：F103 实机 + USART printf，对比"正常固件"与"加空转任务固件"两种构建的切换计数。

**常见翻车点**：
- `extern` 声明的类型和定义不一致（一个 `uint32_t` 一个 `int`），计数错乱。
- 变量忘加 `volatile`，被优化到寄存器里看不到更新。
- 在宏里塞 printf 或队列发送——钩子跑在内核肚子里，阻塞即灾难。
