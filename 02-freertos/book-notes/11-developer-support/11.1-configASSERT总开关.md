## 这一篇讲什么

FreeRTOS 内核源码里埋了上百处 `configASSERT(...)`，校验传入参数、
内部状态、调用上下文。但它默认是**空宏**——不配等于全车没装安全带。
本篇讲它查什么、怎么配、以及为什么嵌入式里比 PC 上更敢用它。

## configASSERT 查什么

内核在关键入口断言的典型条件：

| 断言位置 | 查的内容 | 没它会怎样 |
|---|---|---|
| API 入口 | 句柄非 NULL、参数在合法范围 | 拿野句柄继续跑，死得离现场很远 |
| 中断相关 API | 当前中断优先级是否允许调 API | 静默破坏内核链表（见 [12.2](../12-troubleshooting/12.2-中断优先级三大错.md)） |
| ISR 上下文判断 | 在非 FromISR API 里是否处于 ISR | ISR 里调阻塞 API，挂死 |
| 队列/信号量内部 | 名单指针、计数器一致性 | 数据坏了以后才崩，追不到源头 |

关键点：**断言触发时离 bug 现场最近**。
没有断言，错误参数不会立刻出事，而是腐蚀内核数据结构，
几十毫秒后在毫不相干的地方 HardFault——排查成本翻十倍。

## 标准写法

`FreeRTOSConfig.h` 里定义，编不过就算没配：

```c
/* 基础版：死循环停车，调试器一断就看到现场 */
#define configASSERT( x ) \
    if( ( x ) == 0 ) { taskDISABLE_INTERRUPTS(); for( ;; ); }

/* 进阶版：带文件名行号（printf 自身有风险，见 12.1） */
#define configASSERT( x ) \
    if( ( x ) == 0 ) { vAssertCalled( __FILE__, __LINE__ ); }
```

调试器停车后看调用栈，**栈顶往下第一帧就是违规的那次 API 调用**。

发布固件可以把它编掉（`-DNDEBUG` 风格地重定义为空），
但书的态度是：资源够就留着——它几乎不占时间（一次比较 + 分支）。

## 和 C 库 assert 的区别

| | C 库 `assert` | `configASSERT` |
|---|---|---|
| 谁调用 | 你的代码 | **内核源码内部**（你只管定义宏） |
| 失败动作 | `abort()`，依赖 libc | 你自己写，可以只是关中断停车 |
| 嵌入式适用性 | 拖累 libc、可能用堆 | 零依赖，几行汇编的事 |

## malloc 失败钩子：断言的孪生兄弟

```c
/* FreeRTOSConfig.h */
#define configUSE_MALLOC_FAILED_HOOK    1

/* 你的代码里实现 */
void vApplicationMallocFailedHook( void )
{
    taskDISABLE_INTERRUPTS();
    for( ;; );  /* 创建任务/队列时 heap 不够会进这里 */
}
```

`pvPortMalloc` 返回 NULL 前的**最后一道闸**（分配器背景见
[2.3 本仓选型 heap_4](../02-heap-memory/2.3-本仓选型heap_4.md)）。
`xTaskCreate` 返回 `pdFAIL` 你未必检查，钩子则是强制停车——
heap 耗尽这种慢性病的急性发作点，见
[12.1 症状→病因对照表](../12-troubleshooting/12.1-症状病因对照表.md)。

## 要点回顾

1. `configASSERT` 默认空宏，不配 = 内核不体检。
2. 断言让 bug 死在**现场**，而不是死在几十毫秒后的陌生人手里。
3. 标配写法：关中断 + 死循环；进阶带 `__FILE__`/`__LINE__`。
4. `vApplicationMallocFailedHook` 是 heap 耗尽的强制停车闸。

<details>
<summary>Q1：断言触发后怎么知道是哪个任务干的？</summary>

死循环里关中断停车后，调试器连上，`pxCurrentTCB` 指向当前任务
的 TCB（第一个成员就是栈顶指针，名字字段在里面）。
配了 `configMAX_TASK_NAME_LEN` 的话，任务名字段直接可读——
这就是 [3.1](../03-task-management/3.1-任务函数与创建.md) 说"起名别超 15 字符"的回报时刻。

</details>

<details>
<summary>Q2：configASSERT 会不会改变时序，把 bug 藏起来？</summary>

理论上任何插桩都会扰动时序（Heisenbug），但 configASSERT 只是
一次比较+分支，纳秒级开销，比 printf 低三个数量级。
真正会藏 bug 的是"调试时加 printf"——所以观测才要用
[11.4 trace 钩子宏](11.4-trace钩子宏家族.md) 这种低开销方式。

</details>

## 衔接

断言管"参数和状态对不对"，但有一种错误它抓不全：
**任务写爆了自己的栈**——这是运行时才发生的，得靠专门的检测机制。
