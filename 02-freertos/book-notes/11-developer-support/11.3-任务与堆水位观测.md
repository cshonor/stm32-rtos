## 这一篇讲什么

"系统健不健康"不能靠感觉。本篇四个 API 把 FreeRTOS 的内部状态
变成可打印的表：**任务列表、CPU 占用统计、栈水位、堆水位**。
加上运行时统计对高精度时基的要求——这是配置里最容易翻车的一环。

## vTaskList：任务全家福

```c
/* FreeRTOSConfig.h */
#define configUSE_TRACE_FACILITY   1
#define configUSE_STATS_FORMATTING_FUNCTIONS  1

char buf[ 512 ];
vTaskList( buf );   /* 生成一张文本表，你自己负责把 buf 弄出去 */
```

表的内容（列含义，不贴编造数据）：任务名、状态（X/R/B/S）、
优先级、**栈高水位**（字）、任务编号——
一张表同时看到"谁在阻塞"和"谁的栈快爆了"，排查第一快照。

底层是 `uxTaskGetSystemState()`：把每个任务的信息填进
`TaskStatus_t` 数组（含 xHandle / pcTaskName / eCurrentState /
uxStackHighWaterMark 等），想自定义格式就直接用它。

## vTaskGetRunTimeStats：谁吃了 CPU

```c
#define configGENERATE_RUN_TIME_STATS   1
/* 还必须自己提供两个宏：初始化时基 + 读时基 */
#define portCONFIGURE_TIMER_FOR_RUN_TIME_STATS()  vInitStatsTimer()
#define portGET_RUN_TIME_COUNTER_VALUE()          ulGetStatsCounter()

vTaskGetRunTimeStats( buf );  /* 文本表：每任务累计运行时间 + 百分比 */
```

回答的问题：**"我的 CPU 时间都被谁吃了？"**
空闲任务占比高 = 系统闲；某个任务占比异常 = 它在空转或算法失控。

### 时基必须比 tick 快一个数量级

内核只在**任务切换**时记一次时基读数，差值记给刚切走的任务。
tick 是 1 ms，如果时基也是 1 ms——两次切换之间的耗时**经常测不出**，
统计全是 0 或乱跳。所以官方要求：

> 时基精度至少比 tick 快 10 倍（建议 10–100 倍）。

F103 上的标准做法：拿一个空闲定时器
（[19.5 通用定时器 TIM2/TIM3](../../../01-stm32/book-notes/19-systick-and-timer/19.5-通用定时器TIM2TIM3.md)），
`vInitStatsTimer()` 里把它配成 10–20 kHz 自由运行上计数，
不用中断，只读 CNT。

**注意回绕**：16 位 CNT 在 10 kHz 下约 6.5 秒绕一圈，
内核做差值时用的是无符号减法，短间隔内安全
（同 [19.3 回绕安全比较](../../../01-stm32/book-notes/19-systick-and-timer/19.3-g_ms与回绕安全的时间比较.md) 的原理）。

## 堆水位：xPortGetFreeHeapSize 两兄弟

```c
size_t now = xPortGetFreeHeapSize();           /* 此刻 heap 还剩多少 */
size_t min = xPortGetMinimumEverFreeHeapSize(); /* 历史最少剩多少 ★ */
```

定 `configTOTAL_HEAP_SIZE` 的正确姿势：跑最全功能负载，
读 **MinimumEverFree**（历史最小值），留 30–50% 余量后反推总大小。
注意这两个 API 反映的是 FreeRTOS 的 `pvPortMalloc`（heap_4 的 ucHeap），
**不包括** C 库 malloc 和 MSP 栈（见
[2.3 本仓选型 heap_4](../02-heap-memory/2.3-本仓选型heap_4.md)）。
heap 耗尽的急性症状见
[12.1 症状→病因对照表](../12-troubleshooting/12.1-症状病因对照表.md)。

## 四个 API 一览

| 观测对象 | API | 需要的配置 |
|---|---|---|
| 任务列表+栈水位 | `vTaskList` / `uxTaskGetSystemState` | `configUSE_TRACE_FACILITY` |
| CPU 占用 | `vTaskGetRunTimeStats` | `configGENERATE_RUN_TIME_STATS` + 自配高速时基 |
| 单任务栈水位 | `uxTaskGetStackHighWaterMark`（见 [11.2](11.2-栈溢出检测两档.md)） | `configUSE_TRACE_FACILITY` 等 |
| 堆水位 | `xPortGetFreeHeapSize` / `xPortGetMinimumEverFreeHeapSize` | 无（heap_4 自带） |

## 要点回顾

1. `vTaskList` 一张表看到全部任务的状态和栈水位，排查第一快照。
2. 运行时统计的时基必须 ≥ 10 倍 tick——F103 用 TIM2 自由跑 10 kHz 读 CNT。
3. 定 heap 大小看 `xPortGetMinimumEverFreeHeapSize`（历史最小值），留余量。
4. 这些 API 观测的是 FreeRTOS 的世界；C 库堆、MSP 栈不在其内。

<details>
<summary>Q1：vTaskGetRunTimeStats 的百分比加起来为什么不到 100%？</summary>

表里的分母是"统计开始以来的总时基计数"，而**中断占用的时间
不算任何任务的账**——中断密集时误差明显；
时基回绕、计数器位数不够也会让总数失真。
把它当**相对比较**工具（谁和谁差几倍），别当精密仪器。

</details>

<details>
<summary>Q2：这些统计 API 会不会拖慢系统？</summary>

`vTaskList`/`uxTaskGetSystemState` 要挂起调度器遍历所有 TCB，
任务多时是一次可观的临界区——**别在高频路径里调**，
放在调试命令/低优先级监控任务里偶尔跑一次。
运行时统计本身只是切换时多读一次 CNT，开销可忽略。

</details>
