## 这一篇讲什么

互斥量保护共享资源天经地义，但它藏着一个反直觉的事故：
**高优先级任务被低优先级任务"按在地上摩擦"，中间还夹着一个
看热闹不嫌事大的中优先级任务。**这就是优先级反转——RTOS 教科书
头号反派。本篇把 H/M/L 三任务剧本逐拍演一遍。

## 先用人话说一遍（新手铺垫）

上一篇说互斥量 = 灶台钥匙。这一篇讲的是钥匙制度的一个漏洞，
先记住结论：**用锁保护资源，可能反而让最急的人等得最久**。

生活版剧情：公司只有一间会议室。实习生（L）在里面打电话，
一打一下午。CEO（H）来了要用——按规矩实习生得打完让出，
CEO 等一会儿也认了。坏就坏在：中层经理（M）这时候抱着一摞
材料来"对齐工作"，他职级比实习生高，直接把实习生从工位上
薅走开会去了。实习生还不出会议室，CEO 就干等——
**等的不是实习生打电话的时间，而是经理开完全部会的时间。**

映射关系：职级 = 任务优先级，会议室 = 互斥量保护的资源，
"被拉去对齐工作" = 被中优先级任务抢占 CPU。
注意经理自己根本不碰会议室——这正是反转最阴的地方：
**肇事者是无辜的**。

| 术语 | 一句话解释 |
|---|---|
| 优先级反转 | 高优先级任务因等低优先级任务持有的锁，实际被中优先级任务无限拖延的现象 |
| 抢占式调度 | 高优先级任务一旦就绪，立刻把低优先级任务从 CPU 上换下来的调度方式 |
| 所有权（持有者） | 互斥量的属性：内核记住锁当前归哪个任务，只认它来还 |
| 二值信号量 | 只有"有/无"两种状态的信号量，适合做同步通知，没有所有权概念 |
| 无界等待 | 等待时长没有上限——实时系统的大忌，因为你无法证明任务能按时完成 |

## 演员表

| 任务 | 优先级 | 行为 |
|---|---|---|
| L（Low） | 低 | 长期持有互斥量干活 |
| M（Medium） | 中 | **不碰互斥量**，纯计算，跑起来没完 |
| H（High） | 高 | 偶尔需要同一把互斥量 |

关键设定：**M 不需要互斥量**。它没有任何错，却是事故的核心推手。

## 剧本逐拍（无继承版）

```
t0  L 拿到互斥量 mutex，开始慢慢干活（持有期较长）
t1  H 就绪（比如事件来了）→ 抢占 L → H 运行
t2  H 也 Take 同一把 mutex → 已被 L 持有 → H 进 Blocked
    （调度器回头让 L 继续跑——此时还是正常剧情）
t3  M 就绪 → M 优先级 > L → M 抢占 L，开始它没完没了的计算
t4  L 被 M 挤到 Ready 态排队，拿不到 CPU → 永远还不出 mutex
t5  H 在 Blocked 里等 mutex → 等于在等 M 跑完
── 结果：H（最高优先级）的实际响应时间 = M（中优先级）的运行时间
```

时序一览：

| 时刻 | Running | 阻塞/等待方 | 备注 |
|---|---|---|---|
| t0–t1 | L | — | L 持有 mutex |
| t1–t2 | H | L（被抢占，持锁中） | 正常抢占 |
| t2–t3 | L | H（等 mutex） | 还能忍，L 总会还 |
| t3 起 | **M** | H（等锁）、L（等 CPU） | **反转发生** |

## 为什么这叫"反转"

优先级承诺的是：**高优先级任务想跑就跑**。
t3 之后的事实是：H 想跑，跑不了；M 优先级比 H 低，却跑个没完。
从 H 的视角看，世界的优先级秩序被**倒了过来**——
它的延迟不再由自己决定，而是被一个不相关的 M 决定。

**M 是关键角色**：没有 M，L 迟早跑完还锁，H 最多等"一段持有期"；
有了 M，等待期变成"M 的全部运行时间"——**不可预期、不可限定**。
实时系统的死穴就是"上限未知"。

## 和二值信号量的关系

**用二值信号量当互斥锁，反转照样发生，而且没有任何内置解药。**
信号量没有"持有者"概念，内核不知道谁欠谁的，
想救都救不了。这就是 [ch06 中断管理](../06-interrupt-management/README.md)
里"信号量做同步"和本章"互斥量做互斥"必须分开的根本原因：
**同步用信号量，互斥用 mutex，混用=自动放弃继承机制（优先级继承：内核临时把持锁的低优先级任务抬到等待者的优先级，7.3 详解）。**

```c
/* 错：SemaphoreHandle_t s = xSemaphoreCreateBinary();  拿去保护 UART */
/* 对：SemaphoreHandle_t m = xSemaphoreCreateMutex();  自带所有权+继承 */
```

互斥量创建出来就是"可用"状态（相当于已 Give 一次），
这点和二值信号量（创建为空）也不一样。

## 真实世界回声

书外最有名的反转事故是 1997 年火星探路者号：
总线互斥锁 + 反转导致系统反复复位，最后靠打上
"开启优先级继承"的补丁救回。教科书没骗人。

## 要点回顾

1. 反转剧本：L 持锁 → H 等锁 → M 抢 L → H 的延迟 = M 的运行时间。
2. M 不碰锁却是事故核心——反转的等待期**没有上限**。
3. 二值信号量当锁用 = 同样的坑 + 没解药；互斥必须 `xSemaphoreCreateMutex`（创建互斥量的 API，所有权和继承都是它自带的）。
4. 互斥量创建即"可用"，与二值信号量初始为空相反。

<details>
<summary>Q1：反转在单核上也会发生吗？</summary>

会，而且单核是反转的**标准作案现场**——上面的剧本全程只需要一个核：
抢占式调度 + 优先级排序足以凑齐全部条件。
多核只是让剧情更复杂，不是必要条件。

</details>

<details>
<summary>Q2：把临界区拉长代替互斥量，能绕开反转吗？</summary>

能"绕开"但代价更狠：临界区关中断期间没有抢占，自然没有反转——
可中断延迟也全毁了（见 [7.1](7.1-保护手段光谱.md)）。
用"毁掉整个系统的实时性"来治"一个任务的实时性"，本末倒置。
正解是下一篇的优先级继承。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| 反转是多核才会有的毛病 | 单核只有一个任务在跑，轮不到反转 | 单核正是标准作案现场：抢占式调度 + 优先级排序已凑齐全部条件 |
| H 等得久是因为 L 持锁太久 | 锅在持锁的人 | 锅在不碰锁的 M：H 的延迟 = M 的全部运行时间，与 L 无关 |
| 二值信号量也能当互斥锁用 | 都是 Take/Give，差不多 | 反转照样发生且信号量无所有权、无继承，没有任何内置解药 |
| 互斥量和二值信号量一样创建为"空" | 都得先 Give 一次才可用 | 互斥量创建即"可用"，二值信号量创建为空，初始状态相反 |
| 拉长临界区可以绕开反转 | 关中断期间没有抢占，自然没有反转 | 代价更狠：中断延迟全毁，用整个系统的实时性治一个任务 |

## 衔接

剧本的灾难点在于"内核不知道 L 在替 H 打工"。
如果 L 持有锁期间能**临时借用 H 的优先级**，M 就抢不动它——
这就是优先级继承。下一篇 [7.3 优先级继承](7.3-优先级继承.md)
讲它如何改写剧本，以及它为什么只是"缓解"不是"根治"。

## 代码自测

_注：本节代码按 FreeRTOS API 语义编写，未在本仓库环境实跑，上板验证见「验证路径」。_

```c
/* H/M/L 三任务反转剧本：故意用二值信号量当锁（无继承，反转可见） */
static SemaphoreHandle_t xLock;   /* 二值信号量，不是 mutex */

static void vTaskL( void *pv )    /* 优先级 1：持锁慢慢干 */
{
    for( ;; )
    {
        xSemaphoreTake( xLock, portMAX_DELAY );
        printf( "L: got lock, working...\r\n" );
        for( volatile uint32_t i = 0; i < 5000000; i++ ) { }  /* 长持锁 */
        printf( "L: release\r\n" );
        xSemaphoreGive( xLock );
        vTaskDelay( pdMS_TO_TICKS( 500 ) );
    }
}

static void vTaskM( void *pv )    /* 优先级 2：不碰锁，纯计算 */
{
    vTaskDelay( pdMS_TO_TICKS( 50 ) );          /* 让 L 先拿锁 */
    for( ;; )
    {
        printf( "M: running\r\n" );
        for( volatile uint32_t i = 0; i < 3000000; i++ ) { }
        vTaskDelay( pdMS_TO_TICKS( 100 ) );
    }
}

static void vTaskH( void *pv )    /* 优先级 3：偶尔要同一把锁 */
{
    vTaskDelay( pdMS_TO_TICKS( 60 ) );          /* 保证 L 已持锁 */
    for( ;; )
    {
        printf( "H: want lock\r\n" );
        xSemaphoreTake( xLock, portMAX_DELAY );
        printf( "H: got lock!\r\n" );
        xSemaphoreGive( xLock );
        vTaskDelay( pdMS_TO_TICKS( 1000 ) );
    }
}

void app_init( void )
{
    xLock = xSemaphoreCreateBinary();
    xSemaphoreGive( xLock );        /* 二值信号量创建为空，先补一次 */
    xTaskCreate( vTaskL, "L", 256, NULL, 1, NULL );
    xTaskCreate( vTaskM, "M", 256, NULL, 2, NULL );
    xTaskCreate( vTaskH, "H", 256, NULL, 3, NULL );
}
```

**预期现象**：
- "L: got lock" 先打印；随后 "H: want lock" 出现，H 进阻塞。
- M 就绪后连续刷 "M: running"，L 被挤得跑不动，"L: release" 迟迟不出。
- "H: want lock" 到 "H: got lock!" 之间的间隔，约等于 M 的若干轮运行时间，而不是 L 的持锁剩余时间——这就是反转。
- 把 `xLock` 换成 `xSemaphoreCreateMutex()`（并删掉手动 Give）重跑：H 阻塞瞬间 L 被抬到优先级 3，M 抢不动，"H: got lock!" 很快出现。

**验证路径**：F103 实机 + USART printf，对照二值信号量版和 mutex 版两组日志的时间差。

**常见翻车点**：
- 忘给二值信号量补初始 Give，L 第一次 Take 就永久阻塞。
- 忙等循环没加 `volatile` 被编译器优化掉，"长持锁"变瞬间完成，看不到反转。
- 三个 vTaskDelay 的时序没调好，H 在 L 拿锁之前就绪，剧本开场就错位。
