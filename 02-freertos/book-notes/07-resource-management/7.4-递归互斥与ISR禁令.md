# 7.4 递归互斥量与"互斥量不能 FromISR"

## 这一篇讲什么

互斥量的收尾两个硬知识：同一个任务重复拿同一把锁会怎样
（普通 mutex 自杀，递归 mutex 计数放行），以及为什么
**互斥量是全家族里唯一没有 FromISR 版本的对象**。

## 普通 mutex 重入 = 当场死锁

```c
xSemaphoreTake( m, portMAX_DELAY );   /* 第一次：拿到 */
xSemaphoreTake( m, portMAX_DELAY );   /* 持有者是自己：等自己还锁 → 死锁 */
```

mutex 有**所有权**：只认"当前持有者"。第二句的等待者是持有者本人，
"等自己放手的自己"——这是最容易复现的死锁，没有之一。

什么场景会踩到？**函数嵌套**：

```c
void helper( void )          { xSemaphoreTake( m, ... ); /*...*/ xSemaphoreGive( m ); }
void outer( void )           { xSemaphoreTake( m, ... ); helper(); xSemaphoreGive( m ); }
/*                                   ↑ 已持有           ↑ helper 里再拿 = 死锁 */
```

## 递归互斥：给所有权加个计数器

```c
SemaphoreHandle_t rm = xSemaphoreCreateRecursiveMutex();

xSemaphoreTakeRecursive( rm, portMAX_DELAY );   /* 计数 0→1，拿到 */
xSemaphoreTakeRecursive( rm, portMAX_DELAY );   /* 持有者是自己 → 计数 1→2，放行 */
xSemaphoreGiveRecursive( rm );                  /* 计数 2→1，锁还在我手里 */
xSemaphoreGiveRecursive( rm );                  /* 计数 1→0，真正释放 */
```

| | 普通 mutex | 递归 mutex |
|---|---|---|
| 同一任务重复 Take | 死锁 | 计数放行 |
| Give 次数要求 | 1 次 | **拿几次还几次** |
| 创建 API | `xSemaphoreCreateMutex` | `xSemaphoreCreateRecursiveMutex` |
| Take/Give API | `xSemaphoreTake` / `Give` | `...TakeRecursive` / `...GiveRecursive` |
| 优先级继承 | 有 | 同样有 |

**使用纪律**：递归 mutex 是"函数嵌套都摸同一资源"的创可贴，
不是设计目标。能用清晰的锁分层（谁拿锁谁调用不加锁的原子函数）
就别上递归——拿还次数配不上对，排查起来比死锁还阴间。

## 为什么互斥量没有 FromISR

队列、信号量、事件组、任务通知全都有 `...FromISR`，
互斥量**独独没有**。原因就写在所有权语义里：

1. **继承没有载体**：继承的前提是"持有者是任务，有 TCB、有优先级
   可抬"。ISR 不是任务，没有优先级可继承，也没法配合抬级机制。
2. **阻塞没有意义**：Take 不到要 Blocked——ISR 阻塞谁？
   中断上下文里没有"挂起等锁"这个概念。
3. **所有权无法归还**：ISR 随时打断任何人，"ISR 持锁、下一次中断
   来还"在调度模型里不成立。

所以规则干脆利落：**ISR 想保护共享数据，回 [7.1](7.1-保护手段光谱.md)
的光谱选——临界区（FROM_ISR 版）管短的，守护任务管长的。**

```c
/* ISR 里要往共享结构写数据：两选一 */
taskENTER_CRITICAL_FROM_ISR( mask );  /* 短：改完即退 */
taskEXIT_CRITICAL_FROM_ISR( mask );

xQueueSendFromISR( q, &data, &woken ); /* 长：丢给守门人任务 */
portYIELD_FROM_ISR( woken );
```

## 全家桶 ISR 可用性速查

| 对象 | FromISR | 原因 |
|---|---|---|
| 队列 | ✅ | 无所有权，拷贝即走 |
| 二值/计数信号量 | ✅ | 无所有权，Give 不挑人 |
| 事件组 | ✅（见 [8.1](../08-event-groups/8.1-事件位与WaitBits.md)） | 置位无所有权 |
| 任务通知 | ✅ | 直达 TCB |
| **互斥量** | **没有** | 所有权 + 继承，必须有任务身份 |

## 要点回顾

1. 普通 mutex 重入 = 等自己 = 死锁；函数嵌套是重灾区。
2. 递归 mutex 用计数放行重入，**拿几次还几次**，能不用就不用。
3. 互斥量无 FromISR：所有权和继承都需要"任务身份"，ISR 给不了。
4. ISR 侧替代：短用 FROM_ISR 临界区，长用队列甩给守护任务。

<details>
<summary>Q1：递归 mutex 的优先级继承还生效吗？</summary>

生效，规则和普通 mutex 一样：高优先级任务 TakeRecursive 阻塞时，
持有者被抬级。计数只影响"何时真正释放"，不影响继承。
（嵌套多把递归锁叠加继承的精确时序，待实验验证。）

</details>

<details>
<summary>Q2：互斥量 Give 必须由 Take 的那个任务执行吗？</summary>

设计上**必须**：所有权语义就是"谁拿谁还"。内核不强制检查
（老版本甚至不报错），但跨任务 Give 会让继承的抬级/还级全部错位，
属于语义级 bug。需要"A 拿 B 还"的场景请用二值信号量——
那本来就不是互斥，是同步。

</details>
