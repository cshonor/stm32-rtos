# 7.4 递归互斥量与"互斥量不能 FromISR"

## 这一篇讲什么

互斥量的收尾两个硬知识：同一个任务重复拿同一把锁会怎样
（普通 mutex 自杀，递归 mutex 计数放行），以及为什么
**互斥量是全家族里唯一没有 FromISR 版本的对象**。

## 先用人话说一遍（新手铺垫）

本篇讲互斥量的两个边角，但都是真坑。第一个：你自己拿着钥匙，
又去找自己要钥匙。普通互斥量只认"锁在谁手里"，不认"要锁的人
是不是持有者本人"——于是你等你自己放手，**永远没有结果**。
最容易踩中的场景不是代码里连着写两句 Take，而是函数套函数：
外层拿了锁，调了个内部也拿同一把锁的助手函数。

递归互斥量就是给这个场景准备的：像酒店同一张房卡刷多次进门，
系统给你记个数——拿 N 次，还 N 次，数对上了才真正锁释放。
听着方便，但数数对不上时的 bug 比死锁（多个任务互相持有对方要的锁、谁都不肯先放，全体永久卡住）还难找，所以正文的立场
是"能不用就不用"。

第二个边角一句话：中断里不许碰互斥量。不是"不建议"，是内核
压根没提供这个 API。原因正文逐条讲，核心就一句：**互斥量的
所有权和继承都是给"任务"设计的，中断不是任务，什么都没有。**

| 术语 | 一句话解释 |
|---|---|
| 重入 | 同一段代码（或同一个对象）被同一执行流再次进入，比如持有锁的函数又调了拿同一把锁的函数 |
| 递归互斥量 | 允许持有者重复 Take 的互斥量，内部计数，Take/Give 次数配对才真正释放 |
| `...FromISR` | FreeRTOS 给中断上下文专用的 API 后缀，如 xQueueSendFromISR；互斥量没有此版本 |
| 中断上下文 | ISR 正在执行的那段环境：不属于任何任务，不能阻塞，能用的 API 受限 |
| TCB | 任务控制块，内核给每个任务建的档案（优先级、栈指针、通知值等都在里面） |

## 普通 mutex 重入 = 当场死锁

```c
xSemaphoreTake( m, portMAX_DELAY );   /* 第一次：拿到 */
xSemaphoreTake( m, portMAX_DELAY );   /* 持有者是自己：等自己还锁 → 死锁 */
```

mutex 有**所有权**：只认"当前持有者"。第二句的等待者是持有者本人，
"等自己放手的自己"——这是最容易复现的死锁，没有之一。

什么场景会踩到？**函数嵌套**：

```c
void helper( void )          { xSemaphoreTake( m, ... ); /*...*/ xSemaphoreGive( m ); }
void outer( void )           { xSemaphoreTake( m, ... ); helper(); xSemaphoreGive( m ); }
/*                                   ↑ 已持有           ↑ helper 里再拿 = 死锁 */
```

## 递归互斥：给所有权加个计数器

```c
SemaphoreHandle_t rm = xSemaphoreCreateRecursiveMutex();

xSemaphoreTakeRecursive( rm, portMAX_DELAY );   /* 计数 0→1，拿到 */
xSemaphoreTakeRecursive( rm, portMAX_DELAY );   /* 持有者是自己 → 计数 1→2，放行 */
xSemaphoreGiveRecursive( rm );                  /* 计数 2→1，锁还在我手里 */
xSemaphoreGiveRecursive( rm );                  /* 计数 1→0，真正释放 */
```

| | 普通 mutex | 递归 mutex |
|---|---|---|
| 同一任务重复 Take | 死锁 | 计数放行 |
| Give 次数要求 | 1 次 | **拿几次还几次** |
| 创建 API | `xSemaphoreCreateMutex` | `xSemaphoreCreateRecursiveMutex` |
| Take/Give API | `xSemaphoreTake` / `Give` | `...TakeRecursive` / `...GiveRecursive` |
| 优先级继承 | 有 | 同样有 |

**使用纪律**：递归 mutex 是"函数嵌套都摸同一资源"的创可贴，
不是设计目标。能用清晰的锁分层（谁拿锁谁调用不加锁的原子函数——这里指内部不再碰共享资源、可以安全裸跑的函数）
就别上递归——拿还次数配不上对，排查起来比死锁还阴间。

## 为什么互斥量没有 FromISR

队列、信号量、事件组、任务通知全都有 `...FromISR`，
互斥量**独独没有**。原因就写在所有权语义里：

1. **继承没有载体**：继承的前提是"持有者是任务，有 TCB、有优先级
   可抬"。ISR 不是任务，没有优先级可继承，也没法配合抬级机制。
2. **阻塞没有意义**：Take 不到要 Blocked——ISR 阻塞谁？
   中断上下文里没有"挂起等锁"这个概念。
3. **所有权无法归还**：ISR 随时打断任何人，"ISR 持锁、下一次中断
   来还"在调度模型里不成立。

所以规则干脆利落：**ISR 想保护共享数据，回 [7.1](7.1-保护手段光谱.md)
的光谱选——临界区（FROM_ISR 版）管短的，守护任务管长的。**

```c
/* ISR 里要往共享结构写数据：两选一 */
taskENTER_CRITICAL_FROM_ISR( mask );  /* 短：改完即退 */
taskEXIT_CRITICAL_FROM_ISR( mask );

xQueueSendFromISR( q, &data, &woken ); /* 长：丢给守门人任务 */
portYIELD_FROM_ISR( woken );
```

## 全家桶 ISR 可用性速查

| 对象 | FromISR | 原因 |
|---|---|---|
| 队列 | ✅ | 无所有权，拷贝即走 |
| 二值/计数信号量 | ✅ | 无所有权，Give 不挑人 |
| 事件组 | ✅（见 [8.1](../08-event-groups/8.1-事件位与WaitBits.md)） | 置位无所有权 |
| 任务通知 | ✅ | 直达 TCB |
| **互斥量** | **没有** | 所有权 + 继承，必须有任务身份 |

## 要点回顾

1. 普通 mutex 重入 = 等自己 = 死锁；函数嵌套是重灾区。
2. 递归 mutex 用计数放行重入，**拿几次还几次**，能不用就不用。
3. 互斥量无 FromISR：所有权和继承都需要"任务身份"，ISR 给不了。
4. ISR 侧替代：短用 FROM_ISR 临界区，长用队列甩给守护任务。

<details>
<summary>Q1：递归 mutex 的优先级继承还生效吗？</summary>

生效，规则和普通 mutex 一样：高优先级任务 TakeRecursive 阻塞时，
持有者被抬级。计数只影响"何时真正释放"，不影响继承。
（嵌套多把递归锁叠加继承的精确时序，待实验验证。）

</details>

<details>
<summary>Q2：互斥量 Give 必须由 Take 的那个任务执行吗？</summary>

设计上**必须**：所有权语义就是"谁拿谁还"。内核不强制检查
（老版本甚至不报错），但跨任务 Give 会让继承的抬级/还级全部错位，
属于语义级 bug。需要"A 拿 B 还"的场景请用二值信号量——
那本来就不是互斥，是同步。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| 自己持有的锁再 Take 一次应该直接成功 | 锁在我手里，再拿一次怎么了 | 普通 mutex 只认持有者：等自己放手 = 当场死锁；函数嵌套是重灾区 |
| 递归 mutex 拿两次还一次就行 | 反正锁最后总会释放 | 拿几次必须还几次，计数不归零锁不释放；配不上对的 bug 比死锁还难找 |
| 递归 mutex 大概没有优先级继承 | 特殊锁，机制可能缩水 | 继承规则和普通 mutex 完全一样，计数只影响何时真正释放 |
| 互斥量应该也有 FromISR 版本 | 队列、信号量、事件组、通知全有 | 全家族唯一没有：所有权和继承都要"任务身份"，ISR 给不了 |
| mutex 谁 Give 都行，内核会检查 | 内核应该会拦住乱还锁 | 内核不强制检查（老版本不报错），跨任务 Give 让继承抬级/还级全部错位 |

## 代码自测

_注：本节代码按 FreeRTOS API 语义编写，未在本仓库环境实跑，上板验证见「验证路径」。_

```c
/* 递归互斥：函数嵌套重复拿同一把锁，计数放行 */
static SemaphoreHandle_t xRMutex;

static void helper( void )        /* 内层：也要拿同一把锁 */
{
    xSemaphoreTakeRecursive( xRMutex, portMAX_DELAY );
    printf( "helper: in (2nd take)\r\n" );
    xSemaphoreGiveRecursive( xRMutex );      /* 计数 2→1，锁还在 */
}

static void vWorker( void *pv )
{
    for( ;; )
    {
        xSemaphoreTakeRecursive( xRMutex, portMAX_DELAY );  /* 计数 0→1 */
        printf( "outer: in\r\n" );
        helper();                                /* 嵌套重入，不死锁 */
        printf( "outer: out\r\n" );
        xSemaphoreGiveRecursive( xRMutex );      /* 计数 1→0，真正释放 */
        vTaskDelay( pdMS_TO_TICKS( 200 ) );
    }
}

void app_init( void )
{
    xRMutex = xSemaphoreCreateRecursiveMutex();
    xTaskCreate( vWorker, "W", 256, NULL, 2, NULL );
}
```

**预期现象**：
- 每轮依次打印 "outer: in" → "helper: in (2nd take)" → "outer: out"，200ms 一轮，永不卡死。
- 把 `xRMutex` 换成 `xSemaphoreCreateMutex()`、Take/Give 换成普通版重跑：打印停在一次 "outer: in"——helper 里第二次 Take 等自己放手，死锁。
- 故意少写一句 GiveRecursive：第二轮 Take 后别的任务（如果有）永远拿不到锁，但本任务自己照常跑，极具迷惑性。

**验证路径**：F103 实机 + USART printf，先跑递归版看正常循环，再换普通 mutex 版复现死锁。

**常见翻车点**：
- Take/Give 次数配不上对，锁"看起来能拿"但从不真正释放。
- 递归版和普通版 API 混用（Take 配 GiveRecursive），行为未定义。
- 忘了 `xSemaphoreCreateRecursiveMutex` 需要 `configUSE_RECURSIVE_MUTEXES` 置 1，链接或运行时报错。
