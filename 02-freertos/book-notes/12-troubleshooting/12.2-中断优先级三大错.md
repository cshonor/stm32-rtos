# 12.2 中断优先级三大错：红线、分组、FromISR 混用

## 这一篇讲什么

官方技术支持统计里，**中断优先级配置错误常年霸榜**。
坑集中在同一条红线上：`configMAX_SYSCALL_INTERRUPT_PRIORITY`。
三种摔法：红线本身没理解、优先级分组配错让红线失效、
以及从 ISR 里调了不该调的 API。

## 红线是什么

FreeRTOS 的临界区用 `BASEPRI` 寄存器实现：
**不屏蔽全部中断，只屏蔽"逻辑优先级 ≤ 红线"的中断**。

```
中断优先级（Cortex-M：数字小 = 级别高）

 0 ─────── 最高，硬件不可屏蔽区
 ...
红线 ──── configMAX_SYSCALL_INTERRUPT_PRIORITY
           ↑ 数值 ≥ 红线（级别更低）：可以调 FromISR API
           ↓ 数值 < 红线（级别更高）：任何 FreeRTOS API 都不许碰
 15 ───── 最低（PendSV/SysTick 住这里，见 20.1）
```

**规则一句话：凡是 ISR 里要调 `xxxFromISR()` 的中断，
其优先级数值必须 ≥ 红线**（即逻辑级别必须不高于红线）。

为什么？内核临界区屏蔽不到红线以上的中断——
那种 ISR 可以在"内核正在改链表"的瞬间插进来，
如果它也调 API 改同一条链表 = 数据结构被撕裂。
书说这类错"能跑很久才炸"，是最阴险的一类。

## 错误一：优先级数字方向记反

Cortex-M 的 **0 是最高优先级**——和 FreeRTOS 任务优先级
"数字大 = 高"**方向相反**（[3.1 ★坑2](../03-task-management/3.1-任务函数与创建.md)）。

常见摔法：想把某个 UART 中断设成"低于红线、可以调 API"，
写了 `NVIC_SetPriority(USART1_IRQn, 2)`——
数值 2 < 红线 5，**级别比红线还高**，这个 ISR 调 API 就是违规。
正确是设成数值 ≥ 5（如 6、7）。

配了 configASSERT 的新版内核会在 FromISR API 里**当场断言抓你**——
这是 [11.1](../11-developer-support/11.1-configASSERT总开关.md) 最值钱的一次出场。

## 错误二：优先级分组配错，红线静默失效

`NVIC_PRIORITYGROUP_x` 决定优先级寄存器的 8 位
怎么切成"抢占位 / 子优先级位"。FreeRTOS 要求：
**全部 4 位（F103 实现 4 位）都归抢占优先级，即 `NVIC_PRIORITYGROUP_4`**。

| 分组配错 | 后果 |
|---|---|
| 用了子优先级位 | 低位的优先级设置被当成子优先级，**抢占级别全挤在高几位**——你以为设了 6 和 7 两级，实际抢占级别相同，红线边界全乱 |
| 启动代码和 FreeRTOS 各设一次 | 后设者覆盖先设者，谁在什么时间生效看缘分 |

摔法特征：HAL_Init 或某些库默认设了分组，FreeRTOS 期望另一种。
书的要求：整个系统只允许设一次，且必须是 GROUP_4。

## 错误三：在 ISR 里调了非 FromISR API

| 调了什么 | 为什么炸 |
|---|---|
| `xQueueSend`（无 FromISR） | 内部可能阻塞/进临界区版本不对——ISR 不能阻塞，链表操作未按 ISR 上下文保护 |
| `vTaskDelay` 等任何阻塞 API | ISR 没有"任务"可阻塞，语义上就是灾难 |
| printf | 见 [12.1](12.1-症状病因对照表.md)：慢 + 不可重入 + 栈在 MSP 上爆 |

判别口诀：**ISR 里只能调名字以 `FromISR` 结尾的 API**，
且调完要把 `pxHigherPriorityTaskWoken` 交给 `portYIELD_FROM_ISR`
（机制见 [4.3 FromISR 家族](../04-queue-management/4.3-FromISR家族.md)）。

## 三错合一的自查清单

1. 所有会调 FromISR API 的中断，优先级数值 ≥ `configMAX_SYSCALL_INTERRUPT_PRIORITY`？
2. 优先级分组只设了一次，且是 `NVIC_PRIORITYGROUP_4`？
3. ISR 里出现的每个内核 API，名字都以 `FromISR` 结尾？
4. configASSERT 配了？（新版内核能在违规现场直接断言）

## 要点回顾

1. 红线 = `configMAX_SYSCALL_INTERRUPT_PRIORITY`：数值 ≥ 它才能调 API。
2. 方向记反是头号摔法：Cortex-M **数字小 = 级别高**。
3. 分组必须 `NVIC_PRIORITYGROUP_4` 且只设一次，否则红线静默失效。
4. ISR 里只认 `FromISR` 后缀；configASSERT 能在违规现场抓人。

<details>
<summary>Q1：为什么红线以上的中断连 FromISR API 都不能调？</summary>

因为内核保护数据结构的手段是"把 BASEPRI 抬到红线"——
这只屏蔽得了数值 ≥ 红线的中断。红线以上的中断在内核改链表的
中途也能插进来，此时它若调 API 改同一条链表，没有第二道锁。
书的结论是：这类"高于红线的快速中断"要么纯硬件操作不碰内核，
要么把活儿交给 deferred 任务（[ch06 中断管理](../06-interrupt-management/README.md) 的正题）。

</details>

<details>
<summary>Q2：configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY 和 configMAX_SYSCALL_INTERRUPT_PRIORITY 什么关系？</summary>

前者是**库语义值**（0–15 的逻辑级别），后者是**写进 NVIC 寄存器的值**
（已左移到实现位的高位，F103 上 = 逻辑值 << 4）。
`NVIC_SetPriority` 吃的是库语义值——别拿移位后的值去和它的参数比，
差 16 倍。这也是"优先级数字"在不同 API 里看起来不一致的原因。

</details>
