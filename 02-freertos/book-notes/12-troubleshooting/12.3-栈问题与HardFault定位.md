# 12.3 栈问题的三种死相与 HardFault 定位路径

## 这一篇讲什么

HardFault 是 Cortex-M 的"总住院医师"——所有没配独立处理器的错误
（MemManage/BusFault/UsageFault）最后都汇到这里。
本篇给两件事：**栈类问题的三种典型死相**，
和一套**从 HardFault 现场挖出肇事 PC** 的固定套路。

## 栈问题的三种死相

| 死相 | 机理 | 第一嫌疑 |
|---|---|---|
| **死在陌生函数里**，调用栈看不懂 | 任务栈写爆，踩了自己栈下方的数据，变量/返回地址被改 | 该任务栈太小 → [11.2](../11-developer-support/11.2-栈溢出检测两档.md) |
| **切换任务后立刻跑飞**，PC 在火星 | 栈溢出踩了别的任务的栈，被踩任务弹现场时弹出垃圾 | 谁的栈爆了——溢出钩子会给名字 |
| **一进中断就死** | MSP 爆了（深层嵌套 / ISR 里大局部数组） | MSP 不在任务栈检测范围内，静态核算 + 调试器看 MSP |

共同教训：**栈溢出几乎从不死在溢出发生的那一刻**——
它腐蚀的是别人的现场，案发和死亡之间隔着任意长的时间。
所以 [11.2](../11-developer-support/11.2-栈溢出检测两档.md) 的填充模式检测（抓"历史痕迹"）是刚需。

## HardFault 定位套路：先分 MSP 还是 PSP

进 HardFault 时，CPU 自动把一份现场**压到"出事时正在用的那个栈"上**。
FreeRTOS 里任务跑 PSP、中断跑 MSP（见
[20.1](../../../01-stm32/book-notes/20-towards-freertos/20.1-任务与调度的硬件落点.md)），
所以第一步必须判断**现场压在哪**——看 LR（EXC_RETURN）的 bit 2：
`LR & 0x4 == 0` → 现场在 MSP（中断/内核上下文）；否则在 PSP（某任务里）。

裸 C 的 handler 拿不到这个 LR 值（进 handler 时 LR 已变），
标准做法是用**一小段汇编把正确的栈指针传给 C 函数**：

```c
/* 汇编入口（GCC 语法，概念示意） */
__attribute__( ( naked ) ) void HardFault_Handler( void )
{
    __asm volatile(
        "tst lr, #4          \n"  /* 测 EXC_RETURN bit 2 */
        "ite eq              \n"
        "mrseq r0, msp       \n"  /* bit2=0 → MSP */
        "mrsne r0, psp       \n"  /* bit2=1 → PSP */
        "b prvHardFaultC     \n"  /* r0 = 出事时的栈顶 */
    );
}
```

## 第二步：从压栈现场里读 stacked PC

异常压栈的 8 个字布局（Cortex-M 固定格式）：

```
栈顶 → [0] R0   [1] R1   [2] R2   [3] R3
       [4] R12  [5] LR ← 出事前返回地址
       [6] PC  ← ★ 肇事指令地址   [7] xPSR
```

```c
void prvHardFaultC( uint32_t *pulStack )
{
    volatile uint32_t pc = pulStack[ 6 ];  /* 肇事 PC */
    volatile uint32_t lr = pulStack[ 5 ];
    ( void ) pc; ( void ) lr;
    for( ;; );  /* 停车，调试器看 pc/lr */
}
```

拿到 `pc` 之后：

1. **对照 .map 文件**（或 `arm-none-eabi-addr2line -e xxx.elf <pc>`）
   查到函数和行号；`lr` 再给一级调用来源；
2. PC 来自 PSP → 某任务出的事，结合 `pxCurrentTCB` 看任务名
   （[11.1 Q1](../11-developer-support/11.1-configASSERT总开关.md)）；
   来自 MSP → 中断/内核上下文，先怀疑 [12.2](12.2-中断优先级三大错.md)。

## 顺手看故障状态寄存器

| 寄存器 | 告诉你什么 |
|---|---|
| `SCB->CFSR` | 故障类型：精确/非精确总线错、未定义指令、非法状态切换、除零等 |
| `SCB->MMFAR` / `BFAR` | **肇事内存地址**（仅"精确"总线错时有效） |

"非精确总线错"时 PC 已偏离肇事点几条指令，前后看几条，别死磕一条。

## 要点回顾

1. 栈问题三死相：死在陌生函数 / 切换后跑飞 / 一进中断就死。
2. HardFault 定位第一步：**LR bit 2 判别 MSP/PSP**，汇编入口传对栈指针。
3. stacked PC = `pulStack[6]`，配合 addr2line/.map 直接定位到行。
4. CFSR 给故障类型，精确总线错时 BFAR/MMFAR 给肇事地址。

<details>
<summary>Q1：为什么不用编译器生成的默认 HardFault_Handler？</summary>

默认 handler 通常是个 `b .` 死循环——它替你"停车"了，
但**没保留 LR 判别和栈指针**，调试器连上时关键上下文全丢。
naked 入口的意义就是在第一时间把"案发现场坐标"固定下来。

</details>

<details>
<summary>Q2：stacked PC 指向的函数看起来完全无辜，怎么回事？</summary>

两种典型情况：① 栈溢出踩了数据——这个函数的**变量**被别人改了，
它是受害者不是凶手，回头查 [11.2](../11-developer-support/11.2-栈溢出检测两档.md)；
② 非精确总线错——PC 已过肇事点，前后看几条指令。
另外 PC 落在 RAM 区或对齐异常地址，多半是**返回地址被踩**，沿"谁写过这个栈区域"查。

</details>
