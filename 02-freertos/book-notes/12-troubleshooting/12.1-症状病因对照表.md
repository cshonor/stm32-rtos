# 12.1 症状→病因对照表：死在 vTaskStartScheduler 之前/之后

## 这一篇讲什么

书尾把多年技术支持里**最高频的死机原因**排了个榜。
本篇按"死在哪一刻"组织成对照表：**先定位死相，再查病因**。
原则是：90% 的 FreeRTOS 死机逃不出这几类，逐条对就行。

## 死相一：vTaskStartScheduler 一调就 HardFault

| 候选病因 | 机理 | 怎么验证 |
|---|---|---|
| heap 太小，空闲任务建不出来 | 启动调度器时要 `pvPortMalloc` 空闲任务 TCB+栈 | 配 malloc 失败钩子（[11.1](../11-developer-support/11.1-configASSERT总开关.md)），看是不是停在钩子里 |
| 中断向量表没被正确接管 | SysTick/PendSV/SVC 的向量还指着启动文件的空壳 | 核对工程用的是 **FreeRTOS 提供的 port 层**，SVC_Handler 等名字要对上 |
| MSP 栈不够 | 启动阶段一切还在 MSP 上（见 [20.1](../../../01-stm32/book-notes/20-towards-freertos/20.1-任务与调度的硬件落点.md)） | 链接脚本里 `_Min_Stack_Size` 放大试试 |

## 死相二：调度器跑起来了，但任务永远不切 / 只有一个任务在跑

| 候选病因 | 机理 |
|---|---|
| **SysTick 优先级没调成最低** | tick 中断抢占一切或根本不触发——心跳没了，调度停摆（[19.1](../../../01-stm32/book-notes/19-systick-and-timer/19.1-SysTick是内核自带的心跳.md) 的"RTOS 里要调低"说的就是这个） |
| 优先级数字方向记反 | FreeRTOS **数字大 = 优先级高**，和中断优先级相反（[3.1](../03-task-management/3.1-任务函数与创建.md) ★坑2）。以为给了最高其实给了最低，被空闲任务压着 |
| 高优先级任务不阻塞 | 死循环里没有任何阻塞调用，低优先级任务永远饿死——这是**逻辑错误不是 bug**（[3.3](../03-task-management/3.3-优先级与调度.md)） |

## 死相三：跑一会儿才死（最折磨人的一类）

| 候选病因 | 典型潜伏期 | 检测手段 |
|---|---|---|
| 栈溢出 | 秒~天 | [11.2 栈溢出检测方法二](../11-developer-support/11.2-栈溢出检测两档.md)，当场抓 |
| heap 慢性耗尽（创建失败没检查返回值 / 反复创建不删除） | 分钟~周 | `xPortGetMinimumEverFreeHeapSize`（[11.3](../11-developer-support/11.3-任务与堆水位观测.md)）单调下降就是漏 |
| 任务函数返回了 | 立刻或随机 | [3.1 铁律 2](../03-task-management/3.1-任务函数与创建.md)：函数体必须是死循环 |
| 时间比较写法错误 | **49.7 天** | `uint32_t` 回绕，见 [19.6 时间相关的三个经典 Bug](../../../01-stm32/book-notes/19-systick-and-timer/19.6-时间相关的三个经典Bug.md)；RTOS 里等价物是 `xTaskGetTickCount` 的差值比较 |

heap 耗尽的症状学：`xTaskCreate`/`xQueueCreate` 开始返回失败，
但若没检查返回值、没配 malloc 钩子，**第一块多米诺倒下时毫无声息**，
之后某个队列发送静默失败、数据丢失，最后才是莫名其妙的崩溃。
所以书的态度是：**所有创建 API 的返回值都要查，malloc 钩子必须配**。

## 死相四：printf 一多就死

printf 在 RTOS 里是事故高发区，三重原因：

1. **互踩**：两个任务同时 printf，输出交错还算轻的；
   newlib 的 printf 内部有全局状态（缓冲、堆锁），
   不做重入保护就是数据竞争。
2. **栈胃口大**：printf（尤其带浮点）一次吃掉几百字节栈，
   在只有 512 字节栈的任务里调用 = 直接爆栈（11.2 的检测会抓）。
3. **慢**：一次 printf 是毫秒级，插在时序敏感路径里，
   bug 反而消失（Heisenbug），撤了 printf 又复发——
   这正是 [11.4 trace 钩子](../11-developer-support/11.4-trace钩子宏家族.md)
   存在的原因。

对策：日志走**单一任务**（各任务把消息发队列，一个日志任务统一输出），
或至少给 printf 套互斥锁（[ch07](../07-resource-management/README.md) 的互斥量）。

## 排查顺序总纲

```
死机
 → ① 停在断言/钩子里？      → 现场就是答案
 → ② 调度器都没起来？       → 查 heap、向量表、MSP
 → ③ 起来了不切任务？       → 查 SysTick 优先级、优先级方向
 → ④ 跑一会儿才死？         → 栈检测方法二 + 堆水位 + 查任务函数返回
 → ⑤ 和 printf 相关？       → 单一日志任务
 → ⑥ 以上都不是             → 进 12.2（中断）/ 12.3（HardFault 定位）
```

## 要点回顾

1. 先分类死相（启动即死 / 不切任务 / 跑会儿死 / printf 诱发），再对病因。
2. 三大经典：**栈溢出、heap 耗尽、优先级方向记反**。
3. printf 互踩/爆栈/扰动时序三重罪，日志必须单任务化。
4. 时间比较的回绕安全写法，裸机的账 RTOS 里照样要还。

<details>
<summary>Q1：为什么"高优先级任务空转饿死别人"不算内核 bug？</summary>

抢占式调度的契约就是：**最高优先级就绪任务独占 CPU**。
一个永不阻塞的高优先级任务 = 宣称"我永远最重要"，
内核只是忠实执行。书给的解法：要么该任务里有阻塞调用
（`vTaskDelay`、队列等待），要么降优先级，要么开时间片轮转
（`configUSE_TIME_SLICING`，同优先级轮转）。设计问题，不是配置问题。

</details>

<details>
<summary>Q2：所有创建 API 都查返回值，代码会不会很啰嗦？</summary>

会，但书的立场是这属于"嵌入式基本功"——和裸机篇查 HAL 返回值同理。
折中：配好 malloc 失败钩子 + configASSERT 后，
可以把"创建失败"视为致命错误，只在开发期逐个点查，
发布版信任钩子兜底。两种风格都比"裸奔不查"强一个量级。

</details>
