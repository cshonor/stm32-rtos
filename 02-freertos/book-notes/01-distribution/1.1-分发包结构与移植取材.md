## 这一篇讲什么

官方 zip 解压出来几百个文件，第一次见的人很容易整个拖进工程。
本篇回答两个问题：**Source/ 和 Demo/ 的分工是什么，移植一个 F103
工程最小要取哪几个文件。**

## 分发包顶层结构

```
FreeRTOS/
├── Source/            ← 内核本体，移植唯一真正需要的目录
│   ├── tasks.c        ← 任务调度：TCB、就绪名单、切换、阻塞
│   ├── queue.c        ← 队列 + 信号量 + 互斥量（三者共用同一实现）
│   ├── list.c         ← 双向链表（内核的"容器标准库"）
│   ├── timers.c       ← 软件定时器（可选，ch05）
│   ├── event_groups.c ← 事件组（可选，ch08）
│   ├── croutine.c     ← 协程（已淘汰，别用）
│   ├── portable/      ← 移植层 + heap 分配器（见 1.2）
│   └── include/       ← 全部公共头文件
└── Demo/              ← 几十块板子的示例工程，仅供参考，别抄整个
```

**三个核心 .c 缺一不可**：`tasks.c`、`queue.c`、`list.c`。
`list.c` 只有几百行，但 TCB、就绪名单、延时名单全靠它——
省了它整个内核连不起来。

## 最小取材清单（F103 + GCC 工具链）

| 类别 | 文件 | 不拿的后果 |
|---|---|---|
| 核心 | `tasks.c` `queue.c` `list.c` | 内核不存在 |
| 头文件 | `include/` 整个目录 | 编不过 |
| port 层 | `portable/GCC/ARM_CM3/port.c` + `portmacro.h` | 无法切换任务、无 tick |
| heap | `portable/MemMang/heap_4.c`（五选一） | `xTaskCreate` 没有内存来源 |
| 自己写 | `FreeRTOSConfig.h`（见 [1.3](1.3-FreeRTOSConfig逐项过一遍.md)） | 所有 config 宏未定义，编不过 |

数下来就是：**3 个核心 .c + 1 个 port + 1 个 heap + 1 个自己的 Config**，
加头文件目录，一共"6 个文件 + 一个目录"。
用到软件定时器/事件组时再加 `timers.c` / `event_groups.c`。

## 获取方式与版本概念

- 官网下载 zip，或 GitHub 上 `FreeRTOS/FreeRTOS-Kernel` 仓库
  （V10.4 之后官方主推按 git 仓库引用，源码树更小，不含 Demo）
- **LTS（Long Term Support）版本**：官方对特定版本提供长期维护
  （安全修复、缺陷修复），产品选型时优先 LTS，别追最新 main 分支
- 书基于 V10 时代写作；V11 目录有微调（如 portable 路径细化），
  具体路径待实验时以官方仓为准

## 为什么不能把 Demo 整个复制来改

Demo 工程里塞了：开发板特定驱动、厂商 HAL、测试用例任务、
IDE 工程文件。复制过来的问题是：

1. 不知道哪个文件是"内核必需的"、哪个是"示例特有的"，删错就崩；
2. Demo 的 `FreeRTOSConfig.h` 按那块板的晶振配的，时钟频率不对
   tick 速率全错（"编译过但跑死"的经典来源之一）；
3. 无用任务占着 RAM，F103 的 20K 经不起。

**正确姿势：空工程 + 最小取材清单 + 自己写 Config + 参考 Demo
里 CORTEX_STM32F103 系列的 Config 值做对照。**

## 要点回顾

1. 移植只认 `Source/`，`Demo/` 仅供找感觉。
2. 最小集 = tasks/queue/list 三核心 + 一个 port + 一个 heap + 自写 Config。
3. `list.c` 虽小，是内核容器的地基，省不得。
4. 版本选型优先 LTS；V11 目录与书有出入，以官方仓为准。

<details>
<summary>Q1：queue.c 为什么连信号量也一起实现了？</summary>

FreeRTOS 的信号量、互斥量、递归锁**在代码层面就是队列的特例**：
信号量 = 长度为 N、单项大小为 0 的队列（只存"计数"，不存数据）。
所以 queue.c 一个文件承担了"数据通道 + 同步原语"两块功能，
这也是 ch04/ch06/ch07 的 API 底层都是同一套队列机制的原因。

</details>

<details>
<summary>Q2：croutine.c 是什么，为什么别用？</summary>

协程（co-routine）是 FreeRTOS 早期为极小 RAM 芯片设计的
"共享栈的轻量任务"，代价是一堆限制（不能跨函数阻塞等）。
官方已多年不维护、不推荐新项目使用。
F103 有 20K RAM，正常用任务即可，croutine.c 不要编进工程。

</details>
