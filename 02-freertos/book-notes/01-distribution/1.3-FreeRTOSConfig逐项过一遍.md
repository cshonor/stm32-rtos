## 这一篇讲什么

`FreeRTOSConfig.h` 是整个 FreeRTOS 唯一的配置文件——**编译期裁剪
开关 + 芯片参数 + 行为钩子**全在这里。本篇按功能分组把关键宏过一遍，
并标出"配错会编译过但跑死"的三颗雷。

## 芯片参数组：三颗雷都在这里

```c
#define configCPU_CLOCK_HZ            ( ( unsigned long ) 72000000 )
#define configTICK_RATE_HZ            ( ( TickType_t ) 1000 )
#define configMAX_SYSCALL_INTERRUPT_PRIORITY   5   /* 数值制，见 ch06 */
```

| 宏 | 作用 | 配错的后果 |
|---|---|---|
| `configCPU_CLOCK_HZ` ★雷1 | 告诉内核主频，port 用它算 SysTick 重装值 | 算错 → tick 速率整体偏快/偏慢，所有 `vTaskDelay` 时间全错，**能编译能跑就是时间不对** |
| `configTICK_RATE_HZ` | tick 频率，常用 1000（1ms） | 太高 → tick 中断吃掉 CPU；太低 → 延时粒度变粗 |
| `configMAX_SYSCALL_INTERRUPT_PRIORITY` ★雷2 | 中断优先级红线，见 [6.3](../06-interrupt-management/6.3-中断优先级红线.md) | 配错 → 调 API 的中断和内核临界区互相踩，**偶发跑飞，最难查** |
| `configKERNEL_INTERRUPT_PRIORITY` | 内核自身中断（PendSV/SysTick）优先级 | 必须最低，port 一般已兜底，别动 |

★雷3 在下表：`configTOTAL_HEAP_SIZE` 给小了——`xTaskCreate` 静默失败，
任务没建起来但 main 里看不出来（对策见
[2.3 本仓选型 heap_4](../02-heap-memory/2.3-本仓选型heap_4.md) 的 malloc failed hook）。

## 调度行为组

```c
#define configUSE_PREEMPTION          1     /* 抢占式，RTOS 的默认 */
#define configUSE_TIME_SLICING        1     /* 同优先级轮转 */
#define configMAX_PRIORITIES          7     /* 优先级级数，越少越省 RAM */
#define configMINIMAL_STACK_SIZE      128   /* 单位：字；空闲任务栈深 */
#define configUSE_IDLE_HOOK           0
#define configUSE_TICK_HOOK           0
```

- `configUSE_PREEMPTION = 1`：高优先级就绪立刻抢 CPU；关掉变协作式，几乎没人关
- `configMAX_PRIORITIES` 决定就绪名单数组长度（每级占 RAM），F103 给 7 够用

## 功能裁剪组：用不到就关掉省 flash

```c
#define configUSE_MUTEXES                   1
#define configUSE_COUNTING_SEMAPHORES       1
#define configUSE_TIMERS                    0   /* 软件定时器，见 ch05 */
#define configUSE_TASK_NOTIFICATIONS        1
#define configUSE_QUEUE_SETS                0
#define INCLUDE_vTaskDelay                  1
#define INCLUDE_vTaskDelete                 1
```

两族开关：**configUSE_xxx** 控内核功能是否编译进；**INCLUDE_xxx**
控单个 API 是否可用（关掉后链接器把对应代码丢掉）。
01 阶段 `configUSE_TIMERS` 先置 0，用到 ch05 再开。

## 堆与钩子组

```c
#define configTOTAL_HEAP_SIZE         ( ( size_t ) ( 10 * 1024 ) )
#define configUSE_MALLOC_FAILED_HOOK  1     /* 分配失败当场停车 */
#define configCHECK_FOR_STACK_OVERFLOW 0    /* 调通后再开 1 或 2 */
```

F103 共 20K RAM，堆给 10K 是 01 实验的保守起点
（水位读数待实验验证，见 [2.3](../02-heap-memory/2.3-本仓选型heap_4.md)）。

## 中断映射组（Cortex-M port 的收尾）

```c
/* 让内核接管向量表里的三个异常入口（GCC port 的惯用写法） */
#define vPortSVCHandler     SVC_Handler
#define xPortPendSVHandler  PendSV_Handler
#define xPortSysTickHandler SysTick_Handler
```

这三行把启动文件向量表里的弱符号名映射到 port.c 的实现——
漏了的话第一个任务永远启动不了（进 SVC 后落到默认死循环）。

## 与裸机篇对照

裸机篇 [ch19 SysTick](../../../01-stm32/book-notes/19-systick-and-timer/README.md)
手写 `SysTick->LOAD = 72000000/1000 - 1`；RTOS 里这步由 port.c 代劳，
参数来源就是雷 1 的两个宏——雷 1 的本质是"除法被宏算错了"。

## 要点回顾

1. 三颗雷：CPU 时钟宏、中断红线宏、堆太小——全是"编译过但跑死"型。
2. 裁剪两族：configUSE_xxx 控功能，INCLUDE_xxx 控 API。
3. 三行 Handler 映射把向量表交给 port.c，漏了启动即卡死。
4. tick 1000Hz、优先级 7 级、堆 10K 是 F103 的保守起点，实测后再调。

<details>
<summary>Q1：configTICK_RATE_HZ 能不能配 10000 让延时更精细？</summary>

能编过，但 tick 中断频率提高 10 倍，就绪检查与切换的固定开销也乘 10，
F103 上占比可观。要更细的时基请用硬件定时器，不是靠堆 tick 频率。
具体开销待实验验证。

</details>

<details>
<summary>Q2：为什么配置全是 #define 而不是结构体？</summary>

编译期常量让不用的功能**直接被预处理器/链接器删掉**——裁剪后内核
可以小到几 KB flash，运行时配置做不到。代价：改配置必须全量重编。

</details>
