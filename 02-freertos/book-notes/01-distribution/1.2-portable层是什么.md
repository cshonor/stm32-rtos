## 这一篇讲什么

FreeRTOS 内核 90% 是硬件无关的 C（tasks.c/queue.c/list.c），
剩下 10% 必须贴着具体芯片写——这部分被隔离在 `portable/` 目录，
称为 **port 层（移植层）**。本篇讲它封装的三件事、目录怎么选、
以及为什么 F103 用现成的 `GCC/ARM_CM3` 完全不用改。

## port 层封装的三件事

| 职责 | 落在哪 | 为什么必须硬件相关 |
|---|---|---|
| **上下文切换** | port.c 里的汇编：PendSV 异常里保存/恢复寄存器现场 | 寄存器集、栈帧布局是 CPU 架构决定的 |
| **tick 心跳与首次启动** | SysTick 配置、SVC 启动第一个任务 | SysTick 是内核外设，寄存器地址随架构 |
| **临界区进出** | portmacro.h：`taskENTER_CRITICAL` → 操作 BASEPRI | 用哪个特殊寄存器屏蔽中断随架构 |

对应裸机篇的概念：上下文切换就是 [ch20.1](../../../01-stm32/book-notes/20-towards-freertos/README.md)
讲的"一个任务 = 一个栈 + 一份现场"的保存/恢复动作。

## portable/ 目录怎么选：两层定位

```
portable/
├── GCC/ARM_CM3/        ← 编译器 × 架构
├── GCC/ARM_CM4F/
├── IAR/ARM_CM3/
├── Keil/...
├── RVDS/...
└── MemMang/            ← heap_1~heap_5（与 CPU 无关，独立一类）
```

选 port 层看**两个轴**：

1. **编译器**：本仓用 arm-none-eabi-gcc → `GCC/`
2. **CPU 架构**：F103 = Cortex-M3（无 FPU）→ `ARM_CM3`

所以路径是 `portable/GCC/ARM_CM3/`。若是 F407（M4 带 FPU）则选
`GCC/ARM_CM4F/`——FPU 寄存器也要进出现场，不能用 M3 的 port。

## 为什么 ARM_CM3 不用改一行

Cortex-M 内核是 ARM 定义的**标准化内核**：NVIC、SysTick、PendSV、
SVC、BASEPRI、栈帧布局在所有 M3 芯片上完全一致，与厂商无关。
ST、NXP、GD 的 M3 只是外挂不同，内核行为相同。

port 层只依赖这些标准化部件，所以：

- **同架构同编译器 → port.c 零修改**（F103/GD32/任何 M3 都通用）
- 芯片差异（时钟频率、外设、向量表）走 `FreeRTOSConfig.h` 和
  启动文件解决，不碰 port 层

这与裸机篇 [ch11](../../../01-stm32/book-notes/11-linker/README.md) 的分工一致：
启动文件/向量表是板级的，port.c 是架构级的。

## port 层对上层暴露的接口

```c
/* portmacro.h 提供，内核与应用程序都靠它们 */
taskENTER_CRITICAL() / taskEXIT_CRITICAL()   /* 临界区（BASEPRI 屏蔽） */
portYIELD()                                   /* 任务上下文主动让出 */
portYIELD_FROM_ISR( x )                       /* ISR 尾部请求切换 */

/* port.c 提供，由内核调用 */
xPortStartScheduler()   /* 配置 SysTick、启动第一个任务 */
vPortEndScheduler()     /* 停止调度（很少用） */
```

应用代码**不直接调 port.c 的函数**，都是通过
`xTaskCreate`/`vTaskDelay`/`taskENTER_CRITICAL` 这类
架构无关 API 间接触达——这就是隔离的意义：换芯片时应用层一行不动。

## heap 分配器为什么也算 portable

`portable/MemMang/` 下的 heap_1~heap_5 与 CPU 架构无关，
放在 portable 只是因为"内存布局策略也是移植决策"。
选型表见 [2.2 heap 五个分配器选型](../02-heap-memory/2.2-heap五个分配器选型.md)，
本仓用 heap_4。

## 要点回顾

1. port 层 = 上下文切换 + tick/启动 + 临界区，三件事全是架构相关的。
2. 选 port 看两个轴：编译器（GCC）× 架构（ARM_CM3）。
3. Cortex-M 内核标准化 → 同架构 port 零修改；芯片差异走 Config 与启动文件。
4. 应用只调架构无关 API，不直接碰 port 层。

<details>
<summary>Q1：PendSV 为什么被 port 层设为最低优先级？</summary>

PendSV 是上下文切换的实际执行场所。把它设为**最低**优先级，
保证任何中断都能打断"正在切换"的过程、且切换只在所有 ISR 退净后
发生——切换现场时若被更高优先级中断插队，保存到一半的栈帧就乱了。
这也是 port.c 里 `configKERNEL_INTERRUPT_PRIORITY` 全 1（最低）的原因。

</details>

<details>
<summary>Q2：如果用了没有现成 port 的编译器/芯片怎么办？</summary>

抄一份架构最接近的 port 目录改名改：核心是 port.c 里那几段汇编
（PendSV 处理、SVC 启动）和 portmacro.h 的类型/临界区定义。
工作量不大但**调试成本极高**（切换错误 = 随机 HardFault）。
本仓 F103 + GCC 有现成 port，永远别自写。

</details>
