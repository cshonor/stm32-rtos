# 3.5 空闲任务与钩子函数：系统在"没事干"时干什么

## 这一篇讲什么

`vTaskStartScheduler()` 启动时，内核自动创建一个**优先级 0** 的空闲任务
（idle task）。它看起来是"没事干时的占位符"，实际背着两份正经工作：
**给被删的任务收尸**，和**给你留一个钩子函数的挂载点**。

## 为什么空闲任务必须存在

调度器的不变量是"**永远要有任务能跑**"。
当所有应用任务都 Blocked/Suspended 时，Ready 池里如果空无一人，
调度器就没有合法选择——所以内核保证池底永远坐着空闲任务。

```
Ready 池：  [P3: 任务A] [P1: 任务B] [P0: idle] ← 永远在场
```

推论：**优先级 0 不是你的**——应用任务从 1 开始排，
把任务建在优先级 0 等于和系统保姆抢饭吃。

## 正经工作一：收尸人

`vTaskDelete()` 删除一个任务时，**TCB 和栈不是当场释放的**——
如果任务删的是自己，它此刻还站在自己的栈上执行代码，
当场释放栈 = 抽掉自己脚下的地板。所以内核把"待收尸任务"挂到
一个删除名单，**由空闲任务在下一次跑起来时统一释放内存**。

```
vTaskDelete(x)  →  x 挂入"待删除名单"
（所有任务都阻塞后）idle 运行 → 遍历名单 → vPortFree(TCB+栈)
```

**推论（重要）**：如果应用任务**永远不阻塞**（忙等循环），
空闲任务永远抢不到 CPU，删掉的任务内存**永远还不回来**——heap 慢性失血。
这就是为什么"每个任务循环里至少一个阻塞调用"是 FreeRTOS 的养生之道。

## 正经工作二：空闲钩子

`configUSE_IDLE_HOOK = 1` 后实现 `vApplicationIdleHook()`，
空闲任务每轮循环调一次。适合干的事：

- 喂看门狗（低优先级兜底：高优先级卡死时钩子停喂 → 复位）
- 进低功耗（ch10 的简单版方案）
- 统计空闲占比 ≈ 系统负载的粗略读数

**钩子的两条死规矩**：

1. **永不阻塞**——钩子里调任何可能阻塞的 API（哪怕 vTaskDelay(1)），
   空闲任务被挂起 = 收尸停摆 + 调度器底线崩塌；
2. **快进快出**——钩子里磨洋工 = 直接推迟收尸和低功耗。

## 空闲任务栈从哪来

`configMINIMAL_STACK_SIZE`（port 给的默认值，ARM_CM3 通常 130 字 ≈ 520B）
决定空闲任务（和定时器守护任务）的栈深。钩子函数如果用局部变量多、
或 printf，就得**自己调大这个值**——空闲任务栈溢出的死相
和普通任务一样难看（ch11 的栈检测也罩着它）。

## 与 LDD- 侧对照

| | Linux | FreeRTOS |
|---|---|---|
| 无事可跑时 | swapper/idle 进程（PID 0），进 WFI/halt | idle 任务（优先级 0） |
| 资源回收 | kthread 或 RCU 回调延迟释放 | idle 任务收尸已删任务 |
| 钩子 | 无直接对应（内核 idle loop 有 pm 回调） | vApplicationIdleHook |

## 要点回顾

1. 空闲任务（优先级 0）永远在场，是调度器的兜底；应用任务从优先级 1 起。
2. 它是"收尸人"：`vTaskDelete` 的内存由它释放——**应用任务永不阻塞 = 收尸停摆 = heap 失血**。
3. 空闲钩子：永不阻塞、快进快出；栈深看 `configMINIMAL_STACK_SIZE`。

<details>
<summary>Q1：空闲任务能被 vTaskSuspend 挂起吗？</summary>

不能——内核对挂起空闲任务有防御（会触发 configASSERT）。
这符合不变量：空闲任务是"永远能跑"的最后保证，
挂起它等于拆调度器的地基。

</details>

<details>
<summary>Q2：tickless idle（ch10）和空闲钩子是什么关系？</summary>

ch10 的正式低功耗方案**不是**在钩子里睡觉，而是内核在
"即将进入空闲且预计空闲 N tick"时走 `portSUPPRESS_TICKS_AND_SLEEP`：
停 SysTick、睡到下一个事件、醒后补 tick。
钩子里的 `__WFI()` 是"每次空闲都小睡一会"的简易版——
每次都还会被 SysTick 叫醒；tickless 是"一次睡穿 N 个 tick"的正式版。

</details>
