## 这一篇讲什么

两个延时 API 长得像，语义差得远：
**`vTaskDelay` 是"从现在起睡 N tick"（相对时间），
`vTaskDelayUntil` 是"睡到上次唤醒点 + N tick"（绝对节拍）。**
周期任务选错，周期会越漂越远。

## vTaskDelay：相对延时，周期会漂

```c
for( ;; )
{
    干活();                    /* 假设花 0.3 tick */
    vTaskDelay( pdMS_TO_TICKS(10) );   /* 睡 10 tick */
}
```

时间线（tick = 1ms）：

```
t=0      t=0.3        t=10.3   t=10.6        t=20.6
│干活(0.3)│ 睡10tick   │醒│干活(0.3)│ 睡10tick  │醒
```

实际周期 = **干活时间 + 10 tick ≈ 10.3ms**，而且还叠加上下文切换的抖动——
每次循环都"重新计时"，误差**逐次累积**。做 LED 闪烁无所谓，
做 1kHz 采样就是事故。

## vTaskDelayUntil：绝对节拍，周期锁定

```c
TickType_t xLastWakeTime = xTaskGetTickCount();
const TickType_t xPeriod = pdMS_TO_TICKS(10);
for( ;; )
{
    干活();
    vTaskDelayUntil( &xLastWakeTime, xPeriod );
    /* 内核会把 xLastWakeTime 更新为"本次计划唤醒点" */
}
```

时间线：

```
计划唤醒点：  t=10        t=20        t=30   ← 钉死在 10ms 网格上
实际：  干活(0~0.3)睡→醒 干活(10~10.3)睡→醒 干活(20~…)
```

唤醒时刻锚定在**固定 tick 网格**上，干活花的时间被"睡少点"吸收掉——
**干活时间 < 周期时，周期恒等于 10ms，不漂。**
（新版 FreeRTOS 里此 API 已更名为 `xTaskDelayUntil`，老名字保留兼容。）

## 参数是 tick：pdMS_TO_TICKS 别省

API 吃的都是 tick 数。`configTICK_RATE_HZ = 1000` 时 1 tick = 1ms，
但**代码里写死数字 = 和 tick 配置耦合**：

```c
vTaskDelay( pdMS_TO_TICKS(100) );   /* ✅ 改 tick 率也不用改代码 */
vTaskDelay( 100 );                  /* ❌ tick 率改成 500Hz 就变成 200ms */
```

## 精度下限：最多差 1 个 tick

`vTaskDelay(1)` 不是"睡 1ms"——它在**当前 tick 的任意相位**被调用，
到下一个 tick 边界就算"到期"，实际睡眠 0~1ms 随机。
想至少睡 N ms，得写 `pdMS_TO_TICKS(N) + 1` 或接受 ±1 tick 的量化误差。
**所有 tick 级 API 都有这个 ±1 边界问题，做时序预算时把它算进去。**

## 与裸机篇对照（[19.4](../../../01-stm32/book-notes/19-systick-and-timer/19.4-三种等待的对比.md)）

| 等待方式 | CPU | 周期稳定性 | 谁在用 |
|---|---|---|---|
| 忙等 while 计数 | 占满 | 受中断影响漂移 | 裸机 us 级短延时 |
| SysTick 数标志位 | 占满 | 较好 | 裸机 ms 级 |
| vTaskDelay | **零** | 漂移（相对计时） | 非周期任务（闪烁、轮询间隔） |
| vTaskDelayUntil | **零** | **锁定** | 周期任务（采样、控制环） |

## 与 LDD- 侧对照

`vTaskDelay` ≈ `sleep()/nanosleep()`（相对）；`vTaskDelayUntil` ≈
`clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, ...)`（绝对时间）。
Linux 的 cyclic 周期任务用的就是绝对时间模式——同一思想。

## 要点回顾

1. `vTaskDelay` = 相对延时，周期 = 干活时间 + 设定值，会漂。
2. `vTaskDelayUntil` = 绝对节拍，干活耗时被吸收，周期锁定。
3. 毫秒一律走 `pdMS_TO_TICKS`；所有 tick 级等待有 ±1 tick 量化误差。

<details>
<summary>Q1：干活时间超过周期会怎样？</summary>

`vTaskDelayUntil` 发现"下一个计划唤醒点已经过了"，立即返回不睡眠——
任务变成"连轴转"，周期从此失控（错过一拍），但**不会累积成多拍**
（网格点继续向前推）。这本身就是警报：周期任务里干活超时 = 设计超载，
该用运行时统计（ch11）查出来。

</details>

<details>
<summary>Q2：xTaskGetTickCount 回绕怎么办？</summary>

TickType_t 默认 32 位（可配 16 位），1000Hz 下约 49 天回绕。
`vTaskDelayUntil` 内部做了回绕安全比较（用减法代替直接比大小），
应用层自己比较 tick 时也要用 `(now - last) >= period` 的减法写法，
**不要写 `now >= last + period`**——回绕时后者直接翻车。

</details>
