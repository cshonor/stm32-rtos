## 这一篇讲什么

Ready 池里站了好几个任务，调度器选谁？答案三句话：
**优先级高的先跑；一样高的轮转跑；新来的高优先级立刻抢。**
难点全在细节里——尤其是那个"数字方向"的坑。

## 先用人话说一遍（新手铺垫）

调度规则用**急诊分诊**来记：病人按病情分级（优先级），重症一到
**立刻插队**（抢占），同级的排队**每人看一分钟轮换**（时间片）。
门诊不忙时还有个值班医生兜底坐着（空闲任务，优先级 0）。

最大的坑是**两家医院的病历编号规则相反**：FreeRTOS 这家
"号越大病越重"（0 最低），Cortex-M 中断那家"号越小越急"
（0 最高）。同一块芯片上两家医院同时营业，写配置文件时两个体系
的参数就挨着——串了行，症状是"明明设了高优先级却不抢"。

另一个要刻进脑子的：**急诊室不保证普通病人今天能看上病**。
高优先级任务如果永远不睡（不阻塞），低优先级任务就永远轮不到——
这叫"饿死"，不是 bug，是实时系统拿公平换确定性的取舍。

| 术语 | 一句话解释 |
|---|---|
| 优先级位图 | 一个 32 位变量，每一位代表"该优先级有没有人就绪"，选人时不用逐级翻链表 |
| CLZ | Cortex-M3 的一条指令：数出二进制数前面有几个 0——配合位图一步算出最高就绪优先级 |
| 时间片 | 同优先级轮转的单位：固定 1 个 tick，到点就换下一个同级的跑 |
| 饿死（starvation） | 高优先级任务不阻塞时低优先级永远跑不到的现象；RTOS 不防它，靠设计规避 |
| 协作式调度 | 关掉抢占的模式：任务不主动让就一直跑，教学对照用，工程上不选 |

## 铁律零：数字方向（再说一遍，因为它值一篇）

| 体系 | 数字小 | 数字大 | 可用范围 |
|---|---|---|---|
| FreeRTOS **任务**优先级 | 低（0 最低） | **高** | 0 ~ configMAX_PRIORITIES-1 |
| Cortex-M **中断**优先级 | **高**（0 最高） | 低 | 0 ~ 255（按优先级位数） |

任务优先级是**纯软件概念**（就绪名单的数组下标），
中断优先级是**硬件 NVIC（Cortex-M 的中断管理硬件，管优先级与嵌套）概念**——两套数字方向相反，同片共存。
写 `FreeRTOSConfig.h` 时两类配置紧挨着，是全仓最容易写反的地方。

## 规则一：抢占（preemption）

`configUSE_PREEMPTION = 1`（本仓配置，也是主流）时：

```
任何时刻，Running 的 = Ready 池里优先级最高的那个
高优先级任务一旦变 Ready（延时到/队列到数据）→ 立刻抢，当前任务当场让位
```

"立刻"的硬件路径：SysTick（内核周期定时器，tick 心跳来源）ISR（或 FromISR（ISR 里专用的 API 变体家族，见 4.3） API）置位 PendSV（负责任务切换的异常，见 1.2） →
所有中断退完 → PendSV 换现场（[ch20.1](../../../01-stm32/book-notes/20-towards-freertos/20.1-任务与调度的硬件落点.md)）。
**最坏抢占延迟 ≈ 一次临界区（屏蔽中断与切换来保护共享数据的代码段，见 1.2）或一段关中断时间**，这是 RTOS 实时性的命门指标。

`configUSE_PREEMPTION = 0` 是协作式：任务不主动让（阻塞/yield）就一直跑。
基本只用于教学对照，工程上没人用。

## 规则二：同优先级轮转（time slicing）

`configUSE_TIME_SLICING = 1`（默认）时，同优先级的 Ready 任务
**每个 tick 轮转一次**：SysTick 到点 → 同优先级还有别人 Ready →
换人。所以同优先级任务看到的 CPU 是"每人 ~1 tick 的时间片"。

推论：**两个同优先级任务都忙等不阻塞 = 各占一半 CPU**；
想让出得靠阻塞或 `taskYIELD()`（任务主动让出 CPU 的宏）。

## 规则三：空闲任务垫底

优先级 0 预留给空闲任务（[3.5](3.5-空闲任务与钩子.md)），
你的任务从 1 开始排。就绪名单是 `pxReadyTasksLists[0..N-1]` 数组，
调度选人 = 从高到低扫数组找第一个非空名单——**选人 O(1)**
（用 `uxTopReadyPriority` 位图 + CLZ 指令加速，Cortex-M3 有 CLZ）。

## 一图总结调度决策

```
每个 tick（或每次解除阻塞）：
   高优先级有人 Ready？ ──是──► 抢！Running 换人
        │否
   当前任务同优先级还有别人 Ready？ ──是（且时间片开）──► 轮转
        │否
   继续跑
```

## 与 LDD- 侧对照

| | Linux CFS | FreeRTOS |
|---|---|---|
| 调度单位 | vruntime 最小者优先 | 静态优先级最高者优先 |
| 公平性 | 追求公平（按权重分配 CPU） | **不追求公平**——低优先级可以被永远饿死 |
| 抢占延迟 | 较长（吞吐优先） | 极短（实时优先） |
| 时间片 | 动态 | 固定 1 tick（且仅同优先级轮转用） |

**设计哲学差异要刻进脑子**：FreeRTOS 不承诺"每个任务都有机会跑"——
高优先级任务永不阻塞，低优先级就**永远饿死**。这不是 bug，是实时系统的取舍。
优先级分配是设计问题，不是内核问题。

## 要点回顾

1. 任务优先级数字大=高，与 NVIC 中断优先级方向相反，写配置时别串。
2. 抢占式 = 高优先级就绪立即换人；同优先级每 tick 轮转。
3. RTOS 不保证公平：高优先级不阻塞 → 低优先级饿死，优先级分配是设计职责。

<details>
<summary>Q1：configMAX_PRIORITIES 设多大合适？</summary>

够用就好，两个原因：① 就绪名单数组按它开内存，每级一个链表头；
② 用位图加速时它不能超过 32。
F103 学习工程取 **5~7** 足够（空闲 0、应用 1~4、守护任务按配置定）。
优先级多了反而是设计没想清楚的味道。

</details>

<details>
<summary>Q2：同一优先级能建多少个任务？</summary>

没硬上限（heap 够就行）。就绪名单每一级是个链表，同级任务挂同一条链，
轮转就是沿链表走一圈。所以"同级 N 任务"的开销只是轮转时多走几步链表。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| 任务优先级数字小 = 高 | NVIC 中断就是 0 最高 | FreeRTOS 任务是纯软件概念，**数字大 = 高**；两套方向相反，写 `FreeRTOSConfig.h` 时两个参数紧挨着，最容易串 |
| 调度器会保证每个任务都轮到 | "调度"听起来就该公平 | 不保证公平：高优先级任务永不阻塞，低优先级**永远饿死**——这是取舍不是 bug，优先级分配是设计职责 |
| `configMAX_PRIORITIES` 开大多留余量 | 多多益善 | 每级占一个就绪名单链表头的 RAM；用位图加速时还不能超过 32，F103 学习工程 5~7 级够用 |
| 同优先级两个任务忙等，谁先抢到归谁 | 抢占式嘛，强者通吃 | 同优先级**每 tick 轮转**：两个同级任务都忙等 = 各占一半 CPU，谁也饿不死谁 |

## 代码自测

_注：本节代码按 FreeRTOS API 语义编写，未在本仓库环境实跑，上板验证见「验证路径」。_

```c
/* 演示抢占：低优先级持续干活，高优先级睡醒即抢 */
extern void uart_puts( const char * );

static void vLowTask( void *pv )            /* 优先级 1 */
{
    for ( ;; )
    {
        uart_puts( "L" );
        taskYIELD();                /* 主动让出；删掉它也无所谓——高优先级醒着时根本轮不到它 */
    }
}

static void vHighTask( void *pv )           /* 优先级 2 */
{
    for ( ;; )
    {
        uart_puts( "H\r\n" );
        vTaskDelay( 1000 );         /* 睡 1000 tick；一醒立刻抢占 vLowTask */
    }
}

int main( void )
{
    xTaskCreate( vLowTask, "low", 128, NULL, 1, NULL );
    xTaskCreate( vHighTask, "high", 128, NULL, 2, NULL );
    vTaskStartScheduler();
    for ( ;; );
}
```

**预期现象**：
- 每秒出现一次 `H`，其余时间被 `L` 刷屏——高优先级睡眠期间低优先级才有 CPU。
- `H` 出现的瞬间 `L` 流**立刻**断：抢占延迟是 tick 级以下，肉眼看不到过渡。
- 把 `vTaskDelay(1000)` 从 vHighTask 里删掉：`L` 一个字符都不再出现——这就是饿死。

**验证路径**：F103 实机 + USART printf；对照 20-towards-freertos 章最小移植工程。

**常见翻车点**：
- 把任务优先级记成"数字小=高" → 期望的抢占行为整个反过来。
- 高优先级任务忘记阻塞 → 低优先级与空闲任务全饿死，删任务的内存也收不回来（3.5）。
