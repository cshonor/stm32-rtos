## 这一篇讲什么

任意时刻，一个任务**必然且仅**处于四个状态之一。
状态机是理解所有 RTOS 行为的总纲：调度器做的事本质就是
"在 Ready 集合里挑一个变 Running"。

## 先用人话说一遍（新手铺垫）

四个状态用**医院叫号**来记最牢。医院只有一间诊室（单核 CPU）：

- **Running** = 正在诊室里看病的——任何时刻只有一个；
- **Ready** = 候诊区坐着的，检查齐全、随时能看，叫号系统
  （调度器）只从这里挑人；
- **Blocked** = 被派去做检查了——人不在候诊区，**报告出来**
  （事件/时间到）自动回候诊区，还可以挂"最多等多久"（超时）；
- **Suspended** = 被保安按住的——检查报告来了也没用，**只有
  特定的人发话**（`vTaskResume`）才能放回候诊区。

记住这一对的核心区别：**Blocked 是"等条件"，Suspended 是"被按住"**。
后面所有 API（延时、队列、信号量）都是在"把人送进 Blocked"或
"从 Blocked 放回来"上做文章——这张状态图就是全书的地图。

| 术语 | 一句话解释 |
|---|---|
| 阻塞（Blocked） | 任务主动睡觉等事件的状态：不占 CPU，事件到/超时到自动醒 |
| 挂起（Suspended） | 被外力按住的状态：不占 CPU、不等事件，只能被别人 resume |
| 超时（xTicksToWait） | 阻塞 API 的"最多等多久"参数，0=看一眼就走，portMAX_DELAY=死等 |
| 事件 | 能把任务从 Blocked 捞回 Ready 的东西：延时到期、队列来数据、信号量被给等 |
| 调度器 | 内核里负责"选人"的机制：每 tick 或事件发生时从 Ready 池挑最高优先级的上 CPU |

## 四态与转移

```
                    vTaskSuspend()
        ┌───────────────────────────────────┐
        ▼                                   │
   ┌──────────┐   vTaskResume()    ┌────────┴─────┐
   │Suspended │ ─────────────────► │    Ready     │
   └──────────┘                    └──▲───────┬───┘
        ▲                             │       │ 调度器选中
        │                             │       ▼ （抢占/时间片到）
        │                      解除阻塞 │   ┌─────────┐
        │                             └───┤ Running │
        │ 阻塞式 API：                    │  (在 CPU  │
        │ vTaskDelay /                    │   上执行) │
        │ xQueueReceive(超时)…            └────┬────┘
        │                                    │ 调阻塞式 API
   ┌────┴──────┐                             │
   │  Blocked  │ ◄───────────────────────────┘
   └───────────┘
```

| 状态 | 含义 | 调度器看它吗 |
|---|---|---|
| **Running** | 正在 CPU 上执行（单核任意时刻只有一个） | — |
| **Ready** | 能跑但没轮上（有同/高优先级在跑） | ✅ 选人池 |
| **Blocked** | 在等一个**事件**：延时到期 / 队列有数据 / 信号量被给…… | ❌（事件到了自动回 Ready） |
| **Suspended** | 被 `vTaskSuspend` 显式挂起 | ❌（只有 `vTaskResume` 能救） |

## Blocked vs Suspended：最容易混的一对

| | Blocked | Suspended |
|---|---|---|
| 进的方式 | 任务**自己**调阻塞式 API | 任意任务（包括自己）调 `vTaskSuspend` |
| 出的方式 | **事件**（时间到/数据到）+ 可带超时 | **只能**别的任务调 `vTaskResume` |
| 带超时吗 | 可以（xTicksToWait） | 无超时概念 |
| 典型用途 | 等延时、等队列、等信号量 | 调试期冻结任务、休眠一个完整功能模块 |

一句话：**Blocked 是"等条件"，Suspended 是"被按住"。**

## 关键推论：阻塞是有代价承诺的

任务调 `vTaskDelay(100)` 进 Blocked 时，内核把它从 Ready 名单摘下来，
挂到"延时名单"并记好唤醒 tick（系统心跳的计数，默认 1ms 一跳，见 1.3）——**这期间它对调度器完全隐形，
一个指令都不执行，CPU 占有率是零。**

对照裸机 [19.4](../../../01-stm32/book-notes/19-systick-and-timer/19.4-三种等待的对比.md)
的三种等待：忙等（while 数循环）是"占着 CPU 等"，
`vTaskDelay` 是"让出 CPU 等"。**这就是 RTOS 让超级循环里
"等传感器 50ms"不再拖垮全局的机制。**

## 与 LDD- 侧对照

| FreeRTOS | Linux 任务状态 |
|---|---|
| Running | TASK_RUNNING（且在 CPU 上） |
| Ready | TASK_RUNNING（在运行队列里） |
| Blocked | TASK_INTERRUPTIBLE / TASK_UNINTERRUPTIBLE（睡眠等事件） |
| Suspended | TASK_STOPPED（SIGSTOP（Linux 里"暂停进程"的信号）） |

概念几乎一一对应——**RTOS 没有发明新的状态机，只是把 Linux 那套
"睡眠等事件"的思想裁到单片机上**。学两遍记两遍。

## 要点回顾

1. 四态：Running / Ready / Blocked / Suspended；调度器只从 Ready 里挑人。
2. Blocked 等事件可超时；Suspended 只能被别人 resume。
3. 阻塞 = 让出 CPU 的等待，这是 RTOS 解决"等待拖垮全局"的核心机制。

<details>
<summary>Q1：Blocked 的任务超时和事件同时发生怎么办？</summary>

以 API 的返回值区分：`xQueueReceive` 返回 `pdTRUE`（收到了）还是
`pdFALSE`（超时了）。**调用者必须检查返回值**，
不检查就把"超时"当"收到"处理，是队列编程的头号 bug 来源。

</details>

<details>
<summary>Q2：Suspended 的任务被 vTaskDelete 删了，能删吗？</summary>

能。删除不看状态——Suspended 的任务照样删，TCB+栈回收。
反过来不行：**Blocked 的任务没法被"提前唤醒"**
（没有 vTaskWake 这种 API），要么等事件、要么等超时、要么删了它。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| Blocked 和 Suspended 反正都是"不跑" | 两个词混着用 | Blocked 是**等条件**（事件/超时到自动醒）；Suspended 是**被按住**（只有 `vTaskResume` 能救），出路完全不同 |
| 阻塞 API 返回值不用看 | 等到数据才会返回吧 | 超时也会返回：`xQueueReceive` 超时也返回，靠 `pdTRUE/pdFALSE` 区分；不检查 = 把超时当收到，队列编程头号 bug |
| 想提前唤醒一个 Blocked 的任务 | 总有个 wake 之类的 API | 没有：要么等事件、要么等超时、要么 `vTaskDelete` 删了它 |
| Suspended 的任务得先 Resume 才能删 | 挂着的怎么删 | 删除不看状态：Suspended 照样删，TCB+栈照常回收 |

## 代码自测

_注：本节代码按 FreeRTOS API 语义编写，未在本仓库环境实跑，上板验证见「验证路径」。_

```c
/* 演示状态流转：Blocked（vTaskDelay）↔ Ready ↔ Suspended（vTaskSuspend/Resume） */
extern void uart_puts( const char * );

static TaskHandle_t xPrintHandle = NULL;

static void vPrintTask( void *pv )
{
    for ( ;; )
    {
        uart_puts( "tick\r\n" );
        vTaskDelay( 500 );          /* Running → Blocked，500 tick 后自动回 Ready */
    }
}

static void vBossTask( void *pv )
{
    for ( ;; )
    {
        vTaskDelay( 3000 );
        vTaskSuspend( xPrintHandle );   /* 把打印任务按进 Suspended：打印停止 */
        vTaskDelay( 2000 );
        vTaskResume( xPrintHandle );    /* 唯一救它出来的 API */
    }
}

int main( void )
{
    xTaskCreate( vPrintTask, "print", 128, NULL, 1, &xPrintHandle );
    xTaskCreate( vBossTask, "boss", 128, NULL, 2, NULL );
    vTaskStartScheduler();
    for ( ;; );
}
```

**预期现象**：
- 前 3 秒：每 500ms 打一行 `tick`。
- 3~5 秒：打印停止（vPrintTask 被按进 Suspended，**正在 Blocked 的它也醒不来**）。
- 5 秒后：恢复每 500ms 打印——`vTaskResume` 之后才重新参与调度。

**验证路径**：F103 实机 + USART printf，对秒表看打印节奏的三段变化。

**常见翻车点**：
- 把"暂停功能"做成 `vTaskSuspend`，想要"延时等待"也用它 → Suspended 没有超时概念，忘了 Resume 就永远停摆。
- 句柄没存（创建时传 NULL）→ 想 Suspend 时没有工牌可用。
