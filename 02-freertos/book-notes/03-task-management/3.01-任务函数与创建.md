## 这一篇讲什么

FreeRTOS 的一切从"写一个任务函数"开始。任务函数和普通 C 函数
有三条本质区别（铁律），`xTaskCreate` 的五个参数里藏着两个新手必踩的坑。

## 任务函数的三条铁律

```c
void vTaskFunction( void * pvParameters )
{
    for( ;; )
    {
        /* 任务主体 */
    }
    /* 永远不会执行到这里 */
}
```

| 铁律 | 内容 | 违反的后果 |
|---|---|---|
| 1 | **原型固定**：`void f(void *)`，参数靠 void 指针传 | 编不过（好结果）/ 强转后数据读错（坏结果） |
| 2 | **永不返回**：主体是死循环 | 返回 = 跑出函数体，落到任务栈底的"无效地址"，直接 HardFault |
| 3 | **不能自己结束自己还占着资源**：想退出必须 `vTaskDelete(NULL)` | 占着 TCB+栈不释放，heap 慢性漏光 |

裸机对照：`main` 里的超级循环就是"唯一的任务函数"——
RTOS 只是把这个模式**复制了 N 份**，每份配自己的栈。
（所以 ch20.1 说任务 = 一个栈 + 一份现场。）

## xTaskCreate 五参数逐拆

```c
BaseType_t xTaskCreate(
    TaskFunction_t pxTaskCode,        /* ① 任务函数指针 */
    const char * const pcName,        /* ② 名字（调试用，有长度上限） */
    const configSTACK_DEPTH_TYPE usStackDepth,  /* ③ 栈深 ★坑1 */
    void * const pvParameters,        /* ④ 传给任务的 void* 参数 */
    UBaseType_t uxPriority,           /* ⑤ 优先级 ★坑2 */
    TaskHandle_t * const pxCreatedTask );  /* 输出：任务句柄 */
```

**★坑1：③ 的单位是"字"（4 字节），不是字节。**
`usStackDepth = 128` = 512 字节栈。按字节习惯写 512 就是 2K 栈，
F103 的 20K RAM 经不起几次这样的手滑。

**★坑2：⑤ 的数字方向。**
FreeRTOS **数字越大优先级越高**（`0` 最低，`configMAX_PRIORITIES-1` 最高）——
和 Cortex-M 中断优先级"数字越小越高"**正好相反**。
两套体系在同一块芯片上共存，记反了会出现"高优先级任务怎么不抢"的灵异现象。

返回值：`pdPASS` / `pdFAIL`（heap 不够）。配了
`vApplicationMallocFailedHook`（见 [2.03](../02-heap-memory/2.03-本仓选型heap_4.md)）
失败会当场停车，不会静默带病。

## 一个任务从创建到上 CPU 的完整路径

```
xTaskCreate()
  → pvPortMalloc(TCB) + pvPortMalloc(栈)        ← heap_4 出钱（ch02）
  → 栈上伪造一份"初始寄存器现场"（PC=任务函数入口，R0=pvParameters）
  → TCB 挂入"就绪名单"（pxReadyTasksLists[优先级]）
（全部任务建完）
vTaskStartScheduler()
  → 建空闲任务（+定时器守护任务，若启用）
  → 配置 SysTick、置 PendSV/SysTick 为最低优先级
  → 选中最高优先级就绪任务，SVC 异常启动第一个任务
此后：SysTick 心跳 + PendSV 切换（ch20.1 的硬件落点）
```

## 与 LDD- 侧对照

| | Linux | FreeRTOS |
|---|---|---|
| 创建执行体 | pthread_create / clone | xTaskCreate（同步完成，立即可被调度） |
| 栈 | 线程栈由 libc 从进程地址空间切 | 从 ucHeap 显式切，大小你拍 |
| 函数返回 | 线程函数返回 = 线程体面退出 | **任务函数返回 = 事故** |
| 传参 | void *（同款） | void *（同款） |

## 要点回顾

1. 三铁律：固定原型、永不返回、退出走 `vTaskDelete`。
2. 栈深单位是**字**；优先级**数字大 = 高**（和中断优先级方向相反）。
3. 创建即就绪；`vTaskStartScheduler()` 之后世界才开始转。

<details>
<summary>Q1：任务函数真的返回了会怎样？</summary>

port 层伪造的初始现场里，返回地址（LR）通常指到一个"兜底陷阱"
（不同 port 实现不同，有的指到 `prvTaskExitError` 之类的死循环函数）。
现代版本能兜住并停在错误处理里；老版本/自写 port 就是直接跑飞。
**别把安全寄托在兜底层上——返回本身就是 bug。**

</details>

<details>
<summary>Q2：pcName 给任务起名字有什么用？</summary>

纯调试：`uxTaskGetSystemState` / `vTaskList` 打印任务列表时显示名字，
调试器的 RTOS 感知插件（OpenOCD 也支持）也按名字列任务。
长度受 `configMAX_TASK_NAME_LEN` 限制（默认 16，含 \0），
超了被**静默截断**——起名别超 15 字符。

</details>
