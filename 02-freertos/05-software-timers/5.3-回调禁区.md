# 5.3 回调禁区：为什么不能阻塞、阻塞了会拖死谁

>

## 这一篇讲什么

定时器回调函数只有一条纪律，但违反的代价是系统级的：
**回调里绝对不能进入 Blocked（阻塞态：任务睡着等事件、不占 CPU，见 3.2）态。**本篇讲清为什么、
哪些 API 暗藏阻塞、以及"回调里确实要干重活"的正规出路。

## 先用人话说一遍（新手铺垫）

还记得吗：全店只有一个服务员（守护任务），所有定时器回调都归
他一个人跑。现在想象**他在上菜途中睡着了**（回调里阻塞了）——
后果不是"这道菜慢了"，而是：其他到点的菜全出不了、点单窗口
（命令队列）越积越多、别的任务连 `xTimerStart` 都开始失败。
**一个回调打个盹，整个定时器子系统陪葬。**

所以纪律只有一条：回调里**只许快炒，不许炖汤**。任何带"等待"
参数的 API，等待时间必须写 0（"试一把，不行就走"）。真要炖汤
（写 flash、打长日志），正确姿势是回调里敲一下铃
（`xTaskNotifyGive`），喊后厨的专用厨师去做——回调秒回，
慢活在别的任务里慢慢干。

| 术语 | 一句话解释 |
|---|---|
| 任务通知（task notification） | 内核给每个任务内置的"轻量信号"：不走队列、几乎零开销，ch09 详讲 |
| defer to task（甩活） | 标准模式：回调/ISR（中断服务函数）里只发通知，真正的慢活交给一个阻塞等待的专用任务 |
| 零等待调用 | 等待参数写 0 的 API 用法："能办就办，办不了立刻返回"——回调里唯一合法形态 |

## 为什么阻塞是灾难

所有定时器回调**串行跑在同一个守护任务里**（[5.1](5.1-单次与周期定时器.md)）。
回调 = 守护任务代码的一部分。所以：

```c
void vBadCallback( TimerHandle_t t )
{
    vTaskDelay( pdMS_TO_TICKS(1000) );   /* 守护任务 Blocked 1 秒！ */
}
```

这 1 秒内：守护任务挂着 → 其他所有到点定时器的回调**全部排不上**
→ 命令队列也**没人消费**（[5.2](5.2-定时器命令队列.md)），
应用任务的 `xTimerStart` 开始返回 pdFAIL。

**一个回调阻塞 = 拖死全部定时器 + 定时器 API 开始失败。**
这不是一个定时器变慢，是整个定时器子系统停摆。

## 暗藏阻塞的 API 清单

回调里禁用的不是一个函数，是一类——**任何 xTicksToWait ≠ 0 的调用**：

| API | 陷阱形态 |
|---|---|
| `vTaskDelay` / `vTaskDelayUntil` | 明文阻塞 |
| `xQueueReceive(q, portMAX_DELAY)` | 等数据 = 阻塞 |
| `xQueueSend(q, 非0等待)` | 队列满时等空位 = 阻塞 |
| `xSemaphoreTake(sem, 非0等待)` | 等信号量（任务/中断间"报信"的同步工具，ch06） = 阻塞 |
| `xTaskNotifyWait(... 非0等待)` | 等通知 = 阻塞 |
| 定时器 API 自身带非零等待 | 队列满时等 = 阻塞 |

**允许**的等价物：把等待参数全改成 `0`（"试一把，不行就走"）。
例如 `xQueueSend(q, &x, 0)` 在回调里完全合法——发不进就丢弃/计数，
下次再说。

## 重活的正规出路：defer to task

回调里确实要干慢活（写 flash、打印长日志、复杂计算），
标准模式是**回调只做通知，活交给专用任务**：

```c
void vGoodCallback( TimerHandle_t t )
{
    /* 只发通知，零阻塞；处理任务自己在 Blocked 态等着 */
    xTaskNotifyGive( xWorkerTask );
}

void vWorkerTask( void * p )
{
    for( ;; )
    {
        ulTaskNotifyTake( pdTRUE, portMAX_DELAY );  /* 这里阻塞没问题 */
        do_the_slow_work();                          /* 慢活随便干 */
    }
}
```

这正是 [6.1](../06-interrupt-management/6.1-二值信号量中断同步.md)
"延迟中断处理"的同款模式，只是触发源从 ISR 换成了定时器回调。
队列（[4.3](../04-queue-management/4.3-FromISR家族.md)）也能当这个通道，
按"要不要传数据"选：只报信用通知，要传参数用队列。

## 与 ISR 纪律的对照

| | ISR | 定时器回调 |
|---|---|---|
| 能否阻塞 | 绝对不能（没有任务上下文） | 绝对不能（会拖死守护任务） |
| 能调什么 API | 只能 FromISR 家族 | 普通 API 可以，但等待参数必须为 0 |
| 优先级红线 | 受 configMAX_SYSCALL_INTERRUPT_PRIORITY 管 | 不受（它是任务上下文） |
| 重活出路 | 延迟处理（信号量/队列唤醒任务） | 同款：通知/队列唤醒任务 |

注意第二行：回调是任务上下文，所以**可以用普通 API**，
只是等待时间必须为 0——这是和 ISR 最容易混淆的点。

## 要点回顾

1. 回调 = 守护任务的代码；一个回调阻塞 = 定时器子系统整体停摆。
2. 禁区不是某个函数，是"任何非零等待"——等待参数一律写 0。
3. 重活出路：回调里 xTaskNotifyGive / xQueueSend(...,0)，慢活交给专用任务。
4. 回调是任务上下文：普通 API 可用、无中断红线，但纪律比照 ISR。

<details>
<summary>Q1：回调里打印调试信息（printf/UART）行不行？</summary>

阻塞式 UART 发送本质是"等发送完成"，违反纪律。
行得通的做法：把格式化好的字符串 `xQueueSend(...,0)` 给日志任务，
由它慢慢发（裸机篇 [ch09](../../01-stm32/09-uart-serial/README.md)
的 DMA 发送思路在此直接复用）。发不进就丢日志保系统。

</details>

<details>
<summary>Q2：怎么查出"哪个回调在捣乱"？</summary>

给每个回调首尾打 tick 计数（`xTaskGetTickCount` 差值），
耗时超预期的回调就是它；或开 `configUSE_TICK_HOOK` 观察守护任务
心跳是否停摆。具体手段与数据待实验验证。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| 回调里 `vTaskDelay` 只是这个定时器慢一点 | 以为影响局部 | 守护任务整个睡着：全部定时器陪葬 + 命令队列没人消费，`xTimerStart` 开始失败 |
| 回调里不能调任何普通 API | 和 ISR 纪律记混了 | 回调是任务上下文，普通 API 可以调，但**等待参数必须写 0** |
| 回调里 printf 一下调试没事 | 打印而已能有多慢 | 阻塞式 UART 发送 = 等发送完成 = 违规；改 `xQueueSend(...,0)` 给日志任务 |
| 回调受中断优先级红线管 | 和 FromISR 记混 | 回调不是 ISR，不受 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 约束 |

## 代码自测

_注：本节代码按 FreeRTOS API 语义编写，未在本仓库环境实跑，上板验证见「验证路径」。_

```c
static TaskHandle_t xWorkerTask;
static TimerHandle_t t_sample;

void vSampleCb( TimerHandle_t t )          /* 回调：只敲铃，零阻塞 */
{
    xTaskNotifyGive( xWorkerTask );        /* 微秒级，立刻返回 */
}

void vWorkerTask( void *p )                /* 慢活全在这里干 */
{
    for( ;; )
    {
        ulTaskNotifyTake( pdTRUE, portMAX_DELAY );   /* 阻塞没问题 */
        do_the_slow_work();                          /* 写 flash / 长日志随便 */
        printf( "slow work done @%lu\r\n", xTaskGetTickCount() );
    }
}

void app_init( void )
{
    xTaskCreate( vWorkerTask, "worker", 512, NULL, 2, &xWorkerTask );
    t_sample = xTimerCreate( "smp", pdMS_TO_TICKS(500), pdTRUE, 0, vSampleCb );
    xTimerStart( t_sample, 0 );
}
```

**预期现象**：
- 每 500ms 打印一行 `slow work done`，间隔稳定——回调秒回，不拖守护任务
- 即使 `do_the_slow_work` 耗时 2 秒，其他定时器照常到点（守护任务没被占）
- 对照实验：把回调里改成直接调 `do_the_slow_work()`，其他定时器的打印立刻集体停摆

**验证路径**：F103 实机 + USART printf；用第二个周期定时器的打印是否准时来验证守护任务健康。

**常见翻车点**：
- 回调里顺手加一句阻塞式 printf 调试，全部定时器瞬间不准
- `xQueueSend(q, &x, portMAX_DELAY)` 抄进回调——队列一满守护任务就睡死
