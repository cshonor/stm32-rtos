# 5.2 定时器命令队列：start/stop/reset 都是"发消息"

## 这一篇讲什么

`xTimerStart()` 并不直接"启动定时器"——它往一条队列里
**发一条命令**，由守护任务取出来执行。理解这条命令队列，
定时器 API 的所有怪行为（返回值、FromISR（ISR 里专用的 API 变体家族，见 4.3）变体、阻塞（任务睡着等事件、不占 CPU，见 3.2）参数）全都顺了。

## 先用人话说一遍（新手铺垫）

定时器 API 的工作方式像餐厅**点餐口**：你不能自己冲进厨房
（定时器的活跃名单）动手，只能把单子（start/stop/reset 命令）
塞进传菜口——厨房里唯一的厨师（守护任务）按顺序取单、照单操作。

这个设计一口气解决三个麻烦：厨房里永远只有一个厨师，**不用抢锅**
（定时器数据结构零锁）；外卖小哥（ISR）也能塞单子，不用进厨房；
所有单子按到达顺序处理，**语义完全确定**。

记住一个返回值陷阱：`xTimerStart` 返回 `pdPASS` 只代表
**"单子塞进窗口了"**，不代表菜做好了——回调执行是厨师稍后的事。
窗口塞满时，那个 `xTicksToWait` 参数等的是"窗口腾位置"，不是
"定时器生效"。

| 术语 | 一句话解释 |
|---|---|
| 命令队列 | 内核私有的传输通道：所有定时器 API 都是往它里面发一条消息 |
| 单写者设计 | "只有守护任务能改定时器名单"的结构——天然免锁、免临界区 |
| 活跃名单 | 守护任务维护的"已启动定时器"花名册，到点检查的就是它 |
| `xTimerReset` | 把到期时刻重拨为"现在 + 周期"；心跳看门狗场景的核心动作 |

## 机制全景

```
你的任务/ISR                     内核                         守护任务
─────────────                  ──────────                    ──────────
xTimerStart(t, wait)  ──►  往命令队列塞一条                取出命令：
  {cmd=START, t}      ──►  {START, 定时器t, 时刻}   ──►    把 t 挂进"活跃名单"
                                                            到点后执行回调
```

- 命令队列就是一条普通队列（[ch04](../04-queue-management/README.md) 的机制），
  深度 = `configTIMER_QUEUE_LENGTH`，由内核自动创建，你拿不到句柄
- **所有定时器 API 都是"发命令"**：start、stop、reset、
  change period、delete——无一例外
- 真正操作定时器数据结构的只有守护任务一个执行者
  → **天然免锁**：没有多任务并发改名单的问题

## 为什么这样设计

定时器的活跃名单若允许任意任务直接改，就要全套临界区（屏蔽中断/切换来保护共享数据的代码段，见 1.2）保护；
改成"单写者（守护任务）+ 消息队列"后：

1. 定时器内部数据结构零锁，逻辑简单；
2. ISR 里也能安全操作定时器——发消息不需要碰名单；
3. 所有操作天然排序：命令按到达顺序执行，语义确定。

## API 对照：为什么每个都有 FromISR 版

| 任务上下文 | ISR 上下文 |
|---|---|
| `xTimerStart` | `xTimerStartFromISR` |
| `xTimerStop` | `xTimerStopFromISR` |
| `xTimerReset` | `xTimerResetFromISR` |
| `xTimerChangePeriod` | `xTimerChangePeriodFromISR` |
| `xTimerDelete` | （无 FromISR 版，删除请避开 ISR） |

FromISR 版存在的原因和 [4.3 FromISR 家族](../04-queue-management/4.3-FromISR家族.md)
完全一样：ISR 里不能阻塞，而普通版的 `xTicksToWait` 参数意味着
"队列满时可以等"——ISR 里不允许等。

## xTicksToWait 参数：等的是"队列空位"

```c
/* 命令队列若满，最多等 100ms 腾位置；仍满则放弃，返回 pdFAIL */
if( xTimerStart( t, pdMS_TO_TICKS(100) ) == pdFAIL )
{
    /* 命令没发出去——定时器状态没变，不是"启动失败"，是"没排上队" */
}
```

两个易错点：

- **返回值 pdPASS 只代表"命令进队列了"**，不代表回调已执行——
  执行是守护任务稍后的事
- 调度器启动前调定时器 API，`xTicksToWait` 被忽略（此时不能阻塞），
  队列满了就直接失败

## 队列深度配多少

`configTIMER_QUEUE_LENGTH` 决定能积压多少条未处理命令。
突发的多路 start/reset（比如中断密集期用 FromISR 版）会快速占满。
配 10 是常见起点；够不够看应用并发度，待实验验证。
队列满且等不到位置时的失败计数，可用 `xTimerGetTimerDaemonTaskHandle`
拿到守护任务后配合队列查询调试（进阶，用到再查书）。

## reset 的语义细节

`xTimerReset` = "把到期时刻重设为 now + 周期"。
对休眠中的定时器等效于 start；对活跃的等效于"重新计时"。
**超时看门狗场景全靠它**：每次收到心跳包（对端定期发来的"我还活着"消息）就 reset，
一直收不到 → 到期 → 回调报错。这是单次定时器的第一用例。

## 要点回顾

1. 定时器 API 全是"往命令队列发消息"，守护任务是唯一执行者。
2. 单写者设计 → 定时器名单零锁，ISR 也安全（FromISR 版）。
3. pdPASS = 命令入队，≠ 回调已执行。
4. `xTicksToWait` 等的是队列空位；调度器启动前它无效。

<details>
<summary>Q1：命令队列和普通队列是同一条吗？</summary>

不是。命令队列由内核在 `vTaskStartScheduler` 时专门创建，
与应用队列完全隔离，句柄不暴露。它只是**复用队列机制**
（queue.c 的代码），逻辑上是定时器子系统的私有传输层。

</details>

<details>
<summary>Q2：xTimerDelete 为什么没有 FromISR 版？</summary>

删除要释放定时器内存（动态创建时），ISR 里做内存释放既慢又危险；
而且删除语义在"中断随时可能再来"的场景里本身就矛盾。
官方干脆不提供——设计上把"销毁"留给任务上下文做。
想停中断源的定时器，用 `xTimerStopFromISR`。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| `xTimerStart` 返回 `pdPASS` = 定时器已生效 | 返回值看着像执行结果 | 只代表"命令塞进队列了"，回调执行是守护任务稍后的事 |
| `xTicksToWait` 等的是定时器到期 | 参数名叫 wait，直觉等生效 | 等的是**命令队列腾位置**；仍满返回 `pdFAIL`，且定时器状态根本没变 |
| 调度器启动前 start 也能等 | 以为参数语义一致 | 启动前不能阻塞，`xTicksToWait` 被忽略，队列满就直接失败 |
| 所有定时器 API 都有 FromISR 版 | 表格看着像全家桶 | `xTimerDelete` 没有 FromISR 版——ISR 里停定时器用 `xTimerStopFromISR` |
| 命令队列能拿到句柄自己玩 | 反正就是一条队列 | 内核私有、句柄不暴露，只是复用 queue.c 的机制 |

## 衔接

命令都汇总到守护任务执行，意味着**所有定时器回调共享同一个任务
上下文**——一个回调阻塞，后面所有定时器全陪葬。
这条"回调禁区"的纪律与后果，下一篇 [5.3 回调禁区](5.3-回调禁区.md)。

## 代码自测

_注：本节代码按 FreeRTOS API 语义编写，未在本仓库环境实跑，上板验证见「验证路径」。_

```c
static TimerHandle_t t_wdg;

void vWdgCb( TimerHandle_t t )     /* 超过 2s 没收到心跳才进这里 */
{
    printf( "ALARM: peer lost!\r\n" );
}

void vRxTask( void *p )            /* 模拟心跳看门狗 */
{
    for( ;; )
    {
        /* 每收到一个心跳包就 reset：到期时刻重拨为 now + 2s */
        if( xTimerReset( t_wdg, pdMS_TO_TICKS(100) ) == pdFAIL )
        {
            printf( "cmd queue full, reset lost\r\n" );   /* 命令没排上队 */
        }
        vTaskDelay( pdMS_TO_TICKS(500) );   /* 模拟 2Hz 心跳 */
    }
}

void app_init( void )
{
    t_wdg = xTimerCreate( "wdg", pdMS_TO_TICKS(2000), pdFALSE, 0, vWdgCb );
    xTimerStart( t_wdg, 0 );
    xTaskCreate( vRxTask, "rx", 256, NULL, 2, NULL );
}
```

**预期现象**：
- 心跳正常时 `ALARM` 永不打印——每次 reset 把到期时刻推后，单次定时器到不了点
- 把 `vTaskDelay` 改成 3000ms（心跳变慢），约 2s 后打印 `ALARM: peer lost!`
- 把 `configTIMER_QUEUE_LENGTH` 改小到 1 再密集 reset，出现 `cmd queue full, reset lost`

**验证路径**：F103 实机 + USART printf；对照"心跳中断 → 看门狗超时"两步现象。

**常见翻车点**：
- 把 `xTimerReset` 的 `pdPASS` 当成"看门狗已续命"——只是命令入队，队列满时续命根本没发生
- 在调度器启动前 start/reset，等待参数无效，静默失败难排查
