## 这一篇讲什么

HardFault 是 Cortex-M 的"总住院医师"——所有没配独立处理器的错误
（MemManage/BusFault/UsageFault）最后都汇到这里。
本篇给两件事：**栈类问题的三种典型死相**，
和一套**从 HardFault 现场挖出肇事 PC** 的固定套路。

## 先用人话说一遍（新手铺垫）

HardFault 像一场车祸：车毁了，但 Cortex-M 在碰撞瞬间自动拍了
一张**现场照片**——把出事的 8 个寄存器（含肇事指令的地址 PC）
按固定格式压进栈里。这套"解剖流程"的全部内容就是：
**找到照片洗在哪台相机里，读出车牌号，对着地图找肇事地点。**

麻烦在于相机有两台。FreeRTOS 里任务和中断各用一个栈（PSP/MSP），
照片压在哪台取决于"出事那一刻谁在开车"。进 HardFault 时 LR
寄存器的第 2 位就是相机编号——但它只在进 handler 那一瞬间
有效，所以才需要正文那段 5 行的汇编入口：抢在编号丢失前，
把正确的栈指针递交给 C 代码。之后就是查表：第 6 个字是
肇事 PC，拿去 addr2line 一对，直接给到代码行号。

最后提醒一个反直觉点，也是三种死相的共同根源：**栈溢出的
案发时间和死亡时间可以隔很久**——你踩了邻居家的地板，邻居
三天后才摔进去。所以 HardFault 现场那个"无辜的函数"经常只是
受害者，真凶要用上一章的填充模式检测提前抓。

| 术语 | 一句话解释 |
|---|---|
| MSP / PSP 双栈 | Cortex-M 两个栈指针：中断和启动代码用 MSP，FreeRTOS 任务各用自己的 PSP |
| EXC_RETURN | 异常进入时硬件放进 LR 的特殊值，其 bit 2 标记出事时用的是 MSP 还是 PSP |
| 压栈现场（stacked frame） | 异常瞬间硬件自动保存的 8 个寄存器（R0–R3、R12、LR、PC、xPSR），布局固定 |
| stacked PC | 现场里第 6 个字：肇事指令的地址，定位 HardFault 的头号线索 |
| addr2line | 命令行工具：把地址翻译成源文件和行号（配合 elf 文件使用） |
| 精确 / 非精确总线错 | 精确错时 PC 正指肇事访存指令且 BFAR 给出肇事地址；非精确时 PC 已跑远几条，需前后看 |

## 栈问题的三种死相

| 死相 | 机理 | 第一嫌疑 |
|---|---|---|
| **死在陌生函数里**，调用栈（"谁调了谁"的函数调用链条记录，调试器可查）看不懂 | 任务栈写爆，踩了自己栈下方的数据，变量/返回地址被改 | 该任务栈太小 → [11.2](../11-developer-support/11.2-栈溢出检测两档.md) |
| **切换任务后立刻跑飞**，PC 在火星 | 栈溢出踩了别的任务的栈，被踩任务弹现场时弹出垃圾 | 谁的栈爆了——溢出钩子会给名字 |
| **一进中断就死** | MSP 爆了（深层嵌套 / ISR 里大局部数组） | MSP 不在任务栈检测范围内，静态核算 + 调试器看 MSP |

共同教训：**栈溢出几乎从不死在溢出发生的那一刻**——
它腐蚀的是别人的现场，案发和死亡之间隔着任意长的时间。
所以 [11.2](../11-developer-support/11.2-栈溢出检测两档.md) 的填充模式检测（抓"历史痕迹"）是刚需。

## HardFault 定位套路：先分 MSP 还是 PSP

进 HardFault 时，CPU 自动把一份现场**压到"出事时正在用的那个栈"上**。
FreeRTOS 里任务跑 PSP、中断跑 MSP（见
[20.1](../../01-stm32/20-towards-freertos/20.1-任务与调度的硬件落点.md)），
所以第一步必须判断**现场压在哪**——看 LR（EXC_RETURN）的 bit 2：
`LR & 0x4 == 0` → 现场在 MSP（中断/内核上下文）；否则在 PSP（某任务里）。

裸 C 的 handler 拿不到这个 LR 值（进 handler 时 LR 已变），
标准做法是用**一小段汇编把正确的栈指针传给 C 函数**：

```c
/* 汇编入口（GCC 语法，概念示意） */
__attribute__( ( naked ) ) void HardFault_Handler( void )
{
    __asm volatile(
        "tst lr, #4          \n"  /* 测 EXC_RETURN bit 2 */
        "ite eq              \n"
        "mrseq r0, msp       \n"  /* bit2=0 → MSP */
        "mrsne r0, psp       \n"  /* bit2=1 → PSP */
        "b prvHardFaultC     \n"  /* r0 = 出事时的栈顶 */
    );
}
```

## 第二步：从压栈现场里读 stacked PC

异常压栈的 8 个字布局（Cortex-M 固定格式）：

```
栈顶 → [0] R0   [1] R1   [2] R2   [3] R3
       [4] R12  [5] LR ← 出事前返回地址
       [6] PC  ← ★ 肇事指令地址   [7] xPSR
```

```c
void prvHardFaultC( uint32_t *pulStack )
{
    volatile uint32_t pc = pulStack[ 6 ];  /* 肇事 PC */
    volatile uint32_t lr = pulStack[ 5 ];
    ( void ) pc; ( void ) lr;
    for( ;; );  /* 停车，调试器看 pc/lr */
}
```

拿到 `pc` 之后：

1. **对照 .map 文件**（链接器生成的地址清单：每个函数/变量落在哪个地址；`.elf` 是编译出的可执行文件，带调试符号）
   （或 `arm-none-eabi-addr2line -e xxx.elf <pc>`）
   查到函数和行号；`lr` 再给一级调用来源；
2. PC 来自 PSP → 某任务出的事，结合 `pxCurrentTCB` 看任务名
   （[11.1 Q1](../11-developer-support/11.1-configASSERT总开关.md)）；
   来自 MSP → 中断/内核上下文，先怀疑 [12.2](12.2-中断优先级三大错.md)。

## 顺手看故障状态寄存器

| 寄存器 | 告诉你什么 |
|---|---|
| `SCB->CFSR` | 故障类型：精确/非精确总线错、未定义指令、非法状态切换、除零等 |
| `SCB->MMFAR` / `BFAR` | **肇事内存地址**（仅"精确"总线错时有效） |

"非精确总线错"时 PC 已偏离肇事点几条指令，前后看几条，别死磕一条。

## 要点回顾

1. 栈问题三死相：死在陌生函数 / 切换后跑飞 / 一进中断就死。
2. HardFault 定位第一步：**LR bit 2 判别 MSP/PSP**，汇编入口传对栈指针。
3. stacked PC = `pulStack[6]`，配合 addr2line/.map 直接定位到行。
4. CFSR 给故障类型，精确总线错时 BFAR/MMFAR 给肇事地址。

<details>
<summary>Q1：为什么不用编译器生成的默认 HardFault_Handler？</summary>

默认 handler 通常是个 `b .` 死循环——它替你"停车"了，
但**没保留 LR 判别和栈指针**，调试器连上时关键上下文全丢。
naked（编译器函数属性：不为这个函数自动生成开场/收场代码，寄存器原样保留，适合手写汇编入口）入口的意义就是在第一时间把"案发现场坐标"固定下来。

</details>

<details>
<summary>Q2：stacked PC 指向的函数看起来完全无辜，怎么回事？</summary>

两种典型情况：① 栈溢出踩了数据——这个函数的**变量**被别人改了，
它是受害者不是凶手，回头查 [11.2](../11-developer-support/11.2-栈溢出检测两档.md)；
② 非精确总线错——PC 已过肇事点，前后看几条指令。
另外 PC 落在 RAM 区或对齐异常地址，多半是**返回地址被踩**，沿"谁写过这个栈区域"查。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| 编译器默认的 HardFault_Handler 够用 | 启动文件里已经给了 | 默认是 `b .` 死循环——替你停车了，但 LR 判别和栈指针全丢，案发现场坐标没了（Q1） |
| stacked PC 指向的函数就是凶手 | PC 在哪就是哪出错 | 常是**受害者**（栈被踩、变量被改）或非精确总线错（PC 已跑过肇事点几条）（Q2） |
| 栈溢出会死在溢出的那一刻 | 写爆了立刻崩 | 案发与死亡可隔任意长时间——踩的是别人的现场，所以填充模式检测（11.2）是刚需 |
| 异常现场固定压在一个栈上 | 压栈就是压栈 | 任务用 PSP、中断用 MSP，必须先用 LR（EXC_RETURN）bit 2 判别现场压在哪 |
| C 函数里能直接读到进异常时的 LR | LR 就是个寄存器 | 进 handler 后 LR 已变，必须用 naked 汇编入口抢在变形前把栈指针递给 C |

## 代码自测

_注：本节代码按 FreeRTOS API 语义编写，未在本仓库环境实跑，上板验证见「验证路径」。_

```c
__attribute__( ( naked ) ) void HardFault_Handler( void )
{
    __asm volatile(
        "tst lr, #4          \n"  /* EXC_RETURN bit 2 */
        "ite eq              \n"
        "mrseq r0, msp       \n"  /* bit2=0 → 中断/内核上下文 */
        "mrsne r0, psp       \n"  /* bit2=1 → 某任务 */
        "b prvHardFaultC     \n" );
}

void prvHardFaultC( uint32_t *pulStack )
{
    volatile uint32_t pc   = pulStack[ 6 ];  /* 肇事指令地址 */
    volatile uint32_t lr   = pulStack[ 5 ];
    volatile uint32_t cfsr = SCB->CFSR;      /* 故障类型 */
    ( void ) pc; ( void ) lr; ( void ) cfsr;
    for( ;; );                               /* 停车，调试器看这三个值 */
}

void vCrashTask( void *pv )   /* 故意触发：往非法地址写 */
{
    ( void ) pv;
    vTaskDelay( pdMS_TO_TICKS( 100 ) );
    *( ( volatile uint32_t * ) 0xFFFFFFF0u ) = 0;
}
```

**预期现象**：
- 约 100ms 后停车进 `prvHardFaultC`，调试器读 `pc`。
- `arm-none-eabi-addr2line -e app.elf <pc>` 直接给出 `vCrashTask` 里那行写的文件和行号。
- PC 来自 PSP（bit2=1）→ 结合 `pxCurrentTCB` 看到任务名 `"crash"`。
- `cfsr` 显示总线错/精确错标志位，佐证是非法访存。

**验证路径**：F103 实机 + ST-Link + addr2line（elf 需带 `-g` 调试符号）。

**常见翻车点**：
- handler 忘写 `naked`，编译器生成的开场代码动了寄存器，LR 判别失效。
- addr2line 用了不带调试符号的 elf，只给地址不给行号。
- 非精确总线错时死磕 PC 指的那一条——肇事指令在前面几条，结合 CFSR/BFAR 看。
