## 这一篇讲什么

五个 `heap_x.c` 不是"五个版本越来越好"，是**五种不同的权衡**。
这一篇一张表讲死各自的脾气，再给选型决策。

## 先用人话说一遍（新手铺垫）

五个 heap_x 是**五种储物方案**，选哪个取决于你的使用习惯：

- **heap_1 = 一次性货架**：东西放上去就不拿下来（只分不还）。
  货架永远整整齐齐（零碎片），代价是拿不下来。很多工控设备
  开机建完任务就再不删，正合适。
- **heap_4 = 带整理的储物柜**：东西能放能取，管理员每次取走一格后
  **看看左右有没有空格，有就并成一大格**（相邻块合并）。会留下
  一些缝隙，但不会碎成渣。通用首选。
- **heap_5 = 好几个储藏室拼成一个库存**：柜子和 heap_4 一样，
  但货可以分放在几间不相邻的储藏室（多段不连续 RAM）。

heap_2 是被 heap_4 淘汰的旧款储物柜（取了不并格），heap_3 则是
"还是去 malloc 那家裁缝店，只加了把锁"——本篇的表就是把这五种
脾气一行一行对齐了看。

| 术语 | 一句话解释 |
|---|---|
| 首次适配（first-fit） | 分配时沿空闲块列表从头找，第一个够大的块就用——简单、耗时可估上界 |
| 相邻块合并（coalescing） | 释放时若隔壁也是空闲块就拼成一大块，heap_4/5 缓解碎片的核心动作 |
| CCM | F4 系列独有的"内核直连 RAM"，和普通 SRAM 地址不连续，所以想一起当堆要用 heap_5 |
| 外部 SDRAM | 片外焊的大容量内存芯片，和片内 SRAM 是两段地址，同样需要 heap_5 登记 |
| 编译期选型 | heap_x 是"编哪个 .c 进工程"的决定，运行时不能换，换 = 改 Makefile 重编 |

## 一张表看穿五个 heap

| | 能释放 | 碎片 | 多块 RAM | 耗时确定性 | 一句话定位 |
|---|---|---|---|---|---|
| **heap_1** | ❌ 只分不还 | 无（不还当然不碎） | ❌ | ✅ 完全确定 | 静态系统的最简解 |
| **heap_2** | ✅ | ⚠ 会碎（不合并相邻块） | ❌ | 较好 | 已被 heap_4 取代，别用 |
| **heap_3** | ✅ | 看 libc（所用的 C 标准库） | ❌ | ❌ 不确定 | 就是给 malloc 加个调度器锁，过渡用 |
| **heap_4** | ✅ | 缓解（相邻空闲块合并） | ❌ | 较好（首次适配+合并） | **通用首选** |
| **heap_5** | ✅ | 缓解（同 heap_4 算法） | ✅ 多段不连续 RAM | 较好 | heap_4 + 多内存区 |

## 逐个三句话

**heap_1**：只有 `pvPortMalloc`，`vPortFree` 是空操作。
任务/队列建了就永不删的系统（很多工控设备就是这样），用它最稳——
没有释放就没有碎片，耗时恒定。**"只分不还"不是缺陷，是场景。**

**heap_2**：能 `vPortFree`，但释放的块**不和相邻空闲块合并**。
反复分配/释放**同样大小**的块没问题（原大小块能复用）；
大小随机就会碎成渣。heap_4 出来后它只剩历史价值。

**heap_3**：直接包装 libc 的 malloc/free，外加挂起调度器保证线程安全（多个任务同时调也不出错）。
耗时确定性、碎片问题原样继承——用它等于没解决 2.1 的四宗罪里的两个。

**heap_4**：首次适配 + **相邻空闲块合并**（coalescing），
碎片问题大幅缓解。任务动态创建/删除、队列动态申请的场景选它。
**官方示例和绝大多数工程的默认。**

**heap_5**：算法与 heap_4 相同，但堆可以由**多段不连续 RAM** 拼成
（启动时先用 `vPortDefineHeapRegions()` 登记各区）。
典型用途：片内 SRAM + 外部 SDRAM 一起当堆。
F103 只有一片 20K SRAM，用不上；F407 有 128K+64K CCM 两段，可以考虑。

## 与 LDD- 侧对照

| 概念 | Linux | FreeRTOS |
|---|---|---|
| 分配器策略多样 | glibc malloc / jemalloc / tcmalloc 可选 | heap_1~5 编译期选 |
| 碎片处理 | 分配器内部复杂（bins、arena） | heap_4 只做相邻合并，够用 |
| "只分不还" | 没有对应物（内核 SLAB（Linux 内核的对象缓存分配器）有点神似） | heap_1 是合法主流选择 |

## 要点回顾

1. 五个 heap 是五种权衡，不是版本递进；heap_2 已过时。
2. 系统"建完就不删" → heap_1；要动态创建删除 → heap_4；多段 RAM → heap_5。
3. heap_3 只在你必须和现有 malloc 代码共存时过渡用。

<details>
<summary>Q1：heap_4 的"相邻合并"能彻底消灭碎片吗？</summary>

不能。它只合并**地址相邻**的空闲块。如果分配序列把堆切成
"已用、空闲、已用、空闲"交错，空闲块不相邻就合并不了，
长期运行照样可能"总量够、单块不够"。
**工程对策：创建/删除的对象大小尽量归一化**（所有任务栈一样深之类），
碎片率会大幅下降。

</details>

<details>
<summary>Q2：能不能运行中换 heap？</summary>

不能。heap_x 是编译期选编的一个 .c 文件，换 = 改 Makefile 重编。
这也是"选型"要提前想清楚的原因——好在 2.1 说过 ucHeap 是定长数组，
换 heap 不用动链接脚本，成本就是改一行源文件清单。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| heap_1~heap_5 是版本递进，选最新 | 编号越大越先进 | 五种是**权衡**不是升级：heap_1 至今是"建完不删"场景的主流首选 |
| heap_4 有相邻合并 = 没碎片了 | 合并了空闲块，碎片问题解决了 | 只合并**地址相邻**的块；分配序列交错时照样"总量够、单块不够"，对策是对象大小归一化 |
| 跑着跑着发现 heap 选错了，热切换 | 换个配置项的事 | heap 是编译期选编的一个 .c，换 = 改 Makefile 重编，运行时不能换 |
| heap_3 既兼容 malloc 又解决了问题 | 官方提供的就是方案 | 它只加了把调度器锁，耗时确定性、碎片问题原样继承，等于四宗罪只拆了两个 |

## 代码自测

_注：本节代码按 FreeRTOS API 语义编写，未在本仓库环境实跑，上板验证见「验证路径」。_

```c
/* 演示 heap_4 的相邻合并：交错释放造碎片，相邻释放能并回大块 */
static void vFragTask( void *pv )
{
    void *a = pvPortMalloc( 512 );
    void *b = pvPortMalloc( 512 );
    void *c = pvPortMalloc( 512 );

    vPortFree( b );                 /* 释放中间块：512B 空闲，但被 a、c 夹着 */
    void *big = pvPortMalloc( 900 );/* 要 900B：总量够，单块不够 → 失败 */

    if ( big == NULL )
    {
        /* 碎片现场：空闲 512B，却满足不了 900B */
    }

    vPortFree( a );                 /* 把相邻的 a 也放掉 */
    vPortFree( c );
    big = pvPortMalloc( 900 );      /* 三块相邻空闲已合并 → 这次成功 */
    vPortFree( big );

    for ( ;; ) vTaskDelay( 100 );
}

int main( void )
{
    xTaskCreate( vFragTask, "frag", 128, NULL, 1, NULL );
    vTaskStartScheduler();
    for ( ;; );
}
```

**预期现象**：
- 第一次申请 900B 返回 NULL（中间 512B 空洞用不了）。
- 释放 a、c 后第二次申请 900B 成功（heap_4 把相邻空闲块合并了）。
- 换 heap_2 编进工程再跑：第二次申请**仍然失败**（heap_2 不合并相邻块）——这就是它被取代的原因。

**验证路径**：F103 实机 + USART printf 打印每次返回值；对比实验只需把 Makefile 里 heap_4.c 换成 heap_2.c 重编。

**常见翻车点**：
- 以为换 heap 能运行时切 → 必须改源文件清单重编。
- 长期跑大小随机的分配/释放序列 → heap_4 也会慢慢碎，对象大小要归一化。
