## 这一篇讲什么

选型结论一句话：**本仓选 heap_4**。这一篇把理由钉死，
再解决真正的工程问题：F103 只有 20K RAM，`configTOTAL_HEAP_SIZE` 该写多大？

## 先用人话说一遍（新手铺垫）

20K RAM 像一套 **20 平米的一居室**，所有住户平分：

- 全局变量（.data/.bss（C 程序里全局/静态变量占据的两个内存段））是**固定家具**，搬进来就占着不动；
- 中断栈（MSP）是**门口过道**，平时空着，但来客人叠客人
  （中断嵌套（高优先级中断打断正在跑的低优先级中断））时必须留够，不然直接踩到别人房间；
- `ucHeap` 是**储物间**——任务栈、TCB、队列这些"临时家当"
  全从里面领。储物间划多大，就是本篇要拍的数。

这个数怎么定？**先按清单估算，再量实际水位收紧**——像搬家先按
物品清单租个大点的仓库，住一个月后看最满那次占了多少，再退掉
多余面积。FreeRTOS 把这个"最满那次"直接做成了 API
（`xPortGetMinimumEverFreeHeapSize()`），读出来就是账。

| 术语 | 一句话解释 |
|---|---|
| MSP（中断栈） | 复位和中断专用的栈，大小由链接脚本定，**不走 heap**，预算里要单独留 |
| 栈高水位（high water mark） | 任务栈历史最深用量——离栈顶越近水越"满"，用它判断栈开大了还是开小了 |
| 定时器守护任务 | 开了软件定时器后内核自动建的后台任务（ch05 主角），也吃 heap |
| `configCHECK_FOR_STACK_OVERFLOW` | 栈溢出检测开关：方法 2 会在栈底埋"金丝雀值"，被踩掉就回调报警 |

## 为什么是 heap_4

| 候选 | 排除/入选理由 |
|---|---|
| heap_1 | ❌ 学习阶段要反复创建/删除任务做实验，"只分不还"会把 heap 耗光 |
| heap_2 | ❌ 过时，不合并碎片 |
| heap_3 | ❌ 继承 libc malloc 的不确定性（2.1 四宗罪） |
| **heap_4** | ✅ 动态创建/删除 + 碎片缓解，官方默认，实验全够 |
| heap_5 | ⏸ F103 单段 20K SRAM 用不上多段堆；**F407 阶段再议**（128K SRAM + 64K CCM） |

## configTOTAL_HEAP_SIZE：20K RAM 的预算案

F103RB：20K SRAM。花钱的项目：

```
SRAM 总账（20K = 20480 B）
├── .data + .bss（你的全局变量）        实测：blink 只有 16 B，随应用涨
├── 中断栈（MSP）                       链接脚本里 _estack 定顶，向下长；预算 1K
├── ucHeap[configTOTAL_HEAP_SIZE]       ← 本章主角，heap_4 的全部本钱
│     ├── 每个任务：TCB（约 100+ B）+ 任务栈（xTaskCreate 第三个参数 ×4 字节）
│     ├── 每个队列：结构体 + 存储区（长度 × 项大小）
│     └── 内核对象（信号量/定时器……）
└── （裸机 newlib 的 _sbrk 堆：进了 RTOS 就该让它失业，见 2.1）
```

01-hello-task 的最小预算（两个 LED 任务 + 空闲任务 + 定时器守护任务）：

| 对象 | 估算 | 备注 |
|---|---|---|
| 2 个 LED 任务栈 | 2 × 128 字 × 4 B = **1024 B** | 128 字是书中最小任务的常见起点 |
| 2 个任务 TCB（任务控制块：内核给每个任务建的"档案卡"，见 2.1） | ~2 × 120 B ≈ **240 B** | TCB 结构体随配置略有浮动 |
| 空闲任务（栈+TCB） | 栈=configMINIMAL_STACK_SIZE（一般 130 字）≈ **640 B** | 内核自动建 |
| 定时器守护任务 | 类似空闲 ≈ **640 B**（若启用软件定时器） | configUSE_TIMERS=1 才有 |
| 队列等预留 | **1~2K** | 02-queue 马上要用 |

合计约 4~5K → **`configTOTAL_HEAP_SIZE` 取 8K（8192）宽松起步**，
剩下 ~11K 给 MSP 栈余量、.bss 增长和调试期的 printf 缓冲。

**定大小的方法论**：先按上表算理论值 → 上调一档取整 →
实验里用 `xPortGetFreeHeapSize()` 和 `uxTaskGetStackHighWaterMark()`
把真实水位读出来，**再向下收紧**。这才是最终值；拍脑袋的值只是开工值。

## 分配失败怎么抓（配置清单）

```c
/* FreeRTOSConfig.h 关键三行 */
#define configTOTAL_HEAP_SIZE        ( ( size_t ) ( 8 * 1024 ) )
#define configCHECK_FOR_STACK_OVERFLOW   2   /* ch11 详解，方法二 */
/* malloc 失败钩子：创建对象失败时内核回调这里 */
void vApplicationMallocFailedHook( void )
{
    taskDISABLE_INTERRUPTS();
    for( ;; );   /* 卡死在这——调试器里一眼看到调用栈 */
}
```

配上钩子之后，`xTaskCreate` 返回 `pdFAIL`（FreeRTOS 的统一失败返回值）就不是"静默失败"，
而是**在分配现场当场停车**——2.1 说的第四宗罪被彻底拆掉。

## 要点回顾

1. 本仓选 heap_4：动态实验 + 碎片缓解；heap_5 留给 F407 阶段。
2. `configTOTAL_HEAP_SIZE` 先算后拍（8K 起步），再用水位 API 收紧。
3. `vApplicationMallocFailedHook` + `configCHECK_FOR_STACK_OVERFLOW=2`
   是开车前的安全带，01 实验落地当天就配。

<details>
<summary>Q1：任务栈在 ucHeap 里，MSP（中断栈）在哪？</summary>

MSP 栈**不在** ucHeap 里——它就是链接脚本里 `_estack` 往下那片"什么都没占用"的 RAM。
所以 SRAM 预算里要给 MSP 留够（ISR 嵌套最深时的用量），
这部分不参与 heap 分配，超了就是栈溢出去踩 .bss/ucHeap，
死相会很难看（数据被悄悄改写而不是立刻 HardFault）。

</details>

<details>
<summary>Q2：heap 用不完的部分浪费了怎么办？</summary>

不浪费——`configTOTAL_HEAP_SIZE` 本来就是你自己拍的数，
实验中用 `xPortGetFreeHeapSize()` 读到"历史最低剩余"
（`xPortGetMinimumEverFreeHeapSize()`）后把它收紧即可。
**先宽后紧**是标准流程，反着来（先紧后爆）才难受。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| MSP 中断栈也从 ucHeap 里出 | 栈嘛，都从堆里分 | MSP 是链接脚本 `_estack` 往下那片 RAM，**不走 heap**；预算里漏留会悄悄踩 .bss/ucHeap，而不是立刻 HardFault |
| `configTOTAL_HEAP_SIZE` 先给紧点省 RAM | 用不完浪费 | 标准流程是**先宽后紧**：先拍大，用 `xPortGetMinimumEverFreeHeapSize()` 读历史最低剩余再收紧；先紧后爆最难受 |
| `xTaskCreate` 的栈参数单位是字节 | C 里长度参数一般按字节 | 单位是**字**：F103 上 128 字 = 512 字节，按字节理解栈直接缩 4 倍 |
| 配了 hook 就万事大吉 | 钩子会自动处理失败 | 钩子函数体是你写的，里面必须当场停车（关中断+死循环），光定义个空钩子等于没配 |

## 代码自测

_注：本节代码按 FreeRTOS API 语义编写，未在本仓库环境实跑，上板验证见「验证路径」。_

```c
/* 演示"先宽后紧"：读出堆与栈的真实水位，为收紧 configTOTAL_HEAP_SIZE 提供依据 */
extern void uart_puts( const char * );      /* 伪代码：串口输出 */

static void vMeterTask( void *pv )
{
    char buf[64];
    for ( ;; )
    {
        /* 堆水位：当前剩余 / 历史最低剩余 */
        size_t now = xPortGetFreeHeapSize();
        size_t min = xPortGetMinimumEverFreeHeapSize();
        /* 本任务栈高水位（单位：字） */
        UBaseType_t stack_hwm = uxTaskGetStackHighWaterMark( NULL );
        /* snprintf(buf, 64, "heap now=%u min=%u stack_hwm=%u\r\n", ...); uart_puts(buf); */
        (void)buf;
        vTaskDelay( 1000 );
    }
}

int main( void )
{
    xTaskCreate( vMeterTask, "meter", 128, NULL, 1, NULL );
    vTaskStartScheduler();
    for ( ;; );
}
```

**预期现象**：
- 每秒打印一行：`xPortGetFreeHeapSize()` 基本稳定，`xPortGetMinimumEverFreeHeapSize()` 只降不升。
- 跑过"最忙"的场景后，min 值就是收紧依据：比如 min 还剩 4K，8K 的堆可以砍到 5K。
- `uxTaskGetStackHighWaterMark(NULL)` 若长期 >64 字，说明 128 字栈开大了；逼近 0 说明要爆栈。

**验证路径**：F103 实机 + USART printf，跑过全部功能场景后读数。

**常见翻车点**：
- 刚开机就读水位就收紧 → 最忙场景没跑到，min 值是假的。
- 栈高水位单位是字不是字节，换算错 → 误判栈余量。
- 只读 `xPortGetFreeHeapSize()` 当前值 → 看不出峰值，必须看 MinimumEver。
