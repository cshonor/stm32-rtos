# 9.3 通知的边界：什么时候必须退回用队列

## 这一篇讲什么

任务通知快且省，但它是**有硬边界的优化件**，不是通信原语的终极形态。
本篇把三条边界划清楚：**一对一限制、值的所有权、以及什么场景必须
退回队列/信号量正主**。最后补齐 FromISR 家族的用法。

## 先用人话说一遍（新手铺垫）

工牌便签栏快是快，但快是有代价的——代价就写在它的结构里。
这篇讲的是"什么时候别用它"，三条边界都能从"便签栏长在对方
工牌上"这个事实直接推出来：

第一，**便签栏是私人的**。你没法一张便签同时贴到五个人的
工牌上（不能广播），五个人同时往一张便签上写字也会互相糊掉
（多对一没保护）。所以它是点对点管道，不是公告栏。

第二，**便签栏只有一格，且没有"写不下就等"的服务**。队列满了
发送方可以排队等空位，便签不行——写完就走，对方上一条还没看？
要么覆盖（默认几种写法），要么报失败自己想办法（最后那种写法）。
内核不替你排队。

第三，**便签上就是 32 个格子，没有信封**。传个数、传位掩码、
传指针都行，但指针指向的那包东西它不管——所有权规矩和
"队列传指针"那套完全相同，自己约定。

| 术语 | 一句话解释 |
|---|---|
| 一对一通道 | 通知必须指定目标任务句柄，一个通道设计上一个发送源配一个接收任务 |
| 无类型标量 | 32 位纯数值，内核不解释含义；当计数、位掩码还是指针全看双方约定 |
| 发送方阻塞 | 队列的"满了就等空位"机制；通知没有——发送永远立即完成 |
| 多对一冲突 | 多个发送方并发改同一个通知值，读改写无互斥，会丢更新 |
| 通知值数组 | 新版 FreeRTOS 给每个任务配多个通知槽位（默认 1 个），一种语义占一个槽位 |

## 边界一：只能一对一

通知值长在**接收任务的 TCB 里**，这决定了两个方向都受限：

- **不能一对多**：通知发给指定任务句柄（代表某个内核对象的一把手柄/编号，之后操作对象都靠它），没有"广播给一组任务"的机制。
  事件组能让 N 个任务同等单位，通知做不到。
- **多对一要小心**：多个发送方对同一个 32 位值做读改写，
  没有互斥保护（`eSetBits` 的"或"操作在多发送方并发时会丢位）。
  官方定位就是**一个通知通道配一个发送源**。

## 边界二：只有接收方能阻塞

队列满时**发送方可以阻塞**等空位（[4.2 阻塞语义](../04-queue-management/4.2-阻塞语义与超时.md)）。
通知没有这个机制——发送动作就是改对方 TCB，改完就走，
**发送方无法等"对方把上一条取走"**。

想要"不丢"只能靠 `eSetValueWithoutOverwrite` 的失败返回值自己补救
（重试、计数丢弃），内核不会替你排队。

## 边界三：通知值的所有权

通知值是**无类型的 32 位标量**，所有权语义极简单：
改的那一刻起就归接收方，没有拷贝缓冲、没有排队副本。推论：

- 适合传**标量**：计数、位掩码（用一个整数的每一位各表示一个开关/标志）、状态字、小号数据、指针。
- 传指针时规矩和队列一样（见 [4.4](../04-queue-management/4.4-传指针的代价与规矩.md)）：
  指向的必须是静态/堆存储（static 变量或 malloc 出来的内存：函数返回后依然存活，局部变量不行），且所有权约定要自己管——
  通知本身**只搬 32 位**，不帮你管指针指向的东西。
- 没有"通知里还剩几条没取"的查询——值只有一个，要么在要么被取走。

## 决策表：通知还是正主

| 场景 | 选型 |
|---|---|
| ISR→唯一任务，"发生了一次" | ✅ 通知（Give/Take），最快路径 |
| ISR→唯一任务，传最新采样值 | ✅ 通知（eSetValueWithOverwrite） |
| 唯一发送方→唯一任务，多事件位 | ✅ 通知（eSetBits） |
| 多任务同等事件 | 退回：事件组 |
| 需要互斥 + 优先级继承 | 退回：互斥锁（通知没有继承机制） |
| 数据不能丢、发送方要能等 | 退回：队列（有阻塞语义和多格缓冲） |
| 多对一 / 一对多 | 退回：队列或事件组 |

一句话：**结构上是"一对一管道"的用通知，是"枢纽/总线"的用正主。**

## FromISR 家族：规则和队列那套完全一样

```c
void USART1_IRQHandler( void )
{
    BaseType_t xWoken = pdFALSE;

    /* 收到一帧，通知处理任务（计数 +1 并唤醒） */
    vTaskNotifyGiveFromISR( xRxTask, &xWoken );

    portYIELD_FROM_ISR( xWoken );
}
```

| 任务上下文 | ISR 上下文 |
|---|---|
| `xTaskNotifyGive` | `vTaskNotifyGiveFromISR`（注意 ISR 版返回 void） |
| `xTaskNotify` | `xTaskNotifyFromISR`（多一个 `pxHigherPriorityTaskWoken`） |
| —— | `xTaskNotifyAndQueryFromISR`（顺带读对方旧值，少用） |

规则与 [4.3 FromISR 家族](../04-queue-management/4.3-FromISR家族.md) 完全一致：

- 不能阻塞（本来通知发送就不阻塞，天然适配 ISR）
- `pxHigherPriorityTaskWoken` 初始 `pdFALSE`，退出时 `portYIELD_FROM_ISR`（中断收尾宏：如果刚才的 API 唤醒了更高优先级任务，就当场切换过去）
- 中断优先级数值 ≥ `configMAX_SYSCALL_INTERRUPT_PRIORITY` 才能调

## 要点回顾

1. 通知只能一对一；多发送方并发改值无保护。
2. 发送方不能阻塞——"不丢"只有 `eSetValueWithoutOverwrite` + 自查返回值。
3. 通知值是无类型 32 位，传指针时所有权自己管。
4. 需要互斥、广播、可靠排队时退回正主。
5. FromISR 用法与队列家族同规则。

<details>
<summary>Q1：xTaskNotifyFromISR 的返回值有什么用？</summary>

返回 `pdPASS`（FreeRTOS 的"成功"返回值，就是 1；失败是 pdFAIL = 0）表示通知送达；用 `eSetValueWithoutOverwrite` 且对方
上一条还没取走时返回 `pdFAIL`。ISR 里不能等，收到 `pdFAIL`
的对策和队列满一样：计数丢弃，事后分析——别在 ISR 里重试打转。

</details>

<details>
<summary>Q2：同一个任务能不能同时用通知当信号量和当事件组？</summary>

不推荐。通知值只有一个，Give（+1）和 eSetBits（按位或）会互相污染
对方的语义。新版 FreeRTOS 提供**通知值数组**
（`configTASK_NOTIFICATION_ARRAY_ENTRIES > 1`，每个任务多个槽位），
一个槽位配一种语义才能并存；槽位为 1（默认）时一个任务只用一种。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| 通知可以广播给一组任务 | 效率这么高，多发几个人 | 必须指定目标任务句柄，一对一；一对多是事件组的主场 |
| 发送方能像队列满那样阻塞等空位 | 发不出去就等一会儿 | 发送就是改对方 TCB，改完就走，发送方永远无法阻塞 |
| 同一个任务可同时拿通知当信号量和事件组 | 反正都是那一个值 | Give(+1) 和 eSetBits（按位或）互相污染；要并存得开通知值数组（configTASK_NOTIFICATION_ARRAY_ENTRIES > 1） |
| `vTaskNotifyGiveFromISR` 返回 pdPASS/pdFAIL | 跟任务版对称 | ISR 版返回 void；要判断送达与否用 `xTaskNotifyFromISR` |
| 通知传指针，所有权内核会管 | 内核总该管点什么 | 只搬 32 位，指向的东西所有权自己约定；指向局部变量 = 悬空指针 |

## 代码自测

_注：本节代码按 FreeRTOS API 语义编写，未在本仓库环境实跑，上板验证见「验证路径」。_

```c
/* ISR → 任务的最快路径：USART 收中断里 Give 通知，任务做下半部 */
static TaskHandle_t xRxTask;

void USART1_IRQHandler( void )
{
    BaseType_t xWoken = pdFALSE;
    if( USART1->SR & USART_SR_RXNE )
    {
        ( void ) USART1->DR;                        /* 读走字节，清标志 */
        vTaskNotifyGiveFromISR( xRxTask, &xWoken ); /* 计数 +1 并唤醒 */
    }
    portYIELD_FROM_ISR( xWoken );                   /* 唤醒了更高优先级就当场切 */
}

static void vRxTask( void *pv )
{
    for( ;; )
    {
        /* 来几帧处理几帧：计数信号量用法 */
        uint32_t n = ulTaskNotifyTake( pdFALSE, portMAX_DELAY );
        printf( "rx event, count=%lu\r\n", ( unsigned long ) n );
    }
}

void app_init( void )
{
    xTaskCreate( vRxTask, "RX", 256, NULL, 3, &xRxTask );
    /* USART1 初始化 + 开 RXNE 中断，优先级数值 ≥ configMAX_SYSCALL_INTERRUPT_PRIORITY */
}
```

**预期现象**：
- 串口助手每发一个字节，打印一行 "rx event"；连发快时 `count` 可能 > 1。
- 从 ISR 到任务打印的延迟明显短于事件组 `SetBitsFromISR` 方案——后者还要经定时器守护任务中转。
- 任务不跑时 CPU 全在 idle，没有任何轮询。

**验证路径**：F103 实机，USART1 自收自发或串口助手发字节，观察打印与发送的对应关系；有条件用示波器/逻辑分析仪量 ISR 到任务唤醒的延迟。

**常见翻车点**：
- USART1 中断优先级数值小于 `configMAX_SYSCALL_INTERRUPT_PRIORITY`（即逻辑优先级更高），调 FromISR API 触发断言。
- 忘了 `portYIELD_FROM_ISR( xWoken )`，接收任务要等下一个 tick 才醒，"最快路径"白搭。
- 中断里忘了读 `DR` 清 RXNE 标志，中断反复进入，系统被刷爆。
