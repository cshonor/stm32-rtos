# 5.4 while

> 书：第 5 章 决策和控制语句 · 5.4 while（原书 p65–77 区间内）
> 上一篇：[5.3 循环](5.3-循环.md) ｜ 下一篇：[5.5 for](5.5-for.md)
> 对应实验：`--target=armv7m-none-eabi -mcpu=cortex-m3 -Os` 交叉编译

## 书这一节讲什么

一句话：**`while (条件) { 循环体 }`——条件为真就一直做**。

书把它当"先判断再执行"的循环讲。裸机上 `while` 承担的是**等待**——
等一个硬件标志、等一个外设空闲、等一个计时到达。
而"等待"这件事在裸机上有个致命前提：**循环条件里的变量必须每轮真的被读**。

## 一、实测：等待循环的两个版本

```c
int flag;                       /* 非 volatile：ISR 会改它，但编译器不知道 */
volatile int vflag;
void wait_bad(void){ while (flag  == 0) { } }
void wait_ok (void){ while (vflag == 0) { } }
```

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -Os -c wait.c -o wait.o
$ llvm-objdump -d wait.o

00000000 <wait_bad>:
       0: 4770          bx   lr          ← 整个等待循环没了！直接返回

00000002 <wait_ok>:
       2: f240 0000     movw r0, #0x0
       6: f2c0 0000     movt r0, #0x0
       a: bf00          nop
       c: 6801          ldr  r1, [r0]    ← 循环体内真的读
       e: 2900          cmp  r1, #0x0
      10: d0fc          beq  0xc         ← 跳回去再读
      12: 4770          bx   lr
```

**`wait_bad` 被编译成一条 `bx lr`。** 程序不等了，直接往下跑——
在裸机上的后果是**读到一个还没准备好的寄存器**，
症状千奇百怪（第一次上电正常、提高优化等级后失效、加一行 printf 又好了）。

原因（完整展开在 [5.14 反模式](5.14-反模式.md)）：C 标准允许编译器假定
"无副作用、不访问 volatile 的循环会终止"，而它能证明 `flag` 在循环里不会被改，
于是这个循环踏进了 UB，编译器想怎么处理都行。

## 二、裸机等待循环的三条硬规则

1. **条件变量必须是 `volatile`**——这是"每轮真读"的唯一保证；
2. **循环体写成 `{ }` 而不是 `;`**——`while (cond);` 那个分号在代码里几乎看不见，
   出 bug 时极难发现（而且 `-Wempty-body` 会警告）；
3. **要有超时**——硬件可能永远不响应（外设时钟没开是最常见的原因），
   无限等待 = 死机。

```c
/* 推荐形状 */
uint32_t timeout = 100000u;
while ((USART1_SR & TXE) == 0) {
    if (--timeout == 0u) return -1;      /* 超时返回错误，而不是永远卡住 */
}
```

第三条是书上完全没有的工程经验：**裸机没有 OS 帮你超时**，
一次外设失效就会让整个设备"死机"（连看门狗都得靠喂狗循环跑得到才有用）。

## 三、`while` 在裸机上的两种架构角色

| 角色 | 形态 | 说明 |
|---|---|---|
| **主循环** | `while (1) { poll(); }` | 裸机没有 OS，`main` 不能返回（[ch01](../01-hello-world/1.3-我们的第一个程序.md)） |
| **等待循环** | `while (!(SR & FLAG)) { }` | 等硬件，必须 `volatile` + 超时 |

轮询式主循环（本书 5.10 的架构，也是大多数简单裸机程序的架构）：

```c
while (1) {
    if (button_pressed_debounced()) { toggle_led(); wait_release(); }
    if (uart_rx_ready())            { handle_cmd(); }
}
```

它的对立面是中断驱动（[ch10](../ch10-interrupts.md)）：
主循环 `wfi` 睡觉，ISR 置标志，主循环醒来处理。
**本书第 10 章才会走到中断**，本章是轮询。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "`while` 就是先判断再执行" | 对，但**判断的那一读必须真的发生**——条件变量要 `volatile`（实测 `wait_bad` → `bx lr`） |
| "写 `while (cond);` 省一行" | 那个分号在代码里几乎不可见。`{ }` 更显式，`-Wempty-body` 也能配合 |
| "等标志就一直等" | 要有**超时**。外设时钟没开时标志永远不来，无限等待 = 死机 |
| "轮询够了" | 轮询期间 CPU 干不了别的，也睡不了。产品级做法走中断 + `wfi`（[ch10](../ch10-interrupts.md)） |
| "条件里的寄存器读几次无所谓" | 有些寄存器读一次就清标志（[5.1](5.1-if.md) Q1），放进条件里读会**吃掉数据** |

## 代码自测

<details>
<summary>Q1：`while (!(SR & FLAG)) { }` 我加了 `volatile` 了，还有别的坑吗？</summary>

有，三个：

**① 超时。** 如果外设时钟没开（最常见的低级错误——
[4.12](../04-numbers-and-bitops/4.12-用位操作控制内存映射IO寄存器.md) 里
`RCC_APB2ENR |= (1u<<2)` 就是干这个的），那个标志**永远不会来**，
`volatile` 只会让你更忠实地永远等下去。

```c
uint32_t tmo = 100000u;
while ((USART1_SR & TXE) == 0) { if (--tmo == 0u) return -ETIMEOUT; }
```

**② 读清标志（read-clear）型寄存器。** 有些标志**读一次就消失**：
`while (!(SR & FLAG))` 每轮读一次，可能第一轮的读就把标志清了，
后面再也等不到。这类寄存器要先读一次存起来再判断（[5.1](5.1-if.md) Q1）。

**③ 等待期间要不要喂看门狗。** 如果开了独立看门狗（IWDG），
长时间的等待循环里必须喂狗，否则设备会在等待中被复位——
而你会以为是外设坏了。

一句话：**`volatile` 只解决"每轮真读"，不解决"等多久"和"读的副作用"。**
</details>

<details>
<summary>Q2：轮询和中断，什么时候该用哪个？</summary>

判据是"**事件的紧迫程度**和"CPU 有没有别的事干"：

| 场景 | 轮询 | 中断 |
|---|---|---|
| 事件慢、CPU 没事干（按键、LED） | ✅ 够用，代码简单 | 也可以，但复杂化了 |
| 事件快、有截止时间（UART 接收、SPI 从机） | ❌ 会丢数据 | ✅ 必须 |
| 等待时间远长于处理时间（等 ADC 转换完成） | ✅ 可接受（配超时） | 更好（可以睡） |
| 需要低功耗（电池设备） | ❌ 空转耗电 | ✅ + `wfi` |
| 调试阶段 | ✅ 轮询好查（顺序执行，可单步） | ISR 难单步 |

本书的顺序是**先轮询（第 5 章），再中断（第 10 章）**——
这个顺序是对的：先体会轮询的浪费，才知道中断解决的是什么。

实际工程里的折中：**主循环轮询 + 中断置标志**。
ISR 只做最少的事（读一个字节、置一个 `volatile` 标志），
真正的处理放在主循环里——这样既有中断的实时性，又保持主循环的顺序性
（[ch10](../ch10-interrupts.md) 展开）。
</details>

<details>
<summary>Q3：`while(1)` 主循环里怎么做到"同时"做几件事？</summary>

裸机是单核，没有真正的"同时"。做法是**让每件事都"不阻塞"**：

```c
while (1) {
    task_button();     /* 读一次按键，更新状态机，立刻返回 */
    task_led();        /* 查一下该不该翻转 LED，立刻返回 */
    task_uart();       /* 有字节就处理一个，没有就立刻返回 */
    __asm__ volatile("wfi");
}
```

关键约束：**每个 task 都必须在有限且很短的时间内返回**，
不能有任何"等待"（不能 `delay_ms(20)`、不能 `while(!(SR&FLAG))`）。

需要"等"的事情要改写成**状态机**：

```c
/* ❌ 阻塞版 */
void task_led(void){ on(); delay_ms(500); off(); delay_ms(500); }

/* ✅ 状态机版：靠 SysTick 的 1ms 时基推进 */
void task_led(void){
    static uint32_t last; static uint8_t st;
    if (now_ms() - last < 500u) return;      /* 没到时间，立刻返回 */
    last = now_ms();
    st ^= 1u; (st ? on : off)();
}
```

这个"每个 task 都要能立刻返回"的纪律，就是**裸机的协作式多任务**；
再往前一步就是 RTOS 的抢占式调度（[ch20 规划中](../README.md)）——
FreeRTOS 里每个 task 还是这个形状，只是由调度器决定谁来跑。
时间基准 `now_ms()` 来自 SysTick，见 [ch19](../ch19-systick-and-timer.md)。
</details>
