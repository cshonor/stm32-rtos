## 书这一节讲什么

一句话：**`break` 立刻跳出所在的循环**（或 `switch`），继续执行循环后面的代码。

书讲的是语法。裸机上 `break` 有个书里完全没提、但会让人查一整天的坑：
**在 ISR 里用 `break`，可能跳过清中断标志——然后中断会无限重复触发。**

## 一、实测：`break` 在 Cortex-M 上就是一条条件跳转

```c
int f_break(int *a, int n){ int s=0; for(int i=0;i<n;i++){ if(a[i]<0) break; s+=a[i]; } return s; }
```

```
$ clang ... -Os -c bc.c && llvm-objdump -d bc.o
00000000 <f_break>:
       8: f852 3b04  ldr  r3, [r2], #4      ; 取 a[i]
       c: 2b00       cmp  r3, #0x0          ; a[i] < 0 ?
       e: d405       bmi  0x1c              ; ← break：跳到循环外（0x1c = bx lr）
      10: subs r1,#1
      12: add  r0,r3                        ; s += a[i]
      14: it eq / bxeq lr
      18: b 0x8                             ; 回循环头
      1c: bx lr                             ; 出口
```

`break` 编译成**一条 `bmi` 跳转到循环出口**，开销可忽略。
所以别为了"省一条跳转"而改写代码结构。

## 二、致命坑：ISR 里的 `break` 跳过清中断标志

```c
void USART1_IRQHandler(void){
    while (USART1_SR & RXNE) {
        uint8_t c = USART1_DR;
        if (ring_full(&rb)) break;              /* ← 缓冲满了，跳出 */
        ring_put(&rb, c);
    }
    USART1_SR &= ~RXNE;                          /* ← 被 break 跳过了（如果 break 在最后一步之外） */
}
```

**中断标志（这里是 `RXNE`）必须在 ISR 返回前清掉。**
清不掉会怎样：

- NVIC 看到中断源还是有效的 → ISR 返回后**立刻再次进入 ISR**；
- 主循环再也得不到执行机会；
- 表现为"程序卡死/看起来什么都没跑"，调试器停进去发现一直在 ISR 里。

三种防御写法：

```c
/* ① 单一出口：不用 break，用 if/else 走到最后统一清理 */
void USART1_IRQHandler(void){
    uint32_t sr = USART1_SR;
    if (sr & RXNE) {
        uint8_t c = USART1_DR;             /* ① 先读 DR —— 读 DR 本身就清 RXNE */
        if (!ring_full(&rb)) ring_put(&rb, c);
    }
    /* 没有 break，一定走到最后 */
}

/* ② goto cleanup：集中清理 */
void xxx_IRQHandler(void){
    ...
    if (err) goto cleanup;
    ...
cleanup:
    EXTI_PR = BIT(line);        /* 写 1 清标志 */
}

/* ③ 最稳：先清标志，再干活 */
void EXTI0_IRQHandler(void){
    EXTI_PR = BIT(0);           /* 先写 1 清 pending */
    handle_button();            /* 后面怎么跳都不影响标志 */
}
```

第 ③ 种最推荐——**清标志这件事不依赖控制流**。

## 三、`break` 在 `switch` 里的另一个经典坑（case 穿透）

```c
switch (st) {
case ST_A: do_a();        /* 忘了 break → 顺带执行 do_b() */
case ST_B: do_b(); break;
}
```

裸机上这个 bug 的隐蔽之处在于：状态机里连续两个 case 都执行，
可能是"看起来能工作"的（比如状态推进快了一步），
只有在特定时序下才出错。

编译器防御：`-Wimplicit-fallthrough`（`-Wextra` 里包含）。
想显式穿透就写 `/* fallthrough */` 注释，让编译器闭嘴也让人看懂。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "`break` 跳出循环" | 对，编译成**一条条件跳转**（实测 `bmi`），开销可忽略 |
| "`break` 只是控制流" | 在 ISR 里它可能意味着**清中断标志被跳过** → 中断无限重触发，程序假死 |
| "`switch` 的 case 会自动隔开" | ❌ 不会。漏 `break` 会穿透到下一个 case（`-Wimplicit-fallthrough`） |
| "`break` 只能跳一层" | 对。多层嵌套要 `goto`（向前跳）（[5.11](5.11-循环控制.md)） |
| "循环里 `break` 很自然" | 在**等待循环**里 `break` 前要确认：标志清了吗？超时了吗？ |

## 代码自测

<details>
<summary>Q1：为什么"忘了清中断标志"会让程序看起来彻底死掉？</summary>

因为 NVIC 的判定逻辑是**电平/请求驱动**的，不是"调用过一次就完事"。

流程：

1. 外设（比如 USART）的 `RXNE` 标志为 1 → 向 NVIC 发出中断请求；
2. NVIC 打断 CPU，跳到 `USART1_IRQHandler`；
3. ISR 里如果**没有清除那个标志**（没读 `DR`、没写 `PR`），
   外设依然认为"我有事要报告"，中断请求线依然是有效的；
4. ISR 返回 → NVIC 立刻看到请求还在 → **再次进入 ISR**；
5. 循环 3–4：CPU 永远在 ISR 里，主循环一次都跑不到。

症状：

- 程序"卡死"（其实在疯狂进出 ISR）；
- 调试器暂停时，调用栈显示一直在 `USART1_IRQHandler`；
- 看门狗可能复位设备（如果喂狗在主循环里——那就永远喂不到，于是反复复位）。

**这是裸机最经典的"程序死掉但代码看着没错"之一。**
排查第一问永远是：**这个 ISR 有没有清标志？清得对不对？**

清法因寄存器而异（这是要查手册的）：

| 标志 | 清除方式 |
|---|---|
| `USART_SR` 的 `RXNE` | **读 `DR`** |
| `EXTI_PR` 的某位 | **写 1**（写 0 无效！） |
| `TIM_SR` 的 `UIF` | **写 0**（写 1 无效，跟 EXTI 相反！） |
| SysTick 的 `COUNTFLAG` | 读 `CTRL` |

注意 TIM 和 EXTI 的约定是**相反的**——这就是为什么要查手册而不是凭印象。
</details>

<details>
<summary>Q2：`break` 在等待循环里用，安全吗？</summary>

看 break 之前有没有把"该做的事"做完。两种典型用法：

**① 超时退出（安全）**

```c
uint32_t tmo = 100000u;
while (!(USART1_SR & TXE)) {
    if (--tmo == 0u) break;        /* 超时，跳出 */
}
if (tmo == 0u) return -ETIMEOUT;   /* 跳出之后要处理"超时"这个结果 */
```

关键：**break 之后要检查"为什么跳出来的"**——
是条件满足了，还是超时了？不检查就把超时当成成功，是常见 bug。

**② 条件满足就退出（要注意副作用）**

```c
while (1) {
    uint32_t sr = USART1_SR;
    if (sr & RXNE) { c = USART1_DR; break; }   /* 读 DR 顺带清了 RXNE ✓ */
    if (sr & ORE)  { break; }                   /* ⚠ ORE 也要清，否则下次还在 */
}
```

第二条里的 `ORE`（过载错误）有自己的清除方式（读 `SR` 再读 `DR`），
break 之前没做 → 下次中断还会进来报 ORE。

一句话：**等待循环里的 `break`，要确认三件事——
条件为什么满足？标志清了吗？超时了吗？**
</details>

<details>
<summary>Q3：`switch` 里漏了 `break` 会怎样？编译器不报错吗？</summary>

不报错（穿透是合法语法，有时候正是你想要的），
但 `-Wextra` 会警告：

```
warning: unannotated fall-through between switch labels [-Wimplicit-fallthrough]
```

裸机上这个 bug 的典型场景是**状态机**：

```c
switch (st) {
case ST_LEN:  len = b; n = 0; st = ST_DATA;       /* 漏了 break */
case ST_DATA: buf[n++] = b; ...                    /* ← 会顺带执行！ */
}
```

表现：`ST_LEN` 那一轮会**多收一个字节**，
协议解析错位，但只有在特定帧长下才暴露——很难查。

三种写法：

```c
/* ① 每个 case 都 break（最常见） */
case ST_LEN: len = b; n = 0; st = ST_DATA; break;

/* ② 显式穿透（多个 case 共享代码） */
case ST_A:
case ST_B:                      /* 两个 case 同一处理 */
    handle_ab(); break;

/* ③ 刻意穿透并注明（让编译器闭嘴，让人看懂） */
case ST_A: do_a();
    /* fallthrough */
case ST_B: do_b(); break;
```

配合 `-Wswitch`（枚举漏 case 时警告）+ `-Wimplicit-fallthrough`，
状态机的这两类低级错误都能在编译期抓到——
裸机调试成本高，能用编译器抓的绝不留到板子上。
</details>
