## 书这一节讲什么

一句话：**`if (条件) A else B`——二选一**，可以串成 `else if` 链做多选一。

书讲语法。裸机上的真正问题是：**"多选一"在裸机里该用 `if-else` 链还是查表？**
答案跟 PC 上不一样，因为裸机上"分支"常常是在**选硬件配置**，而配置是可以预计算的。

## 一、实测：二选一的四种写法，机器码相同

```c
int a(int x){ if (x > 0) return 1; return 0; }
int b(int x){ if (x > 0) return 1; else return 0; }
int c(int x){ return (x > 0) ? 1 : 0; }
int d(int x){ return x > 0; }
```

```
$ clang ... -Os -c ifs.c && llvm-objdump -d ifs.o
00000000 <a>:   cmp r0,#0  /  mov.w r0,#0  /  it gt  /  movgt r0,#1  /  bx lr
0000000c <b>:   （同上，逐字节相同）
00000018 <c>:   （同上）
00000024 <d>:   （同上）
```

**结论：二选一怎么写都行，选最清楚的。** 别为了"效率"用三目运算符把代码写得难读。

## 二、`else if` 链 vs 查表：裸机上的真实取舍

典型场景：根据波特率设置分频寄存器。

```c
/* 写法 A：else if 链 */
uint16_t brr;
if      (baud == 9600)  brr = 0x1D4C;
else if (baud == 19200) brr = 0xEA6;
else if (baud == 38400) brr = 0x753;
else if (baud == 115200)brr = 0x271;
else                    brr = 0x271;      /* 默认 */
USART1_BRR = brr;

/* 写法 B：查表 + 循环 */
static const struct { uint32_t baud; uint16_t brr; } tbl[] = {
    { 9600, 0x1D4C }, { 19200, 0xEA6 }, { 38400, 0x753 }, { 115200, 0x271 },
};
uint16_t brr = 0x271;
for (size_t i = 0; i < sizeof tbl/sizeof tbl[0]; i++)
    if (tbl[i].baud == baud) { brr = tbl[i].brr; break; }
USART1_BRR = brr;
```

| | `else if` 链 | 查表 |
|---|---|---|
| 代码量 | 分支多时膨胀 | 数据在 Flash，代码短 |
| 执行时间 | 顺序比较，**不确定**（前面的先命中就快） | 固定 N 次比较 |
| 改配置 | 改代码 | 改数据（甚至可以放 Flash 里可更新的区域） |
| RAM | 0 | 0（表是 `const`，在 Flash） |
| 适合 | 分支少（≤3）、每个分支做的事不同 | 分支多、每个分支只是**选一个值** |

**裸机的判据**：如果每个分支只是"选一个常量值"，用**查表**（表放 `const`，不占 RAM）；
如果每个分支要做不同的动作（初始化不同外设），用 `if-else`。
这也是 Linux 内核里的常见做法（`switch` 只用于动作不同，配置值一律查表）。

## 三、`switch` 呢？书这节没讲，但值得知道

`switch` 在语义上就是"多选一"。编译器对它的处理有三种：

1. **分支少 / case 值稀疏** → 退化成 `if-else` 链（一串 `cmp` + 条件跳转）；
2. **case 值连续且密集** → 生成**跳转表**（一次间接跳转，O(1)）；
3. **只有两三个 case** → 跟 `if-else` 没区别。

裸机上的实际建议：`switch` 用在"状态机"上（状态值是枚举、连续的），
状态机在裸机里到处都是（协议解析、按键状态、通信状态机）——
那是 `switch` 最合适的场景。

## 四、裸机特有的一个坑：`else` 里的"默认动作"

硬件初始化经常是这种形状：

```c
if (use_hse) {
    RCC_CR |= RCC_CR_HSEON;                 /* 开外部晶振 */
    while (!(RCC_CR & RCC_CR_HSERDY)) { }   /* 等它稳定 */
    /* 配 PLL … */
} else {
    /* 用内部 HSI */
}
```

**`else` 分支不是"什么都不做"**，它意味着"用另一套完全不同的时钟配置"。
裸机上漏写 `else` 的后果是：那个寄存器保持复位值，而复位值往往**不是你想要的那个**
（比如 HSI 8MHz vs 你要的 72MHz，全系统时序差 9 倍）。

所以裸机初始化的规则：**每个 `if` 都写 `else`，哪怕 else 里只是一句注释说明"保持复位值是对的"**。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "`if-else` 就是二选一" | 裸机上常常是"两套硬件配置"，漏掉 `else` = 寄存器保持复位值，时序全变 |
| "多选一就用 `else if` 链" | 只是"选一个常量值"时，用 `const` 查表更省代码，且不占 RAM（表在 Flash） |
| "`switch` 一定比 `if-else` 快" | 不一定。case 稀疏时编译器退化成 `if-else` 链；只有密集连续才生成跳转表 |
| "三目运算符更快" | 实测四种写法机器码完全相同 |
| "分支预测会让某个分支变慢" | Cortex-M3 没有复杂分支预测器，短分支靠 `it` 块消除跳转（[5.1](5.1-if.md) 实测） |

## 代码自测

<details>
<summary>Q1：`else if` 链和查表，在 Cortex-M 上哪个更快？</summary>

不一定，要看分支数和命中分布：

- **命中靠前的分支**：`else if` 链更快——第一个 `cmp` 就命中，没进后面的比较；
- **命中靠后的分支**：`else if` 链要把前面所有条件都比一遍，查表的 N 次比较反而不一定更慢
  （因为查表的每次比较是"读 Flash 里的常量 + 比较"，而 Flash 访问在 STM32 上有等待周期）；
- **分支很多（> 8）且值连续**：`switch`（跳转表）是 O(1)，明显最快。

但**裸机上真正决定选型的往往不是速度，是这两条**：

1. **代码量 / Flash 占用**：`else if` 每个分支都要生成比较+跳转指令；
   查表只是数据，且数据可以放 `const`（Flash，1 MB 级别，比代码区更宽裕）。
2. **可维护性**：改配置值只改数据不改代码；甚至可以把表放在可更新的 Flash 扇区里，
   做成"出厂后可调"。

所以实际的选择是：**动作不同 → `if-else`/`switch`；值不同 → 查表**。
只有真的出现性能瓶颈时才去测——先 `llvm-size` 看 Flash 占用，再决定。
</details>

<details>
<summary>Q2：为什么裸机初始化里强调"每个 if 都要写 else"？</summary>

因为**寄存器的复位值不是"没有配置"，而是一个明确的、通常不是你想要的配置**。

举个例子（时钟源选择）：

```c
if (use_hse) {
    /* 开 HSE、等稳定、配 PLL 到 72MHz */
}
/* 忘了 else：CPU 继续用复位默认的 HSI 8MHz 跑 */
```

症状会是：串口波特率差 9 倍（打出一堆乱码）、延时差 9 倍（LED 闪得飞快或者看着不动）、
定时器全都不准。**但程序"能跑"，不会报错**——这类问题在裸机上能查半天。

写 `else` 的价值不只是"填上另一种配置"，更是**强迫你想过那个分支**：

```c
if (use_hse) {
    ...
} else {
    /* 用 HSI 8MHz：本工程不配 PLL，SysTick 按 8MHz 算 */
    _Static_assert(CPU_FREQ_HZ == 8000000, "HSI path assumes 8MHz");
}
```

那句 `_Static_assert` 就是"我确实想过这个分支"的证据，
也是后来改代码时防止两边不一致的护栏（[4.5](../04-numbers-and-bitops/4.5-整数的大小和表示.md) 讲过编译期断言）。
</details>

<details>
<summary>Q3：`switch` 什么时候真的值得用？</summary>

用在**状态机**上——裸机里最典型的场景。

状态机的特点是：状态值是**连续的小整数**（枚举，0/1/2/3…），
每个状态要做**不同的动作**。这正好命中 `switch` 的两个优势：

1. case 值连续密集 → 编译器生成**跳转表**，O(1) 分发；
2. 编译器能检查**是否覆盖所有枚举值**（`-Wswitch`，配合 `-Wall`）——
   加了新状态忘了处理某个 case，编译期就警告。

典型例子（串口协议解析）：

```c
typedef enum { ST_SYNC, ST_LEN, ST_DATA, ST_CRC } rx_state_t;
static rx_state_t st = ST_SYNC;

void rx_fsm(uint8_t b){
    switch (st) {
    case ST_SYNC: if (b == 0xAA) st = ST_LEN; break;
    case ST_LEN:  len = b; n = 0; st = ST_DATA; break;
    case ST_DATA: buf[n++] = b; if (n == len) st = ST_CRC; break;
    case ST_CRC:  st = ST_SYNC; /* 校验… */ break;
    }
}
```

而**如果每个分支只是"选一个常量值"**（波特率 → 分频值、引脚 → 寄存器偏移），
用[查表](#二else-if-链-vs-查表裸机上的真实取舍)更好。

判断一句话：**分支体是"动作" → `switch`；分支体是"值" → 查表。**
</details>
