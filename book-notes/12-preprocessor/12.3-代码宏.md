# 12.3 代码宏

> 书：第 12 章 预处理器 · 12.3 代码宏（原书 p174–185 区间内）
> 上一篇：[12.2 带参数的宏](12.2-带参数的宏.md) ｜ 下一篇：[12.4 条件编译](12.4-条件编译.md)
> 对应实验：`clang -E -P`（`#` / `##` 展开）+ Cortex-M3 `-Os` 下代码宏 vs 手写 inline 的体积对照（实测同为 28 字节）

## 书这一节讲什么

一句话：**能生成代码的宏**——`##` 粘合标识符、`#` 字符串化、以及"宏展开成一段函数"。

书上讲的是 `##` 和 `#` 的语法。本篇补上书里没讲的取舍：
**代码宏能省手写，但它生成的代码在调试器里是"隐形"的**，
而且实测表明——**它在 `-Os` 下并不比手写 `static inline` 更省**。

## 一、`##`：把两段 token 粘成一个标识符

```c
#define CONCAT(a,b) a##b
int CONCAT(my, Var) = 42;
```

**实测展开**：

```
$ clang -E -P m1.c
int myVar = 42;
```

`a##b` 把 `my` 和 `Var` 粘成 `myVar`——**这是函数做不到的事**。

⚠ **`##` 的参数不做宏展开**（和 `#` 一样）：

```c
#define XCAT(a,b)  CONCAT(a,b)     /* 多包一层 */
#define PREFIX     my
CONCAT(PREFIX, Var)                /* → PREFIXVar  ⚠ 不是 myVar */
XCAT(PREFIX, Var)                  /* → myVar      ✅ */
```

想让参数先展开再粘合，**要包两层**（和 [12.2](12.2-带参数的宏.md) 的 `XSTR` 一个套路）。

## 二、`#`：把参数变成字符串

```c
#define STRINGIFY(x) #x
#define XSTR(x)      STRINGIFY(x)
#define VER          3
```

**实测**：

```
$ clang -E -P m1.c
const char *s1 = "SQUARE_OK(2)";    ← STRINGIFY(SQUARE_OK(2))：原样，不展开
const char *s2 = "3";               ← XSTR(VER)：先展开 VER→3，再字符串化
```

典型用途——**断言宏**（本章后面会用到）：

```c
#define assert(e) ((e) ? (void)0 : __assert_func(__FILE__, __LINE__, __func__, #e))
                                                                            ^^
                                              把表达式原样变成字符串，失败时打印出来
```

## 三、代码宏：用宏生成函数

书上的经典例子——用宏生成"某个寄存器某一位"的三个操作函数：

```c
#define REG_BIT_DEF(name, reg, bit) \
    static inline uint32_t name##_get(void){ return ((reg) >> (bit)) & 1u; } \
    static inline void name##_set(void){ (reg) |= (1u << (bit)); } \
    static inline void name##_clear(void){ (reg) &= ~(1u << (bit)); }

REG_BIT_DEF(led, GPIOA_ODR, 5)      /* 生成 led_get / led_set / led_clear */
REG_BIT_DEF(tx,  USART1_SR, 7)      /* 生成 tx_get  / tx_set  / tx_clear  */
```

手写三个寄存器要 27 行，用宏是 2 行。

### 3.1 ⚠ 实测：代码宏**不比**手写 inline 更省

这是本节最值得记的一个数字。

```c
/* ① 用代码宏生成的 */
REG_BIT_DEF(led, GPIOA_ODR, 5)
void use_macro(void){ led_set(); led_clear(); (void)led_get(); }

/* ② 手写 static inline + 裸寄存器操作 */
static inline void led2_set(void){ GPIOA_ODR |= LED_BIT(5); }
void use_plain(void){ led2_set(); GPIOA_ODR &= ~LED_BIT(5); (void)((GPIOA_ODR >> 5) & 1u); }
```

```
$ llvm-nm --print-size -S cm.o
00000000 0000001c T use_macro      ← 0x1c = 28 字节
00000000 0000001c T use_plain      ← 0x1c = 28 字节

$ llvm-size cm.o
   text	   data	    bss
     72	      0	      0
```

**完全一样**。`use_macro` 的反汇编：

```
00000000 <use_macro>:
       0: f640 000c    	movw	r0, #0x80c
       4: f2c4 0001    	movt	r0, #0x4001       ← 0x4001080c 直接进立即数
       8: 6801         	ldr	r1, [r0]
       a: f041 0120    	orr	r1, r1, #0x20     ← led_set()   ：|= (1<<5)
       e: 6001         	str	r1, [r0]
      10: 6801         	ldr	r1, [r0]
      12: f021 0120    	bic	r1, r1, #0x20     ← led_clear() ：&= ~(1<<5)
      16: 6001         	str	r1, [r0]
      18: 6800         	ldr	r0, [r0]          ← led_get()
      1a: 4770         	bx	lr
```

`led_set` / `led_clear` / `led_get` **全部被内联掉了**，
连符号都没留在符号表里（`llvm-nm` 里只有 `use_macro` 和 `use_plain`）。

**所以代码宏的收益是"少写源码"，不是"少生成机器码"。**

### 3.2 那代码宏的代价是什么？

| 代价 | 说明 |
|---|---|
| **调试器里没有行号** | gdb 单步时进不去 `led_set()`——它在源码里根本不存在 |
| **报错信息难读** | 宏体是一整行（用 `\` 续行），错误定位到第 1 行 |
| **名字拼错不报错** | `REG_BIT_DEF(led, GPIOA_ODRR, 5)` → `GPIOA_ODRR` 未声明，报错指向宏体内部 |
| **IDE 跳转失效** | `led_set` 在源码里搜不到（它是 `##` 拼出来的） |
| **可读性** | 新人看 `REG_BIT_DEF(led, GPIOA_ODR, 5)` 不知道生成了什么 |

⚠ **"IDE 跳转失效"在裸机上特别伤**——
寄存器操作本来就是最容易写错的地方，
而代码宏恰好让"跳到定义去看一眼"这件事做不了。

## 四、代码宏的四个经典写法（值得抄的）

书上没有，但工程上天天用：

### ① 数组长度（⚠ 有陷阱）

```c
#define ARRAY_LEN(a) (sizeof(a) / sizeof((a)[0]))
```

⚠ **只在"数组可见"的地方对**。传进函数就退化成指针了：

```c
void f(uint32_t *p){ size_t n = ARRAY_LEN(p); }   /* ❌ sizeof(指针)/sizeof(元素) */
```

实测见 [ch06](../06-arrays-pointers-strings/README.md)。

### ② 容器求成员地址（Linux 内核的 `container_of`）

```c
#define container_of(ptr, type, member) \
    ((type *)((char *)(ptr) - offsetof(type, member)))
```

——RTOS 的链表实现必用（后续 ch20 会碰到）。

### ③ 编译期断言（C11 之前没有 `_Static_assert`）

```c
#define STATIC_ASSERT(cond, msg) typedef char static_assert_##msg[(cond) ? 1 : -1]
STATIC_ASSERT(sizeof(uint32_t) == 4, uint32_must_be_4_bytes);
```

原理：条件为真 → 数组长度 1；为假 → **长度 −1 → 编译错误**。
[ch08](../08-complex-types/README.md) 用的是 C11 的 `_Static_assert`，更清晰。

### ④ 日志宏（自动带文件名和行号）

```c
#define LOG(fmt, ...) printf("[%s:%d] " fmt "\n", __FILE__, __LINE__, __VA_ARGS__)
```

⚠ **`__FILE__`/`__LINE__` 必须在调用点展开**——
这就是 [12.2](12.2-带参数的宏.md) Q3 里说"必须用宏"的理由：
写成 `static inline` 函数，拿到的会是**函数自己那一行**。

## 五、本仓库的取向

> **少用代码宏，多用 `static inline` + 显式的寄存器定义。**

理由不是"宏不好"，而是**实测表明它没有性能收益**（都是 28 字节），
却付出了调试可见性的代价。裸机上调试窗口本来就窄，
**可读性 > 少敲几行**。

**什么时候还是该用代码宏**：

| 情况 | 例子 |
|---|---|
| 要生成**几十上百个**几乎一样的定义 | 32 个寄存器的位定义 |
| 生成的东西**不会被人阅读** | 硬件抽象层的批量定义 |
| 需要 **`##` 拼标识符** | X 宏（X-macro）表驱动 |

**X 宏（X-macro）** 是代码宏的"高级形态"——
用一张表同时生成 `enum`、字符串表、处理函数：

```c
/* 一张表，多处展开 */
#define CMD_LIST(X) \
    X(CMD_LED_ON,  "led on")  \
    X(CMD_LED_OFF, "led off") \
    X(CMD_RESET,   "reset")

/* ① 生成 enum */
typedef enum { CMD_LIST(X_ENUM) } cmd_id_t;
/* ② 生成字符串表 */
static const char *g_cmd_names[] = { CMD_LIST(X_STR) };
```

好处：**加一条命令只改一处**，不会漏。
代价：**可读性进一步下降**——这是有争议的技巧，用之前先问团队。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实测是什么 |
|---|---|
| "代码宏能省代码" | ⚠ 省的是**源码行数**，不是机器码。实测代码宏 28 B vs 手写 inline 28 B，**完全一样** |
| "`##` 的参数会先展开" | ❌ **不展开**。`CONCAT(PREFIX, Var)` → `PREFIXVar`，要包两层 `XCAT` |
| "`#` 的参数会先展开" | ❌ **不展开**。`STRINGIFY(VER)` → `"VER"`，`XSTR(VER)` → `"3"` |
| "`ARRAY_LEN` 到处能用" | ⚠ 只在数组可见处对。传进函数后 `a` 已退化成指针，结果完全错 |
| "代码宏生成的函数能在 gdb 里单步" | ❌ 宏在预处理阶段就没了，**没有独立行号**。实测 `llvm-nm` 里连 `led_set` 符号都没有（被内联了） |
| "宏展开报错好定位" | ❌ 多行宏的报错**定位到第 1 行**（`\` 续行使它们算一行） |

## 代码自测

<details>
<summary>Q1：`#` 和 `##` 的参数为什么不展开？怎么让它展开？</summary>

**因为 C 标准规定：`#` 和 `##` 的操作数不做宏展开。**

**实测**：

```
$ clang -E -P m1.c
const char *s1 = "SQUARE_OK(2)";    ← STRINGIFY(SQUARE_OK(2))：原样
const char *s2 = "3";               ← XSTR(VER)：展开后的值
```

```c
#define STRINGIFY(x) #x
#define XSTR(x)      STRINGIFY(x)     /* ← 多包一层 */
#define VER          3
```

| 写法 | 结果 | 原因 |
|---|---|---|
| `STRINGIFY(VER)` | `"VER"` | `#` 的操作数**不展开** |
| `XSTR(VER)` | `"3"` | 外层 `XSTR` **先展开参数** `VER`→`3`，再传给 `STRINGIFY` |
| `CONCAT(PREFIX, Var)` | `PREFIXVar` | `##` 的操作数**不展开** |
| `XCAT(PREFIX, Var)` | `myVar` | 同理，包两层 |

**机制**：宏替换时，编译器先扫一遍参数——
**当参数出现在 `#` 或 `##` 旁边时，跳过这一轮的展开**。
包一层之后，外层宏的参数**不在** `#`/`##` 旁边（它在 `XSTR(x)` 的 `x` 位置），
所以**外层会先展开**，展开完再传给内层。

**这个技巧的正式名字**叫 "double expansion"（或 "x-stringify"），
在生成版本号字符串时天天用：

```c
#define FW_MAJOR 1
#define FW_MINOR 2
#define FW_PATCH 3
#define STR(x)   #x
#define XSTR(x)  STR(x)
#define DOT(a,b) XSTR(a) "." XSTR(b)

const char *g_fw = XSTR(FW_MAJOR) "." XSTR(FW_MINOR) "." XSTR(FW_PATCH);
/* → "1" "." "2" "." "3" → 编译器拼接成 "1.2.3" */
```

⚠ **注意**：C 的字符串字面量拼接（adjacent string literal concatenation）
是**编译器**做的，不是预处理器。
`-E` 看到的还是 `"1" "." "2" "." "3"` 四段。

**一句话**：**想在 `#`/`##` 里拿到"宏的值"而不是"宏的名字"，就包两层。**
</details>

<details>
<summary>Q2：用代码宏生成寄存器操作函数，真的能省 Flash 吗？</summary>

**不能。省的是源码行数，机器码一个字节都不少。**

**实测（Cortex-M3，`-Os`）**：

```c
/* ① 代码宏生成的 */
#define REG_BIT_DEF(name, reg, bit) \
    static inline uint32_t name##_get(void){ return ((reg) >> (bit)) & 1u; } \
    static inline void name##_set(void){ (reg) |= (1u << (bit)); } \
    static inline void name##_clear(void){ (reg) &= ~(1u << (bit)); }
REG_BIT_DEF(led, GPIOA_ODR, 5)
void use_macro(void){ led_set(); led_clear(); (void)led_get(); }

/* ② 手写 */
static inline void led2_set(void){ GPIOA_ODR |= LED_BIT(5); }
void use_plain(void){ led2_set(); GPIOA_ODR &= ~LED_BIT(5); (void)((GPIOA_ODR >> 5) & 1u); }
```

```
$ llvm-nm --print-size -S cm.o
00000000 0000001c T use_macro      ← 28 字节
00000000 0000001c T use_plain      ← 28 字节
```

**反汇编完全一致的形态**：

```
00000000 <use_macro>:
       0: movw  r0, #0x80c
       4: movt  r0, #0x4001       ← 0x4001080c
       8: ldr   r1, [r0]
       a: orr   r1, r1, #0x20     ← led_set()
       e: str   r1, [r0]
      10: ldr   r1, [r0]
      12: bic   r1, r1, #0x20     ← led_clear()
      16: str   r1, [r0]
      18: ldr   r0, [r0]          ← led_get()
      1a: bx    lr                ← 共 28 字节
```

注意 **`led_set` / `led_clear` / `led_get` 三个符号在 `llvm-nm` 里根本不存在**——
它们全被内联进 `use_macro` 了。
`static inline` 在 `-Os` 下就是"展开"，和宏展开**殊途同归**。

**那代码宏到底省了什么**：

| 项目 | 手写 | 代码宏 |
|---|---|---|
| 源码行数（3 个寄存器 × 3 个操作） | 27 行 | **3 行** ✅ |
| 生成的机器码 | 28 B | **28 B**（一样） |
| gdb 里能单步进 `led_set()` | ✅ | ❌（符号不存在） |
| IDE 里 `Go to definition` 能找到 | ✅ | ❌（名字是 `##` 拼出来的） |
| 报错定位 | 精确行 | ⚠ 宏体第 1 行 |

**结论**：

> **代码宏是"源码组织工具"，不是"代码压缩工具"。**
> 想省 Flash，要看的是 `-Os` / `--gc-sections` / 数据结构
> （[ch11](../11-linker/11.5-映射文件.md)），不是宏。

**什么时候值得用**：要生成**几十上百个**几乎一样的定义时
（比如全芯片 32 个寄存器的位定义），
省下来的源码行数确实能减少手误。
只生成两三个，**手写更划算**——可读性和调试性都更好。
</details>

<details>
<summary>Q3：`ARRAY_LEN(a)` 这个宏有什么坑？为什么传进函数就错了？</summary>

**坑在"数组传进函数会退化成指针"。**

```c
#define ARRAY_LEN(a) (sizeof(a) / sizeof((a)[0]))
```

| 使用位置 | `sizeof(a)` 是什么 | 结果 |
|---|---|---|
| **数组可见的作用域** | 整个数组的字节数 | ✅ 正确 |
| **函数参数里** | **指针的大小** | ❌ 完全错 |

```c
void f(uint32_t *p){
    size_t n = ARRAY_LEN(p);     /* sizeof(uint32_t*) / sizeof(uint32_t) */
}
```

在 32 位 Cortex-M 上：`4 / 4` = **1**。
**任何数组传进来都报 1**，而且**不报错、不警告**。

**为什么会这样**：C 里数组作为函数参数时会**退化（decay）成指向首元素的指针**
（[ch06](../06-arrays-pointers-strings/README.md)）。
`void f(uint32_t p[])` 和 `void f(uint32_t *p)` **完全等价**——
编译器眼里 `p` 就是指针，`sizeof(p)` 是 4。

⚠ **更阴的形式**：

```c
void f(uint32_t p[64]){
    size_t n = ARRAY_LEN(p);     /* 还是 1！[64] 是给人看的，编译器忽略 */
}
```

那个 `[64]` **只是注释**，编译器完全不看。

**三条对策**：

**① 在函数内部不要用 `ARRAY_LEN`**，显式传长度：

```c
void f(uint32_t *p, size_t n);
f(g_buf, ARRAY_LEN(g_buf));        /* ✅ 在调用点用（数组可见） */
```

**② 用哨兵/结束标记**（字符串、链表）：不依赖长度。

**③ 用 C11 的类型检查宏挡住误用**（GCC/Clang 扩展版）：

```c
#define ARRAY_LEN(a) \
    (sizeof(a) / sizeof((a)[0]) \
     + 0 * sizeof(int[__builtin_types_compatible_p(typeof(a), typeof(&(a)[0])) ? -1 : 1]))
```

——原理：如果 `a` 已经是指针，`typeof(a) == typeof(&(a)[0])`，
数组长度 `-1` 触发编译错误。**可读性差，但能挡住 bug。**

⚠ **第三条在裸机上很少用**（太难读）。
工程上更常见的做法是**约定**：`ARRAY_LEN` 只在定义数组的那个文件里用。

**顺带一个常见误用**：结构体指针。

```c
typedef struct { uint32_t buf[64]; } pkt_t;
pkt_t *p = &g_pkt;
size_t n = ARRAY_LEN(p->buf);      /* ✅ 这个是对的：p->buf 是数组类型，没退化 */
```

`p->buf` **不是函数参数**，没有退化，`sizeof` 拿到的就是 256。✅
</details>
