# 7.5 递归

> 书：第 7 章 局部变量和函数 · 7.5 递归（原书 p89–97 区间内）
> 上一篇：[7.4 栈帧](7.4-栈帧.md) ｜ 下一篇：[7.6 编程风格](7.6-编程风格.md)
> 对应实验：`--target=armv7m-none-eabi -mcpu=cortex-m3`（-Os / -O0 对照）

## 书这一节讲什么

一句话：**函数可以调用自己**，书用阶乘当例子讲递归。

书把递归当正常的编程手段讲。但在 20 KB RAM 的 MCU 上，
**递归几乎总是错误的设计**——不是不能跑，而是**深度不可控**。
本篇用实测把这件事量化，并给出替代写法。

## 一、实测：`fact` 在 `-Os` 下根本没有递归

```c
int fact(int n){ return (n<=1) ? 1 : n*fact(n-1); }
```

```
$ clang ... -Os -c ch07.c && llvm-objdump -d ch07_os.o
00000034 <fact>:
      34: 2802     cmp  r0, #0x2
      36: bfbc     itt  lt
      38: 2001     movlt r0, #0x1
      3a: 4770     bxlt lr
      3c: 4601     mov  r1, r0
      3e: 2001     movs r0, #0x1
      40: 4348     muls r0, r1, r0      ← 循环体做乘法
      42: 2902     cmp  r1, #0x2
      44: f1a1 0101 sub.w r1, r1, #0x1
      48: d8fa     bhi  0x40            ← 往回跳，不是 bl 自己！
      4a: 4770     bx   lr
```

**没有 `bl fact`**——编译器把递归改写成了循环（尾递归/累加型递归优化），
栈用量变成 **0**（实测 `.su` 报 `fact 0 static`）。

## 二、实测：`-O0` 下是真递归，每帧 24 字节

```
$ clang ... -O0 -c ch07.c && llvm-objdump -d ch07_o0.o
0000006c <fact>:
      6c: b580     push {r7, lr}      ← 8 字节（返回地址 + 帧指针）
      6e: b084     sub  sp, #0x10     ← 16 字节
      ...
      86: f7ff fffe bl  0x86          ← 真的调用自己
```

`8 + 16 = 24 字节/帧`，与 `.su` 的 `fact 24 static` 完全一致。

**关键教训**：你看到的"栈用量 0"是**优化器的产物，不是语言性质**。
换编译器、换优化等级、递归形式稍微复杂一点（二叉树两个递归调用），
消除就失效了。

## 三、算一笔账：20 KB 栈能递归多深

NUCLEO-F103RB：RAM 20 KB，`_estack = 0x20005000`，
可用栈 ≈ 20 KB − `.data` − `.bss`。

| 函数 | 单帧（实测） | 20 KB 能撑 |
|---|---|---|
| `fact` @ -O0 | 24 B | 20480 / 24 ≈ **853 层** |
| `deep` @ -O0 | 16 B | 20480 / 16 ≈ **1280 层** |
| `fact` @ -Os | 0 B（变循环） | 无限（不占栈） |

看着还挺多？但：

- **`fact(13)` 就已经超过 `INT_MAX`**（13! ≈ 6.2e9）——
  整数溢出比栈溢出先到；
- 真机上还要扣掉**中断帧**（32 字节）和调用链上其他函数的帧；
- 最关键的是：**你没法静态证明"这个递归最多 N 层"**，
  一旦输入来自外部（协议包、用户输入、传感器数据），栈就是定时炸弹。

## 四、替代写法（三选一）

**① 改成迭代（首选）**

```c
int fact_iter(int n){          /* 一帧搞定，栈用量固定 */
    int r = 1;
    while (n > 1) { r *= n; n--; }
    return r;
}
```

**② 显式限制深度（非要递归时）**

```c
int depth_limited(node_t *n, int budget){
    if (n == NULL || budget <= 0) return 0;      /* 预算用完就停 */
    int l = depth_limited(n->left,  budget - 1);
    int r = depth_limited(n->right, budget - 1);
    return 1 + (l > r ? l : r);
}
```

**③ 显式栈（用数组模拟调用栈，放静态区）**

遍历树/图又不想递归时，用一个自己管理的栈（放在 `.bss`，大小编译期定死）：

```c
static node_t *stack[64];        /* 最多 64 层，编译期定死 */
static uint8_t sp;
```

这个做法的额外好处：**深度超限是"返回错误"，而不是"踩内存"**。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "递归是正常手段" | 20 KB RAM 上**几乎不该用**。实测 24 B/帧 → 853 层，而深度通常无法静态证明 |
| "编译器会帮我优化递归" | **有时是，不保证**。实测 `-Os` 变循环（0 B）、`-O0` 真递归（24 B/帧） |
| "尾递归一定能被优化" | C **没有**尾调用保证（ Scheme 有）。这是编译器优化，不是语言语义 |
| "栈溢出会报错" | 不会。静默踩 `.bss`/`.data`（[7.4](7.4-栈帧.md)） |
| "改成迭代很麻烦" | 多数情况不麻烦：累加型递归直接变 `while`；树遍历用显式栈 |

## 代码自测

<details>
<summary>Q1：为什么 `-Os` 下 `fact` 栈用量是 0？递归不需要栈吗？</summary>

递归**本来**需要栈，但 clang 在这个例子里把它消除了。

实测 `-Os` 版的 `fact` 里**没有 `bl fact`**，
而是一个 `bhi 0x40` 往回跳的普通循环（见正文反汇编）。

原因是 `fact(n) = n * fact(n-1)` 属于**累加型递归**：
递归调用是函数体里最后的操作，且不需要保留当前帧的任何状态，
编译器就可以改写成"循环 + 累加器"（`muls` 在循环体里）。

`-O0` 下不优化，就是真递归：`bl` 调用自己 + `push {r7, lr}`。

**关键教训**：这个"0"是优化器的产物。以下任一情况消除就会失效：

- 换优化等级（实测 `-O0` 立刻变 24 B/帧）；
- 换编译器（GCC 和 clang 的消除能力不同）；
- 递归形式变复杂：**两个递归调用**（二叉树遍历）、
  递归调用后还有别的操作（不是纯粹的累加）；
- 函数地址被取、被间接调用（编译器看不到调用点）。

工程规则一句话：**不要依赖编译器消除递归。要么自己写迭代，要么显式限制深度。**
在 20 KB RAM 上赌优化器的心情，代价是一次静默的内存破坏。
</details>

<details>
<summary>Q2：一定要用递归时，怎么保证不爆栈？</summary>

三层防护，按重要性：

**① 显式深度预算（最重要）**

```c
#define MAX_DEPTH 32
int visit(node_t *n, int depth){
    if (n == NULL) return 0;
    if (depth >= MAX_DEPTH) return -1;      /* 超限：返回错误，而不是继续压栈 */
    ...
}
```

把"会不会爆栈"从**不可证明**变成**编译期常量**——
`MAX_DEPTH × 单帧` 是一个能算出来的数字，可以直接对比栈预算。

**② 把单帧算出来，乘上深度**

```
最坏栈用量 = MAX_DEPTH × (单帧 from .su)  + 调用链上其他帧 + 中断帧 32 B
```

用 `-fstack-usage` 拿单帧（[7.4](7.4-栈帧.md) 实测 `fact` 24 B）。

**③ 运行时检测（兜底）**

在递归入口检查栈指针：

```c
extern uint32_t _sstack;                    /* 栈底（链接脚本给） */
#define STACK_LIMIT_BYTES 256u

int visit(node_t *n){
    uint32_t sp;
    __asm__ volatile ("mov %0, sp" : "=r"(sp));
    if ((uint32_t)&_sstack + STACK_LIMIT_BYTES > sp) return -1;   /* 快到底了 */
    ...
}
```

或者用魔数填充的水位检查（[7.4](7.4-栈帧.md) Q1）——
它不能防止这一次溢出，但能在事后告诉你"曾经逼近过"。

**更好的选择是压根不递归**：改成迭代或显式栈，
那样栈用量是编译期常量，连运行时检测都不需要。
</details>

<details>
<summary>Q3：Linux 内核也禁递归吗？为什么？</summary>

禁，而且理由和裸机一样——**栈太小**。

| | 栈大小 | 后果 |
|---|---|---|
| Linux 用户态 | 默认 **8 MB** | 随便递归 |
| **Linux 内核态** | **8 KB**（x86）/ 16 KB（arm64，可配） | 比用户态小三个数量级 |
| 裸机（本仓库） | **20 KB 的一部分** | 同量级 |

所以内核里的规则（和本仓库完全一致）：

- **禁止深递归**：内核文档明确要求"不要写超过几百字节栈帧的函数"，
  有 `-Wframe-larger-than=` 的构建检查（内核默认 1024，arm64 是 2048）；
- **禁止 VLA**：内核在 2018 年（4.20）把 VLA 全面移除了——
  理由正是"栈用量必须编译期可知"；
- **大缓冲一律静态或动态分配**，不压栈。

这让"内核编程"和"裸机编程"在栈这件事上变成了**同一类问题**。
反过来说，你在裸机上学到的栈纪律，到了内核里完全适用；
而内核社区的那些工具（`-Wframe-larger-than`、栈深度分析）
也可以直接搬到裸机工程里用。

一句话：**"栈很小"不是裸机的特例，是"没有 MMU 保护 + 没有 8 MB 默认栈"的所有环境的共性问题。**
</details>
