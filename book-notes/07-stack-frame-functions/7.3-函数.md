# 7.3 函数

> 书：第 7 章 局部变量和函数 · 7.3 函数（原书 p89–97 区间内）
> 上一篇：[7.2 隐藏变量](7.2-隐藏变量.md) ｜ 下一篇：[7.4 栈帧](7.4-栈帧.md)
> 对应实验：`--target=armv7m-none-eabi -mcpu=cortex-m3`（-Os / -O0）

## 书这一节讲什么

一句话：**函数把一段代码打包，可以传参数、返回结果**——C 的基本组织单位。

书讲语法。裸机上"函数调用"的代价值得量化，因为**每次调用都要消耗栈**，
而栈只有 20 KB。本节回答三个问题：一次调用花多少、参数怎么传、什么时候该内联。

## 一、参数怎么传：前 4 个走寄存器，多了走栈

ARM 的调用约定（AAPCS）：

```c
int f(int a, int b, int c, int d, int e);   /* a–d 走 r0–r3，e 走栈 */
```

| 参数 | 落点 |
|---|---|
| 第 1–4 个（且 ≤ 32 位） | `r0`–`r3` |
| 第 5 个及以后 | **栈**（调用者压，被调用者从栈读） |
| 返回值（≤ 32 位） | `r0` |
| 返回值（64 位） | `r0` + `r1` |
| **大结构体返回值** | 调用者传一个**隐藏指针**（指向一块栈上的空间） |

最后一条是裸机上的坑：**返回大结构体会在调用者的栈上开一块空间**，
而且常常顺便生成 `memcpy`（[7.2](7.2-隐藏变量.md) 实测 `__aeabi_memcpy`）。

```c
/* ❌ 裸机上不推荐 */
big_t make(void){ big_t t; /* ... */ return t; }

/* ✅ 调用者提供缓冲区 */
void make(big_t *out){ /* 填 *out */ }
```

第二种写法（"输出参数"）在 Linux 内核和所有裸机代码里都是标准做法。

## 二、实测：函数调用的最小代价

```c
int with_locals(int n){ int buf[8]; ... }     /* 叶子函数，-Os */
```

```
$ clang ... -Os -c ch07.c && llvm-objdump -d ch07_os.o
0000000c <with_locals>:
       c: b088     sub  sp, #0x20     ← 建帧
       ...
      30: b008     add  sp, #0x20     ← 拆帧
      32: 4770     bx   lr            ← 返回（lr 没被动过，不用压栈）
```

叶子函数的代价 = **建帧 + 拆帧 + `bx lr`**，没有内存访问。

非叶子函数（实测 `fact` @ -O0）要多付 `push {r7, lr}`（8 字节）+ 一次 `bl`：

```
0000006c <fact>:
      6c: b580     push {r7, lr}
      6e: b084     sub  sp, #0x10
      86: f7ff fffe bl  0x86          ← 调用自己
```

## 三、`static inline`：零成本抽象

```c
static inline uint32_t reg_read(volatile uint32_t *p){ return *p; }
static inline int      button_pressed(void){ return (GPIOA_IDR & BIT(0)) == 0; }
```

在 `-Os`/`-O2` 下会被**内联展开**，没有调用开销；
`-O0` 下有真实调用（[6.2](../06-arrays-pointers-strings/6.2-底层细节：指针.md) Q2 实测过
`button_pressed` 只有 6 条指令）。

裸机上这是**可读性 + 性能兼得**的标准手段：

- 硬件访问封装成 `static inline` 函数（比宏安全，有类型检查）；
- 短小的工具函数（位操作、边界检查）用它；
- ⚠ 别指望 `-O0` 下的性能。

## 四、什么时候不该调函数：ISR 里

| 约束 | 原因 |
|---|---|
| **不能调用不可重入函数** | `static` 缓冲被覆盖（`strtok`、某些 `printf` 实现） |
| **不能调用会阻塞的函数** | ISR 里"等"就是死锁 |
| **不能调用带锁的函数** | 主循环持有锁时被中断 → 死锁（[ch10](../ch10-interrupts.md)） |
| 调用深度要算进栈预算 | 中断帧 + ISR 的调用链叠加 |

所以裸机 ISR 的惯例是：**ISR 里只做最少的事**（读一个字节、置一个 `volatile` 标志），
真正的处理放主循环。

## 五、函数该多长、多少参数

书 7.6 讲编程风格，这里先给本仓库的口径：

| 项 | 建议 |
|---|---|
| 单函数长度 | ≤ 一屏（40–60 行）；超了就拆 |
| 参数个数 | ≤ 4 个（超过就走栈，且有出错风险）；更多就"配置结构体传指针" |
| 返回值 | 用 `int` 表示错误码（0 成功 / 负 errno），数据走输出参数 |
| 大结构体 | 不按值传，不按值返回（[ch08](../ch08-complex-types.md)） |

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "函数调用很便宜" | 叶子函数确实便宜（建帧 + `bx lr`）；非叶子要多付 `push {r7,lr}`（实测 24 B/帧） |
| "参数随便传" | 前 4 个走寄存器（AAPCS），**第 5 个起走栈** |
| "返回结构体很自然" | 会在**调用者的栈**上开空间，还可能生成 `memcpy`（实测 `U __aeabi_memcpy`） |
| "`inline` 一定更快" | `-O0` 下不内联；`-Os` 下编译器可能忽略你的 `inline`（它自己判断） |
| "函数里随便调库函数" | ISR 里不能调不可重入/阻塞/带锁的函数 |

## 代码自测

<details>
<summary>Q1：为什么裸机代码里到处是"输出参数"，而不是直接返回结构体？</summary>

因为**返回大结构体会让编译器做两件你没要求的事**：

1. **在调用者的栈上开一块空间**（隐藏变量，[7.2](7.2-隐藏变量.md)）：
   调用者把这块空间的地址通过**隐藏的 `r0`** 传给被调函数，
   被调函数往那里写——这叫 "sret"（structure return）；
2. **可能生成一次 `memcpy`**：把局部构造的结构体拷到那块空间
   （实测 `U __aeabi_memcpy` 就是这类产物）。

于是"返回结构体"的真实成本是：**栈（可能几百字节，取决于结构体大小）+ Flash（memcpy）+ 时间**。

标准替代写法：

```c
/* ❌ 按值返回 */
pkt_t parse(const uint8_t *buf, size_t n){ pkt_t p; /* fill */ return p; }

/* ✅ 输出参数：调用者决定内存放在哪 */
int parse(const uint8_t *buf, size_t n, pkt_t *out);   /* 返回错误码 */
```

第二种的好处：

- **内存位置由调用者决定**：可以是静态区、栈、或者池，不隐式吃栈；
- **返回值让出来做错误码**：裸机上"成功/失败"信息比数据更需要明确通道；
- **没有隐藏的 memcpy**。

这就是为什么 POSIX（`read(fd, buf, n)`）、
Linux 内核（`copy_to_user`）、几乎所有裸机驱动都是这个形状。
</details>

<details>
<summary>Q2：`inline` 和 `static inline` 有什么区别？宏呢？</summary>

| 写法 | 语义 | `-Os` 下 | `-O0` 下 |
|---|---|---|---|
| `inline f()` | 建议内联，但仍可能在别处生成副本 | 可能内联 | 真实调用 + 可能"重复定义"链接错误 |
| **`static inline f()`** | 本文件私有，可内联 | ✅ 内联（或干脆不生成函数体） | 真实调用（但不会链接冲突） |
| 宏 `#define F(x)` | 文本替换 | 必然"内联" | 必然"内联" |

**裸机上统一用 `static inline`**：

- 比宏**安全**：有类型检查、参数只求值一次（宏的经典 bug：`MAX(a++, b)`）；
- 比 `inline` **干净**：不会在多个 `.c` 里重复定义。

宏该用在什么时候？**宏能做的事函数做不了**时才用：

```c
#define REG32(base, off) (*(volatile uint32_t *)((base) + (off)))   /* 需要"地址常量" */
#define NELEM(a) (sizeof(a) / sizeof((a)[0]))                       /* 需要编译期 sizeof */
#define BIT(n)  (1u << (n))                                          /* 需要常量表达式 */
#define CONCAT(a,b) a##b                                             /* 需要 token 粘贴 */
_Static_assert(...)                                                  /* 不是宏，但同理 */
```

判据：**需要"编译期的符号/类型/常量"时用宏，需要"类型安全的计算"时用 `static inline`。**
（[ch12 预处理器](../ch12-preprocessor.md) 展开宏的两个经典陷阱。）
</details>

<details>
<summary>Q3：函数参数超过 4 个会怎样？</summary>

第 5 个起走**栈**——调用者压、被调用者从栈读，每次访问都是内存读写。

AAPCS（ARM 的调用约定）：

| 位置 | 落点 |
|---|---|
| 第 1–4 个 32 位参数 | `r0`–`r3`（寄存器，最快） |
| 第 5 个及以后 | 栈 |
| 64 位参数 | 占用 2 个寄存器（且要对齐到偶数号） |

裸机上的实际影响：

1. **性能**：栈上的参数每次用都要 `ldr`；
2. **栈用量**：参数空间算在**调用者**的帧里；
3. **可读性/出错率**：`set_config(1, 2, 0, 1, 0, 3)` 这种调用没人看得懂
   ——而且容易把两个相邻的 `int` 参数顺序写反，**编译器不会报**（类型相同）。

解法：把参数打包成**配置结构体，传指针**：

```c
typedef struct { uint32_t baud; uint8_t parity; uint8_t stop; uint8_t flow; } uart_cfg_t;
int uart_init(const uart_cfg_t *cfg);

/* 调用处：命名初始化，一眼看懂 */
static const uart_cfg_t cfg = { .baud = 115200, .parity = 0, .stop = 1, .flow = 0 };
uart_init(&cfg);
```

三个收益：参数顺序不会写反（有名字）、只用一个寄存器传指针、
而且 `const` 结构体通常能放进 Flash（省 RAM）。
</details>
