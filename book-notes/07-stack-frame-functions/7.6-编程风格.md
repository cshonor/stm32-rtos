# 7.6 编程风格

> 书：第 7 章 局部变量和函数 · 7.6 编程风格（原书 p89–97 区间内）
> 上一篇：[7.5 递归](7.5-递归.md) ｜ 本篇是第 7 章的收尾
> 对应实验：`--target=armv7m-none-eabi` + `-Wall -Wextra` 实测

## 书这一节讲什么

一句话：**代码是写给人看的**——命名、注释、函数长度这些约定。

书讲的是通用风格（命名、缩进、注释）。本篇把它落到**裸机**的具体规则上：
哪些风格要求在 PC 上是"好看"，在裸机上是"能不能活"。

## 一、本仓库的硬规则（违反会出真问题）

| 规则 | 原因 |
|---|---|
| **局部变量一律给初值** | 未初始化 = 栈上残留（[4.4](../04-numbers-and-bitops/4.4-初始化.md)） |
| **大缓冲（> 256 B）不压栈** | 20 KB 栈预算（[7.1](7.1-局部变量.md)） |
| **不用 VLA / `alloca`** | 栈用量必须编译期可知（[7.4](7.4-栈帧.md)） |
| **不递归**（或显式限深） | 深度不可静态证明（[7.5](7.5-递归.md)） |
| **硬件寄存器访问必须有 `volatile`** | 否则可能被优化掉（[5.14](../05-control-flow-button/5.14-反模式.md) 实测 `bx lr`） |
| **数组传参必须带长度** | C 数组不携带长度（[6.1](../06-arrays-pointers-strings/6.1-数组.md)） |
| **跨界数据用 `uint*_t`** | `long` 宽度跨平台不同（[4.5](../04-numbers-and-bitops/4.5-整数的大小和表示.md) 实测） |
| **等待循环必须有超时** | 外设时钟没开时标志永远不来 |

## 二、命名与组织

| 项 | 本仓库口径 | 例子 |
|---|---|---|
| 函数/变量 | 小写 + 下划线 | `uart_send_bytes()`、`rx_head` |
| 宏/常量 | 全大写 | `REG32()`、`RX_BUF_SIZE` |
| 寄存器名 | **跟手册一致** | `RCC_APB2ENR`、`GPIOA_CRL`（别自己起别名） |
| 模块前缀 | 模块名开头 | `uart_init()` / `uart_send()`（C 的"命名空间"，[ch17](../ch17-modular-programming.md)） |
| `static` | 只在本文件用的函数/变量一律加 | 减少全局符号污染 |
| 位号 | 宏或枚举，不写裸数字 | `BIT(2)`，不写 `|= 4` |

最后两条是裸机特有的：**寄存器名照抄手册**，
这样别人（和半年后的你）能直接对照 RM0008 查；
**位号用 `BIT(n)`**，避免"位号 vs 掩码"那个静默错误
（[4.1](../04-numbers-and-bitops/4.1-使用整数.md)）。

## 三、函数长度与注释

| 项 | 建议 |
|---|---|
| 单函数 | ≤ 一屏（40–60 行），超了就拆 |
| 参数 | ≤ 4 个（AAPCS 前 4 个走寄存器），多了用配置结构体 |
| 返回值 | `int`：0 成功 / 负值错误码（`-EINVAL` 风格）；数据走输出参数 |
| 注释 | 写**为什么**，不写**是什么**（`// 开 GPIOA 时钟` 是废话，`// 顺序不能换：先开时钟` 才是注释） |
| 魔数 | 一律 `#define` 或 `enum`，并配 `_Static_assert` |

裸机注释最有价值的两类：

```c
/* ① 顺序约束（违反会静默失效） */
RCC_APB2ENR |= BIT(2);        /* 必须先开时钟，再配 GPIO */
GPIOA_CRL   &= ~(0xFu << 0);

/* ② 硬件约定（手册说的，代码看不出来） */
EXTI_PR = BIT(0);             /* 写 1 清标志；写 0 无效（RM0008 §10.3.6） */
```

## 四、编译选项即风格

把纪律固化进构建，比写在文档里有效：

```makefile
CFLAGS += -Wall -Wextra -Wconversion -Wsign-compare -Wshadow \
          -Wframe-larger-than=256 -fstack-usage -ffreestanding
```

| 选项 | 抓什么 |
|---|---|
| `-Wall -Wextra` | 基础问题（含 `-Warray-bounds`、`-Wimplicit-fallthrough`） |
| `-Wconversion` | 隐式窄化（[4.3](../04-numbers-and-bitops/4.3-赋值.md) 实测 511→255） |
| `-Wsign-compare` | signed/unsigned 比较（[4.8](../04-numbers-and-bitops/4.8-无符号整数类型.md)） |
| `-Wshadow` | 变量遮蔽（同名局部变量藏住全局的） |
| `-Wframe-larger-than=` | 单帧超预算 |
| `-fstack-usage` | 生成栈用量表（[7.4](7.4-栈帧.md)） |

再配主机侧的 `-fsanitize=undefined,address` 跑纯逻辑（[4.9](../04-numbers-and-bitops/4.9-溢出.md)、[6.4](../06-arrays-pointers-strings/6.4-数组溢出.md) 实测有效）。

## 五、"裸机风格"和 Linux 内核风格的交集

本仓库遵循的多数规则其实来自内核社区，因为**约束相同**（栈小、无 MMU 保护、长期运行）：

- 禁递归、禁 VLA；
- 大结构体不按值传递/返回；
- 错误码返回值 + 输出参数；
- 模块前缀当命名空间；
- `goto` 向前跳做统一清理（[5.11](../05-control-flow-button/5.11-循环控制.md)）；
- 位操作用 `BIT(n)`。

差别只有一处：**内核有动态分配和锁，裸机通常没有**
（[ch13](../ch13-dynamic-memory.md) 讲裸机为什么不用堆）。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "风格是可读性问题" | 裸机上一半"风格"其实是**正确性**：忘 `volatile`、数组不传长度、等待不设超时都会静默出错 |
| "注释越多越好" | 写"为什么"（顺序约束、硬件约定）；"是什么"是代码的复读 |
| "函数短一点好看" | 裸机上有硬收益：短函数栈帧小、调用链浅（[7.4](7.4-栈帧.md)） |
| "编译警告先不管" | 裸机上**每一个警告都该处理**：没有运行时兜底，警告往往是唯一的线索 |
| "风格要团队统一" | 对，但**硬件相关的部分要跟手册统一**（寄存器名照抄），这是更高的优先级 |

## 代码自测

<details>
<summary>Q1：为什么裸机工程里"编译警告"特别重要？</summary>

因为**警告常常是你唯一的线索**。

PC 上有三层兜底：MMU（段错误）、sanitizer（精确报告）、
以及"程序崩了所以你一定会去查"。
裸机上这三层都没有——程序不崩，只是行为不对，
而唯一能提前告诉你"这里可疑"的就是编译器警告。

实测过的例子：

| 警告 | 对应的静默 bug |
|---|---|
| `-Warray-bounds` | 常量下标越界（实测 `b[3]` 被抓到；运行时下标抓不到） |
| `-Wconversion` | 隐式窄化：`0x1FF` 存进 `uint8_t` 变成 255 |
| `-Wparentheses` | `if (x = 1)` 的 `=`/`==` 笔误 |
| `-Wimplicit-fallthrough` | `switch` 的 case 漏 `break`（状态机推进错位） |
| `-Wsign-compare` | `int` 与 `unsigned` 比较，负值被提升成巨大正数 |
| `-Wframe-larger-than` | 单帧栈用量超预算 |
| `-Wunused-variable` | 很可能是"改了逻辑但漏了一处" |

所以本仓库的做法：

1. **`-Wall -Wextra` 是底线**，再按项目加 `-Wconversion` 等；
2. **新代码零警告**（老代码的警告要么修、要么明确标注原因）；
3. 重要的项目直接 **`-Werror`**，让 CI 拦住。

一句话：**裸机上的警告不是"建议"，是"编译器在告诉你它发现了什么"。**
</details>

<details>
<summary>Q2：`-Wconversion` 噪音太大怎么办？</summary>

确实大——裸机代码里到处是 `reg |= (1u << n)` 这类运算，
`-Wconversion` 会对"隐式转换可能改变值"的每一处报警。

三种处理方式，按推荐度：

**① 显式转换表达"我知道"**（最推荐）

```c
uint32_t sr = USART1_SR;
uint8_t  b  = (uint8_t)(sr & 0xFFu);     /* 明确：就是要截断 */
```

好处：噪音变成了**文档**——后来读代码的人知道这里是刻意的截断，不是笔误。

**② 统一类型，减少跨界**

很多警告其实是"类型选得不一致"：

```c
uint16_t len;                 /* 从协议里解出来 */
uint32_t n = 0;
while (n < len) { ... }       /* 无警告：都是 unsigned，且 16→32 是安全的加宽 */
```

`-Wconversion` 主要警告**窄化**和**符号性变化**，
把跨界数据的类型统一（[4.7](../04-numbers-and-bitops/4.7-标准整数.md)）能消掉一大半。

**③ 局部关掉（最后手段）**

```c
#pragma clang diagnostic push
#pragma clang diagnostic ignored "-Wconversion"
/* 一段确实需要大量转换的代码（比如位打包） */
#pragma clang diagnostic pop
```

⚠ 别全局关——那就等于把这条防线撤了。

**不推荐的做法**：为了消警告而改用 `int`。
那会把"位模式"数据放进有符号类型，引入
[4.9](../04-numbers-and-bitops/4.9-溢出.md) 里那类 UB（实测 `-O0`/`-O2` 结果不同）。
</details>

<details>
<summary>Q3："代码写给人看"在裸机上有什么额外的含义？</summary>

多一层含义：**代码要写给人对照手册看**。

PC 上代码只跟"需求"对照；裸机代码还要跟**芯片手册**对照。
所以裸机代码里最有价值的两种"可读性"是：

**① 寄存器名 = 手册名**

```c
#define RCC_APB2ENR REG32(0x40021000u, 0x18u)   /* ✅ 照抄手册 */
#define CLOCK_EN    REG32(0x40021000u, 0x18u)   /* ❌ 自己起的名字，查手册时要翻译 */
```

半年后你拿着 RM0008 找 `RCC_APB2ENR`，能直接 Ctrl-F 到代码里。

**② 位号写成"位号"，不写成"值"**

```c
RCC_APB2ENR |= BIT(2);      /* ✅ bit2 = IOPAEN，手册上就是 bit2 */
RCC_APB2ENR |= 4;           /* ❌ 4 是什么？要反过来算成 bit2 */
```

同样，配置值写 `(0x2u << 20)` 而不是 `0x00200000`——
前者直接对应手册的 "CNF5[1:0] + MODE5[1:0] = 0b0010"。

**③ 顺带：把"为什么"写进注释**

```c
GPIOA_ODR |= BIT(0);   /* F1：输入模式下 ODR 位 = 1 选上拉（手册 RM0008 §9.2.4）
                          漏了这行就是浮空输入 —— 电平随机 */
```

这类注释在裸机上的价值远超普通项目，
因为**硬件行为不写在代码里**，只能靠注释传递。

一句话：**裸机代码的可读性 = "能不能对着手册读懂"。**
这也解释了为什么本仓库的命名规则里，"跟手册一致"优先级高于"风格统一"。
</details>
