# 1.2 下载 STM32 系统工作台

> 书：第 1 章 Hello World · 1.2 下载 STM32 系统工作台（原书 p4）
> 上一篇：[1.1 安装 GCC](1.1-安装GCC.md) ｜ 下一篇：[1.3 我们的第一个程序](1.3-我们的第一个程序.md)

## 书这一节讲什么

去 ac6-tools 下载 **System Workbench for STM32**（简称 SW4STM32）——一个基于
Eclipse 的免费 IDE，装完能把 GCC、GDB、ST-Link 驱动一次性配好。

## 这一节基本作废（这是全书过期最快的一页）

**SW4STM32 已经停止维护**，ST 官方现在推的是 **STM32CubeIDE**。
书成于 2021 年，这一段是工具链章节里天然会腐烂的部分。

但"作废"不等于"没用"。这一节真正要你理解的是它解决的那个问题：

> **一个新手要同时搞定编译器、构建系统、烧录器、调试器四件事，中间任何一个环节
> 配错都表现为"点灯不亮"，而且报错信息指向的地方往往不是真正的问题所在。**
> IDE 的价值就是把这四件事打包成一个"验证过的组合"。

## 我换成了什么

| 书的方案 | 我的方案 | 为什么 |
|---|---|---|
| SW4STM32（Eclipse + 内置工具链） | **命令行三件套**：clang + make + openocd | 每一步都看得见，出错能定位到具体环节；Mac 上免安装 |
| IDE 自动配的 ST-Link 驱动 | macOS **免驱**（实测直接认到 `STLINK V2J28M18`） | 不用装任何驱动 |
| IDE 自动配的调试器 | xPack OpenOCD（解压即用，darwin-arm64 原生） | `~/.local/xpack-openocd-0.12.0-7/` |
| IDE 绑定的 GDB | `arm-none-eabi-gdb`（只有调试时才需要） | 编译链完全不用它 |

## 实测：工具都从哪来

```bash
$ ls ~/.local/
xpack-openocd-0.12.0-7/          # openocd，解压即用
arm-gnu-toolchain-14.2.rel1-darwin-arm64-arm-none-eabi/   # 只有 gdb 会用

$ ~/.local/xpack-openocd-0.12.0-7/bin/openocd --version
xPack Open On-Chip Debugger 0.12.0+dev-01204-g329cb0d61 (2024-01-08-15:57)
```

这两个都能**塞在家目录里**，不碰 `/usr/local`、不碰 `/opt`、不需要 sudo——
这是在无权写系统目录的 Mac 上做嵌入式开发的关键前提。

## 如果你还是想装 CubeIDE

不是不行，条件如下（都是公开信息，安装体验我没实测）：

| 项 | 值 |
|---|---|
| 安装包大小 | 约 1.2GB（第三方博客数据） |
| 磁盘要求 | 官方文档写 10GB 空闲 |
| macOS 支持 | 2.1.0 起有 **AArch64 原生包**（自带 JRE/GCC/工具） |
| 我的机器 | `/Applications` 是 `root:admin` 组可写 → **不用 sudo 就能拖进去** |
| 已知坑 | workspace 路径要纯英文；首次启动可能被 macOS 门禁拦，要去"隐私与安全性"手动放行 |
| ⚠ 版本口径 | 文档写支持 macOS 14/15，ST 社区 2026 年回复写支持 macOS 15/26。**装之前去下载页看当前版本的 system requirements** |

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| 书 1.2：装 System Workbench | **已停止维护**。ST 的接替品是 STM32CubeIDE。照着点一遍 = 学一套三年后作废的菜单 |
| "IDE 里配好就不用管环境了" | 恰恰相反：IDE 把环境藏起来了，一旦它配的环境跟你机器不匹配（比如 macOS 版本、Java 版本），**排错难度暴涨** |
| "嵌入式必须装驱动" | ST-Link 在 macOS 上是 **HID 免驱**。Linux 上要装 udev 规则，Windows 上要装 ST-Link 驱动。这跟 OS 有关，不是"嵌入式"的属性 |
| "装 IDE 就是装环境" | IDE = 编辑器 + 构建系统 + 工具链 + 调试前端。真正难配的是最后两样，而它们都有命令行版 |

## 代码自测

<details>
<summary>Q1：为什么嵌入式 IDE 都基于 Eclipse？这正常吗？</summary>

在 2005–2020 这个窗口里，这是**行业常态**，原因是 Eclipse 提供了两样当时很难自己造的东西：

1. **CDT（C/C++ Development Tooling）**：C 语言的索引、跳转、补全，从头写要好几年；
2. **可插拔的构建/调试集成层**：接自己的编译器、自己的 gdbserver 都只需要写插件。

所以几乎所有芯片厂商的官方 IDE 都是 Eclipse 换皮：STM32 的 SW4STM32/CubeIDE、
NXP 的 MCUXpresso、TI 的 Code Composer Studio、Microchip 的 MPLAB X（这个用的是 NetBeans）。
代价是启动慢、吃内存、UI 十年不变。

**近几年的趋势是往 VSCode 迁**（ST 自己都出了 STM32CubeIDE for Visual Studio Code 扩展），
跟嵌入式本身没关系，纯粹是编辑器生态的迁移。
</details>

<details>
<summary>Q2：既然不用 IDE，我怎么确认"环境装好了"？</summary>

按**链路顺序**逐段确认，每段一个命令，哪段不过问题就在哪段：

| 段 | 命令 | 通过的样子 |
|---|---|---|
| 编译器 | `clang --target=armv7m-none-eabi -c x.c -o x.o` | 不报错，`llvm-readelf -h x.o` 显示 `Machine: ARM` |
| 链接器 | `ld.lld -T linker.ld -o x.elf x.o` | 不报错，`llvm-readelf -h x.elf` 显示 `Entry point` |
| 转 bin | `llvm-objcopy -O binary x.elf x.bin` | 生成非空的 `.bin` |
| 硬件连接 | `openocd -f <cfg>` | 日志出现 `STLINK V2J28M18` |
| 目标识别 | 同上 | 日志出现 `SWD DPIDR 0x1ba01477` + `Cortex-M3 r1p1` |
| 烧录 | `openocd -c "program x.bin 0x08000000 verify reset exit"` | `Verified OK` |
| 调试 | `arm-none-eabi-gdb x.elf -ex "target remote localhost:3333"` | 能打出源码行号 |

这套"分层确认"的排障法，比 IDE 里"点一下不亮"再猜要快得多。
</details>
