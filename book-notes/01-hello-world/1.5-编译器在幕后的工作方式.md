## 书这一节讲什么

**全书最重要的一节之一。** 它把"编译"这个笼统动作拆成四步，
每步有明确的输入输出。理解这一步，后面所有链接错误、`undefined reference`、
段符号问题都有了落点。

```
hello.c ──[预处理器 cpp]──▶ hello.i ──[编译器 cc1]──▶ hello.s ──[汇编器 as]──▶ hello.o ──[链接器 ld]──▶ hello.elf
```

## 实测：四步的产物长什么样

拿一个 8 行的 `hello.c` 走一遍（clang 23.1.0，`--target=armv7m-none-eabi`）：

```c
#include <stdint.h>
#define LED_PIN 13u
int add(int a, int b) { return a + b; }
int main(void) {
    volatile uint32_t x = LED_PIN;
    x = (uint32_t)add((int)x, 1);
    return (int)x;
}
```

| 步骤 | 命令 | 产物 | 行数 | 大小 |
|---|---|---|---|---|
| 预处理 | `clang -E` | `hello.i` | 81 | 1776 B |
| 编译 | `clang -S` | `hello.s` | 75 | 1915 B |
| 汇编 | `clang -c` | `hello.o` | —— | 876 B |
| 链接 | `ld.lld -T …` | `hello.elf` | —— | （见 ch11） |

**8 行的源文件，预处理后变成 81 行**——多出来的全是 `<stdint.h>` 的 typedef。

### 1.5.1 预处理器

它的工作只有三件：**展开 `#include`、展开宏、处理条件编译**。
它不理解 C 语法（不知道 `int` 是什么），纯文本替换。

实测 `clang -E` 的输出尾部：

```
typedef long long int intmax_t;
typedef long long unsigned int uintmax_t;
# 2 "hello.c" 2

int add(int a, int b) { return a + b; }
int main(void) {
    volatile uint32_t x = 13u;          ← LED_PIN 被替换成 13u
    x = (uint32_t)add((int)x, 1);
    return (int)x;
}
```

注意 `# 2 "hello.c" 2` 这种 **linemarker**：它告诉编译器"下一行对应源文件
hello.c 的第 2 行"。**这是断点和报错能显示行号的底层机制**——
预处理之后就丢了行号，靠 linemarker 找回来。

### 1.5.2 编译器

从 `.i` 到 `.s`，这是真正"懂 C"的一步：语法分析、语义检查、优化、指令选择、
寄存器分配。产物是**人类可读的汇编**。

实测 `hello.s` 的关键片段（**没加 `-O`，所以是 `-O0` 的代码**）：

```asm
add:
	sub	sp, #8          ← 开栈帧
	str	r0, [sp, #4]    ← 参数 a 存栈
	str	r1, [sp]        ← 参数 b 存栈
	ldr	r0, [sp, #4]    ← 再读回来（-O0 的典型浪费）
	ldr	r1, [sp]
	add	r0, r1
	add	sp, #8
	bx	lr              ← 返回

main:
	.save	{r7, lr}
	push	{r7, lr}
	movs	r0, #13     ← LED_PIN 的常量已经在指令里了
	str	r0, [sp, #4]    ← volatile 写：真的落内存
	ldr	r0, [sp, #4]
	movs	r1, #1
	bl	add
	...
	pop	{r7, pc}        ← 返回：把 lr 弹进 pc
```

三个能立刻看出门道的点：

1. **`-O0` 下 `add` 的参数被存栈又读回**，`-O1` 以上会变成 `add r0, r1` 直接返回；
2. **`volatile` 的写真的产生了 `str`**，没被优化掉；
3. **`push {r7, lr}` / `pop {r7, pc}` 是函数调用的标准开销**——
   `bl` 会把返回地址放进 `lr`，函数里再调别人就会覆盖 `lr`，所以要存栈。
   这就是[7.4 栈帧](../07-stack-frame-functions/7.4-栈帧.md)的正题。

还有一行容易被忽略但很重要：

```asm
.eabi_attribute	34, 1	@ Tag_CPU_unaligned_access
```

**EABI 属性**是给链接器看的元数据。如果两个 `.o` 的属性不兼容
（比如一个软浮点一个硬浮点），链接器会报错拒绝——这就是"ABI 不匹配"报错的来源。

### 1.5.3 汇编器

从 `.s` 到 `.o`：把助记符翻译成机器码，生成**重定位信息**（因为地址还没定），
并按 `section`（`.text` / `.data` / `.bss`）归类。

实测 `llvm-readelf -S hello.o`：

```
[Nr] Name              Type            Address  Off    Size   Flg
[ 2] .text             PROGBITS        00000000 000034 000028  AX
[ 4] .ARM.exidx        ARM_EXIDX       00000000 00005c 000010  AL
[ 8] .ARM.attributes   ARM_ATTRIBUTES  00000000 000082 000041
[ 9] .llvm_addrsig     LLVM_ADDRSIG    00000000 00013c 000001  E
```

两个要点：

- **`Address` 全是 0**。`.o` 里的地址是"待定"的，每个段都从 0 开始，
  真正的地址由链接器给。这就是**重定位（relocation）**概念的由来。
- **`.ARM.exidx`（异常索引表）被 LLVM 自动加进来了**，你一行都没写。
  `.text` 有 40 字节，`.ARM.exidx` 16 字节——**它是 C++ 异常 / 栈回溯用的**，
  纯 C 项目里是纯粹的体积浪费。这个坑在 [11.2 链接过程](../11-linker/11.2-链接过程.md) 会展开。

### 1.5.4 链接器

最后一步：把多个 `.o` 合并，**分配真实地址**，解析跨文件符号引用，
按链接脚本把段摆到 Flash / RAM。

```bash
$ ld.lld -Ttext=0x08000000 -o /dev/null hello.o
ld.lld: warning: cannot find entry symbol _start; not setting start address
```

这个 warning 非常有教育意义：**链接器默认的入口符号是 `_start`**
（Linux 上 crt0.o 提供的那个）。裸机上没有 `_start`，
所以要么在链接脚本里用 `ENTRY(Reset_Handler)` 指定，要么它会静默不设入口地址。

## 一张总表：四步分别在"翻译什么"

| 步骤 | 输入语义 | 输出语义 | 谁懂 C 语法 |
|---|---|---|---|
| 预处理器 | 文本 | 文本 | 不懂，纯替换 |
| 编译器 | C 语法树 | 目标架构汇编 | **懂** |
| 汇编器 | 汇编助记符 | 机器码 + 重定位条目 | 不懂（只认助记符） |
| 链接器 | 目标文件 + 库 | 可执行镜像 | 不懂（只认符号和段） |

**记住最后一行**：链接器完全不懂 C。所以 `undefined reference to 'foo'`
永远不该去怀疑 C 代码写错了，而要怀疑"`foo` 的 `.o` 有没有参与链接 / 顺序对不对"。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "编译器就是 gcc" | `gcc`/`clang` 是**驱动**，下面还分 cpp / cc1 / as / ld 四个程序。`-###` 能看到它真实调了什么 |
| "预处理只是展开 `#include`" | 还负责宏展开 + 条件编译 + **linemarker**（行号映射）。全大写宏名之所以是惯例，就是为了不被普通标识符撞上 |
| "`.o` 文件里的地址就是最终地址" | 不是。`.o` 里每个段都从 0 开始，地址是链接期才定的。这就是"重定位"这个名字的由来 |
| "`undefined reference` 是代码写错了" | 99% 是链接问题：`.o` 没加进去、库顺序不对（GNU ld 是单遍扫描）、或者符号被 `static` 藏了 |
| "`-O` 只影响速度" | 影响**调试能力**：内联之后断点打不上、变量看不到。调试期用 `-Og` 或 `-O0` |
| "链接器只管拼文件" | 它还做：段合并、地址分配、`--gc-sections` 回收、符号解析、生成 map 文件。**`-Map` 是排查段问题的主要工具** |

## 代码自测

<details>
<summary>Q1：为什么 `.o` 里每个段的地址都是 0？如果直接跑 `.o` 会怎样？</summary>

因为**编译期不可能知道最终地址**，理由有两个：

1. 一个 `.c` 会被链进不同的程序（库尤其明显），每次地址都不一样；
2. 链接脚本（`MEMORY` 区域）是链接期的输入，编译器看不到。

所以编译器采用"**相对自己**"的表示：段内偏移从 0 开始，
对外部符号的引用记成"这里要填一个地址，符号名叫 foo"——
这就是**重定位条目（relocation entry）**，放在 `.rel.text` 这类段里。

直接跑 `.o` 不行：它不是可执行格式（没有 program header），
而且里面的重定位还没解析，等于一张"地址待填"的表。
链接器的作用就是把这张表填完，最后写出带 `Entry point` 的 ELF。
</details>

<details>
<summary>Q2：为什么预处理后有 `# 2 "hello.c" 2` 这种怪东西，删掉行不行？</summary>

那是 **linemarker（行标记）**，格式是 `# 行号 "文件名" 标志`。它的作用是告诉下游
编译器："下一行对应 hello.c 的第 2 行"。

因为预处理会把 `#include` 展开成几百行，源文件的行号早就乱了。
没有 linemarker，编译器只能报告"hello.i 第 78 行出错"——
而你手上根本没有 `hello.i` 这个文件。

**删掉不影响编译结果，但会毁掉所有报错和断点的行号信息。**

顺带一个实用推论：`-E` 的输出里有 `# 1 "<built-in>"` 这种伪文件名，
说明这几行是编译器内建定义，不是你代码里的东西。
</details>

<details>
<summary>Q3：`.ARM.exidx` 是哪来的？纯 C 项目里为什么它没用了还占地方？</summary>

它是 **ARM 的异常/回溯索引表**，每个函数一条记录，存"这个函数地址范围 +
如何从它回到调用者"。

它是**编译器自动加的**（LLVM 在 ARM 后端的默认行为），你一句都没写。
存在两个原因：

1. C++ 异常需要它来沿调用栈查找 handler；
2. 调试/崩溃回溯需要它。

**纯 C + 无异常 + 不需要回溯**的项目里，它纯粹占 16 字节/函数左右。
实测在 `hello.o` 上是 16 字节 vs `.text` 40 字节——**相当于 40% 的体积**。

能不能去掉？`-fno-unwind-tables` **去不掉**（本仓库实测无效）。
可靠做法是在链接脚本里 `/DISCARD/ : { *(.ARM.exidx) }`
（或者用 `--gc-sections` 让可达性分析把它收掉）。详见 ch11。
</details>
