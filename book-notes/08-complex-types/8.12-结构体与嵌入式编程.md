# 8.12 结构体与嵌入式编程

> 书：第 8 章 复杂数据类型 · 8.12 结构体与嵌入式编程（原书 p98–118 区间内）**——本章核心**
> 上一篇：[8.11 创建自定义类型](8.11-创建自定义类型.md) ｜ 下一篇：[8.13 typedef](8.13-typedef.md)
> 对应实验：`--target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding`（`offsetof` + `_Static_assert` + 反汇编）

## 书这一节讲什么

一句话：**结构体就是寄存器块的地图。**

这是整章唯一"非语法"的一节，也是整章的**题眼**。
前面 8.1–8.11 讲的所有东西（对齐、填充、位操作、命名、typedef）
都是为了让这一节的写法**不出错**。

芯片把一组相关的寄存器排在连续地址上（GPIOA 的 CRL/CRH/IDR/ODR/BSRR/BRR/LCKR
依次落在 `0x40010800` + `0x00/04/08/0C/10/14/18`），
而 C 的结构体正好描述"一段连续内存里每个偏移是什么"。
所以你可以把基址强制转换成结构体指针，然后写 `GPIOA->BSRR`。

## 一、写法对比：从裸地址到寄存器地图

**阶段①：裸地址（ch03 的写法）**

```c
*(volatile uint32_t *)0x40010810u = (1u << 5);      /* 0x40010810 是什么？ */
```

**阶段②：基址 + 偏移宏**

```c
#define GPIOA_BASE 0x40010800u
#define GPIOA_BSRR (*(volatile uint32_t *)(GPIOA_BASE + 0x10u))
GPIOA_BSRR = (1u << 5);
```

**阶段③：结构体地图（本节）**

```c
typedef struct {
    volatile uint32_t CRL;    /* +0x00 */
    volatile uint32_t CRH;    /* +0x04 */
    volatile uint32_t IDR;    /* +0x08 */
    volatile uint32_t ODR;    /* +0x0C */
    volatile uint32_t BSRR;   /* +0x10 */
    volatile uint32_t BRR;    /* +0x14 */
    volatile uint32_t LCKR;   /* +0x18 */
} GPIO_TypeDef;

#define GPIOA ((GPIO_TypeDef *)0x40010800u)
#define GPIOC ((GPIO_TypeDef *)0x40011000u)

GPIOA->BSRR = (1u << 5);
uint32_t btn = (GPIOA->IDR >> 0) & 1u;
```

**三种写法生成完全相同的机器码**（[8.8](8.8-结构体指针.md) 实测 `movw/movt/str`），
所以选③的理由不是性能，而是：

| 好处 | 说明 |
|---|---|
| 可读性 | `GPIOA->BSRR` 一眼看出是哪个外设哪个寄存器 |
| **可校验** | 偏移错了 `_Static_assert` **编译期就炸**，不是等到"灯不亮" |
| 可移植 | 换芯片只改结构体定义和基址，业务代码一行不动 |
| 可复用 | `GPIOA`/`GPIOC` 共用同一份成员定义，不重复抄 7 个宏 |

## 二、实测：用 `_Static_assert` 把布局钉死

```c
#include <stddef.h>
_Static_assert(offsetof(GPIO_TypeDef, CRL)  == 0x00, "CRL");
_Static_assert(offsetof(GPIO_TypeDef, CRH)  == 0x04, "CRH");
_Static_assert(offsetof(GPIO_TypeDef, IDR)  == 0x08, "IDR");
_Static_assert(offsetof(GPIO_TypeDef, ODR)  == 0x0C, "ODR");
_Static_assert(offsetof(GPIO_TypeDef, BSRR) == 0x10, "BSRR");
_Static_assert(offsetof(GPIO_TypeDef, BRR)  == 0x14, "BRR");
_Static_assert(offsetof(GPIO_TypeDef, LCKR) == 0x18, "LCKR");
_Static_assert(sizeof(GPIO_TypeDef) == 0x1C, "size");     /* 7 × 4 = 28 = 0x1C */
```

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding -Os -c gpio.c
GPIO 布局断言全部通过
```

**故意把 `BSRR` 的期望偏移写错（0x10 → 0x14）试试**：

```
gpio_bad.c:10:16: error: static assertion failed due to requirement
              '__builtin_offsetof(GPIO_TypeDef, BSRR) == 20': BSRR
   10 | _Static_assert(offsetof(GPIO_TypeDef, BSRR) == 0x14, "BSRR");
      |                ^~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
gpio_bad.c:10:45: note: expression evaluates to '16 == 20'
```

编译器直接告诉你：**实际是 16(0x10)，你写的是 20(0x14)**。

这就是本节的**核心工程价值**：
**把"灯不亮"这类运行时谜题，变成"编译失败"这种带精确数字的编译期错误。**

## 三、两条必须遵守的硬约束

**① 每个成员都要 `volatile`**

```c
typedef struct {
    volatile uint32_t CRL;     /* ✅ 每个都写 */
    volatile uint32_t CRH;
    ...
} GPIO_TypeDef;
```

漏一个的后果（ch01 实测过）：编译器可能把对该寄存器的访问优化掉。
典型现场——等待标志位的循环被删成一条 `bx lr`，程序"卡住"在看起来毫无问题的地方。

`volatile` 不能只写在结构体指针上：

```c
volatile GPIO_TypeDef *GPIOA;    /* ⚠ 这个 volatile 修饰的是指针，不是成员 */
```

要每个成员都 `volatile`（或者 `GPIO_TypeDef volatile *`，但那是另一回事）。

**② 绝对不要给寄存器结构体加 `packed`**

```c
typedef struct { ... } __attribute__((packed)) GPIO_TypeDef;   /* ❌ 灾难 */
```

两重后果（[8.4](8.4-内存中的结构体.md)、[8.5](8.5-访问未对齐数据.md) 实测）：

1. **偏移被挤紧**，不再等于手册值 → `GPIOA->BSRR` 写到别的寄存器上；
2. **未对齐访问**：Cortex-M0/M0+ 不支持未对齐 32 位访问 → **HardFault**。

寄存器结构体要的是**反过来**的操作：成员全 `uint32_t` 自然对齐（4 字节），
然后用 `_Static_assert(sizeof == 0x1C)` 确认**没有任何意外填充**。

## 四、配套的编译开关：让编译器替你守着

| 开关 | 抓什么 | 实测输出 |
|---|---|---|
| `-Wpadded` | 结构体被插了填充 | `warning: padding struct 'struct S1' with 3 bytes to align 'b'` |
| `_Static_assert(offsetof(...)==手册值)` | 偏移和手册不符 | `error: static assertion failed ... expression evaluates to '16 == 20'` |
| `sizeof` 断言 | 总大小不对（漏/多成员） | `_Static_assert(sizeof(GPIO_TypeDef)==0x1C, "")` |

三个一起开，寄存器映射就基本不可能悄悄写错。

## 五、和外设驱动的结合形态

```c
/* gpio.h：地图 + 操作 */
typedef struct { volatile uint32_t CRL, CRH, IDR, ODR, BSRR, BRR, LCKR; } GPIO_TypeDef;
#define GPIOA ((GPIO_TypeDef *)0x40010800u)

typedef enum { PIN_RESET = 0u, PIN_SET = 1u } pin_state_t;

static inline void gpio_write(GPIO_TypeDef *g, unsigned pin, pin_state_t s){
    g->BSRR = s ? (1u << pin)                 /* 低 16 位：置位 */
                : (1u << (pin + 16u));        /* 高 16 位：清零 —— 一条 str，原子 */
}
static inline uint32_t gpio_read(GPIO_TypeDef *g, unsigned pin){
    return (g->IDR >> pin) & 1u;
}
```

注意这里**没有**用 `g->ODR |= (1<<pin)`——
那是读-改-写，非原子（[ch04 4.12](../04-numbers-and-bitops/4.12-用位操作控制内存映射IO寄存器.md)）。
用 `BSRR` 只需要一条 `str`。

## 六、与 Linux 驱动 / LDD- 的对照

| 概念 | 裸机（本节） | Linux 驱动 |
|---|---|---|
| 寄存器映射 | `(GPIO_TypeDef *)0x40010800u` 直接强转 | `ioremap()` 拿虚拟地址，**之后写法完全一样** |
| 地址来源 | 芯片手册写死 | 设备树（DT）里读出来 |
| `volatile` | 手写 `volatile uint32_t` | `readl()` / `writel()` 内部带屏障 |
| 布局校验 | `_Static_assert(offsetof(...))` | 同样靠 `offsetof` + 结构体定义 |
| 并发安全 | 关中断 / `BSRR` | spinlock / 原子操作 |

**核心洞察**：Linux 驱动里 `writel(val, base + REG_OFF)` 和裸机的 `gpio->REG = val`
是**同一套思想**——只是 Linux 多了一层 MMU 和地址映射。
你在裸机上学到的"结构体 = 寄存器地图"，到了内核里完全适用。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "结构体是语法，和硬件无关" | **结构体就是寄存器块的地图**——本章题眼 |
| "结构体映射和裸地址一样快" | 实测机器码**完全相同**（[8.8](8.8-结构体指针.md)），差别在可读性与可校验性 |
| "偏移我数过了，不会错" | 用 `_Static_assert` 钉。实测写错时编译器报 `expression evaluates to '16 == 20'` |
| "`volatile` 写在哪都行" | 必须**每个成员**都写。写在指针上（`volatile GPIO_TypeDef *`）修饰的是指针 |
| "`packed` 能省空间，加上更严谨" | ❌ 寄存器结构体加 `packed` = 偏移错位 + M0 上 HardFault |
| "结构体是给软件用的，硬件是地址" | 硬件的手册本来就是一张"偏移表"，结构体就是那张表的代码化 |

## 代码自测

<details>
<summary>Q1：为什么寄存器结构体必须用 `_Static_assert` 校验偏移？不校验会怎样？</summary>

因为**写错偏移不会报错，只会"灯不亮"**。

```c
typedef struct {
    volatile uint32_t CRL, CRH, IDR, ODR, BSRR, BRR, LCKR;
} GPIO_TypeDef;
#define GPIOA ((GPIO_TypeDef *)0x40010800u)
```

这段代码的正确性**完全依赖"我抄对了手册"**。如果抄错了：

- `BSRR` 的偏移写成 `0x14`（实际 `0x10`）→ 写到了 `BRR`；
- 更糟：如果漏了一个成员，后面**所有**偏移都往前挪，
  `GPIOA->BSRR` 会写到 `LCKR` 或更远的未知地址。

这两类错误的表现都是**程序跑得下去、但灯不亮**。
在裸机上"灯不亮"的排查成本极高——你不知道是时钟没配、引脚错了、
还是写到了别的寄存器。

加上断言之后：

```
_Static_assert(offsetof(GPIO_TypeDef, BSRR) == 0x10, "与 RM0008 不符");
```

实测把 `0x10` 写成 `0x14`：

```
gpio_bad.c:10:16: error: static assertion failed due to requirement
              '__builtin_offsetof(GPIO_TypeDef, BSRR) == 20': BSRR
gpio_bad.c:10:45: note: expression evaluates to '16 == 20'
```

**编译失败，且告诉你"实际 16、你写 20"。** 排查时间从"两小时查硬件"变成"0 秒"。

建议**每个**寄存器都写一条（实测 8 条断言全部通过），
外加一条总大小断言：

```c
_Static_assert(sizeof(GPIO_TypeDef) == 0x1C, "");   /* 7 × 4 = 28 */
```

大小断言能抓到"多写/漏写一个成员"这类只挪动后半部分的错误。

**成本：8 行。收益：整类 bug 从"运行时谜题"变成"编译期错误"。**
在裸机上这是我能想到的性价比最高的一笔投入。
</details>

<details>
<summary>Q2：`volatile` 到底该写在哪？写在指针上行不行？</summary>

**写在每个成员上。写在指针上不行（或至少语义不同）。**

```c
/* ✅ 正确：每个成员 volatile */
typedef struct {
    volatile uint32_t CRL;
    volatile uint32_t CRH;
    ...
} GPIO_TypeDef;
#define GPIOA ((GPIO_TypeDef *)0x40010800u)
```

```c
/* ⚠ 语义不同：这个 volatile 修饰的是"指针变量"，不是成员 */
volatile GPIO_TypeDef *GPIOA;
```

后者的意思是"`GPIOA` 这个指针变量本身可能被外部改动"，
**不是**"`CRL` 这个寄存器可能被外部改动"。
所以编译器仍然可以缓存 `GPIOA->CRL` 的读值、合并两次写。

后果（ch01 实测过）：等待标志位的循环

```c
while ((GPIOA->IDR & 1u) == 0) { }      /* 期望：等按键 */
```

如果 `IDR` 不是 `volatile`，编译器会认为"这个值不会变"，
把循环优化成一条 `bx lr`——**程序直接往下跑，看起来像"按键坏了"**。

另一个常见误区：以为"结构体是 volatile 的，成员就都是"。

```c
typedef volatile struct { ... } GPIO_TypeDef;     /* ⚠ 这种写法 */
```

不同编译器对这个的处理不一致，**别赌**。
老老实实每个成员写一个 `volatile`：

```c
typedef struct {
    volatile uint32_t CRL, CRH, IDR, ODR, BSRR, BRR, LCKR;   /* 一行写完，也不费事 */
} GPIO_TypeDef;
```

（注意：一行里 `volatile uint32_t CRL, CRH, ...` 每个变量都带 `volatile`——
`volatile` 是声明说明符，作用于这一行的所有声明符。这与 [8.11](8.11-创建自定义类型.md) 里
`#define` 的 `*` 不共享是**两回事**，别混淆。）
</details>

<details>
<summary>Q3：能不能给寄存器结构体加 `packed`？省几个字节不香吗？</summary>

**不能，而且加了后果严重。**

`packed` 做两件事，两件都是灾难：

**① 偏移全错**

```c
typedef struct { volatile uint32_t CRL; volatile uint32_t CRH; ... }
    __attribute__((packed)) GPIO_TypeDef;
```

`packed` 之后成员被挤紧。如果结构体里混了非 4 字节成员，
后面的偏移就不再是 `0x04/0x08/0x0C...`——
`GPIOA->BSRR` 会写到**别的寄存器**上。

而且寄存器结构体本来全是 `uint32_t`、本来就自然对齐（4 字节），
**加 `packed` 省不下任何字节**——纯亏。

**② 未对齐访问 → M0 HardFault**

实测（[8.4](8.4-内存中的结构体.md)、[8.5](8.5-访问未对齐数据.md)）：

```
struct P { char a; int b; } __attribute__((packed));
packed P: size=5 off(b)=1        ← b 落在奇数地址
```

| 内核 | 未对齐 32 位访问 |
|---|---|
| Cortex-M0 / M0+ | **不支持 → HardFault** |
| Cortex-M3 / M4 / M7 | 支持但慢，且**不是原子的** |
| x86 / arm64 | 支持，无感 |

**寄存器结构体的正确写法是"反过来"的**：

1. 成员全部 `uint32_t`，自然 4 字节对齐；
2. `_Static_assert(sizeof(GPIO_TypeDef) == 0x1C, "")` 确认**没有意外填充**；
3. 开 `-Wpadded`，有人插非 4 字节成员时立刻报警；
4. **永远不加 `packed`**。

`packed` 唯一合理的场景是描述字节流协议格式——
而且即使那样也更推荐按字节手工拼装（[8.5](8.5-访问未对齐数据.md)）。

一句话：**`packed` 是给"字节流"用的，寄存器块是"字对齐的地址空间"，两者不要混。**
</details>
