# 8.9 结构命名

> 书：第 8 章 复杂数据类型 · 8.9 结构命名（原书 p98–118 区间内）
> 上一篇：[8.8 结构体指针](8.8-结构体指针.md) ｜ 下一篇：[8.10 联合体](8.10-联合体.md)
> 对应实验：主机侧 clang 23.1.0（类型兼容性）+ Cortex-M 交叉（`_Static_assert` 校验自引用布局）

## 书这一节讲什么

一句话：**结构体有 tag，typedef 有别名，两个是不同的命名空间**——
怎么给结构体起名字，以及 `struct foo` 和 `foo_t` 什么时候能互相替代。

书讲得偏语言细节。裸机上真正要紧的是另外两件事：

1. **能不能自引用**（链表、树）——决定你必须写 tag；
2. **匿名结构体 typedef 会导致类型不兼容**——两个"长得一样"的结构体不是同一个类型。

## 一、实测：两个"同形"的匿名结构体是不同类型

```c
typedef struct { int x; } anon_a_t;
typedef struct { int x; } anon_b_t;      /* 成员完全一样 */
void take_a(anon_a_t *p){ (void)p; }
int main(void){ anon_b_t b = {1}; take_a(&b); }
```

```
$ clang -c tag.c -o /dev/null
tag.c:7:12: error: incompatible pointer types passing 'anon_b_t *'
                   to parameter of type 'anon_a_t *' [-Wincompatible-pointer-types]
    7 |     take_a(&b);
      |            ^~
```

**布局完全相同也不行**——C 的类型兼容性看的是"是不是同一个声明"，不是"字节长什么样"。

这条在裸机上的实际意义：

```c
/* 两个驱动各自 typedef 一个"看起来一样"的配置结构体 */
typedef struct { uint32_t baud; uint8_t parity; } uart_cfg_t;   /* uart.c */
typedef struct { uint32_t baud; uint8_t parity; } dbg_cfg_t;    /* debug.c */

uart_init(&dbg_cfg);      /* ❌ 编译错误——好事！编译器帮你抓到了误用 */
```

这反而是**想要的行为**：两个子系统不该共享配置类型，编译器替你守住了边界。
（要真想共享，就该**只声明一次**，放公共头文件里。）

## 二、实测：自引用必须有 tag

```c
/* ✅ 有 tag：结构体内可以用 struct node 引用自己 */
typedef struct node { uint32_t v; struct node *next; } node_t;

/* ⚠ 无 tag：typedef 名 node_t 在结构体体内还没生效，没法自引用 */
typedef struct { uint32_t v; void *next; } bad_node_t;    /* 只能退化成 void* */
```

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding -c tag2.c
（断言全部通过）
_Static_assert(sizeof(node_t) == 8, "");
_Static_assert(offsetof(node_t, next) == 4, "");
```

Cortex-M 上 `node_t` = 8 字节（`uint32_t` 4 + 指针 4），`next` 在偏移 4。
换成 Mac/arm64 就是 16 字节（`v` 4 + 填充 4 + 指针 8）——
**所以这两个数字必须用 `_Static_assert` 钉住，别靠脑补**。

`void *next` 那个版本的代价：

```c
bad.next = &other;                        /* 能存 */
node_t *n = bad.next;                     /* ❌ void* 需要强转，丢了类型检查 */
```

**规则：凡是链表/树/队列这类自引用结构，结构体的 tag 是必需品，不是风格问题。**

## 三、实测：`-Wpadded` 把填充直接报出来

命名管不了布局，但布局错了名字再漂亮也没用。clang 有个专门的开关：

```c
struct S1 { char a; int b; char c; };
```

```
$ clang -Wpadded -c pad.c -o /dev/null
pad.c:2:25: warning: padding struct 'struct S1' with 3 bytes to align 'b' [-Wpadded]
pad.c:2:8:  warning: padding size of 'struct S1' with 3 bytes to alignment boundary [-Wpadded]
```

两条警告，正好对应 [8.4](8.4-内存中的结构体.md) 画出来的两处填充：
成员间 3 字节 + 尾部 3 字节 = 12 字节（成员只占 6）。

**寄存器结构体建议开这个开关**：如果哪天有人往 `GPIO_TypeDef` 里插了个 `uint8_t`，
`-Wpadded` 会立刻叫，而不是等到"灯不亮"。

## 四、本仓库的命名约定

| 类别 | 写法 | 例子 |
|---|---|---|
| 寄存器块结构体 | `大写_tTypeDef` 风格或 `xxx_t`，**必须带 tag** | `typedef struct { ... } GPIO_TypeDef;` |
| 业务数据结构体 | `小写_t`，**带 tag**（便于自引用/前向声明） | `typedef struct node { ... } node_t;` |
| 只在本文件用的一次性结构 | 可以匿名 typedef | `typedef struct { int x, y; } pt_t;` |
| 函数指针类型 | `小写_cb_t` / `_fn_t` / `_ops_t` | `typedef void (*uart_rx_cb_t)(...)` |
| 整数宽度 | 一律 `<stdint.h>`，不自己 typedef | `uint32_t` 而非 `u32` |

**前向声明（forward declaration）**是带 tag 的第二个理由：

```c
/* uart.h —— 不想把结构体定义暴露出去 */
struct uart_cfg;                          /* 只需一个 tag */
void uart_init(const struct uart_cfg *c); /* 调用方看不到成员，只能用你给的 API */
```

匿名 typedef 做不了这件事——你必须把整个定义搬进头文件。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "`struct foo` 和 `foo_t` 是一回事" | **两个命名空间**。匿名 typedef 没有 tag，就没法前向声明、没法自引用 |
| "成员一样的结构体可以互相传" | 实测**不行**：`anon_b_t*` → `anon_a_t*` 直接 `-Wincompatible-pointer-types` 报错 |
| "匿名 typedef 更简洁，多用" | 链表/树/前向声明写不了。实测 `typedef struct node {...} node_t` 才能 `struct node *next` |
| "结构体大小我数得出来" | `node_t` 在 Cortex-M 是 8 字节、Mac/arm64 是 16 字节。用 `_Static_assert` 钉 |
| "填充看不出来" | 开 `-Wpadded`：实测报 `padding struct 'struct S1' with 3 bytes to align 'b'` |
| "`void *next` 也能做链表" | 能，但**丢了所有类型检查**，每次取用都要强转 |

## 代码自测

<details>
<summary>Q1：为什么非要写 tag？`typedef struct {...} foo_t;` 不是更简洁吗？</summary>

三个只有 tag 能做到的事：

**① 自引用（链表/树）**

```c
typedef struct { uint32_t v; void *next; } bad_t;      /* 只能退化成 void* */
typedef struct node { uint32_t v; struct node *next; } node_t;   /* ✅ 类型安全 */
```

`typedef` 名在结构体体内**还没定义完**，所以匿名版本没法写 `node_t *next`。
用 `void*` 顶替的代价是每次取 `next` 都要强转，编译器再也帮不了你。

**② 前向声明（隐藏实现）**

```c
/* 头文件里只放这一行，成员定义留在 .c 里 */
struct uart_cfg;
void uart_init(const struct uart_cfg *c);
```

匿名结构体**必须把整个定义搬进头文件**，等于把内部布局公开给了所有使用者——
你以后改一个成员，所有 include 它的文件都要重编译。

**③ 诊断信息更好读**

实测报错里写的是 `struct S1`、参数类型 `anon_a_t *`——
有 tag 时编译器会打出 `struct node`，比"某个匿名类型"好定位得多。

**什么时候可以匿名**：确确实实只在一个 `.c` 里用、不需要自引用、
不需要对外暴露的一次性小结构。满足了就匿名，省一个名字；
否则一律写 tag——**成本是一个单词，收益是三类能力。**
</details>

<details>
<summary>Q2：两个成员完全相同的结构体为什么不能互相赋值 / 传参？</summary>

因为 C 判断类型兼容看的是**声明身份**，不是内存布局。

实测：

```c
typedef struct { int x; } anon_a_t;
typedef struct { int x; } anon_b_t;
void take_a(anon_a_t *p);
anon_b_t b; take_a(&b);
```

```
tag.c:7:12: error: incompatible pointer types passing 'anon_b_t *'
                   to parameter of type 'anon_a_t *'
```

两个结构体都是 `{ int x; }`，大小 4、偏移 0，字节层面无法区分——
**但编译器照样报错**。

这是**特性不是 bug**：

- 如果按布局兼容，那么"UART 配置"和"SPI 配置"只要字段碰巧一样就能互相传，
  这种错误在裸机上会表现为"波特率被写到了时钟分频寄存器里"；
- C 用"同一个声明才兼容"这个规则，把这类误用变成了**编译错误**。

想让两个地方共用同一个类型？**声明一次，放进公共头文件**：

```c
/* cfg.h —— 唯一声明点 */
typedef struct { uint32_t baud; uint8_t parity; } serial_cfg_t;
```

而不是各写一份"看起来一样"的。

**唯一的例外**：如果真的需要按内存布局解释一段字节（比如协议解析），
那就别用类型系统，用显式的字节读写函数（[8.5](8.5-访问未对齐数据.md)）——
那是另一条路，不是靠强制转换结构体指针。
</details>

<details>
<summary>Q3：`-Wpadded` 该不该常开？对寄存器结构体有什么用？</summary>

**该开，尤其在写寄存器结构体时。**

实测输出：

```
$ clang -Wpadded -c pad.c -o /dev/null
pad.c:2:25: warning: padding struct 'struct S1' with 3 bytes to align 'b' [-Wpadded]
pad.c:2:8:  warning: padding size of 'struct S1' with 3 bytes to alignment boundary [-Wpadded]
```

它把 [8.4](8.4-内存中的结构体.md) 手工画出来的两处填充**自动报了出来**。

对寄存器结构体的价值：

```c
typedef struct {
    volatile uint32_t CRL, CRH, IDR, ODR, BSRR, BRR, LCKR;
} GPIO_TypeDef;
```

现在全是 `uint32_t`，自然对齐，`-Wpadded` 一声不响（实测 GPIO 结构体编译无警告）。
**但哪天有人往中间插了个 `uint8_t flags;`**，布局立刻错位，
`-Wpadded` 会当场报警——而不是等你去查"为什么灯不亮"。

配套的第二个保险是 `_Static_assert`（[8.12](8.12-结构体与嵌入式编程.md) 实测）：

```c
_Static_assert(offsetof(GPIO_TypeDef, BSRR) == 0x10, "与 RM0008 不符");
_Static_assert(sizeof(GPIO_TypeDef) == 0x1C, "");
```

两者的分工：

| 手段 | 抓什么 | 什么时候 |
|---|---|---|
| `-Wpadded` | "有填充"这件事本身 | 每次编译，改动立刻可见 |
| `_Static_assert(offsetof)` | 偏移**具体等于几** | 编译期，错了直接 error |

**建议：写寄存器映射时两个都开。** `-Wpadded` 抓"意外"，
`_Static_assert` 抓"和手册不符"——后者是最后一关，硬性的。
</details>
