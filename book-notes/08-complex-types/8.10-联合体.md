# 8.10 联合体

> 书：第 8 章 复杂数据类型 · 8.10 联合体（原书 p98–118 区间内）
> 上一篇：[8.9 结构命名](8.9-结构命名.md) ｜ 下一篇：[8.11 创建自定义类型](8.11-创建自定义类型.md)
> 对应实验：主机侧 clang 23.1.0（小端字节序实测）+ Cortex-M 交叉（`_Static_assert(sizeof)==4`）

## 书这一节讲什么

一句话：**联合体的所有成员共用同一块内存**，大小等于最大成员的大小。

书把它当"省内存的技巧"讲。在裸机上它真正的用处是另一件事：
**同一个 32 位寄存器，用三种看法去读它**——整字、位域、字节数组。

## 一、实测：小端序下的字节排布

```c
typedef union { uint32_t i; uint8_t b[4]; } U;
U u; u.i = 0x12345678;
printf("%02x %02x %02x %02x", u.b[0], u.b[1], u.b[2], u.b[3]);
```

```
$ clang -O2 -o u u.c && ./u
union U: size=4
u.i=0x12345678 -> b[0]=0x78 b[1]=0x56 b[2]=0x34 b[3]=0x12
```

`0x12345678` 的**最低字节 `0x78` 落在最低地址**——这就是**小端（little-endian）**。
Cortex-M 全系小端（且不可配置），Mac/arm64 也是小端，所以主机上跑出来的字节序
和真机一致——**这是我敢在主机上测这条的唯一原因**。

如果协议规定大端（网络字节序、Modbus），这个联合体读出来就**全是反的**。
所以：**联合体看的是"内存里怎么放"，不是"协议里怎么定义"。**

## 二、裸机的主力用法：三种看法看同一个寄存器

```c
typedef union {
    uint32_t w;                       /* 看法①：整字，一次读/写 32 位（高效、对齐、原子） */
    struct {
        uint32_t en   : 1;
        uint32_t mode : 2;
        uint32_t rsv  : 29;
    } bits;                           /* 看法②：位域，按名字访问 */
    uint8_t b[4];                     /* 看法③：按字节，调试打印 / 逐字节发送 */
} ctrl_reg_t;

_Static_assert(sizeof(ctrl_reg_t) == 4, "");      /* Cortex-M 实测通过 */
```

实测位域赋值的结果：

```c
ctrl_t c = { .w = 0 };
c.bits.en   = 1;      /* bit0 */
c.bits.mode = 3;      /* bit1..2 */
```

```
$ clang -O2 -o pr pr.c && ./pr
ctrl bits: w=0x00000007 b0=07 b1=00
```

`1 | (3 << 1) = 7 = 0x07`——**位域在这个编译器上是从最低位往上排的**。

⚠ 但这一条**不是标准保证的**：位域的排列顺序（从低到高还是从高到低）、
是否跨存储单元、能否跨越边界，**全部是 implementation-defined**。
换编译器、换 ABI，位序就可能变。

**所以规则**：
- 位域适合**描述**和**读取**同一块内存（尤其是芯片自己定义的寄存器位）；
- **不要用位域定义跨平台的数据格式**（协议、文件格式、Flash 里持久化的结构）；
- **不要用位域做原子修改**（见下）。

## 三、⚠ 对 volatile 寄存器用位域赋值 = 读-改-写

```c
#define CTRL (*(volatile ctrl_reg_t *)0x40001000u)
CTRL.bits.en = 1;      /* 编译器会生成：读整个 w → 改 1 位 → 写回整个 w */
```

这和 [ch04 4.12](../04-numbers-and-bitops/4.12-用位操作控制内存映射IO寄存器.md) 讲的是**同一个问题**：
在中断/并发下不是原子的，可能丢掉别的位。

正确做法：

| 想做什么 | 用哪个看法 |
|---|---|
| 整体读/写、清零 | `w`（一次 32 位访问） |
| **原子地**改某几位 | 芯片提供的专用寄存器（如 `BSRR`），不是位域 |
| 调试打印、按字节发送 | `b[4]` |
| 只是**读**某几位 | `bits` 可以 |

一句话：**整字用 `w`，原子改用硬件机制，位域只用于读和描述。**

## 四、其他两个用途

**① 拆浮点（调试 / 协议传输）**

```c
union { float f; uint32_t u; } v = { .f = 0.1f };
send_u32(v.u);            /* ch16 实测 0.1f 的位模式是 0x3dcccccd */
```

⚠ 严格说这是 **implementation-defined**（写一个成员、读另一个成员，即 type punning）。
浮点↔整数的最稳写法还是 `memcpy`：

```c
float f = 0.1f; uint32_t u;
memcpy(&u, &f, sizeof u);     /* 语义明确，且编译器会优化成一条寄存器搬移 */
```

**② 互斥缓冲共用 RAM**

```c
static union {
    uint8_t  cmd[256];      /* 收命令时用 */
    uint8_t  resp[256];     /* 发响应时用 */
} buf;                      /* 256 字节，不是 512 */
```

在 8 KB RAM 的 M0 上这是刚需。**但代价是"用错了不报错"**——
你必须自己保证两者不会同时有效，编译器完全不管。

## 五、联合体的大小与对齐

```c
typedef union { uint32_t w; uint8_t b[4]; } U;         /* size = 4 */
```

规则：大小 = **最大成员**的大小（向上补齐到最大成员的对齐值）。
实测 `sizeof(U) == 4`，Cortex-M 上 `_Static_assert(sizeof(ctrl_t)==4)` 通过。

对照一下 packed 结构体（[8.4](8.4-内存中的结构体.md) 实测）：

```
pkt_t  size=7 off(w)=3        /* struct { uint8_t hdr[3]; uint32_t w; } packed */
```

`off(w)=3` 是**奇数**——这正是 [8.5](8.5-访问未对齐数据.md) 里 M0 会 HardFault 的那类地址。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "union 用来省内存" | 裸机主力用途是**同一个寄存器的三种看法**（整字/位域/字节） |
| "union 做类型转换很方便" | 是 **implementation-defined**。浮点↔整数用 `memcpy` 更稳 |
| "位域的位序是标准的" | **不是**。实测 clang 从最低位往上排（en=1,mode=3 → 0x07），但标准不保证 |
| "位域赋值很高效" | 对 volatile 寄存器会生成**读-改-写**，非原子（同 ch04 4.12） |
| "union 大小 = 最大成员" | 对，但还要向上补齐到最大成员的对齐值。实测 `sizeof(U)==4` |
| "小端大端无所谓" | 实测 `0x12345678` → `b[0]=0x78`。协议若是大端，联合体读出来**全反** |

## 代码自测

<details>
<summary>Q1：联合体在裸机上除了省内存，还有什么不可替代的用途？</summary>

最主要的是**同一个 32 位寄存器的三种看法**：

```c
typedef union {
    uint32_t w;                       /* 整字：一次 32 位读/写（对齐、高效） */
    struct { uint32_t en:1; uint32_t mode:2; uint32_t rsv:29; } bits;  /* 位域：按名字 */
    uint8_t b[4];                     /* 字节：调试打印、逐字节发送 */
} ctrl_reg_t;
_Static_assert(sizeof(ctrl_reg_t) == 4, "");      /* 实测通过 */
```

三种看法各自解决一类问题：

| 看法 | 解决什么 | 什么时候用 |
|---|---|---|
| `w` | 一次访问整个寄存器 | 初始化、整体清零、快照/恢复 |
| `bits` | 代码可读性（`c.bits.en` 比 `c.w & 0x1` 强） | **读**、描述 |
| `b[4]` | 按字节看/发送 | 调试打印、通过 8 位总线发送 |

实测位域赋值：

```
c.bits.en = 1; c.bits.mode = 3;   →   w=0x00000007  b[0]=0x07
```

另外两个用途：

1. **拆浮点做调试/协议**（ch16 实测 `0.1f` = `0x3dcccccd`）——
   不过严格写法是 `memcpy(&u, &f, 4)`，不是联合体；
2. **互斥缓冲共用 RAM**——命令缓冲和响应缓冲永不同时有效，
   共用 256 字节而不是各占 256。在 8 KB RAM 的 M0 上是刚需。
</details>

<details>
<summary>Q2：为什么位域不能用来"原子地"改寄存器的某一位？</summary>

因为**位域赋值编译出来是读-改-写**。

```c
CTRL.bits.en = 1;
```

编译器必须：读整个 `w`（32 位）→ 把 bit0 改成 1 → 把整个 `w` 写回去。
中间这两步之间如果来了中断，而中断里改了 `mode`，
那么中断返回后主程序写回的是**旧的 `mode`**——改动被静默覆盖。

这和 [ch04 4.12](../04-numbers-and-bitops/4.12-用位操作控制内存映射IO寄存器.md) 实测的
`GPIOA->ODR |= (1<<5)` 是**同一个问题**，只是换了个写法没换本质。

正确的分工：

| 需求 | 做法 |
|---|---|
| 原子地**置位/清位** | 用芯片提供的硬件机制：`BSRR`（写 1 生效，低 16 置位/高 16 清零） |
| 整体读写 / 清零 | `w`（一次 32 位访问，本身就是单条 `str`） |
| 只是**读**某几位 | `bits` 完全没问题 |
| 关中断下的读-改-写 | 可以，但要显式 `__disable_irq()` / 临界区 |

再加一条**位域自身的坑**：位序是 implementation-defined。
实测 clang 把 `en:1` 放在 bit0、`mode:2` 放在 bit1–2（结果 `0x07`），
但标准没规定，换编译器可能反过来。

**结论**：
- 位域用于**描述和读取**芯片自己定义的寄存器布局，非常好用；
- **不要**用它做原子修改；
- **不要**用它定义跨平台/跨编译器的数据格式（协议、Flash 持久化结构）。
</details>

<details>
<summary>Q3：`union { float f; uint32_t u; }` 做类型双关到底行不行？</summary>

**能跑，但语义上不推荐——用 `memcpy`。**

三档结论：

**① 标准怎么说**
写一个成员、读另一个成员（type punning）在 C 里是
**implementation-defined**（C99 之后有个脚注明确允许"读另一个成员的相应字节"，
但浮点↔整数的解释语义并没有被完整定义）。
在 GCC / clang 上它稳定工作，是广泛依赖的事实标准。

**② 更稳的写法**

```c
float f = 0.1f;
uint32_t u;
memcpy(&u, &f, sizeof u);        /* 语义 100% 明确 */
```

**③ 代价？几乎没有**

实测：开优化后 `memcpy` 4 字节会被编译器完全消除，
生成的是一条寄存器搬移（和联合体写法一模一样的代码）。
所以"为了性能用联合体"这个理由是**不成立**的。

什么时候联合体可以接受？

- 调试代码（打印浮点位模式）——随便用，不会被移植；
- 同一个芯片、同一个编译器下的寄存器描述——本来就是实现相关的；
- 已经写进项目且跑得很好的老代码——**别为了改而改**。

什么时候必须用 `memcpy`：

- 协议 / 文件格式 / 跨编译器的数据交换；
- 浮点↔整数的转换（ch16 会用到 `0.1f` = `0x3dcccccd`）。

**一句话：联合体适合"看同一块内存"，`memcpy` 适合"转换类型"。目的不同，别混用。**
</details>
