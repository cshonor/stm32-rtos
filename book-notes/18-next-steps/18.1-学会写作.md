## 书这一节讲什么

一句话：**写作不是"记录你学过的东西"，而是"检验你到底懂没懂"。**

书的最后一章没有技术内容，是"元建议"。
但 18.1 这条落到本仓库就是一条硬纪律：

> **只记"我理解的 + 我实测的"，不抄书。**

## 一、本仓库的三条写作纪律

1. **每篇都有"原书怎么说 / 实际是什么"对照表**——
   这个表逼着你去验证，而不是复述。**写不出来说明没懂**；
2. **每个数字都要有出处**（实测命令 + 输出）——
   不许出现"大约几十个周期"这种话；
3. **没测过的一律标注"未实测"**——
   见 [13.3 Valgrind](../13-dynamic-memory/13.3-Valgrind.md)（整篇标未实测）、
   [16.6 次正规数](../16-floating-point/16.6-次正规数.md)（FPU 陷阱那段标未实测）。

而精确的陈述会自动暴露错误。**

## 四、怎么把这条纪律落到代码上

| 场景 | 做法 |
|---|---|
| 笔记 | "原书怎么说 / 实际是什么" 表 + 实测命令 |
| 代码注释 | **注释写"为什么"，不写"做了什么"**（代码已经说了做了什么） |
| 提交信息 | 写清"改了什么 + 实测数据 + 下一批做什么" |
| 踩坑 | ⚠ 标出来，别默默修掉——坑比结论更有价值 |

```c
/* ❌ 复述代码 */
i++;                    /* i 加 1 */

/* ✅ 写"为什么" */
i &= (RING_SIZE - 1);   /* RING_SIZE 是 2 的幂，用掩码代替取模（M0 上没有硬件除法） */
```

## 坑点

| 坑 | 原书怎么说 | 实际是什么（实测） |
|---|---|---|
| "笔记是给自己看的，随便写" | —— | ⚠ 本次拆分实测：**凭印象填的 7 处数字里错了 6 处** |
| "抄一遍书就是笔记" | 强调写作价值 | ❌ 复述不产生检验；**"原书 vs 实际"表才产生检验** |
| "没测过的可以不写" | —— | ⚠ 更好的是**写出来并标注"未实测"**——提醒未来的自己 |
| "写文档是收尾工作" | —— | ⚠ 裸机上"补文档"几乎不会发生；**注释和笔记要跟着代码一起写** |

<details>
<summary>Q1：写笔记到底有什么用？直接读不就行了？</summary>

**读是输入，写是检验。** 本次拆分的实测数据就是证据：

顶层索引里 7 章的小节范围，**6 章是错的**：

| 章 | 原来写的 | 实际 |
|---|---|---|
| 11 | 11.1–11.9 | **11.1–11.6** |
| 12 | 12.1–12.8 | **12.1–12.6** |
| 13 | 13.1–13.6 | **13.1–13.4** |
| 14 | 14.1–14.8 | **14.1–14.6** |
| 15 | 15.1–15.5 | **15.1–15.4** |
| 17 | 17.1–17.7 | **17.1–17.6** |
| 16 | 16.1–16.7 | ✅ 正确 |

这些数字**读的时候没人会去核对**——它们看起来很合理。
只有当你必须"逐条列出来、写成表格"时，才会去翻原文，才发现对不上。

**这就是写作的检验作用：把"我觉得对"变成"我核对过"。**
</details>

<details>
<summary>Q2：没实测过的内容该怎么处理？不写吗？</summary>

**写，但明确标注"未实测"。**

⚠ 不写的问题：你会以为自己知道，实际上只是"听说过"。

本仓库的三处实例：

| 位置 | 处理 |
|---|---|
| [13.3 Valgrind](../13-dynamic-memory/13.3-Valgrind.md) | **整篇**标注未实测（本机 `valgrind` 未安装），内容降级为"机制说明 + 命令参考" |
| [16.6 次正规数](../16-floating-point/16.6-次正规数.md) | "FPU 走陷阱"那段标注**机制说明，本机未实测** |
| [17.5](../17-modular-programming/17.5-确定性与不确定性库.md) | "GNU ld 报 undefined reference"标注**本机无 GNU ld，未实测** |

⚠ 而且标注之后往往会发现**实测结果和课本不一样**——
比如 17.5 实测发现 ld.lld 库放前面**能过且静默**，
和教科书的"undefined reference"完全不同。

**"我没测过"这句话本身就是有价值的信息。**
</details>

<details>
<summary>Q3：代码注释应该写什么？</summary>

**写"为什么"，不写"做了什么"。**

```c
/* ❌ 复述代码——代码自己已经说了 */
i++;                    /* i 加 1 */
len = strlen(s);        /* 取字符串长度 */

/* ✅ 写"为什么"——代码里看不出来的部分 */
i &= (RING_SIZE - 1);   /* RING_SIZE 是 2 的幂，用掩码代替取模（M0 无硬件除法） */

volatile uint32_t *sr;  /* 必须 volatile：不优化掉重复读（ch01 实测过） */

if (c == '\n') uart_putc('\r');   /* 手动补 CR：裸机没有"文本模式"（16.3 实测） */

uint32_t used;          /* ⚠ 用 uint32 而不是 uint8：offsetof 从 1 变 4，
                           否则 M0 上未对齐访问 HardFault（13.1 实测，代价 48 B） */
```

**判据**：如果删掉注释后，读者能从代码本身看出来——那这条注释就是废话。
值得写的是**约束、取舍、踩过的坑、为什么不用另一种写法**。

裸机上尤其重要：**约束（Flash/RAM/时序）代码里看不出来**，
不写下来三个月后你自己也不知道当初为什么这么写。
</details>
