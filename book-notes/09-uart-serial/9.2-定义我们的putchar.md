# 9.2 定义我们的 putchar

> 书：第 9 章 STM 上的串口输出 · 9.2 定义我们的 putchar（原书 p119–134 区间内）
> 上一篇：[9.1 一次写一个字符的字符串](9.1-一次写一个字符的字符串.md) ｜ 下一篇：[9.3 串行输出](9.3-串行输出.md)
> 对应实验：`--target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding`（`-O0` / `-Os` / `-O2` 三档反汇编）

## 书这一节讲什么

一句话：**自己写一个 `putchar()`**——名字可以和标准的 `putchar` 一样，
因为裸机上标准库那一个根本不存在。

书把它叫 "our putchar"。这一节的关键是：
**`putchar` 不是一个函数，而是一个"契约"**——
"给我一个字节，我保证把它送出去"。后面所有东西（`puts`、`printf`、日志）
都建立在这个契约上。

## 一、契约：三条必须满足

```c
int uart_putc(int c){                  /* 签名故意和 putchar 一致 */
    while ((USART1_SR & TXE) == 0u) { }   /* ① 等到能发 */
    USART1_DR = (uint32_t)(uint8_t)c;     /* ② 写一个字节 */
    return c;                             /* ③ 成功返回该字符（失败返回 EOF） */
}
```

| 契约项 | 为什么 |
|---|---|
| 参数/返回是 `int` 不是 `char` | 为了能返回 `EOF`(-1)，`char` 装不下（[ch06](../06-arrays-pointers-strings/6.5-字符和字符串.md) 讲过 `getchar` 返回 int 的同一个理由） |
| 阻塞到发完 | 调用方不需要关心时序；代价是 CPU 空转 |
| 返回原字符 | 与标准 `putchar` 一致，将来换实现不用改调用方 |

⚠ `(uint8_t)c` 这个转换**不能省**：

```c
USART1_DR = (uint32_t)c;      /* c = 0xFFFFFF80（比如打印 latin-1 字符）→ 写了 32 位 */
USART1_DR = (uint32_t)(uint8_t)c;   /* ✅ 只取低 8 位 */
```

`USART1_DR` 虽然是个 32 位寄存器地址，但**只有低 8/9 位有效**——
写进去的高位会被忽略（F1 上是忽略，别的芯片不一定）。显式截断最安全。

## 二、实测：三档优化下的 `uart1_putc`

```c
#define USART1_SR (*(volatile uint32_t *)0x40013800u)
#define USART1_DR (*(volatile uint32_t *)0x40013804u)
#define TXE (1u << 7)
void uart1_putc(char c){ while ((USART1_SR & TXE) == 0u){} USART1_DR = (uint32_t)c; }
```

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding -Os -c uart.c
00000000 <uart1_putc>:                    ← 6 条指令，0 字节栈
       0: f643 0100  movw r1, #0x3800     ; 地址低半
       4: f2c4 0101  movt r1, #0x4001     ; 地址高半 → r1 = 0x40013800
       8: 680a       ldr  r2, [r1]        ; 读 SR
       a: 0612       lsls r2, r2, #0x18   ; bit7 → 符号位
       c: d5fc       bpl  0x8             ; 为 0 则回读
       e: 6048       str  r0, [r1, #0x4]  ; 写 DR（偏移寻址，不再算地址）
      10: 4770       bx   lr
```

三个值得记住的细节：

1. **`movw` + `movt` 装常量地址**——ARM 没法一条指令装 32 位立即数，
   所以要两条。这就是"寄存器地址 = 编译期常量"的代价（每条用到 USART 的函数都有）。
2. **`lsls` + `bpl` 代替 `ands` + `cmp` + `beq`**——
   编译器把 bit7 顶到符号位，用"正数则跳"判断，省一条指令。
3. **`str r0, [r1, #0x4]`**——`DR` 在 `SR + 4`，编译器直接用偏移寻址，
   不再重新装一次 `0x40013804`。

`-O0` 下是同一个循环，但多了把 `c` 存栈 (`strb.w r0, [sp, #0x3]`)、
栈用量 **4 字节**；`-O2` 下循环被展开成 3 次读（跳过了部分分支开销）。

## 三、TXE 还是 TC？这是个真问题

`USART_SR` 里有两个"发完了"的标志，容易混：

| 位 | 名字 | 含义 | 用途 |
|---|---|---|---|
| bit 7 | **TXE** | **发送数据寄存器空**（可以写下一个字节） | 流式发送用这个 |
| bit 6 | **TC** | **发送完成**（移位寄存器也空了，最后一个字节已经上线路） | 关串口/改波特率/进低功耗前用这个 |

```c
/* 流式发送：等 TXE 就够 */
while ((USART1_SR & TXE) == 0u){} USART1_DR = c;

/* 关 UART / 改 BRR / 进 STOP 之前：必须等 TC */
while ((USART1_SR & TC) == 0u){}
USART1_CR1 &= ~(1u << 13);          /* 才能安全关掉 UE */
```

⚠ 常见 bug：**只等 TXE 就关串口**。TXE=1 只说明 DR 空了，
最后一个字节还在移位寄存器里往外发——此时关掉 UE，
**最后一个字节发不出去**（表现为"日志最后几个字符丢失"）。

还有一个细节：**TC 需要先读 SR 再写 DR 才会被清零**（RM0008 的硬件行为），
所以"等 TC"之前如果刚写过 DR，标志是自动清的；
但如果没写过，TC 可能一开始就是 1，循环直接跳过。

## 四、`putchar` 的三种实现路线

| 路线 | 怎么做 | 代价 | 适用 |
|---|---|---|---|
| **UART 轮询**（本章） | 等 TXE 写 DR | 阻塞 CPU | **生产/量产唯一可选**，也是调试主力 |
| **ITM / SWO** | 写 `ITM_STIM0`（`0xE0000000`） | 需 SWO 引脚 + 调试器 | 调试期，不占 UART，M3/M4+ 支持 |
| **semihosting** | `bkpt 0xAB` 让调试器接管 | **极慢**（每次几 ms），且断开调试器就崩 | 只在早期 bring-up 用过一次 |

本仓库主线是 **UART 轮询**，理由：

1. 量产可用（不依赖调试器）；
2. 速度够（115200 下日志完全够用）；
3. **在 HardFault handler 里也能用**——不依赖中断控制器（中断版则依赖）。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "`putchar` 就是写一个字节" | 它是一条**契约**：阻塞到发出、返回原字符。签名用 `int` 是为了能返回 `EOF` |
| "`DR` 是 32 位寄存器，写 32 位没问题" | 只有低 8/9 位有效。要显式 `(uint8_t)c` 截断 |
| "等 TXE 就够了" | 流式发送够；**关串口/改波特率前必须等 TC**，否则最后一个字节丢失 |
| "TXE 和 TC 差不多" | TXE = DR 空（可写下一个）；TC = 移位寄存器也空（真发完了） |
| "自己写的 putchar 和标准的一样" | 签名可以一致，但**没有缓冲、没有 errno、没有线程安全**。裸机上这三样都得自己补 |

## 代码自测

<details>
<summary>Q1：为什么标准 `putchar` 返回 `int` 而不是 `char`？</summary>

为了能返回 **`EOF`（-1）**。

```c
int putchar(int c);      /* 成功返回 c，失败返回 EOF */
```

`char` 类型装不下 `-1` 和"值为 0xFF 的字符"这两种情况——
如果返回 `char`，`0xFF` 会被解释成 `-1`（在 `char` 有符号的平台上），
调用方分不清"成功输出了 0xFF"和"失败了"。

C 标准的做法是：**用 `int` 传递字符，字符值放在低 8 位（0..255），
`-1` 保留给 EOF**。所以：

```c
int c = uart_getc();          /* 假设有接收 */
if (c == EOF) { /* 失败 */ }
else { char ch = (char)c; }   /* 真正用的时候再转成 char */
```

这和 [ch06 6.5](../06-arrays-pointers-strings/6.5-字符和字符串.md) 讲的
`getchar()` 返回 `int` 是**同一个理由**。

裸机上我们自己写的版本：

```c
int uart_putc(int c){
    while ((USART1_SR & TXE) == 0u){}
    USART1_DR = (uint32_t)(uint8_t)c;
    return c;             /* 永远成功 —— 因为轮询版没有失败路径 */
}
```

⚠ 注意 "永远成功" 这个事实：**轮询版没有超时，也就没有失败**。
如果 TXE 因为硬件故障永远不为 1，它会**永久卡死**而不是返回错误。
这是裸机 I/O 的一个普遍特征：**要么成功，要么卡住**。

想要"能失败"，就要加超时（[ch05 5.14 反模式](../05-control-flow-button/5.14-反模式.md) 讲过裸机等待必须带超时）：

```c
int uart_putc_timeout(int c, uint32_t budget){
    while (((USART1_SR & TXE) == 0u) && budget--) {}
    if (budget == 0) return EOF;                  /* 超时：返回错误而不是卡死 */
    USART1_DR = (uint32_t)(uint8_t)c;
    return c;
}
```
</details>

<details>
<summary>Q2：`USART1_DR = (uint32_t)c;` 少了 `(uint8_t)` 转换会怎样？</summary>

看情况——**在 STM32F1 上大概率"没事"，但这个"没事"不能依赖**。

```c
USART1_DR = (uint32_t)c;            /* ⚠ c 可能是 0xFFFFFF80 */
USART1_DR = (uint32_t)(uint8_t)c;   /* ✅ 一定是 0x00000080 */
```

`USART1_DR` 的地址是 32 位的，但**数据寄存器只有低 8 位（或 9 位，取决于 M 位）有效**。
写进去的高 24 位在 F1 上会被硬件忽略。

那什么时候会出问题？

**① 打印非 ASCII 字节**

```c
uart_putc(0x80);        /* 如果 char 有符号，0x80 是 -128 → (uint32_t)(-128) = 0xFFFFFF80 */
```

在 **char 有符号**的平台（arm-none-eabi 默认 `char` 是 **unsigned**，
但 clang 在 x86/Linux 上是 **signed**——这就是可移植性问题）。

**② 配合 9 位数据位 / 奇偶校验**

`DR` 的 bit8 在某些配置下有意义，写进去的垃圾位可能触发意外行为。

**③ 别的芯片**

不是所有 UART 都"忽略高位"。有些芯片的 DR 写入会触发 FIFO 推送、
或把写入宽度当成数据宽度。依赖"硬件会忽略"是可移植性风险。

**④ 调试时看不到真实值**

用调试器看 `USART1_DR` 时看到 `0xFFFFFF80`，你会怀疑自己写错了——
实际上只是没截断。

**规则**：跨宽度写入寄存器时，**显式截断到目标宽度**。

```c
USART1_DR = (uint32_t)(uint8_t)c;    /* 意图明确 */
```

这不是多余的转换——它把"我要低 8 位"这个意图**写进了代码**，
同时消除了 `char` 有符号性带来的平台差异。
</details>

<details>
<summary>Q3：TXE 和 TC 到底什么时候用哪个？</summary>

一张表解决：

| 位 | 名字 | 含义 | 什么时候用 |
|---|---|---|---|
| bit 7 | **TXE** (Transmit data register Empty) | DR 空了，**可以写下一个字节** | 流式发送每一个字节 |
| bit 6 | **TC** (Transmission Complete) | 移位寄存器也空了，**最后一个字节已经发上线路** | 关 UART / 改 BRR / 进低功耗 |

```c
/* 流式发送：等 TXE */
void uart_putc(char c){
    while ((USART1_SR & TXE) == 0u){}
    USART1_DR = (uint32_t)(uint8_t)c;
}

/* 收尾：等 TC */
void uart_flush(void){
    while ((USART1_SR & TC) == 0u){}      /* 等最后一个字节真的出去 */
}

void uart_deinit(void){
    uart_flush();
    USART1_CR1 &= ~(1u << 13);            /* 现在才能安全关 UE */
}
```

**只等 TXE 就关串口的经典 bug**：

```
uart_puts("boot ok\n");       /* 最后一个 '\n' 写进 DR，TXE 立刻变 1（DR 空了） */
USART1_CR1 &= ~(1u<<13);      /* 关 UE —— 但 '\n' 还在移位寄存器里！ */
/* 结果：主机收到 "boot ok"，最后的 '\n' 丢了 */
```

表现为"日志最后几个字符总是丢失"——因为断电/复位/关串口总是发生在最后。

⚠ 一个额外坑：**TC 的清零需要"先读 SR 再写 DR"**。
如果从没写过 DR，TC 可能复位后就是 1，`uart_flush()` 会直接返回
（这是正确行为——确实没有待发数据）。

**记忆口诀**：
- **TXE = "可以再给我一个字节"** → 发送循环用；
- **TC = "我彻底干完了"** → 收尾/关停用。
</details>
