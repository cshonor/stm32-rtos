# 9.1 一次写一个字符的字符串

> 书：第 9 章 STM 上的串口输出 · 9.1 一次写一个字符的字符串（原书 p119–134 区间内）
> 下一篇：[9.2 定义我们的 putchar](9.2-定义我们的putchar.md)
> 对应实验：主机侧实测（`write(2)` 逐字符开销）+ Cortex-M 交叉（`volatile` 与非 `volatile` 反汇编对照）

## 书这一节讲什么

一句话：**字符串输出 = 循环里一个字符一个字符地写**，到 `'\0'` 停。

书在这里讲的是最朴素的模型。这一节真正的价值是**把"一个字符"的代价量化**——
因为后面整个 `printf` 体系都建立在这个原子操作上。

## 一、最朴素的写法

```c
void uart_puts(const char *s){
    while (*s) uart_putc(*s++);      /* 到 '\0' 停 */
}
```

三个必须想清楚的点：

1. **`*s` 是 `char`，不是"字符串"**——UART 是字节设备，它只认识字节；
2. **`'\0'` 不会被发出去**——它是 C 的约定，不是串口的约定。
   对端（比如 Python 脚本）收到的是一串没有终止符的字节；
3. **`s` 是 `const char *`**——这段数据通常在 Flash（`.rodata`），不是 RAM。

## 二、实测：一次 `write()` 系统调用要 0.93 µs

在 PC 上"写一个字符"是一次系统调用。实测它的**固定开销**：

```c
for (int i = 0; i < N; i++) write(fd, &buf[i], 1);    /* 逐字符 */
```

```
$ clang -O2 -o wr2 wr2.c && ./wr2        # Mac/arm64，200 × 200000 次取平均
逐字符：200×200000 次 write = 37.2807 s → 0.932 us/次
```

**一次 `write(2)` ≈ 0.93 µs**（4000 万次平均）。

⚠ 这里要诚实：我又测了"一次写 200 KB"，结果接近 0——因为目标是 `/dev/null`，
内核直接丢弃，测不出吞吐。**所以这个数字只代表"每次系统调用的固定开销"**，
不代表真实串口吞吐。但它足够说明一件事：

| 平台 | 写一个字符的成本 |
|---|---|
| Mac/Linux（经 libc → `write(2)` → 内核 tty 驱动） | **0.93 µs**（实测，纯系统调用开销） |
| 裸机（写 `USART1_DR`） | 一条 `str`，约 **0.05 µs** @ 72 MHz（几条指令） |

**裸机上"写一个字符"比 PC 上便宜一个数量级**——但裸机上你**没有**内核帮你缓冲、重传、流控。

## 三、实测：等 TXE 的循环，`volatile` 差一个就死

这是本章最重要的实测。同一段代码，只有 `volatile` 不同：

```c
#define USART1_SR      (*(volatile uint32_t *)0x40013800u)   /* ✅ */
#define USART1_SR_BAD  (*(uint32_t *)0x40013800u)            /* ❌ */
#define TXE (1u << 7)

void uart1_putc    (char c){ while ((USART1_SR     & TXE) == 0u){} USART1_DR = c; }
void uart1_putc_bad(char c){ while ((USART1_SR_BAD & TXE) == 0u){} USART1_DR = c; }
```

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding -Os -c uart.c
$ llvm-objdump -d uart_Os.o

00000000 <uart1_putc>:              ← volatile 版：真循环
       0: f643 0100  movw r1, #0x3800
       4: f2c4 0101  movt r1, #0x4001
       8: 680a       ldr  r2, [r1]        ← 32 位读，在循环体内
       a: 0612       lsls r2, r2, #0x18   ← bit7 顶到符号位
       c: d5fc       bpl  0x8             ← 还是 0？回去再读
       e: 6048       str  r0, [r1, #0x4]  ← 写 DR（SR + 4）
      10: 4770       bx   lr

00000012 <uart1_putc_bad>:          ← 非 volatile 版：只读一次
      12: f643 0100  movw r1, #0x3800
      16: f2c4 0101  movt r1, #0x4001
      1a: 780a       ldrb r2, [r1]        ← ⚠ 变成 8 位读！还只读一次
      1c: 0612       lsls r2, r2, #0x18
      1e: bf44       itt  mi
      20: 6048       strmi r0, [r1, #0x4]
      22: 4770       bxmi lr
      24: e7fe       b    0x24            ← 不满足？跳到自己，永久死循环
```

**两个关键发现（比"循环被删掉"更值得记住）：**

1. **`ldr` 变成了 `ldrb`**：编译器推理"你只关心 bit7，那在低字节里"，
   于是把 32 位读**窄化成 8 位读**。这在真实硬件上未必错，但已经说明
   编译器的推理**基于它自己的模型，不是基于硬件**。
2. **循环变成了"只读一次 + 死循环"**（`b 0x24` 跳自己）。
   不是"跳过等待继续写"，而是**一旦 TXE 为 0 就永远卡死**。

真机上的表现：复位后 TXE=1 → **第一个字符正常发出**；
写 DR 后 TXE 被硬件清零 → **第二个字符时死锁**。
现象是"只发出一个字符就卡住"——极难排查。

> 这条修正了旧笔记里"被优化成 `bx lr`"的说法：实测 `-Os`/`-O2` 下是
> **只读一次 + 无限自跳**，而不是删除循环。`-O0` 下两个版本的循环都还在。

## 四、栈用量实测

```
$ clang ... -O0 -fstack-usage -c uart.c
uart.c:13:uart1_putc      4   static
uart.c:20:uart1_putc_bad  4   static
uart.c:25:uart1_init      8   static

$ clang ... -Os -fstack-usage -c uart.c
（-Os 下 uart1_putc 被内联，.su 里只剩）
mp.c:14:mini_printf  40   static
mp.c:7:put_uint      24   static
```

`uart1_putc` 在 `-O0` 下只用 **4 字节栈**（一个 `char c` 的槽位）。
整个输出路径非常轻——这让"在 HardFault handler 里打日志"成为可行手段。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "字符串就是 `char*`，循环写到 `'\0'`" | 对，但 **`'\0'` 不会被发出去**。对端收到的是无终止符的字节流 |
| "写一个字符很便宜" | 实测 PC 上一次 `write(2)` = **0.93 µs**；裸机写 `USART1_DR` 是一条 `str`。差别在"谁替你缓冲" |
| "等待循环没问题" | ⚠ 实测：非 `volatile` 版本在 `-Os` 下变成 `ldrb` + `b 0x24`（**只读一次 + 死循环**） |
| "`volatile` 只是防止值被缓存" | 实测它决定了**循环结构本身**：volatile 版是 `ldr`+`bpl` 真循环；非 volatile 版被重写成条件执行 + 自跳 |
| "输出函数占栈" | 实测 `uart1_putc` `-O0` 只 4 字节栈 |

## 代码自测

<details>
<summary>Q1：为什么 `'\0'` 不会被发出去？对端怎么知道一串结束了？</summary>

因为 `while (*s)` 在读到 `'\0'` 时**循环就停了**——
`uart_putc` 根本没被调用，那个字节从没进过 `USART1_DR`。

```c
void uart_puts(const char *s){ while (*s) uart_putc(*s++); }
/*                                    ↑ 读到 '\0' 时条件为假，退出 */
```

`'\0'` 是 **C 语言的字符串终止约定**，不是串口协议的一部分。
UART 是字节流设备，它不知道什么是"字符串"。

**对端怎么办？** 三种常见做法：

| 做法 | 例子 | 适用 |
|---|---|---|
| **定长** | "每帧固定 8 字节" | 二进制协议 |
| **分隔符** | 以 `\n` / `\r\n` 结尾（日志最常见） | 文本协议、命令行 |
| **长度前缀** | 先发 1–2 字节长度，再发数据 | 变长二进制帧 |

裸机日志几乎都用 **`\n` 结尾**：

```c
uart_puts("init ok\n");        /* 主机上按行读，天然分帧 */
```

⚠ 反过来要注意：**如果数据里本身可能含 `'\0'`（二进制），就不能用 `uart_puts`**，
必须显式传长度：

```c
void uart_write(const uint8_t *buf, size_t n){ while (n--) uart_putc((char)*buf++); }
```

这也是为什么后面写 `mini_printf` 时，`%s` 分支用 `while (*s)` 是对的（字符串），
而协议发送一定要带长度参数。
</details>

<details>
<summary>Q2：实测里非 volatile 版本为什么变成 `ldrb`？这是 bug 吗？</summary>

`ldrb` 本身不是 bug，但**它是"编译器在替你推理"的证据**。

实测对照：

```
volatile 版： 680a   ldr  r2, [r1]      ← 32 位读
非 volatile： 780a   ldrb r2, [r1]      ← 8 位读
```

编译器的推理链是：

1. 这个地址是普通内存（非 volatile），程序里没人写它 → 它的值不会变；
2. 你只用了 `& 0x80`（bit7）→ bit7 在小端下位于**最低字节**；
3. 那就只需要读那一个字节 → 用 `ldrb`，更省。

**在这个特定芯片上，`ldrb 0x40013800` 恰好能读到 bit7，所以功能上没错。**
但这个"恰好"建立在编译器的假设上：

- 假设"没人写它"——**硬件每时每刻都在改 SR**，这是编译器看不见的；
- 假设"读字节和读字等价"——对某些外设（读一次就清除标志的寄存器）
  读 8 位和读 32 位的**副作用完全不同**。

真正的杀手是后面那一步：既然值不会变，循环就没意义了 →
变成"读一次 + 条件执行 + `b 0x24`（跳自己）"。

```
      1e: bf44   itt  mi
      20: 6048   strmi r0, [r1, #0x4]
      22: 4770   bxmi lr
      24: e7fe   b    0x24        ← 不满足就永远卡在这
```

**真机表现**：复位后 TXE=1，第一个字符正常发出；
写 DR 后硬件清 TXE，第二次调用时读到 0 → **永久死锁**。
现象是"只输出一个字符就卡住"。

`volatile` 的作用不是"告诉编译器值会变"（它看不见硬件），
而是**禁止这一整条推理**：每次都必须真的按你写的方式去读。
</details>

<details>
<summary>Q3：既然裸机写一个字符这么便宜，为什么不能每个字节都 `printf`？</summary>

"便宜"是**单次**的，`printf` 的贵在**别处**。

实测对照：

| 操作 | 成本 |
|---|---|
| 裸机写一次 `USART1_DR` | 一条 `str`，约 0.05 µs @ 72 MHz |
| PC 上一次 `write(2)` | **0.93 µs**（实测 4000 万次平均） |
| 一次 `mini_printf("%d", x)` | 除法循环 + 多次 `uart_putc`，几十 µs |

所以问题不在"写一个字符"，而在：

**① 波特率是硬上限**

115200 bps、8N1（10 bit/字节）→ **每秒最多 11520 字节 ≈ 11.5 KB/s**。
一次 `printf("val=%d\n", x)` 假设输出 10 字节，就吃掉 **0.87 ms**。
在 1 kHz 的控制循环里，打 3 条日志就把 CPU 预算用光了。

**② 轮询发送期间 CPU 在空转**

```c
while ((USART1_SR & TXE) == 0u) { }    /* 等一个字节发完 */
```

115200 下每个字节要等 **86.8 µs**（8.68 µs/bit × 10 bit）。
72000 个时钟周期就这么烧掉了。

**③ 格式化本身不便宜**

`%d` 要做除法——**M3 有 `udiv` 指令**（实测见 [9.5](9.5-串口HelloWorld.md)），
但 `%x`/`%d` 的逐位拆解仍是"除法 + 取模"循环，一个 10 位数字要 10 次；
`%f` 更糟：**M3 没有 FPU**，浮点是软件模拟，一次几百 µs。

**所以规则是**：

| 场景 | 建议 |
|---|---|
| 启动/错误日志 | 随便打（低频，价值高） |
| 主循环里每周期打 | ❌ 别。改成"每 N 个周期打一次"或"变化时打" |
| 高频采样数据 | ❌ 别打文本。用二进制 + DMA，或者只打统计量 |
| HardFault 里 | ✅ 打（轮询版可用，不依赖中断） |

**一个实用技巧**：给日志加"节流"——

```c
static uint32_t last_tick;
if (now - last_tick >= 1000) { last_tick = now; mini_printf("..."); }   /* 每秒最多一次 */
```
</details>
