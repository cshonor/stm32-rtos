# 6.3 数组和指针算术

> 书：第 6 章 数组、指针和字符串 · 6.3 数组和指针算术（原书 p78–88 区间内）
> 上一篇：[6.2 底层细节：指针](6.2-底层细节：指针.md) ｜ 下一篇：[6.4 数组溢出](6.4-数组溢出.md)
> 对应实验：主机侧 clang 23.1.0（`-O0`）+ `--target=armv7m-none-eabi` 交叉

## 书这一节讲什么

一句话：**指针可以加减整数，步长是 `sizeof(指向的类型)` 而不是 1 字节**；
`p[i]` 就是 `*(p + i)`。

书讲的是规则。裸机上这一节的直接用途是：
**寄存器块的遍历、缓冲区搬运、以及"基址 + 偏移"这个贯穿全书的写法。**

## 一、实测：步长与下标

```c
int a[4] = {10,20,30,40};
int *p = a;
printf("a+1 / &a+1 / *(p+2) / p[2] / 2[p]");
```

```
$ clang -O0 -o arr arr.c && ./arr
a+1=0x16f68f5f4  (差 4 字节)      ← 指针算术：一步 = sizeof(int) = 4
&a+1=0x16f68f600 (差 16 字节)     ← &a 是"指向整个数组的指针"，一步 = 16
*(p+2)=30  p[2]=30  2[p]=30       ← 下标 = 指针算术的语法糖
```

三条结论：

1. **`p + 1` 前进 `sizeof(*p)` 字节**，不是 1；
2. **`p[2]` 就是 `*(p + 2)`**——下标运算符只是加法的糖；
3. **`2[p]` 也成立且等于 `p[2]`**（因为 `*(2 + p) == *(p + 2)`）——
   这证明下标真的只是加法。**别在生产代码里这么写。**

## 二、寄存器块能不能用下标访问？能，但极其容易写错

```c
volatile uint32_t *const gpioa = (volatile uint32_t *)0x40010800u;
gpioa[0]   /* 偏移 0x00 = CRL   */
gpioa[1]   /* 偏移 0x04 = CRH   ← 因为步长是 4 字节 */
gpioa[4]   /* 偏移 0x10 = BSRR  */
```

**`gpioa[n]` 里的 n 是"第 n 个 32 位字"，不是"第 n 个寄存器"。**
`BSRR` 在偏移 0x10，对应 `gpioa[4]`——这个 4 只能靠人数出来，维护必错。

两种更稳的写法：

```c
/* A：宏 + 显式字节偏移（本仓库 ch03–ch05 用的） */
#define REG32(base, off) (*(volatile uint32_t *)((base) + (off)))
#define GPIOA_BSRR REG32(0x40010800u, 0x10u)

/* B：结构体映射（CMSIS 风格，ch08 讲） */
typedef struct { volatile uint32_t CRL, CRH, IDR, ODR, BSRR, BRR, LCKR; } GPIO_TypeDef;
#define GPIOA ((GPIO_TypeDef *)0x40010800u)
GPIOA->BSRR = ...;
```

B 更好：偏移由**结构体布局**保证，还能用
`_Static_assert(offsetof(GPIO_TypeDef, BSRR) == 0x10, "")` 在编译期校验
（[4.5](../04-numbers-and-bitops/4.5-整数的大小和表示.md) 讲过这个手段）。

**结论：不要用裸的 `gpioa[n]` 访问寄存器。**

## 三、缓冲区的指针算术（这个用法是对的）

```c
/* 环形缓冲的读写（unsigned 回绕 + 指针算术） */
static uint8_t rb_buf[64];
static volatile uint32_t rb_head, rb_tail;

void rb_put(uint8_t b){
    rb_buf[rb_head & (RB_SIZE - 1)] = b;      /* 用 & 代替取模（SIZE 是 2 的幂） */
    rb_head++;                                 /* 自由回绕（ch04 讲过） */
}
uint8_t rb_get(void){
    uint8_t b = rb_buf[rb_tail & (RB_SIZE - 1)];
    rb_tail++;
    return b;
}
```

指针版（等价，有时更快）：

```c
void rb_put(uint8_t b){
    uint32_t h = rb_head++ & (RB_SIZE - 1);
    *(rb_buf + h) = b;          /* 就是 rb_buf[h] */
}
```

**别写成 `rb_buf + rb_head`**（不取模）——那是越界。

## 四、"基址 + 偏移"：整数加法 vs 指针算术

这是最容易混的地方：

```c
#define GPIOA_BASE 0x40010800u

GPIOA_BASE + 0x10u              /* 整数加法 → 0x40010810（加 16 字节）✅ */
(uint32_t*)GPIOA_BASE + 0x10u   /* 指针算术 → 0x40010840（加 16×4 = 64 字节）❌ */
```

同一句 `+ 0x10`，两种含义差 4 倍。
所以本仓库统一：**base 当整数、off 用字节、最后一次性转换成指针**——
就是 `REG32(base, off)` 宏。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "`p + 1` 前进一个字节" | 前进 `sizeof(*p)` 字节。实测 `a+1` 与 `a` 差 **4**；`&a+1` 差 **16** |
| "`p[i]` 和 `*(p+i)` 是两个东西" | **同一个东西**（实测 `2[p]` 也等于 `p[2]`，证明只是加法） |
| "寄存器块可以用下标遍历" | 能，但 `gpioa[n]` 的 n 是"第 n 个字"，不是"第 n 个寄存器"——极易错 |
| "`base + 0x10` 一定是加 16 字节" | 取决于 base 是整数还是指针。实测两种写法差 4 倍 |
| "指针算术越界会崩" | 裸机上不会（[6.4](6.4-数组溢出.md) 实测） |

## 代码自测

<details>
<summary>Q1：`2[p]` 为什么合法？这说明了什么？</summary>

因为**下标运算符的定义就是加法**，而加法是可交换的。

C 标准定义：`E1[E2]` 等价于 `*((E1) + (E2))`。所以：

```
p[2]  →  *(p + 2)
2[p]  →  *(2 + p)     ← 加法交换律 → *(p + 2) → 同一个东西
```

实测：`*(p+2)=30  p[2]=30  2[p]=30`——三个都等于 30。

这说明 **下标不是"数组的专有操作"，它只是"指针加个偏移再解引用"的简写**。
理解这一点之后，下面这些就都不神秘了：

```c
char *s = "hello";
s[2]        == *(s + 2)   == 'l'
& s[2]      == s + 2
&s[0] + 2   == s + 2
```

反面：**`2[p]` 合法不代表该写**。
它的唯一价值是证明"下标就是加法"，生产代码里写它只会让人停下来想两秒。

裸机上的一个正面用途：理解 `REG32(base, off)` 为什么用整数加法——
因为我们要的是"地址 + 字节偏移"，
而不是"指针 + sizeof(元素)"（后者会把偏移乘 4）。
</details>

<details>
<summary>Q2：`&a + 1` 和 `a + 1` 差了多少？为什么？</summary>

实测（Mac/arm64，`int a[4]`）：

```
a+1  = 0x16f68f5f4   （差 4 字节）
&a+1 = 0x16f68f600   （差 16 字节）
```

因为**两者类型不同，指针算术的步长 = sizeof(指向的类型)**：

| 表达式 | 类型 | 指向的对象大小 | +1 前进 |
|---|---|---|---|
| `a + 1` | `int *`（退化后） | 一个 `int` = 4 | **4** 字节 |
| `&a + 1` | `int (*)[4]` | 整个数组 = 16 | **16** 字节 |

`&a` 是"指向含有 4 个 int 的数组的指针"——听起来很绕，
但它的实际用途是**多维数组和"整块操作"**：

```c
void clear_all(int (*arr)[4]){ /* 收到的是"整个数组"的指针，不是首元素 */ }
```

裸机上的直接后果是地址计算：
**写 `GPIOA_BASE + 1` 时，加的是 1 还是 4，取决于那个 base 的类型。**
所以本仓库的 `REG32(base, off)` 用整数常量（不带指针类型），
保证 `+ off` 一定是"加 off 个字节"。
</details>

<details>
<summary>Q3：遍历缓冲区用下标还是用指针递增？</summary>

在 Cortex-M 现代编译器下**通常没差别**——两者都会生成同样高效的
`ldr rX, [rY], #4`（后自增寻址）之类的指令。

```c
for (size_t i = 0; i < n; i++) sum += buf[i];        /* 下标 */
for (const int *p = buf; p < buf + n; p++) sum += *p; /* 指针 */
```

实测过同类情况（[5.5 for](../05-control-flow-button/5.5-for.md)）：
编译器会把求和循环直接优化成闭式解（`umull`），两者都消失。
所以**这是可读性问题，不是性能问题**。

选择建议：

| 场景 | 用 |
|---|---|
| 需要下标做别的事（存索引、比较位置） | 下标 |
| 只是一次遍历 | 哪个清楚用哪个（多数人更习惯下标） |
| 遍历链表/非连续结构 | 指针（没得选） |
| 需要在循环里改指针（比如解析协议逐段推进） | 指针 |

裸机上的一个真实理由选**下标**：越界时下标值更容易在调试器里看出来
（`i` 是个变量，能打印；指针要算差值）。
排查"数组越界"这类最难查的 bug 时，这一点很有价值。
</details>
