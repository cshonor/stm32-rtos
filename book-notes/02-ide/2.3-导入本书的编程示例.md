# 2.3 导入本书的编程示例

## 书这一节讲什么

书配套的示例代码在 No Starch 官网，下载后通过 IDE 的「Import → Existing Projects
into Workspace」导进来。

## 我的处理方式：不导入，自己写

三个理由：

1. **书里的工程带着 SW4STM32 的私有工程文件**（`.cproject` / `.project`），
   换 IDE 就废，命令行更没法用；
2. **导入是"拿来就跑"，跳过的是理解**。本仓库的做法是：自己手写启动文件、链接脚本、
   Makefile，写完之后再跟书对照——**这样才知道每一行是干什么的**；
3. **导入的工程里有一堆你不知道的历史包袱**（过期的链接脚本、用不上的库路径）。
   出了问题你连"哪一份是对的"都判断不了。

## 如果一定要导入，要先做的三件事

| 步骤 | 做什么 | 为什么 |
|---|---|---|
| ① 看链接脚本 | 打开 `*.ld`，确认 `MEMORY` 区域和芯片一致 | 书的板子是 **NUCLEO-F030R8**（Cortex-M0，Flash 64K/RAM 8K），我用的是 **F103RB**（Cortex-M3，Flash 128K/RAM 20K）。**区域不对会直接链接失败或跑飞** |
| ② 看启动文件 | 确认向量表条目数和目标核匹配 | M0 和 M3 的向量表条目不同（M0 没有部分异常） |
| ③ 看编译选项 | 确认 `-mcpu` 等目标选项 | 书里是 `cortex-m0`，我这边必须换成 `cortex-m3` |

**这三件事做完，你其实已经理解了工程的一半**——所以真的不如自己写。

## 板子差异表（书的板子 vs 我的板子）

| 项 | 书的 NUCLEO-F030R8 | 我的 NUCLEO-F103RB |
|---|---|---|
| 内核 | Cortex-**M0** | Cortex-**M3** |
| 位操作指令 | 部分缺失（M0 指令集是 M3 的子集） | 完整 Thumb-2 |
| Flash / RAM | 64K / 8K | **128K / 20K**（实测 `flash size = 128 KiB`） |
| GPIO 配置寄存器 | `MODER` / `OTYPER` / `OSPEEDR` / `PUPDR`（F0 系列风格） | **`CRL` / `CRH`**（F1 系列风格，一个引脚 4 位） |
| 时钟使能寄存器 | `RCC_AHBENR` 里有 GPIO 位 | **`RCC_APB2ENR`** 里有 GPIO 位 |
| 时钟树 | 无 PLL 也能跑（HSI 8MHz） | 常配 PLL 到 72MHz |
| 用户 LED 引脚 | PA5 | **PA5**（恰好一样） |

⚠️ **最容易踩的一条**：F0/F4/F7 系列配引脚用独立的 `MODER/OTYPER/OSPEEDR/PUPDR` 寄存器，
而 **F1 系列用 `CRL`/`CRH` 一个寄存器管 8 个引脚、每引脚 4 位**。
照抄书里的代码到 F103 上会完全不工作，**而且不报错**。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "导入示例就能跑" | 跑得起来的前提是**芯片型号和板子都对**。书用 F030R8，我用 F103RB，GPIO 寄存器模型都不一样 |
| "同一系列的 STM32 代码能通用" | 不能。F0/F1/F4/F7 的 GPIO 寄存器布局**互不兼容**（F1 是 CRL/CRH，其余多数是 MODER 系列） |
| "示例代码是最佳实践" | 示例代码的目标是"能演示功能"，不是"工程良好"。它常常省略错误处理、硬编码地址、不用 `volatile` |
| "导入别人的工程比重写快" | 短期快，长期慢。**读一份不理解的工程，比写一份理解的代码费时间** |

## 代码自测

<details>
<summary>Q1：F1 和 F0 的 GPIO 配置寄存器到底差在哪？为什么这是个"静默失败"？</summary>

| 系列 | 寄存器 | 模型 |
|---|---|---|
| F1 | `GPIOx_CRL`（pin 0–7）/ `GPIOx_CRH`（pin 8–15） | 每引脚 **4 位**：2 位 MODE + 2 位 CNF |
| F0/F4/F7/G0/H7… | `GPIOx_MODER` / `OTYPER` / `OSPEEDR` / `PUPDR` | 每属性一个 32 位寄存器，**每引脚 2 位** |

照抄书里 F0 的代码到 F103 上，会发生什么？

F0 写 `GPIOA->MODER |= (1 << 10)`（把 PA5 设成输出）；
F103 上没有 `MODER` 这个寄存器——**如果代码用的是地址常量，它会写到 `GPIOA + 0x00`，
而在 F1 上 0x00 是 `CRL`**。于是你以为在配 PA5，实际在配 PA0/PA1 的 4 位字段。

**结果是：编译过、链接过、烧录成功、板子不亮、没有任何报错。**
这就是嵌入式最典型的"静默失败"——所以每次换芯片，第一件事是**对着参考手册核地址**。
</details>

<details>
<summary>Q2：怎么快速确认自己的板子到底是什么型号？</summary>

不改代码，直接从调试器读芯片 ID（实测）：

```
$ openocd -f f103rb.cfg -c "init" -c "halt" -c "flash info 0" -c "shutdown"
Info : device id = 0x20036410
Info : flash size = 128 KiB
```

`0x20036410` 是 STM32F103 中容量器件的 DEV_ID。两个信息一次拿到：

- **device id** → 查 RM0008 的 "Device electronic signature" 章节，能对上具体型号；
- **flash size** → 直接读出来的字节数，**比看丝印可靠**（克隆板丝印经常不对）。

另外 openocd 的 cfg 文件里也能读到内核类型（`Cortex-M3 r1p1 processor detected`），
这个能区分 M0/M3/M4，对选 `-mcpu` 很关键。
</details>
