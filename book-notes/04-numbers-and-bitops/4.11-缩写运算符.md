# 4.11 缩写运算符

> 书：第 4 章 数字和变量 · 4.11 缩写运算符（原书 p44–64 区间内）
> 上一篇：[4.10 有符号整数的补码表示](4.10-有符号整数的补码表示.md) ｜ 下一篇：[4.12 用位操作控制内存映射 I/O 寄存器](4.12-用位操作控制内存映射IO寄存器.md)
> 对应实验：`--target=armv7m-none-eabi -mcpu=cortex-m3 -Os` 交叉编译 + 主机侧 UBSan

## 书这一节讲什么

一句话：`x += y` 是 `x = x + y` 的简写，`++`、`--`、`|=`、`&=`、`^=`、`<<=` 同理，
少打几个字。

在裸机上，**缩写运算符和位操作是一对**：`reg |= BIT(n)` 是"置位"的标准写法，
`reg &= ~BIT(n)` 是"清位"。但缩写运算符有个容易被忽略的本质——
**它隐含一次读和一次写**，这在寄存器上不是免费的。

## 一、实测：缩写运算符在寄存器上 = 读-改-写

```c
#define REG (*(volatile uint32_t *)0x4001080cu)
void f(void){ REG |= (1u << 5); }
void g(void){ REG = REG + 1; }
```

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -Os -c volinc.c -o volinc.o
$ llvm-objdump -d volinc.o
00000000 <f>:                     ← REG |= (1u<<5)
       8: 6801     ldr  r1, [r0]      ← 读
       a: f041 0120 orr  r1, r1, #0x20 ← 改
       e: 6001     str  r1, [r0]      ← 写
      10: 4770     bx   lr

00000012 <g>:                     ← REG = REG + 1
      1a: 6801     ldr  r1, [r0]      ← 读
      1c: 3101     adds r1, #0x1      ← 改
      1e: 6001     str  r1, [r0]      ← 写
      20: 4770     bx   lr
```

**一行 C 语句 = 3 条指令。** 中间那次 `orr`/`adds` 之后、下一次 `str` 之前，
如果来了中断且 ISR 改了同一个寄存器的另一位，这里的 `str` 会把 ISR 的修改**覆盖回去**。

这是 [4.12](4.12-用位操作控制内存映射IO寄存器.md) 要解决的那个问题的起点。

## 二、`i++` vs `++i`：裸机上没区别（实测）

```c
int post(int *p){ int i = 0; i++; return i + *p; }
int pre (int *p){ int i = 0; ++i; return i + *p; }
```

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -Os -c inc.c -o inc.o
00000000 <post>:
       0: 6800     ldr  r0, [r0]
       2: 3001     adds r0, #0x1
       4: 4770     bx   lr
00000006 <pre>:
       6: 6800     ldr  r0, [r0]
       8: 3001     adds r0, #0x1
       a: 4770     bx   lr
```

**生成的机器码完全一样。** 因为自增的结果没被使用（"值被丢弃"语境），
编译器不需要构造临时对象。

只有在**自增的结果被使用**时（`a = i++` vs `a = ++i`）才有差别，
那时候 `i++` 需要多保存一份旧值——对 `int` 也就是多一个寄存器，不会有指令数爆炸。

所以"裸机上一定要写 `++i` 因为更快"这个说法，**在标量整数上是不成立的**
（C++ 迭代器才需要关心）。写你觉得清楚的那种。

## 三、`*= 2` 和 `<<= 1` 不等价（实测）

```c
int s = 1 << 30;      unsigned u = 1u << 30;
s *= 2;  u *= 2;
int t = 1 << 30;      t <<= 1;
```

```
$ clang -O2 -fsanitize=undefined -o abbr abbr.c && ./abbr
abbr.c:5:7: runtime error: signed integer overflow: 1073741824 * 2 cannot be represented in type 'int'
abbr.c:6:29: runtime error: left shift of 1073741824 by 1 places cannot be represented in type 'int'
```

两者都是 UB，但**触发的条款不同**：

| 写法 | signed 下 | unsigned 下 |
|---|---|---|
| `x *= 2` | 乘法溢出 → UB | 定义良好的回绕（模 2^32） |
| `x <<= 1` | 左移进符号位 → UB | 定义良好 |
| `x += x` | 加法溢出 → UB | 定义良好 |

**裸机的实际结论**：想做"乘以 2 的幂"的位运算，就用 unsigned 左移
（`u <<= 1`），别在 signed 上玩——否则 UBSan 在主机上能抓，板子上抓不到
（[4.9](4.9-溢出.md) 有完整讨论）。

## 四、缩写运算符的五个裸机用法

| 写法 | 语义 | 典型用途 |
|---|---|---|
| `reg \|= BIT(n)` | 置位（不动其他位） | 开时钟、使能外设 |
| `reg &= ~BIT(n)` | 清位 | 关闭、清标志 |
| `reg ^= BIT(n)` | 翻转 | ⚠ 有坑，见 [4.12](4.12-用位操作控制内存映射IO寄存器.md) |
| `reg = BIT(n)` | **写 1 生效**（不是缩写） | `BSRR` / `SR` 类寄存器，原子 |
| `cnt += 1` / `cnt++` | 计数 | unsigned 下回绕安全 |

注意第 4 行：`BSRR` 用的是**普通赋值**，不是 `|=`——因为它的硬件语义就是
"写 1 生效、写 0 无效"，用 `|=` 反而要读一遍（多两条指令，还引入竞态）。
这是"缩写运算符用错了地方"的典型例子。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "缩写只是少打字" | 它隐含**读-改-写**：实测 1 行 C = 3 条指令（ldr/orr/str），中间可被打断 |
| "裸机上 `++i` 比 `i++` 快" | 实测两者机器码**完全相同**（`ldr` + `adds`）。标量整数无差别 |
| "`x *= 2` 和 `x <<= 1` 一样" | signed 下都是 UB，但条款不同（UBSan 分别报乘法溢出和移位溢出） |
| "寄存器操作都要用 `\|=`" | `BSRR` 这类"写 1 生效"的寄存器要用**普通赋值**，`\|=` 反而更慢且引入竞态 |
| "缩写运算是原子的" | 不是。3 条指令，中断可插入（[ch10](../ch10-interrupts.md)） |

## 代码自测

<details>
<summary>Q1：`reg |= BIT(5)` 和 `reg = BIT(5)` 该选哪个？</summary>

取决于**寄存器的硬件语义**，不是语法偏好：

| 寄存器类型 | 写 0 的含义 | 正确写法 |
|---|---|---|
| 普通配置寄存器（`CRL`、`ODR`、`RCC_APB2ENR`） | "把这一位设成 0" | `reg |= BIT(5)`（只改我关心的位） |
| 写 1 生效寄存器（`BSRR`、`SR` 的某些位、`IFCR`） | "不影响这一位" | `reg = BIT(5)`（一次 `str` 搞定） |

判断方法：**看手册里那位是 `rw`（读写）还是 `w`（只写）**，
以及它对"写 0"的描述。STM32 的 `BSRR` 明确写着
"write 1 to set, write 0 has no effect"——那就是"写 1 生效"型，用普通赋值。

实测差异：

```
toggle_bsrr:  2 条 str，无 ldr         ← 物理上不可能覆盖别人的位
toggle_odr_xor: ldr / eor / str 3 条   ← 可被中断打断
```

用错了不会报错，只会让代码更慢，并且埋一个偶发的"位丢失"bug。
</details>

<details>
<summary>Q2：为什么"读-改-写"在中断下会丢修改？举个具体时序。</summary>

假设 `GPIOA_ODR` 同时被主循环（控制 LED，bit 5）和 ISR（控制另一个 IO，bit 6）修改。

主循环执行 `GPIOA_ODR |= (1u << 5)`，实测编译成：

```
ldr r1, [r0]      ; ① 读 ODR = 0x00（bit5=0, bit6=0）
orr r1, r1, #0x20 ; ② 改 r1 = 0x20
str r1, [r0]      ; ③ 写回
```

时序：

1. 主循环执行 ①，读到 `r1 = 0x00`；
2. **中断来了**，ISR 执行 `GPIOA_ODR |= (1u << 6)`，完整三步，ODR 变成 `0x40`；
3. 中断返回，主循环继续 ② ③：基于**过期的 0x00** 算出 `0x20` 并写回；
4. 结果 ODR = `0x20` —— **ISR 设置的 bit 6 没了**。

这就是"读-改-写不原子"的完整后果，而且它是**偶发**的：
只有中断恰好插在 ① 和 ③ 之间才出错，可能几小时才复现一次。

三种解法（[4.12](4.12-用位操作控制内存映射IO寄存器.md) 展开）：
① 用 `BSRR` 这类写 1 生效的影子寄存器（物理上免疫）；
② 改之前关中断、改完再开（临界区）；
③ 用 `LDREX/STREX` 独占访问（M3/M4 支持）。
</details>

<details>
<summary>Q3：`i++` 在 `volatile` 变量上会生成几条指令？</summary>

至少三条，而且是**两次独立的硬件访问**：

```c
volatile uint32_t cnt;
cnt++;
```

等价于 `cnt = cnt + 1`，在 Cortex-M 上是：

```
ldr  r1, [r0]     ; 读（硬件访问 1）
adds r1, #0x1     ; 改
str  r1, [r0]     ; 写（硬件访问 2）
```

如果 `cnt` 是一个**硬件计数器寄存器**（有些外设有自增寄存器），
`cnt++` 会：读一次（可能触发清标志）、写一次（可能覆盖硬件刚更新的值）——
**两次副作用**，而你可能只想要其中一次。

裸机上的规则：**对硬件寄存器，不要写 `reg++` / `reg += 1`**，
显式写 `reg = SOME_VALUE` 或者用专用的置位/清位寄存器。
缩写运算符用在普通变量上没问题，用在 MMIO 上要时刻记着"它其实是三步"。
</details>
