# 4.10 有符号整数的补码表示

> 书：第 4 章 数字和变量 · 4.10 有符号整数的补码表示（原书 p44–64 区间内）
> 上一篇：[4.9 溢出](4.9-溢出.md) ｜ 下一篇：[4.11 缩写运算符](4.11-缩写运算符.md)
> 对应实验：主机侧 clang 23.1.0（`-O2`）实测

## 书这一节讲什么

一句话：**负数按补码存**：`-1` 不是"符号位 1 + 数值 1"，而是**取反加一**的结果，
所以 32 位下 `-1` 的位模式是全 1（`0xffffffff`）。

书讲补码是为了解释"为什么 `INT_MIN` 的绝对值比 `INT_MAX` 大 1"。
裸机上补码的知识有两个具体用途：**看懂掩码**（为什么 `~0u` 是全 1）
和**正确处理有符号的传感器数据**（右移、符号扩展、跨宽度赋值）。

## 一、实测：位模式

```
$ clang -O2 -o shift shift.c && ./shift
signed   -8 >> 1            = -4
unsigned 0x80000000u >> 1   = 0x40000000
(unsigned)(-8) >> 1         = 0x7ffffffc  (先转无符号再移：补 0)
INT32_MIN = -2147483648 ; 位模式 0x80000000
sizeof(int32_t)=4 sizeof(int)=4
```

配合 [4.5](4.5-整数的大小和表示.md) 的极值实测：

```
INT_MAX hex = 0x7fffffff ; INT_MIN hex = 0x80000000
(int)-1 = 0xffffffff (补码全 1)
~0u = 0xffffffff ; 1u<<31 = 0x80000000
```

**记住四个位模式，裸机上的掩码算术就够用了：**

| 表达式 | 位模式 | 用途 |
|---|---|---|
| `~0u` | `0xFFFFFFFF` | "全 1"掩码的规范写法 |
| `1u << 31` | `0x80000000` | 最高位（也是 `INT32_MIN` 的位模式） |
| `(uint32_t)-1` | `0xFFFFFFFF` | 同上，但来源是有符号 -1（补码定义） |
| `INT32_MIN` | `0x80000000` | 最小负数，**`-INT32_MIN` 仍是 UB** |

## 二、为什么"取反加一"这件事对裸机重要

因为**清位操作 `&= ~(mask)` 依赖它**：

```c
GPIOA_CRL &= ~(0xFu << 20);     /* 0xFu<<20 = 0x00F00000；取反 = 0xFF0FFFFF */
```

`~` 是按位取反，不需要理解补码也能用。
但下面这类"数值 → 掩码"的转换就绕不开补码：

```c
uint32_t mask = (1u << width) - 1u;    /* width=4 → 0xF；比写 0xF 自解释 */
```

还有**符号扩展**：把一个 12 位有符号 ADC 值（`0x800` ~ `0xFFF` 是负数）扩展成 32 位：

```c
int32_t adc_signed = (int32_t)((raw ^ 0x800u) - 0x800u);   /* 手写符号扩展 */
```

`raw ^ 0x800 - 0x800` 是"位模式层面"的补码转换，不依赖编译器的实现定义行为——
比 `(int16_t)raw` 这种依赖实现的方式更可控。

## 三、右移：算术 vs 逻辑

实测里最有信息量的一行：

```
signed   -8 >> 1            = -4         ← 算术右移，补符号位，等于除以 2
(unsigned)(-8) >> 1         = 0x7ffffffc ← 逻辑右移，补 0，结果是 2147483644
```

同一个 `-8`：

- 保持 `int` → 右移补符号位 → `-4`（语义正确：除以 2）
- 转成 `unsigned` → 位模式变成 `0xFFFFFFF8` → 右移补 0 → `0x7FFFFFFC`（语义错）

所以规则是：**有符号数据做算术（右移、比较）时，全程保持有符号类型**，
直到要写进寄存器那一刻才转无符号。中途的类型跳变是这类 bug 的唯一来源。

## 四、`INT_MIN` 的不对称（书里强调的那点）

```
INT_MAX =  2147483647  (0x7fffffff)
INT_MIN = -2147483648  (0x80000000)
```

`-INT32_MIN` 在数学上是 2147483648，但 `int32_t` 装不下 → **UB**。
实测可见 `INT_MIN hex = 0x80000000`，取负（取反加一）之后还是 `0x80000000`——
它自己是自己的负数。

裸机上的发作场景：`abs()` 类的绝对值运算、`-delta` 之类的取反。
处理办法是**先转宽类型**：

```c
int32_t d = ...;
int64_t abs_d = (d < 0) ? -(int64_t)d : (int64_t)d;   /* 先扩宽再取负 */
```

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "补码 = 符号位 + 绝对值" | 不是。实测 `-1` 是 `0xffffffff`（全 1），是 `~1 + 1` 的结果 |
| "`-1` 就是最高位为 1" | `-1` 是**全 1**；只有 `INT_MIN` 才是"只有最高位为 1"（实测 `0x80000000`） |
| "右移一位就是除以 2" | 只对有符号（算术右移）成立。实测 `(unsigned)(-8)>>1 = 0x7ffffffc`，完全不是除 2 |
| "`abs(INT_MIN)` 没问题" | UB：`-INT32_MIN` 溢出。实测 `INT_MIN` 位模式 `0x80000000`，取负还是它自己 |
| "有符号无符号转换只是重新解释" | 位模式不变，但**后续运算语义全变**（右移、比较、提升） |

## 代码自测

<details>
<summary>Q1：为什么裸机代码里写"全 1"要用 `~0u`，而不是 `-1`？</summary>

因为**类型不同，语义不同**：

| 写法 | 类型 | 位模式 | 问题 |
|---|---|---|---|
| `~0u` | `unsigned` | `0xFFFFFFFF` | ✅ 无符号全 1，位操作的标准写法 |
| `-1` | `int` | `0xFFFFFFFF` | ⚠ 位模式一样，但类型是 signed |
| `0xFFFFFFFF` | （可能是 `unsigned`） | `0xFFFFFFFF` | ⚠ 写死了 32 位，移植到 64 位上下文会错 |

位模式三者相同（实测 `(int)-1 = 0xffffffff`、`~0u = 0xffffffff`），
差别在**后续运算**：

```c
uint32_t a = ~0u >> 1;    /* 0x7FFFFFFF —— 逻辑右移 */
int32_t  b = -1   >> 1;   /* -1        —— 算术右移，还是 -1 */
```

同一个"全 1"，右移之后一个变成 0x7FFFFFFF，一个还是 -1。

所以规则：**凡是"位模式"语境（掩码、清位、置位），用 `~0u`、`1u << n` 这类无符号写法**；
`-1` 只用在"数值"语境（表示错误码、表示负数）。两者别混。
</details>

<details>
<summary>Q2：从一个 12 位 ADC 读出 `0xFFF`，这是 -1 还是 4095？</summary>

看手册怎么定义，但**代码要显式表达你的解释**，不能靠"碰巧"。

如果手册说这是**二进制补码**（很多传感器/ADC 是有符号输出），
`0xFFF` 是 -1。把它变成 32 位有符号数：

```c
uint32_t raw = adc_read() & 0xFFFu;              /* 12 位原始值 */
int32_t  val = (int32_t)((raw ^ 0x800u) - 0x800u); /* 符号扩展：0xFFF → -1 */
```

`raw ^ 0x800` 翻转符号位，`- 0x800` 把偏移挪回来——这是**位模式层面**的补码转换，
不依赖"右移是算术还是逻辑"这类实现定义行为。

如果写成 `int32_t val = (int16_t)raw;` 就错了：`raw = 0x0FFF` 会被当成 +4095，
因为 16 位下最高位还是 0，符号位在第 15 位。
**符号位在哪个位置，是由数据宽度决定的**——12 位数据的符号位是 bit 11，不是 bit 15。

判断方法：读手册里"Output coding"那一栏（通常写 binary offset / two's complement），
然后按符号位所在位做扩展。
</details>

<details>
<summary>Q3：为什么 `abs()` 在裸机上要小心？</summary>

因为 `abs(INT32_MIN)` 是 UB。

实测：`INT_MIN` 位模式是 `0x80000000`，值是 `-2147483648`。
取负 = 取反加一 = `0x7FFFFFFF + 1 = 0x80000000`——**还是它自己**。
数学上的答案 2147483648 装不进 `int32_t`，所以这是 signed 溢出，即 UB。

在 `-O2` 下编译器可以假定 `abs()` 的参数不是 `INT_MIN`，
于是基于这个假定做的优化可能删掉你的边界检查（[4.9](4.9-溢出.md) 实测过同类现象）。

安全的写法是**先扩宽再取负**：

```c
static inline int64_t abs64(int32_t v){ return (v < 0) ? -(int64_t)v : (int64_t)v; }
```

或者如果结果确定装得下，手动处理那个唯一的问题点：

```c
int32_t safe_abs(int32_t v){ return (v == INT32_MIN) ? INT32_MAX : (v < 0 ? -v : v); }
```

裸机上这类"边界值恰好是 UB"的坑特别多，因为**UB 在板子上不会报错**，
只会静默产出一个错值，然后这个错值被写进寄存器。
把 `-Wall -Wextra` 打开、把能挪到主机上验证的逻辑用 UBSan 跑一遍，是性价比最高的防线。
</details>
