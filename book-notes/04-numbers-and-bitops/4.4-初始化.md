# 4.4 初始化

> 书：第 4 章 数字和变量 · 4.4 初始化（原书 p44–64 区间内）
> 上一篇：[4.3 赋值](4.3-赋值.md) ｜ 下一篇：[4.5 整数的大小和表示](4.5-整数的大小和表示.md)
> 对应实验：`--target=armv7m-none-eabi` 交叉编译 + `llvm-objdump -h` / `llvm-nm`

## 书这一节讲什么

一句话：**变量在使用前必须有个确定的值**，声明时写 `= 初值` 就是初始化。

书里的理由是"否则变量里是垃圾值"。这个理由在 PC 上成立，
在裸机上要分成两半说：**全局变量有初值/无初值都不是垃圾（有人替你清了），
局部变量才真的是垃圾**。而"有人"是谁，决定了你能不能相信它。

## 一、实测：谁在替你初始化

```c
int g_init = 42;      /* .data */
int g_zero;           /* .bss  */
static int s_zero;
```

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding -c seg.c -o seg_arm.o
$ llvm-nm seg_arm.o
00000000 D g_init      ← .data
00000004 B g_zero      ← .bss
00000000 b main.l_zero ← .bss
```

`g_zero` 是 0，**不是因为 C 语言保证，而是因为启动代码里有一段清零 `.bss` 的循环**，
以及一段把 `.data` 从 Flash 拷到 RAM 的循环。这两段是启动文件（`.S`）里的，
在 `main` 之前跑——ch03 实测过的启动流程就是它。

**结论：裸机上"全局变量默认为 0"是一个你亲手实现的约定，不是天赐的。**
启动文件写错（比如 `.bss` 的起止符号没对齐），全局变量就全是垃圾，
而且症状千奇百怪：某个计数器从随机数开始、某个布尔量一上电就是 true。

## 二、局部变量：真的没人管

```c
void f(void){
    uint32_t x;       /* 栈上的 4 字节，值是上一次调用留下的东西 */
    ...
}
```

栈不会自动清零（清零要花时间，且没有意义）。
PC 上你可能"碰巧"每次都看到 0（因为操作系统给的页是清过零的），
**裸机上栈是同一块 RAM 反复复用**，上一次调用的残留值就是你的初值。

裸机的硬性纪律：**局部变量声明时要么给初值，要么在第一次使用前赋值。**
这条在 `-Wall` 下的 `-Wuninitialized` / `-Wmaybe-uninitialized` 能抓到大部分。

## 三、三种初始化的成本对照

| 写法 | 段 | Flash | RAM | 上电成本 |
|---|---|---|---|---|
| `uint32_t a;` | `.bss` | 0 | 4 | 清零循环扫过 |
| `uint32_t a = 0;` | **`.data`** ⚠ | 4 | 4 | 从 Flash 拷贝 |
| `uint32_t a = 5;` | `.data` | 4 | 4 | 从 Flash 拷贝 |
| `const uint32_t a = 5;` | `.rodata` | 4 | **0** | 无（直接在 Flash 里读） |
| 局部 `uint32_t a = 5;` | 栈 | 指令里的立即数 | 4（栈） | 每次调用执行一条 `movs` |

⚠ 那条最容易踩：**写 `= 0` 反而更贵**——它把变量从 `.bss` 挪进 `.data`，
白占一份 Flash 镜像和一次拷贝。裸机的习惯写法是**不写 `= 0`**。

## 四、初始化在裸机上真正的坑：顺序

`main` 之前只有两件事：`.data` 拷贝、`.bss` 清零（还有 `.init_array`，C++ 才用）。
**没有任何"模块初始化"机制**——不像 Linux 内核有 `initcall`、不像 PC 有 libc 的
`.init_array` 帮你跑构造函数。

所以：

```c
/* 错误示范：依赖另一个 .c 里的全局变量"已经被算好" */
uint32_t baud = uart_compute_baud();   /* 这不是常量表达式，C 语言根本不允许 */
```

C 语言规定全局变量的初值必须是**常量表达式**，这条规则恰好挡住了这个坑。
但下面这种就挡不住：

```c
uint32_t g_ticks = 0;      /* 假设它是 0 */
/* 另一个模块在 main 之前（比如某个 __attribute__((constructor))）改过它？ */
```

裸机上没有 constructor 机制（除非你自己实现 `.init_array`），
**所有跨模块的初始化顺序都由你在 `main` 里显式排**。
这是裸机工程里 `init_bsp()` / `periph_init()` 这类函数存在的理由。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "没初始化的变量是垃圾值" | **全局/静态**变量不是——实测落在 `.bss`，由启动代码清零。**局部**变量才是真垃圾（栈复用） |
| "`int x = 0;` 更规范" | 裸机上更贵：把变量从 `.bss` 挪到 `.data`，多占 4 字节 Flash 和一次拷贝（实测 `D` vs `B`） |
| "上电后 RAM 里都是 0" | 上电后 RAM 里是**随机**的，是启动代码清成 0 的。启动文件不对就是垃圾 |
| "初始化顺序由编译器管" | 裸机没有 `.init_array` 构造函数机制，跨模块顺序全靠 `main` 里显式排 |
| "`const` 是编译期检查" | 它同时是**省 RAM 的手段**：`const` 数据落在 Flash，不占 20 KB RAM（实测 `.rodata` 不进 `.data`/`.bss`） |

## 代码自测

<details>
<summary>Q1：为什么裸机上强烈建议"全局变量不要写 `= 0`"？</summary>

两个理由，第二个更实际。

1. **Flash 成本**：写了 `= 0`，编译器会把它放进 `.data`，初值 0 要在 Flash 里存一份镜像。
   实测符号类型从 `B`（`.bss`）变成 `D`（`.data`）。
   100 个全局计数器就多 400 字节 Flash + 400 字节拷贝时间。
2. **启动时间**：`.data` 拷贝发生在 `main` 之前，拷贝越多上电越慢。
   而对"上电后立刻要响应外部事件"的设备（比如上电 10 ms 内必须拉低某个 IO），
   这段时间是实打实的。

反过来，**只有非 0 初值才写初始化**。写 `= 0` 不仅没收益，还把语义搞模糊了
（读者会以为这个 0 有什么意义）。
</details>

<details>
<summary>Q2：局部变量没初始化，在 Mac 上跑是 0，烧到板子上就是随机值——为什么？</summary>

因为 Mac 上的栈来自操作系统新给的页，**内核保证新页清零**（安全要求，否则会泄露别的进程的数据）；
而裸机的栈就是那 20 KB RAM 里的一块，被**反复复用**：

```
main() 调用 f()，f() 的栈帧用了 0x20004F00
f() 返回，栈指针回到原处
main() 调用 g()，g() 的栈帧也落在 0x20004F00 ← 里面还是 f() 留下的东西
```

所以未初始化的局部变量读到的是"上一次用到这块栈的函数"的残留。
这个值是**稳定的但毫无意义**——同一种烧录、同一个调用序列下每次都一样，
于是你会误以为它"就是 0"或者"就是某个值"，直到某天调用顺序变了，程序开始偶发异常。

裸机排查这类问题的第一招：**把所有局部变量都初始化**，
如果问题消失，说明原来就是栈残留；如果还在，才是真 bug。
</details>

<details>
<summary>Q3：启动代码万一没清 `.bss`，症状是什么样的？</summary>

症状是"偶发 + 换个编译选项就变"，非常难查。典型表现：

- 某个全局计数器初值是几万，一上电就"已经计了很多次"；
- 某个 `bool flag` 是 true，导致程序上电就走进了错误处理分支；
- 指针变量是随机值 → 一解引用就 HardFault；
- 换 `-O0`/-`O2`、增删一个无关函数之后症状变化（因为链接布局变了，RAM 里残留的模式也变了）。

验证方法很简单，在 `main` 开头打印/断点看几个"应该是 0"的全局变量；
或者直接在启动文件里确认 `.bss` 清零循环的两端符号
（通常是 `_sbss` / `_ebss`，来自链接脚本——[ch11](../ch11-linker.md) 会讲这两个符号怎么定义）。

这条也是"为什么裸机要自己写启动文件"的最好论据：
**PC 上 libc 替你做的那些事，在裸机上要么自己做，要么就得知道它没做。**
</details>
