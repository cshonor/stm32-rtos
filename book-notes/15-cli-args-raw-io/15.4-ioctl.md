> **三种不同的 errno**、命令号位域解码

## 书这一节讲什么

一句话：**`ioctl(fd, cmd, arg)` 是 `read/write` 之外的"杂项抽屉"——
凡是既不是读数据、也不是写数据的设备操作，都往这里塞。**

它的签名是**可变、无类型**的：

```c
int ioctl(int fd, unsigned long request, ...);   /* 第三个参数是什么？看 request */
```

所以本章的核心不是"怎么用"，而是**"怎么判断它到底成没成"**——
本篇把**同一类失败给出三种不同 errno** 这件事测出来。

## 一、⚠ 实测：同一句 ioctl，三种场景下三种失败

```c
ioctl(fd, TIOCGWINSZ, &ws);   /* 问终端多大 */
ioctl(fd, FIONREAD,   &n);    /* 问还有多少字节可读 */
```

**场景 A：stdout 不是终端（本环境被重定向到 socket）**

```
$ ./io2
isatty(0)=0 isatty(1)=0 isatty(2)=0
ioctl(stdout, TIOCGWINSZ) -> -1  errno=102 (Operation not supported on socket)
ioctl(stdin,  FIONREAD)   -> -1  errno=19  (Operation not supported by device)
```

**场景 B：stdin 接上管道，有 6 字节数据**

```
$ echo "hello" | ./io2
ioctl(stdin, FIONREAD)  -> 0  可读=6 字节          ← ✅ 同一个调用，这次成了
```

**场景 C：在伪终端里跑（`script -q /dev/null ./io2`）**

```
isatty(0)=1 isatty(1)=1 isatty(2)=1
ioctl(stdout, TIOCGWINSZ) -> 0  行=0 列=0          ← ✅ 成功（但尺寸全 0）
ioctl(stdin,  FIONREAD)   -> 0  可读=1 字节
```

**汇总**：

| 目标 fd | 请求 | 结果 | errno |
|---|---|---|---|
| 非终端 stdout | `TIOCGWINSZ` | **-1** | **102** `Operation not supported on socket` |
| 无数据 stdin | `FIONREAD` | **-1** | **19** `Operation not supported by device` |
| 普通文件 | `TIOCGWINSZ` | **-1** | **25** `Inappropriate ioctl for device` |
| 有数据的管道 | `FIONREAD` | **0** | —— 可读 **6** 字节 |
| 普通文件（3 字节） | `FIONREAD` | **0** | —— 可读 **3** 字节 |
| 目录 | `FIONREAD` | **0** | —— 可读 **768** 字节 |
| pty stdout | `TIOCGWINSZ` | **0** | —— 行=0 列=0 |

## 二、⚠ 本课最重要的一条：失败时不要猜 errno

"这个 ioctl 用错了对象"这**一件事**，在本机上给出了 **3 个不同的 errno**：

| errno | 值 | 字符串 | 出现场合 |
|---|---|---|---|
| `ENOTSOCK` | 102 | Operation not supported on socket | 目标是个 socket |
| `ENODEV` | 19 | Operation not supported by device | stdin 没数据（本环境） |
| `ENOTTY` | 25 | Inappropriate ioctl for device | ⭐ 经典：对普通文件做终端 ioctl |

✅ **所以正确的写法是"只判成败，不判具体 errno"**——除非你确实要区分：

```c
if (ioctl(fd, TIOCGWINSZ, &ws) == -1) {
    /* 别写 if (errno == ENOTTY) —— 上面三个值都可能 */
    use_default_size();         /* 用默认 80x24 兜底 */
}
```

⚠ **反过来，`FIONREAD` 对"普通文件"和"目录"居然是成功的**
（返回剩余字节数 3 / 768）——**别以为 ioctl 只对设备有效**，
文件系统对象也会响应一部分请求。

## 三、命令号是怎么编出来的（实测）

内核用 4 个宏把"方向 + 魔数 + 序号 + 数据大小"压进一个整数：

```c
#define MY_MAGIC 'm'
#define MY_RESET     _IO(MY_MAGIC, 0)          /* 无数据 */
#define MY_GET_BAUD  _IOR(MY_MAGIC, 1, int)    /* 内核→用户 */
#define MY_SET_BAUD  _IOW(MY_MAGIC, 2, int)    /* 用户→内核 */
#define MY_XFER      _IOWR(MY_MAGIC, 3, int)   /* 双向 */
```

```
$ ./cmd
sizeof(int) = 4, IOC_VOID=0x20000000 IOC_OUT=0x40000000 IOC_IN=0x80000000 IOC_INOUT=0xc0000000
MY_RESET    = 0x20006d00  dir=2     len=8192 grp='m' nr=0
MY_GET_BAUD = 0x40046d01  dir=4     len= 4 grp='m' nr=1
MY_SET_BAUD = 0x80046d02  dir=8     len= 4 grp='m' nr=2
MY_XFER     = 0xc0046d03  dir=c     len= 4 grp='m' nr=3
FIONREAD    = 0x4004667f  dir=4     len= 4 grp='f' nr=127
TIOCGWINSZ  = 0x40087468  dir=4     len= 8 grp='t' nr=104
OTHER_1     = 0x40046e01  dir=4     len= 4 grp='n' nr=1
```

字段位置（低 → 高）：`nr[0..7]` · `grp[8..15]` · `size[16..29]` · `dir[30..31]`

| 字段 | 含义 | 实测例 |
|---|---|---|
| `nr` | 命令序号（0–255） | `TIOCGWINSZ` → **104** |
| `grp` | 魔数（一个字符，防撞号） | `'t'`=终端、`'f'`=文件、`'m'`=自制 |
| `size` | 第三参数的大小 | `TIOCGWINSZ` → **8**（`struct winsize`） |
| `dir` | 数据方向 | 2=无 / 4=读 / 8=写 / c=读写 |

**防撞号的意义**（实测）：`_IOR('m',1,int)` = `0x40046d01`，`_IOR('n',1,int)` = `0x40046e01`——
**只有魔数那一位不同**，所以两个驱动各自定义 `nr=1` 也不会串。
⚠ 如果你偷懒不加魔数，将来第二块板子上的驱动就会**静默接受别人的命令**。

**⚠ 两个平台差异（实测踩到）**：

1. **macOS 没有 `_IOC_DIR` / `_IOC_TYPE` / `_IOC_SIZE` 解包宏**（Linux 专有）。
   直接写会报 `call to undeclared function '_IOC_DIR'`，本篇的解包是自己写的位移。
2. **macOS 的 `IOC_VOID = 0x20000000`（bit 29），正落在 size 字段里**——
   所以 `MY_RESET` 解出来的 `len` 是 **8192** 而不是 0。
   **别自己写解码宏去做逻辑判断**，只用它打印调试，判断一律用现成常量比对。

## 四、裸机映射：`ioctl` = 命令分发表

裸机没有 `ioctl` 系统调用，但**这个模式非常好用**：
给每个外设驱动挂一张"命令 → 处理函数"的表，就是裸机版的 ioctl。

```c
typedef int (*ioctl_fn)(void *arg);

typedef struct {
    unsigned long cmd;
    ioctl_fn      fn;
} drv_cmd_t;

#define UART_MAGIC 'u'
#define UART_SET_BAUD  _IOW(UART_MAGIC, 1, uint32_t)
#define UART_GET_BAUD  _IOR(UART_MAGIC, 2, uint32_t)
#define UART_FLUSH_TX  _IO(UART_MAGIC,  3)

static const drv_cmd_t uart_cmds[] = {
    { UART_SET_BAUD, uart_cmd_set_baud },
    { UART_GET_BAUD, uart_cmd_get_baud },
    { UART_FLUSH_TX, uart_cmd_flush_tx },
};

int uart_ioctl(unsigned long cmd, void *arg) {
    for (size_t i = 0; i < ARRAY_LEN(uart_cmds); i++)
        if (uart_cmds[i].cmd == cmd) return uart_cmds[i].fn(arg);
    return -1;                    /* 未知命令：返回 -1，不猜 */
}
```

好处（和 PC 上一样的那三条）：

- **一个入口**：上层不必知道驱动内部函数名；
- **可扩展**：加命令 = 加表项，不改 API 签名；
- **可返回错误**：`-1` + 自己的错误码（裸机没有 `errno`，见 [15.2](15.2-原始IO.md)）。

⚠ **裸机上 `arg` 的类型完全靠约定**——编译器不会替你检查。
所以**在命令名里把类型写明**（`_IOW(..., uint32_t)`），
并且处理函数第一件事就是断言 `arg != NULL`。

## 坑点

| 坑 | 原书怎么说 | 实际是什么（实测） |
|---|---|---|
| ioctl 失败就是 `ENOTTY` | 一般写作 `ENOTTY` | ⚠ 本机实测出了 **102 / 19 / 25 三种** errno |
| ioctl 只对设备有效 | 隐含"设备专用" | ⚠ 对**普通文件**（3 字节）和**目录**（768 字节）也成功了 |
| 返回值就是数据 | 没提 | 返回 **0/-1** 表示成败，数据**写在第三参数里** |
| 命令号随便编 | —— | ⚠ 必须带魔数：`'m'`/`'n'` 同 nr 才不撞（`0x...6d01` vs `0x...6e01`） |
| `_IOC_DIR` 到处都有 | —— | ⚠ **macOS 没有**，只有 Linux 有 |
| `TIOCGWINSZ` 一定拿得到尺寸 | 默认能 | ⚠ pty 下成功但**行=0 列=0**，照样要兜底 |

## 代码自测

<details>
<summary>Q1：`ioctl(fd, FIONREAD, &n)` 返回 -1，errno=25。能不能断定 fd 不是终端？</summary>

**在本机不能写死判断。** 实测"ioctl 不适用"给了三个值：

| errno | 值 | 场合 |
|---|---|---|
| `ENOTSOCK` | 102 | 目标是 socket |
| `ENODEV` | 19 | stdin 无数据 |
| `ENOTTY` | 25 | 对普通文件做终端 ioctl |

errno=25 确实"通常"意味着不是终端，但**可移植代码只应判 `-1` 并走兜底**，
不要 `if (errno == ENOTTY)`。想主动判断是不是终端，用 `isatty(fd)`
（实测在 pty 下返回 1、在重定向下返回 0，比 errno 可靠得多）。
</details>

<details>
<summary>Q2：为什么 `ioctl(普通文件, FIONREAD)` 会成功并返回 3？</summary>

因为 `FIONREAD` 的语义是"这个 fd 上还有多少字节可读"，
**文件对象也能回答**（剩余字节数）。实测：

- 3 字节的 `raw.txt` → `可读=3 字节`
- 目录 `.` → `可读=768 字节`

所以 ioctl 不是"设备专用"的——它本质上是
**"凡是 read/write 语义表达不了的操作，都走这个文件控制通道"**，
文件系统对象也接了其中一部分。
⚠ 这也意味着：**你不能靠"ioctl 成功了"来推断 fd 是终端**。
</details>

<details>
<summary>Q3：`_IO('m',0)` 解出来的 size 字段是 8192，是不是我写错了？</summary>

不是你写错，是**macOS 的编码布局和 Linux 不同**。

实测 `IOC_VOID=0x20000000`，也就是"无数据"这个方向位在 **bit 29**，
而 size 字段是 bit 16..29——**两者重叠**。
所以 `_IO('m',0)` = `0x20006d00`，按 size 解就是 `(0x20006d00>>16)&0x3FFF = 8192`。

Linux 的方向位只用 bit 30/31（`_IOC_NONE=0`），size 字段是干净的 14 位，
同一个宏在 Linux 上解出来是 **0**。

**结论**：不要自己写 `_IOC_SIZE` 之类的解包宏去做业务逻辑，
打印调试可以，判断一律用现成常量比对（`cmd == MY_GET_BAUD`）。
</details>

<details>
<summary>Q4：裸机上没有 ioctl，为什么还要学这个模式？</summary>

因为**"一个入口 + 命令号 + 参数指针"是驱动分发的通用形状**，
和有没有内核无关。裸机版只是把系统调用换成普通函数：

```c
int uart_ioctl(unsigned long cmd, void *arg);   /* 查表分发 */
```

学到的三件事可直接搬：

1. **命令号带魔数**（`'u'`），多驱动共存时不撞号——实测 `'m'` 与 `'n'` 只差一位；
2. **方向写进命令名**（`_IOR`/`_IOW`/`_IOWR`），读者一眼看出谁写谁——
   裸机没有内核帮你检查，靠命名纪律；
3. **未知命令返回 -1**，不做猜测。

对照 [ch09 UART](../09-uart-serial/README.md) 的 `uart1_*` 函数族：
现在它们是散装的，用命令表收口后，上层只需要记一个入口。
</details>
