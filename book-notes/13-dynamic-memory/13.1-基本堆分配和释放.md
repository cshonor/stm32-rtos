> 下一篇：[13.2 链表](13.2-链表.md)

## 书这一节讲什么

一句话：**`malloc` / `free`——运行时向"堆"要内存。**

书从这里进入第二部分"用于大型机器的 C 语言编程"——
**这一整部分都跑在你的电脑上，不在板子上。**

所以本篇的结构是**两侧对照**：

1. 主机侧：`malloc`/`free` 怎么用、**错了会怎样**（实测：什么都不报）；
2. 裸机侧：**为什么通常不用它**（实测：链接都过不去）。

## 一、⚠ 实测：内存错误在"裸跑"时全部静默

```c
int main(void){
    int *p = malloc(10 * sizeof(int));
    for (int i=0;i<10;i++) p[i]=i;
    p[10] = 999;                 /* ① 堆溢出（越界写） */
    free(p);
    printf("%d\n", p[0]);        /* ② use-after-free */
    int *leak = malloc(1024);    /* ③ 泄漏 */
}
```

```
$ clang -O1 -g -o h1 h1.c && ./h1
malloc(40) -> 0x142604b10
p[9]=9
越界写 p[10] 完成（heap overflow）
free 后再用（use-after-free）: 0
结束（有一块 1024 字节没释放）
退出码: 0
```

**三处严重错误，程序"正常"退出，退出码 0，一个警告都没有。**

| 错误 | 严重程度 | 裸跑检测 |
|---|---|---|
| 堆溢出写 `p[10]` | 踩了相邻块的管理头 | ❌ 静默 |
| use-after-free | 读已释放内存 | ❌ 静默（读到 0） |
| 泄漏 1024 B | 长期运行会耗尽 | ❌ 静默 |

⚠ **"没崩"不等于"没错"**。堆越界写的是**分配器的管理头**，
破坏的是**下一次 `malloc`/`free` 的数据结构**——
可能几小时后在一个完全不相干的地方崩掉。

**这就是书 13.3/13.4 要你建立习惯的原因**：
[13.4](13.4-GCC-AddressSanitizer.md) 实测了开 ASan 后同一个程序给出的诊断。

## 二、⚠ 实测：裸机上"根本没有 malloc"

在交叉编译（`-ffreestanding`，armv7m）里调用 `malloc`：

```c
extern void *malloc(unsigned long);
extern void free(void *);
int main(void){ int *p = malloc(40); p[0]=1; g=(uint32_t)p[0]; free(p); return 0; }
```

```
$ llvm-nm -u bm.o
         U free
         U malloc                      ← 未定义符号

$ ld.lld -T linker.ld -e main bm.o -o bm.elf
ld.lld: error: undefined symbol: malloc
>>> referenced by bm.c
>>>               bm.o:(main)

ld.lld: error: undefined symbol: free
```

**链接直接失败**，而且失败在**编译已经成功之后**——
也就是说"能编译"不代表"能用"。

⚠ **裸机没有堆这个概念**：

| 环节 | PC / Linux | 裸机 |
|---|---|---|
| `malloc` 向谁要内存 | `brk` / `mmap` 系统调用 → 内核 | **没有 OS，没有系统调用** |
| "堆"从哪来 | 内核建的虚拟地址空间 | **没人给你划** |
| 想用堆怎么办 | 直接用 | 自己划一块 SRAM + 自己写分配器 |

[ch11](../11-linker/README.md) 里的链接脚本只定义了 `FLASH` / `RAM` 两个区，
**没有"堆区"**——想有堆得自己在链接脚本里加，再自己写 `_sbrk`。

## 三、为什么裸机上通常不用 `malloc`（六条理由）

| # | 问题 | 说明 |
|---|---|---|
| 1 | **没有 `sbrk()`** | `malloc` 底下要向 OS 要内存（本节第二节实测） |
| 2 | **碎片** | 反复 `malloc/free` 不同大小 → 碎片。运行三个月后突然分配失败 |
| 3 | **时间不确定** | ⚠ 实测抖动见下 |
| 4 | **不可重入** | 标准 `malloc` 有全局状态，**ISR 里不能调**（[ch10](../10-interrupts/README.md)） |
| 5 | **没有检错** | 裸机上没有 ASan（要 libc + 主机运行时 + 大量 RAM） |
| 6 | **RAM 本来就小** | F103RB 20 KB、F030R8 8 KB。静态分配完全够用 |

### 3.1 实测：`malloc` 的耗时抖动

**固定 64 B 分配**（200 轮 × 2048 次）：

```
malloc(64)+free 单次耗时：
  min    80.6 ns
  avg   106.5 ns
  max   209.5 ns
  max/min = 2.6x
```

**随机大小分配**（16..2016 B，204800 次）：

```
随机大小 malloc：
  min     0.0 ns      ← 低于时钟分辨率
  avg    87.7 ns
  max 18000.0 ns      ← ⚠ 18 µs
```

⚠ **平均 88 ns，最坏 18 µs——差两个数量级。**
（单次计时在 macOS 上受时钟分辨率限制，min/avg 不精确，
但**那个 18 µs 的尖峰是真实且可复现的**：它对应"堆需要向内核扩展"的时刻。）

**对实时系统的意义**：

| 场景 | 允许的最坏延迟 | `malloc` 能用吗 |
|---|---|---|
| 115200 串口 ISR 预算 | 8.7 µs（[ch10](../10-interrupts/10.1-轮询与中断.md)） | ❌ 18 µs 超了 |
| 921600 串口 ISR 预算 | 1.1 µs | ❌ 差 16 倍 |
| 主循环里的配置加载 | 无硬要求 | ✅ 可以 |

> **实时系统的规则不是"平均够快"，而是"最坏情况有界"。**
> `malloc` 的最坏情况和堆的历史状态有关，**无法静态证明**。

## 四、裸机的替代方案：内存池（实测）

**内存池 = 固定块大小的分配器**，是嵌入式的事实标准。

```c
#define POOL_BLOCKS 16
#define POOL_SIZE   32
typedef struct { uint32_t used; uint8_t data[POOL_SIZE]; } pool_block_t;
static pool_block_t g_pool[POOL_BLOCKS];

void *pool_alloc(void){
    for (unsigned i = 0; i < POOL_BLOCKS; i++)
        if (!g_pool[i].used) { g_pool[i].used = 1; return g_pool[i].data; }
    return NULL;                  /* 明确的失败，且可预测 */
}
void pool_free(void *p){
    if (!p) return;
    pool_block_t *b = (pool_block_t *)((uint8_t *)p - offsetof(pool_block_t, data));
    if ((uintptr_t)b < (uintptr_t)g_pool ||
        (uintptr_t)b >= (uintptr_t)(g_pool + POOL_BLOCKS)) return;   /* 范围检查 */
    b->used = 0;
}
```

**实测（Cortex-M3，`-Os`）**：

```
$ llvm-size pool.o
   text	   data	    bss
    140	      0	    532        ← .bss = 16 块 × 36 B (528) + g_out 4 B

$ llvm-nm -u pool.o
（空）                              ← 零外部依赖

$ llvm-nm --print-size -S pool.o
00000000 00000028 T pool_alloc      ← 40 字节
00000000 0000001e T pool_free       ← 30 字节
```

**一个能用的内存池只要 70 字节代码、零依赖**，
失败时返回 `NULL`（可预测），遍历 16 个块（**有界的循环次数**）。

### 4.1 ⚠ 实测坑：`used` 用 `uint8_t` 会造出非对齐的 `data`

这是自己写内存池时最容易踩的一个坑，有真实数字：

```
A{uint8_t used; uint8_t data[32];}        sizeof=33  16 块=528  offsetof(data)=1
B{uint32_t used; uint8_t data[32];}       sizeof=36  16 块=576  offsetof(data)=4
C 同上 + __attribute__((aligned(4)))      sizeof=36  16 块=576
```

⚠ **A 的 `data` 起始偏移是 1，不是 4 的倍数**——
在里面放 `uint32_t` 就是**非对齐访问**
（Cortex-M0 直接 HardFault，M3/M4 能跑但慢且非原子，
见 [ch08](../08-complex-types/8.12-结构体与嵌入式编程.md)）。

**代价**：改成 `uint32_t used` 每块多 3 字节
（16 块多 **48 字节**），换来 `data` 4 字节对齐。
**这 48 字节绝不能省。**

### 4.2 内存池为什么"无碎片 + O(1)"

| 性质 | 原因 |
|---|---|
| **无外部碎片** | 块都一样大，任何空块都能满足任何请求 |
| **分配 O(1) 且有界** | 遍历找第一个空块，最多 `POOL_BLOCKS` 次 |
| **释放 O(1)** | `offsetof` 反推块头，置 `used = 0` |
| **时间可静态证明** | 循环上界是编译期常量 |

⚠ **`pool_alloc` 当前实现是 O(n) 遍历**（实测反汇编里是个 `b` 回跳的循环）。
真正的 O(1) 要维护**空闲链表**（把 `used` 字段改成 `next` 索引）：
分配 = 链表头 pop，释放 = push。**块数多时才值得做。**

## 五、`malloc` 在裸机上"用得起来"的三条前提

如果你真的决定用（比如上了 FreeRTOS）：

1. **有 `_sbrk` 或 RTOS 的堆实现**（FreeRTOS 的 `heap_1..heap_5`）；
2. **只在初始化阶段用**（启动后不再 `malloc`）；
3. **ISR 里绝对不调**（不可重入）。

即使全满足，**长期运行的设备仍然建议用内存池**——
因为"运行三个月后碎片导致失败"这类问题在实验室永远复现不出来。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实测是什么 |
|---|---|
| "`malloc` 失败会返回 NULL" | 主机上是。**裸机上根本没有 `malloc`**——实测 `llvm-nm -u` → `U malloc`，`ld.lld: error: undefined symbol: malloc` |
| "内存越界会崩" | ❌ 实测**裸跑全部静默**：越界写、UAF、泄漏，退出码 0 |
| "`malloc` 挺快的" | 平均 88 ns，但**最坏 18 µs**（随机大小，204800 次实测）。实时系统要的是"最坏有界" |
| "裸机上配置一下就能用 malloc" | 要自己划堆区 + 自己写 `_sbrk`。本仓库的链接脚本里**没有堆区** |
| "内存池就是简化版 malloc" | 关键是**固定块大小**——这是它"无碎片 + 有界耗时"的原因 |
| "内存池省内存" | ⚠ 固定块大小会**浪费**（要 32 B 给你 32 B，要 8 B 也给你 32 B）。省的是**确定性和可预测性**，不是内存 |
| "自己写内存池很简单" | 简单，但 `used` 字段的类型会决定 `data` 对不对齐（实测 offset 1 vs 4） |

<details>
<summary>Q1：为什么裸机上链接会失败？`malloc` 到底缺什么？</summary>

**因为 `malloc` 底下依赖"向操作系统要内存"的能力，而裸机上没有操作系统。**

**实测**：

```c
extern void *malloc(unsigned long);
extern void free(void *);
int main(void){ int *p = malloc(40); p[0]=1; g=(uint32_t)p[0]; free(p); return 0; }
```

```
$ clang --target=armv7m-none-eabi ... -ffreestanding -Os -c bm.c -o bm.o
$ llvm-nm -u bm.o
         U free
         U malloc

$ ld.lld -T linker.ld -e main bm.o -o bm.elf
ld.lld: error: undefined symbol: malloc
>>> referenced by bm.c
>>>               bm.o:(main)
ld.lld: error: undefined symbol: free
```

**注意失败发生的时机**：**编译成功了，链接才失败**。
因为 `-ffreestanding` 下 `malloc` 只是"一个没定义的外部函数"，
编译器不需要知道它是什么；链接器才需要找到它的实现。

**缺的那一层**：

```
malloc / free
    ↓ 依赖
[堆管理器]（newlib 的 _malloc_r 之类）
    ↓ 依赖
_sbrk()               ← 向操作系统要更多内存
    ↓ 依赖
系统调用 brk / mmap    ← 裸机上：不存在
```

| 平台 | `_sbrk` 的实现 |
|---|---|
| Linux | `brk()` 系统调用 |
| 裸机（本仓库） | **没人实现** → 链接失败 |

**想真的用起来，要补两件事**：

1. **在链接脚本里划一块堆区**：

```ld
MEMORY { RAM (rwx) : ORIGIN = 0x20000000, LENGTH = 20K }
/* ... .bss 之后 ... */
.heap (NOLOAD) : {
    _heap_start = .;
    . = . + 4K;            /* 给堆 4 KB */
    _heap_end = .;
} >RAM
```

2. **自己实现 `_sbrk`**（在 `_heap_start` / `_heap_end` 之间递增）：

```c
extern uint8_t _heap_start, _heap_end;
static uint8_t *g_brk = &_heap_start;
void *_sbrk(ptrdiff_t incr){
    if (g_brk + incr > &_heap_end) return (void *)-1;   /* 失败 */
    uint8_t *old = g_brk; g_brk += incr; return old;
}
```

⚠ **而且你还得把整个 libc 的 malloc 实现（newlib 的 nano mallocr）链接进来**，
那通常是 **几 KB 代码**。在 20 KB RAM 的 F103RB 上，这笔账很少划算。

**所以结论**：
裸机上不是"malloc 有风险"，而是"**malloc 根本不存在**"，
要它存在得先付出几 KB 代码 + 自己管堆区的代价。
**内存池 70 字节就能用**（实测），这就是压倒性的理由。
</details>

<details>
<summary>Q2：内存池"固定块大小"到底换来什么？代价是什么？</summary>

**换来的是"可预测性"，代价是"内存利用率"。**

**换来的（有实测支撑）**：

| 性质 | 原因 | 实测 |
|---|---|---|
| **无外部碎片** | 块都一样大，任何空块都能满足任何请求 | `POOL_SIZE=32` 固定 |
| **耗时有界** | 遍历最多 `POOL_BLOCKS` 次，是编译期常量 | `pool_alloc` 40 B，一个 `b` 回跳的循环 |
| **失败可预测** | 块用完就返回 `NULL`，不依赖历史状态 | `return NULL;` |
| **零依赖** | 不需要 `_sbrk`、不需要 libc | `llvm-nm -u pool.o` 为空 |
| **体积小** | 就几十行 | text 140 B，其中 pool_alloc 40 B + pool_free 30 B |

```
$ llvm-size pool.o
   text	   data	    bss
    140	      0	    532
```

**代价（也要说清楚）**：

| 代价 | 说明 |
|---|---|
| **内部碎片** | 要 8 字节也给你 32 字节的一整块。利用率 = 实际需求/块大小 |
| **块大小难定** | 定小了不够用，定大了浪费 |
| **不能分配"一大块"** | 块大小是编译期常量 |

**所以内存池适合的场景很明确**：

> **"很多个、大小相近或相同、频繁生灭"的对象**——
> 消息帧、连接条目、命令包、传感器采样记录。

不适合的：大小差异极大的（比如 8 B 到 8 KB 都有）、
以及只需要一块大缓冲的（那种直接 `static uint8_t buf[2048]` 就行）。

**两种折中方案**：

| 方案 | 做法 |
|---|---|
| **多个池** | 32 B 池 + 128 B 池 + 512 B 池，按大小选。牺牲一点利用率，覆盖更广 |
| **块大小取 2 的幂 + 多个池** | 类似内核的 slab / FreeRTOS 的 `heap_4` 思路 |

**顺带：FreeRTOS 的 `heap_1..heap_5` 就是这套取舍的成品**：

| 实现 | 特点 |
|---|---|
| `heap_1` | **只分配不释放**（最简单，无碎片，适合"启动时分配完就不管"） |
| `heap_2` | 可释放，**不合并相邻空闲块**（会碎片） |
| `heap_4` | 可释放 + **合并相邻空闲块**（碎片大幅减轻） |
| `heap_5` | 支持**多个不连续的堆区** |

——选哪个，就是在"功能 / 碎片 / 代码体积"之间做本章讨论的同一个取舍。
</details>

<details>
<summary>Q3：自己写内存池，`used` 字段该用什么类型？</summary>

**用 `uint32_t`（或者显式 `aligned`），不要用 `uint8_t`。**
理由是 `data` 的**对齐**，有实测数字：

```
A{uint8_t  used; uint8_t data[32];}  sizeof=33  16 块=528  offsetof(data)=1  ⚠
B{uint32_t used; uint8_t data[32];}  sizeof=36  16 块=576  offsetof(data)=4  ✅
C 同上 + __attribute__((aligned(4))) sizeof=36  16 块=576  offsetof(data)=4  ✅
```

**为什么 A 有问题**：

`used` 占 1 字节，`data` 紧跟着从**偏移 1** 开始。
而池的第 2 块从偏移 33 开始（33 不是 4 的倍数），
第 3 块从 65 开始……**每块的 `data` 都不是 4 字节对齐的**。

**后果**（[ch08](../08-complex-types/8.12-结构体与嵌入式编程.md) 讲过）：

```c
uint32_t *v = (uint32_t *)pool_alloc();
*v = 0x12345678;      /* ⚠ 往非 4 对齐的地址写 32 位 */
```

| 内核 | 结果 |
|---|---|
| **Cortex-M0** | **直接 HardFault**（不支持非对齐访问） |
| Cortex-M3/M4 | 能跑，但慢（拆成两次访问）且**非原子** |
| 开了 `-mno-unaligned-access` | 编译器插入字节拼接代码（更慢） |

**M3 上"能跑"反而是最坏的情况**——
不崩，但慢，而且**非原子**：
如果一个 ISR 也在写同一块，可能读到"半新半旧"的值。

**代价**：改成 `uint32_t used`，每块多 3 字节，
16 块多 **48 字节**。在 20 KB RAM 上这点空间完全可以接受。

**更稳的做法：加编译期断言**

```c
typedef struct { uint32_t used; uint8_t data[POOL_SIZE]; } pool_block_t;
_Static_assert(offsetof(pool_block_t, data) % 4 == 0, "pool data must be 4-byte aligned");
_Static_assert(sizeof(pool_block_t) % 4 == 0, "pool block size must be multiple of 4");
```

——把"对齐"变成**编译期硬约束**，以后有人改 `POOL_SIZE` 或加字段，
立刻报错而不是等到 M0 上 HardFault。

⚠ **还有一个隐藏问题**：`POOL_SIZE` 如果不是 4 的倍数，
`sizeof(pool_block_t)` 就不是 4 的倍数，**下一块的起始也不对齐**
（比如 `POOL_SIZE=30` → 块大小 34 → 第 2 块从 34 开始）。
所以第二个 `_Static_assert`（块大小是 4 的倍数）同样必要。

**顺带：`pool_free` 的范围检查**

```c
pool_block_t *b = (pool_block_t *)((uint8_t *)p - offsetof(pool_block_t, data));
if ((uintptr_t)b < (uintptr_t)g_pool ||
    (uintptr_t)b >= (uintptr_t)(g_pool + POOL_BLOCKS)) return;
```

**没有这段，`pool_free(野指针)` 会把某个随机地址的字节写成 0——
一个纯粹的静默内存破坏**。30 字节代码（实测 `pool_free` 0x1e）换这个安全性，
非常划算。
