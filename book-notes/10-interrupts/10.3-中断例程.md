# 10.3 中断例程

> 书：第 10 章 中断 · 10.3 中断例程（原书 p135–153 区间内）
> 上一篇：[10.2 串口 I/O 中断](10.2-串口IO中断.md) ｜ 下一篇：[10.4 用缓冲区提速](10.4-用缓冲区提速.md)
> 对应实验：`--target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding`（`-Os` 反汇编 + 临界区对照）

## 书这一节讲什么

一句话：**ISR（中断服务例程）怎么写**——形态、约束、标志清除。

书讲的是"写一个中断处理函数"。裸机上这里真正要紧的是三件事：

1. **ISR 在 Cortex-M 上就是普通函数**（[10.2](10.2-串口IO中断.md) 实测过）；
2. **中断标志怎么清，没有统一规则**——每个外设都不同；
3. **ISR 里不能做什么**——这在 PC 上是代码规范，在裸机上是**正确性问题**。

## 一、最简形态

```c
static volatile uint8_t g_flag, g_byte;

void USART1_IRQHandler(void){
    if (USART1_SR & RXNE) {
        uint8_t c = (uint8_t)USART1_DR;    /* 读 DR 自动清 RXNE */
        g_byte = c;
        g_flag = 1;
    }
}
```

实测反汇编（`-Os`）：

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding -Os -c isr.c
00000000 <USART1_IRQHandler>:                 ← 13 条指令
       0: f643 0000  movw r0, #0x3800
       4: f2c4 0001  movt r0, #0x4001
       8: 6801       ldr  r1, [r0]       ; 读 SR
       a: 0689       lsls r1, r1, #0x1a  ; bit5(RXNE) → 符号位
       c: bf58       it   pl
       e: 4770       bxpl lr             ; 没收到 → 直接返回
      10: 6840       ldr  r0, [r0, #0x4] ; 读 DR（清 RXNE）
      ...
      28: 4770       bx   lr
```

ISR 的三个形式约束：

| 约束 | 原因 |
|---|---|
| 返回类型 `void` | 没有调用者接收返回值 |
| 参数 `void` | 没有调用者传参 |
| 名字必须是**向量表里的那个** | 链接器靠名字匹配（ch03 实测的弱别名机制） |

## 二、三条铁律

| 铁律 | 原因 |
|---|---|
| **快进快出** | ISR 期间同级/低优先级中断被屏蔽。慢 ISR = 丢中断 |
| **不做阻塞等待** | ISR 里 `while(!TXE);` 可能永远等不到（若那个外设的中断优先级更低） |
| **不用不可重入的函数** | `malloc`、`printf`（有静态缓冲）、任何带静态状态的函数 |

## 三、⚠ 中断标志怎么清：没有统一规则

**这是本节最重要的一句话：每个外设、每个标志的清除方式都不同，必须查手册。**

| 机制 | 例子 | 操作 |
|---|---|---|
| **读数据寄存器自动清** | USART 的 RXNE | `c = USART1_DR;` |
| **写数据寄存器自动清** | USART 的 TXE | `USART1_DR = c;` |
| **写 1 清除（w1c）** | **EXTI 的 PR**、多数 STM32 状态位 | `EXTI_PR = (1u << 0);` ← **写 1 清** |
| **写 0 清除** | 少数外设 | `SR &= ~BIT;` |

**EXTI 是最容易搞反的那个**：

```c
EXTI_PR = (1u << 0);          /* ✅ 写 1 清除挂起位 */
EXTI_PR &= ~(1u << 0);        /* ❌ 错！写 0 对该位无效，标志清不掉 */
```

写错的表现：**ISR 被无限重入**——因为标志一直挂着，
ISR 一返回硬件立刻又进来，主循环永远得不到执行。
现象是"程序卡死"但调试器看到 PC 一直在 ISR 里。

w1c 的设计理由和 [ch04 4.12](../04-numbers-and-bitops/4.12-用位操作控制内存映射IO寄存器.md)
的 `BSRR` 一样：**让你能用一条 `str` 精确清除某一位**，
不需要读-改-写（避免并发下的竞争）。

## 四、ISR 的正确姿势：置标志，主循环干活

```c
/* ISR：只做最少的事 */
void USART1_IRQHandler(void){
    if (USART1_SR & RXNE) {
        rb_put(&g_rx_rb, (uint8_t)USART1_DR);   /* 入队，O(1) */
        g_rx_flag = 1;                          /* volatile 标志 */
    }
}

/* 主循环：慢慢处理 */
int main(void){
    for (;;) {
        if (g_rx_flag) {
            g_rx_flag = 0;
            uint8_t b;
            while (rb_get(&g_rx_rb, &b) == 0) process(b);   /* 这里可以慢、可以 printf */
        }
        do_other_work();
    }
}
```

**这就是裸机上的"中断下半部"**。Linux 用 softirq / tasklet / workqueue / 线程化 IRQ
做同样的事（[LDD- 轨](../README.md)），裸机上是你手写的一个 `volatile` 标志。

## 五、实测：临界区与开关中断

共享变量要保护时，标准写法是"读 PRIMASK → 关中断 → 干活 → 恢复 PRIMASK"：

```c
void crit_ok(void){
    uint32_t m;
    __asm__ volatile ("mrs %0, primask" : "=r"(m));   /* 读当前状态 */
    __asm__ volatile ("cpsid i");                      /* 关中断 */
    g_shared++;
    __asm__ volatile ("msr primask, %0" :: "r"(m));    /* 恢复原值 */
}
```

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding -Os -c crit.c
00000010 <crit_ok>:
      18: f3ef 8010  mrs  r0, primask      ← 读
      1c: b672       cpsid i               ← 关（一条 16 位指令）
      1e: 680a       ldr  r2, [r1]
      20: 3201       adds r2, #0x1
      22: 600a       str  r2, [r1]         ← 读-改-写
      24: f380 8810  msr  primask, r0      ← 恢复
      28: 4770       bx   lr

00000000 <crit_bad>:                        ← 无保护版
       8: 6801       ldr  r1, [r0]
       a: 3101       adds r1, #0x1
       c: 6001       str  r1, [r0]         ← 3 条指令，非原子！
       e: 4770       bx   lr
```

对照：

| 版本 | 指令数 | 原子性 |
|---|---|---|
| `crit_bad` | 3（ldr/adds/str） | ❌ **非原子**：`ldr` 和 `str` 之间可被中断 |
| `crit_ok` | 8 | ✅ 临界区内不会被打断 |

**为什么恢复 PRIMASK 的"原值"而不是无条件 `cpsie i`**：

```c
__asm__ volatile ("cpsie i");      /* ❌ 无条件开中断 */
```

如果这段代码**本身在另一个临界区内**被调用（嵌套），
无条件开中断会**提前解除外层的保护**。恢复原值才支持嵌套。

`cpsid i` / `cpsie i` 都是**单条 16 位 Thumb 指令**，代价极小（实测）。

## 六、时间预算：ISR 能有多慢？

若中断频率为 `f` Hz、ISR 耗时 `t` 秒，CPU 开销 = `f × t`。要求 **< 10%**（留余量）：

| 波特率 | 字节率 | ISR 预算（10% CPU） |
|---|---|---|
| 9600 | ~960 B/s | ~104 µs/字节 |
| 115200 | ~11520 B/s | **~8.7 µs/字节** |
| 921600 | ~92160 B/s | **~1.1 µs/字节** ← 此时轮询和简单 ISR 都不够，要 DMA |

对照：一次 `printf` 是**毫秒级**——比 8.7 µs 的预算**大 100 倍以上**。
所以"ISR 里调 printf"不是"稍微慢一点"，是**致命的**。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "写中断例程" | Cortex-M 上 ISR **就是普通 C 函数**（[10.2 实测](10.2-串口IO中断.md)） |
| "清标志就是 `SR &= ~BIT`" | ❌ **没统一规则**。USART 读 DR 清；**EXTI 是写 1 清（w1c）**，写 0 无效 |
| "ISR 里调 printf 方便调试" | 毫秒级 vs 8.7 µs 预算——**差 100 倍**。且有静态缓冲 → 数据错乱 |
| "`volatile` 标志就够了" | 只在**单写者**时够。双写者必须关中断 |
| "关中断= `__disable_irq()`，开=`__enable_irq()`" | ⚠ 要**恢复 PRIMASK 原值**以支持嵌套。实测 `mrs`/`msr` + `cpsid i` |
| "清标志放最后" | 要**保证不被 `break`/`return` 跳过**。漏清 = ISR 无限重入 = 卡死 |

## 代码自测

<details>
<summary>Q1：中断标志到底怎么清？为什么有的读一下就清，有的要写 1？</summary>

**没有统一规则，每个外设、每个标志都不同，必须查参考手册。**

三种常见机制：

| 机制 | 例子 | 操作 |
|---|---|---|
| **读数据寄存器自动清** | USART 的 RXNE | `c = USART1_DR;` |
| **写数据寄存器自动清** | USART 的 TXE | `USART1_DR = c;` |
| **写 1 清除（w1c）** | **EXTI 的 PR**、多数 STM32 状态位 | `EXTI_PR = (1u << 0);` |
| **写 0 清除** | 少数外设 | `SR &= ~BIT;` |

**最容易理解错的是 w1c**。它的语义是：

> "你写 1 的那位被清除，写 0 的那位**不受影响**。"

所以想清 bit0，就是 `REG = (1u << 0)`——**写 1**。
而很多人下意识写成 `REG &= ~(1u << 0)`（写 0），
对 w1c 寄存器来说**这个操作无效**（写 0 不影响），标志清不掉。

**后果**：ISR 无限重入。

```
ISR 进入 → 处理 → 想清标志但没清掉 → bx lr
   ↑                                      │
   └────── 硬件看到标志还挂着，立刻再进 ───┘
```

表现为"程序卡死"，但调试器里 PC 一直在 ISR 内。**这是最能浪费一下午的 bug 之一。**

**为什么硬件要设计成 w1c？**

为了让你能用**一条 `str` 指令**精确清除某一位，
不需要"读 → 改 → 写"三步。在并发场景（ISR 和主循环都可能动这个寄存器）下，
读-改-写会丢掉另一方的改动——w1c 天然避免了这个问题。

这和 [ch04 4.12](../04-numbers-and-bitops/4.12-用位操作控制内存映射IO寄存器.md)
讲的 `BSRR`（写 1 生效、写 0 无效）是**同一套设计思路**。
NVIC 的 ISER/ICER 也是这个设计（[10.2](10.2-串口IO中断.md)）。

**排查清单**（ISR 卡死/无限重入时）：

1. 查手册确认这个标志的清除方式（**是 w1c 还是写 0**）；
2. 确认清除动作**一定会被执行**（不被 `break`/`return`/提前 `return` 跳过，
   见 [ch05 5.14](../05-control-flow-button/5.14-反模式.md) Q4）；
3. 确认清除时机：一般"读 SR → 处理 → 清标志"；
   但如果处理很慢且是 w1c，**先清更安全**（避免处理期间又来事件被丢）。

<details>
<summary>Q2：ISR 里到底能干什么、不能干什么？给个清单。</summary>

**✅ 可以（快、确定、无状态）**

- 读写 `volatile` 标志、环形缓冲入队（`rb_put`）
- 读写寄存器（清中断标志、读数据）
- 简单的算术和位操作
- 调用**可重入的**、无静态状态的函数
- 发 RTOS 的 FromISR 系列通知（`xQueueSendFromISR`）

**❌ 不可以（慢、阻塞、有状态）**

| 禁止项 | 原因 |
|---|---|
| `printf` / 格式化输出 | 毫秒级（预算是 8.7 µs）；且多数实现有静态缓冲 → 数据错乱 |
| `malloc` / `free` | 有全局堆状态，不可重入；时间不确定 |
| 忙等循环（`while(!TXE);`） | 若那个外设中断优先级更低，**永远等不到** → 死锁 |
| 延时函数 | 同上，且拖慢所有同级中断 |
| 浮点运算（M0/M3） | 软件浮点几百条指令；M4 还会触发 FPU 上下文压栈 |
| 调 `rb_get` 做解析 | 那是主循环的活，ISR 只负责"收进来" |
| 递归 / 深调用链 | 栈上多压 32 字节，深链 + ISR 可能爆栈 |

**⏱ 时间预算（实测推导）**

CPU 开销 = 中断频率 × ISR 耗时，要求 < 10%：

| 波特率 | 字节率 | ISR 预算 |
|---|---|---|
| 9600 | ~960 B/s | ~104 µs/字节 |
| 115200 | ~11520 B/s | **~8.7 µs/字节** |
| 921600 | ~92160 B/s | **~1.1 µs/字节** ← 要 DMA |

115200 下 8.7 µs 看着宽松？——**一次 `printf` 是毫秒级，差 100 倍。**

⚠ 还有一个容易漏的：**ISR 期间的栈**。
硬件自动压 8 个寄存器 = **32 字节**，
再加上你 ISR 里局部变量的帧。所以栈预算要按
"主循环最深调用链 + 32 + ISR 自身帧"算（[ch07](../07-stack-frame-functions/README.md)）。
</details>

<details>
<summary>Q3：临界区为什么必须"恢复 PRIMASK 原值"而不是无条件开中断？</summary>

为了**支持嵌套**。

实测的两种写法：

```c
/* ✅ 正确：保存并恢复原值 */
uint32_t m;
__asm__ volatile ("mrs %0, primask" : "=r"(m));    /* mrs  r0, primask */
__asm__ volatile ("cpsid i");                      /* cpsid i          */
g_shared++;
__asm__ volatile ("msr primask, %0" :: "r"(m));    /* msr  primask, r0 */

/* ❌ 错误：无条件开中断 */
__asm__ volatile ("cpsid i");
g_shared++;
__asm__ volatile ("cpsie i");                      /* cpsie i          */
```

**为什么会出问题**——考虑嵌套调用：

```c
void outer(void){
    __asm__ volatile ("cpsid i");      /* 外层关中断 */
    ...
    inner();                            /* 内层也进临界区 */
    ...
    /* 这里仍然期望中断是关的！ */
    __asm__ volatile ("cpsie i");
}

void inner(void){
    __asm__ volatile ("cpsid i");
    g_shared++;
    __asm__ volatile ("cpsie i");      /* ❌ 无条件开了！外层的保护被提前解除 */
}
```

`inner()` 返回后，`outer()` 剩下的代码**已经不在临界区里了**——
尽管 `outer()` 自己还没结束。这类 bug 表现为"偶发的数据错乱"，极难复现。

**恢复原值就不一样**：

```c
void inner(void){
    uint32_t m;
    __asm__ volatile ("mrs %0, primask" : "=r"(m));   /* m = 1（已经是关的） */
    __asm__ volatile ("cpsid i");
    g_shared++;
    __asm__ volatile ("msr primask, %0" :: "r"(m));   /* 恢复成 1（还是关的）✅ */
}
```

**代价**：多两条指令（`mrs` + `msr`），换来嵌套安全。实测 `crit_ok` 8 条指令 vs
`crit_bad` 3 条——多出来的 5 条里有 2 条就是这个保存/恢复。

**另外两个实践要点**：

1. `cpsid i` / `cpsie i` 是**单条 16 位 Thumb 指令**（实测 `b672` / `b662`），
   开关本身极便宜；
2. **临界区要尽量短**。关中断期间所有可屏蔽中断都不响应——
   关 1 ms 就等于放弃了 1 ms 的实时性。
   规则：临界区里只做"读-改-写共享变量"这一件事，别的都挪出去。

**进阶**：如果只想屏蔽**低于某优先级**的中断（而不是全关），
用 `BASEPRI` 寄存器——这样更高优先级的紧急中断仍能响应。
这是 RTOS 里的常见做法（FreeRTOS 的 `taskENTER_CRITICAL_FROM_ISR`）。
</details>
