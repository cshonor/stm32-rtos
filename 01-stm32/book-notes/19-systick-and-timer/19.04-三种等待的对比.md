## 书这一节讲什么

书里没有。**裸机上有三种"等一段时间"的做法，只有一种是正确的。**

| 做法 | 代码 | CPU 占用 | 精度 | 适用场景 |
|---|---|---|---|---|
| **忙等循环** | `for(i=0;i<N;i++);` | 100% | 差（随优化变） | 极短的（几微秒）延时 |
| **阻塞延时** | `delay_ms(500);` | 100%（在等） | 好 | 初始化、演示 |
| **非阻塞判据** | `if ((int32_t)(millis()-next)>=0)` | **0%** | 好 | **所有正式场合** |

## 一、⭐ 实测：忙等循环在各优化级别下的存活情况

`wait.c` 里四个函数，交叉编译到 Cortex-M3，逐级别数指令条数：

| 函数 | `-O0` | `-O1` | `-O2` | `-Os` | `-Os` 下变成什么 |
|---|---|---|---|---|---|
| `wait_bad`（非 volatile 计数） | 18 | **2** | **2** | **1** | `bx lr` ← **整个循环没了** |
| `wait_vol`（volatile 计数） | 18 | 14 | 29 | 12 | 循环保住（`sub sp` / `str` / `ldr` / `cmp` ...） |
| `wait_flag`（非 volatile 标志） | 8 | 8 | **1** | **1** | `bx lr` ← **空转等标志也没了** |
| `wait_flag_v`（volatile 标志） | 8 | 6 | 16 | 6 | 循环保住（`ldr` / `cmp` / `beq` ...） |

**三个结论**：

1. **非 volatile 的等待在 `-O1` 及以上会被整个删掉**——
   `wait_bad` 在 `-Os` 下只剩一条 `bx lr`，**延时直接变成 0**；
2. **就算保住了，指令数也随优化级别乱跳**——`wait_vol` 从 `-O0` 的 18 条
   到 `-O1` 的 14 条、`-O2` 的 29 条、`-Os` 的 12 条，**同一个源文件四种延时**；
3. **`volatile` 能保住循环，但代价是每次迭代真的访存**——
   `-Os` 下 `wait_vol` 的循环体是 `str / ldr / cmp`，比寄存器计数慢得多。

⚠ 这类 bug 的经典表现：**Debug 版（`-O0`）时序正常，Release 版（`-O2`）时序全乱。**

## 二、⭐ 实测：忙等版 vs SysTick 版，固件差多少

两个最小裸机镜像（都有向量表 + 一个 `volatile uint32_t g_led`），
`ld.lld` + `linker.ld --gc-sections` 真实链接：

```
=== busy 版：delay(40000) 忙等翻转 LED ===
   text    data     bss     dec     hex
     48       0       4      52      34

=== tick 版：SysTick 1 ms 心跳 + 非阻塞判据 ===
   text    data     bss     dec     hex
     52       0       8      60      3c
```

**差值只有 8 字节**（text +4、data +4）。也就是说：

> **用"正确的非阻塞方案"替换"错误的忙等方案"，代价是 8 字节 Flash + 4 字节 RAM。**

⚠ 这 4 字节 data 就是 `g_ms` 本身。如果向量表要写全 16 项（[19.03](19.03-g_ms与回绕安全的时间比较.md)），
总共也才 132 字节。**没有任何理由为了省这点空间去用忙等。**

## 三、阻塞版：能用，但要清楚代价

```c
/* ⚠ 阻塞：能用，但期间什么都干不了 */
void delay_ms(uint32_t ms){
    uint32_t start = millis();
    while ((int32_t)(millis() - start) < (int32_t)ms) { }
}
```

这个版本**时序是对的**（基于 `g_ms`，不受优化影响），
问题在于**阻塞期间主循环停摆**：

```
delay_ms(500) 期间：
  - 串口来了数据？收不到（ISR 能进，但主循环处理不了）
  - 按键按了？检测不到
  - 看门狗？可能超时复位（如果延时比喂狗周期长）
```

⚠ 而且一旦习惯了阻塞延时，就很容易在 **ISR 里也不小心用上**——
而 **ISR 里阻塞 = 死锁**（ch10 讲过）。所以从一开始就养成非阻塞的习惯。

## 四、裸机主循环的标准结构（超级循环 / super-loop）

```c
int main(void){
    init_all();
    uint32_t t_led = millis(), t_sensor = millis(), t_uart = millis();
    for (;;) {
        uint32_t now = millis();
        if ((int32_t)(now - t_led)    >= 0) { t_led    = now + 500; task_led(); }
        if ((int32_t)(now - t_sensor) >= 0) { t_sensor = now + 10;  task_sensor(); }
        if ((int32_t)(now - t_uart)   >= 0) { t_uart   = now + 1;   task_uart(); }
        /* 还可以进低功耗：__WFI(); */
    }
}
```

这就是**没有 RTOS 的"多任务"**——靠时间片轮询。
它简单、确定、无栈切换开销，代价是：
**任何一个 task 阻塞了，全部 task 都停**（ch20 的 RTOS 就是来解决这个的）。

## 坑点

| 坑 | 原书怎么说 | 实际是什么（实测） |
|---|---|---|
| "写个 `for` 循环就能延时" | —— | ❌ `-O1` 起就**整个被删**；实测 `wait_bad` 在 `-Os` 下只剩 `bx lr` |
| "加个 `volatile` 就安全了" | —— | ⚠ 循环保住了，但**指令数随 `-O` 乱跳**（`wait_vol`：18/14/29/12 条）→ 四种延时长度 |
| "空转等标志挺好用" | —— | ❌ 非 volatile 版本在 `-O2`/`-Os` 下**退化成 `bx lr`**（实测 1 条指令） |
| "非阻塞方案更占资源" | —— | ❌ 实测**只多 8 字节**（52 → 60）；写全向量表也才 132 字节 |
| "`delay_ms(500)` 挺好用" | —— | ⚠ 期间 CPU 100% 空转且**其他任务全停**；正式代码用非阻塞判据 |
| "改了优化级别不影响功能" | —— | ❌ 实测同一源码 `-O0`→`-Os`，两个等待函数**直接消失** |

## 代码自测

<details>
<summary>Q1：为什么优化器敢把空循环整个删掉？</summary>

因为 **C 标准的"as-if 规则"**：只要**可观察行为**不变，编译器可以任意改写程序。

"可观察行为"只包括：对 `volatile` 对象的访问、对文件的读写、输入输出。
一个非 volatile 的空循环**不改变任何可观察状态**，
所以编译器认为"删掉它和跑完它，效果完全一样"——于是就删了。

实测证据就是 `wait_bad` 在 `-Os` 下的全部内容：

```
00000000 <wait_bad>:
       0:  bx  lr          ← 就这一条，循环没了
```

⚠ **这不是编译器的 bug，是代码的问题**：
你写的循环**本来就没告诉编译器"这个循环有副作用"**。

**两种修法，用途完全不同**：

```c
/* ① volatile：保住循环（用于"真的要空转一小会儿"）*/
for (volatile uint32_t i = 0; i < n; i++) { }

/* ② 直接用硬件定时器（用于"要精确延时"）*/
/* 见 19.3 的非阻塞判据——这才是正解 */
```

⚠ 但 ① 只是"保住循环"，**精度依然没有保证**（实测指令数随 `-O` 变）。
要精确延时，只能靠硬件时钟，不能靠数指令。
</details>

<details>
<summary>Q2：既然非阻塞方案只多 8 字节，为什么还有人用忙等？</summary>

三个真实原因，都不是"省资源"：

1. **不需要时基就能用**——忙等是"零依赖"的，
   连 SysTick 都没配的时候，想让 LED 闪一下，只能忙等。
   所以**启动阶段、调试阶段**用忙等是完全合理的；
2. **极短延时的场合确实要用**——比如 SPI 片选拉低后要保持 100 ns，
   这种量级**开中断进 ISR 都比延时本身长**，只能用几条 `__NOP()`；
3. **惯性/教程害人**——大量入门教程（包括本书 ch05 的写法）
   直接用忙等做演示，读者照抄到产品代码里就出事。

**判据表**（本节主线结论）：

| 场景 | 做法 |
|---|---|
| 极短延时（几微秒，如 SPI 片选保持） | `__NOP()` 或数条指令，**并注释说明为什么不精确** |
| 初始化时的等待（如传感器上电稳定） | 阻塞 `delay_ms()` 可以接受（此时没有别的任务） |
| **运行期的一切延时** | **非阻塞判据**（[19.03](19.03-g_ms与回绕安全的时间比较.md)） |

⚠ **判断标准不是"延时多长"，而是"延时的同时要不要干别的事"**。
只要答案是"要"，阻塞就是错的。
</details>

<details>
<summary>Q3：超级循环里一个 task 卡住了，会有什么症状？</summary>

**症状是"所有功能都变慢"，而且极难定位。**

因为超级循环是**串行轮询**的：

```c
for (;;) {
    if (time_for_a()) task_a();
    if (time_for_b()) task_b();      /* ← 这个卡了 50 ms */
    if (time_for_c()) task_c();      /* ← c 就要多等 50 ms */
}
```

`task_b()` 里一旦有人加了 `while(等待传感器响应)`，
`task_a` 和 `task_c` 的周期**全都**被拖长——
但你去看 `task_a` 的代码，它完全没问题。

⚠ **这就是超级循环的隐藏陷阱：它假设"每个 task 都会很快返回"**，
而这个假设**没有任何机制去保证**，只能靠人的纪律。

**什么时候该换 RTOS**（ch20）：

| 信号 | 说明 |
|---|---|
| **有阻塞操作** | 比如"等传感器响应 50 ms"——超级循环下这 50 ms 全系统停摆 |
| **任务响应时间要求差异大** | 有的要 1 ms 响应，有的可以 100 ms——需要优先级 |
| **任务间要传数据** | 队列比自己写环形缓冲 + 标志清楚得多 |
| **代码量上千行** | 状态机开始失控，RTOS 的"每个任务顺序执行"更好维护 |

**本仓库的路线**：先写超级循环（理解"时间"怎么造），
再上 FreeRTOS（ch20），**两相对比才明白 RTOS 到底解决了什么问题**。
直接上 RTOS 只会觉得"它好复杂"，不知道它好在哪。
</details>
