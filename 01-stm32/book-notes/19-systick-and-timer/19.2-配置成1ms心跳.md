## 书这一节讲什么

书里没有。**这一节是整个补充篇最"短平快"的一步：把 SysTick 配成 1 ms 中断一次**，
然后在 ISR 里给一个全局计数器加一。

配置三个寄存器就完事，但**重载值填 8000 还是 7999** 是新手必踩的第一个坑。

## 一、配置代码

```c
#define SYST_CSR (*(volatile uint32_t *)0xE000E010u)
#define SYST_RVR (*(volatile uint32_t *)0xE000E014u)
#define SYST_CVR (*(volatile uint32_t *)0xE000E018u)

static volatile uint32_t g_ms;      /* 毫秒计数（uint32_t 约 49.7 天回绕） */

void systick_init_1ms(uint32_t cpu_hz){
    SYST_RVR = (cpu_hz / 1000u) - 1u;    /* 重载值：1 ms */
    SYST_CVR = 0;                        /* 清当前值 */
    SYST_CSR = (1u << 2)                 /* CLKSOURCE: 1=CPU 时钟 */
             | (1u << 1)                 /* TICKINT:   1=计数到 0 触发中断 */
             | (1u << 0);                /* ENABLE */
}

void SysTick_Handler(void){              /* 名字是硬件约定的，不能改 */
    g_ms = g_ms + 1u;                    /* ISR 里只做这一件事 */
}
```

## 二、⭐ 实测：RVR 到底填 7999 还是 7999+1

计数器**包含 0**，所以从 `RVR` 减到 `0` 一共是 `RVR + 1` 个时钟周期：

```
周期 = (RVR + 1) / fclk    →    RVR = fclk / 目标频率 - 1
```

本机实测（`/tmp/ch19lab/wrap.c`，clang 23.1.0 编译后运行）：

```
CPU= 8 MHz → RVR = 8000000/1000 - 1 = 7999   （周期 = 7999+1 = 8000 个时钟）
CPU=72 MHz → RVR = 72000000/1000 - 1 = 71999 （周期 = 71999+1 = 72000 个时钟）
⚠ 写成 hz/1000（不减 1）会比标称慢 1/1000；写成 8000/72000 同理
```

⚠ **NUCLEO-F103RB 上电默认是 HSI 8 MHz**（不是 72 MHz）。
如果配了 PLL 到 72 MHz，这个值要改成 71999。
**写错的表现是"延时差 9 倍"**——和 ch09 波特率算错是同一类错误。

## 三、⭐ 实测：这段配置代码编译出来有多大

把上面的 `systick_init_1ms(8000000u)` 单独编成裸机镜像（`-Os`，`--gc-sections`）：

```
$ llvm-size app_cfg.elf
   text    data     bss     dec     hex
     36       0       0      36      24
```

`text 36` 里还包括 8 字节向量表，所以**真正的配置函数约 26 字节**。反汇编：

```
08000008 <Reset_Handler>:                 ← systick_init_1ms 被内联进来了
 8000008: movw r0, #0xe010
 800000c: movt r0, #0xe000               ← r0 = 0xE000E010（CSR 基址）
 8000010: movw r1, #0x1f3f               ← r1 = 7999
 8000014: str  r1, [r0, #0x4]            ← SYST_RVR = 7999   ✅ 常量折叠，零运行时除法
 8000016: movs r1, #0x0
 8000018: str  r1, [r0, #0x8]            ← SYST_CVR = 0
 800001a: movs r1, #0x7
 800001c: str  r1, [r0]                  ← SYST_CSR = 0x7（ENABLE|TICKINT|CLKSOURCE）
 800001e: nop
 8000020: b    0x8000020                 ← for(;;)
```

**三次 `str` 就配完了。** 而且注意 `cpu_hz / 1000 - 1` 被**常量折叠成 7999**——
传常量进去时，除法在编译期就消失了，运行时零开销。

⚠ 但如果 `cpu_hz` 是**运行时变量**，除法就真的会在 M3（无硬件除法）上
调 `__aeabi_uidiv`——**那时链接会失败**（本仓库环境无 armv7m compiler-rt builtins，
见 [16.7](../16-floating-point/16.7-替代方案.md)）。
所以：**裸机上尽量把时钟频率写成编译期常量。**

## 四、SysTick 的 24 位上限：多久会撑不住

RVR 只有 24 位（最大 `0xFFFFFF` = 16777215）。算式推导（非真机实测）：

| fclk | RVR=0xFFFFFF 最长周期 | 1 kHz 所需 RVR | 10 Hz 所需 RVR |
|---|---|---|---|
| 8 MHz | 2097.152 ms | 7999 ✅ | 799999 ✅ |
| 72 MHz | 233.017 ms | 71999 ✅ | 7199999 ✅ |
| 168 MHz | 99.864 ms | 167999 ✅ | 16799999 ❌ |

⚠ **主频越高，单次能定的时间越短**。168 MHz 上连 100 ms 都定不出来。
所以 SysTick 只该做**高频心跳**，长定时交给软件计数器（[19.3](19.3-g_ms与回绕安全的时间比较.md)）。

## 代码自测

<details>
<summary>Q1：为什么 RVR 要减 1？不减会怎样？</summary>

**因为计数器包含 0。** 从 `RVR` 递减到 `0` 一共经历 `RVR + 1` 个时钟：

```
RVR = 7999  →  7999, 7998, ..., 1, 0   →  8000 个时钟 = 8000 / 8MHz = 1.000 ms  ✅
RVR = 8000  →  8000, 7999, ..., 1, 0   →  8001 个时钟 = 8001 / 8MHz = 1.000125 ms
```

不减 1 的误差是 **`1/8000` = 0.0125%**，单次看不出来，
但它是**系统性偏差、会累积**：

```
1 小时 = 3,600,000 ms
不减 1 → 每小时多走 3,600,000 × 0.125 μs = 0.45 秒
一天   → 多走约 10.8 秒
```

如果设备要跑一个月不校时，**这就成了 visible bug**。
而且这类 bug 极难定位：它"看起来是准的"，只有长时间对比才发现。

**判据**：凡"减到 0 触发"的计数器（SysTick、TIM 的 ARR、看门狗），
重载值统统是 `目标计数值 − 1`。
</details>

<details>
<summary>Q2：我怎么知道板子现在到底跑在多少 MHz？</summary>

三个办法，从可靠到不可靠：

**① 直接测量（最可靠）**——配一个 GPIO 每 1 ms 翻转，用示波器/逻辑分析仪看周期。
这是唯一不依赖任何假设的办法。

**② 用另一个已知时钟交叉验证**——比如 UART 波特率（ch09）。
波特率算错的表现是"乱码"，时钟算错的表现是"波特率对了但延时不对"，
两者结合能定位到底是哪个时钟分支错了。

**③ 读 RCC 寄存器反推**——读 `RCC_CFGR` 的 PLL 倍频位和 `RCC_CR` 的时钟就绪位，
反推当前 SYSCLK。**注意**：这只能证明"寄存器被写成了什么"，
不能证明"时钟真的起来了"（比如 HSE 起振失败会自动回退到 HSI）。

⚠ **本仓库诚实标注**：以上三种**本机均未实测**（没有真机 + 没有示波器）。
本节所有 MHz 相关的数字都来自 NUCLEO-F103RB 的公开规格（上电 HSI 8 MHz），
**不是我量出来的**。

**教训**：这类"以为是多少 MHz"的假设，正是"延时差 9 倍"这个经典 bug 的根源。
**开机第一件事应该是确认时钟，而不是假设时钟。**
</details>

<details>
<summary>Q3：为什么实测里配置函数只剩 3 条 str？</summary>

因为**参数是编译期常量，除法被常量折叠了**。

```c
systick_init_1ms(8000000u);        /* 常量 → 8000000/1000-1 = 7999 直接算好 */
```

编译器看到 `cpu_hz` 恒等于 8000000，于是在编译期算出 7999，
生成 `movw r1, #0x1f3f`（0x1F3F = 7999）——**运行时不做任何除法**。

⚠ 对照一下：如果写成运行时变量

```c
systick_init_1ms(get_cpu_hz());    /* 变量 → 真的要除 */
```

Cortex-M3 **没有硬件除法指令**，编译器会插入对 `__aeabi_uidiv` 的调用。
而本仓库的 armv7m 目标**没有 compiler-rt builtins**
（[16.7](../16-floating-point/16.7-替代方案.md) 实测过 `__aeabi_fmul`/`__aeabi_dmul` 同样缺失），
链接会直接报 `undefined symbol`。

**裸机上的通用结论**：能在编译期算的，绝不放到运行时算。
这不只是"快一点"，在 M0/M3 上**可能是"能不能链接通过"的区别**。
</details>
