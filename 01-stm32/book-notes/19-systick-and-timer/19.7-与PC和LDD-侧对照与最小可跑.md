## 书这一节讲什么

书里没有。**这一节做两件事**：

1. 把裸机的"时间"和 PC / Linux 内核的"时间"对照起来——**会发现是同一套东西**；
2. 给出本篇的**最小可跑代码**（可以直接抄进项目的那几十行）。

## 一、裸机 ↔ PC / Linux 对照

| 概念 | PC / Linux | 裸机 STM32 |
|---|---|---|
| 时间源 | TSC / HPET / clocksource 框架 | SysTick（内核自带）+ 通用定时器 |
| 获取当前时间 | `clock_gettime()` | `millis()`（自己维护） |
| 延时 | `sleep()` / `nanosleep()`（进程让出 CPU） | 阻塞版占 CPU；非阻塞版靠主循环判据 |
| 定时回调 | `timerfd` / `hrtimer` | 主循环里判时间，或定时器中断 |
| 心跳 | 内核的 `jiffies` / `HZ` | **SysTick 的 `g_ms`** ← **完全对应** |
| 溢出处理 | 内核用 `time_after()` 宏 | `(int32_t)(a-b) >= 0` ← **同一个技巧** |

⭐ **内核的 `time_after(a, b)` 就是 `(long)(a) - (long)(b) > 0`**——
和 [19.3](19.3-g_ms与回绕安全的时间比较.md) 的写法**一字不差**。
学两遍，记两遍，两边都受用。

## 二、⭐ 实测：读一次时间，裸机和 PC 差 13 倍

主机侧 2×10⁷ 次循环实测（clang 23.1.0 `-O2`，macOS arm64）：

```
millis()（读 volatile 全局）:     1.63 ns/次
clock_gettime(MONOTONIC)    :    21.13 ns/次
比值                        :     12.9 x

分辨率实测（连续两次读取的差值）: 1000 ns
```

**裸机的 `millis()` 比 PC 的 `clock_gettime()` 快 12.9 倍。**

原因很直白：

| | 裸机 `millis()` | PC `clock_gettime()` |
|---|---|---|
| 做什么 | 读一个内存地址（实测编成**一条 `ldr`**） | 进内核（或 vDSO）、读硬件计数器、换算成 `timespec` |
| 权限 | 直接访问，无切换 | 至少一次函数调用，可能涉及特权切换 |
| 实测成本 | **1.63 ns** | **21.13 ns** |

⚠ **别误读成"裸机更快所以更好"**——
`clock_gettime()` 贵，是因为它给你的是**纳秒级、跨进程一致、可回溯**的时间；
`millis()` 便宜，是因为它只是"我自己的一个计数器"。
**对 HFT 的启示是反过来的**：在 PC 上做低延迟时，
`clock_gettime()` 的 21 ns 是**真实开销**，高频路径上要缓存时间戳、
用 TSC 直读，或者降低采样频率——**每一处"取个时间"都不是免费的**。

⚠ **诚实标注**：以上是 **macOS arm64 的实测**，不是 Linux。
Linux 上 `clock_gettime(CLOCK_MONOTONIC)` 走 vDSO 通常更快（个位数 ns），
数值会不同，**但"比读一个全局变量贵一个量级"这个结论不变**。

## 三、最小可跑（可以直接抄走）

```c
/* ---- 时基：SysTick 1 ms 心跳 ---- */
static volatile uint32_t g_ms;

void SysTick_Handler(void){ g_ms++; }        /* 名字是硬件约定的 */
uint32_t millis(void){ return g_ms; }

/* ---- 回绕安全的时间比较（背下来） ---- */
static inline int time_after(uint32_t a, uint32_t b){
    return (int32_t)(a - b) > 0;
}
static inline int time_after_eq(uint32_t a, uint32_t b){
    return (int32_t)(a - b) >= 0;
}

/* ---- 用法：超时 ---- */
static uint32_t s_deadline;
void start_timeout(uint32_t ms){ s_deadline = millis() + ms; }
int  timed_out(void){ return time_after_eq(millis(), s_deadline); }

/* ---- 用法：周期性任务（超级循环） ---- */
void loop(void){
    static uint32_t t_led;
    if (time_after_eq(millis(), t_led)) { t_led = millis() + 500; led_toggle(); }
}
```

⚠ **配套两件事，漏一件就跑不起来**：

1. **向量表要写全**——`SysTick_Handler` 必须在第 15 项，
   否则会被 `--gc-sections` 删掉（[19.3](19.3-g_ms与回绕安全的时间比较.md) 实测）；
2. **RVR 要按真实主频算**——F103 上电是 HSI 8 MHz → `RVR = 7999`
   （[19.2](19.2-配置成1ms心跳.md) 实测）。

## 坑点

| 坑 | 原书怎么说 | 实际是什么（实测） |
|---|---|---|
| "PC 上取时间很便宜" | —— | ❌ 实测 **21.13 ns/次**（macOS arm64），比裸机 `millis()` 的 1.63 ns **贵 12.9 倍** |
| "裸机的时间机制和 PC 完全不同" | —— | ❌ `jiffies` ↔ `g_ms`、`time_after()` ↔ `(int32_t)(a-b)` **一一对应，连技巧都一样** |
| "抄了 millis() 就能用" | —— | ⚠ 还要**向量表写全**（否则 ISR 被 gc）+ **RVR 按真实主频算**（否则差 9 倍） |
| "`time_after` 是内核专用的高级技巧" | —— | ❌ 就是 `(long)(a)-(long)(b) > 0`，裸机上一样写，**零额外指令**（[19.3](19.3-g_ms与回绕安全的时间比较.md) 实测 `subs`+`bmi`） |

## 代码自测

<details>
<summary>Q1：为什么内核要用 time_after()，不能直接比较 jiffies？</summary>

**因为 `jiffies` 会回绕，和裸机的 `g_ms` 是同一个问题。**

Linux 内核里 `jiffies` 是 `unsigned long`，在 32 位平台上会回绕
（`HZ=1000` 时约 49.7 天——**和裸机 `uint32_t` 毫秒完全同一个数字**，这不是巧合，
因为两者都是 2³² 毫秒）。

内核的做法（`<linux/jiffies.h>`）：

```c
#define time_after(a,b)     ((long)((b) - (a)) <  0)
#define time_before(a,b)    time_after(b,a)
#define time_after_eq(a,b)  ((long)((a) - (b)) >= 0)
#define time_before_eq(a,b) time_after_eq(b,a)
```

**和本篇的写法是同一个东西**，只是符号方向换了一下：

| 内核 | 本篇 |
|---|---|
| `time_after(a,b)` → `(long)((b)-(a)) < 0` | `(int32_t)(a - b) > 0` |
| `time_after_eq(a,b)` → `(long)((a)-(b)) >= 0` | `(int32_t)(a - b) >= 0` |

**为什么内核要提供这个宏而不是让大家自己写**：
因为"直接比较"在**测试时永远不会出错**——
要等到 49.7 天后才暴露，而那时没人会想到是这行代码。
宏把正确用法**固化**下来，让写错变难。

**裸机上的对应做法**：也把判据封成 `static inline` 函数（见第三节），
**不要在主循环里手写裸比较**。同一条纪律，同一套原因。
</details>

<details>
<summary>Q2：21 ns 的 clock_gettime() 对 HFT 意味着什么？</summary>

**意味着"取时间戳"本身是一个要进预算的开销。**

粗算一笔账（用本次实测的 21.13 ns）：

| 场景 | 每秒取时间次数 | 开销 |
|---|---|---|
| 每个 tick 打一次时间戳（1 万 tick/s） | 10⁴ | 0.21 ms/s = **0.021% CPU** |
| 每个订单事件打一次（10 万事件/s） | 10⁵ | 2.1 ms/s = **0.21% CPU** |
| 每个包打两次（收+发，100 万包/s） | 2×10⁶ | 42 ms/s = **4.2% CPU** ⚠ |

最后一行是真实存在的量级——**100 万包/秒时，光打时间戳就烧掉 4% 的核**。

**这是本次实测给我的最实用的一条**：
在 PC 上写低延迟代码时，"顺手取个时间"不是免费的。常见对策：

1. **降低采样频率**——不是每个包都打戳，批量打；
2. **缓存时间戳**——一个循环批次内共用一个戳（精度换开销）；
3. **直读 TSC**——`rdtsc` / `rdtscp` 是个位数 ns，但**要处理跨核一致性和频率缩放**；
4. **只在关键路径打戳**——热路径之外的诊断信息异步记录。

⚠ 反过来，**这也是裸机的优势**：
`millis()` 只有 1.63 ns，MCU 上"到处打时间戳"几乎不要钱。
**约束不同，最优解就不同**——这正是本仓库两边都学的价值。
</details>
