# 16.01 数字表示

> 书：第 16 章 浮点数 · 16.01 数字表示（原书 p219+ 区间内）
> 下一篇：[16.02 舍入误差](16.02-舍入误差.md)
> 对应实验：主机侧实测（clang 23.1.0 / macOS arm64）+ 交叉编译
> `--target=armv7m-none-eabi -mcpu=cortex-m3`

## 书这一节讲什么

一句话：**浮点数 = 科学计数法的二进制版——符号 + 指数 + 尾数三段拼起来的位模式。**

书把它放在第二部分"用于大型机器的 C 语言编程"，原因很实在：
**书里的板子 NUCLEO-F030R8 是 Cortex-M0，没有 FPU**，浮点全靠软件模拟，
所以作者把浮点挪到"跑在电脑上的那一半"讲。

这本身就是一条结论：

> **在你确认芯片有 FPU 之前，不要假设浮点是便宜的。**

## 一、实测：三种浮点类型的尺寸

```
$ ./fp
sizeof float=4 double=8 long double=8
FLT_DIG=6 DBL_DIG=15 LDBL_DIG=15
FLT_EPSILON=1.192092896e-07  DBL_EPSILON=2.2204460492503131e-16
FLT_MIN=1.175494351e-38  FLT_MAX=3.402823466e+38
DBL_MIN=2.2250738585072014e-308  DBL_MAX=1.7976931348623157e+308
FLT_TRUE_MIN=1.401298464e-45  DBL_TRUE_MIN=4.940656458e-324
FLT_MANT_DIG=24 DBL_MANT_DIG=53
```

| 类型 | 实测大小 | 尾数位（`*_MANT_DIG`） | 指数位 | 十进制可靠位（`*_DIG`） |
|---|---|---|---|---|
| `float` | **4** B | **24**（含隐含位） | 8 | **6** |
| `double` | **8** B | **53** | 11 | **15** |
| `long double` | **8** B ⚠ | 53 | 11 | 15 |

⚠ **`long double` 实测只有 8 字节**——和 `double` **完全一样**。
这是 **macOS arm64 的 ABI 事实**（AAPCS64 里 `long double` == `double`）。
在 x86-64 Linux 上它通常是 16 字节（x87 80 位扩展精度），**本机未实测**，
但足以说明：**`long double` 不是"可移植的更高精度"**，别指望它。

## 二、位模式：把 `0.1f` 拆开看（实测）

```
$ ./fp
0.1f = 0.10000000149   位模式 0x3dcccccd
1.0f = 1               位模式 0x3f800000
-0.0f = -0             位模式 0x80000000
```

```
0x3dcccccd = 0 01111011 10011001100110011001101
             │ │        │
             │ │        └─ 尾数（23 位）→ 1.10011001100110011001101
             │ └────────── 指数（8 位）= 0x7B = 123 → 实际指数 = 123 − 127 = −4
             └──────────── 符号 = 0（正）

值 = 1.6000000238418579 × 2⁻⁴ = 0.10000000149011612
```

**关键**：它**不是 0.1**，是 `0.10000000149011612`。
这就是 [16.02](16.02-舍入误差.md) 里 `0.1 + 0.2 != 0.3` 的物理原因。

对照 `double`（实测位模式）：

```
0.1 = 0.10000000000000000555   0x3fb999999999999a
0.2 = 0.20000000000000001110   0x3fc999999999999a
0.3 = 0.29999999999999998890   0x3fd3333333333333
```

注意 `0x...999a` 结尾的 `a`——**这是四舍五入上来的最后一位**（不是截断）。

## 三、⚠ 实测：`-0.0 == 0.0` 为真，但位模式完全不同

```
-0.0f 位模式 = 0x80000000
-0.0 == 0.0 ? 是   ← ⚠ 相等但位模式不同
```

IEEE-754 规定了**两个零**。`==` 把它们判为相等，但：

- 比较相等时看不出来（`0x00000000` vs `0x80000000`）；
- **按位模式传协议时会传出一个"负零"**；
- `1.0 / -0.0` = `-inf`（符号不同，见 [16.04](16.04-无穷大.md)）。

## 四、裸机的用法：按位模式传浮点，别格式化

协议里传浮点，`printf("%f")` 是最差的选择。
用 union 取位模式，**精确、4 字节、零格式化开销**：

```c
typedef union { float f; uint32_t u; } fbits_t;

void send_float(float v) {
    fbits_t b = { .f = v };
    send_u32_le(b.u);          /* ⚠ 字节序要显式定义 */
}
```

实测 `0.1f` → `0x3dcccccd`，小端下发出去就是 `cd cc cc 3d`。

⚠ **前提**：两端都是 IEEE-754 单精度 + 同样的字节序。
跨平台/跨语言就用 [16.07](16.07-替代方案.md) 的定点整数，别赌这个。

## 五、⚠ 实测：M3 上"浮点"其实是函数调用

交叉编译到 Cortex-M3（`--target=armv7m-none-eabi -mcpu=cortex-m3 -Os`）：

```
$ llvm-nm -u m3.o
         U __aeabi_dadd
         U __aeabi_ddiv
         U __aeabi_dmul
         U __aeabi_fadd
         U __aeabi_fdiv
         U __aeabi_fmul
```

`U` = 未定义符号——**编译器生成的是对库函数的调用，不是几条指令**。
`float` 走 `__aeabi_f*`，`double` 走 `__aeabi_d*`，都来自软浮点库
（libgcc / compiler-rt）。

**同一份代码在 M4F 上的对照**（`-mcpu=cortex-m4 -mfloat-abi=hard -mfpu=fpv4-sp-d16`）：

```
$ llvm-nm -u m4.o
         U __aeabi_dadd      ← ⚠ double 还在
         U __aeabi_ddiv
         U __aeabi_dmul
```

**`float` 的三个 `__aeabi_f*` 全部消失**（变成硬件指令），
但 **`double` 的三个还在**——M4F 只有**单精度** FPU。

反汇编直接证实了这一点：

```
[fmul_add]         [dmul_add]          [fdiv]           [ddiv]
  vmul.f32 s0,s0,s1  bl __aeabi_dmul     vdiv.f32 s0,s0,s1  bl __aeabi_ddiv
  vadd.f32 s0,s0,s2  bl __aeabi_dadd
```

| 芯片 | `float` | `double` |
|---|---|---|
| **M0 / M3** | 软件（`__aeabi_f*`） | 软件（`__aeabi_d*`） |
| **M4F / M7（单精度）** | ✅ **硬件**（`vmul.f32`/`vdiv.f32`） | ⚠ **仍是软件** |

**所以"用 `float` 而不是 `double`"在 M4F 上依然重要。**

## 坑点

| 坑 | 原书怎么说 | 实际是什么（实测） |
|---|---|---|
| `long double` 精度更高 | 一般这么认为 | ⚠ **macOS arm64 上和 `double` 一样**（实测 8 字节，`LDBL_DIG=15`） |
| `float` 存的是十进制 | —— | ❌ 二进制科学计数法；实测 `0.1f = 0.10000000149011612` |
| `-0.0` 不存在 | 一般不提 | ⚠ 存在：`0x80000000`，且 `-0.0 == 0.0` 为真 |
| 有 FPU 就都快 | —— | ⚠ M4F 上 `float` 硬件、**`double` 仍走 `__aeabi_d*`（实测未定义符号仍在）** |
| 浮点指令就几条指令 | —— | ⚠ M3 上是**库函数调用**（`U __aeabi_fmul`） |

## 代码自测

<details>
<summary>Q1：`0.1f` 的位模式 `0x3dcccccd` 里，指数是多少？实际指数是多少？</summary>

`0x3dcccccd` 的二进制（1+8+23）：

```
0 01111011 10011001100110011001101
```

- 符号 = `0`（正）
- 指数字段 = `01111011` = **0x7B = 123**
- **实际指数 = 123 − 127（bias）= −4**

所以值 = `1.10011001100110011001101₂ × 2⁻⁴`
     = `1.6000000238418579 × 0.0625`
     = **0.10000000149011612**

⚠ 注意 IEEE-754 有个**隐含前导 1**：尾数字段存的是小数部分，
真正的尾数是 `1.xxx`。所以 `FLT_MANT_DIG=24`（23 位存的 + 1 位隐含）。
</details>

<details>
<summary>Q2：我想用 `long double` 提高精度，行吗？</summary>

**在本机（macOS arm64）上不行——它就是 `double`。**

实测：

```
sizeof float=4 double=8 long double=8
FLT_DIG=6 DBL_DIG=15 LDBL_DIG=15
```

`long double` 的大小、`LDBL_DIG`、`LDBL` 系列宏全都和 `double` 一致。
这是 AAPCS64 的规定。（x86-64 Linux 上是 16 字节的 x87 扩展精度，
**本机未实测**，但正因如此——**它不可移植**。）

✅ 要更高精度的正确做法：

1. 换算法（Kahan 补偿求和，见 [16.02](16.02-舍入误差.md)）；
2. 用定点数（[16.07](16.07-替代方案.md)）；
3. 真的需要任意精度就上专门的库。
</details>

<details>
<summary>Q3：为什么 M4F 上 `float` 快了，`double` 还是慢？</summary>

因为 **M4F 的 FPU 是单精度的**（`fpv4-sp-d16`，`sp` = single precision）。

实测两套未定义符号对比：

```
M3（-mcpu=cortex-m3）:
    U __aeabi_fadd  U __aeabi_fmul  U __aeabi_fdiv    ← float 也是软件
    U __aeabi_dadd  U __aeabi_dmul  U __aeabi_ddiv

M4F（-mcpu=cortex-m4 -mfloat-abi=hard -mfpu=fpv4-sp-d16）:
    U __aeabi_dadd  U __aeabi_dmul  U __aeabi_ddiv    ← ✅ 只剩 double
```

反汇编里 `float` 版本已经是 `vmul.f32` / `vdiv.f32`，
`double` 版本还是 `bl __aeabi_dmul`。

**结论**：即使在有 FPU 的 M4F 上，
**把 `double` 换成 `float` 仍然是有效的优化**——不是"省内存"，是"从库调用变成硬件指令"。
</details>

<details>
<summary>Q4：把浮点通过串口发出去，传位模式要注意什么？</summary>

三点：

1. **字节序要显式定义**。实测 Cortex-M 是小端，`0x3dcccccd` 在线上是
   `cd cc cc 3d`。用显式拼装的 `send_u32_le()`，
   不要直接 `send_bytes((uint8_t*)&f, 4)`（[ch08](../08-complex-types/README.md)）。
2. **两端都要是 IEEE-754 单精度**。如果对方是别的语言/别的平台，
   改用 [16.07](16.07-替代方案.md) 的定点整数（无歧义）。
3. **`-0.0` 会原样传出去**（实测位模式 `0x80000000`），
   接收方如果用 `== 0.0` 判断没问题，但用位模式判断就要小心。
</details>
