# 16.02 舍入误差

> 书：第 16 章 浮点数 · 16.02 舍入误差（原书 p219+ 区间内）
> 上一篇：[16.01 数字表示](16.01-数字表示.md) ｜ 下一篇：[16.03 精度位数](16.03-精度位数.md)
> 对应实验：主机侧实测（clang 23.1.0 / macOS arm64）

## 书这一节讲什么

一句话：**浮点运算几乎总会丢一点精度，误差会积累、会不对称、还会被顺序放大。**

本篇把三类误差**全部实测出来**：单次比较、重复累加、累加顺序。

## 一、⚠ 实测：`0.1 + 0.2 != 0.3`

```
$ ./fp
0.1 + 0.2 = 0.30000000000000004441   (== 0.3 ? 否)
差值 = 5.5511151231257827021e-17
0.1 = 0.10000000000000000555   位模式 0x3fb999999999999a
0.2 = 0.20000000000000001110   位模式 0x3fc999999999999a
0.3 = 0.29999999999999998890   位模式 0x3fd3333333333333
```

不是 bug，是**二进制无法精确表示十进制的 0.1**：

```
0.1 (十进制) = 0.0001100110011001100110011... (二进制，无限循环)
```

**类比**：十进制里 `1/3 = 0.333...`，`3 × 0.333 = 0.999 ≠ 1`。
同样的道理，只是发生在二进制上。

✅ **正确的比较方式**：

```c
/* ❌ 错 */
if (x == 0.3) { ... }

/* ✅ 对：绝对容差（量级已知） */
if (fabs(x - 0.3) < 1e-9) { ... }

/* ✅ 更好：相对容差（量级变化大） */
static int nearly_eq(double a, double b, double rel) {
    double scale = fabs(a) > fabs(b) ? fabs(a) : fabs(b);
    return fabs(a - b) <= scale * rel;      /* rel 如 1e-9 */
}
```

⚠ **不要用 `FLT_EPSILON` 当万能容差**：实测 `FLT_EPSILON = 1.19209e-07`，
它是"**1.0 附近**的间隔"。在 `1e20` 那里间隔是 `1.6e10`（见 [16.03](16.03-精度位数.md) 的 ULP 表），
绝对容差完全失效。

## 二、⚠ 实测：重复累加，误差会积累

```
float  0.1f 累加 10 次 = 1.0000001192092895508   (== 1.0f ? 否)
double 0.1  累加 10 次 = 0.99999999999999988898   (== 1.0  ? 否)
Kahan  0.1  累加 10 次 = 1                        (== 1.0  ? 是)
```

三个结论：

1. **10 次就对不上了**——哪怕用 `double`；
2. `float` 的偏差是**正向**的（`1.0000001`），`double` 是**负向**的（`0.99999999`）——
   **误差方向不固定，不要靠"偏大/偏小"去补偿**；
3. **Kahan 补偿求和一次就修正回来了**（实测正好 `1`）。

```c
/* Kahan 补偿求和：把"这次丢掉的低位"攒起来下次补上 */
double sum = 0.0, c = 0.0;
for (int i = 0; i < n; i++) {
    double y = x[i] - c;        /* 先减掉上次丢掉的 */
    double t = sum + y;
    c = (t - sum) - y;          /* 这次又丢了什么 */
    sum = t;
}
```

## 三、⚠ 实测：加法顺序会改变结果

```
大数先加: 1e16 + 1000×1 = 10000000000000000     ← ⚠ 1000 全丢了
小数先加: 1000×1 + 1e16 = 10000000000001000     ← ✅ 保住了
```

**同一个和，两种答案，差了 1000。**

原因：`1e16` 附近的间隔（ULP）远大于 1，
所以每次 `+1` 都被舍掉；先把 1000 个 1 加成 1000，一次加进去才留得住。

**工程后果**（裸机场景尤其常见）：

| 场景 | 风险 | 对策 |
|---|---|---|
| 传感器滑动平均 | 累加 N 个采样，误差随 N 增长 | 先减均值再累加，或 Kahan |
| 积分 / PID 的 I 项 | 长时间累积漂移 | 限幅 + 定点数 |
| 大数 + 小量修正 | 小量被吃掉 | **先加小的** |

## 四、⚠ 实测：大数吃小数的临界点

```
1e20 + 1 == 1e20 ? 是
1e16 + 1 == 1e16 ? 是
1e15 + 1 == 1e15 ? 否     ← ⚠ 这里还加得上
DBL_EPSILON 的意义：1.0 + DBL_EPSILON/2 == 1.0 ? 是
```

`double` 有 53 位尾数 ≈ 15~17 位十进制。
`1e15` 的 ULP 还小于 1，`1e16` 的 ULP 就大于 1 了——
所以 `+1` 在 `1e16` 处开始失效。

（对照 [16.03](16.03-精度位数.md) 的 ULP 表：`1e7` 处 `float` 的间隔已经是 **1**，
意味着 `float` 根本没法表示 `10000001`。）

## 五、裸机上的对策

| 对策 | 适用 | 实测依据 |
|---|---|---|
| **① 用整数表示物理量**（`temp_mC`、`volt_mV`） | ✅ 首选 | 完全无误差 |
| **② 定点数 Q16.16** | 需要小数运算 | 见 [16.07](16.07-替代方案.md) |
| **③ Kahan 求和** | 必须浮点的累加 | 实测修正回 `1` |
| **④ 调换累加顺序** | 大数 + 小量 | 实测差 1000 |
| ⑤ 用 `double` 而不是 `float` | 治标 | 只是把误差缩小，不消除 |

⚠ **ISR 里不要做浮点累加**：[ch10](../10-interrupts/README.md) 讲过 ISR 要快，
而浮点在 M3 上是库函数调用（[16.01](16.01-数字表示.md) 实测 `U __aeabi_fmul`）。

## 代码自测

<details>
<summary>Q1：`0.1 + 0.2 != 0.3`，是不是我编译器有问题？</summary>

不是。实测：

```
0.1 + 0.2 = 0.30000000000000004441   (== 0.3 ? 否)
0.1 的位模式 = 0x3fb999999999999a
0.2 的位模式 = 0x3fc999999999999a
0.3 的位模式 = 0x3fd3333333333333
```

三个数都是"最接近的那个可表示值"，
但两个近似值相加的结果 ≠ 第三个近似值。

**正确处理**：

```c
if (fabs(x - 0.3) < 1e-9) { ... }              /* 量级已知 */
if (nearly_eq(x, 0.3, 1e-9)) { ... }           /* 量级未知 */
```

**最彻底的处理**：用整数。嵌入式里 `int32_t temp_mC`（毫摄氏度）
根本没有这个问题。
</details>

<details>
<summary>Q2：累加 1000 个采样值做平均，误差会有多大？怎么减小？</summary>

**会随次数增长，而且顺序会影响结果。** 实测：

```
大数先加: 1e16 + 1000×1 = 10000000000000000     ← 1000 全丢
小数先加: 1000×1 + 1e16 = 10000000000001000     ← 保住
```

三种减小误差的办法，按推荐度：

1. **先减均值再累加**（去掉大数）：`sum += (x[i] - mean0)`；
2. **Kahan 补偿求和**：实测 10 次累加从 `0.99999999999999989` 修正回精确的 `1`；
3. **换成定点/整数**：最彻底。

⚠ 滑动平均还有一个隐藏问题：**窗口里的旧值减不掉**
（浮点减法和加法不对称，会留下残差）。所以滑动平均优先用
**整数累加器 + 移位**（如 16 点平均用 `>>4`），既无误差也更快。
</details>

<details>
<summary>Q3：`FLT_EPSILON` 能不能直接当比较容差用？</summary>

**不能。** 实测 `FLT_EPSILON = 1.192092896e-07`，
它的定义是"**1.0 与下一个可表示 float 的差**"。

而 float 的间隔是**随指数增长**的（[16.03](16.03-精度位数.md) 实测 ULP）：

| 量级 | float ULP |
|---|---|
| 1 | 1.19e-07 |
| 1e6 | 0.0625 |
| **1e7** | **1** |
| 1e9 | 64 |

所以在 `1e7` 附近，两个相邻的 float 相差 **1**——
用 `1e-7` 做容差意味着"要求完全相等"，比较永远失败。

✅ 正确做法：**相对容差**（`fabs(a-b) <= max(|a|,|b|) * rel`），
容差随量级自动缩放。
</details>

<details>
<summary>Q4：裸机上做 PID，积分项用 float 累积会不会出问题？</summary>

会，而且很典型。三个实测过的风险叠加：

1. **误差积累**：`0.1` 累加 10 次就已经不是 1 了（实测 `0.99999999999999989`）；
   I 项每秒累加几十次，几分钟就有可见漂移；
2. **大数吃小数**：I 项变大后，新的小增量被吃掉（实测 `1e16 + 1 == 1e16`），
   表现为"积分饱和后完全不响应"；
3. **速度**：M3 上浮点是 `__aeabi_f*` 库调用（[16.01](16.01-数字表示.md) 实测），
   控制循环有硬实时预算。

✅ 工程做法：

- I 项用 **Q16.16 定点**（[16.07](16.07-替代方案.md)）；
- I 项**限幅**（防积分饱和，顺便避开大数吃小数）；
- 误差用整数表示（`int32_t err_mV`），别用 `float`。
</details>
