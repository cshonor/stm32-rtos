# 00.01 没有操作系统的 C 语言（freestanding）

> 本篇不属于书里任何一章，是读全书之前必须先钉住的前提。
> 下一篇：[00.02 操作硬件的三个手段](00.02-操作硬件的三个手段.md)
> 对应实验：`01-stm32/00-toolchain-clang/`

## 这一节要解决什么

一个问题：**没有操作系统，C 语言靠什么碰到硬件？**

这个问题拆成三小问，正好就是本篇的三块：

1. **标准层面**：没有 OS，C 标准还保证你什么？→ 一、freestanding
2. **编译器层面**：标准库没了，为什么还会冒出 undefined symbol？→ 二、隐式调用
3. **运行时层面**：`main` 之前那一堆准备工作谁干？→ 三、四、crt0 归你

## 一、C 标准的"抽象机器"里根本没有硬件

ISO C 标准只定义两样东西：**抽象机器**（abstract machine）和**可观察行为**
（observable behavior）。"GPIO""Flash""中断向量"这些词，C 标准里一个字都没有。

### 抽象机器是什么意思

C11 §5.1.2.3：标准的全部语义都是对着一台**假想机器**描述的。真实编译器可以
随便优化——重排、合并、删除、内联——**只要可观察行为不变**（即 as-if 规则）。
而可观察行为只有两类：**volatile 对象的访问**和**输入输出**。

推论很关键：**硬件对抽象机器是隐形的。** 编译器看到 `*(u32 *)0x4001100C = 0;`
时，它不知道这个地址后面连着 GPIO，只看到"一次普通的内存写"——
于是它有权把这次写删掉、合并、挪到循环外。所以"用 C 碰到硬件"必须借助
语言里额外的语法手段（`volatile`），那是
[00.02](00.02-操作硬件的三个手段.md) 的事。

### 标准定义的执行环境只有两种

| 环境 | 启动 | 入口函数 | 终止 | 标准库 |
|---|---|---|---|---|
| hosted | OS 加载，crt0 准备环境 | `main`，签名固定 | `main` 返回 / `exit()` 关进程 | 全套保证 |
| **freestanding** | **实现定义**（＝你自己定） | **实现定义**：叫什么、什么签名都行 | 实现定义（通常＝无处可退） | **只保证**一小撮头文件 |

注意 freestanding 那一行的"入口函数"：标准**不要求**它叫 `main`。
本仓库里它还叫 `main`，只是因为我们自己的 `Reset_Handler` 里写了 `main();`
这一行调用——它可以叫任何名字、返回 `void`。hosted 那套
`int main(int argc, char **argv)` 的规则在这里不适用。

### freestanding 保证的头文件只有一小撮

C99 §4p6 明确列出的、freestanding 实现**必须**提供的头只有 7 个：

```
<float.h>  <iso646.h>  <limits.h>  <stdarg.h>  <stdbool.h>  <stddef.h>  <stdint.h>
```

逐个看这 7 个给了你什么：

| 头 | 内容 | 性质 |
|---|---|---|
| `<float.h>` | `FLT_MAX`、`DBL_EPSILON` 等浮点格式常量 | 纯宏 |
| `<limits.h>` | `INT_MAX`、`CHAR_BIT` 等整数范围 | 纯宏 |
| `<stdarg.h>` | `va_list` / `va_start` 变参机制 | 编译器内建 |
| `<stdbool.h>` | `bool` / `true` / `false` | 纯宏 |
| `<stddef.h>` | `size_t`、`NULL`、`offsetof` | 类型 + 宏 |
| `<stdint.h>` | `uint32_t` 等定宽整数类型 | 类型 + 宏 |
| `<iso646.h>` | `and` / `or` 等运算符替代拼写 | 纯宏 |

**共同点：没有一个函数。** 全是常量、类型、宏——所以它们不需要任何
运行时支撑，这正是它们被选进 freestanding 清单的原因。

版本差异：C11/C17 加 `stdalign.h`、`stdnoreturn.h` 变 9 个，C23 加
`stdbit.h` 变 10 个；逐版本对照与"能 include ≠ 标准保证"的本机实测辨析
在 [00.03 二·补](00.03-没有GCC行不行.md)，此处不重复。

**没有 `<stdio.h>`，没有 `<stdlib.h>`，没有 `<string.h>`。**

## 二、标准留的那扇后门

标准允许编译器在 freestanding 下仍然**隐式调用**四个函数：`memcpy` / `memmove` /
`memset` / `memcmp`。你不需要 `#include` 它们，但**必须在某个地方提供实现**。

这不是理论。实测（`01-stm32/00-toolchain-clang`，`make check-libc`）：

```
--- 未定义符号（谁被偷偷调用了）---
U __aeabi_memcpy      ← struct big 整体赋值，编译器替你写了 memcpy 调用
U __aeabi_dadd        ← 浮点乘加，M3 没有 FPU，走软件浮点
U __aeabi_dmul
U __aeabi_ldivmod     ← long long 除法
```

### 谁在偷调：五类"无害"写法

探针在 `libc-trap.c`，每一条都是"看起来人畜无害"的 C 写法：

| 你写的 | 编译器生成的调用 | 为什么 |
|---|---|---|
| `*d = *s;`（64 字节结构体整体赋值） | `__aeabi_memcpy` | 逐字节展开代码体积太大，标准点名允许调 `memcpy` |
| `for` 循环给数组清零 | `memset` | 循环习语识别（loop idiom recognition） |
| `a * b + 1.0`（double） | `__aeabi_dmul` + `__aeabi_dadd` | M3 没有 FPU，浮点全部走软件实现 |
| `a / b`（int） | `__aeabi_idiv` | M3 没有硬件除法指令 |
| `long long` 除法 | `__aeabi_ldivmod` | 64 位除法更要 helper |

⚠️ 这些符号分**两族**，来源不同，别混为一谈：

- **mem 四函数**：语言层面的例外，C 标准点名允许隐式调用；
- **`__aeabi_*` 数学 helper**：ABI 层面（ARM EABI / compiler-rt），跟 libc 无关——
  但 `-nostdlib` 会把 compiler-rt / libgcc 一起摘掉，所以照样 undefined。

### 自己提供实现时的两个坑（`startup.c` 里已经踩过）

1. **名字必须是 `__aeabi_memcpy`**（还有对齐变体 `__aeabi_memcpy4` / `__aeabi_memcpy8`），
   只写 `memcpy` 会链不上——编译器内部生成的调用落在 EABI 名字上。
2. **`__aeabi_memset` 的参数顺序与 `memset` 相反**：
   `__aeabi_memset(dst, n, c)`——n 在前、c 在后。
   照抄 `memset(dst, c, n)` 的签名会得到一个"能链接、但行为全错"的炸弹，
   而且没有任何报错。

`-fno-builtin` 能挡住"循环识别成 `memset`"这类优化，但**挡不住结构体整体赋值**
生成的 `memcpy`——那是语义级的复制，不是库函数识别。所以本仓库的做法是
**两头都做**：`-ffreestanding -fno-builtin` 压编译器，
`startup.c` 里自带 `memset` / `memcpy` / `__aeabi_*` 实现兜底。

一句话记住：**在裸机上，"标准库"不是不存在，而是变成了你的活。**

## 三、少掉的不只是一个库

不是"少了一个库"，是少了一整套**替 C 运行环境做初始化的人**。

Linux 上跑一个 C 程序的真实路径：

```
execve 把 ELF 交给内核
  → 内核 loader 把 PT_LOAD 段映射进地址空间（代码 RX、数据 RW）
  → 内核设置 SP，并把 argc / argv / envp / auxv 按 ABI 摆上栈顶
  → 跳到 _start（crt1.o 里的汇编，来自 libc）
  → __libc_start_main：初始化 libc、设 TLS/errno、跑 .init_array
  → 调 main(argc, argv)
  → main 返回 → exit()：跑 atexit 链表、冲刷 stdio → exit_group 系统调用
```

裸机上，这条链上**除了 `main`，其他每一环都没人做**：

| C 运行环境的前置条件 | Linux/PC | 裸机 STM32 | 谁做 |
|---|---|---|---|
| 栈指针 SP | 内核设 | **向量表第 0 个字**，上电时硬件自动加载 | 硬件 |
| 入口 PC | `_start` | **向量表第 1 个字** → `Reset_Handler` | 硬件 + 你 |
| `.data` 初值搬运 | loader / dynamic linker | 手写循环 | 你 |
| `.bss` 清零 | 内核（新页本来就是 0） | 手写循环 | 你 |
| 堆 | `brk` / `mmap` | 自己划一块 SRAM | 你 |
| `printf` | `write(2)` 系统调用 | UART 寄存器 / ITM / semihosting | 你（ch09） |
| `malloc` | glibc | 自己写 allocator 或全静态分配 | 你 |
| `argc` / `argv` / `environ` | 内核摆上栈 | 不存在，也没人给你 | —— |
| TLS / `errno` | `__libc_start_main` | 没有线程局部存储；要 `errno` 就自己定义一个全局变量 | 你 |
| `atexit` / 析构 | `exit()` 跑链表 | 没有"退出"这回事 | —— |
| 除零 / 访存越界 | SIGFPE / SIGSEGV（内核兜） | **HardFault 向量 → 你的死循环** | 你 |
| 程序退出 | `exit_group` 关进程 | 无处可退，停在原地 | —— |

SP 那一行值得单独展开（这也是 00 章 README 的自测题"为什么栈指针不用你设"）：
Cortex-M 复位时硬件自动做两件事——从 `0x0000_0000`（经 BOOT 引脚别名到
`0x0800_0000`）取**向量表第 0 个字装进 MSP**，取**第 1 个字装进 PC**。
所以只要向量表第 0 个字填对（链接脚本里
`_estack = ORIGIN(RAM) + LENGTH(RAM)`），上电即拥有合法栈，一行代码都不用写。

## 四、实测：那 16 条指令就是"你"那一列

`Reset_Handler` 是上面那张表里"你"那一列的具体实现（真机烧录后的实测反汇编）：

```
8000054: movw r1, #0x124 / movt r1, #0x800   ; _sidata = 0x08000124（Flash）
8000060: movt r2, #0x2000                    ; _sdata  = 0x20000000（RAM）
8000064: ldr  r3, [r1], #4                   ; 搬 .data
8000068: str  r3, [r2], #4
8000070: movw r0, #0x8 / movt r0, #0x2000    ; _ebss
8000074: movw r1, #0x4 / movt r1, #0x2000    ; _sbss
8000088: str  r2, [r1], #4                   ; 清 .bss
8000090: bl   0x800009c <main>
8000094: b    0x8000094                      ; main 不该返回
```

逐段对应回 `startup.c` 的 C 源码：

| 反汇编段 | 干什么 | 对应 C 代码 |
|---|---|---|
| `8000054`–`8000068` | `_sidata` → `_sdata` 逐字搬运 | 第一个 `for`：搬 `.data` |
| `8000070`–`8000088` | `_sbss` → `_ebss` 逐字清 0 | 第二个 `for`：清 `.bss` |
| `8000090` `bl <main>` | 进 `main` | `main();` |
| `8000094` `b .` | 原地死循环兜住 | `for (;;) { }` |

两个必须说清的点：

1. **顺序不能换**：必须先搬 `.data` / 清 `.bss`，再进 `main`。
   反过来的话，`main` 一进去读全局变量，读到的就是 SRAM 上电残留值——
   表现为"有时候对、有时候错"，最难查的那类 Bug。
2. **`main` 真返回了也不会"退出"**：它掉进 `for (;;)`，CPU 空转，功耗照付，
   开了看门狗就被复位。**freestanding 没有"程序结束"这个概念**——
   没有进程可关，没有 `exit_group` 可调。

一个反直觉但准确的结论：**裸机从复位到 `main` 之间的代码，量级等同于
Linux 内核 `start_kernel` 之前那一小段。** 只是内核那段的作者是 Linus，
这里的作者是你，16 行指令。

## 五、这套东西和 HFT / Linux 侧有什么关系

- **隐式 `memcpy` ＝ 热路径上的隐藏成本。** 结构体整体赋值在 M3 上是一次
  `__aeabi_memcpy` 调用，在 x86 服务器上是一次 memcpy + cache line 迁移。
  看到"大结构体按值传参/赋值"就该条件反射地问：**这背后是谁在拷贝？拷多少？**
- **除法和浮点要花钱，裸机上直接看得见。** M3 上 `a / b` 是一次函数调用
  （几十周期起步）；服务器上整数除法同样是几十周期的微码序列，浮点除法更贵。
  HFT 代码"热路径避免除法/浮点"的纪律，追到底就是上面那张 undefined symbol 表。
- **每一层抽象都有人付费。** hosted 环境里 loader / libc / 内核替你做的那串事，
  在裸机上全部显形为你要亲手写的 16 条指令。追问"这一行代码背后谁在干活"——
  这个习惯从 crt0 一路通到内核 syscall、驱动、kernel bypass。
- **同一个问题的三层**：裸机复位 → `main` ≈ Linux `_start` → `main` ≈
  内核 head.S → `start_kernel`。三层的本质是一句话：
  **C 运行环境不会自己长出来。**

## 坑点（常识怎么说 / 实测是什么）

| 常识怎么说 | 实测是什么 |
|---|---|
| "freestanding 就是什么头文件都不能用" | 7 个头（C11 起 9 个）照用——它们只有常量/类型/宏，没有函数，不需要运行时 |
| "我自己写了 `memcpy` 就万事大吉" | 编译器叫的是 `__aeabi_memcpy`（含 4/8 对齐变体），只写 `memcpy` 链不上；且 `__aeabi_memset(dst, n, c)` 参数顺序与 `memset` **相反** |
| "加了 `-fno-builtin` 就不会有隐式调用" | 结构体整体赋值仍可能生成 `memcpy`（语义级复制）；`__aeabi_idiv` 这类 ABI helper 与 builtin 开关无关 |
| "`main` 是程序第一个运行的函数" | `Reset_Handler` 才是（向量表第 1 个字）。`main` 只是你 crt0 里的一次普通调用 |
| "程序跑完会自动退出" | 无处可退。`main` 返回后必须自己兜住（`for(;;)`），否则 PC 跑进不知道哪片内存 |

## 代码自测

<details>
<summary>Q1：<code>-ffreestanding</code> 和 <code>-nostdlib</code> 有什么区别？只加一个行不行？</summary>

两者管的对象不同，**要一起加**：

- `-ffreestanding`：告诉**编译器前端/中端**"这里没有宿主环境"。影响的是语义判断
  （比如 `main` 不特殊对待、不假定有 `exit`、允许 `__builtin` 走裸实现）。
  它**不阻止**你去链接 libc。
- `-nostdlib`：告诉**链接器**别自动带上 `crt0.o`、`libc`、`libgcc`。

只加 `-ffreestanding`：语义对了，但链接器还是会拉 libc，最后得到一个
"看起来能跑但依赖一堆你不知道的东西"的镜像。
只加 `-nostdlib`：链接干净了，但编译器仍按 hosted 规则优化，可能生成你不期望的调用。

⚠️ 加 `-nostdlib` 之后连 `libgcc`/`compiler-rt` 都没了，`long long` 除法、
软件浮点这些 helper 要自己提供（上面 `__aeabi_ldivmod` 就是被这个逼出来的）。
</details>

<details>
<summary>Q2：为什么 <code>.bss</code> 要清零，而 <code>.data</code> 要搬运？不能都放 Flash 里省事吗？</summary>

因为 **Flash 是只读的、RAM 是可写的**，而 C 语言对两类变量承诺了不同的语义：

| 段 | C 语义 | 放哪里 | 上电后 |
|---|---|---|---|
| `.data` | 有初值的全局/静态变量，**可写** | 初值存 Flash，变量本体在 RAM | 搬运一次 |
| `.bss` | 无初值的全局/静态变量，**初值 = 0** | 不占 Flash，只在 RAM 里占地址 | 清零 |

如果 `.data` 直接放 Flash，你写它就会失败（NOR Flash 写入要先擦整页，见 ch02 Q4）。
如果 `.bss` 不占 Flash 也不清零，main 里第一个读到全局变量的语句就会读到
**SRAM 上电残留值**——表现是"有时候对、有时候错"，最难查的那类 Bug。
</details>

<details>
<summary>Q3：既然 freestanding 只有 7 个头，我 <code>#include &lt;stdio.h&gt;</code> 为什么不一定报错？</summary>

因为报不报错取决于**实现提供了什么**，不取决于标准要求什么。

clang 在你的 SDK 路径下（比如 `--sysroot` 指向 arm-none-eabi 的 newlib）确实能找到
`<stdio.h>` 文件，于是编译通过——然后在**链接**阶段倒在
`undefined reference to 'printf'`。

裸机开发的典型痛点就在这：错误在链接期才暴露，而不是编译期。
所以本仓库的做法是 `-ffreestanding -fno-builtin -nostdlib`，
**宁可编译期就缺，也不要链接期才发现。**
</details>

<details>
<summary>Q4：freestanding 下 <code>main</code> 必须叫 <code>main</code>、必须是 <code>int main(void)</code> 吗？</summary>

**都不必须。** 标准对 freestanding 的入口只说"以实现定义的方式确定"——
叫什么、什么签名、返回什么，全由实现（＝你自己）定。

本仓库的真实入口是 `Reset_Handler`（链接脚本 `ENTRY(Reset_Handler)` +
向量表第 1 个字），`main` 只是 `Reset_Handler` 里的一行普通调用。
它可以改名叫 `app_main`、返回 `void`、不带参数，完全合法。

hosted 那套"`main` 必须是 `int main(int, char**)` 或 `int main(void)`，
`return 0` 即 `exit(0)`"的规则，在 freestanding 下整条不适用——
因为根本没有"退出状态给谁"这个问题。
</details>

<details>
<summary>Q5：向量表第 0 个字为什么不放"第一条指令的地址"，而是放栈顶地址？</summary>

因为 Cortex-M 的设计哲学是：**先能调用函数，才谈得上执行程序。**

C 函数一进来就要 `push` 寄存器、开栈帧——**没有合法 SP，第一条 C 代码都跑不了**。
所以硬件复位时一次性解决两个前置条件：向量表第 0 个字装进 MSP（栈顶），
第 1 个字装进 PC（复位入口）。`Reset_Handler` 第一行就是 C，靠的就是这个设计。

对照 x86：复位后直接跳到 `0xFFFFFFF0` 取指令，栈要引导代码自己设——
所以 x86 的 BIOS/bootloader 开头都是汇编。Cortex-M 把"设 SP"这步硬化了，
**启动代码才能纯 C 写**（本仓库 `startup.c` 就是证明，一行汇编都没有）。
</details>
