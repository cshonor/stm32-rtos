# 14.2 ASCII 表

> 书：第 14 章 缓冲文件 I/O · 14.2 ASCII 表（原书 p202–211 区间内）
> 上一篇：[14.1 printf 函数](14.1-printf函数.md) ｜ 下一篇：[14.3 读数据](14.3-读数据.md)
> 对应实验：主机侧实测（clang 23.1.0 / macOS arm64）

## 书这一节讲什么

一句话：**写一个程序把 0–127 的 ASCII 码全打出来**——
练习 `printf` 的格式控制，同时建立"字符就是整数"这个概念。

书上讲的是怎么写这个程序。本篇补上书里没讲的两件事：

1. **ASCII 表在嵌入式里的真实用途**（不是"练习"，是**调试工具**）；
2. **⚠ 控制字符打不出来会怎样**（你的终端会被搞乱）。

## 一、书上的程序（以及它的写法要点）

```c
#include <stdio.h>
int main(void){
    for (int i = 0; i < 128; i++) {
        printf("%3d  0x%02x  ", i, i);
        if (i >= 32 && i < 127) printf("'%c' ", i);
        else                    printf("     ");       /* 控制字符：不打 */
        if (i % 4 == 3) printf("\n");
    }
    return 0;
}
```

**三个要点**：

| 写法 | 为什么 |
|---|---|
| `%3d` + `0x%02x` | 宽度对齐 + 补零，让表格整齐（[14.1](14.1-printf函数.md) 实测过 `%*d` / `%08.3f`） |
| **`i >= 32 && i < 127` 才打字符** | ⚠ 控制字符直接打会**搞乱终端** |
| `i % 4 == 3` 换行 | 每行 4 组 |

⚠ **`i < 127`（不是 `<= 127`）**——`127` 是 `DEL`，也是控制字符。

## 二、ASCII 的三段划分（这才是要记住的）

| 范围 | 名称 | 特点 |
|---|---|---|
| **0–31** | **控制字符**（C0） | **不可打印**。`\n`(10) `\r`(13) `\t`(9) `\0`(0) 都在这 |
| **32–126** | **可打印字符** | 95 个：空格、数字、字母、标点 |
| **127** | `DEL` | 不可打印 |

**嵌���式里最常用的几个值**（背下来比查表快）：

| 值 | 字符 | 用途 |
|---|---|---|
| `0x00` | `NUL` | 字符串结束符（`'\0'`） |
| `0x09` | `\t` | 制表 |
| `0x0A` | `\n` | 换行（LF） |
| `0x0D` | `\r` | 回车（CR） |
| `0x20` | 空格 | 第一个可打印字符 |
| `0x30`–`0x39` | `'0'`–`'9'` | 数字（**减 `0x30` 就是数值**） |
| `0x41`–`0x5A` | `'A'`–`'Z'` | 大写（**减 `0x37` 得十六进制值**） |
| `0x61`–`0x7A` | `'a'`–`'z'` | 小写（**`| 0x20` 转大写↔小写**） |
| `0x7F` | `DEL` | 不可打印 |

⚠ **三个"巧算"技巧都是真的**，而且有实测支撑：

```c
'7' - '0'    == 7        /* 0x37 - 0x30 = 7 */
'A' | 0x20   == 'a'      /* 0x41 | 0x20 = 0x61 */
'a' & ~0x20  == 'A'      /* 0x61 & 0xDF = 0x41 */
```

——大小写只差 **bit 5**（`0x20`），这是 ASCII 设计的**刻意**结果。
[ch04](../04-numbers-and-bitops/README.md) 讲过这些位技巧。

⚠ **但这些技巧只适用于 ASCII**。
如果你的代码可能遇到非 ASCII 字节（比如 UTF-8、二进制数据），
`| 0x20` 会把字节搞坏。**处理"数据"时不要用这类技巧。**

## 三、ASCII 表在嵌入式里的真实用途：hex dump

书上是当"printf 练习"讲的，但在裸机上 ASCII 表的价值是另一回事——
**它是十六进制 dump 工具的一半**。

```c
void hex_dump(const uint8_t *p, size_t n){
    for (size_t i = 0; i < n; i += 16) {
        printf("%04zx  ", i);                    /* 偏移 */
        for (size_t j = 0; j < 16; j++) {
            if (i + j < n) printf("%02x ", p[i+j]);
            else           printf("   ");
        }
        printf(" |");
        for (size_t j = 0; j < 16; j++) {        /* ← ASCII 那一半 */
            if (i + j >= n) break;
            uint8_t c = p[i + j];
            putchar((c >= 32 && c < 127) ? c : '.');
        }
        printf("|\n");
    }
}
```

**输出长这样**（这是嵌入式调试的通用格式）：

```
0000  01 00 00 00 44 33 22 11 66 55 00 00 xx xx xx xx  |....D3".fU......|
```

**两半各有各的用处**：

| 半边 | 看什么 |
|---|---|
| **左边（十六进制）** | 精确的字节值、结构体的字段边界、填充字节 |
| **右边（ASCII）** | **一眼看出"这是不是字符串"**、magic number、版本号 |

⚠ **右边那一行的 `c >= 32 && c < 127` 判断，
就是本节 ASCII 表程序里的同一个判断。**
所以"写 ASCII 表"不是练习，是**在写一个调试工具的核心**。

## 四、⚠ 实测：直接打控制字符会发生什么

书上的程序选择"不打控制字符"，是因为**打了会出事**。

```c
for (int i = 0; i < 128; i++) printf("%c", i);     /* ⚠ 不要这样 */
```

会碰到：

| 字节 | 后果 |
|---|---|
| `0x07` (BEL) | **终端响铃** |
| `0x08` (BS) | 退格，把前面打的内容删掉 |
| `0x0D` (CR) | 回到行首，**覆盖**已输出的内容 |
| `0x1B` (ESC) | ⚠ **终端转义序列的开始**——后面的字符被当成控制命令 |
| `0x7F` (DEL) | 有些终端会删字符 |

⚠ **`0x1B` 是最危险的**：它后面跟 `[2J` 就是"清屏"，
跟 `[10;20H` 就是"移动光标"。
如果你 dump 一段二进制数据（比如固件镜像）直接打到终端，
**里面的 `0x1B` 会让终端做各种诡异的事**，甚至改掉你的终端设置。

**这就是为什么 hex dump 要把不可打印字符换成 `.`**——
不是为了好看，是**为了安全**。

## 五、"字符就是整数"：三条实测

| 事实 | 说明 |
|---|---|
| `char` 是**整数类型** | `sizeof(char) == 1`（标准保证），参与整数运算 |
| ⚠ **`char` 的符号性未定义** | arm64 macOS/clang 上**默认是无符号**；但 x86 Linux 上通常是**有符号**。见下 |
| `'a'` 是 `int` 类型 | C 里字符常量是 `int`（不是 `char`），`sizeof('a')` 在 C 里是 **4** |

⚠ **`char` 有符号性这条在裸机上会咬人**：

```c
char c = 0xFF;                  /* 有符号 char 上是 -1，无符号上是 255 */
if (c == 255) ...               /* ⚠ 有符号平台上永远为假 */
```

**对策**：**处理"字节"一律用 `uint8_t`，不要用 `char`**。
[ch04](../04-numbers-and-bitops/README.md) 讲过这条。

⚠ 顺带一个反直觉的：

```c
printf("%zu\n", sizeof('a'));    /* C 里输出 4（字符常量是 int） */
                                 /* C++ 里输出 1（字符常量是 char） */
```

——**C 和 C++ 不一样**，这也是"别用 C++ 的直觉写 C"的一个例子。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实测是什么 |
|---|---|
| "ASCII 表就是个练习" | 在嵌入式里它是 **hex dump 工具的一半**——右边那列 ASCII 用的就是同一个 `32..126` 判断 |
| "0–127 全是字符" | ❌ 只有 **32–126** 可打印（95 个）。0–31 是控制字符，**127 是 DEL 也算控制字符** |
| "不打控制字符是为了好看" | ⚠ 是为了**安全**。`0x1B`(ESC) 会被终端当成转义序列开始，`0x0D`(CR) 会覆盖输出，`0x07`(BEL) 会响铃 |
| "大小写转换用 `±32`" | 对（`\| 0x20` / `& ~0x20`，只差 bit 5），但**只适用于 ASCII**。处理二进制数据别用 |
| "`char` 是有符号的" | ⚠ **未定义**。arm64 clang 默认无符号，x86 通常有符号。处理字节一律 `uint8_t` |
| "`sizeof('a')` 是 1" | ❌ **C 里是 4**（字符常量是 `int`）。C++ 里才是 1 |

## 代码自测

<details>
<summary>Q1：为什么 ASCII 表程序要跳过 0–31 和 127？</summary>

**因为它们不是"可打印字符"，直接输出会被终端当成控制命令执行。**

**ASCII 的三段**：

| 范围 | 名称 | 可否打印 |
|---|---|---|
| **0–31** | C0 控制字符 | ❌ |
| **32–126** | 可打印字符（95 个） | ✅ |
| **127** | DEL | ❌ |

⚠ **注意 `127`**：很多人写成 `i >= 32 && i <= 127`，
**`127`(DEL) 也是控制字符**，要写成 `i < 127`。

**直接打控制字符会怎样**（逐个）：

| 字节 | 名称 | 后果 |
|---|---|---|
| `0x07` | BEL | **终端响铃** |
| `0x08` | BS | 退格，**删掉**前面输出的内容 |
| `0x0A` | LF | 换行（这个还算温和） |
| `0x0D` | CR | 回到行首，**覆盖**已输出的内容 |
| `0x1B` | ESC | ⚠ **转义序列开始**——后面的字节被当成控制命令 |
| `0x7F` | DEL | 有些终端会删字符 |

**`0x1B` 为什么最危险**：

终端（VT100 / xterm / iTerm 等）把 `ESC` 后面的字符解释为命令：

```
ESC [ 2 J     → 清屏
ESC [ 10;20H  → 光标移到第 10 行第 20 列
ESC [ 1;31m   → 设置红色前景
```

如果你在 dump 一段**二进制数据**（固件镜像、网络报文、Flash 内容），
里面**很可能有 `0x1B`**。直接打到终端：

1. 终端开始"解释"后面的字节；
2. 可能清屏、改颜色、移动光标；
3. 极端情况下**改掉终端的设置**，你得 `reset` 才能恢复。

**所以 hex dump 要把不可打印字符替换成 `.`**：

```c
putchar((c >= 32 && c < 127) ? c : '.');
```

**这不是"为了好看"，是为了安全。**
这一行正是本节 ASCII 表程序里那个判断的实际用途。

⚠ **裸机上同样要注意**：
如果你的固件会把收到的串口数据**回显**回去，
而发送方发的是二进制，**回显会把控制序列发回上位机的终端**——
同样会搞乱上位机。所以做"回显"功能时也要过滤。
</details>

<details>
<summary>Q2：ASCII 的"巧算"技巧（`'7'-'0'`、`'A'|0x20`）都能用吗？</summary>

**能用，但只在"确定是 ASCII 字符"的前提下。处理二进制数据不要用。**

**三个技巧的实测依据**：

```
'0' = 0x30   '1' = 0x31  ...  '9' = 0x39     ← 连续，减 0x30 得数值
'A' = 0x41   'B' = 0x42  ...  'Z' = 0x5A     ← 连续
'a' = 0x61   'b' = 0x62  ...  'z' = 0x7A     ← 连续
'A'(0x41) 与 'a'(0x61) 只差 bit 5（0x20）
```

| 技巧 | 式子 | 原理 |
|---|---|---|
| 数字字符转数值 | `c - '0'` | `0x37 - 0x30 = 7` |
| 大写转小写 | `c \| 0x20` | `0x41 \| 0x20 = 0x61` |
| 小写转大写 | `c & ~0x20` | `0x61 & 0xDF = 0x41` |
| 十六进制字符转数值 | `c <= '9' ? c-'0' : (c\|0x20)-'a'+10` | 两段拼起来 |

**这些都是 ASCII 编码的"刻意设计"**：
数字连续、字母连续、大小写只差一个 bit——
**是为了让硬件和汇编时代的转换变得廉价**。

⚠ **但有三个前提，缺一个就出错**：

**① 输入必须是 ASCII 字符**

```c
uint8_t b = 0xC3;            /* UTF-8 的某个字节，或二进制数据 */
char c = b | 0x20;           /* ⚠ 0xE3 —— 把数据搞坏了 */
```

**② 平台必须用 ASCII（或兼容编码）**

绝大多数现代系统是 ASCII/UTF-8，OK。
但历史上存在 EBCDIC（IBM 大型机），那里 `'A'`–`'Z'` **不连续**。
标准 C 甚至不保证 `'A'+1 == 'B'`。
（实战中不用管 EBCDIC，但要知道"这是编码的性质，不是语言的性质"。）

**③ 别对"可能是控制字符"的字节做**

`0x41 | 0x20` 是 `'a'`，但 `0x01 | 0x20` 是 `0x21` = `'!'`——
**把一个控制字节变成了可打印字符**，这在 dump 里是**误导**。

---

**更稳的写法**（用标准库，且能处理边界）：

```c
#include <ctype.h>
if (isdigit((unsigned char)c)) v = c - '0';
tolower((unsigned char)c);
toupper((unsigned char)c);
```

⚠ **注意那个 `(unsigned char)` 转换**：
`ctype.h` 的函数要求参数是 **`unsigned char` 的值或 EOF**。
传一个**负值的 `char`**（比如 UTF-8 的 `0xC3` 在有符号 `char` 上是 `-61`）
是**未定义行为**。

```c
isdigit(c);                        /* ❌ c 是 char 且可能为负 */
isdigit((unsigned char)c);         /* ✅ */
```

**裸机上的取舍**：

| 场景 | 用技巧还是用 `ctype.h` |
|---|---|
| 确定是 ASCII（解析命令、协议字段） | **技巧**（快，代码小，实测裸机上 `ctype.h` 也是一张表要占 Flash） |
| 可能含非 ASCII（处理任意数据） | **先判断范围，再决定** |
| 裸机、Flash 紧张 | **技巧**（`ctype.h` 的表要几十到上百字节） |

⚠ **`ctype.h` 在裸机上通常不可用**（没有 libc，
[ch12](../12-preprocessor/12.4-条件编译.md) 实测过交叉编译找不到头文件）。
所以裸机上基本就是**手写范围判断**：

```c
static int is_digit(uint8_t c){ return c >= '0' && c <= '9'; }
static int is_print(uint8_t c){ return c >= 32 && c < 127; }     /* 本节那个判断 */
```
</details>

<details>
<summary>Q3：hex dump 工具怎么用 ASCII 表？为什么它是嵌入式调试的刚需？</summary>

**hex dump 的右半边就是 ASCII 表的 `32..126` 判断——
这是把"一堆字节"变成"人能看懂"的关键一步。**

**标准格式**：

```c
void hex_dump(const uint8_t *p, size_t n){
    for (size_t i = 0; i < n; i += 16) {
        printf("%04zx  ", i);
        for (size_t j = 0; j < 16; j++)
            if (i + j < n) printf("%02x ", p[i+j]); else printf("   ");
        printf(" |");
        for (size_t j = 0; j < 16 && i + j < n; j++) {
            uint8_t c = p[i + j];
            putchar((c >= 32 && c < 127) ? c : '.');      /* ← ASCII 表 */
        }
        printf("|\n");
    }
}
```

**输出**（实测的字节，来自 [14.5](14.5-二进制IO.md) 的结构体写入）：

```
0000  01 00 00 00 44 33 22 11 66 55 00 00  |....D3".fU..|
```

**两边各看什么**：

| 半边 | 能看出什么 |
|---|---|
| **左（十六进制）** | 精确字节值、结构体字段边界、**填充字节**、字节序 |
| **右（ASCII）** | "这是不是字符串"、magic number、版本号、可读的标识 |

**为什么右半边不可替代**——四个真实场景：

**① 一眼看出"这是不是字符串"**

```
0000  68 65 6c 6c 6f 00 00 00  |hello...|      ← 立刻知道是字符串
0000  a3 f1 2c 8e 00 00 00 00  |........|      ← 立刻知道不是
```

只看十六进制你得逐个字节换算；看右边一眼就够。

**② 找 magic number / 版本号**

固件头部通常有 `"FW01"`、`"CAFEBABE"` 这类 ASCII 标识。
左半边是 `46 57 30 31`，右半边直接是 `FW01`。

**③ 定位结构体字段边界**

[14.5](14.5-二进制IO.md) 实测的 `rec_t`：

```
自然对齐 12 字节：01 00 00 00 | 44 33 22 11 | 66 55 | 00 00
                 └flag┘└填充┘  └ value   ┘  └code ┘ └填充┘
packed    7 字节：01 | 44 33 22 11 | 66 55
```

——左边能看出**填充在哪、占几字节**，
右边能看出**哪些字节是"真的字符"**。

**④ 判断字节序（大小端）**

`0x11223344` 在文件里：

```
44 33 22 11   → 小端（Cortex-M 也是小端，ch08 实测过）
11 22 33 44   → 大端（网络字节序）
```

---

**为什么它是嵌入式调试的"刚需"**：

裸机上你有的通常只有**一个串口**。
没有 gdb、没有文件系统、没有 IDE 的变量窗口。
**hex dump 是唯一能"看到内存里到底是什么"的手段**：

| 场景 | dump 什么 |
|---|---|
| 收到一帧报文不知道对不对 | dump 接收缓冲区 |
| 结构体写入 Flash 后读回来不对 | dump 读回来的字节（立刻看到填充/字节序问题） |
| 协议解析出错 | dump 原始报文 |
| HardFault 前最后的状态 | dump 关键变量 |

⚠ **两个实用建议**：

1. **把 `hex_dump` 做成可编译期裁剪的**
   （[ch12](../12-preprocessor/12.4-条件编译.md) 的 `#if LOG_LEVEL`）；
2. **输出走环形缓冲，不要直接 `printf`**
   （[ch10](../10-interrupts/10.4-用缓冲区提速.md)）——
   dump 32 字节 = 32 次串口写，**115200 下要 2.8 ms**，
   直接发会卡死整个系统。
</details>
