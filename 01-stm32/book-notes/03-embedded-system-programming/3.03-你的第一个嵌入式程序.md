## 3.3.1 初始化硬件：第一件事永远是开时钟

STM32 上电后，**所有外设的时钟默认是关闭的**（省电）。所以哪怕你把 GPIO 配置寄存器
写对了，只要时钟没开：

- 写 `GPIOA_CRL` → **写了不生效**
- 读 `GPIOA_ODR` → 读到 0
- **没有任何报错、没有警告、没有 HardFault**

### 实测：复位后是 0，写一行变成 4

```console
# 复位后（还没跑我们的程序时）halt 读：
0x40021018: 00000000          ← RCC_APB2ENR，全 0，GPIOA 时钟是关的

# 程序跑起来后：
0x40021018: 00000004          ← bit2 (IOPAEN) 被置起来了
```

### 实测：不开时钟时读写寄存器会怎样

这是"必须先开时钟"这个说法背后真正需要知道的事。
实验：程序只开 GPIOA 时钟，然后在**没开 GPIOC 时钟**的情况下读它、写它
（探针程序 `portprobe.c`，完整输出见实验 README §5）：

| 操作 | 时钟关时 | 开时钟后 | 结论 |
|---|---|---|---|
| 读 `GPIOC_CRL` | `0x44444444` | `0x44444444` | **配置寄存器能读到复位值** |
| 读 `GPIOC_IDR` | `0x00000000` | `0x0000fffe` | **状态寄存器读不到**（IDR 的值来自引脚采样，采样要时钟） |
| 写 `GPIOC_ODR = 0xA5A5A5A5`，立刻读回 | `0x00000000` | — | **写丢失** |
| 开时钟后再读 `GPIOC_ODR` | — | `0x00000000` | **那个写确实没进寄存器，不是"暂时读不到"** |
| 程序有没有崩？ | `stage = 13`，13 步全跑完 | — | **没有 HardFault，静默失败** |

三条结论：

1. **写会静默丢失**。这就是"灯不亮，代码看起来完全正确"的第一号成因。
2. **读的后果分两类**：配置类寄存器（CRL/CRH）能读到复位值；
   状态类寄存器（IDR）读到 0。机制上可以理解为存储单元仍可读、
   但采样逻辑需要时钟（**机制是推断，行为是实测的**）。
3. ⚠ **这个行为是 F1 的，别外推到别的系列**。F4/L4 等系列对未使能时钟的外设访问
   会产生**总线错误（BusFault）**。判断方法永远是查该系列的参考手册 + 实测。

```c
/* 唯一的写法 */
#define RCC_APB2ENR (*(volatile uint32_t *)0x40021018u)
#define RCC_IOPAEN  (1u << 2)

RCC_APB2ENR |= RCC_IOPAEN;
```

反汇编（实测，3 条指令）：

```asm
movw  r1, #0x1018
movt  r1, #0x4002        ; r1 = 0x40021018
ldr   r3, [r1]           ; ┐
orr   r3, r3, #0x4       ; │ 读-改-写
str   r3, [r1]           ; ┘
```

## 3.3.2 GPIO 引脚编程：把 PA5 配成输出

F1 的引脚配置不在"每引脚一个寄存器"里，而是**挤在 CRL/CRH 两个 32 位寄存器里，
每个引脚占 4 位**：

```
GPIOA_CRL  管 PA0–PA7        GPIOA_CRH  管 PA8–PA15
每 4 位: [CNF1 CNF0 MODE1 MODE0]
```

所以 PA5（第 5 个引脚）占 `CRL` 的 **bits[23:20]**（5 × 4 = 20）。

```c
#define LED_PIN   5u

GPIOA_CRL &= ~(0xFu << (LED_PIN * 4u));   /* 先清 PA5 的 4 位 */
GPIOA_CRL |=  (0x2u << (LED_PIN * 4u));   /* CNF=00, MODE=10 → 2MHz 通用推挽输出 */
```

| 值 | CNF | MODE | 含义 |
|---|---|---|---|
| `0x0` | 00 | 00 | 模拟输入（**复位默认**） |
| `0x4` | 01 | 00 | 浮空输入 |
| `0x8` | 10 | 00 | 上/下拉输入（上还是下由 ODR 对应位决定） |
| `0x1` | 00 | 01 | 通用推挽输出，10 MHz |
| `0x2` | 00 | 10 | 通用推挽输出，2 MHz ← **本实验用这个** |
| `0x3` | 00 | 11 | 通用推挽输出，50 MHz |
| `0xB` | 10 | 11 | 复用推挽输出 50 MHz（UART 的 TX 用这个） |

### 为什么必须"先清后置"——一个寄存器管 8 个引脚

**这是 F1 布局最值得体会的一点。** 如果你图省事写成：

```c
GPIOA_CRL = 0x00200000;      /* ❌ 只想配 PA5 */
```

那 PA0–PA4、PA6、PA7 的配置会被**一起写成 `0000`（模拟输入）**。
等于把别人的配置抹了。实测反汇编（6 条指令、2 次 ldr + 2 次 str）：

```asm
ldr   r1, [r0]           ; ┐
bic   r1, r1, #0xf00000  ; │ 清 PA5 的 4 位（&= ~）
str   r1, [r0]           ; ┘
ldr   r3, [r0]           ; ┐
orr   r3, r3, #0x200000  ; │ 置（|= 0x2 << 20）
str   r3, [r0]           ; ┘
```

**这 6 条指令里，`ldr` 和 `str` 之间是可以被中断打断的** —— 如果 ISR 也改了同一个
`CRL` 的另一个引脚，你的第二次 `str` 会把它的修改覆盖回去。
这就是"读-改-写不原子"的原始形态（ch10 会再咬回来一次）。

> **F0/F4 用 `MODER`（每引脚 2 位）**，虽然也是位打包，但一个寄存器只放 16 个引脚，
> 而且有独立的 `OTYPER`/`OSPEEDR`/`PUPDR` 分担，所以"清+置"的位宽小一些。
> 书里用的是 F0，看到的是 2 位布局 —— 原理相同，位宽不同。

### 实测：配置生效了

```console
# 复位后没人碰过的端口（GPIOC / GPIOD）：
0x40011000: 44444444         ← GPIOC_CRL 复位值 = 0x44444444（每脚 0b0100 = 浮空输入）

# 我们配过 PA5 的 GPIOA：
0x40010800: 44244444         ← PA5 那 4 位从 4 变成 2 ✅
             ↑
             第 6 个十六进制位 = bits[23:20]
```

程序里也存了一份：`crl_after_config = 0x44244444`，与真机读回一致。

## 3.3.3 切换 LED：为什么必须用 BSRR

### 三种写法，三种指令数（实测反汇编）

```c
/* ① 读-改-写：3 条指令，中间可被中断 */
GPIOA_ODR ^= (1u << 5);
```

```asm
ldr   r1, [r0]           ; 读 ODR
eor   r1, r1, #0x20      ; 改
str   r1, [r0]           ; 写回
```

```c
/* ② BSRR：1 条 str，物理上不可能碰别人的位 */
GPIOA_BSRR = (1u << 5);          /* 置位 PA5 */
GPIOA_BSRR = (1u << (5u + 16u)); /* 复位 PA5 */
```

```asm
str.w r12, [r0, #0x10]   ; ★ 就这一条。没有 ldr
```

```c
/* ③ BRR：BSRR 高 16 位的"专用版"，同样只写 */
GPIOA_BRR = (1u << 5);           /* 复位 PA5 */
```

**`BSRR` 是硬件给"读-改-写不原子"的补偿**：写低 16 位的某位 = 置位对应引脚；
写高 16 位的某位 = 复位对应引脚；**写 0 的位完全不影响**。
所以在硬件层面，一次 `str` 就是原子的"只改我关心的那一位"。

### 实测：LED 真的在闪（证据链）

**第一步：程序在跑的时候 halt，读回状态**

```console
0x40010800: 44244444 88844444 0000dffc 0000a020 00000000 00000000
             ↑CRL     ↑CRH     ↑IDR     ↑ODR     ↑BSRR    ↑BRR
```

程序里的观测点：

| 变量 | 值 | 结论 |
|---|---|---|
| `odr_after_set` | `0x0000a020` | 写 `BSRR=1<<5` 后读 ODR，**bit5 = 1 → LED 亮** |
| `odr_after_reset` | `0x0000a000` | 写 `BSRR=1<<21` 后读 ODR，**bit5 = 0 → LED 灭** |
| `blink_count` | `0x1d` = 29 | 从复位到这一刻翻转了 29 次 |

**注意这两个值的差**：`0x0000a020 ^ 0x0000a000 = 0x00000020` —— **只差 bit5**。
这就是"BSRR 只动我关心的那一位、不碰 PA13/PA15 上拉"的硬证据。

**第二步：让它自由跑 3 秒，看计数器涨不涨**

```console
=== T1 ===   blink_count = 0x37 (55)    ODR = 0x0000a020  (bit5=1，亮)
=== 自由跑 3000 ms ===
=== T2 ===   blink_count = 0x3e (62)    ODR = 0x0000a000  (bit5=0，灭)
```

`62 - 55 = 7` 次翻转 / 约 3 秒 → **半周期约 428 ms，完整闪烁约 1.17 Hz**。

**第三步：调试器直接写寄存器（一行 C 代码都不跑）**

```console
> mww 0x40010810 0x20        # 写 BSRR：置位 PA5
0x4001080c: 0000a020         # ODR bit5 立刻 = 1（LED 亮，肉眼可见）
> mww 0x40010814 0x20        # 写 BRR：复位 PA5
0x4001080c: 0000a000         # ODR bit5 立刻 = 0（LED 灭）
```

**这三步合起来的意义**：把"寄存器 ↔ 物理现象"直接连起来了。
灯不亮的时候，你可以先用 `mww` 验证"寄存器写进去灯会不会亮"，
从而**把问题切成"硬件/配置"和"代码逻辑"两半**——这是嵌入式排障里非常实用的手法。

### 关于极性：PA5 是高电平点亮

实测：ODR bit5 = 1 时 LED 亮。所以 NUCLEO-F103RB 的 LD2 是 `PA5 → LED → 电阻 → GND`。

**这件事不能类推**：不同板子接线不同，有的板子是引脚拉低才亮。
新拿一块板子，第一件事就是实测极性（`mww` 打一下最快）。

## 3.3.4 构建完成的程序

```console
$ make
blink_gpio.elf  :
section                   size        addr
.isr_vector                 96   134217728     ← 0x08000000
.text                      280   134217824     ← 0x08000060
.data                        0   536870912
.bss                        16   536870912     ← 16 字节 = 4 个 uint32 观测点
.noinit                      8   536870928     ← 8 字节 = stage + apb2enr_readback
.flash_overflow_check        0   134218104
.ARM.attributes             37           0
blink_gpio.bin = 376 字节

$ make flash
Info : device id = 0x20036410
Info : flash size = 128 KiB
Warn : Adding extra erase range, 0x08000178 .. 0x080003ff
** Programming Finished **
** Verified OK **
** Resetting Target **
```

**`Verified OK` 才是"程序进去了"的证据** —— openocd 写完会把 Flash 读一遍逐字节比对。

### 段大小加不起来？因为 `.bss` / `.noinit` 不占 Flash

`96 + 280 + 0 + 16 + 8 = 400`，但 `.bin` 只有 **376 字节**。差 24 字节正是
`.bss`(16) + `.noinit`(8)。

原因：它们在 ELF 里是 **`NOBITS` 段** —— 只是一段"RAM 地址范围"，
**Flash 里一个字节都不占**，内容由启动代码造出来：

```console
$ llvm-readelf -S blink_gpio.elf | grep -E "bss|noinit|data"
  [ 3] .data     PROGBITS  20000000 010178 000000     ← PROGBITS：Flash 里有内容（虽然这次是 0 字节）
  [ 4] .bss      NOBITS    20000000 020000 000010     ← NOBITS：Flash 里没有
  [ 5] .noinit   NOBITS    20000010 020000 000008     ← NOBITS：Flash 里没有
```

> 顺带：`.bin` 的 376 = `.isr_vector`(96) + `.text`(280) = 376 ✅
> **`.bin` 就是"要写进 Flash 的字节流"，所以只包含 PROGBITS 的内容。**

### 烧录后板子在干什么（可复核）

| 现象 | 怎么验证 |
|---|---|
| LED 在闪（约 1.17 Hz） | 肉眼看；或 `make probe` 连读两次 `blink_count` |
| 时钟开了 | `0x40021018: 00000004` |
| PA5 配成 2MHz 推挽 | `0x40010800: 44244444` |
| 输出在 1/0 之间跳 | `odr_after_set=0x0000a020` / `odr_after_reset=0x0000a000` |
| 启动代码跑完了 | `boot_stage = 3` |

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实测是什么 |
|---|---|
| "配好 GPIO 就能点灯" | **必须先开 `RCC_APB2ENR`**。不开时钟时：写**静默丢失**、读配置寄存器得到复位值、读 `IDR` 得到 0，**全程不报错不 HardFault**（实测 `stage = 13` 跑完） |
| "复位后寄存器都是 0" | GPIO 的 `CRL`/`CRH` 复位值是 **`0x44444444`**（每脚浮空输入），不是 0；且 PA13/14/15、PB3 的复位值不是 `4` 而是 `8`（调试口） |
| "`GPIOA_ODR = 0x20` 就能点亮 PA5" | 能点亮，但会**顺手抹掉 PA13/PA15 的上拉**。实测 `GPIOA_ODR` 在没人配置时就已经是 `0x0000a000`（bit13/15 = 1）。改单个引脚用 `BSRR` |
| "`GPIOA_CRL = 0x00200000` 配置 PA5" | 会把 PA0–PA4/PA6/PA7 一起改成模拟输入。**必须 `&= ~` 再 `\|=`**（实测 6 条指令） |
| "`ODR ^= BIT` 翻转很简洁" | 3 条指令（ldr/eor/str），中间可被中断打断。`BSRR` 只有 1 条 `str` |
| "`BSRR` 读回来能看刚才写了什么" | **`BSRR`/`BRR` 是只写寄存器，读回恒为 0**（实测 `0x40010810: 00000000`）。要看输出状态读 `ODR` |
| "烧进去多少字节就占多少字节" | 擦除按页（1 KiB）对齐，实测 `Warn: Adding extra erase range, 0x08000178 .. 0x080003ff` |
| "段大小加起来应该等于镜像大小" | `.bss`/`.noinit` 是 `NOBITS`，**不占 Flash**。376 = 96 + 280（只有 PROGBITS 进 `.bin`） |
| "延时循环次数 × 周期数 ÷ 主频 = 秒数" | 实测 `delay(400000)` → 半周期约 **428 ms**，反推每次迭代 **8.6 个周期**，是"4 周期"直觉的 2 倍多。而且优化级别一变全变 |
| "`volatile` 参数是保险，加了不影响性能" | 它让 `delay` 每次迭代都从栈上重读 `n`（实测多出 `ldr`+`str` 两条），**慢，但保证循环不被优化掉** |
| "F030 和 F103 差不多，代码可以直接抄" | **GPIO 配置寄存器完全不同**（2 位 `MODER` vs 4 位 `CRL/CRH`），时钟使能位号也不同。其余（BSRR、向量表、启动流程）通用 |

## 代码自测

<details>
<summary>Q1：为什么"先开时钟"这件事这么反直觉？</summary>

因为它和你熟悉的两种模型都不一样：

| 模型 | 资源使用前要不要"申请" | 忘了会怎样 |
|---|---|---|
| PC 上的文件/网络 | 要（`open` / `socket`） | **返回错误码**，你能立刻发现 |
| PC 上的内存 | 不用（`malloc` 后直接用） | 段错误（`SIGSEGV`），也是立刻发现 |
| **裸机上的外设** | **要（写 RCC 寄存器）** | **什么都不发生**。不报错、不异常、写丢、读 0 |

第三种是最难受的：**它把"错误"伪装成"没反应"**。
代码逻辑、编译、链接、烧录、校验全部通过，就是灯不亮。

所以裸机开发有一条纪律：**任何"写寄存器"的操作，都要配一个"读回来验证"的动作。**
本实验的 `apb2enr_readback`、`crl_after_config` 就是这个纪律的产物 ——
不是给程序用的，是**给调试器用的证据**。

工程上的延伸：这种"读回验证"在时钟初始化、Flash 配置、PLL 锁定这类场合是必需的，
因为**芯片手册里写的"写入生效"经常有延迟或者前置条件**（比如 PLL 要等 LOCK 位）。
`do { r = RCC_CR; } while (!(r & PLLRDY));` 这种写法就是在等硬件确认。

</details>

<details>
<summary>Q2：`GPIOA_CRL` 的复位值为什么不是 0 而是 `0x44444444`？</summary>

因为**"0" 在 GPIO 里不是一个有意义的配置**。

看编码表：`0000` = 模拟输入。这是**最省电、最不干扰外部电路**的状态 ——
输入缓冲器关闭、输出驱动器关闭，引脚对外界几乎"透明"。

如果复位值真是 0，那所有引脚一上电就是"模拟输入"，对某些场景反而不好：

- **浮空输入（`0100`）** 至少让引脚的电平可以被读出来（虽然不定）；
- 对调试口（PA13/PA14/PA15、PB3）还额外配上**上拉（`1000`）**，
  这样 SWD/JTAG 在芯片一上电、软件还没跑的时候就能被调试器识别 ——
  **这就是为什么这些引脚的复位值是 `8` 而不是 `4`**（实测 `GPIOA_CRH = 0x88844444`、
  `GPIOB_CRL = 0x44484444`）。

一个实践含义：**"复位值"不是"安全值"，只是"设计者的选择"**。
想省电就把它配成模拟输入；想让它别乱动就配上拉/下拉。

另一个含义：**不要假设任何寄存器的复位值是 0 或某个整齐的常量。**
本仓库的实测里，`GPIOA_ODR` 复位后是 `0x0000a000` 而不是 0 —— 这是调试口上拉在 ODR 里的体现。
如果你写 `ODR = 0x20` 去点灯，就会把这两个上拉位写掉。

**查手册 + 实测，两条都要。**

</details>

<details>
<summary>Q3：为什么 `BSRR` 能做到"一条指令就原子地改一个位"？</summary>

因为它不是"寄存器"，而是一个**写操作的门**（write-only 的硬件动作触发器）。

普通寄存器（如 `ODR`）是**存储**：你写什么，就存什么。
要改其中一位，必须先读出其余的位 —— 因为硬件不知道你想保留哪些。

`BSRR` 是**动作**：每一位对应一个动作（"把 pin n 置 1" / "把 pin n 置 0"），
写 0 表示"不做这个动作"，不是"把这一位清零"。

```
GPIOA_BSRR = 0x00000020     → 只做一件事：PA5 = 1，其他 31 位全部"不做动作"
GPIOA_BSRR = 0x00200000     → 只做一件事：PA5 = 0
GPIOA_BSRR = 0x00000020 | 0x00040000  → 同时：PA5=1 且 PA10=0
```

**关键点：它没有"读"这一步，所以谈不上"不原子"。**
这不是软件技巧，是硬件设计者预见到了"读-改-写"在中断/多核/DMA 场景下的危险，
于是给了一个专门的"单次操作口"。

同类的设计还有很多，见到就优先用：

| 芯片/外设 | "写 1 生效"的寄存器 |
|---|---|
| STM32 GPIO | `BSRR` / `BRR` |
| STM32 中断 pending | `EXTI_PR`（写 1 清标志）、`SCB->ICSR` 的 `PENDSVSET` |
| STM32 定时器 | `TIMx_SR`（写 0 清标志 —— 反过来的约定，要小心） |
| Cortex-M 内核 | `SCB->AIRCR` 的 `VECTKEY`（必须写特定 key 才生效） |

**判据（[4.12](../../book-notes/04-numbers-and-bitops/4.12-用位操作控制内存映射IO寄存器.md) 给过）**：
"这个寄存器有没有提供写 1 生效的影子寄存器？有就用它，没有才读-改-写，
并且读-改-写期间要关中断。"

</details>

<details>
<summary>Q4：为什么 `delay(400000)` 实测下来比我算的慢一倍？</summary>

因为"循环周期数"是心算最容易错的地方。看实测反汇编：

```asm
800014c:  ldr   r5, [sp]        ; ← 2 周期（访存）
800014e:  subs  r6, r5, #0x1    ; ┐ 1 周期
8000150:  str   r6, [sp]        ; ← 2 周期（访存）
8000152:  cbz   r5, ...         ; 1~3 周期（分支，预测不准时更贵）
8000154:  nop                   ; 1 周期
8000156:  b     ...             ; 2 周期（跳转）
```

算下来大约 **8~9 个周期**，实测反推 `8e6 × 0.428 ÷ 400000 ≈ 8.6`，**吻合**。

而"直觉估算"通常是这样来的：`subs` + `bne` = 2 条指令 ≈ 2 周期。
差了 4 倍，原因有三个：

1. **参数是 `volatile`** → 编译器每次迭代都必须真去访问内存（`ldr`+`str` 各 2 周期）；
2. **`nop` 是我主动加的**（防止空循环被优化掉，见 [3.02 Q2](3.02-建立嵌入式项目.md)）；
3. **分支指令在 Cortex-M3 上不是 1 周期**（流水线重填）。

**实践含义**：裸机上的精确定时**永远不要靠空循环**。三种正确做法：

| 做法 | 精度 | 代价 |
|---|---|---|
| SysTick 硬件计数器 | 1 个时钟周期 | 需要一个时基（补充篇 ch19） |
| 通用定时器（TIM） | 1 个时钟周期 | 多占一个外设 |
| 空循环 | **±50% 甚至更多** | 看起来简单，实则不可控 |

不过空循环有一件事很有用：**做"最短等待"**，比如等一个几乎立刻就绪的标志位
（UART 的 TXE、SPI 的 TXE）。这时候关心的是"至少等够几个周期"，
不需要精确时间，而且比调用定时器便宜。

</details>

<details>
<summary>Q5：我用调试器 `mww` 直接点灯成功了，那程序代码还有什么用？</summary>

两者解决的是不同问题。用一张表说清：

| | 调试器 `mww` | 程序代码 |
|---|---|---|
| 谁能做 | 只有接着调试器、halt 着的时候 | 芯片独立运行时的唯一手段 |
| 能持续多久 | 你松手（resume）就没了 | 一直有效 |
| 能有多复杂 | 一条命令写一个值 | 可以写状态机、协议、算法 |
| 能对外部事件反应 | 不能 | 能（中断、轮询） |
| 主要用途 | **验证硬件通路 / 定位问题** | 实现功能 |

`mww` 这个手法的真正价值在**排障时的二分**。假设"灯不亮"，你可以这样切：

```
① mww 0x40021018 0x4          # 手动开时钟 → 读回是 4 吗？
   ├─ 不是 → 时钟寄存器路径有问题（可能是芯片型号不对/地址写错）
   └─ 是 ↓
② mww 0x40010800 0x44244444   # 手动把 PA5 配成输出
③ mww 0x40010810 0x20         # 手动置位
   ├─ 灯亮 → 硬件通路完全正常，问题在**我的代码**（配置写错/被覆盖/没跑到）
   └─ 灯不亮 → 问题在**硬件**（LED 焊反/SB 跳线断开/引脚被别的东西占着）
```

**这一步能把"灯不亮"这个模糊症状，一刀切成"代码问题"或"硬件问题"两半**，
省掉几个小时的无头排查。

顺带一提：`mww` 之所以能这么用，是因为 SWD 调试口**直接读写芯片的总线**，
和 CPU 是否执行代码无关。这也是为什么"程序跑飞了、HardFault 了"的时候，
调试器仍然能救场 —— 它不依赖你的程序是好的。

</details>
