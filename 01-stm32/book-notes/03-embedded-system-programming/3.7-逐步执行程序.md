## 书这一节讲什么

书这一节在 IDE 里按键盘：

| IDE 按钮 | 快捷键 | 干什么 |
|---|---|---|
| Step Into | `F5` | 走进被调用的函数 |
| Step Over | `F6` | 把被调用的函数**当作一行**执行完 |
| Step Return | `F7` | 跑完当前函数，回到调用者 |
| Resume | `F8` | 继续跑（到下一个断点） |

对应到 gdb：

| IDE | gdb | 语义 |
|---|---|---|
| Step Into | `step` | **进**函数（源码级） |
| Step Over | `next` | **迈过**函数（源码级） |
| Step Return | `finish` | 跑完当前函数 |
| Resume | `continue` | 继续 |
| —— | `stepi` | **汇编级**单步（一条指令） |
| —— | `nexti` | 汇编级步过 |

**书里没讲 `stepi`/`nexti`，但在裸机上它们比 `step`/`next` 更常用** ——
原因见下面"为什么 `next` 会骗你"。

## 实测：从 `main` 开头一步步走

回到 [3.6](3.6-调试应用程序.md) 里那个断点，`main` 停在 `main.c:70`。现在连续 `next`：

```console
(gdb) break main
Breakpoint 1, main () at main.c:70
70	    boot_stage = 1;
(gdb) printf "CRL=%#x  APB2ENR=%#x  boot_stage=%u\n", \
              *(unsigned int*)0x40010800, *(unsigned int*)0x40021018, boot_stage
CRL=0x44444444  APB2ENR=0  boot_stage=3          ← ★ 注意 boot_stage = 3！
```

### 第一个反直觉：断在 `boot_stage = 1` 这行，读到的 `boot_stage` 是 **3**

gdb 的断点语义是"**该行尚未执行**"。所以此刻 `boot_stage` 还是**上一次运行留下来的值**。

为什么是 3？因为 `boot_stage` 被放在 **`.noinit` 段**：

```c
__attribute__((section(".noinit"))) volatile uint32_t boot_stage;
```

`.noinit` 的语义就是"**启动代码不清零**"（[3.3.3](3.3-你的第一个嵌入式程序.md) 的实测：
写在 `.bss` 里的面包屑会被清零循环抹掉，所以必须放 `.noinit`）。
上一次程序跑到 `boot_stage = 3` 就一直在闪灯，值留在 RAM 里；
这次复位后 RAM 没被清，所以读到 3。

**这正是一个可用的调试手法**：`.noinit` 变量天然携带"**上一次运行的最后状态**"。
程序莫名重启时，看它能知道上次跑到哪一步 —— 这是裸机上少数几个"黑匣子"之一。

### 然后逐步走（寄存器值才是可信的）

```console
(gdb) next                # 执行 L70: boot_stage = 1
77	    RCC_APB2ENR |= RCC_IOPAEN;
(gdb) print boot_stage
$1 = 1                                    ← ✅ L70 生效

(gdb) next                # 执行 L77: 开时钟
79	    apb2enr_readback = RCC_APB2ENR;
(gdb) printf "APB2ENR=%#x\n", *(unsigned int*)0x40021018
APB2ENR=0x4                               ← ✅ 时钟开了，从 0 变 4

(gdb) next                # 执行 L79: 读回存起来
80	    boot_stage = 2;
(gdb) printf "apb2enr_readback=%#x\n", apb2enr_readback
apb2enr_readback=0x4                      ← ✅ 变量真的存进去了

(gdb) next                # 执行 L80
96	    crl_after_config = GPIOA_CRL;      ← 行号跳到了 96
(gdb) printf "boot_stage=%u\n", boot_stage
boot_stage=2                              ← ✅

(gdb) next
93	    GPIOA_CRL &= ~(0xFu << (LED_PIN * 4u));   ← 行号又跳回 93
(gdb) printf "CRL=%#x\n", *(unsigned int*)0x40010800
CRL=0x44444444                            ← 还没清位

(gdb) next
96	    crl_after_config = GPIOA_CRL;
(gdb) printf "CRL=%#x\n", *(unsigned int*)0x40010800
CRL=0x44044444                            ← ✅ 清位生效：第 6 位 4 → 0

(gdb) next
94	    GPIOA_CRL |=  (0x2u << (LED_PIN * 4u));
(gdb) printf "crl_after_config=%#x  boot_stage=%u\n", crl_after_config, boot_stage
crl_after_config=0  boot_stage=2          ← ✅ 还没执行到赋值那行
```

**值的变化顺序完全正确**（`0x44444444` → `0x44044444` → 再置位成 `0x44244444`），
但**行号显示是 `96 → 93 → 96 → 94`** —— 乱了。

## 为什么 `next` 会"乱跳"？—— 行号 vs 指令，不是一回事

根因：**你写的是"行"，CPU 执行的是"指令"，而优化器在两者之间做了重排。**

编译时的流水线是：

```
main.c（你的行）
   ↓  编译器（-Os 会重排、合并、拆分、内联）
指令序列（真正的执行顺序）
   ↓  编译器同时生成"行号表"（.debug_line）
行号 → 地址 的映射表（可能有多个地址映射到同一行，也可能顺序不一致）
   ↓  gdb 读这张表
你看到的"当前行"
```

`-Os` 会做这些事，每一件都会打乱行号：

| 优化动作 | 对行号的影响 |
|---|---|
| **指令重排** | 后半段的指令被提到前面 → 行号顺序打乱（本实验的 `96 → 93`） |
| **内联** | `delay` 的函数体被塞进 `main`，但行号仍标 `main.c:63` |
| **循环优化** | 循环体被拆开/轮转，同一行会在多个地址出现 |
| **公共子表达式消除** | 两行的代码合并到一处 |
| **常量传播** | 整行代码消失（`-Os` 下 `blink_count++` 可能变成一条 `adds`） |

**所以"当前行"是给人类看的近似值，不是事实。** 三个可靠度排序：

```
寄存器值  >  汇编指令  >  源码行号
 最可信      可信        最不可信
```

### 应对：降优化，或者看汇编

```console
# 办法 1（学习阶段首选）：不优化
$ make CFLAGS="-O0 -g"

# 办法 2：汇编级单步（不跟 C 行号走）
(gdb) layout asm          # 或者
(gdb) stepi
(gdb) x/i $pc             # 看一眼下一条要执行什么
(gdb) info line *$pc      # 反查"这条指令属于哪一行"（可能没有）
```

## 实测：汇编级单步走 `Reset_Handler`

`stepi` 是最诚实的单步 —— **执行一条机器指令**。用它看启动代码最清楚：

```console
(gdb) monitor reset halt
(gdb) maintenance flush register-cache
(gdb) info registers pc sp
pc  0x8000060  <Reset_Handler>
sp  0x20005000                      ← RAM 顶（20K RAM：0x20000000 + 0x5000）

(gdb) stepi
82	    movs    r1, #1                  ← startup.S 的源码行（汇编也有 -g）
(gdb) info registers pc sp
pc  0x8000062  <Reset_Handler+2>    ← 只前进 2 字节（Thumb-2 指令 2 或 4 字节）
sp  0x20005000                      ← 没变：还没压栈
```

`Reset_Handler` 的完整反汇编（实测，`disassemble /r 0x08000060,+40`）：

```asm
   addr      opcode      指令
0x08000060  480e     ldr   r0, [pc, #56]      @ (0x800009c)   ; r0 = &boot_stage
0x08000062  2101     movs  r1, #1                            ; r1 = 1
0x08000064  7001     strb  r1, [r0, #0]                      ; ★ boot_stage = 1
0x08000066  480d     ldr   r0, [pc, #52]      @ (0x800009c)
0x08000068  2102     movs  r1, #2
0x0800006a  7001     strb  r1, [r0, #0]                      ; ★ boot_stage = 2
0x0800006c  490c     ldr   r1, [pc, #48]      @ (0x80000a0)   ; r1 = _sidata（Flash）
0x0800006e  4a0d     ldr   r2, [pc, #52]      @ (0x80000a4)   ; r2 = _sdata（RAM）
0x08000070  4b0d     ldr   r3, [pc, #52]      @ (0x80000a8)   ; r3 = _edata
0x08000072  e003     b.n   0x0800007c                          ; 先跳到条件判断
0x08000074  f851 4b04  ldr.w r4, [r1], #4                       ; ← 循环体：读 Flash，r1 += 4（后索引）
0x08000078  f842 4b04  str.w r4, [r2], #4                       ; ← 写 RAM，r2 += 4
0x0800007c  429a     cmp   r2, r3                              ; r2 == _edata ?
0x0800007e  d3f9     bcc.n 0x08000074                          ; 没到就继续搬
0x08000080  4806     ldr   r0, [pc, #24]      @ (0x800009c)
0x08000082  2103     movs  r1, #3
0x08000084  7001     strb  r1, [r0, #0]                      ; ★ boot_stage = 3（.data 搬完）
0x08000086  4909     ldr   r1, [pc, #36]      @ (0x80000ac)   ; 接下来要清 .bss
```

**这段 20 条指令里能学到 4 件事**：

| 观察 | 说明 |
|---|---|
| `ldr r0, [pc, #56]` 反复出现三次（`0x08000060/66/80`） | **字面池（literal pool）**：地址存在 PC 附近，`ldr` 从那里取。三个 `ldr` 落在同一处 `0x800009c` —— 链接器把它们**合并**了 |
| `ldrb`/`strb` 而不是 `str` | `boot_stage` 是 `uint32_t`，但赋的是常量 1/2/3，**编译器只写一个字节**（省 3 条指令）→ **这就是为什么它叫"面包屑"而不是"可信变量"** |
| `ldr.w r4, [r1], #4` / `str.w r4, [r2], #4` | **后索引寻址**：取完值自动把指针加 4。**一条指令完成"搬一个字 + 游标前进"** —— 这是 `.data` 复制循环的标准写法 |
| `b.n 0x800007c` 在循环体**之前** | 保证"`.data` 为空时不进循环"（先判断后执行）。本实验 `.data` 是 0 字节，所以循环体**一次都没进**就跳出来了 |

> **一条实际意义**：`boot_stage` 只写入 1 个字节。
> 如果你在**另一个字节**上留了脏数据，`boot_stage` 读出来仍然正常 ——
> 但如果你跨字节比较（比如跟 `0x00000003` 做 `==`），在 `-O0` 下可能出问题。
> **`volatile` + 合适宽度**，两个都要。

## 寄存器视角：`r0`/`r1`/`r2`/`r3` 是哪个 C 表达式

这是"单步时看寄存器"这个技巧的核心。实测，在 `main.c:94`（置位那行）之前停下时：

```console
(gdb) info registers r0 r1 r2 r3 sp lr pc xpsr
r0    0x40010800      ← GPIOA_BASE（编译器把它缓存在 r0 里，反复用）
r1    0x44044444      ← CRL 清位后的中间值（下一句要 orr 0x200000 再写回）
r2    0x20000010      ← &apb2enr_readback（.noinit 区）
r3    0x44044444      ← 同一个中间值的另一副本
sp    0x20004ff8
lr    0x800009b       ← 返回地址（Reset_Handler 里 bl main 的下一条，Thumb 位 = 1）
pc    0x8000100       ← <main+72>
xpsr  0x21000000      ← APSR: N=0 Z=0 C=1 V=0 + 异常号
```

**怎么"读"寄存器**（这是要练的手感）：

| 寄存器 | 通常是 |
|---|---|
| `r0`–`r3` | **参数 / 返回值 / 临时值**（ARM AAPCS 调用约定：前 4 个参数放 r0–r3，返回值放 r0） |
| `r4`–`r11` | **被调用者保存**（callee-saved）：函数想用必须自己压栈 |
| `r12` (`ip`) | intra-procedure 临时寄存器 |
| `r13` `sp` | 栈指针 |
| `r14` `lr` | 返回地址（**最低位 = 1 表示 Thumb**） |
| `r15` `pc` | 程序计数器 |
| `xpsr` | 状态：`N Z C V` + `IPSR`(异常号) + `EPSR`(T 位) |

`xpsr = 0x21000000` 拆开看：

```
0x21000000 = 0010 0001 0000 ... 
              ↑
   APSR 的 C 位（进位）= 1     ← 上一条 add/cmp 产生了进位
   IPSR = 0                    ← 不在任何异常里（0 = Thread 模式）
```

**这比 `print` 多一层**：`print` 告诉你"变量是几"，寄存器告诉你"**CPU 现在手头有什么**"。
两者不一致时（比如变量在内存里还是旧值、寄存器里已是新值），
就能判断"这条语句执行到哪一步了"。

## `delay` 为什么 `step` 不进去？—— 它被内联了

[3.4](3.4-探索构建过程.md) 里已经看到：`delay` 被 `-Os` 内联进了 `main`。
后果是：

```console
(gdb) break delay
Function "delay" not defined.        ← 内联之后，没有这个函数了
```

**验证它确实被内联**：`make regs` 的反汇编里，`main` 中间直接出现了延时循环：

```asm
 800014c:  ldr   r5, [sp]       ; ← 每次迭代都从栈上重新读 n（n 是 volatile 参数）
 800014e:  subs  r6, r5, #0x1
 8000150:  str   r6, [sp]       ; ← 写回
 8000152:  cbz   r5, 0x8000158
 8000154:  nop
 8000156:  b     0x800014c      ; 6 条指令的循环
```

而 gdb 连接时（程序正在闪灯）报的 PC：

```console
0x08000156 in delay (n=41648) at main.c:64
```

**`0x08000156` 正好是上面那条 `b 0x800014c`** ——
两个独立来源（`llvm-objdump` 与 gdb）**对上了**。这就是交叉验证的价值：
它能同时确认"反汇编读对了"和"gdb 的符号/行号映射没问题"。

**三个办法进入内联函数**：

| 办法 | 命令 | 说明 |
|---|---|---|
| 汇编级单步 | `stepi` | 不关心函数边界，一条条走 —— **最简单可靠** |
| 降优化 | `-O0` | `static` 函数在 `-O0` 下不会被内联（或者加 `__attribute__((noinline))`） |
| 加 `noinline` | `__attribute__((noinline)) static void delay(...)` | **强制**不内联，代价是多几条指令 |

**顺带一个反直觉**：内联**不是**为了"省调用开销"这么简单。它让编译器
**看清上下文**（比如知道 `n` 是常量 400000），从而做循环展开等优化。
但代价是**调试体验崩掉**。工程上的常见折中：

```make
# 调试构建：不内联、不优化
CFLAGS_DEBUG   := -O0 -g -fno-inline -fno-omit-frame-pointer
# 发布构建：激进优化
CFLAGS_RELEASE := -Os -g -flto
```

**注意两个都带 `-g`** —— 你总不会希望"只有出问题的那一版没有符号"。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "断点停在哪一行，就读到那一行执行后的状态" | gdb 语义是**该行尚未执行**。停在 `boot_stage = 1;` 时读到的是**上一次运行**留下的 3（因为它在 `.noinit` 里） |
| "单步时行号顺序应该和你写的顺序一致" | `-Os` 下实测 `96 → 93 → 96 → 94`。**指令重排/内联/循环优化都会打乱行号**。可信度排序：寄存器值 > 汇编 > 源码行 |
| "`step` 应该能走进我写的每个函数" | 被内联的 `delay` **在符号表里都不存在**（`break delay` → `Function not defined`）。要看它只能 `stepi` 或加 `__attribute__((noinline))` |
| "`-g` 会拖慢程序" | **不会**。`-g` 只往 `.elf` 里塞调试信息，**不进 Flash**（[3.4](3.4-探索构建过程.md)：`.bin` 只有 376 B）。发布版也建议保留 `-g` |
| "优化等级是性能问题，不影响正确性" | 优化会**改变时序**（内联、重排），也会让 `volatile` 缺失的 bug **显形**。`volatile` 参数是 `delay` 在 `-Os` 下还能工作的唯一原因 |
| "寄存器里的函数地址应该是偶数" | Thumb 下**最低位恒为 1**（`lr = 0x800009b`）。这是状态位，`info symbol` 会自动掩掉 |
| "看 `xpsr` 没意义" | `xpsr` 的 `IPSR` 字段就是**当前异常号**（0 = Thread 模式）。程序莫名跑飞时看它，能立刻知道"是不是进了 HardFault" |
| "延时循环里单步很快" | 实测 `delay` 每次迭代 6 条指令，`delay(400000)` = **240 万条指令**。在这种循环里 `next` 一次要跑 ~428 ms，连续单步基本等于死机。**单步前先想清楚"这一步会执行多少指令"** |

## 代码自测

<details>
<summary>Q1：`next` 和 `stepi` 到底差在哪？什么时候必须用 `stepi`？</summary>

差的不是"粒度"，是**信息来源**：

| | `next` / `step` | `stepi` / `nexti` |
|---|---|---|
| 单位 | **一行 C 源码** | **一条机器指令** |
| 靠什么实现 | 行号表（`.debug_line`）+ 临时断点 | 直接设置单步标志（`xPSR.T`/`DHCSR`），CPU 执行一条就停 |
| 依赖 `-g` | ✅ 必须有 | ❌ 不需要 |
| 受优化影响 | ✅ **严重影响**（乱跳、跳不到） | ❌ 不影响（它就是指令流） |
| 快慢 | 一行可能 = 几十条指令 | 一条指令 |
| 看不到源码 | —— | 只有反汇编 |

**必须用 `stepi` 的四种场合**：

1. **`-g` 没加 / 调试信息不全**（比如在看别人给的 `.bin` 反汇编）
2. **函数被内联**（`break delay` 找不到符号）
3. **进异常/中断**（`HardFault_Handler` 里没有 C 行号可跟，
   必须 `stepi` 走，或者看 `SCB->CFSR`）
4. **要精确验证"这一句 C 编成了几条指令"**
   —— [3.3](3.3-你的第一个嵌入式程序.md) 里"配置 PA5 = 6 条指令、
   `BSRR` = 1 条 `str`"就是用 `stepi`/反汇编确认的

**一个实用的混合策略**（本仓库的做法）：

```console
(gdb) break main        # 用 C 级断点快速定位
(gdb) next              # 用 C 级单步走"我认识的部分"
...到这行了，寄存器值和我想的不一样...
(gdb) disassemble /r $pc, +40     # 切到汇编看这一段到底干了什么
(gdb) stepi             # 逐条验证
```

**别一开始就 `stepi` 从头走** —— 一个 300 行的程序你要按 3000 次。

<details>
<summary>Q2：为什么 `boot_stage` 只被写了一个字节（`strb`）？</summary>

先看这三条指令**在哪** —— 它们在 **`Reset_Handler` 里**（地址 `0x08000060` 段），
**不在 `main` 里**。也就是说：**这个 `strb` 是 `startup.S` 手写的，不是编译器生成的。**

```asm
0x08000060  480e   ldr   r0, [pc, #56]   @ (0x800009c)   ; r0 = &boot_stage
0x08000062  2101   movs  r1, #1
0x08000064  7001   strb  r1, [r0, #0]                     ; ★ 只写 1 字节
```

写启动代码的人当然可以写 `str r1, [r0]`（一次 4 字节）。选 `strb` 的动机通常是
**"只改我要的那一位/字节，不碰别的"** —— 这在操作**硬件寄存器**时是美德
（[3.3.3 的 BSRR](3.3-你的第一个嵌入式程序.md) 就是这个道理），
但在写**普通变量**时就成了隐患：**高 3 个字节不会被动过。**

**后果：同样是按 32 位读，不同阶段读到的东西不一样。**

```c
volatile uint32_t boot_stage;
if (boot_stage == 3) { ... }    /* 启动阶段可能读到 0x??????03 → 判断失败 */
```

**同一个变量，两个地方用了不同的写入宽度**（实测，两边都核过）：

| 在哪写 | 指令 | 宽度 | 来源 |
|---|---|---|---|
| `Reset_Handler` `0x08000064` | `strb r1, [r0]` | **1 字节** | `startup.S` 手写（L83 / L88 / L103） |
| `main` `0x080000c8` | `str r0, [r2]` | **4 字节** | 编译器按 `volatile uint32_t` 生成 |

两边都能查：

```console
$ grep -n "strb" startup.S
83:    strb    r1, [r0]
88:    strb    r1, [r0]
103:    strb    r1, [r0]
$ make regs | grep "str.*\[r2\]"
 80000c8:  str  r0, [r2]          # r2 = &boot_stage = 0x20000010 → 32 位写入
```

**分阶段的实际情况**（变量在 `0x20000010`，小端）：

- **`Reset_Handler` 阶段**：只有首字节被写，高 3 字节**保留上一次运行的残留**；
- **`main` 跑起来之后**：`str` 写满 4 字节 → 值才完整。

**验证**（两个视图一起看，差额就是残留）：

```console
(gdb) x/1xb 0x20000010        # 03 00 00 00 → 干净；若后面几位非 0 就是残留
(gdb) x/1xw 0x20000010        # 0x00000003
```

> **实践结论**：`.noinit` 变量能当"上一次运行的黑匣子"用，**前提是写入宽度一致**。
> 混用 `strb` / `str` 会产生"高字节残留"这类**只有反汇编才看得见**的不一致 ——
> 这也是为什么本仓库每个实验都要能让 `make regs` 一键看反汇编。

两个一起看，就知道高字节有没有脏数据。

</details>

<summary>Q3：单步的时候，`delay(400000)` 会等多久？</summary>

**会等真实的 428 毫秒**（实测：半周期 428 ms，[3.3.3](3.3-你的第一个嵌入式程序.md)）。

**关键点：单步不改变程序的时间行为** —— 它只让 CPU **停下来等你按键盘**，
但一旦 `continue`/`next` 跨过延时循环，那 400000 次迭代是**真的一次次跑完**的。

（唯一例外是"每步都停"的单步：gdb 用单步模式时 CPU 会**逐条执行 + halt**，
这个"halt-执行-再 halt"的往返（经 SWD）会让实际耗时**远大于** 428 ms。
所以 `stepi` 穿过 240 万条指令的循环，现实里等于"挂住"。）

**这带来三个实际影响**：

| 影响 | 说明 |
|---|---|
| **单步前先想"这一步多少指令"** | 在 `delay(...)` 这行按 `next` 是安全的（跨过整行 ≈ 428 ms）；按 `stepi` 是灾难 |
| **调试会改变时序，但不改变"程序自己的时钟"** | 你 halt 着的几秒里，**主循环没在跑，但 SysTick/定时器在跑**。所以 halt 之后 `blink_count` 和"实际时间"的对应关系就断了 |
| **换 SysTick 后体验质变** | 用"读硬件计数器 + 比较时间戳"替代空循环后，`next` 一次只等几条指令 —— **这是把 `delay()` 换成定时器的"调试友好"理由** |

**还有一个隐蔽的坑**：如果延时循环里读的是**外设寄存器**（比如等 UART 的 TXE），
那在 halt 期间外设继续工作、标志可能已经置位，`next` 一按就过去了 ——
**你测不到"超时"路径**。这类 bug 只能靠断点 + 观察点，不能靠单步。

</details>

<summary>Q4：`finish` 和 `until` 怎么用？</summary>

两个都是"批量 `next`"，但作用域不同：

| 命令 | 作用 | 典型用途 |
|---|---|---|
| `finish` | 跑完**当前函数**，回到调用者 | 走进一个函数发现"不是这里的问题"，快速退出 |
| `until <line>` | 跑到**指定行**（同函数内） | 开头已知前 20 行没问题，直接跳到第 21 行 |
| `until`（不带参数） | 跑完当前循环的一次迭代（等价跳出循环体） | 在循环里按 `next` 太累时用 |
| `advance <line>` | 类似 `until`，但**不跨函数**，也不会执行到 `line` 之后就停 | 想停在特定行 |

**实测情形**：本实验 `main` 里有 `for(;;)` 死循环，`until` 特别有用：

```console
(gdb) until 101        # 直接跑到 BSRR 置位那行
(gdb) next             # 跨过置位
(gdb) printf "ODR=%#x blink_count=%u\n", *(unsigned int*)0x4001080c, blink_count
```

**注意 `until` 的语义陷阱**：它是"**跑到该行**"，但如果该行**在循环里**，
它会跑到**当前迭代**的那一行就停（不是每次迭代都停）。所以：

```console
(gdb) until 101
... 停在第 101 行
(gdb) until 101        # 再执行一次，跑到下一个迭代的第 101 行
```

**`finish` 在裸机上的一个坑**：它靠**栈帧信息**判断"函数结束"。
本实验**关掉了 unwind 表**（`-fno-unwind-tables`），而且 `main` 里是 `for(;;)`
（永不返回）。所以对 `main` 用 `finish` 会一直等下去 —— **它永远不会返回**。

> **通用建议**：在裸机调试里，`finish` 只对"**会返回的、有栈帧信息的**函数"可靠。
> 死在 `for(;;)` 或 `while(1)` 的代码里，用**断点 + `continue`** 代替。

</details>

<summary>Q5：为什么本篇一直强调"寄存器比行号可信"？</summary>

因为**行号是给人看的，寄存器是给硬件用的**。

一条 C 语句从源文件到执行，中间有两层"翻译"：

```
你写的              C = A + B
                     ↓ 编译器
机器码              adds r2, r0, r1        ← 这一层是真的
                     ↓ 同时生成调试信息
行号表              0x8000100 → main.c:94  ← 这一层是"注释"，可能不准
```

**行号表为什么会不准**：它是由编译器在优化过程中**尽力维护**的。
"尽力"的意思是 —— 当优化器把两条语句合成一条指令时，它只能把这条指令
**标成其中一行的行号**；当它把一行拆成两条分支时，两个分支都会标成同一行。

**所以下面这些"怪现象"都是正常的**：

| 现象 | 真正原因 |
|---|---|
| `next` 跳过的行号顺序和你写的不同 | 指令被重排 |
| 同一行停了两次 | 该行对应多条指令 |
| 单步走到 `.h` 文件里去了（比如 `stdint.h`） | 宏展开/内联把代码归给了头文件的行 |
| `print x` 说 `<optimized out>` | `x` 被放进寄存器且没有"位置描述"了 |

**判据（实战口诀）**：

> **"行号告诉我大概在哪，寄存器告诉我到底发生了什么。"**
> 两者冲突时，**相信寄存器，用 `x`/`info registers` 验证，不要相信高亮的那一行。**

这也解释了为什么本仓库的每个实验都要**在 `main.c` 里埋 `volatile` 观测点变量**：

```c
volatile uint32_t crl_after_config;   /* 配完 PA5 之后 CRL 的真实值 */
volatile uint32_t odr_after_set;      /* BSRR 置位后读到的 ODR */
```

它们**不参与逻辑**，唯一的用途是：**烧完之后用 `x/6xw 0x20000000`
一次性读回 6 个"程序自己以为的值"，然后和真机寄存器对照**。

- 程序里的值 = 真机寄存器值 → ✅ 代码按预期改了硬件
- 程序里的值 ≠ 真机寄存器值 → 说明"软件看到的"和"硬件真的"不一致
  （时钟没开写丢失、被中断打断、寄存器只写读不回来……）

**这个手法不依赖断点、不依赖单步、不受优化影响** ——
它把"调试"从"在线行为"变成了"**离线证据**"。
在时序敏感、跑飞、偶发的问题上，这是唯一还能工作的办法。

</details>
