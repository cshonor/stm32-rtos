## 书这一节讲什么

在 Eclipse 的 Project Explorer 里展开一个 STM32 工程，你会看到一堆东西，
它们分成三类，**处理方式完全不同**：

| 类别 | 例子 | 你要做的 |
|---|---|---|
| **源文件** | `.c` / `.h` / `.s` / `.ld` | **改它、提交它** |
| **构建产物** | `Debug/` 目录、`.o` / `.elf` / `.map` | **别提交、别手改**（会被覆盖） |
| **IDE 私有配置** | `.project` / `.cproject` / `.settings/` | 通常提交（团队共享工程设置），但**别手写** |

书这一节的教学目的：**别把这三类搞混**。很多人第一次做嵌入式的困惑不是"不会写代码"，
而是"不知道自己在改哪个文件"。

## 我们的等价物：一个实验目录的全部文件

```console
$ cd 01-stm32/03-gpio-blink && ls -l
  Makefile                   5628 bytes      ← 源：构建规则
  README.md                 17102 bytes      ← 源：实测记录（本仓库的核心产出）
  linker.ld                  3776 bytes      ← 源：内存布局（书第 11 章）
  main.c                     5158 bytes      ← 源：我们的程序
  portprobe.c                4678 bytes      ← 源：探针程序
  startup.S                  8284 bytes      ← 源：向量表 + Reset_Handler
  --- 以下全是产物 ---
  main.o                     3728 bytes
  portprobe.o                4704 bytes
  startup_s.o                3036 bytes
  blink_gpio.elf           134856 bytes
  portprobe.elf            135172 bytes
  blink_gpio.bin              376 bytes
  portprobe.bin               468 bytes
  blink_gpio.map             5687 bytes
  portprobe.map              6692 bytes
```

**上面 6 个是源，下面 9 个是产物。** 判据简单到不能再简单：

> **删掉它，`make` 能不能重新造出来？能 → 产物。**

## 六个源文件各自的职责（这是本篇最该记住的表）

| 文件 | 谁写的 | 干什么 | 书里对应 |
|---|---|---|---|
| `main.c` | 你 | 业务逻辑：开时钟 → 配引脚 → 翻转 | 3.3 |
| `portprobe.c` | 你 | 只读探针，测"时钟没开时寄存器什么行为" | 3.3 的补充实验 |
| `startup.S` | **通常由工具生成** | 向量表 + `Reset_Handler`（搬 `.data`/清 `.bss`/跳 `main`） | 书里是工程模板自带的 |
| `linker.ld` | **通常由工具生成** | 告诉链接器：Flash/RAM 各多大、段怎么摆 | 第 11 章整章 |
| `Makefile` | 你（或工具生成后改） | 三条命令 + 依赖 | 1.4 / 1.6 |
| `README.md` | 你 | 实测数据、坑点、命令速查 | 本仓库自加 |

**两个反直觉点**：

1. **`startup.S` 和 `linker.ld` 不是你"写"的，是"抄来改"的**。
   在 System Workbench / CubeIDE 里，这两个文件由工具按你选的芯片型号生成；
   在我们这套手工环境里，是从 `01-bare-metal` 继承下来、按板子改的
   （本目录的 `linker.ld` 就改了一处：Flash 从 64K 改成 **128K**，因为实测板子是 `device id 0x20036410`）。
   **它们是"板级配置"，不是"算法"。**

2. **`README.md` 被当成一等公民**。书里 IDE 项目没有这个，但
   "为什么这个值是这个值"如果不写下来，三个月后连自己都不知道。
   本目录的 README 里存的都是**实测输出**（`Verified OK`、`0x44244444`、`blink_count 55→62`），
   不是"说明文档"。

## 仓库整体结构（ST 的工程 → 我们的仓库）

书里的世界观是"**一个 IDE 工程**"。我们这个仓库装的是**一条学习路线上的所有实验 + 笔记**：

```
STM32-/
├── README.md           路线表（8 行）+ 教材信息
├── .gitignore          ★ 产物清单（见下）
├── .gitattributes      跨平台换行符（Mac ↔ Windows）
├── 01-stm32/              第一部分：裸机（对应书 1–12 章）
│   ├── book-notes/         按《裸机C编程》逐小节拆的笔记（NN-slug/X.Y-名字.md）
│   ├── 00-toolchain-clang/   书 1.1 的 clang 版
│   ├── 01-bare-metal/        书 3.1–3.3 的启动/向量表
│   ├── 02-libopencm3/        第三方库路线
│   └── 03-gpio-blink/        ★ 本实验（书 3.3–3.5）
├── 02-freertos/           第二部分：RTOS（对应补充篇 ch20）
│   └── book-notes/         《Mastering the FreeRTOS RTK》配套笔记（骨架）
├── 03-zephyr/             第三部分：现代 RTOS/框架
│   └── book-notes/         Eliasz《Zephyr RTOS Embedded C Programming》配套笔记（骨架）
├── third_party/        submodule（如 libopencm3）
```

**关键设计**：每条轨道自带 `book-notes/`，**笔记与实验同轨对应**。
书讲 3.3，实验就在 `01-stm32/03-gpio-blink/`，笔记就在 `01-stm32/book-notes/03-embedded-system-programming/3.3-*.md`。
**"读到哪、做到哪、记到哪"三件事在同一个坐标系里**，找东西不用回忆。

## `.gitignore` 实测：本仓库忽略什么

```gitignore
# 构建产物
build/
*.o  *.elf  *.bin  *.hex  *.map  *.su  *.lst  *.d  *.a

# 只作参考的上游克隆
_refs/

# genlink 现场生成的链接脚本（派生物）
generated.*.ld

# 日志 / Python / IDE
*.log   __pycache__/   .vscode/   .idea/   .DS_Store
```

三条值得展开的取舍：

**① `.map` 和 `.su` 被忽略，但它们有临时价值。**
前面 [3.4](3.4-探索构建过程.md) 说过：`.map` 是唯一能回答"这个函数为什么没进 Flash"的文件。
**做体积优化期间建议临时 `git add -f`，改完再撤**。默认忽略是对的，但要记得它能救场。

**② `.vscode/` 被忽略 —— 这是一个可争议的决定。**
Cortex-Debug 的 `launch.json`（`servertype: openocd` + `svdFile`）是**团队资产**，
不是产物。本仓库忽略它是因为**路径里带 `$HOME` 绝对路径**（openocd 装在 `~/.local/xpack-...`），
换台机器就不能用。
→ **更好的做法**：把它提交，但用 `${env:HOME}` 变量代替绝对路径。等你真配了 VSCode 调试，
建议按这个改（见 [3.6](3.6-调试应用程序.md) 末尾）。

**③ `_refs/` 不进库。**
里面是 `git clone` 来的上游代码（几百 MB），**复制进仓库会让 clone 变慢十几倍**。
要用人自己去 clone —— 所以**每个用到 `_refs/` 的 lab 必须在 README 里写清 clone 命令和 commit**，
否则三个月后就是"跑不起来的实验"。

## 从 IDE 工程切到这份仓库，三个最大的不同

| | System Workbench（书） | 本仓库 |
|---|---|---|
| **"项目"的边界** | 一个 IDE 工程 = `.project` + `.cproject` + `Debug/` | 一个**目录**，没有工程文件 |
| **构建配置存在哪** | `.cproject` 里 XML（点 GUI 改，不可 diff） | `Makefile` 里（**纯文本，能 diff、能 code review**） |
| **怎么多配置** | `Debug` / `Release` 两个文件夹 | `make CFLAGS="-O0 -g"` / `make CFLAGS="-Os"` |

**第一条是被严重低估的优势。**
`.cproject` 是个几千行 XML，你改了哪个编译选项、谁改的，**完全看不出来**。
`Makefile` 一行一个 `git diff` 就清楚了。工程一大，"构建配置能不能 code review"
直接决定"新人多久能上手"。

**代价**：Makefile 得自己写对。这就是为什么 [3.4 Q4](3.4-探索构建过程.md) 里
头文件依赖那一节不能跳过 —— **IDE 替你做的事，现在得你自己做，而且要做得对。**

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "工程里的文件越多越完整" | 本实验**真正的源只有 6 个文件**，其余 9 个都是产物。看不懂工程，通常是因为没分清这两类 |
| "`startup.S` / `linker.ld` 是核心代码，要好好研究" | 它们是**板级配置**，由工具生成、按芯片改。改错会挂，但它们的"难点"不在逻辑，在**跟手册对上** |
| "IDE 工程文件要一起提交，团队才能共享设置" | `.cproject` 是 XML，**改了什么看不见**。Makefile 是文本，一行就是一行 —— 这是本仓库弃用 Eclipse 的实质理由之一 |
| "构建产物顺手也传上去，别人下载就能用" | 产物每次重编都变（`.elf` 134 KB），**仓库迅速膨胀**，而且 checkout 后时间戳错乱会让 make 增量判断失效 |
| "忽略 `.map` 就行，用不到" | 体积优化 / 查"符号放哪了"时**只有它**能回答。默认忽略，需要时 `git add -f` |
| "每章笔记写一章一篇最省事" | 一章 400 行没人看得下去。本仓库规范是**二级小节一个文件**（50–120 行），见 [book-notes/README](../README.md) |
| "`_refs/` 里的上游代码放着方便" | 几百 MB 复制进 git，clone 直接变慢十倍。**进门要留 clone 命令，不然实验会烂掉** |

## 代码自测

<details>
<summary>Q1：`make clean` 之后 `ls` 该剩下什么？</summary>

```console
$ make clean        # rm -f *.o *.elf *.bin *.map *.su
$ ls
Makefile  README.md  linker.ld  main.c  portprobe.c  startup.S
```

**正好是那 6 个源文件。**

这不是巧合，而是本目录 Makefile 的一个**设计意图**：
`clean` 目标必须和 `.gitignore` 一致。如果 `clean` 之后还剩东西，
说明"要么它是源（该进 git），要么 clean 漏了（该加进 clean）"。

**用这条规则反查工程健康度**：

```console
$ make clean && git status --porcelain
```

- **输出为空** → ✅ 完美：本地目录 = git 里的内容 = 全部源文件
- **输出有 `??`** → 有产物没被 `.gitignore` 覆盖（或真有新源文件没提交）
- **输出有删除** → 源文件被 `clean` 误删了，赶紧修 Makefile

**这条命令值得加进 CI**：它不检查功能，但检查"仓库边界对不对"。
很多项目的仓库膨胀、构建诡异，根因就是这条边界烂掉了。

</details>

<details>
<summary>Q2：为什么 `startup.S` 和 `linker.ld` 要"抄来改"而不是自己写？</summary>

因为它们是**芯片/板子的描述**，不是**程序逻辑**。

`startup.S` 里那 96 字节向量表，内容是芯片定义的：

```
第 0 字  MSP 初值              ← 由 RAM 大小决定（本板 20K → 0x20005000）
第 1 字  Reset_Handler         ← 我们的
第 2 字  NMI_Handler           ← 芯片定的顺序
第 3 字  HardFault_Handler     ← 芯片定的顺序
...
```

**顺序写错一个，中断就会跳到错误的地方** —— 而这种 bug 的症状是"偶发跑飞"，
极其难查。所以没人凭记忆手写向量表，都是拿 ST 官方的
`startup_stm32f103xb.s` 改（或者像本仓库一样拿自己上一版改）。

`linker.ld` 同理：

```ld
MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 128K    ← 来自芯片手册
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 20K     ← 来自芯片手册
}
```

**两个数字都在芯片手册里，一个都不能猜。** 本实验实测把 Flash 从 64K 改成 128K ——
因为 `openocd` 报 `device id = 0x20036410`（F103RB，128K），而不是按型号名字猜。

**自己写这两份文件仍然值得做一次**（就像本仓库 `01-bare-metal` 干的），
但目的是**理解**，不是"以后都手写"。**理解了之后用工具生成的版本，
才看得懂它、改得动它、出问题知道去哪查。**

</details>

<details>
<summary>Q3：我能在同一个目录里放多个 `main.c` 吗？</summary>

能，如果它们**不属于同一个可执行文件**。本目录就是这么干的：

```make
blink_gpio.elf: startup_s.o main.o      linker.ld     ← 主程序
portprobe.elf:  startup_s.o portprobe.o linker.ld     ← 探针程序
```

`make` 是 Makefile，`make probe-ports` 烧 `portprobe.bin`，`make flash` 烧 `blink_gpio.bin`。

**但要注意"共享源文件"的坑**：两个 `.elf` 都用 `startup_s.o`。
这意味着 **`startup.S` 里改了任何东西，必须两个都重编重烧**，
否则会出现"探针程序用的是新启动代码、主程序还是旧的"这种诡异局面。

判据：**共享的 `.o` 意味着共享的 bug。** 当共享文件开始变多
（`startup.S`、`linker.ld`、`board.h`…），就该考虑建一个
`common/` 目录 + 把公共部分编成 `libboard.a`，而不是靠"记得重烧"。

**Eclipse 里的对应问题**：一个工程里两个 `main` 会直接报
`multiple definition of main`，因为 IDE 默认"一个工程 = 一个可执行文件"。
本仓库的 Makefile 显式写了两个目标，反而更清楚。

</details>

<details>
<summary>Q4：`README.md` 写什么才不是废话？</summary>

**只写"从我这儿测出来的东西"。** 本目录 README 的目录就说明了标准：

| 章节 | 写什么 | 不写什么 |
|---|---|---|
| 板上有什么 | 板子型号、MCU、LED 接哪个脚、调试器 | ❌ 抄官网参数表 |
| 寄存器地图 | 用到的寄存器 + 地址 + 位号 + **RM0008 章节号** | ❌ 整本手册搬过来 |
| 实测 | **贴原始命令输出**（`Verified OK`、`0x44244444`、`55→62`） | ❌ "经测试可以正常工作" |
| 坑点 | **"常识怎么说 / 实测是什么"两列对照** | ❌ 泛泛的注意事项 |
| 命令速查 | 我会用到的那几条 | ❌ 列全工具的所有参数 |

**最值钱的是"坑点"那张表**，因为它是**只有做过的人才知道的信息**：

```
| "BSRR 读回来能看刚才写了什么" | BSRR/BRR 是只写寄存器，读回恒为 0（实测 0x40010810: 00000000）|
```

左边那一列是"几乎所有人会以为的"，右边是"实测的"。
**这张表的价值随时间增长 —— 因为你三个月后会再犯一次左边的错。**

**反例**：写"本实验实现了 GPIO 点灯功能，通过配置 RCC 和 GPIO 寄存器完成"——
这句话没有任何信息量，任何人都能从上位机代码猜出来。

</details>

<details>
<summary>Q5：为什么 `book-notes/` 放进 `01-stm32/` 里，不和实验目录平铺混在一起？</summary>

> ⚠ 本问题在 2026-10-09 重构后改写：原来问的是"为什么 `book-notes/` 和 `01-stm32/`
> 要分开放（两个顶层目录）"。当时确定的"三轨各配一本书"结构（stm32 →《裸机C编程》、
> freertos →《Mastering the FreeRTOS RTK》、zephyr → Eliasz 的 Zephyr 书）
> 让答案变成了现在的样子：**每条轨道一个目录，书笔记随轨道走**。

因为笔记和实验的**生命周期不同**，而轨道才是它们共同的归属。

| | `book-notes/`（每轨一个） | 实验目录（`01-`/`02-`/…） |
|---|---|---|
| 与书的关系 | 严格跟随书的章节号 | 按自己的路线编号，能和书对上但不必一致 |
| 改动频率 | 编笔记时改 | 跑实验、改板子时改 |
| 失效条件 | 书换版本才失效 | **换板子/换工具链就失效** |
| 读者 | 读笔记的我 | 跑代码的我 |

**为什么不把笔记直接塞进实验目录**：实验目录里塞 8 篇 Markdown，
`ls` 一眼看不出哪个是代码；而笔记目录里混着 `.c`，检索笔记时要过滤一堆代码。
所以轨道内部仍是"一个 `book-notes/` + 若干实验目录"，互不干扰。

**为什么笔记要跟着轨道走（而不是悬在仓库顶层）**：三条轨道的教材不同、
启动时间不同（stm32 已写完、02-freertos/zephyr 还是骨架），
笔记放轨道内，"这条线读到哪了"看一眼目录就知道。

**代价是链接变多**。所以本仓库的纪律是：

- 每篇笔记头部**必须**有"对应实验"的相对链接；
- 每个实验 README **必须**有"对应笔记"的相对链接；
- 两边的相对链接**用脚本校验过**（0 条失效），见 [book-notes/README](../README.md) 的规范。

**泛化一点**：任何"产出物"和"过程记录"要不要放一起，
判据都是**"它们会不会因为同一个原因失效"**。
