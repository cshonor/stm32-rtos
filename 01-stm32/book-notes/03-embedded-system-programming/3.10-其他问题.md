## 一、书里的 System Workbench 已经停止维护了

书第 2 章全程用 **System Workbench for STM32**（也叫 SW4STM32，Eclipse 系）。
**ST 官方已经不再维护它**，现在是 **STM32CubeIDE**。

**但这不影响本章的价值**：3.3 之后讲的全是**芯片行为**（时钟、GPIO、向量表），
不是 IDE 操作。IDE 换不换，`RCC_APB2ENR` 的那一位还是那一位。

**而且 CubeIDE 现在内置了两套编译器**（官方 release note rn0114 原文）：

| 组件 | 版本 |
|---|---|
| Eclipse + CDT | 2025-12 + CDT 12.3.0 |
| **GNU tools for STM32** | 基于 GNU Tools for Arm Embedded Processors **14.3.rel1** |
| **STARM-Clang** | **21.1.1** ← ST 自己的 LLVM/Clang 工具链 |
| GCC GDB | 同 GNU tools 14.3.rel1 |
| 调试服务 | ST-LINK_gdbserver / J-Link GDB server / **OpenOCD 0.12.0+dev** |
| 烧录 | STM32CubeProgrammer v2.23.0 |
| Windows 侧构建工具 | BusyBox v1.31.0 + make 4.4.1 |

⚠ **两个我没核实的点**（不当结论写）：
- `STARM-Clang 21.1.1` 里的 "21" 看着像 LLVM 21，但我没查到它对应的上游 LLVM 版本。

  真要装之前去官网看**当前版本**的 system requirements。

## 二、那"要不要装 CubeIDE"？

**结论：你现在这条路线（clang + ld.lld + make + openocd + gdb）不需要它，
装了反而挡路。**

理由不是"装不了"（CubeIDE 2.1.0 起有 macOS AArch64 原生包，
且 `/Applications` 是 `root:admin` 组可写，拷贝进去不用 sudo），
而是**设计目标相反**：

| | CubeIDE | 你现在的路线 |
|---|---|---|
| 目标 | 让配置"一键完成" | 让每一步**看得见** |
| 时钟树 | 图形界面拖拽，生成 HAL 代码 | 自己算位、自己写 `RCC_APB2ENR` |
| 引脚 | 点一下选"GPIO_Output" | 自己算 `CRL` 的哪 4 位 |
| 启动文件 | 自动生成，藏在项目里 | 自己写 `startup.S`，逐条看反汇编 |

**你现在的目标恰恰是"看清上电到 main 之间发生了什么"**，
而 CubeIDE 的设计目标就是把这些藏起来。**这是选择问题，不是能力问题。**

**什么时候你真的会想要它**：

1. **上手正点原子 F407 之类**：时钟树（PLL、分频）和多引脚复用靠手算很烦；
2. **要用 HAL / USB / ETH / 中间件**：初始化代码几千行，没人手写；
3. **FreeRTOS 阶段**：想看每个任务的栈水位、状态、切换，命令行 gdb 做不到。

**性价比最高的折中**（不装 1.2 GB 的 Eclipse）：
给 VSCode 装 **Cortex-Debug** 扩展 + 一个 `STM32F103.svd`，复用你现有的
openocd 和 `arm-none-eabi-gdb`，就能得到**外设寄存器树**（RCC/GPIO/USART
的每一位都展开显示当前值）。这补的正是本章唯一的短板：**没有可视化的寄存器视图**。

配置要点（将来做的时候照这个填）：

```jsonc
// .vscode/launch.json
{
  "type": "cortex-debug",
  "servertype": "openocd",
  "executable": "${workspaceFolder}/blink_gpio.elf",
  "configFiles": ["${workspaceFolder}/../02-libopencm3/openocd/f103rb.cfg"],
  "svdFile": "${workspaceFolder}/STM32F103.svd",       // ← 寄存器视图靠它
  "device": "STM32F103RB",
  "request": "launch"
}
```

> ⚠ 本仓库的 `.gitignore` 目前**忽略了 `.vscode/`**（因为 `configFiles` 里带
> `$HOME` 绝对路径）。真配的时候建议改用 `${env:HOME}` 然后把它提交 ——
> 调试配置是团队资产，不是产物。详见 [3.05](3.05-探索项目文件.md)。

## 三、SWD 和 JTAG 有什么区别？为什么板载只用 SWD？

| | JTAG | **SWD**（本实验用的） |
|---|---|---|
| 引脚数 | 5+（TCK/TMS/TDI/TDO/nTRST） | **2**（SWCLK/SWDIO）+ 可选 SWO |
| 协议 | 串行移位（TAP 状态机） | 双向半双工，专门的包协议 |
| 多器件 | 支持菊花链 | 一般一对一 |
| 速度 | 一般够用 | **更快**（尤其批量读内存） |
| 占用引脚 | PA13/14/15 + PB3/PB4 | **PA13(SWDIO) / PA14(SWCLK)** |

**NUCLEO 板默认用 SWD**，省引脚。本实验的实测副产物正好印证了这一点：

```console
$ make probe-ports    # 读回各端口复位值
GPIOA_CRH = 0x88844444     ← PA13/PA14/PA15 = 0b1000（上下拉输入）
GPIOB_CRL = 0x44484444     ← PB3 = 0b1000（JTDO/TRACESWO）
```

**这几个 `8` 就是"调试口预留"的痕迹** —— 芯片一上电、软件还没跑的时候，
调试口就得能被识别，所以它们默认带上下拉。

**实践含义**：

- **别把 PA13/PA14/PA15/PB3 当普通 GPIO 用** —— 一旦你在程序早期把它们重配成
  普通输出，**下次就连不上调试器了**（"变砖"的常见原因之一）。
- 真要用这几个脚（引脚不够时），必须**在程序里留"上电后的时间窗"**
  （比如前 100 ms 不重配），否则就得靠按住 RESET 抢时序。
- **SWO**（单线跟踪输出）是 SWD 的可选第四根线，能输出 `ITM` 的 printf
  —— 这是比 UART 更省引脚的调试打印通道，第 9、10 章会用到。

## 四、为什么本仓库用 F103RB，书里用 F030R8？

**因为手上有什么板子就用什么，而且 F103RB 是更好的教学板。**

| | F030R8（书） | F103RB（本仓库） |
|---|---|---|
| 内核 | Cortex-M0（ARMv6-M） | **Cortex-M3（ARMv7-M）** |
| 指令集 | 无 Thumb-2、无 `str.w`、无硬件除法 | **完整的 Thumb-2** |
| Flash / RAM | 64K / 8K | **128K / 20K** |
| GPIO 配置 | `MODER`（每脚 2 位） | `CRL`/`CRH`（每脚 4 位） |
| 价格 | 更便宜 | 略贵 |

**为什么 M3 更适合教学**：

- **Thumb-2**：可以反汇编出 `str.w r12, [r0, #0x10]` 这种 32 位编码，
  "一条指令完成 BSRR 写"对比"三条指令读-改-写"更直观（M0 上只有 16 位指令）；
- **硬件除法、`ldr.w`/`str.w`、`.ARM.exidx` 的行为**都在 M3 上更丰富；
- **F1 是 STM32 最经典的一代**，资料和坑最多，踩坑能查到答案。

**代价**：本章笔记里凡是涉及**位布局**的地方（`CRL` 的 4 位 vs `MODER` 的 2 位），
都同时标了两种；【对照表见 [3.3.2](3.03-你的第一个嵌入式程序.md)】。

## 五、连不上板子了怎么办？（本章最实用的排障清单）

**症状**：`openocd` 报 `Error: open failed` / `No ST-LINK detected` /
`target not examined yet` / 或者连上了但 `halt` 不动。

**按这个顺序查（从最可能到最不可能）**：

| # | 检查 | 命令 / 做法 |
|---|---|---|
| 1 | **USB 线是不是数据线** | 换一根线。很多线只供电 —— **这是第一大原因** |
| 2 | **板子上电了吗** | 看电源灯（LD1）；`openocd` 会报 `Target voltage: 3.23 V`，不是 0 才对 |
| 3 | **上一步把调试脚重配成 GPIO 了** | 按住板上的 RESET 键 → 执行 `openocd ... -c "init; halt"` → 松手。抢在那个时间窗里连上 |
| 4 | **另一个进程占着 ST-Link** | `pkill -f openocd`、关掉 IDE、关掉 STM32CubeProgrammer |
| 5 | **程序进了低功耗模式** | `monitor reset halt` 一般能救；彻底不行就上电时按住 RESET |
| 6 | **时钟配错导致 Flash 访问变慢** | `monitor flash probe 0` 看能不能识别；必要时降 adapter 速度：`-c "adapter speed 500"` |
| 7 | **板子真坏了 / 供电不足** | 换 USB 口（直连，别用 hub） |

**本实验实测过的两条真实报错**：

```console
# 无板时（未插 USB）
Error: open failed
Runtime Error: embedded:startup.tcl:55: in procedure 'init' called at file "f103rb.cfg"

# 板子被别的东西占着
Error: init mode failed (unable to connect to the target)
```

**另一个坑**（本章踩到过）：`openocd` **不加 `shutdown`/`exit` 就不会退出**，
一直占着 3333 端口。脚本里写自动化时务必：

```console
openocd -f f103rb.cfg -c "init" -c "halt" -c "mdw 0x08000000 4" -c "shutdown"
```

## 六、除了 ST-Link，还有哪些调试器？

本章用的板载 ST-Link 是最省事的（NUCLEO 板自带）。其他常见选择：

| 调试器 | 特点 | 成本 |
|---|---|---|
| **ST-Link/V2-1**（板载） | 免费、SWD、openocd 支持好 | 0（跟板子来） |
| ST-Link/V2 独立版 | 便宜、克隆多（克隆的升级有变砖风险） | ¥20 |
| **J-Link**（SEGGER） | 最稳、速度最快、支持最全 | ¥300+（教育版便宜） |
| **CMSIS-DAP / DAPLink** | 开源、任意 MCU 都能做、openocd 支持 | ¥20 或自制 |
| **Black Magic Probe** | 开源、**自带 GDB server**（不需要 openocd） | ¥100 |
| Raspberry Pi Pico（刷 picoprobe/DAPLink） | **几块钱的调试器**，还能同时当 USB-串口 | ¥20 |
| pyOCD + 任意 CMSIS-DAP | 纯 Python 工具链（不用 openocd） | 0 |

> **Raspberry Pi Pico 那条路值得单独提**：刷上 `debugprobe` 固件就是
> 一个 CMSIS-DAP 调试器，还能通过 `uart` 引脚透传串口 ——
> **相当于一块钱人民币级别的"ST-Link + USB 串口"二合一**。
> 你手上正好有 Pi 5，`openocd` 也可以直接跑在 Pi 上（远程调试）。

**为什么本仓库坚持 openocd**：它是**唯一跨调试器统一**的方案 ——
换 ST-Link、J-Link、DAPLink，配置文件换一行，GDB 那一侧完全不变。
**把调试器和工具链解耦**，这是长期做嵌入式很值得的一笔投资。

## 七、本章留下的三个"技术债"

诚实记下来，避免以后忘记为什么代码长这样：

| 债 | 现在怎么处理 | 什么时候还 |
|---|---|---|
| **`delay()` 是空循环** | 明确标注"教学用"，不写进任何计时逻辑 | 补充篇 ch19（SysTick） |
| **`main` 里是 `for(;;)` 死循环** | 本章不需要"程序结束"的概念 | ch10 中断 / ch20 FreeRTOS |
| **引脚配置没做抽象** | 直接写 `GPIOA_CRL`，寄存器地址用 `#define` | 第 8 章（结构体映射寄存器）/ ch17（模块化） |

**为什么"记债"比"现在修"更重要**：本章的目标是**看清机制**，
过早引入抽象（HAL、驱动层、结构体寄存器映射）会让你看不清
"到底哪一位在起作用"。

**这是学习的节奏问题**：先手写寄存器 → 再抽象成结构体 → 最后用 HAL/库。
**每一步都知道上一步在干什么，抽象才不会变成黑盒。**
