# 1.1 安装 GCC

> 书：第 1 章 Hello World · 1.1 安装 GCC（原书 p3）
> 下一篇：[1.2 下载 STM32 系统工作台](1.2-下载STM32系统工作台.md)
> 对应实验：`01-stm32/00-toolchain-clang/`

## 书这一节讲什么

一句话：**去装 arm-none-eabi 工具链**。书的路线是 GNU Arm Embedded Toolchain
（现在叫 Arm GNU Toolchain），装完 `arm-none-eabi-gcc -v` 能看到版本号就算成。

## 我为什么没照做

不是不能装，是**在 Mac 上没必要**。三点理由：

1. **要下 300MB+ 的安装包**，而且主流的 "Arm GNU Toolchain for macOS" 安装包
   是 `.pkg` 格式，安装器会往 `/usr/local` 写东西——这台机器 `/usr/local` 是
   `root:wheel 755`，我写不进去（要 sudo，而 `sudo -n` 被拒）。
2. **clang 自带 arm 后端**，一个命令就能产出 Cortex-M3 机器码；
3. **换掉之后学到的东西更多**：GCC 的驱动脚本会替你隐式做很多事，
   clang 的 `-###` 能让你看见每一步真实调用。

## 交叉编译到底是什么（原理详解）

这一节回答那个装包之前就该想清楚的问题：**为什么本机已经有一个 gcc/clang 了，
还非得再去"下载一个"？**

**交叉编译 = 在 A 平台上运行编译器，产出面向 B 平台的代码。**
A == B 叫本地编译（native），A != B 叫交叉（cross）。判断标准看**产物**，
不看编译器在哪台机器上跑。

### 为什么本机 gcc 的产物 STM32 跑不了：三层不匹配

编译器是个翻译。本机 gcc 只会"x86-64（或 Apple Silicon 的 arm64）这门语言"，
而 Cortex-M3 只懂 ARM Thumb——翻错语种，烧进去就是天书。拆开是三层，
一层比一层深：

| 层 | 本机 gcc 的产物 | STM32（F103）需要 | 不匹配的后果 |
|---|---|---|---|
| ① 指令集（ISA） | x86-64 / arm64 | ARMv7-M 的 Thumb-2 | 机器码完全不同，CPU 译第一条指令就跑飞 |
| ② ABI（二进制约定） | System V / Darwin ABI | ARM EABI：参数怎么传、栈怎么对齐 | 就算指令凑巧有几条相同，函数调用规矩也对不上 |
| ③ 运行环境（OS） | 假定底下有 macOS/Linux 内核：`printf` 最终走 `write` 系统调用 | **什么都没有**——你的程序就是全部软件 | 链了 glibc 的程序，连"谁来执行系统调用"都没有 |

第 ③ 层就是 `00-toolchain-clang` 里 `-ffreestanding -nostdlib` 存在的原因：
不是指令对了就行，还得告诉编译器"别假定有操作系统、别链本机 C 库"
（参见 [00.1 没有 OS 的 C 语言](../00-mental-model/00.1-没有OS的C语言.md)）。

这三层合起来有个正式名字——**target triple（目标三元组）**：

```
armv7m  -  none  -  eabi
   │         │        └─ ABI：嵌入式二进制接口（参数传递 / 栈对齐 / 系统调用约定）
   │         └────────── OS：底下有没有内核（none = 裸机）
   └──────────────────── ISA：CPU 懂哪套指令（ARMv7-M = Cortex-M3）
```

编译器输出的每一条机器码、每一次函数调用、每一个库假设，都要同时满足这三项。
`arm-none-eabi-gcc` 这个名字本身就是那张三层表（更细的拆解见本篇末尾 Q1）。

### 为什么 GCC 必须"另外下载一个"，clang 不用

这是 **GCC 的架构决定的，不是惯例**：GCC 在编译它自己的时候，
就把目标 triple **焊死**了。

- 一个 gcc 二进制 = 一个 target。你 Mac 上的 gcc 构建时选了
  `x86_64-apple-darwin`（或 `arm64-apple-darwin`），它就**永远只会**产出
  macOS 程序，**没有任何命令行参数能让它改口**。
- 想让 gcc 说 ARM 裸机的话？只能拿 GCC 源码按 `arm-none-eabi` 这个 triple
  **重新编译一个**编译器——这就是 `arm-none-eabi-gcc` 的由来。
  因为每个人都自己编一遍太蠢，Arm 官方直接发编译好的压缩包给你下载。

clang/LLVM 恰好相反：它的多后端是**运行期可选**的——一个 clang 二进制内置
所有目标的后端，用 `--target=` 现场切换。这就是为什么本仓可以
"不装 arm-none-eabi-gcc 也照样编 F103 固件"。

| | GCC | clang/LLVM |
|---|---|---|
| 目标支持 | 编译（GCC 自身）时焊死，一个二进制一个 triple | 运行期 `--target=` 选，一个二进制全后端 |
| 换目标的办法 | 重新编一个编译器（下载的包就是这么来的） | 同一个二进制加一行参数 |
| 产出的 ELF | 面向同一 triple 时**没有区别** | 同左 |

**关键一句**：两者产物的 ELF 没有区别——区别的只是编译器自己的架构设计，
不是"交叉"这件事本身。交叉编译的定义不看"你换了几个编译器"，
只看产物面向哪个 triple。

### "都是 ARM 也不行"

树莓派 5 和 STM32 都是 ARM 家族，但 Pi 是 `aarch64-linux-gnu`
（64 位 ISA + Linux + glibc），F103 是 `armv7m-none-eabi`
（Thumb-2 + 无 OS + EABI）。在 Pi 上用它的本机 gcc 编出的程序，
烧进 F103 一样跑不了——三层表里它只对得上"家族"两个字。

**交叉编译看的是 target triple，不是品牌。**

### 下载的那个包里到底装了什么

`arm-none-eabi-gcc` 那个 300MB+ 的压缩包，远不止一个编译器：

| 组件 | 干什么 |
|---|---|
| 交叉 gcc（驱动 + cc1） | C → ARM 汇编 → 调 as |
| ARM 版 binutils | `as`（汇编器）、`ld`（链接器）、`objcopy`/`objdump`/`nm` |
| **newlib** | 给裸机用的精简 C 库（printf/malloc 的 ARM 裸机版） |
| 对应头文件 + 启动代码 | `stdio.h` 等 + 部分厂商 crt0 |

clang 路线里，前两样有平替（clang 本体 + LLVM 的 `ld.lld`/`llvm-objcopy`），
**唯独 newlib 没有**——这正是 `00-toolchain-clang/libc-trap.c` 存在的原因：
在缺库的情况下调 `printf` 这类函数，会掉进你亲手埋的链接陷阱，
逼你先搞清楚"这个库函数底下到底缺哪一层"，再去补 `_write`/`_sbrk`
（详见 [00.3 没有 GCC 行不行](../00-mental-model/00.3-没有GCC行不行.md)）。

### 本机编译的正当分工

"必须交叉"只针对**碰硬件**的代码。纯逻辑代码（环形缓冲、协议解析、
状态机、算法）在主机上编了直接跑单元测试，还有 ASan/Valgrind 可用——
本仓 [13-dynamic-memory](../13-dynamic-memory/README.md) 的笔记就是这么干的。

分工原则：**碰寄存器的必须交叉，纯逻辑的主机测**。
这也是 [1.4 改进程序和构建流程](1.4-改进程序和构建流程.md) 让同一份代码
挂两个 target 的原因。

### 一句话版（拿去面试说）

> 交叉编译的本质是让产物服从目标平台的 target triple（ISA + OS + ABI）。
> GCC 把 triple 焊死在编译器里，所以每个目标要单独下载一个 gcc；
> clang 一个二进制多后端，`--target` 现场切换。
> 两者产出的 ELF 没有区别——区别的只是编译器自己的架构设计，
> 不是"交叉"这件事本身。

## 等价替换（实测）

```bash
export PATH=~/micromamba/envs/cdev/bin:$PATH     # clang 23.1.0 + llvm 工具

# 传统写法
arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -c main.c -o main.o

# 我的写法
clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb \
      -ffreestanding -fno-builtin -c main.c -o main.o
```

验证一下真的能用：

```bash
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -c main.c -o main.o -###
...
 "/Users/a0000/micromamba/envs/cdev/bin/clang-23" "-cc1" "-triple" "armv7m-none-eabi" ...
```

`-###` 把真实调用的每一条命令都打出来，不复述、不猜——这是选 clang 最实际的收益。

## 装不装，怎么选（决策表）

| 你的情况 | 建议 |
|---|---|
| 只是想理解机制、写自己的 Makefile | **clang + ld.lld**，不用装 |
| 要编译厂商 SDK（HAL/LL）或别人的工程 | 装 Arm GNU Toolchain，省事 |
| 有功能安全 / 客户指定需求 | 装 Arm 官方或商业工具链 |
| 要跟书里的命令逐条对齐 | 装（但这意味着接受书里的工具链假设） |

三条可走的安装路径（本机实测/已知情况）：

| 路径 | 命令 | 本机可行性 |
|---|---|---|
| Arm GNU Toolchain（`.pkg`） | 官网下载安装器 | ⚠ 安装器要写 `/usr/local`，需 sudo 密码 |
| Arm GNU Toolchain（压缩包） | 解压到 `~/.local/` 再加 PATH | ✅ 可行（本机已有 `arm-gnu-toolchain-14.2.rel1-darwin-arm64-arm-none-eabi`） |
| 系统包管理器 | `brew install` | ❌ 本机无 Homebrew（无 root） |

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "装完 GCC 就能开发 STM32 了" | GCC 只是**编译器**。你还缺链接脚本、启动文件、烧录工具、调试器——书要再花 10 章才补齐 |
| "工具链 = 编译器" | 实际是一组程序：`gcc`（驱动）+ `cc1`（编译器）+ `as`（汇编器）+ `ld`（链接器）+ `objcopy`/`objdump`/`gdb`。缺一个都跑不完整流程 |
| "版本越新越好" | 嵌入式里更看重**别人验证过的版本**。STM32CubeIDE 直到 2.1.0 默认才升到 GCC 14.3.1；社区里还有人从 14.3.1 **降回** 13.3.rel1 来绕开 `dangerous relocation: unsupported relocation` 这类链接错误 |
| "macOS 上装不了 GNU 工具链" | 装得了，但 macOS 自带的 `/usr/bin/ld` 是 Mach-O 链接器，跟它没关系。交叉工具链里的 `arm-none-eabi-ld` 是独立的一份 |

⚠️ 一个我没核实到底的点：Arm GNU Toolchain 的 macOS 版对一个版本的 OS 有最低要求，
本机是 macOS 26.6.2（很新），我**没实测过**它的 `.pkg` 装不装得上，只确认了
`~/.local/` 里那份 14.2.rel1 darwin-arm64 压缩包是能跑的。

## 代码自测

<details>
<summary>Q1：`arm-none-eabi` 这个名字怎么读？为什么不能直接叫 `arm-gcc`？</summary>

`arm-none-eabi` 是一个 **target triple**，三段各有含义：

| 段 | 值 | 含义 |
|---|---|---|
| arch | `arm` | 目标架构是 ARM |
| vendor | `none` | 无厂商 |
| os | `eabi` | 裸机 EABI（Embedded ABI），**没有操作系统** |

之所以要显式区分，是因为 ARM 生态里 arm-gcc 有**好多个**，ABI 完全不通：
`arm-linux-gnueabihf`（Linux，硬件浮点）、`arm-linux-gnueabi`（Linux，软浮点）、
`arm-none-eabi`（裸机）、`aarch64-linux-gnu`（64 位 Linux）。

**后缀不同 = 编译出的目标文件不能混链。** 这也是为什么"装错了工具链"
会得到一堆莫名其妙的链接错误，而不是一句清晰的报错。
</details>

<details>
<summary>Q2：`gcc` 到底是编译器还是驱动？</summary>

**是驱动（driver）**，这是最容易误解的一点。

你敲 `arm-none-eabi-gcc -c main.c -o main.o`，实际发生的是：

```
gcc(驱动) → 读命令行 → 决定要跑哪几步
   → cc1（真正的 C 编译器：C → 汇编）
   → as（汇编器：汇编 → 目标文件 .o）
   → 如果要链接：collect2 → ld（链接器）
```

驱动自己一行机器码都不生成。所以：

- `-###`（clang）或 `-v`（GCC）能看到它到底调了什么；
- `gcc -c` 停在第 2 步，`gcc`（不带 `-c`）会一路走到链接；
- 用 `clang` 时，`clang` 就是那个驱动，下面换成 `-cc1` 和集成汇编器。

理解这一点之后，[1.5 编译器在幕后的工作方式](1.5-编译器在幕后的工作方式.md)
那一节就不再是"黑盒魔法"，只是这四步的展开。
</details>

<details>
<summary>Q3：本机 gcc 加个 <code>-mcpu=cortex-m3</code> 参数不行吗？为什么非得换编译器？</summary>

**不行。** `-mcpu` 这类参数只能在你**已经会说那门语言**之后调方言——
它的作用是"在同一个 triple 内部微调生成哪种子型号指令"
（比如 `arm-linux-gnueabihf-gcc -mcpu=cortex-a72`）。

GCC 的后端是编译它自己时静态链接进去的：x86-64 版的 gcc 二进制里
**根本没有 ARM 代码生成器**，你传 `-mcpu=cortex-m3` 它只会报
`unrecognized command line option` 或生成错误的代码。

这就是"GCC per-target 焊死"在命令行上的表现：
**参数能改方言，改不了语种。改语种只能换编译器。**

clang 之所以一个 `--target` 就能改语种，是因为 LLVM 把**所有**后端
都链进了同一个二进制，运行期查表选用——架构决策不同，不是参数多少的问题。
</details>

<details>
<summary>Q4：既然 clang 一个二进制全后端，为什么工业界主流还是 GCC 工具链？</summary>

三个现实原因，都写在前面"装不装，怎么选"决策表里：

1. **生态验证程度**：ST 的 HAL/LL、CubeMX 生成的工程、绝大多数开源
   嵌入式项目，CI 里跑的都是 GCC。你用 clang 编别人的工程，
   碰到 `-mthumb-interwork`、`--specs=nano.specs` 这类 GCC 专有参数
   就得自己找平替。
2. **功能安全 / 认证**：车规、医疗等行业要的是"经过认证的工具链版本"，
   Arm 官方 GCC 包（和 IAR/Keil 这类商业链）有完整的验证报告链。
3. **历史惯性 + LTS**：Arm 每季度发维护版，十年内的工程都能复现构建。

所以个人学习用 clang（看得清每一步、零安装），
**进公司干活大概率还是得会 GCC**——两条路都懂，才理解它们只是
同一个 target triple 的两种实现。
</details>
