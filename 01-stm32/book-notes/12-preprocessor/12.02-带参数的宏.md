# 12.02 带参数的宏

> 书：第 12 章 预处理器 · 12.02 带参数的宏（原书 p174–185 区间内）
> 上一篇：[12.01 简单宏](12.01-简单宏.md) ｜ 下一篇：[12.03 代码宏](12.03-代码宏.md)
> 对应实验：主机侧运行实测（`SQUARE_BAD` = **7**、`MAX(READ_DR(),READ_DR())` 读了 **3** 次）+ `clang -E -P` 展开对照

## 书这一节讲什么

一句话：**`#define NAME(a,b) 替换文本`——看起来像函数，实际是文本替换。**

书上讲语法和"要加括号"。本篇把两个陷阱**跑出真实数字**：

1. **缺括号**：`SQUARE_BAD(3+1)` = **7**（不是 16）；
2. **重复求值**：`MAX(READ_DR(), READ_DR())` 在裸机上会**读 3 次**寄存器。

第二个在嵌入式里是**数据丢失级**的 bug，比书上说的严重。

## 一、陷阱 1：缺括号（实测 7 vs 16）

```c
#define SQUARE_BAD(x) (x*x)        /* 只给整体加括号 */
#define SQUARE_OK(x)  ((x)*(x))    /* 每个参数也加括号 */
```

**实测运行**：

```
$ clang -O0 -o m2 m2.c && ./m2
SQUARE_BAD(3+1) = 7
SQUARE_OK (3+1) = 16
```

**看展开结果就明白了**：

```
$ clang -E -P m1.c
int result  = (3 + 1*3 + 1);      ← 乘法优先级吃掉括号：3 + 3 + 1 = 7
int result2 = ((3 + 1)*(3 + 1));  ← 16
```

**规则（两条，缺一不可）**：

> ① **宏体里每个参数都要单独加括号**；
> ② **整个宏体也要加括号**。

```c
#define MUL(a,b) ((a) * (b))      /* ✅ */
#define MUL_BAD(a,b) (a * b)      /* ❌ 参数没括号 */
#define MUL_BAD2(a,b) (a) * (b)   /* ❌ 整体没括号：MUL_BAD2(1,2)+3 = 1*2+3 = 5 */
```

⚠ **`MUL_BAD2` 那种错更隐蔽**：单独用看不出问题，
一旦放进更大的表达式（`x = MUL_BAD2(1,2) + 3`）就错。

## 二、陷阱 2：参数被求值多次（裸机上的杀伤力）

`MAX(a,b)` 展开后 `a` 和 `b` 各出现**两次**。带副作用就出事。

**实测**：

```
$ ./m2
MAX(i++,j++): m=5  i=4 j=6        ← j 从 4 变成 6（加了两次！）
TWICE(k++):   t=11  k=7           ← k 从 5 变成 7（加了两次）
```

| 表达式 | 期望 | 实测 | 为什么 |
|---|---|---|---|
| `MAX(3++,4++)` 的 `i` | 4 | **4** ✅ | `i++` 在条件里只求一次 |
| 的 `j` | 5 | **6** ❌ | 条件里求一次，选中的分支里又求一次 |
| `TWICE(5++)` 的 `k` | 6 | **7** ❌ | `((k++) + (k++))`，两次 |

### 2.1 ⚠ 裸机上最危险的形式：宏里读寄存器

```c
#define READ_DR()  (*(volatile uint32_t *)0x40013804u)
int m = MAX(READ_DR(), READ_DR());
```

**实测（用计数器模拟"读一次消费一次"）**：

```
MAX(READ_DR(),READ_DR()) 读了几次 DR: 3
```

**是 3 次，不是 2 次**。

展开看：

```c
((READ_DR()) > (READ_DR()) ? (READ_DR()) : (READ_DR()))
 └──── ① ────┘   └──── ② ────┘   └──── ③ 或 ④ ────┘
```

条件部分求 **2 次**（比较两边各一次），
然后**被选中的那一支再求 1 次** → 合计 **3 次**。

**后果**（[ch10 讲过](../10-interrupts/README.md)）：
**读 USART 的 DR 寄存器是"消费型"操作——读一次清一次 RXNE 标志。**
求值 3 次 = **丢了 3 个字节的数据**，但代码看起来只"用了 2 个"。
这类 bug 表现为"数据偶发丢失"，在中断驱动的接收路径上极难查。

### 2.2 编译器会警告吗？一半会

实测 `TWICE(k++)`：

```
m2.c:14:31: warning: multiple unsequenced modifications to 'k' [-Wunsequenced]
   14 |     int k = 5; int t = TWICE(k++);
      |                               ^~
m2.c:5:25: note: expanded from macro 'TWICE'
    5 | #define TWICE(x)      ((x) + (x))
      |                         ^     ~
```

⚠ **但 `MAX(i++, j++)` 没有警告**——因为 `?:` 的三个操作数之间
**有顺序点（sequence point）**，clang 认为它是合法的。
而 `MAX(READ_DR(), READ_DR())` 也没有警告（函数调用不被判为"未序列化修改"）。

**结论**：

> **不能靠编译器警告发现重复求值。**
> `-Wunsequenced` 只覆盖 `+`、`*` 这类没有顺序点的运算符，
> 而 `MAX`（用 `?:`）恰好绕过了它。

## 三、三条对策

| 对策 | 做法 | 适用 |
|---|---|---|
| **① 参数只用无副作用的表达式** | 先存进局部变量：`uint32_t a = READ_DR(); uint32_t b = READ_DR(); MAX(a,b);` | 改不了宏时 |
| **② 用 `static inline` 代替** | `static inline int max_int(int a,int b){ return a>b?a:b; }` | ✅ **推荐** |
| **③ 用 `__auto_type` / 语句表达式** | GCC/Clang 扩展，能做成"类型安全的 MAX" | 牺牲可移植性 |

**② 的实测**（`-Os`，Cortex-M3）：`static inline` 和宏**生成完全一样的指令**，
所以"宏比 inline 快"这个理由在 `-Os` 下不成立：

```
$ llvm-nm --print-size -S cm.o
00000000 0000001c T use_macro      ← 用宏生成的函数：28 字节
00000000 0000001c T use_plain      ← 手写 inline 的函数：28 字节
```

**`static inline` 的三个优势**：

1. **参数只求值一次**（函数调用语义）；
2. **有类型检查**（`MAX("a", 3)` 会报错，宏不会）；
3. **调试信息完整**（gdb 里能单步进函数，宏不能——[ch02 实测](../02-ide/README.md)）。

⚠ 用 `static inline` 时要**给参数也加括号就没意义了**（它是函数），
但要记得**函数体内的参数不要重复用**——
`static inline int sq(int x){ return x*x; }` 里 `x` 是局部变量，求值一次，安全。

## 四、本仓库的取向

> **常量和位运算用宏，逻辑用 `static inline`。**

| 场景 | 用 | 理由 |
|---|---|---|
| `BIT(n)`、`REG32(base,off)` | **宏** | 需要编译期常量 |
| `MAX` / `MIN` / `ABS` | **`static inline`** | 参数只求值一次 |
| 寄存器读写的封装 | **`static inline`** | 有类型检查 + 调试可见 |
| 生成标识符（`##`） | **宏** | 函数做不到（[12.03](12.03-代码宏.md)） |

## 五、`#` 的"不再展开"特性（容易踩）

```c
#define STRINGIFY(x) #x
#define XSTR(x)      STRINGIFY(x)
#define VER          3
```

**实测**：

```
$ clang -E -P m1.c
const char *s1 = "SQUARE_OK(2)";    ← STRINGIFY(SQUARE_OK(2))：原样，没展开
const char *s2 = "3";               ← XSTR(VER)：先展开再字符串化
```

| 写法 | 结果 | 机制 |
|---|---|---|
| `STRINGIFY(SQUARE_OK(2))` | `"SQUARE_OK(2)"` | `#` 的参数**不再做宏展开** |
| `XSTR(VER)` | `"3"` | 多包一层：外层先展开 `VER`→`3`，再交给 `#` |

**想让宏的值变成字符串，必须包两层**（`XSTR` 模式）。
这个技巧在生成版本号字符串时天天用：

```c
#define FW_VER_MAJOR 1
#define FW_VER_MINOR 2
#define STR(x)  #x
#define XSTR(x) STR(x)
const char *g_fw = XSTR(FW_VER_MAJOR) "." XSTR(FW_VER_MINOR);   /* "1" "." "2" */
```

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实测是什么 |
|---|---|
| "宏要加括号" | 是。实测 `SQUARE_BAD(3+1)` = **7**。`(x*x)` 和 `(x)*(x)` 都不够，要 `((x)*(x))` |
| "`MAX(a,b)` 挺好用" | 参数求值 2 次（实际连条件一起是 **3 次**，实测 `MAX(READ_DR(),READ_DR())` 读了 **3 次**） |
| "编译器会警告重复求值" | ⚠ **只警告一半**：`TWICE(k++)` 有 `-Wunsequenced`，`MAX(i++,j++)` **没有**（`?:` 有顺序点） |
| "宏比函数快" | ❌ `-Os` 下 `static inline` 生成**完全一样**的指令（实测都是 28 字节）；宏还少了类型检查和调试信息 |
| "嵌入式里宏更安全" | 恰恰相反：裸机上"读寄存器是消费型操作"，宏的重复求值会**真丢数据** |
| "`STRINGIFY(x)` 能拿到宏的值" | ❌ `#` 的参数**不再展开**。`STRINGIFY(VER)` 得 `"VER"`，要包两层 `XSTR(VER)` 才得 `"3"` |

## 代码自测

<details>
<summary>Q1：为什么 `SQUARE_BAD(3+1)` 是 7？括号到底该加在哪？</summary>

**因为乘法优先级高于加法，而宏只是替换文本。**

**实测**：

```
$ clang -E -P m1.c
int result  = (3 + 1*3 + 1);      ← SQUARE_BAD
int result2 = ((3 + 1)*(3 + 1));  ← SQUARE_OK

$ ./m2
SQUARE_BAD(3+1) = 7
SQUARE_OK (3+1) = 16
```

`(3 + 1*3 + 1)` 按优先级算：`3 + (1*3) + 1` = `3 + 3 + 1` = **7**。

**括号要加两处，缺一不可**：

```c
#define MUL(a,b)     ((a) * (b))     /* ✅ 两处都有 */
#define MUL_BAD(a,b) (a * b)         /* ❌ 参数没括号 */
#define MUL_BAD2(a,b) (a) * (b)      /* ❌ 整体没括号 */
```

⚠ **`MUL_BAD2` 这种错更隐蔽**，因为单独用是对的：

```c
int x = MUL_BAD2(1, 2);        /* (1) * (2) = 2 ✅ 看着没问题 */
int y = MUL_BAD2(1, 2) + 3;    /* (1) * (2) + 3 = 2 + 3 = 5  */
                               /* 期望 (1*2)+3 = 5 ... 这个例子碰巧对 */
int z = MUL_BAD2(1+1, 2);      /* (1+1) * 2 = 4 ✅ */
int w = 1 / MUL_BAD2(2, 3);    /* 1 / (2) * (3) = (1/2)*3 = 0  ← ⚠ 期望 1/6，但整型本来就是 0 */
```

**真正会咬人的组合是 `/` 和 `%`**，以及 `-`：

```c
#define SUM(a,b) (a) + (b)
int v = SUM(1, 2) * 3;      /* (1) + (2) * 3 = 7  ← 期望 9！ */
```

**规则**：

> **每个参数单独加括号，整个宏体再加一层括号。两个都做，不要偷懒。**

**顺带**：宏体里出现 `--`、`++`、`=` 这类有副作用的运算符时，
配合"参数可能出现多次"，问题会叠加——见 Q2。
</details>

<details>
<summary>Q2：`MAX(READ_DR(), READ_DR())` 到底读了几次寄存器？为什么？</summary>

**3 次**（实测计数器给出的数字）。

```
$ ./m2
MAX(READ_DR(),READ_DR()) 读了几次 DR: 3
```

**展开看就清楚了**：

```c
#define MAX(a,b)  ((a) > (b) ? (a) : (b))
MAX(READ_DR(), READ_DR())
  ↓
((READ_DR()) > (READ_DR()) ? (READ_DR()) : (READ_DR()))
 └────── ① ────┘   └────── ② ────┘   └────── ③ 或 ④ ────┘
```

| 位置 | 求值次数 |
|---|---|
| `>` 左边 | 1 |
| `>` 右边 | 1 |
| 被选中的那一支（第 3 或第 4 处） | 1 |
| **合计** | **3** |

**为什么裸机上这是致命的**：

USART 的 DR（数据寄存器）是**消费型**的
（[ch10](../10-interrupts/README.md) 讲过：**读 DR 会清 RXNE 标志**）。
所以：

- 代码里写的是"取两个字节的最大值"；
- 实际从硬件**读走了 3 个字节**；
- 第 1、2 个字节被比较后**丢掉了**。

表现为**"数据偶发丢失"**——速率越高越频繁，
用逻辑分析仪看串口线上数据是全的，但程序拿到的是残的。
这类 bug 极难定位。

**同样的坑还有**：

```c
#define FIFO_POP()  (*(volatile uint32_t *)0x40013804u)
uint32_t a = FIFO_POP(), b = FIFO_POP();          /* 这个是对的（两次显式调用） */
uint32_t m = MAX(FIFO_POP(), FIFO_POP());         /* ⚠ 弹了 3 次 */
```

**对策（按推荐顺序）**：

**① 先存局部变量**（最省事，不改宏）：

```c
uint32_t a = READ_DR();
uint32_t b = READ_DR();
uint32_t m = MAX(a, b);          /* 只读 2 次，符合直觉 */
```

**② 换成 `static inline`**（最彻底）：

```c
static inline uint32_t max_u32(uint32_t a, uint32_t b){ return a > b ? a : b; }
```

函数参数**只求值一次**，且 `-Os` 下实测和宏**生成完全一样的指令**
（`use_macro` 28 B / `use_plain` 28 B，见 [12.01](12.01-简单宏.md)）。

**③ 如果一定要用宏**（要兼容多种类型），用语句表达式 + `__auto_type`：

```c
#define MAX_SAFE(a,b) ({ __auto_type _a = (a); __auto_type _b = (b); _a > _b ? _a : _b; })
```

——GCC/Clang 扩展，**牺牲可移植性**，且 gdb 里没有行号信息。

⚠ **别指望编译器警告**：实测 `MAX(i++, j++)` **没有**触发 `-Wunsequenced`
（`?:` 的三个操作数之间有顺序点，clang 认为合法）。
只有 `((x) + (x))` 这种**没有顺序点**的运算符才会警告。
</details>

<details>
<summary>Q3：`static inline` 能完全替代宏吗？什么时候必须用宏？</summary>

**大部分情况能，但有三件事宏能做而 `static inline` 做不到。**

**实测：性能上没有任何差别**（`-Os`，Cortex-M3）：

```
$ llvm-nm --print-size -S cm.o
00000000 0000001c T use_macro      ← 走宏生成的函数：0x1c = 28 B
00000000 0000001c T use_plain      ← 手写 static inline：0x1c = 28 B
```

两个函数的指令字节数**一模一样**（`static inline` 被完全内联了）。
所以"宏更快"这个理由不成立。

**必须用宏的三件事**：

| # | 场景 | 例子 | 为什么 inline 不行 |
|---|---|---|---|
| ① | **生成标识符** | `REG_BIT_DEF(led, GPIOA_ODR, 5)` 生成 `led_get`/`led_set`/`led_clear` | 函数名**不能在函数里拼出来**——`##` 是预处理期的能力 |
| ② | **需要编译期常量** | `#if CFG_BAUD > 57600`、`int arr[BIT(5)]` | `static inline` 的返回值**不是常量表达式** |
| ③ | **用到 `__FILE__` / `__LINE__`** | `LOG("x=%d", v)` 要自动带行号 | 必须在调用点展开，inline 函数里拿到的是**自己那一行** |

**③特别说明**：

```c
#define LOG(fmt, ...) printf("[%s:%d] " fmt "\n", __FILE__, __LINE__, __VA_ARGS__)
```

写成 `static inline void log_at(const char *file, int line, ...)` 也行，
但**每个调用点都要手写 `__FILE__, __LINE__`**——
漏写一次就得到一个错的行号，而且编译器不报错。
用宏则由预处理器自动填，**不可能写错**。

**可以用 `static inline` 替代的（推荐替换）**：

| 宏 | 换成 |
|---|---|
| `MAX` / `MIN` / `ABS` | `static inline int max_int(int,int)` |
| `SQUARE(x)` | `static inline int sq(int)` |
| 寄存器读写封装 | `static inline void reg_set(volatile uint32_t*, uint32_t)` |

**`static inline` 的三个实际优势**：

1. **参数只求值一次**（函数调用语义，杜绝 Q2 那种丢数据）；
2. **有类型检查**（`MAX("a", 3)` 会报错；宏只会给出莫名其妙的展开）；
3. **调试信息完整**——宏展开的代码在 gdb 里**没有独立行号**
   （[ch02](../02-ide/README.md) 实测过源码级调试的价值）。

**本仓库的取向（一句话）**：

> **常量、位运算、编译期开关、生成标识符、自动带 `__LINE__` → 宏；
> 其余一切逻辑 → `static inline`。**
</details>
