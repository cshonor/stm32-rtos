# 7.04 栈帧

> 书：第 7 章 局部变量和函数 · 7.04 栈帧（原书 p89–97 区间内）
> 上一篇：[7.03 函数](7.03-函数.md) ｜ 下一篇：[7.05 递归](7.05-递归.md)
> 对应实验：`--target=armv7m-none-eabi -mcpu=cortex-m3`（-Os / -O0 + `-fstack-usage`）

## 书这一节讲什么

一句话：**每次函数调用会在栈上分配一块"栈帧"**，放局部变量、参数、返回地址。

书讲概念。本篇用反汇编把它**钉成具体数字**——
因为裸机上"栈够不够"是必须算出来的，不是"跑一下看看"。

## 一、实测：栈帧的建立与销毁

```c
int with_locals(int n){ int buf[8]; int i; int s=0;
    for(i=0;i<8;i++) buf[i]=n+i;
    for(i=0;i<8;i++) s+=buf[i];
    return s; }
```

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -Os -c ch07.c -o ch07_os.o
$ llvm-objdump -d ch07_os.o
0000000c <with_locals>:
       c: b088     sub  sp, #0x20     ← 一进来就减 32 字节（建帧）
       e: 2200     movs r2, #0
      10: 4669     mov  r1, sp        ← r1 = 数组基址（就是 sp）
      14: 1883     adds r3, r0, r2
      16: f841 3022 str.w r3, [r1, r2, lsl #2]
      ...
      30: b008     add  sp, #0x20     ← 返回前加回去（拆帧）
      32: 4770     bx   lr            ← 返回
```

**`sub sp, #0x20` / `add sp, #0x20` 这一对就是栈帧的建立与销毁。**
32 字节 = `buf[8]`（8 × 4），和 `.su` 报的数字完全对上：

```
$ cat ch07_os.su
ch07.c:2:with_locals  32   static
```

注意**没有 `push {..., lr}`**——因为 `with_locals` 是**叶子函数**（不再调别人），
`lr` 不用保存（[7.02](7.02-隐藏变量.md) 讲过这条）。

## 二、`-fstack-usage`：把栈用量变成一张表

```
$ clang ... -Os -fstack-usage -c ch07.c && cat ch07_os.su
ch07.c:1:leaf         4    static
ch07.c:2:with_locals  32   static
ch07.c:6:fact          0   static
ch07.c:7:deep          0   static

$ clang ... -O0 -fstack-usage -c ch07.c && cat ch07_o0.su
ch07.c:1:leaf         12   static
ch07.c:2:with_locals  44   static
ch07.c:6:fact         24   static      ← 真递归，每帧 24 字节
ch07.c:7:deep         16   static
```

三条读法：

1. **数字是"单帧"**，不含递归深度、不含调用链上其他函数；
2. **`static` 那列**表示"编译期可知"——如果是 `dynamic`，
   说明用了变长数组（VLA）或 `alloca`，**栈用量不再可静态分析**；
3. **优化等级直接改变数字**（`leaf` 4 → 12），所以要用**发布配置的等级**来算。

## 三、整条调用链怎么算

**① 手工累加（最常用）**

```
main → parse → read_byte → uart_getc
 8  +  32   +    16      +    24     = 80 字节
```

**加上中断帧**：Cortex-M 进中断时硬件自动压 8 个寄存器 = **32 字节**
（可能还有对齐到 8 字节的填充）。
用了 FPU 的 M4 上再多 136 字节（惰性压栈时）。

**② `-Wframe-larger-than=`（单帧超限报警）**

```
clang -Wframe-larger-than=256 ...      /* 单帧超过 256 字节就警告 */
```

**③ 运行时水位（最可靠）**

启动时把整个栈区填成魔数（如 `0xDEADBEEF`），
跑一段时间后从栈顶往下扫，看魔数被改到哪——那就是历史最高水位。
这比静态计算可靠，因为它包含中断、包含所有路径。

## 四、裸机的栈布局（NUCLEO-F103RB）

```
0x20005000  _estack          ← 栈顶（栈从这里往下长）
   ↓        栈（可用空间 = 20KB − .data − .bss）
   ...
0x20000000  .data / .bss     ← 静态区（从 RAM 底部往上）
```

**栈往下长，静态区在上（地址低）**——
所以栈溢出会**踩到 `.bss`/`.data`**，也就是别人的全局变量
（[6.04 数组溢出](../06-arrays-pointers-strings/6.04-数组溢出.md) 讲过同样的静默破坏）。

链接脚本里可以把栈放在 RAM 最低端、并留一段哨兵区
（[11.03 链接器定义的符号](../11-linker/11.03-链接器定义的符号.md)）。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "栈帧就是局部变量的空间" | 还有 `push {r7, lr}`（非叶子函数，实测 8 字节）、参数区、对齐填充 |
| "栈够不够跑一下就知道" | 栈溢出**不报错**。要 `-fstack-usage` + 最深路径 + 运行时水位三重确认 |
| "`-fstack-usage` 报 0 就安全" | 只说明**单帧**为 0。递归要乘深度，调用链要累加 |
| "`static` 那列不用看" | 出现 `dynamic` 说明有 VLA/`alloca`——**栈用量不可静态分析**，裸机上禁用 |
| "中断不占栈" | 占：硬件自动压 8 个寄存器 = 32 字节，叠加在最深调用链上 |
| "栈溢出会 HardFault" | 只有踩到返回地址时才会。踩到 `.bss` 是**静默的变量被改** |

## 代码自测

<details>
<summary>Q1：`-fstack-usage` 报的是单帧，整条调用链怎么算？</summary>

三种做法，成本从低到高：

**① 手工累加（最常用，也够用）**

沿"最深的那条调用路径"把 `.su` 的数字加起来：

```
main → parse → read_byte → uart_getc
 8  +  32   +    16      +    24     = 80 字节
+ 中断帧 32 字节（Cortex-M 硬件自动压 8 个寄存器）
= 112 字节峰值（普通路径）
```

难点是**找出最深的那条路径**——手工做容易漏（尤其有函数指针、回调时）。

**② 让工具帮忙**

- `-Wframe-larger-than=256`：单帧超限报警（快速抓"某个函数特别能吃栈"）；
- 静态分析思路：栈用量 = 自身 + max(所有被调用者的用量)，
  是在**调用图**上求最长路径。LLVM/GCC 生态有现成脚本（如 `puncover`、`stack-usage` 工具），
  本仓库暂时手工做（`make check-stack` 读 `.su`）。

**③ 运行时实测水位（最可靠）**

```c
/* 启动时把栈区填成魔数（放在启动代码里，main 之前） */
extern uint32_t _sstack, _estack;
void stack_fill(void){ for (uint32_t *p = &_sstack; p < &_estack; p++) *p = 0xDEADBEEF; }

uint32_t stack_used(void){
    uint32_t *p = &_sstack;
    while (p < &_estack && *p == 0xDEADBEEF) p++;
    return (uint32_t)(&_estack - p) * 4;      /* 从栈顶往下被用了多少 */
}
```

跑一段时间（覆盖所有中断路径）后读一次，就是**历史最高水位**。
它包含了静态分析算不到的东西：中断嵌套、函数指针、库函数内部的帧。

**本仓库的做法：① 静态算 + ③ 真机测水位，两者取大值再加余量。**
</details>

<details>
<summary>Q2：为什么栈溢出"不报错"？PC 上不是会段错误吗？</summary>

因为**没有任何一层在检查栈指针**。

PC/Linux 用户态有三重保护：

1. **MMU 的守卫页**：栈底下面是一页未映射的内存，踩到就 SIGSEGV；
2. **ASan 的 redzone**：在栈变量两侧插不可访问的红色区域；
3. **`-fstack-protector`**：函数返回前检查栈上的金丝雀值。

裸机（Cortex-M3，F1）上**一个都没有**：

- 没有 MMU：所有地址都是真实可访问的物理地址，写哪儿都"成功"；
- 栈往下长，紧挨着的就是 `.bss`/`.data`，**踩到的是别人的全局变量**；
- F1 的 Cortex-M3 没有 Stack Limit 寄存器（M33/M55 才有 `__stack_limit`）。

后果链条：

```
栈溢出 → 踩 .bss/.data → 某个全局变量变成奇怪的值 → 行为异常（最难查）
       或踩到栈上保存的 lr → 函数返回跳到非法地址 → HardFault（还算好查）
```

补充一个细节：**Cortex-M 有两个栈指针**（MSP 主栈、PSP 进程栈），
复位后默认用 MSP；RTOS 里任务用 PSP，中断仍用 MSP。
所以 RTOS 下"栈预算"要算**两份**：每个任务的栈 + MSP（中断用）。

对策排序：
1. 静态算（`-fstack-usage` + 最深路径 + 中断帧）；
2. 运行时水位（魔数填充）；
3. 链接脚本里留"栈溢出哨兵"区（[11.03 链接器定义的符号](../11-linker/11.03-链接器定义的符号.md)）；
4. 把 `.bss` 放在栈的上方，让溢出先踩到不那么关键的区域。
</details>

<details>
<summary>Q3：变长数组（VLA）为什么在裸机上禁用？</summary>

因为它让**栈用量变成运行时的未知数**。

```c
void f(size_t n){ int a[n]; ... }      /* VLA：栈用量取决于 n */
```

`-fstack-usage` 会把它标成 `dynamic`：

```
ch07.c:9:f   0    dynamic      ← 编译期算不出来
```

三个后果：

1. **没法静态预算**。栈够不够只能靠"跑一遍"，
   而裸机上的栈溢出是静默的——你根本不知道自己已经踩线了；
2. **`n` 来自外部时就是攻击面**。协议包里的长度字段、用户输入的计数，
   一个恶意值就能让栈爆掉。这在有通信功能的设备上是真实的安全问题
   （参考 Linux 内核，**内核代码里 VLA 已被全面移除**）；
3. **生成的代码更复杂**：需要动态计算栈指针、可能调用 `alloca`，
   还常常顺带破坏优化。

替代写法（三选一）：

```c
/* ① 固定上限（最常见） */
#define MAX_ITEMS 64
void f(size_t n){ if (n > MAX_ITEMS) return; int a[MAX_ITEMS]; ... }

/* ② 调用者提供缓冲（最灵活） */
void f(int *a, size_t n);

/* ③ 静态 + 断言（编译期定死） */
static int a[MAX_ITEMS];
_Static_assert(MAX_ITEMS >= 64, "");
```

一句话：**裸机上 "栈用量必须编译期可知" 是硬约束。**
任何让 `-fstack-usage` 出现 `dynamic` 的写法都不要进代码。
（顺带：C11 起 VLA 是可选特性，C23 里又变成必须支持但依然不推荐在裸机用。）
</details>
