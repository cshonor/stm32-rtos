# 13.4 GCC AddressSanitizer

> 书：第 13 章 动态内存 · 13.4 GCC AddressSanitizer（原书 p186+ 区间内）
> 上一篇：[13.3 Valgrind](13.3-Valgrind.md) ｜ 下一篇：[第 13 章目录](README.md)
> 对应实验：**全部为本次实测**（clang 23.1.0 / macOS arm64 / Apple Silicon）

## 书这一节讲什么

一句话：**`-fsanitize=address`——编译期插桩，运行时抓内存错误。**

书上的标题写的是 "GCC AddressSanitizer"，
但**ASan 是编译器特性，不是 GCC 独有**——
clang 同样支持，而且**本机实测 clang 的 ASan 完全可用**。

本篇是本章唯一**全部实测**的一节：
[13.1](13.1-基本堆分配和释放.md) 里那个"三处错误全静默"的程序，
开了 ASan 会给出什么诊断，以及**三个实测才发现的坑**。

## 一、实测：ASan 抓堆溢出（含完整调用栈）

```c
int *p = malloc(10 * sizeof(int));
for (int i=0;i<10;i++) p[i]=i;
p[10] = 999;                 /* ← 堆溢出 */
```

```
$ clang -O1 -g -fsanitize=address -o h1a h1.c && ./h1a
=================================================================
==44198==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x604000000438
WRITE of size 4 at 0x604000000438 thread T0
    #0 0x000104f93b30 in main h1.c:8
    #1 0x000192837e7c in start+0x1a1c (dyld:arm64e+0x31e7c)

0x604000000438 is located 0 bytes after 40-byte region [0x604000000410,0x604000000438)
allocated by thread T0 here:
    #0 0x000105487488 in malloc+0x70 (libclang_rt.asan_osx_dynamic.dylib:arm64+0x57488)
    #1 0x000104f93a30 in main h1.c:4
    #2 0x000192837e7c in start+0x1a1c (dyld:arm64e+0x31e7c)

SUMMARY: AddressSanitizer: heap-buffer-overflow h1.c:8 in main
Shadow bytes around the buggy address:
=>0x604000000400: fa fa 00 00 00 00 00[fa]fa fa fa fa fa fa fa fa
```

**四条关键信息**：

| 信息 | 值 |
|---|---|
| 错误类型 | `heap-buffer-overflow` |
| 越界的确切偏移 | **`0 bytes after 40-byte region`**（就差 0 字节） |
| 出错的源码行 | `h1.c:8` |
| **分配点** | `h1.c:4`（连当初在哪分配的都告诉你） |

对比 [13.1](13.1-基本堆分配和释放.md) 的裸跑：

```
越界写 p[10] 完成（heap overflow）      ← 什么都不报
```

**这就是"写 C 不配 sanitizer = 闭着眼睛开车"的意思。**

## 二、实测：三类错误都能抓（但有个优化级陷阱）

| 错误类型 | 代码 | ASan 输出 | 实测结果 |
|---|---|---|---|
| **堆溢出** | `p[10] = 999` | `heap-buffer-overflow ... 0 bytes after 40-byte region` | ✅ 抓到 |
| **use-after-free** | `free(p); p[0]` | `heap-use-after-free ... uaf.c:3` | ✅ 抓到 |
| **double free** | `free(p); free(p);` | `attempting double-free ... dbl.c:2` | ⚠ **只在 `-O0` 抓到** |
| **泄漏** | `malloc(1024)` 不释放 | 无输出 | ❌ **本机抓不到** |

### 2.1 ⚠ 实测坑①：`-O1` 以上，优化器会把"问题代码"删掉

```c
int main(void){ int *p = malloc(16); free(p); free(p); return 0; }
```

| 优化级 | ASan 输出 | 退出码 |
|---|---|---|
| **`-O0`** | `ERROR: AddressSanitizer: attempting double-free ... ABORTING` | **134** ✅ |
| `-O1` | **（无输出）** | 0 ❌ |
| `-O2` | **（无输出）** | 0 ❌ |

**为什么会这样**——数一下 LLVM IR 里的 `malloc`/`free` 调用：

```
=== -O0 ===
  malloc|free 调用数: 3
=== -O1 ===
  malloc|free 调用数: 0        ← ⚠ 全被删了
```

clang 在 `-O1` 下做了**"死 malloc 消除"**（dead malloc elimination）：
`malloc` 的结果只被 `free` 用，没有任何可观测效果 → **整对删掉**。
没有 `malloc` 了，自然没有 double free 可言。

⚠ **实践含义**：

> **用 ASan 查问题时，优先用 `-O0` 或 `-O1`；
> 用 `-O2` 跑出来的"干净"结果可能只是优化器帮你把 bug 删了。**

（本书其他章节的实测也反复印证这点：
[ch05](../05-control-flow-button/README.md) 的 `volatile` 等待循环在 `-Os` 下被改成死循环、
[ch09](../09-uart-serial/9.1-一次写一个字符的字符串.md) 的同类发现。）

### 2.2 ⚠ 实测坑②：本机 LeakSanitizer 不报泄漏

```c
int main(void){ int *p = malloc(1024); p[0]=1; return 0; }
```

```
$ clang -O1 -g -fsanitize=address -o leaka leak.c
$ ./leaka
$ echo $?
0                                    ← 无输出，退出码 0

$ ASAN_OPTIONS=detect_leaks=1 ./leaka
$ echo $?
0                                    ← 还是没输出

$ ASAN_OPTIONS=detect_leaks=1:verbosity=1 ./leaka
==44282==LeakSanitizer: checking for leaks
                                     ← 打了"在检查"，但没报出那 1024 字节
```

⚠ **结论：在这台 Mac（Apple Silicon / macOS）上，
ASan 的 LeakSanitizer 不可靠。**
它打印了 `checking for leaks`，说明**代码跑到了**，但**没检出**。

**后果**：如果你靠 ASan 查泄漏（本机），会**误以为没有泄漏**。
查泄漏要么用 Linux 上的 Valgrind（[13.3](13.3-Valgrind.md)），
要么自己在裸机侧加分配计数（[13.1](13.1-基本堆分配和释放.md) 的内存池思路）。

### 2.3 实测：ASan 依赖的运行时库

```
$ otool -L dbla | grep -i asan
	@rpath/libclang_rt.asan_osx_dynamic.dylib
```

——**ASan 不是"纯编译"，它链接了一个运行时库**。
这正是它**跑不进裸机**的原因之一（另一个是 shadow memory）：

| ASan 需要 | 裸机有吗 |
|---|---|
| `libclang_rt.asan_osx_dynamic.dylib`（运行时） | ❌ |
| `malloc`/`free` 拦截（要 libc） | ❌ |
| shadow memory（应用内存的 1/8 + redzone） | ❌ 20 KB RAM 放不下 |

## 三、UBSan：另一个必开的 sanitizer

`-fsanitize=undefined`（UBSan）查的是**未定义行为**，和 ASan 互补：

```sh
clang -O1 -g -fsanitize=address,undefined -fno-omit-frame-pointer -o app app.c
```

| sanitizer | 查什么 |
|---|---|
| **`-fsanitize=address`** | 越界（堆/栈/全局）、UAF、双重释放、泄漏 |
| **`-fsanitize=undefined`** | 有符号整数溢出、空指针解引用、移位越界、**对齐** |

⚠ **UBSan 的"对齐"检查对嵌入式特别有用**：

```c
uint32_t *v = (uint32_t *)(buf + 1);      /* 非 4 对齐 */
*v = 0x12345678;                          /* UBSan: misaligned address */
```

在 **Cortex-M0 上这是 HardFault**（[ch08](../08-complex-types/8.12-结构体与嵌入式编程.md)），
在 M3/M4 上"能跑但慢且非原子"——
**UBSan 能在主机上提前抓到它**，这正是"主机侧跑逻辑"的价值。

## 四、怎么接进日常构建

**开发阶段默认全开**：

```make
# Makefile（开发配置）
CFLAGS_DEV = -O0 -g -Wall -Wextra \
             -fsanitize=address,undefined \
             -fno-omit-frame-pointer
LDFLAGS_DEV = -fsanitize=address,undefined

# 发布配置（裸机）：不加 sanitizer
CFLAGS_REL = -Os -ffunction-sections -fdata-sections
```

⚠ **`-fno-omit-frame-pointer` 不是可选的**——
没有它，ASan 打印的调用栈会缺帧（你只看到 `main` 看不到是谁调的）。

**常用运行时开关**（`ASAN_OPTIONS` 环境变量）：

```sh
ASAN_OPTIONS=detect_leaks=1          ./app     # 开泄漏检测（本机实测无效）
ASAN_OPTIONS=halt_on_error=0         ./app     # 报错不退出，继续跑
ASAN_OPTIONS=abort_on_error=1        ./app     # 报错时 abort（方便挂 gdb）
ASAN_OPTIONS=detect_stack_use_after_return=1 ./app   # 查"返回后使用栈变量"
```

## 五、⚠ ASan 查不了什么（别高估它）

| 查不了 | 说明 |
|---|---|
| **未初始化内存读** | Valgrind 的独门绝技（[13.3](13.3-Valgrind.md)） |
| **逻辑错误** | 算法写错了它不管 |
| **竞态 / 数据竞争** | 要用 `-fsanitize=thread`（TSan） |
| **优化器删掉的问题** | ⚠ 本节 2.1 实测的 `-O1` double-free |
| **本机上的泄漏** | ⚠ 本节 2.2 实测 |
| **裸机上的任何东西** | 要 libc + 运行时 + 大量 RAM |

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实测是什么 |
|---|---|
| "ASan 是 GCC 的" | ❌ 编译器特性。实测 **clang 23.1.0 的 ASan 在 macOS arm64 上完全可用**（`libclang_rt.asan_osx_dynamic.dylib`） |
| "开了 ASan 就都能抓" | ⚠ **double free 只在 `-O0` 抓到**：`-O1` 下 LLVM IR 的 malloc/free 调用数是 **0**（优化器删掉了） |
| "ASan 能查泄漏" | ⚠ **本机不行**：实测 `ASAN_OPTIONS=detect_leaks=1` 只打出 `LeakSanitizer: checking for leaks`，1024 字节的泄漏**没报出来** |
| "ASan 零成本" | 要链接运行时库（实测 `otool -L` 能看到 `libclang_rt.asan_osx_dynamic.dylib`）+ shadow memory。**裸机上放不下** |
| "越界会崩" | 裸跑不崩（[13.1](13.1-基本堆分配和释放.md) 实测退出码 0）。ASan 会报，且给出 **"0 bytes after 40-byte region"** 这种精确偏移 |
| "开 `-O2` 跑 ASan 更接近发布版" | ⚠ 优化器会把 bug 删掉，给你"干净"的假象。排查期用 `-O0`/`-O1` |

## 代码自测

<details>
<summary>Q1：ASan 报的 "0 bytes after 40-byte region" 怎么读？</summary>

这是 ASan 输出里**信息密度最高的一行**，逐段拆：

```
0x604000000438 is located 0 bytes after 40-byte region [0x604000000410,0x604000000438)
                          ^^^^^^^^^^^^^^ ^^^^^^^       ^^^^^^^^^^^^^^ ^^^^^^^^^^^^^^
                          越界了多少      区域大小       区域起始        区域结束
```

**实测的完整输出**：

```
==44198==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x604000000438
WRITE of size 4 at 0x604000000438 thread T0
    #0 0x000104f93b30 in main h1.c:8

0x604000000438 is located 0 bytes after 40-byte region [0x604000000410,0x604000000438)
allocated by thread T0 here:
    #1 0x000104f93a30 in main h1.c:4

SUMMARY: AddressSanitizer: heap-buffer-overflow h1.c:8 in main
```

**逐行读**：

| 行 | 含义 |
|---|---|
| `heap-buffer-overflow` | 错误类型：**堆缓冲溢出** |
| `on address 0x604000000438` | 出事的地址 |
| `WRITE of size 4` | 是**写**，写了 **4 字节**（对应 `int`） |
| `in main h1.c:8` | **出错行**：`h1.c` 第 8 行 |
| `0 bytes after 40-byte region` | 目标地址在**这块区域末尾之后 0 字节** |
| `[0x604000000410, 0x604000000438)` | 区域范围（40 字节 = 10 × `sizeof(int)`） |
| `allocated ... h1.c:4` | **当初在哪分配的**：`h1.c` 第 4 行 |

**对照代码**：

```c
4:  int *p = malloc(10 * sizeof(int));      /* 40 字节 */
...
8:  p[10] = 999;                            /* 第 11 个元素，越界 */
```

`p[10]` 的地址 = `p + 10*4` = 区域起始 + 40 = **正好是区域末尾**。
"0 bytes after" = **刚好越界到边界外第一个字节**。

**这个数字能直接告诉你错在哪类问题**：

| 报的是 | 典型原因 |
|---|---|
| `0 bytes after N-byte region` | **差一错误**（`i <= n` 写成了 `i < n+1`，或者 `p[n]` 越界） |
| `k bytes after N-byte region`（k>0） | 索引算错了，或者拷贝长度算错 |
| `k bytes before N-byte region` | 指针往前越界（负索引、指针算术写反） |
| `inside N-byte region` | 不是越界，是 **use-after-free**（区域还在但已经被释放） |

**"shadow bytes" 那段也值得看一眼**：

```
Shadow bytes around the buggy address:
=>0x604000000400: fa fa 00 00 00 00 00[fa]fa fa fa fa fa fa fa fa
                                      ^^
                                      方括号标出事的那一个字节
```

| shadow 值 | 含义 |
|---|---|
| `00` | 这块内存**可访问** |
| `fa` | **redzone**（不可访问的区域，分配器故意留的隔离带） |
| `fd` | 已释放（freed） |
| `f1`–`f3` | 栈对象的 redzone |

——`00 00 00 00 00` 后面紧跟着 `[fa]`：
**可访问的 5 个字节之后就是 redzone**，一眼看出边界在哪。

**一句话**：
> **"N bytes after M-byte region" 这个数字就是 bug 的精确坐标，
> 比"程序崩了"有用一万倍。裸机上你拿不到这个数字。**
</details>

<details>
<summary>Q2：为什么 `-O1` 下 ASan 抓不到 double free？这对日常使用意味着什么？</summary>

**因为优化器把整个 `malloc`/`free` 对删掉了——没代码可查了。**

**实测**：

```c
int main(void){ int *p = malloc(16); free(p); free(p); return 0; }
```

| 优化级 | ASan 输出 | 退出码 |
|---|---|---|
| **`-O0`** | `ERROR: AddressSanitizer: attempting double-free ... ABORTING` | **134** ✅ |
| `-O1` | **（无输出）** | 0 ❌ |
| `-O2` | **（无输出）** | 0 ❌ |

**`-O0` 下的完整输出**：

```
==44256==ERROR: AddressSanitizer: attempting double-free on 0x602000000970 in thread T0:
    #0 0x000102f2b574 in free+0x74 (libclang_rt.asan_osx_dynamic.dylib:arm64+0x57574)
    #1 0x000102a93e94 in main dbl.c:2

0x602000000970 is located 0 bytes inside of 16-byte region [0x602000000970,0x602000000980)
freed by thread T0 here:
    #1 0x000102a93e8c in main dbl.c:2
previously allocated by thread T0 here:
    #1 0x000102a93e80 in main dbl.c:2

SUMMARY: AddressSanitizer: double-free dbl.c:2 in main
==44256==ABORTING
```

**为什么会消失**——数 LLVM IR 里的调用：

```
$ clang -O0 -S -emit-llvm -o - dbl.c | grep -cE "call.*(malloc|free)"
3
$ clang -O1 -S -emit-llvm -o - dbl.c | grep -cE "call.*(malloc|free)"
0          ← ⚠ 一个都不剩
```

clang 做了 **dead malloc elimination**：
`malloc` 的结果只被 `free` 用，**没有任何可观测的副作用**
（没有写入、没有返回、没有传给外部函数）→ 整对删除。
`-O0` 不做这个优化，所以调用还在。

**这对日常使用的三点含义**：

**① 排查期用 `-O0` / `-O1`，别用 `-O2`**

`-O2` 跑出来的"ASan 没报错"可能有两种含义：

- 你的代码真的没错；
- **优化器把有问题的代码删了**。

**你分不清是哪一种。** 所以用 `-O0` 的结果才可信。

⚠ 但反过来也成立：
**`-O0` 报的错，在 `-O2` 下可能真的不影响发布版**
（因为那代码被删了）。
所以 ASan 报错后要**判断这是不是一个真实场景的 bug**，
不能盲目"修给 ASan 看"。

**② 写测试时要让分配结果"被用到"**

如果测试代码长这样：

```c
void *p = malloc(64);
assert(p != NULL);
/* 什么都没干 */
free(p);
```

优化器可能整段删掉——**你的测试什么都没测到**。
至少要写点东西进去：

```c
void *p = malloc(64);
assert(p != NULL);
memset(p, 0xCD, 64);        /* 让它有可观测效果 */
...
free(p);
```

**③ 这个教训在本书反复出现**

| 章节 | 同类发现 |
|---|---|
| [ch05 volatile](../05-control-flow-button/README.md) | 非 `volatile` 的等待循环在 `-Os` 下被改成**死循环** |
| [ch09 9.1](../09-uart-serial/9.1-一次写一个字符的字符串.md) | 同上，实测是 `ldrb` + `b 0x24`（读一次 + 无限自跳） |
| 本节 | double free 在 `-O1` 下被"死 malloc 消除"删掉 |

> **共同规律：优化器只保证"可观测行为不变"，
> 而很多 bug 恰恰藏在"不可观测"的地方。
> 所以"能优化掉"和"没 bug"是两回事。**
</details>

<details>
<summary>Q3：ASan 和 UBSan 该开哪个？裸机项目怎么用？</summary>

**两个都开，开发期常开，发布期都不开。**

**它们查的是不同维度的问题**：

| sanitizer | 查什么 | 裸机相关度 |
|---|---|---|
| **ASan** (`-fsanitize=address`) | 越界（堆/栈/全局）、UAF、双重释放 | 高（内存池、环形缓冲） |
| **UBSan** (`-fsanitize=undefined`) | 有符号溢出、空指针、移位越界、**对齐** | **很高**（见下） |

**UBSan 对嵌入式特别有价值的三条**：

**① 对齐检查（Cortex-M0 上是 HardFault）**

```c
uint8_t buf[8];
uint32_t *v = (uint32_t *)(buf + 1);    /* 非 4 对齐 */
*v = 0x12345678;                        /* UBSan: misaligned address */
```

| 内核 | 结果 |
|---|---|
| **Cortex-M0** | **HardFault**（不支持非对齐访问） |
| Cortex-M3/M4 | 能跑，慢，且**非原子** |

——M3 上"能跑"是最糟的情况：不崩，但有问题。
**UBSan 能在主机上提前抓到**，省掉一次"上板才发现"的循环。
（对齐问题的完整讨论见 [ch08](../08-complex-types/8.12-结构体与嵌入式编程.md)，
内存池的对齐坑见 [13.1](13.1-基本堆分配和释放.md) 实测的 `offsetof(data)=1`。）

**② 有符号整数溢出（UB）**

```c
int a = INT_MAX;
a = a + 1;                    /* UB！UBSan: signed integer overflow */
```

裸机上结果是"看编译器心情"（`-fwrapv` 与否）。
**涉及计数器、时间戳比较的代码**特别容易踩
（比如"超时判断 `now - last > timeout`"在有符号数溢出时的行为）。

**③ 移位越界**

```c
uint32_t x = 1u << 33;        /* UB！UBSan: shift exponent 33 is too large */
```

写寄存器位定义时手滑写错位数，UBSan 直接抓到。

---

**裸机项目的实操方案**：

| 阶段 | 配置 |
|---|---|
| **主机侧单元测试** | `-O0 -g -fsanitize=address,undefined -fno-omit-frame-pointer` ✅ |
| **主机侧性能测试** | `-O2`（不开 sanitizer） |
| **裸机构建** | `-Os -ffunction-sections -fdata-sections`（**不加 sanitizer**） |

⚠ **关键：把"不依赖硬件的逻辑"抽出来，让它在主机上能跑**

```
裸机代码                       主机测试（开 sanitizer）
─────────────────────────────────────────────────
ring buffer (ch10)      →     rb_put/rb_get 行为验证 ✅ 已做
protocol parser         →     构造畸形输入跑一遍
memory pool (13.1)      →     pool_alloc/pool_free 全覆盖
linked list (13.2)      →     push/pop/remove/越界/UAF
```

[ch10](../10-interrupts/10.4-用缓冲区提速.md) 的环形缓冲实测
（`put ok=63 full_reject=137 head=63 tail=0`）就是这个套路的样板——
**主机侧跑出真数字，再把同样的代码搬到裸机上**。

**最后三条注意事项**：

1. **`-fno-omit-frame-pointer` 必须加**——
   否则 ASan 的调用栈缺帧（只看得到 `main`，看不到是谁调的）。
2. **ASan 报错后要判断"这是不是真实场景"**——
   `-O0` 报的错在 `-O2` 下可能被优化掉（见 Q2）。
3. **裸机上 ASan 用不了**（要 libc + 运行时 + shadow memory），
   替代方案是[自己写带检查的分配器](13.1-基本堆分配和释放.md)（实测 `pool_free` 30 字节）。
