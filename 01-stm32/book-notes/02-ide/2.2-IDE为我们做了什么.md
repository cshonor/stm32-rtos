## 书这一节讲什么

**第 2 章真正值钱的只有这一节。** 书在这里回头解释：前面让你点的那些按钮，
背后到底做了什么。

把这个问题答清楚，IDE 就不是黑盒了——换任何 IDE、或者根本不用 IDE，
你都知道该敲什么。

## 一、IDE 不是编译器，是一层"替你敲命令"的壳

这是最容易混淆的一点。**IDE 自己一行代码都不编译**，它只是把你手敲的命令排成按钮。

| 你点的按钮 | 背后真正执行的 | 命令行等价物 |
|---|---|---|
| Build / 锤子图标 | `arm-none-eabi-gcc -c ... && arm-none-eabi-ld -T ...` | `make` |
| Debug / 虫子图标 | ① 起调试服务器 ② 连 gdb ③ 下载镜像 ④ 打断点 ⑤ run | `openocd` + `arm-none-eabi-gdb` |
| Run | 下载 + 复位 + 全速跑 | `openocd -c "program x.bin 0x08000000 verify reset exit"` |
| 单步 / Step Over | gdb `nexti` / `step` | 同左 |
| 变量窗口 | gdb `print` + ELF 里的 DWARF | 同左 |
| 工程向导 | 生成 Makefile / 链接脚本 / 启动文件 | 手写（[ch03](../03-embedded-system-programming/README.md)、[第 11 章 链接器](../11-linker/README.md)） |

一句话：**IDE 里唯一不属于命令行的东西，是"它替你生成了那堆配置文件"。**
而那堆文件恰恰是最该自己写一遍的——启动文件、链接脚本、编译选项，
这三样就是整个裸机开发的骨架。

## 二、三条链路与它们的命令行等价物

```
┌─ ① 构建 ──────────────────────────────────────────┐
│  main.c / startup.S                                │
│    → clang -c            (编译，见 1.5 的四步)      │
│    → ld.lld -T linker.ld (链接，见 ch11)            │
│    → llvm-objcopy -O binary  (ELF → 裸 .bin)        │
│  产物：app.elf（给 gdb）/ app.bin（给烧录器）        │
└────────────────────────────────────────────────────┘
                │
┌─ ② 烧录 ──────────────────────────────────────────┐
│  openocd（主机进程）                                │
│    ├─ USB  ── ST-Link V2-1（板载调试器）            │
│    └─ SWD  ── Cortex-M3 的 DP（DPIDR 0x1ba01477）   │
│  作用：把 .bin 写进 0x08000000 起的内部 Flash        │
└────────────────────────────────────────────────────┘
                │
┌─ ③ 调试 ──────────────────────────────────────────┐
│  openocd 开 gdb server :3333                        │
│      ↑ TCP                                          │
│  arm-none-eabi-gdb app.elf                          │
│    → target remote localhost:3333                   │
│    → 用 ELF 里的符号表/DWARF 做源码级断点            │
└────────────────────────────────────────────────────┘
```

三个关键点，书上不会讲，但不懂就会卡死：

1. **烧录进 Flash 的是 `.bin`，调试用的是 `.elf`。**
   `.bin` 是纯字节流，没有地址信息（所以 `program` 必须显式给 `0x08000000`）；
   `.elf` 带符号表和 DWARF，gdb 靠它把 `0x080000c4` 翻译成 `main.c:38`。
   两个文件来自同一次链接，**用途完全不同，别混用**。
2. **ST-Link 是板子上的另一颗芯片。** USB 那头接电脑，SWD 那头接 STM32。
   "板子没反应"要分两段排查：电脑认不认 ST-Link，ST-Link 认不认目标。
3. **调试服务器和调试器是两个进程。** openocd 是 server，gdb 是 client。

## 三、实测：三条链路逐条跑通

### 3.1 构建

```
$ make
clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -g -c startup.S -o startup_s.o
clang ... -ffreestanding -fno-builtin ... -c main.c -o main.o
ld.lld -T linker.ld --gc-sections -Map=blink_asm.map -o blink_asm.elf startup_s.o main.o
llvm-objcopy -O binary blink_asm.elf blink_asm.bin
blink_asm.elf  :
section                   size        addr
.isr_vector                 96   134217728
.text                      196   134217824
.data                        4   536870912
.bss                         8   536870916
.noinit                      4   536870924
```

`134217728 = 0x08000000`（Flash），`536870912 = 0x20000000`（RAM）。
产物 `blink_asm.bin` = **296 字节**。

### 3.2 烧录

```
$ openocd -f f103rb.cfg -c "program blink_asm.bin 0x08000000 verify reset exit"
Info : STLINK V2J28M18 (API v2) VID:PID 0483:374B
Info : Target voltage: 3.238247
Info : Unable to match requested speed 1000 kHz, using 950 kHz
Info : SWD DPIDR 0x1ba01477
Info : [stm32f1x.cpu] Cortex-M3 r1p1 processor detected
xPSR: 0x01000000 pc: 0x08000364 msp: 0x20005000     ← 还是上一版程序
** Programming Started **
Info : device id = 0x20036410
Info : flash size = 128 KiB
Warn : Adding extra erase range, 0x08000128 .. 0x080003ff
** Programming Finished **
** Verify Started **
** Verified OK **
** Resetting Target **
```

注意 `msp: 0x20005000` 这行：还没烧新程序时，栈顶已经是 `0x20005000`。
这是**上一版程序**的向量表第 0 个字——说明栈顶不是软件设的，
是**上电时硬件从 0x08000000 读出来装进 MSP 的**（[00.1](../00-mental-model/00.1-没有OS的C语言.md) 的实测佐证）。

### 3.3 调试

```
$ arm-none-eabi-gdb blink_asm.elf -batch \
    -ex "target remote localhost:3333" -ex "monitor halt" \
    -ex "info registers sp pc xpsr" -ex "x/4xw 0x08000000" \
    -ex "print/x g_has_init" -ex "print boot_stage" -ex "print g_tick"
stack_probe () at main.c:38                      ← 源码级！
sp             0x20004f80          0x20004f80
pc             0x80000c4           0x80000c4 <stack_probe+12>
0x8000000 <g_vectors>:	0x20005000	0x08000061	0x080000b5	0x080000b5
$1 = 0xa5a5a5a5
$2 = 4 '\004'
$3 = 528395
```

这一屏同时证明了四件事（[ch03](../03-embedded-system-programming/README.md) 会逐一展开）：

- `x/4xw 0x08000000` 读到的**板子上的**向量表，和主机侧 ELF 里 `.isr_vector`
  **逐字节一致** → 烧进去了，且在 0x08000000；
- `g_has_init = 0xa5a5a5a5` → `.data` 初值从 Flash 搬进 RAM 成功；
- `boot_stage = 4` → 程序已经跑进 `main`；
- `g_tick = 528395` → 循环在跑（`g_tick` 在 `.bss`，说明 `.bss` 没被踩坏）。

**这就是 IDE"变量窗口"背后的东西**：gdb 读 ELF 的 DWARF 拿到 `g_tick` 的地址，
再通过 openocd 走 SWD 把那 4 个字节读回主机。没有魔法。

## 四、与 PC / LDD- 侧的对照

| 环节 | PC / Linux 开发 | 裸机 STM32 |
|---|---|---|
| 构建 | `gcc hello.c -o hello`（默认动态链接 glibc） | `clang --target=... -ffreestanding` + 自己的链接脚本 |
| 产物运行方式 | `./hello` → 内核 loader 建进程 | 烧进 Flash，复位后**硬件**从 0x08000000 开始跑 |
| "把程序放进去"的人 | 内核（execve） | **你 + openocd** |
| 调试器 | `gdb ./hello`（直接 ptrace 本进程） | gdb → TCP → openocd → USB → ST-Link → SWD → 目标核 |
| 断点的物理实现 | 内核替换指令成 `int3` / perf 硬件断点 | **芯片里的 FPB** |
| 断点数量上限 | 软件断点几乎无限 | **硬件只有 6 个**（实测输出里明写） |
| 单步 | ptrace 单步 | SWD 的 debug 状态机 + FPB 比较器 |
| 打印 | `printf` → write(2) | 没有，除非自己移植 UART（[9.5 串口 Hello World](../09-uart-serial/9.5-串口HelloWorld.md)） |

一个值得记住的类比：**openocd 的角色 ≈ Linux 里的 `gdbserver`，
只不过它跑在主机上、通过 USB 转 SWD。** 理解了 gdbserver 的远程调试模型，
这条链路就是同一个模型的硬件版。

## 五、最小可跑的命令集

```bash
# 构建（IDE 的 Build 按钮）
make

# 烧录（IDE 的 Run 按钮）
openocd -f f103rb.cfg -c "program app.bin 0x08000000 verify reset exit"

# 调试（IDE 的 Debug 按钮，分两步）
openocd -f f103rb.cfg            # 终端 1，前台挂着，监听 :3333
arm-none-eabi-gdb app.elf -ex "target remote localhost:3333"   # 终端 2
```

```gdb
# 进了 gdb 之后，最常用的五条
(gdb) monitor reset halt        # 复位并停住（不是 continue）
(gdb) load                      # 也可以用 gdb 下载 elf（等价于 program）
(gdb) break main
(gdb) continue
(gdb) x/4xw 0x08000000          # 看内存；裸机上这是最重要的"printf"
```

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "烧录大小 = 镜像大小" | 实际按 **Flash 擦除扇区**对齐。实测 296 字节的镜像触发 `Warn: Adding extra erase range, 0x08000128 .. 0x080003ff`——擦了整 1 KiB（F1 的最小擦除单位） |
| "SWD 设 1000 kHz 就是 1000 kHz" | 实测 `Unable to match requested speed 1000 kHz, using 950 kHz`。ST-Link 分频器凑不出精确值，**这是正常的 Info** |
| "IDE 里断点随便设" | Cortex-M3 的 FPB 只有 **6 个硬件断点 / 4 个观察点**。软件断点要改 Flash，慢且耗擦写寿命 |
| "macOS 上搞嵌入式要装一堆东西" | openocd 有 darwin-arm64 原生构建（xPack，家目录解压即用）；**ST-Link 在 macOS 上免驱**；`arm-none-eabi-gdb` 只在调试时才需要 |
| "烧录命令写 `program xxx verify reset` 就够" | 少了 `exit`（或 `-c shutdown`），openocd 会**一直挂着不退**。实测第一次 2 分钟没退出，只能 pkill |
| "变量窗口是 IDE 自己实现的" | 就是 gdb 的 `print`。IDE 没做任何魔法，只是把结果画成表格 |

## 代码自测

<details>
<summary>Q1：为什么烧录用 .bin、调试用 .elf？只用一个不行吗？</summary>

不行，两者信息量不同。

- `.bin` 是 `objcopy -O binary` 抽出来的**纯字节流**，没有地址、没有符号。
  烧录时必须显式告诉 openocd "从 0x08000000 开始写"——那个地址是**你给的**，不是文件里的。
- `.elf` 带 program header（地址）、symbol table（符号→地址）、DWARF（源码行号→地址）。
  gdb 靠它才能把 `0x080000c4` 显示成 `main.c:38`。

反过来，`.elf` 其实也能烧（openocd 会解析 program header，不用给地址），
但它烧的是**所有可加载段**，调试信息不属于 `PT_LOAD` 所以不会进去。
真正的区别是：

| 用途 | 用哪个 | 为什么 |
|---|---|---|
| 量产 / 校验 | `.bin` | 保证"烧进去的字节 = 我要的字节，一个不多" |
| 调试 | `.elf` | 图它的符号和行号 |
| 用 gdb 下载 | `.elf` 或 `.bin` | `load` 命令走 ELF，`program` 走 bin |
</details>

<details>
<summary>Q2：完整链路 gdb → openocd → ST-Link → SWD → 芯片，怎么分层排障？</summary>

**从上往下一层一层确认**，每层都有对应的日志行：

| 层 | 出现的日志 | 没出现说明什么 |
|---|---|---|
| USB | `Info : STLINK V2J28M18 (API v2) VID:PID 0483:374B` | 线是充电线 / USB 口问题 / 权限 |
| SWD | `Info : SWD DPIDR 0x1ba01477` | 接线（SWCLK/SWDIO/GND）、板子没供电、复位脚被拉低 |
| 内核 | `Cortex-M3 r1p1 processor detected` | 芯片型号选错了（cfg 文件不对） |
| Flash | `device id = 0x20036410` / `flash size = 128 KiB` | 芯片读保护 / 时钟太慢 |
| gdb 连接 | `Listening on port 3333` | 端口被占（上一个 openocd 没退干净） |
| 源码级 | `xxx () at main.c:38` | 没带 `-g` / ELF 不对 / 地址对不上 |

**排障口诀：哪一行没出现，问题就在那一层。** 不要跳层猜。
</details>

<details>
<summary>Q3：为什么 `Unable to match requested speed 1000 kHz, using 950 kHz` 不用管？</summary>

这是 `Info` 不是 `Error`。SWD 时钟由 ST-Link 内部的分频器从它自己的主频分出来，
能取到的频率是**离散的**。你要求 1000 kHz，分频器只能凑出 950 kHz，
它就取最接近的、**不超过**你要求值的那一档，然后告诉你一声。

真正的故障长这样，对比一下就分得清：

| 日志 | 含义 |
|---|---|
| `Error: init mode failed (unable to connect to the target)` | SWD 没连上（接线/供电/复位脚） |
| `Warn : target was in unknown state when halt was requested` | 目标在跑但状态不明，加 `reset halt` 而不是 `halt` |
| `Error: jtag status contains invalid mode value` | 速度太高或信号质量差，**这时候才该降速** |

一句话：**只有 `Error` 才是错的，`Info`/`Warn` 要先读懂再决定要不要管。**
</details>

<details>
<summary>Q4：296 字节的镜像，为什么 openocd 说要擦到 0x080003ff？</summary>

因为 NOR Flash 的擦除粒度**远大于**写入粒度。STM32F1 内部 Flash 的最小擦除单位是
**1 KiB 页**，而写入可以按半字（2 字节）进行。

`blink_asm.bin` 是 296 = 0x128 字节，落在第 0 页（0x08000000–0x080003FF）里。
要写这一页的任何位置，必须**整页先擦成 0xFF**：

```
Warn : Adding extra erase range, 0x08000128 .. 0x080003ff
```

意思是"你只让我烧 296 字节，但我得把这一页剩下的也一起擦了"。
这不是浪费，是 Flash 的物理约束。

由此引出一个工程结论（[11.6 高级用法](../11-linker/11.6-高级用法.md) 会用到）：
**改一个字节的代价是擦一整页**，所以频繁改写的配置数据不能裸放在 Flash。
</details>

<details>
<summary>Q5：既然 gdb + openocd 全都能做，为什么工业界还是用 IDE？</summary>

因为 IDE 卖的不是"能不能做"，是**三样命令行给不了的东西**：

1. **外设寄存器视图（SVD）**：把 `0x4001100C` 展开成 `GPIOC->ODR` 的每一位、
   每个位域的名字。命令行要做同样的事得自己写脚本（`x/1xw` 之后心算位域）。
   ——这一条现在有解：VSCode + Cortex-Debug 插件同样支持 SVD。
2. **工程向导的正确性兜底**：启动文件、链接脚本、时钟初始化，
   手写出错概率不低，向导生成的是厂商验证过的。
3. **团队协作的一致性**：IDE 工程文件进版本库，所有人拿到同一套编译选项。

反过来，命令行的优势是**可解释**：每一步命令都看得见，出问题能定位到具体环节，
也容易写进 CI。

**两者不是替代关系，是"先学会原理，再用工具偷懒"的顺序关系。**
</details>
