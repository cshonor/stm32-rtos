## Q1：不用 IDE，写出"编译 + 烧录 + 调试"的三条最简命令。

```bash
make                                                   # ① 构建
openocd -f f103rb.cfg -c "program app.bin 0x08000000 verify reset exit"   # ② 烧录
openocd -f f103rb.cfg &                                # ③ 调试（终端 1）
arm-none-eabi-gdb app.elf -ex "target remote localhost:3333"              # ③ 调试（终端 2）
```

**评分点**：② 必须有 `verify reset exit`；③ 必须是两个进程，不是一条命令。

## Q2：板子插上电脑，openocd 报 `Error: init mode failed`，按什么顺序排查？

按链路从外到内，**每步看一行日志**：

| 顺序 | 检查 | 通过的样子 |
|---|---|---|
| 1 | USB 线是不是数据线 | 出现 `STLINK V2J28M18 ... VID:PID 0483:374B` |
| 2 | 板子供电（NUCLEO 的 CN2 跳线是否把 ST-Link 的 3.3V 接给目标） | 出现 `Target voltage: 3.2xxxx` |
| 3 | SWD 接线（NUCLEO 板载是直连的，外接板子才要查 SWCLK/SWDIO/GND） | 出现 `SWD DPIDR 0x1ba01477` |
| 4 | 复位脚 / 目标是否在低功耗模式 | 出现 `Cortex-M3 r1p1 processor detected` |
| 5 | cfg 文件里的芯片型号对不对 | 出现 `device id = ...` |

顺序不能跳。最常见的误判是：看着"连不上"就去降 SWD 速度，
**而真正的问题是一根充电线**。

## Q3：为什么 `program app.bin 0x08000000` 里的地址不能省，而 `program app.elf` 能省？

因为**地址信息在不在文件里**：

| 文件 | 含地址信息吗 | 所以 |
|---|---|---|
| `.bin` | ❌ 纯字节流 | 必须由你告诉 openocd 写到哪 |
| `.elf` | ✅ program header 里有 VMA | openocd 自己解析，不用给 |

⚠️ 但 `.elf` 烧的是**所有可加载段**，包括 `.noinit`、可能包括你不想覆盖的区域。
量产场景用 `.bin` + 显式地址更可控——**"烧进去的字节 = 我要的字节"**。

## Q4：同一个 `.elf`，为什么 gdb 能显示 `main.c:38`，而 `objdump` 只显示地址？

因为二者读的是 ELF 里**不同的表**：

| 工具 | 读什么 | 得到什么 |
|---|---|---|
| `objdump -d` | `.text` + 符号表（`.symtab`） | `080000c4 <stack_probe+12>:` |
| `gdb` | 上面的 + **DWARF 调试段**（`.debug_line` / `.debug_info`） | `main.c:38` |

DWARF 是 `-g` 生成的。**没加 `-g`，gdb 也只能显示地址**——

```
(gdb) info line *0x080000c4
No line number information available for address 0x80000c4
```

这是"为什么调试版必须 `-g`"的准确原因，不是"为了保险"。

## Q5：`arm-none-eabi-gdb` 和 `gdb` 有什么区别？能用系统的 gdb 吗？

**格式不同，不能随便换。**

- `arm-none-eabi-gdb`：能读 **ELF**、能按 ARM 指令集反汇编、知道 Cortex-M 的寄存器编号；
- macOS 自带的 `/usr/bin/gdb`（或 lldb）：面向 **Mach-O**，看不懂 ELF 符号表。

判断方法很简单：`file app.elf` 显示 `ELF 32-bit LSB executable, ARM, EABI5` 就该用前者。
本机实测路径：

```
~/.local/arm-gnu-toolchain-14.2.rel1-darwin-arm64-arm-none-eabi/bin/arm-none-eabi-gdb
```

⚠️ 记一个反直觉点：**编译链完全不需要这份工具链**。
clang + ld.lld 就能产出 `.elf`，`arm-none-eabi-gdb` 只是"读 ELF 的 gdb"，
只在调试时需要（也只在调试时用它的 gdb／readelf 之类）。
