# 8.03 结构体

> 书：第 8 章 复杂数据类型 · 8.03 结构体（原书 p98–118 区间内）
> 上一篇：[8.02 预处理技巧和枚举](8.02-预处理技巧和枚举.md) ｜ 下一篇：[8.04 内存中的结构体](8.04-内存中的结构体.md)
> 对应实验：主机侧 clang 23.1.0 + `--target=armv7m-none-eabi` 交叉（`_Static_assert` 校验）

## 书这一节讲什么

一句话：**结构体把一组不同类型的变量打包成一个整体**——
`struct point { int x; int y; };`。

书讲语法（声明、成员访问）。裸机上这一章的核心在
[8.12 结构体与嵌入式编程](8.12-结构体与嵌入式编程.md)：
**结构体就是寄存器块的地图**。本节先把"结构体是什么"钉死。

## 一、语法三件事

```c
struct point { int x; int y; };      /* ① 声明类型 */
struct point p = { .x = 1, .y = 2 }; /* ② 定义变量（指定初始化器） */
int a = p.x;                          /* ③ 成员访问 */
struct point *q = &p; int b = q->y;   /*    指针用 -> */
```

裸机上推荐 **指定初始化器**（`.x = 1`）：
顺序写错了编译器会按名字对齐，不会因为成员顺序调整而赋值错位。

## 二、为什么裸机必须关心结构体的内存布局

因为**结构体最常见的用途是映射寄存器块**：

```c
typedef struct {
    volatile uint32_t CRL;    /* 偏移 +0x00 */
    volatile uint32_t CRH;    /* 偏移 +0x04 */
    volatile uint32_t IDR;    /* 偏移 +0x08 */
    volatile uint32_t ODR;    /* 偏移 +0x0C */
    volatile uint32_t BSRR;   /* 偏移 +0x10 */
    volatile uint32_t BRR;    /* 偏移 +0x14 */
    volatile uint32_t LCKR;   /* 偏移 +0x18 */
} GPIO_TypeDef;

#define GPIOA ((GPIO_TypeDef *)0x40010800u)
```

这意味着：**结构体的每个成员落在哪个字节偏移，必须和芯片手册一字不差。**
差一个字节 → `GPIOA->BSRR` 就写到了 `BRR` 上 → 灯不亮，且不报错。

所以必须编译期校验（[4.05](../04-numbers-and-bitops/4.05-整数的大小和表示.md) 讲过这个手段）：

```c
#include <stddef.h>
_Static_assert(offsetof(GPIO_TypeDef, CRL)  == 0x00, "");
_Static_assert(offsetof(GPIO_TypeDef, BSRR) == 0x10, "");
_Static_assert(sizeof(GPIO_TypeDef)         == 0x1C, "");
```

## 三、结构体 vs 数组：什么时候用哪个

| | 结构体 | 数组 |
|---|---|---|
| 成员类型 | 可以不同 | 必须相同 |
| 访问方式 | 名字（`.CRL`） | 下标（`buf[i]`） |
| 布局 | **可能有填充**（[8.04](8.04-内存中的结构体.md)） | 紧密排列 |
| 裸机用途 | 寄存器块、协议帧头、配置 | 缓冲区、采样序列 |

协议帧头是结构体的另一个典型用途：

```c
typedef struct {
    uint8_t  sync;      /* 0xAA */
    uint8_t  len;
    uint16_t crc;
} __attribute__((packed)) frame_hdr_t;   /* ⚠ packed 有坑，见 8.5 */
```

## 四、裸机的两条硬约束

1. **映射寄存器的结构体，成员类型只能是定宽整数**（`uint32_t` 等），
   不能用 `int`、`enum`、位域（[8.01](8.01-枚举.md) Q2）；
2. **每个成员都要 `volatile`**——漏一个，编译器就可能把对该寄存器的访问优化掉
   （[5.14](../05-control-flow-button/5.14-反模式.md) 实测 `wait_bad` → `bx lr` 就是这类后果）。

```c
typedef struct {
    volatile uint32_t CRL;      /* ← 每个都 volatile */
    volatile uint32_t CRH;
    ...
} GPIO_TypeDef;
```

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "结构体就是打包几个变量" | 裸机上它是**寄存器块的地**图——布局错了就是写错寄存器 |
| "结构体大小 = 成员之和" | **不是**，有对齐填充（[8.04](8.04-内存中的结构体.md) 实测 S1=12、成员只占 6） |
| "`->` 和 `.` 只是写法不同" | 对；但 `->` 用于指针，寄存器映射就是"基址指针 + `->`" |
| "成员顺序随便排" | 顺序决定大小和偏移。寄存器结构体**必须按手册顺序** |
| "结构体赋值很自然" | 可能生成 `memcpy` 调用（[7.02](../07-stack-frame-functions/7.02-隐藏变量.md) 实测 `U __aeabi_memcpy`） |

## 代码自测

<details>
<summary>Q1：为什么寄存器结构体里每个成员都要 `volatile`？漏一个会怎样？</summary>

因为 `volatile` 的语义是"**每次访问都必须真的发生**"，
而编译器是按**每个成员的类型**来判断的——不是按整个结构体。

```c
typedef struct {
    volatile uint32_t CRL;
    uint32_t          CRH;      /* ← 漏了 volatile！ */
} bad_t;
```

对 `CRH` 的访问，编译器认为"这是个普通内存变量，我可以优化"：

```c
GPIOA->CRH = 0x1;  GPIOA->CRH = 0x2;   /* 可能被合并成只写一次 0x2 */
while (!(GPIOA->CRH & FLAG)) { }        /* 可能被判定为"条件不变"而删掉 */
```

实测证据（[5.14](../05-control-flow-button/5.14-反模式.md)）：
非 `volatile` 的 `while (flag == 0) { }` 被编译成**一条 `bx lr`**——
等待循环整个消失。寄存器结构体里漏一个 `volatile`，后果完全同类。

而且这类 bug **只在打开优化后出现**：
`-O0` 下一切正常，一到 `-Os` 就失效——
排查时会以为是硬件问题。

规则：**映射硬件的结构体，每个成员都 `volatile`，一个不漏。**
（CMSIS 头里就是这么写的，可以照抄它的风格。）
</details>

<details>
<summary>Q2：`offsetof` 是什么？为什么要用它校验？</summary>

`offsetof(type, member)`（在 `<stddef.h>` 里）返回**成员在结构体里的字节偏移**，
是编译期常量。

```c
_Static_assert(offsetof(GPIO_TypeDef, BSRR) == 0x10, "与 RM0008 不符");
```

为什么需要它：

1. **结构体布局可能被意外改变**——有人插了一个成员、
   改了类型、加了 `packed`、或者换编译器改了对齐规则；
2. **没有任何运行时检查会告诉你**（没有 MMU、写错寄存器不报错）；
3. `offsetof` + `_Static_assert` 把"运行时玄学"前移成"**编译期硬错误**"——
   改错的那一刻编译就炸，带着文件名和行号。

这是裸机上性价比最高的检查之一：一行代码，零运行成本。

完整用法：

```c
#include <stddef.h>
typedef struct { volatile uint32_t CRL, CRH, IDR, ODR, BSRR, BRR, LCKR; } GPIO_TypeDef;

_Static_assert(offsetof(GPIO_TypeDef, CRL)  == 0x00u, "");
_Static_assert(offsetof(GPIO_TypeDef, IDR)  == 0x08u, "");
_Static_assert(offsetof(GPIO_TypeDef, BSRR) == 0x10u, "");
_Static_assert(sizeof(GPIO_TypeDef)         == 0x1Cu, "");   /* 总大小也要对 */
```

**每个映射寄存器的结构体都该配一组这样的断言**——
这是把"芯片手册"编码进代码的方式，
也是后来换芯片/改定义时最可靠的护栏。
</details>

<details>
<summary>Q3：结构体和数组都能表示"一块连续内存"，寄存器块该用哪个？</summary>

用**结构体**——因为寄存器块的成员**宽度相同但语义不同**，而且偏移不是等间距的。

对比：

```c
/* 数组：只能按下标，偏移是"第 n 个字" */
volatile uint32_t *gpio = (volatile uint32_t *)0x40010800u;
gpio[4] = ...;        /* 这是 BSRR（偏移 0x10）？没人看得出来 */

/* 结构体：按名字，偏移由定义保证 */
GPIOA->BSRR = ...;    /* 一眼看出 */
```

三种写法的对比（[6.03](../06-arrays-pointers-strings/6.03-数组和指针算术.md) 也讲过）：

| 写法 | 可读性 | 安全性 |
|---|---|---|
| `REG32(base, off)` 宏 | 中（地址常量可见） | 高（偏移是显式字节数） |
| **结构体映射** | **高**（`GPIOA->BSRR`） | **高**（`offsetof` 可编译期校验） |
| 数组下标 `gpio[n]` | 低（n 是"第几个字"） | 低（改定义就错位） |

结构体还有一个数组做不到的优势：
**成员宽度可以不同**（虽然寄存器通常都是 32 位，
但有些外设块里混着 16 位寄存器），
以及**可以用 `offsetof` 逐个校验**。

所以 CMSIS、Linux 内核（`ioremap` + 结构体）、
Zephyr 全都用结构体映射——这是业界共识。
</details>
