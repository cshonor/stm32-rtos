# 8.05 访问未对齐数据

> 书：第 8 章 复杂数据类型 · 8.05 访问未对齐数据（原书 p98–118 区间内）
> 上一篇：[8.04 内存中的结构体](8.04-内存中的结构体.md) ｜ 下一篇：[8.06 结构体初始化](8.06-结构体初始化.md)
> 对应实验：主机侧对照 + `--target=armv7m-none-eabi`（M0 的 HardFault 结论来自手册/架构，非本机实测）

## 书这一节讲什么

一句话：**访问未对齐的数据（比如 32 位值放在奇数地址）在某些架构上会出错**。

书点了一句。这一句在裸机上的后果是**直接 HardFault**——
值得单独一篇把它讲透。

## 一、各架构的未对齐访问支持

| 内核 / 架构 | 未对齐的 32 位访问 | 后果 |
|---|---|---|
| **Cortex-M0 / M0+** | ❌ **不支持** | **HardFault**（直接崩） |
| Cortex-M3 / M4 / M7 | ✅ 支持（但慢，且**不保证原子**） | 通常能用，别依赖 |
| x86 / arm64（Mac） | ✅ 支持 | 无感 |

⚠ 上表是 ARM 架构的通用事实（来自 ARM 架构参考手册与各 Cortex-M 的 TRM），
**M0 的 HardFault 不是本仓库在真机上实测的**（本仓库的板子是 F103RB = Cortex-M3）。

## 二、翻车现场

```c
#pragma pack(1)
struct pkt { uint8_t type; uint32_t len; } __attribute__((packed));

struct pkt *p = (struct pkt *)rx_buf;    /* rx_buf 可能不是 4 字节对齐 */
uint32_t n = p->len;                      /* ← M0 上：HardFault */
```

实测（[8.04](8.04-内存中的结构体.md)）：`packed` 后 `len` 在**偏移 1**——
如果 `rx_buf` 是 4 字节对齐的，那么 `&p->len` 的地址是 `基址+1`，**未对齐**。

在 M3 上这不崩（硬件支持），但：

- 要花额外的总线周期（慢）；
- **不保证原子**：读取过程中可能被中断打断（对跨字的访问）；
- 换到 M0 就直接 HardFault——**代码不可移植**。

## 三、正确做法：按字节拼装

```c
static uint32_t read_le32(const uint8_t *b){
    return (uint32_t)b[0]
         | ((uint32_t)b[1] << 8)
         | ((uint32_t)b[2] << 16)
         | ((uint32_t)b[3] << 24);
}
uint32_t n = read_le32(rx_buf + 1);     /* 任何对齐都安全 */
```

三个收益：

1. **对齐安全**：字节访问永远对齐；
2. **字节序明确**：显式指定小端（LE），不依赖平台；
3. **可移植**：M0/M3/M4/PC 上都一样。

**顺带解决了字节序问题**：Cortex-M 是小端，
但协议（网络字节序、Modbus CRC）可能规定大端——
显式拼装同时解决对齐和字节序。

```c
static uint32_t read_be32(const uint8_t *b){      /* 大端 */
    return ((uint32_t)b[0] << 24) | ((uint32_t)b[1] << 16)
         | ((uint32_t)b[2] << 8)  | (uint32_t)b[3];
}
```

## 四、小端实测（union 观察）

```
$ clang -O2 -o un un.c && ./un
union U: size=4
u.i=0x12345678 -> b[0]=0x78 b[1]=0x56 b[2]=0x34 b[3]=0x12
```

`0x12345678` 的最低字节 `0x78` 在 **b[0]（低地址）** → 小端。
Cortex-M 也是小端（ARM 默认小端），所以按字节拼装时要按 LE 顺序。

## 五、还有哪些地方会遇到未对齐

| 场景 | 说明 |
|---|---|
| `packed` 结构体 | 本节的翻车现场 |
| 把 `uint8_t buf[]` 强转成 `uint32_t *` | `((uint32_t*)buf)[0]` —— buf 对齐未知 |
| 协议帧里的字段 | 字段偏移常常不是 4 的倍数 |
| DMA 缓冲区 | DMA 常要求对齐（有些 DMA 要求 4 字节对齐） |
| 从 Flash 读结构化数据 | 同上 |

安全写法判据：**只要"不确定对齐"，就用字节拼装/`memcpy`，不要强转指针。**

```c
uint32_t v;
memcpy(&v, buf + 1, sizeof v);      /* ✅ 安全，且 -O2 下编译成一条 ldr（对齐时） */
```

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "未对齐访问会慢一点" | M0/M0+ 上是**HardFault**，不是慢一点 |
| "M3 支持，随便用" | 支持但**不保证原子**，且换 M0 就崩——不可移植 |
| "`(uint32_t*)buf` 很方便" | buf 对齐未知 → 未对齐访问。用 `memcpy`/字节拼装 |
| "小端大端不用管" | 协议可能规定大端。显式拼装能同时解决对齐 + 字节序 |
| "`packed` 只是省空间" | 它让成员落在未对齐地址，是本节 HardFault 的直接来源 |

## 代码自测

<details>
<summary>Q1：`memcpy` 解包协议字段，性能会差吗？</summary>

不会——**编译器会把固定大小的 `memcpy` 优化成一条加载/存储指令**（当它能证明对齐时）。

```c
uint32_t v;
memcpy(&v, buf + 1, 4);        /* 4 字节，编译期已知 */
```

在 `-O2` 下 clang 会直接生成 `ldr`（如果它能推断对齐）或
未对齐安全的 `ldr`（ARMv7 支持）。**手写字节拼装通常也是同样高效**。

对比三种写法：

| 写法 | 安全性 | 性能 | 字节序 |
|---|---|---|---|
| `*(uint32_t *)(buf+1)`（强转） | ❌ 未对齐 + 严格别名违规 | 快（但可能是错的） | 依赖平台 |
| `memcpy(&v, buf+1, 4)` | ✅ | 快（编译器优化） | 依赖平台（小端） |
| `read_le32(buf+1)` 字节拼装 | ✅ | 快（通常 4 条指令或一条 `ldr`+`rev`） | **显式** |

推荐第三种，因为**字节序是显式写出来的**——
半年后读代码的人知道这是小端，而前两种要靠"目标平台是小端"这个隐含前提。

一句话：**别为了"可能的性能"用不安全的写法。先测，再决定。**
裸机上绝大多数协议解析的瓶颈根本不在这几条指令上。
</details>

<details>
<summary>Q2：怎么判断一个地址是否对齐？</summary>

用**位与**判断：

```c
static inline int is_aligned_4(const void *p){
    return (((uintptr_t)p) & 3u) == 0u;      /* 低 2 位为 0 = 4 字节对齐 */
}
```

（[6.02](../06-arrays-pointers-strings/6.02-底层细节：指针.md) 讲过：指针转整数用 `uintptr_t`，别用 `uint32_t`。）

什么时候需要判断：

1. **DMA 缓冲**：很多 DMA 控制器要求源/目的地址对齐
   （STM32F1 的 DMA 通常要求按数据宽度对齐）；
2. **调试断言**：

```c
void dma_start(const void *buf, size_t n){
    _Static_assert(...)  /* 编译期做不到（地址是运行时的） */
    if (!is_aligned_4(buf)) return -EINVAL;      /* 运行时拒绝 */
    ...
}
```

3. **确保自己的静态缓冲对齐**：

```c
static uint8_t rx_buf[256] __attribute__((aligned(4)));   /* 强制 4 字节对齐 */
```

`__attribute__((aligned(N)))` 让链接器保证该对象的地址对齐——
**这是最省事的做法**：与其运行时检查，不如声明时就要求对齐。
</details>

<details>
<summary>Q3：M3 支持未对齐访问，那我在 M3 上可以放心用 `packed` 吗？</summary>

能跑，但有三条理由建议别依赖：

**① 不可移植**：本仓库的板子 F103RB 是 M3，
但同系列还有 M0（F0 系列）、你的下一个项目可能是 M0+。
代码在 M3 上跑通 ≠ 在 M0 上能跑——而 HardFault 是最难查的（没有错误信息，只有停在那）。

**② 不保证原子**：ARMv7-M 的未对齐访问在**内部被拆成多次对齐访问**，
如果这期间来了中断，而 ISR 也访问同一块内存，就可能读到"半个新值半个旧值"。
（单次对齐的 32 位访问是原子的，未对齐的不是。）

**③ 性能**：拆成多次访问 = 多个总线周期。在 ISR 或高频路径上是真实损耗。

那 `packed` 的正确用法是什么？**只用它计算偏移，不直接解引用**：

```c
typedef struct { uint8_t sync; uint32_t len; uint16_t crc; }
    __attribute__((packed)) frame_t;

/* 用 offsetof 拿布局（编译期常量，零成本） */
#define FRAME_OFF_LEN offsetof(frame_t, len)     /* = 1 */

/* 用字节拼装读值（不产生未对齐访问） */
uint32_t n = read_le32(rx_buf + FRAME_OFF_LEN);
```

这样你得到了 `packed` 的全部好处（布局由编译器算，改定义自动同步），
又完全避开了未对齐访问。
</details>
