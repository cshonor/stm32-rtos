# 6.04 数组溢出

> 书：第 6 章 数组、指针和字符串 · 6.04 数组溢出（原书 p78–88 区间内）
> 上一篇：[6.03 数组和指针算术](6.03-数组和指针算术.md) ｜ 下一篇：[6.05 字符和字符串](6.05-字符和字符串.md)
> 对应实验：主机侧 clang 23.1.0（`-O0 -Wall -Wextra` 对比 `-fsanitize=address`）

## 书这一节讲什么

一句话：**数组下标越界是未定义行为**，写到了不属于这个数组的内存里。

书想说但没说透的是：**在裸机上它永远静默**。
PC 上你至少还有段错误；裸机上什么都没有——
这是所有 bug 里最难查的一类。

## 一、实测 A：常量下标，编译器能静态抓到

```c
int b[3] = {1,2,3};
int guard = 77;
b[3] = 99;                    /* 越界 */
```

```
$ clang -O0 -Wall -Wextra -o oob1 oob1.c
oob1.c:5:5: warning: array index 3 is past the end of the array (that has type 'int[3]') [-Warray-bounds]
    5 |     b[3] = 99;
      |     ^ ~
oob1.c:3:5: note: array 'b' declared here
1 warning generated.
$ ./oob1
b[0..2]=1,2,3 guard=77        ← 还是跑起来了，没崩
```

**clang 能在下标是编译期常量时报 `-Warray-bounds`**——这一层是免费的，必须开。
但它只是警告，程序照样编译、照样运行。

## 二、实测 B：运行时下标，编译器一声不响

```c
int b[3] = {1,2,3};
int guard = 77;
volatile int i = 3;           /* 让下标"运行时才知道" */
b[i] = 99;
```

```
$ clang -O0 -Wall -Wextra -o oob2 oob2.c
（无警告）
$ ./oob2
b[0..2]=1,2,3 guard=77 (越界写后)     ← 静默，看不出任何异常
```

**下标来自变量时，`-Wall -Wextra` 完全无感。** 而真实代码里下标几乎都来自变量
（循环计数、协议里的长度字段、用户输入的索引）。

## 三、实测 C：ASan 能抓，但裸机上没有 ASan

```
$ clang -O1 -fsanitize=address -o oob2a oob2.c && ./oob2a
==41845==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x00016d78f58c
WRITE of size 4 at 0x00016d78f58c thread T0
    #0 0x00010266fc54 in main+0x19c (oob2a:arm64+0x100003c54)
    #1 0x000192837e7c in start+0x1a1c (dyld:arm64e+0x31e7c)
```

ASan 直接报出 `stack-buffer-overflow` **并给出调用栈**——
同样是那个 bug，主机上一秒定位，裸机上可能查一周。

| 环境 | 越界的后果 |
|---|---|
| 主机 + ASan | 立刻报 `stack-buffer-overflow` + 调用栈（实测） |
| 主机 + `-Warray-bounds` | 只有**常量**下标能报（实测） |
| Linux 用户态（无 ASan） | 可能 SIGSEGV，也可能静默 |
| **裸机** | **永远静默**。无 MMU、无守卫页、无 sanitizer |

## 四、裸机上越界写会踩到什么

实测里 `b[3] = 99` 改掉的是栈上紧邻的 4 个字节。在真机上那 4 个字节可能是：

| 被踩的东西 | 症状 |
|---|---|
| 另一个全局变量 | "某个变量莫名变了"（最常见） |
| 栈上的**返回地址** | 函数返回时跳到奇怪的地方 → **HardFault** |
| 保存的 `lr` / 寄存器 | 同上，HardFault |
| 保存的 `r4–r11`（被调用者保存寄存器） | 上一层函数里的局部变量莫名变值 |
| 栈上的数组（另一个） | 两个数组互相破坏 |

**症状和原因相隔很远**——越界发生在 A 函数，崩溃在 B 函数，而且只在特定输入下复现。

## 五、五条对策（按成本排序）

1. **所有数组操作显式带长度**：函数签名里就有 `len`；
2. **`_Static_assert` 钉死大小**：`_Static_assert(NELEM(buf) == 64, "")`，
   以及"环形缓冲 SIZE 必须是 2 的幂"这类不变量；
3. **边界检查写进代码**：`if (idx >= n) return -EINVAL;`
   ——裸机上这句检查不能省（PC 上还有人靠"反正会段错误"偷懒）；
4. **哨兵 / 填充模式**：数组两端放魔数（如 `0xDEADBEEF`）定期检查；
   栈上填 `0xDEADBEEF` 用调试器看栈用了多少；
5. **主机侧先跑一遍 ASan**：把不依赖硬件的逻辑挪到 Mac 上验证，
   把这类错误挡在板子之外。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "数组越界会崩溃" | 裸机上**不会**。实测无 ASan 运行完全静默 |
| "`-Wall` 能抓越界" | 只抓**常量**下标（实测 `-Warray-bounds`）。运行时下标一声不响 |
| "运行时下标越界，ASan 能抓" | 主机上能（实测报 `stack-buffer-overflow` + 调用栈）；裸机上没有 ASan |
| "越界写会踩到数组后面" | 踩到什么取决于布局：全局变量 / **返回地址** / 保存寄存器 → HardFault |
| "边界检查浪费性能" | 裸机上这条检查是最便宜的保险。一次 HardFault 的排查成本远高于几条指令 |

## 代码自测

<details>
<summary>Q1：为什么裸机上数组越界特别危险？PC 上不也越界吗？</summary>

差别在于**有没有任何一层告诉你**。

PC/Linux 用户态有三层保护：

1. **编译器**：`-Warray-bounds`（常量下标，实测有效）；
2. **MMU**：踩到未映射页 → SIGSEGV，进程立刻死；
3. **运行时检查**：ASan（实测报 `stack-buffer-overflow` + 调用栈）、
   `_FORTIFY_SOURCE`、`-fstack-protector`。

裸机上这三层**全都没有**：

- 没有 MMU：所有地址都是"真实可访问"的物理地址，写哪儿都成功；
- 没有 ASan（要 libc + 主机运行时支持）；
- 没有进程隔离：踩坏的就是你自己的 `.data`/`.bss`/栈。

于是同一个 bug 的表现完全不同：

| | PC（有 ASan） | 裸机 |
|---|---|---|
| 何时发现 | 越界的那一刻 | 可能是几小时后 |
| 信息 | 精确的文件/行/调用栈 | 无 |
| 症状 | 立刻中止 | 某个无关变量变值 / HardFault |

所以裸机的对策必须是**前移**：
编译期断言钉大小、代码里显式检查边界、主机侧先跑 ASan。
**能挡在编译期和主机侧的，绝不留到板子上。**
</details>

<details>
<summary>Q2：`-Warray-bounds` 抓不到的情况有哪些？</summary>

实测对照：

| 情况 | clang 23 能否报 |
|---|---|
| 常量下标 `b[3]`（数组 `int b[3]`） | ✅ 报 `-Warray-bounds` |
| 下标来自 `volatile int i` | ❌ 不报 |
| 下标来自函数参数 | ❌ 通常不报（除非能内联+推导范围） |
| 指针（不是数组）做下标 | ❌ 不报（编译器不知道指向多少元素） |
| 数组**传进函数后**在函数里越界 | ❌ 不报（已经退化成指针） |

最后一条最致命，也是最日常的：

```c
void process(uint8_t *buf, size_t len){ buf[len] = 0; }   /* 编译器一无所知 */
```

这也是为什么"传数组必须传长度"（[6.01](6.01-数组.md) Q3）——
编译器不会替你记着长度，你必须在代码里带着它、并在写的那一刻检查它。

补充手段（主机侧）：

- `-fsanitize=address`：抓堆/栈/全局越界（实测有效）；
- `-fsanitize=undefined`：抓 UB（[4.09](../04-numbers-and-bitops/4.09-溢出.md) 实测过 signed 溢出）；
- `-D_FORTIFY_SOURCE=2`（Linux glibc）：抓 `memcpy`/`strcpy` 这类已知长度的操作；
- `-fstack-protector-strong`：检测栈上的返回地址被改（裸机上也能用，
  但需要自己提供 `__stack_chk_fail`）。
</details>

<details>
<summary>Q3：怀疑裸机上有越界，怎么查？</summary>

按成本从低到高：

**① 静态先看**（零成本）

```bash
clang --target=armv7m-none-eabi -Wall -Wextra -Warray-bounds -c *.c
llvm-size firmware.elf        # .data/.bss 有没有异常增长
```

**② 哨兵值**（几行代码）

```c
#define GUARD 0xDEADBEEFu
typedef struct { uint32_t guard0; uint8_t data[64]; uint32_t guard1; } buf_t;
/* 定期检查 guard0/guard1 是否还是 GUARD */
```

被踩坏的那一瞬间不会停，但下一次检查能发现"**在两次检查之间**被踩了"，
逐步缩小范围。

**③ 栈填充 + 看栈用了多少**（调试器）

- 启动时把栈区填成 `0xDEADBEEF`；
- 跑一段时间后用调试器看 `msp` 以下被改写了多少 → 估算栈峰值；
- 如果栈快满了，任何越界都会立刻踩到返回地址。

**④ MPU（如果有）**
Cortex-M3/M4 有**内存保护单元**：可以把某段 RAM 设成只读/不可访问，
越界写会触发 MemManage Fault——**精确捕获**。
代价是要配置 MPU 区域（8 个区域，粒度有要求）。

**⑤ 主机侧复现**
把出问题的那段逻辑（不碰硬件的部分）搬到 Mac 上编一份 ASan 版本跑。
实测 ASan 能直接给出 `stack-buffer-overflow` 和调用栈——
这是性价比最高的一条，因为裸机上每一次迭代都要烧录 + 复位。
</details>
