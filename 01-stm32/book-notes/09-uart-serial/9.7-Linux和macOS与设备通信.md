## 书这一节讲什么

一句话：**在 Linux / macOS 上怎么打开串口看板子输出**。

书讲的是 `screen` / `minicom` 这类工具。本机是 macOS，所以下面**macOS 部分是实测的**，
Linux 部分是文档级整理（会标注）。

## 一、实测：本机上的串口设备

```
$ ls -l /dev/cu.usbmodem2103 /dev/tty.usbmodem2103
crw-rw-rw-  1 root  wheel  0x9000007 Sep 24 20:41 /dev/cu.usbmodem2103
crw-rw-rw-  1 root  wheel  0x9000006 Sep 24 20:41 /dev/tty.usbmodem2103
```

`usbmodem` 这个前缀就是 **USB CDC ACM**（NUCLEO 的 ST-Link VCP 属于这一类）。
Linux 上同类设备叫 `/dev/ttyACM0`；如果是 FTDI/CH340 这类 USB 转串口芯片，
Linux 上是 `/dev/ttyUSB0`。

**`cu.` 和 `tty.` 必须选对**（macOS 专有坑）：

| 前缀 | 行为 | 开发板用哪个 |
|---|---|---|
| `tty.` | 打开时**等 DCD 载波**（为 modem 设计） | ❌ 可能卡住 |
| `cu.` | call-out，**不等载波**，直接打开 | ✅ **用这个** |

## 二、实测：默认参数（stty）

```
$ stty -a < /dev/cu.usbmodem2103
speed 9600 baud; 0 rows; 0 columns;
...
cflags: cread cs8 -parenb -parodd hupcl -clocal -cstopb -crtscts -dsrflow
        -dtrflow -mdmbuf
```

逐条读：

| 字段 | 值 | 含义 |
|---|---|---|
| `speed` | **9600 baud** | ⚠ **默认 9600**，不是 115200 |
| `cs8` | 8 数据位 | ✅ |
| `-parenb` | **无**校验 | ✅（`-` 表示关闭） |
| `-cstopb` | **1** 停止位 | ✅（`-cstopb` = 1 位，`cstopb` = 2 位） |
| `-crtscts` | **无**硬件流控 | ✅ |

所以默认就是 **9600 8N1 无流控**——但你的板子很可能发的是 115200。

⚠ **实测的一个坑**：用 `stty -f` 设完波特率，再查还是 9600：

```
$ stty -f /dev/cu.usbmodem2103 115200
（执行成功，无输出）

$ stty -a < /dev/cu.usbmodem2103 | head -1
speed 9600 baud;        ← 又变回 9600 了！
```

原因：`stty -f` 是**打开设备 → 设置 → 关闭**，
设备关闭后参数不保留；而 `stty -a < ...` 是新开一个连接，回到默认值。

**所以要用"打开时就指定波特率"的工具**，而不是事后 `stty`：

```bash
screen /dev/cu.usbmodem2103 115200        # ✅ 打开时指定
```

## 三、实测：本机可用的终端程序

```
$ which screen minicom
/usr/bin/screen
minicom not found

$ which cu
/usr/bin/cu
```

| 工具 | 本机状态 | 用法 |
|---|---|---|
| **`screen`** | ✅ **系统自带**（`/usr/bin/screen`） | `screen /dev/cu.usbmodem2103 115200` |
| **`cu`** | ✅ 系统自带（`/usr/bin/cu`） | `cu -l /dev/cu.usbmodem2103 -s 115200` |
| `minicom` | ❌ 未安装 | `brew install minicom` |
| **pyserial** | ❌ 未安装（两个 Python 环境都没有） | `pip install pyserial` → `python3 -m serial.tools.miniterm /dev/cu.usbmodem2103 115200` |

**推荐 `screen`**——系统自带、零安装。退出按 `Ctrl-A` 然后 `k`（kill），确认 `y`。

⚠ screen 的一个坑：**如果串口没数据，你会以为没连上**。
先确认板子在发东西（[9.5 Q3](9.5-串口HelloWorld.md) 的 `set {int}0x40004404 = 0x41`）。

## 四、Linux 部分（未在本机实测）

> ⚠ 本机是 macOS，**以下 Linux 命令未经我实测**，为文档级整理。

```bash
# 找设备
$ dmesg | tail                       # 插上板子后看内核日志
$ ls /dev/ttyACM* /dev/ttyUSB*

# 权限（最常见的问题）
$ sudo usermod -a -G dialout $USER   # 加组后要重新登录
# 或临时：
$ sudo chmod 666 /dev/ttyACM0

# 打开
$ screen /dev/ttyACM0 115200
$ python3 -m serial.tools.miniterm /dev/ttyACM0 115200

# 查/设参数
$ stty -F /dev/ttyACM0 -a
$ stty -F /dev/ttyACM0 115200 cs8 -parenb -cstopb
```

⚠ Linux 上的头号问题是**权限**：
`/dev/ttyACM0` 默认属 `dialout` 组，不在组里就 `Permission denied`。
macOS 上实测是 `crw-rw-rw-`（人人可写），所以没这个问题。

## 五、从"能看"到"能测"：脚本化

人眼看日志不够，工程上要**脚本化**——这也是选 miniterm / pyserial 的理由：

```python
#!/usr/bin/env python3
# log_capture.py —— 抓日志并加时间戳
import serial, time, sys
with serial.Serial('/dev/cu.usbmodem2103', 115200, timeout=1) as s:
    while True:
        line = s.readline()
        if not line: continue
        print(f"[{time.time():.3f}] {line.decode('utf-8', 'replace').rstrip()}")
        sys.stdout.flush()
```

⚠ 装 pyserial 要用**用户级 pip**（本机 `/opt`、`/usr/local` 写不进去，
只能装到自己的 venv 里）——本机两个 Python 环境都还没有 pyserial，需要时再装：

```bash
/Users/a0000/.workbuddy/binaries/python/envs/default/bin/pip install pyserial
```

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "串口设备就是 /dev/ttyXXX" | macOS 有两个：`tty.`（等载波，可能卡住）和 **`cu.`（用这个）** |

| "python 有 pyserial" | 实测本机**两个 Python 环境都没有**，要自己装 |

<details>
<summary>Q1：macOS 上 `cu.` 和 `tty.` 到底有什么区别？用错了会怎样？</summary>

这是从 Unix 时代 modem 留下来的二分：

| 前缀 | 全称 | 打开时的行为 |
|---|---|---|
| `tty.` | **dial-in**（拨入） | 打开时**阻塞等待 DCD（数据载波检测）**变高 |
| `cu.` | **call-out**（拨出） | **不等** DCD，直接打开 |

历史上：一台机器接了个 modem，别人打电话进来时（dial-in），
你要等载波建立才知道有连接；而你自己往外拨（call-out）时，
你主动发起，不等别人的载波。

**开发板为什么必须用 `cu.`**：

板子的 USB CDC 实现**不会提供 DCD 信号**（那本来是 modem 的概念）。
所以：

```bash
screen /dev/tty.usbmodem2103 115200    # ⚠ 可能挂在 open() 上，永远不返回
screen /dev/cu.usbmodem2103  115200    # ✅ 直接打开
```

用错的表现是"命令敲下去没反应/卡住"——很容易被误判成"串口坏了"。

**实测本机两者都存在**：

```
crw-rw-rw-  1 root  wheel  0x9000007 Sep 24 20:41 /dev/cu.usbmodem2103
crw-rw-rw-  1 root  wheel  0x9000006 Sep 24 20:41 /dev/tty.usbmodem2103
```

注意两者权限都是 `crw-rw-rw-`（**所有人可读写**），
所以权限这关在 macOS 上不是问题——**选错前缀才是**。

**记忆法**：`cu` = "**C**all **U**p"（往外拨），我们主动连板子 → 用 `cu.`。
</details>

<details>
<summary>Q2：为什么 `stty -f` 设完波特率还是 9600？</summary>

因为 **`stty -f` 设置完就关闭了设备，参数不持久**。

实测：

```
$ stty -f /dev/cu.usbmodem2103 115200
（无输出，命令成功）

$ stty -a < /dev/cu.usbmodem2103 | head -1
speed 9600 baud;          ← 又回到 9600
```

`stty -f` 的工作方式是：**打开设备 → `tcsetattr()` → 关闭**。
设备（这里是 USB CDC）在最后一次关闭后会把线路参数**重置为默认值**。

而 `stty -a < /dev/...` 是**新开一个连接**，读到的是默认值。

**正确的做法**：让**持有设备的那个进程**去设置，即"打开时指定"：

```bash
screen /dev/cu.usbmodem2103 115200          # ✅ screen 自己 open 时设
cu    -l /dev/cu.usbmodem2103 -s 115200     # ✅
python3 -m serial.tools.miniterm /dev/cu.usbmodem2103 115200   # ✅
```

如果想在一个**已经打开**的终端会话里改（比如 screen 里再改），
那 `stty -f` 是有效的——因为 screen 还持有设备，不会因为 stty 关闭而重置：

```bash
screen /dev/cu.usbmodem2103 9600
# 在另一个终端里：
stty -f /dev/cu.usbmodem2103 115200         # 这次生效（screen 还开着）
```

**结论**：

- 开新连接 → **用工具的参数指定波特率**，别指望 `stty -f` 持久；
- 改已经打开的连接 → `stty -f` 有效；
- 查当前参数 → `stty -a < /dev/xxx`（但读到的是默认值，参考价值有限）。

⚠ 顺带一个：`screen` 里改波特率是可以的（`Ctrl-A :` 然后 `exec ... !!`），
但最简单还是**退出重开**。
</details>

<details>
<summary>Q3：主机收不到数据，怎么一层层排查？</summary>

按"从物理到逻辑"，每层都能独立验证：

**① 主机认不认设备（实测过）**

```bash
$ ls /dev/cu.usbmodem*        # 本机实测：/dev/cu.usbmodem2103
```

有 → USB 通；没有 → 线 / 供电 / 驱动。（macOS 上不需要装驱动。）

**② 参数对不对（实测过）**

```bash
$ stty -a < /dev/cu.usbmodem2103 | head -1
speed 9600 baud;              # ⚠ 默认 9600
$ screen /dev/cu.usbmodem2103 115200      # 用参数指定
```

**最省事的一招：先试 9600。**
如果 115200 是乱码而 9600 能读 → 说明板子的实际波特率比你想的低
（典型是按 72 MHz 算了 BRR 但实际是 8 MHz，差 9 倍——见
[9.4 Q2](9.4-串行通信简史.md)）。

**③ 板子到底有没有发（用调试器，不依赖串口）**

```
(gdb) x/1xw 0x4002101C        # RCC_APB1ENR：bit17(USART2) 是否为 1
(gdb) x/1xw 0x40004408        # USART2_BRR：分频值
(gdb) x/1xw 0x4000440C        # USART2_CR1：UE/TE (0x200C?)
(gdb) x/1xw 0x40010800        # GPIOA_CRL：PA2/PA3 配对了没
```

**④ 直接写 DR 试一下（最强的一招）**

```
(gdb) set {int}0x40004404 = 0x41      # 直接往 USART2_DR 写 'A'
```

主机能收到 `A` → **硬件链路和参数全通**，问题在你的代码。
收不到 → 问题在初始化（时钟 / 引脚 / BRR / UE）。

**⑤ 用哪个串口（NUCLEO 的头号坑）**

**USART2（PA2/PA3）**才接到 ST-Link 的 VCP。
代码用 USART1（PA9/PA10）的话，板载 USB 口永远收不到——
要么改代码用 USART2，要么从 PA9/PA10 飞线接外部 USB-TTL。
详见 [9.5 Q3](9.5-串口HelloWorld.md)。

**口诀**：
**先证明硬件能通（④），再证明参数对（②），最后才怀疑自己的代码。**
第 ④ 步把问题一刀切成两半，是最省时间的一招。
</details>
