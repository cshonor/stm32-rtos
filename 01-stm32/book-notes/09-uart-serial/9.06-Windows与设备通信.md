## 书这一节讲什么

一句话：**在 Windows 上用什么程序打开串口、怎么看板子发来的东西**。

书给的是 Windows 的操作流程（PuTTY、设备管理器、COM 口）。
这一节的价值不在"点哪个按钮"，而在**理解三件事**：

1. **COMx 是什么**（Windows 的串口命名）；
2. **驱动从哪来**（ST-Link VCP 的 USB 驱动）；
3. **USB CDC 和真串口的差别**（这决定了你能不能设波特率）。

## 一、Windows 的串口叫 COMx

| | 设备名 | 例子 |
|---|---|---|
| Linux | `/dev/ttyUSB0`、`/dev/ttyACM0` | 由 udev 自动建节点 |
| macOS | `/dev/cu.usbmodem*`、`/dev/tty.usbmodem*` | 实测见 [9.07](9.07-Linux和macOS与设备通信.md) |
| **Windows** | **COM3、COM4…** | 设备管理器里分配 |

⚠ Windows 的一个老毛病：**COM 号会变**。
换个 USB 口就可能从 COM3 变成 COM5——因为 Windows 按"首次见到该设备的端口"分配。
排查时先在**设备管理器 → 端口 (COM 和 LPT)** 里确认当前是几号。

## 二、驱动：ST-Link VCP

NUCLEO 板载 ST-Link 的虚拟串口在 Windows 上需要驱动：

| 方式 | 说明 |
|---|---|
| **ST 官方驱动** | `STSW-LINK009`（ST-Link/V2 USB driver），装完出现 "STMicroelectronics STLink Virtual COM Port" |
| **WinUSB / libusb** | 给 OpenOCD / pyocd 用，**不产生 COM 口**（那是调试通道，不是串口） |

⚠ 容易混的一点：**ST-Link 在 Windows 上会枚举成两个设备**：

1. **调试接口**（ST-Link Debug，给 CubeIDE / OpenOCD 用）；
2. **虚拟串口**（STLink Virtual COM Port，就是板子的 USART2）。

装错驱动 / 只装了一个，表现就是"能下载程序但收不到串口数据"。

## 三、用什么终端程序

| 工具 | 特点 |
|---|---|
| **PuTTY** | 最经典。选 "Serial"，填 `COM3` 和 `115200` |
| **Tera Term** | 嵌入式常用，支持脚本、支持发送文件 |
| **VSCode + Serial Monitor 插件** | 和代码在一起，方便 |
| **`mode` 命令 + `copy`**（cmd） | `mode COM3: baud=115200 parity=n data=8 stop=1` |
| **PowerShell** | 需要 .NET `System.IO.Ports.SerialPort`，或装 pyserial |

⚠ PuTTY 的一个坑：**默认会做"行尾转换"和本地回显**。
裸机日志一般只发 `\n`，PuTTY 显示正常；
如果你发命令给板子，要注意它发出的是 `\r` 还是 `\r\n`
（在 `Terminal` 设置里可以配 "Implicit CR in every LF"）。

## 四、CDC / VCP 的一个关键事实：波特率其实是"假"的

这是本节最值得记住的一条（也适用于 macOS/Linux 的 usbmodem）：

**USB CDC（虚拟串口）是 USB 批量传输，UART 参数不真正生效。**

```
MCU --UART(115200)--> ST-Link --USB CDC--> PC
        ↑ 这一段是真的 UART             ↑ 这一段没有波特率概念
```

所以：

1. **主机端设的波特率不影响 USB 段的速率**——只影响 ST-Link 和 MCU 之间那段；
2. 但如果 PC 设 9600 而板子发 115200，**ST-Link 那边会丢/错数据**——
   因为它按 9600 去采样；
3. 反过来：有些 VCP 实现**忽略**主机设的波特率（一直按自己配的跑），
   这会造成"设错了也能收到"的假象——**别依赖这个**。

**结论：两边都要设对。** 不要因为"好像设错了也能通"就不管。

## 五、排查清单（Windows 特有）

| 现象 | 查什么 |
|---|---|
| 设备管理器里没有 COM 口 | 驱动没装 / USB 线是纯充电线 / 板子没供电 |
| 有 COM 口但打不开 | 被别的程序占用（串口是**独占**的，两个程序不能同时开） |
| 能打开但全是乱码 | 波特率不对（见 [9.04 Q2](9.04-串行通信简史.md)） |
| 能下载程序但串口没数据 | 只装了调试驱动，VCP 驱动没装；或者程序用的是 USART2 而不是 USART1 |
| COM 号变了 | 换 USB 口导致的，去设备管理器确认当前号 |

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "插上就有 COM 口" | **要装驱动**（STSW-LINK009）。而且 ST-Link 会枚举成**两个**设备（调试 + VCP） |
| "COM3 永远是 COM3" | **会变**。换 USB 口就可能变，去设备管理器确认 |
| "串口设 115200 就是 115200" | 对 USB CDC 来说，**主机端的值只是"告诉对端我期望多少"**；MCU↔ST-Link 那段才是真 UART |
| "波特率设错了应该收不到" | ⚠ 有些 VCP 实现忽略主机设置，造成"设错也能通"的假象——别依赖 |
| "两个终端能同时看一个串口" | ❌ 串口是**独占**设备，第二个程序打开会失败 |

## 代码自测

<details>
<summary>Q1：为什么 Windows 上串口叫 COM3 而 Linux/macOS 是 /dev/ttyXXX？</summary>

历史 + 设计哲学的差别：

**Windows：COM 口来自 DOS/PC 兼容机的遗留**

- `COM1`/`COM2` 是 1981 年 IBM PC 上的 8250 UART 的名字；
- Windows 延续了这个编号，USB 转串口设备**也分配 COM 号**（从 COM3 往上）；
- 编号由系统在"设备首次出现在某个 USB 口"时分配，存在注册表里 → **换口就变号**。

**Unix：一切皆文件**

- Linux：`/dev/ttyUSB0`（FTDI/CH340 这类 USB 转串口）、`/dev/ttyACM0`（USB CDC ACM，NUCLEO 属于这类）；
- macOS：`/dev/cu.usbmodem*`（callout）/ `/dev/tty.usbmodem*`（dial-in），
  实测本机有 `/dev/cu.usbmodem2103`；
- 节点由内核/udev 动态创建，**名字里带设备信息**，不太会"变号"。

**macOS 上 `cu.` 和 `tty.` 的差别**（这个容易踩）：

| 前缀 | 全称 | 行为 |
|---|---|---|
| `tty.` | dial-in | 打开时会**等待**载波信号（DCD）；适合真正的 modem |
| `cu.` | call-out | **不等待** DCD，直接打开 |

**连开发板要用 `cu.` 开头那个**——因为板子不会给 DCD 信号，
用 `tty.` 可能打开时卡住。这是 macOS 上"screen 打不开串口"的常见原因。

（这条是 macOS 实测得出的，Windows 那边没有这个二分。）
</details>

<details>
<summary>Q2：USB 虚拟串口（CDC）和真正的串口有什么不一样？</summary>

三条实质性差别：

**① 波特率只是"约定"，不是物理速率**

```
MCU ==真UART(115200)==> ST-Link ==USB批量传输==> PC
```

USB 段是 12/480 Mbps 的批量传输，**根本没有"每秒几个 bit"的概念**。
主机设的 115200 只是通过 USB 的控制传输**告诉 ST-Link**"请按 115200 和 MCU 说话"。

所以：
- 主机设的值**不影响** USB 段速度；
- 但**必须和 MCU 的一致**，否则 ST-Link↔MCU 那段会错。

**② 没有真正的"调制解调器控制信号"**

RTS/CTS/DTR/DSR 这些在真串口上是电平，在 CDC 里是**USB 控制消息**（可选实现）。
很多 VCP 实现根本不实现硬件流控——所以**高速通信时 CDC 更容易丢字节**。

**③ 延迟特性不同**

USB 是**轮询**的（主机每 1 ms 问一次设备），所以：
- CDC 的单向延迟典型 **1–2 ms**，比真串口（几十 µs）高；
- 数据会被攒成 USB 包批量上报 → 你看到的输出是**一坨一坨**的，不是逐字节的。

**工程影响**：

| 场景 | 结论 |
|---|---|
| 调试日志 | ✅ 完全够用（延迟无所谓） |
| 实时命令交互 | ⚠ 1–2 ms 延迟可接受，但别当"实时" |
| 高速数据流（>100 KB/s） | ❌ 别用 CDC。用真 USB 批量端点，或者接受丢字节 |
| 需要硬件流控 | ❌ CDC 多半不支持，要在协议层做流控（ACK / 窗口） |

**一句话**：CDC 是"方便"，不是"等价替代"。
调试用很爽，做产品的高速通信要重新评估。
</details>

<details>
<summary>Q3：Windows 上收不到数据，按什么顺序排查？</summary>

（⚠ 本机是 macOS，**以下为本节未实测的文档级整理**，顺序本身是通用的。）

**① 有没有 COM 口**

设备管理器 → 端口 (COM 和 LPT) → 有没有 "STMicroelectronics STLink Virtual COM Port (COMx)"。
- 没有 → 驱动 / USB 线 / 供电问题；
- 有黄色感叹号 → 驱动没装好。

**② 号对不对**

记下当前的 COMx。**换过 USB 口就重新确认**。

**③ 端口有没有被占用**

串口是**独占**设备。CubeIDE 的 Serial Monitor、之前没退出的 PuTTY、
甚至某些 IDE 插件都会占着。全都关掉再试。

**④ 参数对不对**

```
mode COM3: baud=115200 parity=n data=8 stop=1        # cmd 里查/设
```

或在 PuTTY 里：Serial line = `COM3`，Speed = `115200`，
Connection type 选 **Serial**（不是 SSH/Telnet——这是新手最常见的点错）。

**⑤ 板子到底有没有发**

和 [9.04 Q2](9.04-串行通信简史.md) 一样，用调试器绕过代码：

```
(gdb) set {int}0x40004404 = 0x41       # USART2_DR 直接写 'A'（NUCLEO 是 USART2）
```

能收到 `A` → 链路和参数都对，问题在你的代码。
收不到 → 问题在初始化（时钟 / 引脚 / BRR / UE）。

**⑥ 用哪个串口**

NUCLEO-F103RB：**USART2（PA2/PA3）**才接到 ST-Link。
如果你的代码用的是 USART1（PA9/PA10），板载 USB 口**永远收不到**（[9.05 Q3](9.05-串口HelloWorld.md)）。

**口诀：先证明硬件通，再证明参数对，最后才怀疑自己的代码。**
</details>
