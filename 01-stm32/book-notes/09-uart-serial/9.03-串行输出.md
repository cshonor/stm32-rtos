# 9.03 串行输出

> 书：第 9 章 STM 上的串口输出 · 9.03 串行输出（原书 p119–134 区间内）
> 上一篇：[9.02 定义我们的 putchar](9.02-定义我们的putchar.md) ｜ 下一篇：[9.04 串行通信简史](9.04-串行通信简史.md)
> 对应实验：`--target=armv7m-none-eabi -mcpu=cortex-m3`（`mini_printf` 的 `.text` 大小与栈用量实测）

## 书这一节讲什么

一句话：**把 `putc` 组装成"输出一串字符"的能力**——
`puts`、`printf`，以及它们背后的**缓冲**问题。

书这一节在搭输出体系。裸机上真正要紧的是**两个数字**：
**代码占多少 Flash** 和 **发一串要多久**。这两个数字决定你的日志能写多密。

## 一、从 `putc` 到 `puts` 到 `printf`

```c
int uart_putc(int c);                        /* 9.2：一个字节 */
void uart_puts(const char *s){ while (*s) uart_putc((int)(uint8_t)*s++); }
int  mini_printf(const char *fmt, ...);      /* 本章的终点 */
```

层次关系：

```
mini_printf  →  格式化（%d %u %x %s）
             →  put_uint（除法拆位）
             →  uart_putc
             →  等 TXE → 写 USART1_DR
```

每一层都只加"翻译"，不加"魔法"。这就是裸机输出体系和 PC 上最大的差别——
**PC 上中间几层是内核和 libc 写的，裸机上全是你写的**。

## 二、实测：整条输出链路只占 340 字节 Flash

```c
/* uart1_putc + put_uint + mini_printf，支持 %d %u %x %s %c %% */
```

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding -Os -c mp.c
$ llvm-size mp_os.o
   text    data     bss     dec     hex filename
    340       0       0     340     154 mp_os.o

$ llvm-nm -u mp_os.o                 ← 未定义符号：空
（没有任何 __aeabi_* / libc 依赖）
```

**340 字节**，而且**零外部依赖**（`llvm-nm -u` 输出为空，
连 `__aeabi_memcpy` 都没有——因为全程没有内存拷贝）。

`-O0` 下是 548 字节。**340 vs 548**——优化等级直接决定你的日志系统占多少 Flash。

对照：一个完整 `printf`（带浮点）通常 **10–30 KB**。
NUCLEO-F103RB 的 Flash 是 **128 KB**——
**一个 `printf` 就吃掉 8%–23% 的 Flash**。这就是为什么裸机上要自己写。

栈用量实测（`-fstack-usage`）：

```
-Os：mini_printf 40 B   put_uint 24 B      （uart1_putc 被内联，无独立条目）
-O0：mini_printf 48 B   put_uint 48 B   uart1_putc 4 B
```

`mini_printf` 的栈用量 **40–48 字节**——在 20 KB 栈预算里完全不算什么，
但要知道它最大的开销是 `put_uint` 里的 `char tmp[16]`。

## 三、实测：`put_uint` 的边界值

```c
static void put_uint(unsigned v, unsigned base, int upper){
    char tmp[16]; int n = 0;
    do { unsigned d = v % base;
         tmp[n++] = (d<10)?(char)('0'+d):(char)((upper?'A':'a')+d-10);
         v /= base; } while (v);
    while (n) uart1_putc(tmp[--n]);        /* 逆序输出 */
}
```

主机侧跑逻辑（把 `uart1_putc` 换成 `putchar`）：

```
$ clang -O2 -o mph mph.c && ./mph
115200
deadbeef
0                     ← 用 do-while，v=0 也能输出一个 '0'
4294967295            ← UINT32_MAX 完整输出
len=29
```

三个设计点：

1. **用 `do-while` 而不是 `while`**：`v == 0` 时也要输出一个 `'0'`
   （`while` 版本会输出空字符串——这是个很容易漏的 bug）；
2. **`tmp[16]` 够用**：32 位无符号数在**二进制**下最多 32 位，
   但我们在 10/16 进制下最多 `4294967295`（10 位）、`FFFFFFFF`（8 位）——
   **16 字节对 10/16 进制绰绰有余**。⚠ 但如果支持 `%b`（二进制）就需要 32 字节；
3. **先逆序存、再逆序输出**：避免递归或反转操作。

## 四、算一笔账：发一串字符要多久

115200 bps、8N1 = 每字节 **10 bit**（起始 + 8 数据 + 停止）：

```
1 bit  = 1/115200  = 8.68 µs
1 字节 = 86.8 µs
吞吐   = 115200/10 = 11520 字节/秒 ≈ 11.5 KB/s
```

| 输出内容 | 字节数 | 115200 下耗时 | 9600 下耗时 |
|---|---|---|---|
| `"\n"` | 1 | 86.8 µs | 1.04 ms |
| `"ok\n"` | 3 | 260 µs | 3.1 ms |
| `mini_printf("v=%d\n", 1234)` | 7 | **608 µs** | 7.3 ms |
| 一行 40 字符日志 | 40 | **3.5 ms** | 41.7 ms |

**在 1 kHz 控制循环（周期 1000 µs）里，一行 40 字符的日志就吃掉 3.5 个周期。**
这是裸机日志最容易被忽视的成本——不是 Flash，是**时间**。

⚠ 而这段时间 CPU **完全是空转的**（轮询等 TXE）。

## 五、缓冲：要不要加？

| 方案 | CPU 占用 | 复杂度 | 适用 |
|---|---|---|---|
| **无缓冲**（每字节等 TXE） | 100% 空转 | 最低 | 日志（本章） |
| **软件环形缓冲 + 中断发送** | 接近 0 | 中（[10.04 用缓冲区提速](../10-interrupts/10.04-用缓冲区提速.md)） | 协议通信、大数据量 |
| **DMA** | 0 | 高 | 高速流 |

**调试日志我倾向"无缓冲"**，三个理由：

1. 日志是"卡住也要打出来"的东西——卡住本身也是信息（说明系统卡在这）；
2. **HardFault handler 里能用**：不依赖 NVIC 和中断优先级；
3. 如果加了缓冲，HardFault 时缓冲区里没发出去的内容**就丢了**——
   而你最需要的恰恰是崩溃前的最后几行。

⚠ 但要做**节流**：见 [9.01 Q3](9.01-一次写一个字符的字符串.md) 的"每秒最多一次"。

## 六、格式化字符串的 Flash 成本

```c
mini_printf("temp=%d C\n", t);
```

`"temp=%d C\n"` 这 10 个字节在 **`.rodata`**（Flash），不是 RAM。
100 条这样的日志 = 1–2 KB Flash。

⚠ 一个裸机常见浪费：**`__FILE__` / `__LINE__` 宏**看着方便，
但每条断言里的 `__FILE__` 都是完整路径字符串：

```c
ASSERT(x);   /* 展开后带 "/Users/.../src/drv/uart.c" —— 每次调用点一份 */
```

在 128 KB Flash 上，几十处断言就能吃掉几 KB。要用就**统一到一个函数里**：

```c
void assert_failed(const char *file, unsigned line);   /* 字符串只存一份（如果编译器合并） */
```

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "输出就是写一个字符的循环" | 对，但成本是**每个字节 86.8 µs**（115200），一行日志 3.5 ms |
| "用标准 `printf` 就行" | freestanding 下**没有 libc**（ch01 实测）。完整 printf 要 10–30 KB Flash |
| "自己写 printf 很麻烦" | 实测：340 字节 Flash、40 字节栈、`llvm-nm -u` **零外部依赖** |
| "`put_uint` 用 while 循环" | ❌ `v==0` 会输出空串。**必须用 `do-while`**（实测 `put_uint(0)` → `0`） |
| "加缓冲总是更好" | 日志**不加**：HardFault 时缓冲区内容会丢，而你最需要那几行 |
| "日志想打就打" | 一行 40 字符 = 3.5 ms。1 kHz 循环里打 3 行就用光 CPU 预算 |

## 代码自测

<details>
<summary>Q1：为什么要自己写 `mini_printf`？接 newlib 不行吗？</summary>

能接，但代价和收益不成正比。三层理由：

**① freestanding 下根本没有 libc**

ch01 实测过：C11 §4p6 只保证 7 个头文件，没有 `<stdio.h>`。
本仓库又是 `-nostdlib`，所以连"链接一个 libc"这一步都不存在。

**② 接 newlib 还要写 syscall 桩**

newlib 的 `printf` 最终会调 `_write()`、`_sbrk()` 这些桩函数。
裸机上这些要么你自己写（`_write` 里调 `uart_putc`），要么链接错误。
写桩本身不难，但**你要理解 newlib 的整个 reentrancy 结构**——学习成本比写个 mini printf 高。

**③ 代价实测**

| | 完整 printf（newlib） | 自写 mini_printf（实测） |
|---|---|---|
| Flash | **10–30 KB**（含浮点格式化） | **340 字节**（`-Os`） |
| RAM | 可能用 malloc | 0 |
| 栈 | 几百字节 | **40 字节**（`-Os` 实测） |
| 外部依赖 | 一堆 `__aeabi_*` / libc | **零**（`llvm-nm -u` 输出为空） |
| `%f` | 支持（软件浮点，几百 µs 一次） | 不支持（**这是有意的**） |

F103 只有 **128 KB Flash**——完整 printf 占 8%–23%，而它 90% 的功能你永远用不到。

**④ `%f` 在 M3 上尤其不划算**

Cortex-M3 **没有 FPU**，浮点是软件模拟。一次 `%f` 几百 µs 到几 ms。
裸机调试里，浮点值通常是先乘 1000 转成整数再打（"毫伏"、"毫度"），
既快又避免了浮点格式化的依赖。

**结论**：日志只需要 `%d %u %x %s %c %%`——
实测 340 字节、零依赖、够用。**这就是本仓库的选择。**

⚠ 自写时唯一必须补的是**长度限制**：
标准 `snprintf` 有 `size` 参数就是为了防溢出，
裸机上缓冲区溢出是**静默的**（[ch06 6.04](../06-arrays-pointers-strings/6.04-数组溢出.md) 实测）。
所以目标缓冲要么足够大，要么带长度检查。
</details>

<details>
<summary>Q2：`put_uint` 里为什么用 `do-while`？用 `while` 会怎样？</summary>

因为 `v == 0` 时 `while` 版本会**什么都不输出**。

```c
/* ❌ while 版 */
static void put_uint_bad(unsigned v, unsigned base){
    char tmp[16]; int n = 0;
    while (v) { tmp[n++] = ...; v /= base; }      /* v=0 → 一次都不进 */
    while (n) uart1_putc(tmp[--n]);               /* n=0 → 什么都不发 */
}
/* put_uint_bad(0, 10) → 输出空字符串，而正确结果是 "0" */

/* ✅ do-while 版 */
static void put_uint(unsigned v, unsigned base, int upper){
    char tmp[16]; int n = 0;
    do { ... } while (v);                          /* v=0 也进一次，得到 '0' */
    while (n) uart1_putc(tmp[--n]);
}
```

实测（主机侧跑同样逻辑）：

```
put_uint(0u, 10)          → "0"           ← do-while 正确
put_uint(115200, 10)      → "115200"
put_uint(0xDEADBEEF, 16)  → "deadbeef"
put_uint(4294967295u, 10) → "4294967295"  ← UINT32_MAX 也正确
```

这是那种**只在边界值出现**的 bug：你测了 1、123、12345 都对，
上线后某个计数器刚好是 0，日志里那个字段就**凭空消失**了。

**第二个设计点：`tmp[16]` 够不够？**

- 十进制：32 位无符号最大 `4294967295` = **10 位**；
- 十六进制：最大 `FFFFFFFF` = **8 位**；
- 所以 16 字节对 `%d %u %x` **绰绰有余**。

⚠ 但如果你要支持 **`%b`（二进制）**，32 位需要 **32 字节**——`tmp[16]` 就会溢出。
这是"以后加功能时踩的坑"，所以写代码时最好注释清楚：

```c
char tmp[16];   /* 够 32 位数的 10/16 进制；若要 %b 需 32 */
```

**第三个点：为什么先逆序存再逆序出？**

拆位是**从低位到高位**（`v % base` 先拿到个位），
但打印要**从高位到低位**。所以存进 `tmp` 是低位在前，
输出时 `--n` 倒着取，正好反过来。
这比"先算位数再从高位拆"简单，也比递归省栈（[ch07 7.05](../07-stack-frame-functions/7.05-递归.md) 讲过裸机别递归）。
</details>

<details>
<summary>Q3：日志要不要加缓冲？我的 HardFault 日志总是丢是为什么？</summary>

**丢日志的原因通常就是"加了缓冲"**。

两种实现的对比：

```c
/* A. 无缓冲（本章）：每个字节等 TXE 直接写 DR */
void uart_putc(char c){ while((USART1_SR&TXE)==0u){} USART1_DR=c; }

/* B. 缓冲 + 中断发送（ch10） */
void uart_putc(char c){ ring_push(&tx_ring, c); enable_tx_irq(); }
/* 真正的发送发生在 ISR 里 */
```

HardFault 发生时：

| | A 无缓冲 | B 缓冲 |
|---|---|---|
| 崩溃前已发出的日志 | ✅ 都在主机上 | ⚠ 只发出 ISR 处理过的那部分 |
| 缓冲区里还没发的 | 不存在这个问题 | ❌ **全丢** |
| 依赖 NVIC 工作正常？ | ❌ 不依赖 | ✅ 依赖（HardFault 时中断可能被屏蔽） |
| 能否在 HardFault handler 里用 | ✅ 能（轮询不依赖中断） | ⚠ 不能（ISR 不会被调用） |

**关键**：HardFault 时你最需要的恰恰是**崩溃前的最后几行**，
而那几行恰好还在缓冲区里没发出去——**永远看不到**。

**所以规则**：

| 输出 | 方案 |
|---|---|
| 调试日志 / 断言 / HardFault 信息 | **无缓冲轮询**（本章） |
| 协议通信 / 大数据量 | 环形缓冲 + 中断（ch10） |
| 高速流 | DMA |

如果两者都要，可以做**双通道**：

```c
void log_putc(char c){ while((USART1_SR&TXE)==0u){} USART1_DR=c; }   /* 日志：直接写 */
int  proto_write(const uint8_t*, size_t);                             /* 协议：走缓冲+中断 */
```

⚠ **注意混用时的竞态**：日志直接写 DR、协议走中断，
两者都动 `USART1_DR` 时要保证不会互相踩（简单做法：协议发送期间日志也入队，
或者干脆分时用两个串口）。

**无缓冲的唯一代价是 CPU 空转**（每字节 86.8 µs @ 115200）。
用**节流**解决（[9.01 Q3](9.01-一次写一个字符的字符串.md)），而不是用缓冲解决。
</details>
