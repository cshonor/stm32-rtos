# 11.01 编译和链接的内存模型

> 书：第 11 章 链接器 · 11.01 编译和链接的内存模型（原书 p154–173 区间内）
> 下一篇：[11.02 链接过程](11.02-链接过程.md)
> 对应实验：`ld.lld 23.1.0` 真实链接 + `-Map=` map 文件 + `llvm-readelf -S` / `llvm-objcopy`

## 书这一节讲什么

一句话：**编译产出的 `.o` 里地址都是"相对的/未定的"，链接器负责给每个段和符号定下最终地址**。

书讲的是模型。裸机上这个模型有个 PC 上没有的关键点：
**没有操作系统帮你加载，所以"地址"必须是链接期就定死的物理地址。**

## 一、实测：一个真实链接的 map 文件

本节的实测来自一次**真的链接**（clang 编译 → `ld.lld -T linker.ld -Map=`）：

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding -Os -c startup.c main.c
$ ld.lld -T linker.ld -Map=blink.map --gc-sections -o blink.elf startup.o main.o

$ cat blink.map
```

## 二、VMA 和 LMA：`.data` 的"双重身份"

看 `.data` 那一行：**VMA = `0x20000000`，LMA = `0x0800084`**。

| 缩写 | 全称 | 含义 |
|---|---|---|
| **VMA** | Virtual Memory Address | **运行时**这个段在哪（RAM） |
| **LMA** | Load Memory Address | **加载**时这段内容存在哪（Flash） |

为什么 `.data` 必须有两个地址？

```
编译/链接时：初值 0xA5A5A5A5 是一串字节 → 必须存在非易失的 Flash
运行时    ：它是变量，要能被写        → 必须在 RAM
```

**判据两问**：

1. "这段内容掉电后必须还在吗？" 在 → **LMA 在 Flash**；
2. "这段运行时要被写吗？" 要 → **VMA 在 RAM**。

两个答案不同 → VMA ≠ LMA。

启动代码的工作就是把字节从 LMA 搬到 VMA（[ch03](../03-embedded-system-programming/README.md)）：

```c
void Reset_Handler(void){
    uint32_t *src = &_sidata, *dst = &_sdata;
    while (dst < &_edata) *dst++ = *src++;      /* LMA → VMA */
    for (uint32_t *p = &_sbss; p < &_ebss; ) *p++ = 0;   /* .bss 清零 */
    main();
}
```

**在 C 代码看来，变量从一开始就在 RAM 里**——因为搬运发生在 `main` 之前。

链接脚本里对应的一行是 `>RAM AT>FLASH`。

## 三、实测：`.bss` 不占 Flash（`NOBITS`）

```
$ llvm-readelf -S blink.elf
  [Nr] Name              Type            Address  Off    Size   ES Flg
  [ 1] .isr_vector       PROGBITS        08000000 010000 000010 00   A
  [ 2] .text             PROGBITS        08000010 010010 000074 00  AX
  [ 3] .data             PROGBITS        20000000 020000 000004 00  WA
  [ 4] .bss              NOBITS          20000004 020004 000004 00  WA
```

`.bss` 的类型是 **`NOBITS`**——它在文件里**不占任何字节**，只有一个"运行时要占 4 字节"的声明。

看烧录镜像就明白了：

```
$ llvm-objcopy -O binary blink.elf blink.bin
blink.bin = 136 字节
```

算一遍：

```
.isr_vector 16 + .text 116 + .data（初值）4 = 136     ← .bss 的 4 字节不在里面！
```

**136 而不是 140**——这就是 `NOBITS` 的意义：`.bss` 的内容全是 0，
不需要存，启动时清零就行。

## 四、内存模型：地址是**物理**的

| | PC / Linux | 裸机 STM32 |
|---|---|---|
| 地址性质 | **虚拟**（页表映射） | **物理**（没有 MMU） |
| 谁定地址 | 内核的 ELF loader + `mmap` | **链接脚本**（唯一权威） |
| 默认脚本 | 内置的，从来不看 | **必须自己写** |
| `.data` 初值 | loader 按 `PT_LOAD` 映射 | 启动代码手动搬（LMA → VMA） |
| `.bss` | 新页本来就是 0 | **手动清零** |
| 栈 | 内核建，默认 8 MB | `_estack` 符号，链接脚本定 |

**这是理解后面所有内容的前提**：
裸机上"`0x20000000`"不是一个"请求"，它就是**SRAM 的第一个字节的物理地址**。
写错了就是写到了别的地方，没有 MMU 拦你。

## 五、段的分类（按"放哪、要不要初始化"）

| 段 | 内容 | 在哪 | 初始化 |
|---|---|---|---|
| `.isr_vector` | 向量表 | Flash | 不需要（本来就有内容） |
| `.text` | 代码 | Flash | 不需要 |
| `.rodata` | `const` 数据、字符串字面量 | Flash | 不需要 |
| `.data` | **有初值**的全局/静态变量 | **VMA: RAM / LMA: Flash** | **要搬** |
| `.bss` | 无初值（或初值 0）的全局/静态变量 | RAM | **要清零** |
| `.noinit` | 不想被初始化的变量（如复位原因） | RAM | **不动** |
| 栈 / 堆 | —— | RAM | 不初始化（栈靠 `_estack`） |

后三条是本仓库实测过的段归属（[ch04](../04-numbers-and-bitops/README.md)、
[ch06](../06-arrays-pointers-strings/README.md)）。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "`.data` 在 RAM 里" | 它的 **LMA 在 Flash**。实测 map：`20000000  8000084`。初值存 Flash，运行时在 RAM |
| "`.bss` 占 Flash" | 不占（`NOBITS`）。实测 `.bin` = 136 字节 = 16+116+4，`.bss` 的 4 字节不在内 |
| "链接器把 .o 拼起来就行" | 还要**定地址**。裸机没有 loader，链接脚本是唯一的地址权威 |
| "地址是虚拟的" | 裸机是**物理**的。没有 MMU，写错地址不会有任何保护 |
| "栈由系统建" | 由链接脚本的 `_estack` 符号定，实测 `0x20005000` |

<details>
<summary>Q1：VMA 和 LMA 到底有什么区别？什么时候它们不一样？</summary>

- **VMA（Virtual Memory Address）**：程序**运行时**这个段的地址。代码在这里执行、变量在这里被读写。
- **LMA（Load Memory Address）**：这个段的**内容**在上电时位于哪里（烧录器把字节写到哪个地址）。

大多数段两者相同：`.text` 在 Flash 里执行（XIP），烧在哪就在哪跑。
**只有一个段必然不同：`.data`。**

实测（本章的 map 文件）：

```
     VMA      LMA     Size
20000000  8000084        4     4 .data
```

- LMA `0x08000084`：初值字节在 Flash 的这里；
- VMA `0x20000000`：变量的家在 RAM 的这里。

**两个问题决定两个地址**：

1. "这段内容掉电后必须还在吗？" → 在，所以 **LMA 在 Flash**；
2. "这段运行时要被写吗？" → 要，所以 **VMA 在 RAM**。

答案不同 → VMA ≠ LMA → 启动代码必须搬运。

**其他 VMA ≠ LMA 的场景**：

| 场景 | LMA | VMA |
|---|---|---|
| **`.data`（最常见）** | Flash | RAM |
| 从 Flash 加载、在 RAM 里执行的代码 | Flash | RAM（更快 / 要自修改） |
| bootloader | Flash 的某个区 | RAM（搬过去执行） |
| 压缩镜像 | 压缩数据 | 解压后的位置 |

**判据一句话**：
**"掉电后必须还在吗？"** 在 → LMA 在 Flash。
**"运行时要写吗？"** 要 → VMA 在 RAM。
两个答案不同 → 需要搬运，且启动代码必须做这件事。
</details>

<details>
<summary>Q2：为什么 `.bss` 不占 Flash 空间？它真的"不存在"吗？</summary>

因为它的内容**全是 0，而 0 不需要存储**。

**ELF 层面**：`.bss` 段的类型是 **`NOBITS`**（实测）：

```
$ llvm-readelf -S blink.elf
  [ 3] .data   PROGBITS  20000000  020000  000004  ...
  [ 4] .bss    NOBITS    20000004  020004  000004  ...
                 ↑ 文件里不占字节
```

`NOBITS` 的意思是"这个段在文件里**没有内容**，但运行时要占 `000004` 字节"。
它只有地址范围，没有数据。

**烧录镜像层面**（实测）：

```
$ llvm-objcopy -O binary blink.elf blink.bin
blink.bin = 136 字节
```

```
.isr_vector  16
.text       116
.data 初值    4     ← LMA 那 4 个字节
─────────────────
合计        136     ← .bss 的 4 字节不在里面
```

**运行时**：它当然"存在"——在 RAM 里占 4 字节，只是内容是启动时清零来的：

```c
for (uint32_t *p = &_sbss; p < &_ebss; ) *p++ = 0;
```

**为什么这个设计重要**：

一个 4 KB 的全局数组（比如 `static uint8_t buf[4096];`）：

| 段 | Flash 占用 | RAM 占用 |
|---|---|---|
| 放 `.bss`（无初值） | **0** | 4096 |
| 放 `.data`（初值全 0，`= {0}`） | **4096** | 4096 |

⚠ **编译器有时会把"初值全零"的数组放进 `.data`**——那就白白吃掉 4 KB Flash。
所以裸机上的习惯是：**大缓冲不写初值**（让它进 `.bss`），需要初值时显式初始化。

验证方法（实测）：

```
$ llvm-size -A blink.elf
.data   4
.bss    4
```

如果 `.data` 异常大，查是不是有大数组被初始化了。
</details>

<details>
<summary>Q3：为什么裸机上"地址"必须是链接期定死的物理地址？</summary>

因为**没有操作系统，也没有 MMU**。

PC 上的流程：

```
你写 void f(){} → 编译 → 链接（给个虚拟地址 0x401000）
                       → 运行：./a.out
                          → fork/exec → 内核读 ELF 的 PT_LOAD
                          → mmap 到某块物理页，建页表
                          → CPU 用虚拟地址跑
```

关键点：**链接器给的地址只是"建议"，真正的物理页是运行时内核分配的**。
所以 PC 上可以有 ASLR（地址随机化）、可以动态链接、可以共享库。

裸机的流程：

```
你写 void f(){} → 编译 → 链接（地址 = 0x08000123，物理地址）
                       → 烧录器把字节写到 Flash 的 0x08000123
                       → 上电，CPU 直接从 0x08000000 取指
```

**中间没有 loader**。所以：

1. **地址必须是物理的**：`0x08000000` 就是 Flash 的起始，
   `0x20000000` 就是 SRAM 的起始（芯片手册写死的）；
2. **地址必须链接期定死**：没人会在运行时帮你改；
3. **写错地址没有任何保护**：没有 MMU，写到 `0x20005000`（RAM 之外）
   就是写到总线上的未知区域，不报错。

**由此推出三条实践规则**：

| 规则 | 原因 |
|---|---|
| **`MEMORY` 必须和芯片手册一致** | 换芯片（F103RB 128K/20K → F407 1M/192K）就要改，这是最容易忘的一步 |
| **寄存器地址要写代码里（或 CMSIS 头）** | 它们是物理地址，不是"设备号" |
| **栈的位置要链接脚本定** | 没有内核帮你建栈，`_estack` 就是唯一依据 |

**对照一下 Linux 内核**：
内核自己也是"物理地址 + 链接脚本"（`vmlinux.lds.S`）这套思路，
只是它运行在有 MMU 的环境里、并且负责给别人建页表。
所以你在裸机上学到的链接脚本知识，到内核里完全适用——
**LDD- 轨里那些 `vmlinux.lds.S`、`initcall` 分级、`.modinfo`，
都是同一套"用链接脚本布局"的思想，只是规模大得多**。
</details>
