# 11.5 映射文件

> 书：第 11 章 链接器 · 11.5 映射文件（原书 p154–173 区间内）
> 上一篇：[11.4 重定位](11.4-重定位.md) ｜ 下一篇：[11.6 高级用法](11.6-高级用法.md)
> 对应实验：`ld.lld -Map=blink.map`（真链接）+ `--print-gc-sections` + `-ffunction-sections` 对照实测

## 书这一节讲什么

一句话：**map 文件是"你的程序到底长什么样"的唯一权威**。

编译器的 `size` 只给你 3 个数字，`nm` 只给你符号名。
**只有 map 文件同时给你：每个段在哪、多大、来自哪个 `.o`、每个符号的确切地址。**

书上教的是"怎么读懂 map"。本篇把它落到**四个高频用法**上，
每个都配本仓库的真实 map 输出。

## 一、map 文件的列分别是什么意思

先取本仓库 `blink.map`（`ld.lld -T linker.ld -Map=blink.map`，真文件）：

```
     VMA      LMA     Size Align Out     In      Symbol
       0        0        0     1 _estack = ORIGIN(RAM) + LENGTH(RAM)
 8000000  8000000       10     4 .isr_vector
 8000000  8000000        0     1         . = ALIGN(4)
 8000000  8000000       10     4         startup.o:(.isr_vector)
 8000000  8000000       10     1                 g_vectors
 8000010  8000010       74     4 .text
 8000010  8000010       5a     4         startup.o:(.text)
 8000010  8000010        0     1                 $t
 8000011  8000011        2     1                 Default_Handler
 8000013  8000013       58     1                 Reset_Handler
 800006c  800006c       18     4         main.o:(.text)
 800006c  800006c        0     1                 $t
 800006d  800006d       18     1                 main
20000000  8000084        4     4 .data
20000000  8000084        0     1         _sdata = .
20000000  8000084        4     4         main.o:(.data)
20000000  8000084        4     1                 g_has_init
20000004  8000088        0     1         . = ALIGN(4)
20000004  8000088        0     1         _edata = .
20000004  8000088        0     1 _sidata = LOADADDR(.data)
20000004 20000004        4     4 .bss
20000004 20000004        0     1         _sbss = .
20000004 20000004        4     4         main.o:(.bss)
20000004 20000004        4     1                 g_tick
20000008 20000008        0     1         . = ALIGN(4)
20000008 20000008        0     1         _ebss = .
```

| 列 | 含义 | 怎么用 |
|---|---|---|
| **VMA** | 运行地址（程序跑起来后 CPU 看到的地址） | 调试时 `x/1xw <VMA>` |
| **LMA** | 加载地址（烧进 Flash 时放在哪） | `.data` 的 LMA 才是烧录位置 |
| **Size** | 大小（**十六进制**，注意没有 `0x` 前缀） | `74` = 116 字节 |
| **Align** | 对齐 | 对小地址没意义，看段的对齐约束 |
| **Out** | 输出段（链接脚本里的 `.text` 等） | 最左列、顶格 |
| **In** | 输入段（`startup.o:(.text)`） | 缩进一级，**"这段来自哪个 .o"** |
| **Symbol** | 符号 | 缩进两级 |

⚠ **两个最容易看错的点**：

1. **Size 是十六进制但没有 `0x`**：`74` 不是 74 字节，是 **0x74 = 116 字节**。
2. **`In` 行里带着 `.o` 文件名**：这是排查"这个字节是谁贡献的"的唯一线索。
   `main.o:(.text)` = 18 字节（0x18），`startup.o:(.text)` = 5a = 90 字节。

## 二、用法①：Flash 用了多少、还剩多少

从 map 顶格行读 **VMA 在 `0x0800xxxx` 区间**的段：

```
 8000000  8000000       10     4 .isr_vector      ← 0x10 =  16 B
 8000010  8000010       74     4 .text            ← 0x74 = 116 B
                                                   合计   132 B
```

对照 `MEMORY` 里的 `FLASH : ORIGIN = 0x08000000, LENGTH = 128K`：

```
占用 = 132 / 131072 = 0.10%
结束地址 = 0x08000000 + 0x84 = 0x08000084
剩余 = 131072 - 132 = 130940 B ≈ 127.9 KB
```

**交叉验证**（三个工具必须一致，不一致说明你算错了）：

```
$ llvm-size blink.elf
   text	   data	    bss	    dec	    hex	filename
    132	      4	      4	    140	     8c	blink.elf
```

⚠ **注意 `text` 这一列的含义**：它是 **`.isr_vector` + `.text` + `.rodata` 之和**（132），
但**不含 `.data` 在 Flash 里的那份副本**（4 字节）。
所以：

```
烧进 Flash 的实际字节 = size 的 text + data = 132 + 4 = 136
```

**实测验证**：

```
$ llvm-objcopy -O binary blink.elf blink.bin && ls -l blink.bin
-rwxr-xr-x  1 a0000  wheel  136 ... blink.bin
```

`136 = 132 + 4`，✅ 对上了。
（`.bss` 的 4 字节 **不在 bin 里**，因为它是 NOBITS——见 [11.1](11.1-编译和链接的内存模型.md)。）

## 三、用法②：找某个变量/函数在哪

直接搜符号名：

```
20000004 20000004        4     1                 g_tick
```

→ `g_tick` 在 `0x20000004`，4 字节。
gdb 里 `x/1xw 0x20000004` 就能看到它的值
（[ch03 实测](../03-embedded-system-programming/README.md) 就用这个方法读到了 `g_tick` 的累加值）。

**函数同理**，但要注意 Thumb 位——map 里给的是**奇数**值：

```
 8000013  8000013       58     1                 Reset_Handler
```

| 用途 | 用哪个值 |
|---|---|
| `x/10i 0x08000012`（看指令） | `llvm-nm` 给的**偶数** |
| 构造函数指针 | map 给的**奇数** `0x08000013` |
| 看函数占多大 | `size` 列：`0x58` = 88 字节 |

详见 [11.4 重定位](11.4-重定位.md) 的三方对照。

**顺便算栈余量**（这是 map 文件最实用的"免费体检"）：

```
_estack = 0x20005000     （顶格行，20K RAM 的顶）
_ebss   = 0x20000008     （.bss 结束）
```

```
可用栈 = 0x20005000 - 0x20000008 = 0x4FF8 = 20472 B ≈ 20.0 KB
```

⚠ 这是"**静态**余量"——不包含**堆**（如果有 `malloc`）和**各层函数调用的栈帧**。
真正的栈溢出要靠填充模式（fill pattern）在运行时查。

## 四、用法③：找"谁被 `--gc-sections` 丢了"

这是最有价值也最容易踩坑的一个用法。

### 4.1 ⚠ 实测：`--gc-sections` 单独用是**没用的**

写了个有死代码的例子：

```c
uint32_t g_used  = 1;
uint32_t g_dead  = 2;                              /* 没人引用 */
uint32_t dead_fn(uint32_t a){ return a * 3 + 7; }  /* 没人调用 */
uint32_t live_fn(uint32_t a){ return a + 1; }
int main(void){ return (int)(g_used + live_fn(1)); }
```

**只加 `--gc-sections`，不加 `-ffunction-sections`**：

```
$ llvm-size gc_gc.elf      # --gc-sections
   text	   data	    bss
    134	      8	      0

$ llvm-size gc_nogc.elf    # 不加
   text	   data	    bss
    134	      8	      0
```

**完全一样**。`dead_fn` 和 `g_dead` 都还在。

**原因**：GC 的**最小单位是"段"（section）**，不是"函数"。
默认编译下，一个 `.o` 的所有函数挤在**同一个 `.text` 段**里：

```
 8000010  8000010       1a     4         gc.o:(.text)     ← 一个段装了全部函数
 8000011  8000011        8     1                 dead_fn
 8000019  8000019        4     1                 live_fn
```

`main` 活在这个段里 → **整个段被判活** → `dead_fn` 搭便车留下。

### 4.2 加上 `-ffunction-sections -fdata-sections` 才生效

```
$ clang ... -ffunction-sections -fdata-sections -c gc.c -o gcs.o
$ ld.lld -T linker.ld -e Reset_Handler --gc-sections --print-gc-sections \
         -Map=gcs_gc.map gcs.o startup.o -o gcs_gc.elf
removing unused section gcs.o:(.text)
removing unused section gcs.o:(.text.dead_fn)
removing unused section gcs.o:(.ARM.exidx.text.dead_fn)
removing unused section gcs.o:(.text.live_fn)
removing unused section gcs.o:(.ARM.exidx.text.live_fn)
removing unused section gcs.o:(.data.g_dead)
```

段名变成了 `.text.dead_fn` / `.data.g_dead`——**一个函数一个段**，GC 才能单独删。

| 组合 | text | data | 说明 |
|---|---|---|---|
| 粗分节 + 无 gc | 134 | 8 | 基线 |
| 粗分节 + gc | 134 | 8 | ⚠ **没变化** |
| 细分节 + 无 gc | 134 | 8 | 没变化 |
| **细分节 + gc** | **122** | **4** | ✅ **text −12 B，data −4 B** |

`−12 = dead_fn(8) + live_fn(4)`（`live_fn` 被内联了，函数体也没了）；
`−4 = g_dead`。

**所以启用 GC 的正确姿势是编译和链接两头都开**：

```make
CFLAGS += -ffunction-sections -fdata-sections
LDFLAGS += --gc-sections
```

### 4.3 `--print-gc-sections`：让"丢了谁"可见

`ld.lld` 的 **map 文件里不列出被丢弃的段**（GNU `ld` 会在 map 末尾写
`Discarded input sections`，lld 不会）。想看被丢了什么，要单独加
**`--print-gc-sections`**，它打在 stderr 上。

典型输出里那两行值得注意：

```
removing unused section gcs.o:(.ARM.exidx.text.dead_fn)
```

——每个函数段都会带一个 `.ARM.exidx.*` 异常回溯段。
Cortex-M 用不上（没有 C++ 异常），
本仓库的链接脚本用 `/DISCARD/ : { *(.ARM.exidx*) }` 直接扔掉
（见 [11.2](11.2-链接过程.md)）。

### 4.4 ⚠ `__attribute__((used))` 管不了链接器的 GC

这是 [ch01](../01-hello-world/README.md) 就踩过的坑，这里补上机制解释：

| 属性 | 管得了谁 | 作用 |
|---|---|---|
| `__attribute__((used))` | **编译器** | 防止"没被引用的静态变量被优化掉"（停留在 `.o` 里） |
| `KEEP(*(...))` | **链接器** | 防止"没被引用的段被 `--gc-sections` 删掉" |

**两者是两道独立的关卡**，`used` 过了编译器那一关，
链接器照样能把它删了——**向量表就是典型**（硬件读它，没人"调用"它）：

```ld
.isr_vector : { . = ALIGN(4); KEEP(*(.isr_vector)) } >FLASH
```

实测：去掉 `KEEP` 之后 `g_vectors` 从符号表里**消失**
（[11.2](11.2-链接过程.md) 的 KEEP 对照实验）。

## 五、用法④：识别"不占 Flash 的段"

map 末尾会有一些 VMA = 0 的段：

```
       0        0       29     1 .comment
       0        0       41     1 .ARM.attributes
       0        0      110     4 .symtab
       0        0       51     1 .shstrtab
       0        0       81     1 .strtab
```

| 段 | 是啥 | 进不进 Flash |
|---|---|---|
| `.comment` | 编译器版本字符串（"clang version 23.1.0"） | ❌ |
| `.ARM.attributes` | CPU/arch 属性标签 | ❌ |
| `.symtab` / `.strtab` / `.shstrtab` | **符号表**，给 `nm`/`objdump` 看的 | ❌ |

**为什么 VMA = 0 就不进 Flash**：它们没有 `SHF_ALLOC` 标志
（`llvm-readelf -S` 里 `Flg` 列没有 `A`）：

```
  [ 5] .comment          PROGBITS        00000000 020004 000029 01   MS  0   0  1
                                         ^^^^^^^^                    ^^
                                         Address=0                   没有 A → 不分配
  [ 2] .text             PROGBITS        08000010 010010 000074 00  AX  0   0  4
                                                                    ^^
                                                                    A → 分配
```

**实践意义**：`llvm-size` 报的 132 字节**不含**这些，
`objcopy -O binary` 也不会把它们写进 `.bin`。
所以**发布固件时不用刻意 strip 符号表来"瘦身"**——
它本来就不在 bin 里。（但 `.elf` 文件本身会大，传输时才有差别。）

## 六、读 map 的四条口诀

| 想回答的问题 | 看什么 |
|---|---|
| Flash/RAM 用了多少 | 顶格行的 **VMA 区间** + `MEMORY` 的 `LENGTH` |
| 某个符号在哪 | 直接搜 **Symbol 列** |
| 谁被丢了 | `--print-gc-sections` 的 stderr（map 里没有） |
| 这个字节是谁贡献的 | **In 列**的 `xxx.o:(.yyy)` |

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实测是什么 |
|---|---|
| "map 里的 Size 是字节数" | ⚠ 是**十六进制**但没有 `0x` 前缀：`74` = **116** 字节 |
| "开了 `--gc-sections` 就会删死代码" | ⚠ **必须同时开 `-ffunction-sections -fdata-sections`**。实测只开 gc：134/8 → 134/8，**一个字节没少** |
| "`__attribute__((used))` 能保住变量" | 只管**编译器**那关。链接器的 GC 要 `KEEP()`（ch01 坑点） |
| "被 GC 掉的段能在 map 里看到" | ⚠ **lld 的 map 不列丢弃段**，要 `--print-gc-sections`（GNU ld 才写进 map） |
| "`llvm-size` 的 text 就是占的 Flash" | 差一点：还要 **+ data**（`.data` 有 Flash 里的副本）。实测 132 + 4 = **136** = `blink.bin` 的大小 |
| "符号表会占 Flash" | 不会：无 `SHF_ALLOC`，VMA = 0，不进 `.bin` |

## 代码自测

<details>
<summary>Q1：为什么我开了 `--gc-sections`，死代码一个字节都没少？</summary>

因为 **GC 的最小单位是"段"，而你没分段**。

实测（`gc.c` 里有一个没人调用的 `dead_fn` 和没人引用的 `g_dead`）：

| 编译选项 | 链接选项 | text | data |
|---|---|---|---|
| 默认 | 无 gc | 134 | 8 |
| 默认 | `--gc-sections` | **134** | **8** |
| `-ffunction-sections -fdata-sections` | 无 gc | 134 | 8 |
| `-ffunction-sections -fdata-sections` | `--gc-sections` | **122** | **4** |

**原因**：默认编译下 clang 把一个 `.o` 里所有函数塞进**同一个 `.text` 段**：

```
 8000010  8000010       1a     4         gc.o:(.text)
 8000011  8000011        8     1                 dead_fn
 8000019  8000019        4     1                 live_fn
```

`main` 活在这个段里 → 整个段被判活 → `dead_fn` 搭便车。
GC 想删也没法删（它只能整段删）。

开了 `-ffunction-sections` 之后，段名变成 `.text.dead_fn`、`.data.g_dead`，
**一个函数/变量一个段**，GC 才能精确剔除：

```
$ ld.lld ... --gc-sections --print-gc-sections
removing unused section gcs.o:(.text.dead_fn)
removing unused section gcs.o:(.data.g_dead)
```

**正确姿势（两头都要开）**：

```make
CFLAGS  += -ffunction-sections -fdata-sections
LDFLAGS += --gc-sections
```

⚠ **代价**：细分节会让目标文件里多出成百上千个段，链接稍慢；
另外每个函数段会带一个 `.ARM.exidx.*`，
Cortex-M 上要用 `/DISCARD/ : { *(.ARM.exidx*) }` 清掉
（见 [11.2](11.2-链接过程.md)）。

**一句话**：`--gc-sections` 是"垃圾收集器"，
`-ffunction-sections` 是"把垃圾分成一个个小袋子"——
**不装袋，收集器就无从下手。**
</details>

<details>
<summary>Q2：`llvm-size` 的 text 是 132，但 `blink.bin` 是 136 字节，差的 4 字节是什么？</summary>

差的是 **`.data` 在 Flash 里的那份"初值副本"**。

**实测**：

```
$ llvm-size blink.elf
   text	   data	    bss	    dec	    hex	filename
    132	      4	      4	    140	     8c	blink.elf

$ llvm-objcopy -O binary blink.elf blink.bin && ls -l blink.bin
-rwxr-xr-x  1 a0000  wheel  136 ... blink.bin
```

**拆解**：

| 部分 | 字节 | 在哪 | 说��� |
|---|---|---|---|
| `.isr_vector` | 16 | Flash `0x08000000` | map 里 size `10` = 0x10 |
| `.text`（含 `.rodata`） | 116 | Flash `0x08000010` | map 里 size `74` = 0x74 |
| **`.data` 的初值副本** | **4** | Flash `0x08000084` | **就是差的这 4 字节** |
| `.bss` | 4 | RAM `0x20000004` | **NOBITS，不进 bin** |

```
text(132) + data(4) = 136 = blink.bin ✅
```

**为什么 `.data` 要占两份地方**：

`.data` 是"有初值的全局变量"（实测里的 `g_has_init = 0xA5A5A5A5`）。
它**运行时必须在 RAM**（要能写），但**掉电后 RAM 是空的**——
所以初值必须**预先存在 Flash 里**，上电时由启动代码搬过去。
这就是 VMA/LMA 分离（[11.1](11.1-编译和链接的内存模型.md)）：

```
20000000  8000084        4     4 .data
^^^^^^^^  ^^^^^^^
VMA=RAM   LMA=Flash  ← 烧录位置
```

map 里 `_sidata = LOADADDR(.data) = 0x8000084`，
启动代码就从这个地址往 `0x20000000` 搬 4 字节。

**所以算"Flash 用了多少"时，要用 `text + data`**，
只用 `text` 会**少算**，而且少算的部分恰好是最容易出 bug 的部分
（`.data` 搬运地址算错 = 全局变量初值是垃圾）。

**`.bss` 为什么不占**：它是 NOBITS，
ELF 里只记录"我要 4 字节"，**不存内容**（内容反正全是 0，启动代码清零即可）。
</details>

<details>
<summary>Q3：想看"哪些段被 GC 掉了"，map 文件里为什么找不到？</summary>

因为 **GNU ld 和 LLVM lld 的行为不一样**：

| 工具 | 被丢弃的段在哪 |
|---|---|
| **GNU `ld`** | map 文件末尾有 `Discarded input sections:` 一节 |
| **LLVM `ld.lld`** | ⚠ **map 里没有**，要加 `--print-gc-sections`，输出在 **stderr** |

**实测（lld）**：

```
$ ld.lld -T linker.ld -e Reset_Handler --gc-sections \
         --print-gc-sections -Map=gcs_gc.map gcs.o startup.o -o gcs_gc.elf
removing unused section gcs.o:(.text)
removing unused section gcs.o:(.text.dead_fn)
removing unused section gcs.o:(.ARM.exidx.text.dead_fn)
removing unused section gcs.o:(.text.live_fn)
removing unused section gcs.o:(.ARM.exidx.text.live_fn)
removing unused section gcs.o:(.data.g_dead)
```

这 6 行**只出现在终端上**，不会写进 `gcs_gc.map`。
所以排查"我的函数怎么不见了"时，别只翻 map。

⚠ **注意第一行 `removing unused section gcs.o:(.text)`**：
即使开了 `-ffunction-sections`，`.o` 里仍会有一个"兜底"的 `.text` 段
（放 `asm` 语句、某些编译器生成的公共代码），它同样会被删。

**排查"函数不见了"的三步**：

1. `--print-gc-sections` 看是不是被 GC 删了 → 加 `KEEP()`；
2. `llvm-nm xxx.o` 看 `.o` 里有没有这个符号 → 没有就是编译器阶段就没生成（`static` + 未使用被优化，加 `used`）；
3. `llvm-nm xxx.elf` 看链接后有没有 → 有但 map 里没有，说明它在**被 `/DISCARD/` 的段**里。

**顺带**：`.ARM.exidx.*` 是异常回溯表（C++ 异常 / `unwind` 用）。
Cortex-M 裸机不需要，**每个函数一个**会白白撑大 `.o`，
本仓库统一 `/DISCARD/ : { *(.ARM.exidx*) }`。
</details>

<details>
<summary>Q4：怎么从 map 文件算出"栈还剩多少"？这个数可信吗？</summary>

**算法**（实测 `blink.map`）：

```
_estack = 0x20005000     ← 顶格行：_estack = ORIGIN(RAM) + LENGTH(RAM)
                            = 0x20000000 + 20K(0x5000)
_ebss   = 0x20000008     ← .bss 段结束
```

```
静态可用栈 = 0x20005000 - 0x20000008 = 0x4FF8 = 20472 B ≈ 20.0 KB
```

**⚠ 这个数不可信（ underestimates 风险的方向要搞清楚）**。它只算：

```
栈空间 = 栈顶 - (data + bss 结束)
```

**没算进去的三样东西**：

| 没算的 | 影响 | 怎么查 |
|---|---|---|
| **堆**（`malloc`） | 如果有 `_sbrk`，堆通常从 `_ebss` 往上长，**直接吃栈的空间** | 链接脚本里看 `_heap_start` / `_end` |
| **最深调用链的栈帧** | 20 KB 看着多，但一个深递归/大局部数组能瞬间吃掉 | `-fstack-usage`（[ch09 9.3](../09-uart-serial/9.3-串行输出.md) 实测过） |
| **中断嵌套的栈帧** | 每个 ISR 都要压栈，嵌套 8 层就是 8 份 | 每个 ISR 的 `.su` 值 × 嵌套层数 |

**真正可信的做法——填充模式（fill pattern）**：

1. 上电后把 `_ebss` 到 `_estack` 之间全部填成 `0xDEADBEEF`（或 `0xCCCCCCCC`）；
2. 跑一段时间（最好跑满最坏路径）；
3. 从 `_estack` 往下扫，找**第一个不等于填充值的地址**；
4. 那个地址就是"栈曾经到过的最低点"，剩余 = 它 − `_ebss`。

**链接期能做的唯一保险**是 `ASSERT`（[11.2](11.2-链接过程.md) 实测过）：

```ld
ASSERT(_ebss < _estack - 512, "RAM 不够：栈至少要 512 字节")
```

实测把 RAM 改成 512 字节时链接**直接失败**：

```
ld.lld: error: RAM 不够：栈至少要 512 字节
```

——把"运行时踩内存"前移成"链接期硬错误"，
这是链接脚本最划算的一招。
</details>
