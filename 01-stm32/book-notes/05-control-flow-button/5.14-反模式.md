# 5.14 反模式

> 书：第 5 章 决策和控制语句 · 5.14 反模式（5.14.1 空 while 循环 / 5.14.2 while 中的赋值）
> 上一篇：[5.13 continue](5.13-continue.md) ｜ 本篇是第 5 章的收尾
> 对应实验：`--target=armv7m-none-eabi -mcpu=cortex-m3` + 主机侧 clang 23.1.0（含 UBSan）

## 书这一节讲什么

书列了两个反模式：

- **5.14.1 空 `while` 循环**：`while (cond);` 这种写法不好；
- **5.14.2 `while` 条件里的赋值**：`while (ch = getchar())` 容易把 `=` 写成 `==`。

书把它们当**风格问题**讲。实测之后你会发现：
**在裸机上它们是正确性问题**——前者会让等待循环整个消失，
后者会让编译器不再替你检查 `=`/`==` 笔误。

## 一、5.14.1 实测：空 `while` 被编译成一条 `bx lr`

```c
int flag;                        /* 非 volatile：ISR 会改它 */
volatile int vflag;
void wait_bad(void){ while (flag  == 0) { } }
void wait_ok (void){ while (vflag == 0) { } }
```

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -Os -c wait.c -o wait.o
$ llvm-objdump -d wait.o

00000000 <wait_bad>:
       0: 4770          bx   lr        ← 整个等待循环没了！直接返回

00000002 <wait_ok>:
       2: movw/movt r0, #0x0           ; &vflag
       a: nop
       c: 6801          ldr  r1, [r0]  ← 循环体内真的读
       e: 2900          cmp  r1, #0x0
      10: d0fc          beq  0xc       ← 跳回再读
      12: 4770          bx   lr
```

**这不是编译器的 bug，是标准允许的。**
C11 §6.8.5p6：如果循环的条件不是常量表达式，且循环体
**不执行 I/O、不访问 volatile 对象、不做同步操作**，
编译器可以**假定这个循环会终止**。
编译器能证明 `flag` 在循环里不会被改（它不知道 ISR 会改），
于是"永远出不来"= 踏进 UB，编译器想怎么处理都行——它选了最快的一条 `bx lr`。

后果：**程序不等了，直接往下跑**，读到一个还没准备好的寄存器。

**规则**：等待硬件标志的循环，条件里的变量**必须是 `volatile`**，
循环体写 `{ }` 而不是 `;`。

## 二、5.14.2 实测：`while` 条件里的赋值与 `-Wparentheses`

```
$ clang -Wall -Wextra -c assign.c
assign.c:1:48: warning: using the result of an assignment as a condition without parentheses [-Wparentheses]
    1 | void copy(char *d, const char *s){ while (*d++ = *s++) ; }
      |                                           ~~~~~^~~~~~
assign.c:1:48: note: place parentheses around the assignment to silence this warning
```

加了括号就不警告了：

```
$ clang -Wall -Wextra -c assign2.c     # while ((*d++ = *s++) != '\0')
（无输出 —— 不警告）
```

所以真正的风险是：**你本意写 `==`，手滑写成 `=`，又加了括号（或没开 `-Wall`）**。
那时 `while (x = 0)` 会静默变成"永远不进循环"。

推荐写法（意图明确，且 `!= '\0'` 把比较显式写出来）：

```c
while ((*d = *s) != '\0') { d++; s++; }
```

## 三、书里没列但裸机上代价更高的三个反模式

**① 用浮点做循环变量（实测）**

```
$ clang -O2 -o fl fl.c && ./fl
累加次数 n = 10 ; 最终 f = 1.00000011920928955078
```

`0.1f` 累加 10 次不是 1.0 而是 `1.000000119...`——
`f < 1.0f` 的判断正好卡在边界上，循环次数可能和你想的不一样
（换个初值/步长就变）。而且 M0/M3 **没有 FPU**，浮点是软件模拟的，慢几个数量级
（[16.2 舍入误差](../16-floating-point/16.2-舍入误差.md)）。

**② 用空循环做延时（实测）**

```
-O0:  d0 = 22 条指令的真循环
-O2:  d0 = 一条 bx lr        ← 循环消失
-Os:  d0 = 一条 bx lr        ← 循环消失
d1（volatile int i）: 三档都保留
```

（[5.5 for](5.5-for.md) 有完整反汇编）即使加 `volatile` 保住循环，
延时长度也随优化等级和主频变。正解是 SysTick（[ch19](../19-systick-and-timer/19.4-三种等待的对比.md)）。

**③ 在循环条件里调用有副作用的函数**

```c
while (uart_getchar() != '\n') ;     /* 每次判断都真的读一次串口，数据被吃掉 */
```

`uart_getchar()` 读 `DR` 会清 `RXNE`，
所以每判断一次就消费一个字节——你以为在"找换行符"，
其实把数据全读了却没存。

正确写法是**先读，再判断**：

```c
int c;
while ((c = uart_getchar()) != '\n') { line[n++] = (char)c; }
```

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| 5.14.1 空 `while` 是"风格不好" | 裸机上是**正确性问题**：实测 `while (flag==0){}` → `bx lr`，循环消失。条件变量必须 `volatile` |
| 5.14.2 `while` 里赋值是"不清晰" | 除了不清晰，它还会让 `-Wparentheses` **失效**（加括号就不警告），`=`/`==` 笔误没人管 |
| "`volatile` 是给编译器看的注解" | 它是**语义的一部分**：告诉编译器"每次都必须真的读，不许替我推理" |
| "循环条件里读寄存器很方便" | 每次判断都是真实硬件访问，可能**吃掉数据**（读清标志） |
| "空循环延时 20ms 够用" | 实测开优化就没了；即使保住也不准（随 `-O` 和主频变） |

## 代码自测

<details>
<summary>Q1：为什么 `wait_bad` 被编译成 `bx lr`？编译器没看到 ISR 会改 flag 吗？</summary>

**它看不到，而且标准允许它"假定看不到"。**

编译器的推理链（针对单文件编译）：

1. `flag` 是全局变量，初值 0；
2. 条件 `flag == 0` 为真 → 进循环；
3. 循环体是空的 `{}`，没有 I/O、没有 `volatile`、没有函数调用 →
   **`flag` 在循环里不可能被改变**；
4. 于是这个循环要么不进，要么永远出不来；
5. C11 §6.8.5p6：**编译器可以假定循环会终止**，
   而"能证明永不终止的循环"= 未定义行为；
6. UB 意味着编译器做什么都合法 → 生成 `bx lr`（最快）。

关键点在第 3 步：**编译器不知道 ISR 的存在**。
ISR 是运行时才发生的控制流转移，编译器在翻译 `wait_bad` 时看不到任何调用它的地方。
（即使看到了，C 语言的内存模型也不保证 ISR 对非 volatile 变量的修改是"可观察"的。）

`volatile` 解决的就是这个：它把"读 `vflag`"变成**可观察行为**，
编译器**必须**每轮真的读，不许推理它的值。

一句话：**`volatile` 不是告诉编译器"这个值会变"，
是告诉它"每次都必须真的去读，不许替我推理"。**
</details>

<details>
<summary>Q2：`while (cond);` 和 `while (cond) { }` 有区别吗？</summary>

语义完全一样，生成的代码也一样。区别在于**人能不能看见**。

```c
while (!(USART1_SR & TXE)) ;      /* ← 那个分号，代码审查时几乎必然漏看 */
while (!(USART1_SR & TXE)) { }    /* ← 一眼看出"循环体是空的" */
```

一个分号的差别，决定了几个月后你（或同事）能不能一眼看出
"这里是个忙等"。而裸机上的忙等往往是 bug 的根源
（阻塞、耗电、延时不准）。

配套手段：

1. **开 `-Wempty-body`**（`-Wextra` 里包含），让编译器提醒你；
2. 空循环体里放一条 `__asm__ volatile("nop");`，
   既显式（说明"这里故意什么都不做"），又给调试器一个能停住的地方；
3. 更好的做法是**根本不写空等待**——改成状态机 + 超时（[5.4](5.4-while.md)）。

`nop` 那个技巧还有个实际用途：实测 `wait_ok` 的循环里就有 `nop`
（编译器自己插的，用于对齐），而单步调试时停在 `nop` 上比停在跳转上更容易看清楚。
</details>

<details>
<summary>Q3：除了书里这两个，我该一开始就避开的裸机反模式有哪些？</summary>

按"踩中概率 × 排查难度"排：

**① 空循环等待/延时**（本章实测）
开优化就没了。→ 用 SysTick。

**② 循环条件里做 I/O**
`while (uart_getchar() != '\n')` 会吃掉数据。→ 先读进变量再判断。

**③ 用浮点做循环变量或循环边界**（实测 `0.1f` 累加 10 次 = `1.000000119`）
→ 用整数（毫秒数、计数）做循环，浮点只在最后一步换算。

**④ 依赖"循环体为空"产生副作用**
比如靠 `for (i=0;i<n;i++)` 的次数去驱动某个硬件时序。
→ 时序必须由硬件定时器产生，不能由指令数决定。

**⑤ 在循环里反复读同一个 MMIO 寄存器**
每次读都是总线访问，且有副作用。→ 读一次存起来。

**⑥ 无限等待没有超时**
外设时钟没开 → 标志永远不来 → 死机。
→ 所有等待循环都配超时（[5.4](5.4-while.md)）。

共同的本质一句话：**裸机上"看起来能跑"和"真的按你想的跑"之间，
隔着一个优化器。** 凡是涉及"等硬件""数时间""读两次"的代码，
都要问一句：**编译器有没有权力把它改掉？**
</details>
