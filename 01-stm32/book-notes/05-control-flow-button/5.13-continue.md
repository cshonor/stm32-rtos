# 5.13 continue

> 书：第 5 章 决策和控制语句 · 5.13 continue（原书 p65–77 区间内）
> 上一篇：[5.12 break](5.12-break.md) ｜ 下一篇：[5.14 反模式](5.14-反模式.md)
> 对应实验：`--target=armv7m-none-eabi -mcpu=cortex-m3 -Os` 交叉编译

## 书这一节讲什么

一句话：**`continue` 跳到下一轮循环**（跳过本次循环剩下的部分）。

书讲语法。实测会告诉你一件有意思的事：**`continue` 经常被编译器整个改掉**——
它不产生跳转，而是被重写成"条件执行"。

## 一、实测：`continue` 被改写成条件清零

```c
int f_break(int *a, int n){ int s=0; for(int i=0;i<n;i++){ if(a[i]<0) break; s+=a[i]; } return s; }
int f_cont (int *a, int n){ int s=0; for(int i=0;i<n;i++){ if(a[i]<0) continue; s+=a[i]; } return s; }
```

```
$ clang ... -Os -c bc.c && llvm-objdump -d bc.o

00000000 <f_break>:                      ← break 版
       8: ldr  r3, [r2], #4
       c: cmp  r3, #0x0
       e: bmi  0x1c                      ← 真有一条跳转（跳出循环）
      10: subs r1,#1 / add r0,r3
      18: b 0x8
      1c: bx lr

0000001e <f_cont>:                       ← continue 版
      28: ldr  r3, [r2], #4
      2c: subs r1,#1
      2e: ea23 73e3  bic.w r3, r3, r3, asr #31    ← 负数 → 0；非负数 → 不变
      32: add  r0, r3
      34: bne 0x28                        ← 只有循环回边，没有 continue 的跳转
      36: bx lr
```

编译器把"负数就 `continue`（不加）"重写成：
**把负数变成 0 再加**（`bic.w r3, r3, r3, asr #31` 是"若 r3 为负则清零"
——`asr #31` 得到全 1 掩码，`bic` 就是 `r3 & ~mask` = 0）。

结果：**`continue` 版本比 `break` 版本还少一次跳转**。
这说明：

1. `continue` 是**给人读的**，编译器会按数据流重写；
2. 别为了"省跳转"把 `continue` 改写成别的形式——适得其反。

## 二、什么时候 `continue` 真的有价值

**减少缩进层数**（这是它唯一但重要的价值）：

```c
/* 不用 continue：三层嵌套 */
for (i = 0; i < n; i++) {
    if (buf[i].valid) {
        if (buf[i].type == TYPE_A) {
            if (!buf[i].skip) {
                process(&buf[i]);
            }
        }
    }
}

/* 用 continue：平铺的"守卫链"（guard clauses） */
for (i = 0; i < n; i++) {
    if (!buf[i].valid) continue;
    if (buf[i].type != TYPE_A) continue;
    if (buf[i].skip) continue;
    process(&buf[i]);
}
```

**守卫链**在裸机代码里特别常见：先排除各种"不用处理"的情况，
剩下的就是真正要做的。读代码时不用在脑子里维护多层条件。

## 三、裸机上的注意点

| 场景 | 注意 |
|---|---|
| 循环里有 `volatile` 读 | `continue` 之前的那次读**照常发生**（不会被撤销） |
| 循环里有副作用（读 DR 清标志） | `continue` 之前已经读了 → 标志已经清了 |
| ISR 里的 `continue` | 同 `break`：确认清理动作没被跳过 |
| 深层嵌套 + 多层 `continue` | 考虑抽成小函数用 `return` 代替 |

最后一条：如果循环体里有超过 3 个 `continue`，
通常说明这个循环该拆成"过滤函数 + 处理函数"两个函数了。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "`continue` 会跳到下一轮" | 语义上是，但**机器码常常没有跳转**：实测被重写成 `bic.w` 条件清零 |
| "`continue` 比 `break` 慢" | 实测相反：continue 版循环里跳转更少 |
| "用 `continue` 省一层缩进，性能会差" | 不会。它是给人读的语法，编译器按数据流重写 |
| "`continue` 跳过后面的代码" | 对——包括后面的**清理动作**。ISR 里尤其注意 |
| "循环里读寄存器，continue 就不读了" | ❌ **读了就是读了**，continue 只是不执行后面的 C 语句 |

## 代码自测

<details>
<summary>Q1：`bic.w r3, r3, r3, asr #31` 这条指令在干什么？</summary>

它在做"**如果 r3 是负数，就把它变成 0；否则保持不变**"——
一条指令实现了 `if (a[i] < 0) continue;` 的效果。

拆解：

```
asr #31        ; 算术右移 31 位：
               ;   正数 → 0x00000000
               ;   负数 → 0xFFFFFFFF（补码的符号位复制）
bic r3, r3, X  ; r3 = r3 & ~X
               ;   X = 0x00000000（原值正数）→ r3 & ~0 = r3  （不变）
               ;   X = 0xFFFFFFFF（原值负数）→ r3 & 0  = 0    （清零）
```

于是 `s += (a[i] < 0 ? 0 : a[i])` —— 正好等价于"负数就 continue（不加）"。

这是 ARM 的**条件执行 + 数据运算**替代**控制流**的典型例子：
跳转会打断流水线（Cortex-M3 的预取很简单），
而一条算术指令不会。编译器在 `-Os` 下总爱干这种事。

对我们的启示：**写"意图清楚的 C"，让编译器去选指令形态。**
如果你手写 `s += (a[i] < 0 ? 0 : a[i]);`，
在某些编译器上反而可能生成真实的跳转——可读性没变好，性能还可能变差。
</details>

<details>
<summary>Q2：`continue` 在循环里读了寄存器之后跳过，那次读算不算？</summary>

**算，而且不会被撤销。** `continue` 只影响 C 语句的执行顺序，
不影响已经发生的硬件访问。

```c
for (int i = 0; i < n; i++) {
    uint32_t sr = USART1_SR;         /* ← 每次都是真实的硬件读 */
    if (sr & RXNE) {
        c = USART1_DR;               /* ← 读 DR 会清 RXNE，这个副作用也发生了 */
        continue;
    }
    /* continue 跳过了这里，但上面那次读 SR/DR 已经生效 */
}
```

这件事在两类场合会咬人：

1. **读清标志型寄存器**：`continue` 之前读了 `DR`，`RXNE` 已经被清了。
   下一轮再读 `SR` 就看不到那个标志——这是**正确**的（标志该清），
   但如果你指望"下一轮还能看到同一个标志"，逻辑就错了。
2. **计数/采样型寄存器**：`continue` 之前读了 `ADC_DR`，
   那次采样的结果就被消费掉了（很多 ADC 读 DR 会启动下一次转换）。

所以裸机的规则还是那句（[5.9](5.9-获取按钮状态.md) Q1）：
**能读一次就别读两次；读到的值存进局部变量再用。**
`continue` 不会帮你"退回去"。
</details>

<details>
<summary>Q3：循环体里有一堆 `continue`，该怎么重构？</summary>

超过 3 个 `continue` 时，拆成"过滤 + 处理"两个函数通常更清楚：

```c
/* 重构前：一堆守卫 */
for (i = 0; i < n; i++) {
    if (!buf[i].valid) continue;
    if (buf[i].type != TYPE_A) continue;
    if (buf[i].skip) continue;
    if (buf[i].len > MAX_LEN) continue;
    process(&buf[i]);
}

/* 重构后：谓词 + 处理 */
static int is_processable(const pkt_t *p){
    return p->valid
        && p->type == TYPE_A
        && !p->skip
        && p->len <= MAX_LEN;
}

for (i = 0; i < n; i++)
    if (is_processable(&buf[i])) process(&buf[i]);
```

收益：

1. **`is_processable` 可测试**：能在主机侧单独验证（裸机调试成本高的直接对策）；
2. **循环体一眼看懂**：只剩"符合条件的就处理"；
3. **可复用**：别处也要同一个判据时不用复制粘贴。

裸机上的额外收益：`is_processable` 是**纯函数**（不碰硬件），
可以放心在主机侧用 UBSan/ASan 跑一遍
（[4.9](../04-numbers-and-bitops/4.9-溢出.md) 讲过把纯逻辑挪到主机验证的策略）。

反过来说，**别过度抽象**：只有 1–2 个条件的循环，写 `continue` 守卫链就好，
拆函数反而增加跳转成本（`-O0` 下不被内联）和阅读跳转。
</details>
