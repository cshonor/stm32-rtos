# 4.5 整数的大小和表示

> 书：第 4 章 数字和变量 · 4.5 整数的大小和表示（原书 p44–64 区间内）
> 上一篇：[4.4 初始化](4.4-初始化.md) ｜ 下一篇：[4.6 数字表示](4.6-数字表示.md)
> 对应实验：Mac 主机 clang 23.1.0 实测 + `--target=armv7m-none-eabi` 交叉校验

## 书这一节讲什么

一句话：**`int` 有多大是由实现决定的，C 标准只保证 `char` = 1 字节、
`short` ≤ `int` ≤ `long`**。书在这里让你意识到"不同系统上整数可能不一样大"。

这一节在裸机上是**硬约束级别**的：写寄存器时类型宽度错了，
不是"算错一点"，是**写到另一个地址**。

## 一、实测：同一份代码，两个平台的宽度不一样

主机（Mac，arm64，LP64）：

```
$ clang -O2 -o sizes sizes.c && ./sizes
sizeof: char=1 short=2 int=4 long=8 long long=8 ptr=8
INT_MAX=2147483647 INT_MIN=-2147483648 UINT_MAX=4294967295
```

目标机（Cortex-M3，ILP32）——不能跑 `printf`，用**编译期断言**验证：

```c
/* arm_width.c */
#include <stdint.h>
_Static_assert(sizeof(void*) == 4, "ptr on Cortex-M");
_Static_assert(sizeof(int)   == 4, "int");
_Static_assert(sizeof(long)  == 4, "long on Cortex-M != 8");
_Static_assert(sizeof(long long) == 8, "long long");
```

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding -c arm_width.c
（无输出 = 全部通过，说明 Cortex-M 上 long 确实是 4）

$ # 把 sizeof(long)==4 改成 ==8 再编：
arm_width_bad.c:4:16: error: static assertion failed due to requirement 'sizeof(long) == 8'
    4 | _Static_assert(sizeof(long)  == 8, "long on Cortex-M != 8");
      |                ^~~~~~~~~~~~~~~~~~
arm_width_bad.c:4:30: note: expression evaluates to '4 == 8'
```

| 类型 | Mac（arm64 / LP64） | Cortex-M3（ILP32） | 裸机该用什么 |
|---|---|---|---|
| `char` | 1 | 1 | `uint8_t` |
| `short` | 2 | 2 | `uint16_t` |
| `int` | 4 | 4 | `int`（数量）/ `int32_t`（跨界） |
| `long` | **8** | **4** | ⚠ 别用，用 `uint32_t` / `int32_t` |
| `long long` | 8 | 8 | 64 位计数才用（Cortex-M 上多条指令） |
| 指针 | 8 | 4 | —— |

**`long` 这一行就是本节的全部价值。** 在 Mac 上写 `unsigned long mask = 1UL << 20;`
看不出问题；同一份代码交叉编译到 Cortex-M，`long` 变成 4 字节，
如果那段代码还依赖 64 位语义（比如做地址运算、做时间戳），行为就变了。

## 二、为什么"表示"也重要：极值的十六进制

```
INT_MAX hex = 0x7fffffff ; INT_MIN hex = 0x80000000
```

知道这两个数长什么样，才能一眼看出"这个寄存器值是不是踩到了符号位"。
裸机上最常见的误判：`0x80000000` 到底是"很大的正数"还是"最小的负数"——
取决于你把它读成 `uint32_t` 还是 `int32_t`，**位模式完全一样**。

## 三、`_Static_assert`：把宽度钉死在编译期

裸机上**不能运行程序来验证假设**，所以编译期断言是唯一手段：

```c
_Static_assert(sizeof(uint32_t) == 4, "");                     /* 类型宽度 */
_Static_assert(offsetof(GPIO_TypeDef, BSRR) == 0x10, "");      /* 寄存器布局 vs 手册 */
_Static_assert(CPU_FREQ_HZ == 72000000, "");                   /* 时钟配置 */
```

第二条最有价值：**手写寄存器结构体与手册偏移对不上时，编译期就炸**，
而不是等到真机上"灯不亮"再猜。

顺带实测一件事：`stdint.h` 在 `-ffreestanding`（没有 libc）下照样能用——

```
$ clang ... -ffreestanding -c fs.c    # fs.c 只有 #include <stdint.h> + 两个变量
（无报错）
```

因为 `stdint.h` 是编译器自带的头，描述的是**目标平台的类型宽度**，不依赖任何库。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "`int` 一般是 32 位" | 这个平台上确实是 4，但 `long` **Mac 上是 8、Cortex-M 上是 4**（实测断言）。别用 `long` |
| "换平台重新编译就行" | 重新编译能过，但语义变了：`long` 从 8 变 4，地址运算/时间戳/协议字段全跟着变 |
| "用 `sizeof` 打印看看" | 裸机上没有 `printf`。要用 `_Static_assert` 在**编译期**证明（实测贴了失败输出） |
| "`stdint.h` 要有 libc" | 它是编译器自带的头，`-ffreestanding` 下实测可用 |
| "`char` 就是字符" | `char` 的符号性是实现定义的（arm 上默认 `unsigned`）。跨界字节一律 `uint8_t` |

## 代码自测

<details>
<summary>Q1：为什么裸机代码里几乎见不到 `int` 和 `long`？</summary>

两个原因，第二个才是关键。

1. **宽度要确定**。C 标准对 `int` 只保证 ≥16 位、对 `long` 只保证 ≥32 位，
   实际宽度由 ABI 决定。实测 Mac 上 `long`=8、Cortex-M 上 `long`=4，
   同一份代码在两个平台上的宽度不一样。
2. **语义要确定**。寄存器里的位模式是**硬件定义**的：
   `0x00100000` 是一个 32 位无符号数。用有符号类型去承载它，
   一旦最高位是 1 就变成负数，右移和比较的语义跟着变
   （实测 `(unsigned)(-8) >> 1 = 0x7ffffffc`，而 `-8 >> 1 = -4`）。

所以规则是：**"值"用有符号（`int` / `int32_t`），"位模式"用无符号（`uint32_t`）**。
寄存器地址、掩码、位号、协议字段全是位模式 → 全用 `uint*_t`，常量加 `u` 后缀。
</details>

<details>
<summary>Q2：`_Static_assert` 在裸机上有什么用？我又不能运行程序。</summary>

正因为**不能运行**，编译期断言才更重要——它在编译期求值，不过就硬报错，
不占一行运行代码、不需要运行时环境。

裸机上最适合钉死这三类假设：

```c
_Static_assert(sizeof(uint32_t) == 4, "");                  /* 类型宽度 */
_Static_assert(offsetof(GPIO_TypeDef, BSRR) == 0x10, "");   /* 寄存器布局与手册一致 */
_Static_assert(CPU_FREQ_HZ == 72000000, "");                /* 时钟配置 */
```

第二条最有价值：**手写寄存器结构体和手册偏移对不上，编译期就炸**，
不用等到真机上"灯不亮"再去猜。
这是把"运行时玄学"前移成"编译期确定性"的典型手段——
裸机调试成本远高于主机，任何能前移的检查都值得做。
</details>

<details>
<summary>Q3：我在 Mac 上用 `long` 写的代码，交叉编译到板子上会有多糟？</summary>

取决于你拿 `long` 干什么：

| 用途 | 后果 |
|---|---|
| 循环计数（`for (long i=0;i<100;i++)`） | 没事，只是多占寄存器/内存 |
| 存位掩码（`unsigned long mask`） | 没事（4 字节够用），但如果移植到 64 位平台就有隐患 |
| 地址运算（`long addr = base + off`） | ⚠ 宽度变化，高位截断风险 |
| 64 位时间戳（`long us`） | ❌ 在 Cortex-M 上变成 32 位，**约 71 分钟就回绕** |
| 协议字段打包（假定 8 字节） | ❌ 结构体布局变化，与对端对不上 |

最后一类最隐蔽：你以为在定义"8 字节的协议头"，
到了板子上变成 4 字节，而对端是按 8 字节解析的——
两边都编译通过、都跑得起来，就是数据永远是错的。

一句话总结：**裸机上把 `long` 当成"写不得"的类型**，
需要确定宽度就写 `int32_t` / `uint32_t`，需要 64 位就写 `int64_t` / `uint64_t`。
</details>
