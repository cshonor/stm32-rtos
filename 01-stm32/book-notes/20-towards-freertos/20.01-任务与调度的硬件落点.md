## 这一篇讲什么

"RTOS 能同时跑好几个任务"这句话听起来像魔法。
这一篇把它拆穿：**任务切换不是软件技巧，是两个 Cortex-M 异常 +
两个栈指针配合出来的硬件机制。**理解了落点，调试器里看到的每一幕都有解释。

## 一个任务在硬件眼里是什么

任务 = **一个栈 + 一份寄存器现场**。

"切换任务"的本质：

```
把当前任务的寄存器现场存到它自己的栈上
   → 换栈指针（SP 指向下一个任务的栈）
   → 从下一个任务的栈上把寄存器现场弹回来
```

CPU 本身根本不知道"任务"的存在——它只是在执行代码。
是 RTOS 内核**周期性地打断它**，每次打断换一份现场。

## 落点一：SysTick 是调度器的心跳

[19.01](../19-systick-and-timer/19.01-SysTick是内核自带的心跳.md) 说过 SysTick 是
"唯一所有 Cortex-M 都有的定时器"——这就是所有 RTOS 都拿它当心跳的原因。

FreeRTOS 的节拍（tick）默认 1 ms：

```
SysTick 中断（每 1 ms）
   → xTaskIncrementTick()：到期的延时任务置为就绪
   → 如果有更高优先级任务就绪 → 置位 PendSV
```

注意最后一步：**SysTick ISR 本身不做任务切换，它只是"请求"切换。**
真正切换的是 PendSV。

## 落点二：PendSV 是真正换现场的地方

PendSV（Pendable Service Call）是 Cortex-M 专门为
"可挂起的系统调用"设计的异常，两个关键性质：

1. **优先级必须配成最低**——所以它永远在所有外设中断都处理完之后才执行
   （想想 19.1 说的"SysTick 默认优先级 0 是最高，RTOS 里要调低"，
   配的就是这两个异常）；
2. **可以由软件置位触发**——SysTick ISR 里置位它，等所有 ISR 退完，它才跑。

为什么要绕这一层？如果 SysTick ISR 里直接换现场，
而这个 ISR 又打断了另一个外设 ISR（中断嵌套），
换回来的"现场"就是错的。**PendSV 优先级最低 = 保证切换发生在
"所有中断都干净退完"的时刻。**

```
SysTick ISR（高优先级）   ──置位──→   PendSV（最低优先级）
  "要不要换任务？要"                  等所有 ISR 退完 → 真正换现场
```

## 落点三：MSP/PSP 双栈

Cortex-M 有两个栈指针：

| 栈指针 | 谁在用 | 裸机里 | FreeRTOS 里 |
|---|---|---|---|
| **MSP**（主栈指针） | 复位后默认、所有 ISR/异常 | **唯一**的栈（`_estack = 0x20005000`，见 3.3） | 内核 + ISR 用 |
| **PSP**（进程栈指针） | 线程模式可选 | 从来不用 | **每个任务一个栈**，PSP 指向当前任务的栈 |

裸机的 `main` 和所有中断共用 MSP 一个栈；
上了 FreeRTOS 之后，**任务跑在 PSP 上、中断跑在 MSP 上**。

任务切换时内核做的事（在 PendSV 里）：

```
1. 把当前任务剩下的寄存器（R4–R11）压到当前 PSP 指向的栈
   （R0–R3/R12/LR/PC/xPSR 进异常时硬件已自动压好了）
2. 把当前 PSP 存进当前任务的 TCB（任务控制块）
3. 从下一个任务的 TCB 取出它保存的 PSP
4. 从那个栈弹出 R4–R11，异常返回
   → 硬件自动从新栈弹出 R0–R3/LR/PC → CPU 接着跑"另一个任务"
```

**落点检查**：这套东西在调试器里是看得见的——
`02-freertos/01-hello-task` 落地后，halt 在 PendSV_Handler 里
`info registers sp psp msp` 就是这篇的活教材（⬜ 待实测）。

## 与 LDD- 侧对照

| 概念 | Linux 调度器 | FreeRTOS（Cortex-M3） |
|---|---|---|
| 调度时机 | 定时器 tick + 系统调用返回点 | SysTick tick + PendSV |
| 现场保存 | `switch_to` 汇编，进程内核栈 | PendSV 汇编，任务栈（PSP） |
| 中断与调度 | 中断返回时检查 `need_resched` | SysTick 置位 PendSV，**切换推迟到中断退完** |
| 双栈 | 用户栈 / 每线程内核栈 | PSP（任务）/ MSP（ISR + 内核） |

设计上惊人地像：**都把"要不要调度"和"真正切换"分成两步**，
都把切换压到"中断退干净的边界"。这不是巧合，是同一类约束的答案。

## 坑点（常识怎么说 / 实际是什么）

| 常识怎么说 | 实际是什么 |
|---|---|
| "RTOS 的任务切换是软件模拟的并发" | 落点是**硬件异常**：SysTick 提需求、PendSV 换现场、PSP/MSP 双栈分工。调试器里全部可见 |
| "SysTick 中断里直接做切换就行" | 不行——中断嵌套时现场会错。所以 Cortex-M 给了 **PendSV**：优先级最低，保证在所有 ISR 退完后切换 |
| "RTOS 项目的 SysTick 优先级不用管" | 必须管：SysTick 和 PendSV 都要**调到低优先级**（PendSV 最低），默认 0 是最高，会让调度打断外设 ISR |
| "每个任务一个栈是 RTOS 的发明" | 是 **PSP 这个硬件**的用武之地。裸机时代 PSP 一直闲着，RTOS 第一次让它干活 |
| "任务栈大小随便给" | 每个任务栈几十~几百字节，本板 RAM 只有 20 KB——**栈预算是 RTOS 项目的头等大事**（3.04 的 `-fstack-usage` 在这里变成每个任务都要量） |

## 代码自测

<details>
<summary>Q1：为什么任务切换不放在 SysTick ISR 里直接做，而要绕一道 PendSV？</summary>

因为 **SysTick ISR 可能嵌套在别的中断里**。

Cortex-M 支持中断嵌套：高优先级中断可以打断低优先级中断。
假设 UART ISR 正在跑（现场是 UART ISR 的），SysTick 来了把它打断。
如果此时在 SysTick ISR 里直接换任务现场，
保存的"任务现场"其实是 **UART ISR 的现场**——
换回来之后 UART ISR 再也回不去了，系统直接乱。

PendSV 的设计就是解决这个：

1. SysTick ISR 里只做轻活（tick 计数、判断要不要切换），
   要切换就**置位 PendSV**；
2. PendSV 优先级配成**全系统最低**，
   所以它会一直 pending 到**所有 ISR（包括嵌套的）全部退完**；
3. 那一刻栈上干干净净只剩任务现场，切换才是安全的。

一句话：**SysTick 负责"提出切换请求"，PendSV 负责"在安全的时机执行"。**
这个分工和 Linux 的 `need_resched` 标志 + 中断返回点检查是同构的。
</details>

<details>
<summary>Q2：MSP 和 PSP 各干什么？为什么 RTOS 需要两个栈指针？</summary>

| | MSP | PSP |
|---|---|---|
| 裸机 | 唯一的栈（main + 所有 ISR） | 闲置 |
| FreeRTOS | **ISR + 内核**专用 | **任务**专用，指向当前任务的栈 |

两个栈指针解决两个问题：

**① 中断栈和任务栈解耦。**
裸机里 ISR 压栈是压在 main 的栈上（ch07 实测过进 ISR 多压 32 字节）。
RTOS 里如果 ISR 还压在当前任务的栈上，
每个任务的栈都得额外留"最坏情况的中断嵌套深度"——RAM 根本不够。
ISR 统一走 MSP，**任务栈只需考虑任务自己**。

**② 切换任务 = 换一个 PSP 值。**
每个任务有自己独立的一块 RAM 当栈，
TCB 里存着它"上次被切走时 PSP 停在哪"。
PendSV 里换任务，本质上就是**换一个栈指针 + 弹一套寄存器**。

进 PendSV 时硬件已经自动把 R0–R3/R12/LR/PC/xPSR 压到了当前 PSP 上
（异常进栈永远用当前 active 的 SP），PendSV 只需手动压 R4–R11——
这就是"32 字节自动 + 32 字节手动"的完整现场。
</details>

<details>
<summary>Q3：FreeRTOS 为什么敢给产品用？许可证上有什么讲究？</summary>

**FreeRTOS 是 MIT 许可证**（仓库根 README 明确记录）。

MIT 意味着：

- 可以静态链接进闭源固件，无源码开放义务；
- 无 copyleft——和 LDD- 侧内核模块的 GPL 语境完全不同
  （"GPL 只在内核语境存在；MCU 裸机无许可证负担"）；
- 只需保留版权声明。

对照组是 libopencm3（LGPL-3.0 / GPL-3.0）：
**静态链接它会带上 LGPL 的义务**，做产品前要单独评估。

所以选型结论很直接：
RTOS 内核选 FreeRTOS（MIT，无负担），
寄存器层要么自己写（主线）、要么用 libopencm3（评估 LGPL 义务）。
</details>
