## 这一篇讲什么

前两篇讲了 RTOS 给的三件东西：任务切换（20.1）、队列/信号量（20.2）。
这一篇把账算平：**这些东西要付什么成本、什么信号说明非付不可**，
以及第一个实验 `02-freertos/01-hello-task` 具体验证什么。

## 成本清单

| 成本 | 量级 | 说明 |
|---|---|---|
| Flash | 几 KB | 内核代码（调度器 + 队列 + 信号量） |
| RAM | 每任务几十~几百字节 | **每个任务一个栈**（20.1 的 PSP），本板只有 20 KB |
| 心智 | 中 | 调度、优先级、同步原语都要懂，bug 从"顺序错"升级成"时序错" |
| 调试 | 更复杂 | 多栈、要查任务状态；断点停一个任务时别的还在跑 |

对照超级循环：Flash 开销 0、RAM 共享一个栈、单线程调试。
**所以 RTOS 不是"更高级"，是"更贵"——得有非买不可的理由。**

## 五个"该上了"的信号

沿用 [19.4](../19-systick-and-timer/19.4-三种等待的对比.md) 那张表，
逐条落到本仓库：

| 信号 | 超级循环的症状 | RTOS 给的药 |
|---|---|---|
| **有阻塞操作** | "等传感器 50 ms"全系统停摆 | `vTaskDelay`：这个任务睡，别的照跑 |
| **响应时间要求差异大** | 快的被慢的拖死 | 优先级抢占 |
| **任务间要传数据** | 手写环形缓冲 + 标志，越写越乱 | 队列（20.2） |
| **代码量上千行** | 状态机失控 | 每个任务一个顺序执行的 `for(;;)` |
| **团队开发** | 主循环里互相踩 | 一人一个任务 |

本板 20 KB RAM 的限制反而是好事：**它逼着你在
"超级循环还够用"和"非上 RTOS 不可"之间做出清醒判断**，
而不是无脑上框架。

## 落点：02-freertos/01-hello-task 验证什么

`02-freertos/README.md` 的定义：**两个任务 LED 交替（调度器第一课）**。

这个最小实验要亲眼看到的，就是 20.1 讲的那套机制：

```
任务 A：闪 LED，vTaskDelay(500)  ← 睡着时 PSP 停在它的栈上
任务 B：闪另一只/同一颗 LED，vTaskDelay(500)
调度器：SysTick 每 1 ms tick → PendSV 换现场 → 两个任务轮流跑
```

裸眼看是"两颗灯交替"；
在调试器里应该能核对（⬜ 待实测）：

1. halt 在任务 A 里，读 `psp` 指向 A 的栈、`msp` 指向内核栈；
2. 单步过 `vTaskDelay`，任务 A 消失（不在就绪表），CPU 跑任务 B；
3. SysTick 计数在两个任务间均匀推进。

**为什么这个实验值得先做**：如果 01 跑不通，
问题一定在移植层（`FreeRTOSConfig.h`、port 层、栈分配），
而不是队列信号量——**先把"两个栈换来换去"这件最根本的事钉死**。

后续三个实验恰好是本篇三个概念的落点：

| 实验 | 对应概念 |
|---|---|
| `01-hello-task` | 任务 + 调度（20.1） |
| `02-queue` | 中断 → 队列 → 任务（20.2，对照 LDD-/09 下半部） |
| `03-semaphore` | 二值信号量做按键去抖（20.2） |
| `04-mutex-priority` | 优先级反转与互斥量（20.1 优先级的阴暗面） |

## 移植要碰什么（事实来自 02-freertos/README.md）

- 源码：官方 FreeRTOS-Kernel，**MIT 许可**（产品可用，见 20.1 Q3）；
- 移植只碰两处：**`FreeRTOSConfig.h`**（tick 频率、堆大小、优先级数）
  + **port 层**——F103 是 Cortex-M3，用现成的 `GCC/ARM_CM3` port，
  **不用自己写汇编**；
- port 层实现的就是 20.1 那套：`SysTick_Handler` 接 tick、
  `PendSV_Handler` 换现场、SVC 启动第一个任务。

## 坑点（常识怎么说 / 实际是什么）

| 常识怎么说 | 实际是什么 |
|---|---|
| "上 RTOS 是技术升级，早上早好" | 是**成本换能力**：几 KB Flash + 每任务一栈 + 调试复杂度。任务少、无阻塞、RAM 紧时超级循环更优 |
| "RTOS 的延时比裸机准" | `vTaskDelay` 的粒度是 tick（默认 1 ms），**不比** 19.2 的 millis 判据准。它换来的是"睡的时候不烧 CPU、别的任务照跑" |
| "FreeRTOS 移植要写很多汇编" | 不用。Cortex-M3 有现成 `GCC/ARM_CM3` port，只配 `FreeRTOSConfig.h` |
| "两个任务闪灯太 trivial，跳过直接做队列" | 01 是**移植层的试金石**：栈分配、`FreeRTOSConfig.h`、port 层任何一处错都在 01 暴露。跳过去，bug 会伪装成"队列有问题" |
| "RTOS 项目不用懂裸机了" | 恰好相反：**调度落点是裸机异常**（SysTick/PendSV），队列前身是 ch10 的环形缓冲。裸机不懂，RTOS 只能算会用 |

## 代码自测

<details>
<summary>Q1：超级循环明明也能"多任务"，RTOS 真正买到的是什么？</summary>

买到三样超级循环给不了的东西：

**① 阻塞不等于停摆。**
超级循环里 `while(等待)` 会冻住所有任务；
RTOS 里 `vTaskDelay` / `xQueueReceive` 只冻住**自己这个任务**，
CPU 立刻给别人。这是质变。

**② 优先级。**
超级循环的响应延迟 = 一圈里最长那个 task 的时间；
RTOS 里高优先级任务**抢占**低优先级的，响应延迟可预测——
这对"电机控制 100 μs 必须响应、日志可以 1 s 后写"这类系统是刚需。

**③ 同步原语。**
队列/信号量把"ISR → 处理者"的通信从手工状态机变成原语（20.2）。

付的账也再念一遍：几 KB Flash、每任务一个栈（本板 20 KB RAM 下
任务数撑死个位数）、调试从单线程升级成多栈。
**所以判据不是"RTOS 好不好"，是"我有没有那五个信号"**。
</details>

<details>
<summary>Q2：`vTaskDelay(500)` 和裸机的 `delay_ms(500)` 差在哪？</summary>

同一个"等 500 ms"，机制完全不同：

| | 裸机 `delay_ms`（19.2） | `vTaskDelay` |
|---|---|---|
| 实现 | `while (millis() - start < 500);` 空转 | 任务进阻塞表，**让出 CPU** |
| 期间 CPU | 100% 烧在这个循环上 | 跑别的任务 / 进 idle |
| 期间别的任务 | **全停** | 照跑 |
| 粒度 | 1 ms（millis 分辨率） | 1 tick（默认 1 ms，**同量级**） |

注意最后一行：**`vTaskDelay` 并没有更准**——
它的到期检查同样靠 SysTick tick，粒度同样是 1 ms。
它的价值不是精度，是**等待期间不独占 CPU**。

所以"RTOS 延时更准"是误解；
准确说法是"RTOS 让延时从系统级停摆变成任务级小睡"。
真正要更准的周期（100 μs 级），两边答案一样：通用定时器（19.4）。
</details>

<details>
<summary>Q3：为什么 01-hello-task 必须做在队列/信号量实验之前？</summary>

因为它是**移植层的隔离测试**。

一个 FreeRTOS 工程跑不起来，可能的故障点有：
`FreeRTOSConfig.h` 配错、port 层选错、栈分配不足、
向量表没接到 `SysTick/PendSV/SVC_Handler`……
如果第一个实验就上队列，任何一个上述故障都会伪装成
"队列 API 有问题"，排查面直接翻倍。

01-hello-task 把变量压到最少：

- 不用队列、不用信号量、不用动态内存；
- 只有两个任务 + `vTaskDelay`；
- 跑通 = **调度机制（SysTick/PendSV/双栈）全部正确**，
  这是后续一切的地基。

这和本仓库裸机侧的纪律是同一条（3.3 先点灯再上中断）：
**每一层用最简单的实验钉死，再往上一层。**
⬜ 实验落地后，halt 读 `psp`/`msp`、单步过 `vTaskDelay`
的观察记录会补进本篇。
</details>
