## 这一篇讲什么

ch10 讲中断时已碰过这个问题：UART ISR 收到一个字节，
怎么安全地交给主循环处理？当时的答案是**手写环形缓冲区 + volatile 标志**。
本篇讲 RTOS 的正式答案：**队列（传数据）和信号量（传事件）**——
以及为什么 ISR 里要用专门的 `FromISR` 版本。

## 从 ch10 的环形缓冲区说起

裸机版"ISR → 主循环"通信（ch10 的写法）：

```c
/* 裸机版：自己维护的环形缓冲区 */
static volatile uint8_t  s_buf[64];
static volatile uint32_t s_head, s_tail;   /* ISR 写 tail，主循环写 head */

void USART1_IRQHandler(void){
    s_buf[s_tail++ % 64] = USART1_DR;      /* 中断里只做"收进来" */
}
/* 主循环里轮询 head != tail 再处理 —— "下半部"思想的手工版 */
```

这个模式本身没问题（LDD-/09 的下半部就是同一个思想），
但它有三个手工代价：**主循环必须轮询**（没数据也空转）、
**满/空边界自己写**（写错就是丢数据）、**没有唤醒机制**（不能"睡到数据来"）。

## 队列：把环形缓冲区 + 阻塞等待做成原语

FreeRTOS 的队列 = **环形缓冲区 + 任务阻塞/唤醒机制**：

```c
xQueueHandle q = xQueueCreate(64, sizeof(uint8_t));

void USART1_IRQHandler(void){
    uint8_t c = USART1_DR;
    xQueueSendFromISR(q, &c, NULL);     /* ← 注意：FromISR 版 */
}

void uart_task(void *p){                /* 一个专门处理串口的任务 */
    uint8_t c;
    for (;;) {
        xQueueReceive(q, &c, portMAX_DELAY);   /* 没数据就睡，CPU 占用 0 */
        process(c);
    }
}
```

对手工版的三个代价，逐条解决：

| 手工环形缓冲 | 队列 |
|---|---|
| 主循环轮询 | `xQueueReceive` **阻塞**：没数据时任务睡着，调度器根本不排它 |
| 满/空边界自己写 | 内核维护，写满可以阻塞或丢弃（由你选） |
| 没有唤醒 | 数据一到，等待中的任务**立刻变就绪**（高优先级还会触发切换） |

**落点**：`02-freertos/02-queue`（中断 → 队列 → 任务，
就是"下半部思想的 RTOS 版"，对照 LDD-/09）。

## 信号量：不传数据，只传"发生了一件事"

有时候 ISR 要交代的不是数据，只是一个事件："按键按了"。
这时用**二值信号量**——一个容量为 1 的"空队列"：

```c
xSemaphoreHandle sem = xSemaphoreCreateBinary();

void EXTI15_10_IRQHandler(void){        /* 按键中断 */
    xSemaphoreGiveFromISR(sem, NULL);
}

void button_task(void *p){
    for (;;) {
        xSemaphoreTake(sem, portMAX_DELAY);   /* 睡到按键发生 */
        handle_key();                          /* 去抖等慢活放任务里做 */
    }
}
```

为什么去抖要放任务里？因为去抖要**等 20 ms 再采样**——
ISR 里等 20 ms 是死锁级的错误（ch10），
任务里 `vTaskDelay(20)` 则名正言顺：**它睡它的，别的任务照跑。**
这就是 20.1 那个调度机制换来的自由。

**落点**：`02-freertos/03-semaphore`（二值信号量做按键去抖）。

## 为什么 ISR 里必须用 `FromISR` 版本

`xQueueSend` 在队列满时会**阻塞等待**——而 ISR 里阻塞 = 死锁
（中断不退出，谁去消费队列？）。`xQueueSendFromISR` 的区别：

- **永不阻塞**：满了直接返回错误；
- **不直接触发任务切换**：被唤醒的任务优先级更高时，
  通过第三个参数 `pxHigherPriorityTaskWoken` 告诉你"出去后该切了"，
  真正的切换还是交给 PendSV（呼应 20.1：切换永远发生在中断退干净后）。

这条纪律和 ch10 的"ISR 里只做最轻的事"是同一条纪律的 RTOS 版：
**ISR 负责把事扔进队列/信号量，慢活永远留给任务。**

## 与 LDD- 侧对照

| 概念 | Linux 内核 | FreeRTOS |
|---|---|---|
| ISR → 处理者传数据 | kfifo / 工作队列（workqueue） | **队列**（`xQueueSendFromISR`） |
| ISR → 处理者传事件 | `complete()` / `wake_up()` | **信号量**（`xSemaphoreGiveFromISR`） |
| 上下半部 | top half 收中断，bottom half 做慢活 | ISR 发给队列，**任务**做慢活 |
| 阻塞读 | `wait_event_interruptible` | `xQueueReceive(portMAX_DELAY)` |

一句话：**RTOS 任务就是"可以被中断唤醒的下半部"。**

## 坑点（常识怎么说 / 实际是什么）

| 常识怎么说 | 实际是什么 |
|---|---|
| "有了 RTOS 就不用懂环形缓冲区了" | 队列**就是**环形缓冲区 + 阻塞唤醒。不懂 ch10 那个手工版，队列满了丢数据你都看不出为什么 |
| "ISR 里调 `xQueueSend` 也行吧" | 不行。它可能阻塞，ISR 里阻塞 = 死锁。**ISR 里只许用 `FromISR` 版**，且永不阻塞 |
| "`FromISR` 版会立刻切换到高优先级任务" | 不会立刻切。它只置 `pxHigherPriorityTaskWoken`，真正切换仍走 PendSV、等中断退完（20.1） |
| "去抖就是 ISR 里 `delay_ms(20)`" | ISR 里延时 = 死锁级错误。去抖属于"慢活"，放任务里用 `vTaskDelay` 做——这正是信号量实验的内容 |
| "信号量比队列快所以都用信号量" | 二者分工不同：**传数据用队列，传事件用信号量**。按键事件不需要数据，但串口字节必须要 |

## 代码自测

<details>
<summary>Q1：队列和裸机的环形缓冲区比，本质进步在哪？</summary>

不在数据结构——**队列底层就是环形缓冲区**。进步在两点：

**① 阻塞与唤醒成了原语。**
裸机版主循环必须轮询 `head != tail`；
队列版任务在 `xQueueReceive` 上**睡着**，数据到了由内核唤醒。
睡着的任务不占 CPU——这是"轮询"和"事件驱动"的分水岭。

**② 边界条件归内核管。**
手工版的满/空判断、`volatile`、回绕，写错一处就是丢数据。
队列把这些收进内核，你只需回答："满了是等还是丢？""等多久？"

代价也要记清：队列创建要 RAM（缓冲区 + 控制块），
每进出一个字节都要过内核——**极端高频的字节流还是 DMA + 半满中断
更合适**（19.4 Q1 的③），队列适合"事件级"的流量。
</details>

<details>
<summary>Q2：为什么 ISR 里只能用 `FromISR` 版本？用普通版会发生什么？</summary>

因为普通版**可能阻塞**。

`xQueueSend` 的语义是"队列满了就等到有位置"。
"等待"在任务里没问题——任务睡了，调度器跑别的。
但在 ISR 里"等"意味着**中断不退出**：

- 中断不退出，同优先级和更低优先级的中断全被压住；
- 消费者任务永远轮不到跑，队列永远满着；
- 死锁，而且是硬件级的——看门狗不喂的话只能复位。

`FromISR` 版用两条规则躲开这个死结：

1. **永不阻塞**：满了立即返回 `errQUEUE_FULL`，由 ISR 决定丢还是攒；
2. **切换延迟到 PendSV**：唤醒了高优先级任务也不立刻切，
   把"该切了"记在 `pxHigherPriorityTaskWoken` 里，
   等所有中断退干净由 PendSV 统一换现场（20.1 的机制）。

这条和 Linux 里"中断上下文不能 `schedule()`"是**同一条铁律**：原子上下文不许睡。
</details>

<details>
<summary>Q3：按键去抖为什么适合用二值信号量而不是队列？</summary>

因为按键事件**没有数据要传**——"按了"本身就是全部信息。

队列的每个元素要占 RAM（哪怕 1 字节 × 深度），
而且消抖场景下短时间内可能来一串边沿中断（抖动），
攒进队列毫无价值——任务只需要知道"发生过至少一次"。

二值信号量正是"容量 1 的事件标志"：

```
抖动期 10 次中断 → 10 次 Give → 信号量仍是 1（多的 Give 无害）
任务 Take 到一次 → 睡 20 ms（vTaskDelay，别的任务照跑）
→ 再采样电平 → 确认有效按键
```

注意 `vTaskDelay(20)` 这步：去抖的等待**只能在任务里做**——
**同一个"等 20 ms"，在超级循环里靠问时间，在 RTOS 里靠挂起自己。**

**落点**：`02-freertos/03-semaphore` 就是把这三行写成真机实验。
</details>
