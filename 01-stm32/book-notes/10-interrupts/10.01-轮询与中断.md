# 10.01 轮询与中断

> 书：第 10 章 中断 · 10.01 轮询与中断（原书 p135–153 区间内）
> 下一篇：[10.02 串口 I/O 中断](10.02-串口IO中断.md)
> 对应实验：`--target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding`（`-Os` 反汇编）+ 主机侧 `write(2)` 计时

## 书这一节讲什么

一句话：**先让你体会轮询有多浪费，再引出中断**。

书用"CPU 一直在问'好了吗'"来对比。这个比喻是对的，
但裸机上要把它变成**可计算的数字**——因为"浪费多少"决定了你该不该上中断。

## 一、轮询的代价：CPU 100% 在问

```
轮询：                              中断：
主循环 ──读 SR──空？──读 SR──空？    主循环 ──干活──干活──干活──┐
        ↑______________|                                      │ ← 中断来了
   CPU 100% 在问"好了吗"                                    ISR 处理
                                    主循环 ←──继续干活───────┘
```

[ch09](../09-uart-serial/README.md) 的 `uart1_putc` 就是轮询——
实测反汇编里那个 `bpl 0x8` 自跳就是"一遍遍问"。

**用数字说话**（115200 bps、8N1）：

| 项 | 值 |
|---|---|
| 1 bit | 8.68 µs |
| **1 字节（10 bit）** | **86.8 µs** |
| 吞吐 | 11520 字节/秒 |
| 72 MHz 下一个字节的等待 | **6249 个时钟周期** |

**发一个字节，CPU 空转 6249 个周期。** 这就是轮询的全部代价。

## 二、中断的价值不是"更快"，是"不用等"

这是一个常被说错的点。看实测对比：

| | 轮询 | 中断 |
|---|---|---|
| 单字节延迟 | 86.8 µs（等硬件） | 86.8 µs（**一样**，硬件速度不变） |
| 这期间 CPU | **空转** | **干别的** |
| 吞吐上限 | 11520 B/s | 11520 B/s（**一样**） |
| 代码复杂度 | 低 | 中（两道使能 + ISR + 缓冲） |

**中断不改变硬件速度，它改变的是"等待期间 CPU 能不能干别的"。**
书 10.4 叫"用缓冲区提速"——严格说提速的是**并发**，
缓冲区只是让它**不丢数据**。

## 三、实测：PC 侧的同一个问题（系统调用开销）

裸机的"轮询 vs 中断"在 PC 上的对应物是"同步 I/O vs 异步 I/O"。
先看同步 I/O 的每次开销（[ch09 9.01](../09-uart-serial/9.01-一次写一个字符的字符串.md) 实测）：

```
$ clang -O2 -o wr2 wr2.c && ./wr2        # Mac/arm64
逐字符：200×200000 次 write = 37.2807 s → 0.932 us/次
```

一次 `write(2)` **0.93 µs**。20 万字节逐个发 = 186 ms，
而这 186 ms 里**发起方什么也做不了**（除非用 `select`/`epoll`/io_uring）。

所以这个问题是**通用的**：

| 环境 | 轮询 | 事件驱动 |
|---|---|---|
| 裸机 | `while(!(SR&TXE));` | 中断 + ISR |
| Linux | `read()` 阻塞 | `epoll` / `io_uring` |
| JS | 阻塞等 | Promise / 事件循环 |

**机制不同，问题同一个：等待期间能不能干别的。**

## 四、什么时候该上中断？三条判据

| 判据 | 轮询 | 中断 |
|---|---|---|
| **事件什么时候来** | 我知道（主动发送） | **不知道**（接收、按键） |
| **等待期间有活干吗** | 没有（启动日志） | 有（主循环在跑控制逻辑） |
| **频率** | 低频 | 高频 |

结论：

- **发送** → **轮询就够了**（我知道什么时候要发，而且日志要"卡住也打出来"）；
- **接收** → **必须中断**（不知道字节什么时候来，F1 的 DR 只有 1 个字节，
  主循环一走开就丢）；
- **高速流**（>100 KB/s）→ 两个都不够，上 DMA。

这就是很多量产产品的实际配置：**轮询发送 + 中断接收**。

## 五、轮询也不是没优点

别把轮询当"原始做法"鄙视掉——它有三个中断给不了的好处：

1. **简单**：没有 ISR、没有临界区、没有重入问题；
2. **确定**：执行时间可预测（最坏 = 等一个字节的时间）；
3. **在 HardFault 里能用**：轮询不依赖 NVIC 工作正常。
   中断版在 HardFault 时 ISR **不会被调用**——
   而你最需要的恰恰是崩溃前的日志（[ch09 9.03](../09-uart-serial/9.03-串行输出.md) Q3）。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "中断比轮询快" | ❌ **硬件速度一样**（115200 都是 11520 B/s）。中断的价值是"等待期间 CPU 能干别的" |
| "轮询总是浪费" | 日志场景轮询更好：简单、确定、**HardFault 里能用** |
| "接收也可以轮询" | ❌ F1 的 DR **只有 1 个字节**，主循环一走开就丢。接收必须中断 |
| "等一个字节没什么" | 72 MHz 下是 **6249 个周期**（86.8 µs × 72 MHz） |
| "上中断就完事了" | 中断带三样新东西：两道使能门、ISR 约束、共享数据并发。都有代价 |

## 代码自测

<details>
<summary>Q1：轮询和中断的"速度"到底差在哪？给我一个可判定的标准。</summary>

**吞吐上限完全相同，差在 CPU 占用率。**

算一遍（115200 bps、8N1、72 MHz）：

```
1 bit      = 1/115200 s  = 8.68 µs
1 字节     = 10 bit      = 86.8 µs
吞吐上限   = 115200/10   = 11520 字节/秒
等待周期数 = 86.8 µs × 72 MHz = 6249 个周期
```

**这三项在轮询和中断下完全一样**——因为它们是 UART 硬件决定的。

差别只在"这 6249 个周期里 CPU 在干嘛"：

| | 轮询 | 中断 |
|---|---|---|
| 等待期间 | `bpl 0x8` 自跳（实测反汇编） | 执行主循环代码 |
| CPU 有效利用率 | **≈ 0%** | ≈ 100%（减去 ISR 时间） |

**可判定的标准**（用 CPU 占用率算）：

```
轮询的 CPU 开销 = 100% × (等待时间 / 总时间)
```

如果主循环本来就没别的事干（比如启动阶段打几条日志），轮询开销 100% 也无所谓——
反正 CPU 闲着也是闲着。
如果主循环要跑 1 kHz 控制逻辑（周期 1000 µs），
而你要发 10 个字节（868 µs）——**轮询直接吃掉 87% 的周期**，必须上中断。

**一句话判据**：
**看"等待期间 CPU 有没有别的活"。有 → 中断；没有 → 轮询。**
而不是看"快不快"。
</details>

<details>
<summary>Q2：为什么"发送可以轮询、接收必须中断"？</summary>

因为**主动性不同**。

**发送是我发起的**：

```c
uart_puts("temp=25\n");      /* 我知道这一刻要发，发完就走 */
```

什么时候发、发多少，全在我的控制之下。
轮询的"卡住"至多影响我自己的时序，不会丢数据。

**接收是对端发起的**：

```c
/* 我完全不知道下一个字节什么时候到 */
```

而硬件的缓冲极小：

| 芯片 | 接收缓冲 |
|---|---|
| **STM32F1 的 USART** | **1 个字节**（就是 DR 本身） |
| STM32F4/F7 | 仍然只有 DR（部分有 1 字节 + 移位寄存器） |
| 有 FIFO 的 UART（16550 等） | 16 字节 |

**F1 上，主机连发两个字节而你的 ISR 没来得及取走第一个，第二个就没了。**

轮询接收为什么不行：

```c
for (;;) {
    if (USART1_SR & RXNE) { c = USART1_DR; process(c); }   /* process 慢一点就丢字节 */
    do_other_work();                                        /* 这段时间内来了字节 → 丢 */
}
```

`do_other_work()` 期间来的字节**直接丢失**（DR 被覆盖）。
除非你保证主循环一次迭代 < 86.8 µs（115200 下），这不现实。

中断接收：

```c
void USART1_IRQHandler(void){
    if (USART1_SR & RXNE) rb_put(&g_rx_rb, (uint8_t)USART1_DR);   /* 几微秒，抢在下一个字节前 */
}
```

ISR 只做"取走字节"，**几微秒**完成，远小于 86.8 µs 的字节间隔——所以不丢。

⚠ 但即使这样，**ISR 慢了还是会丢**。所以：
- ISR 只入队，不做解析（[10.03](10.03-中断例程.md)）；
- 波特率越高，ISR 的时间预算越紧（115200 → 8.7 µs，921600 → 1.1 µs）；
- 921600 这种速率，ISR 都不够了 → **DMA**。

**这就是"轮询发 + 中断收"成为标准配置的原因**——
它精确匹配了"发送是主动的、接收是被动的"这个不对称性。
</details>

<details>
<summary>Q3：轮询的三个优点是什么？什么时候反而该选轮询？</summary>

中断不是"更高级"，它是**有代价的**——换来并发，付出复杂度。轮询保留的三个优点：

**① 简单：没有并发问题**

轮询版本里，所有代码都在一个执行流里，
不需要考虑：

- 共享变量的原子性；
- ISR 能不能调这个函数；
- 临界区开在哪、恢复什么值。

中断一上，这三类问题立刻出现（[10.04](10.04-用缓冲区提速.md) 讲单写者规则）。

**② 确定：执行时间可预测**

`uart_putc` 的最坏时间 = 等一个字节 = 86.8 µs（115200）。
中断版本的最坏时间取决于**有多少个更高优先级中断**——不确定。

在对时序敏感的地方（比如 bit-banging 某个协议），
"确定地慢"比"通常很快但偶尔被中断打断"更好。

**③ 在 HardFault 里能用（这条最实际）**

HardFault 时：

| | 轮询 | 中断版 |
|---|---|---|
| 依赖 NVIC 工作正常？ | ❌ 不依赖 | ✅ 依赖 |
| ISR 会被调用？ | 不适用 | ❌ 不会（中断被屏蔽） |
| 崩溃前的日志 | ✅ 已发出的都在主机上 | ❌ 缓冲区里的**全丢** |

**你最需要的恰恰是崩溃前的最后几行**，而中断版的那些行还在缓冲区里没发出去。

所以本仓库的选择：

| 用途 | 方案 |
|---|---|
| 调试日志 / 断言 / HardFault | **轮询**（[ch09 9.03 Q3](../09-uart-serial/9.03-串行输出.md)） |
| 协议接收 | 中断 + 环形缓冲（[10.04](10.04-用缓冲区提速.md)） |
| 高速发送 | DMA |

⚠ 一个细节：**轮询版在 HardFault 里能用，前提是 HardFault handler 里不要再做可能失败的事**。
比如不要再等 TXE 等到超时（用带预算的等待，见
[ch09 9.02 Q1](../09-uart-serial/9.02-定义我们的putchar.md)）。
</details>
