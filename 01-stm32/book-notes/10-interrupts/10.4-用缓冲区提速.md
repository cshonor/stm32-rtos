# 10.4 用缓冲区提速

> 书：第 10 章 中断 · 10.4 用缓冲区提速（原书 p135–153 区间内）
> 上一篇：[10.3 中断例程](10.3-中断例程.md) ｜ 下一篇：[10.5 完整程序](10.5-完整程序.md)
> 对应实验：`--target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding`（`-Os` 反汇编 + `-fstack-usage`）+ 主机侧环形缓冲行为验证

## 书这一节讲什么

一句话：**用环形缓冲区解耦 ISR 和主循环**——
ISR 只管把字节塞进去，主循环慢慢取。

书叫它"用缓冲区提速"。严格说**提速的是并发，缓冲区只是让它不丢数据**
（[10.1](10.1-轮询与中断.md)）。但它是本章最实用的一段——
因为 F1 的 USART **只有 1 个字节的 DR**。

## 一、为什么必须缓冲

```
主机连发：[A][B][C]  （115200 下每 86.8 µs 一个）
              ↓
USART1_DR（只有 1 字节）→ ISR 必须在这个字节被覆盖前取走
```

| 芯片 | 接收缓冲 |
|---|---|
| **STM32F1 USART** | **1 字节**（就是 DR） |
| STM32F4/F7 | 仍只有 DR（部分有 1 字节 + 移位寄存器） |
| 16550 等 PC UART | 16 字节 FIFO |

**所以 ISR 必须快，且主循环处理不能阻塞 ISR**——
这就需要一个中间的缓冲。

## 二、环形缓冲的实现

```c
#define RB_SIZE 64u                       /* 必须是 2 的幂 */
typedef struct {
    volatile uint32_t head;               /* ISR 写 */
    volatile uint32_t tail;               /* 主循环写 */
    uint8_t buf[RB_SIZE];
} ringbuf_t;

/* ISR 侧：只动 head */
int rb_put(ringbuf_t *rb, uint8_t c){
    uint32_t next = (rb->head + 1u) & (RB_SIZE - 1u);
    if (next == rb->tail) return -1;      /* 满 */
    rb->buf[rb->head] = c;
    rb->head = next;
    return 0;
}

/* 主循环侧：只动 tail */
int rb_get(ringbuf_t *rb, uint8_t *c){
    if (rb->head == rb->tail) return -1;  /* 空 */
    *c = rb->buf[rb->tail];
    rb->tail = (rb->tail + 1u) & (RB_SIZE - 1u);
    return 0;
}
```

它正确工作，靠的是前几章讲过的四件事：

| 依赖 | 出处 |
|---|---|
| `& (RB_SIZE-1)` 代替 `% RB_SIZE`（SIZE 是 2 的幂） | [ch04 位操作](../04-numbers-and-bitops/README.md) |
| `head`/`tail` 是 unsigned，**回绕是定义良好的** | [ch04 unsigned 溢出](../04-numbers-and-bitops/README.md) |
| **单写者**（ISR 只写 head、主循环只写 tail） | 本节 |
| `head`/`tail` 必须 `volatile` | [ch05 `wait_bad` 实测](../05-control-flow-button/README.md) |

## 三、实测：`& (SIZE-1)` vs `% N`

```c
uint32_t next = (rb->head + 1u) & (RB_SIZE - 1u);   /* 2 的幂：位与 */
uint32_t next = (rb->head + 1u) % 60u;              /* 非 2 的幂：取模 */
```

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding -Os -c rb.c
$ llvm-objdump -d rb_os.o

00000000 <rb_put>:                        ← 位与版：11 条指令
       0: 6802       ldr  r2, [r0]        ; head
       2: 6843       ldr  r3, [r0, #0x4]  ; tail
       4: 3201       adds r2, #0x1
       6: f002 023f  and  r2, r2, #0x3f   ← 一条 and！
       a: 429a       cmp  r2, r3
       ...

00000044 <rb_put_mod>:                    ← 取模版：19 条指令
      46: f648 0389  movw r3, #0x8889     ← 魔法数（乘法的倒数）
      4e: f6c8 0388  movt r3, #0x8888
      52: fbac 3203  umull r3, r2, r12, r3 ← 乘法
      56: 0953       lsrs r3, r2, #0x5
      58: 011b       lsls r3, r3, #0x4
      5a: eba3 1252  sub.w r2, r3, r2, lsr #5
      60: ebac 0282  sub.w r2, r12, r2, lsl #2
      ...                                 ← 多 8 条指令做除法

$ llvm-nm -u rb_os.o
（空 —— 因为 % 60 的除数是常量，编译器用"乘法 + 移位"代替了除法）
```

**11 条 vs 19 条指令**。编译器很聪明——除数是常量时它用
**乘法逆元**（0x88888889）把除法变成 `umull` + 移位，
所以**没有**拉进 `__aeabi_uidiv`。

但如果 `RB_SIZE` 是**运行时变量**（比如可配置的缓冲），
那就是真的 `udiv` 调用，在 M0 上还会变成 `__aeabi_uidiv` 库函数
（[ch09 9.5 实测](../09-uart-serial/9.5-串口HelloWorld.md)）。

**规则：环形缓冲的大小用 2 的幂，写死成宏常量。**

栈用量实测（`-fstack-usage`，`-Os`）：

```
rb.c:5:rb_put       0   static
rb.c:12:rb_get      0   static
rb.c:20:rb_put_mod  0   static
```

**全是 0**——ISR 调用它们不额外占栈，这对栈预算是好消息。

## 四、实测：容量是 `RB_SIZE - 1`，不是 `RB_SIZE`

```c
for (int i = 0; i < 200; i++) if (rb_put(&rb, (uint8_t)i) == 0) ok++; else full++;
```

```
$ clang -O2 -o rbh rbh.c && ./rbh
put ok=63 full_reject=137 head=63 tail=0
get n=63 first=0 last=62  head=63 tail=63
after 300 put/get: head=43 tail=43 max_head=63 (必须<64)
```

**64 的缓冲只能装 63 个字节。**

原因：判满的条件是 `(head + 1) == tail`，
所以 `head` 永远追不上 `tail`——**必须浪费一个格子**来区分"满"和"空"。
（否则 `head == tail` 既表示空又表示满，无法区分。）

回绕验证：`max_head = 63`，**始终 < 64** —— `& (SIZE-1)` 工作正常。

## 五、⚠ 单写者规则：它能不用关中断的唯一原因

这是本节的**并发核心**。

```c
/* ISR 只写 head，只读 tail（判满用） */
int rb_put(ringbuf_t *rb, uint8_t c){
    uint32_t next = (rb->head + 1u) & (RB_SIZE - 1u);
    if (next == rb->tail) return -1;
    rb->buf[rb->head] = c;
    rb->head = next;          /* ← head 的唯一写者 */
    return 0;
}
```

**危险的组合只有一种：两个执行流都写同一个变量。**

```
ISR   ：读 head(5) → +1 → 写 6
主循环：读 head(5) → +1 → 写 6      ← 丢了一次入队
```

只要 `head` 只有 ISR 写，这个问题就不存在。
ISR 读 `tail` 是安全的——最坏情况是**多判了一次满**（缓冲看着比实际满一点），
不破坏数据，只少装一个字节。

**什么时候必须关中断**：

- 主循环也要写 `head`（比如"丢弃一个字节"）；
- **多个 ISR**（不同优先级）写同一个缓冲；
- 缓冲元素不是单字节（比如一个 8 字节的帧，`head` 和 `buf` 的更新不是一步完成）。

```c
uint32_t m;
__asm__ volatile ("mrs %0, primask" : "=r"(m));
__asm__ volatile ("cpsid i");
/* 临界区 */
__asm__ volatile ("msr primask, %0" :: "r"(m));     /* 恢复原值，支持嵌套 */
```

实测这套序列是 8 条指令、用 `cpsid i` 单条 16 位指令关中断——见
[10.3](10.3-中断例程.md) 的实测。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "缓冲区能提速" | 提速的是**并发**。缓冲区的真实作用是**不丢数据**（F1 的 DR 只有 1 字节） |
| "64 的缓冲能装 64 个" | 实测**只能装 63 个**（要留一格区分满/空） |
| "`% SIZE` 就行" | 实测：2 的幂用 `&(SIZE-1)` 是 11 条指令；非 2 的幂即使常量也要 19 条（乘法逆元） |
| "环形缓冲要关中断" | **单写者时不需要**。这是设计优势，别浪费 |
| "`volatile` 就够了" | 只在单写者时够。`volatile` **不保证原子**（[ch01](../README.md)） |
| "缓冲区越大越好" | 大了浪费 RAM（20 KB 总量）；按"最坏突发长度"定，通常 64–256 |

## 代码自测

<details>
<summary>Q1：环形缓冲区为什么单写者就不需要关中断？</summary>

因为**每个变量只有一个写者**，"读-改-写"的原子性问题就不存在了。

看 `rb_put`：

```c
int rb_put(ringbuf_t *rb, uint8_t c){
    uint32_t next = (rb->head + 1u) & (RB_SIZE - 1u);
    if (next == rb->tail) return -1;
    rb->buf[rb->head] = c;
    rb->head = next;            /* ← head 的唯一写者（ISR） */
    return 0;
}
```

**危险的组合只有这一种：两个执行流都写同一个变量。**

```
ISR   ：读 head(5) → +1 → 写 6
主循环：读 head(5) → +1 → 写 6      ← 丢了一次入队
```

这就是 ch04 讲的"读-改-写不原子"。但只要 `head` 只有 ISR 写，
这个问题根本不会出现——**没有第二个写者**。

**ISR 读 `tail` 安全吗？**

安全。`tail` 只被主循环写，ISR 只是**读**它。
最坏情况是：ISR 读到的 `tail` 比实际值旧一点点，
导致判满时**多判了一次**（缓冲看起来比实际满一点）。

后果是什么？**少装一个字节**，不是数据错乱。这是可接受的降级，
比"关中断"的代价（放弃实时性）小得多。

**什么时候必须关中断**：

| 场景 | 为什么 |
|---|---|
| 主循环也要写 `head`（比如"丢弃一个字节"） | 出现双写者 |
| **多个 ISR** 写同一个缓冲 | 两个 ISR 之间也可能互相打断（优先级不同） |
| 缓冲元素不是单字节 | `head` 和 `buf` 的更新不是一步完成，会撕裂 |

这时候用临界区（实测 8 条指令）：

```c
uint32_t m;
__asm__ volatile ("mrs %0, primask" : "=r"(m));
__asm__ volatile ("cpsid i");
/* 读-改-写共享状态 */
__asm__ volatile ("msr primask, %0" :: "r"(m));   /* 恢复原值，不是无条件开中断 */
```

**设计上的建议**：能用单写者就别用锁。
ISR 只动 `head`、主循环只动 `tail` 这个约定**几乎零成本**
（实测 `rb_put` 栈用量 0、11 条指令），
而临界区会让每次入队都短暂屏蔽所有中断。
</details>

<details>
<summary>Q2：缓冲区该开多大？</summary>

按**最坏突发长度**定，不是"越大越好"。

**算一遍**（115200 bps 接收）：

```
字节间隔 = 86.8 µs
如果主循环最长 5 ms 不取数据 → 突发长度 = 5000 / 86.8 ≈ 58 字节
```

所以 **64** 就够了；留余量选 **128**。

**选多大的判据**：

| 因素 | 影响 |
|---|---|
| **主循环最长多久不取** | 决定下限。这是唯一的硬约束 |
| 波特率 | 越高，同样时间内的字节越多 |
| RAM 总量 | NUCLEO-F103RB 只有 **20 KB**。开 4 KB 的缓冲是奢侈的 |
| 协议帧长 | 至少能装下一整帧，否则解析会很痛苦 |

**典型值**：

| 场景 | 大小 |
|---|---|
| 调试日志（低频） | 64 |
| 115200 命令交互 | 128 |
| 921600 数据流 | 256 + DMA |
| 完整协议帧（如 Modbus RTU 256 B） | 256 或 512 |

⚠ **别忘了容量是 `SIZE - 1`**（实测 64 → 63）。
如果你的协议帧正好 64 字节，开 64 会**装不下一帧**——开 128。

**溢出策略也要想清楚**：

```c
if (rb_put(&rb, c) != 0) {        /* 满了 */
    /* 三种选择：
       ① 丢弃新字节（最简单，适合日志）
       ② 丢弃最老的（覆盖 tail，适合"只看最新值"的采样）
       ③ 记一个 overflow 计数器（**一定要有**，否则你不知道丢过） */
    g_rx_overflow++;
}
```

**第 ③ 条是必须的**：环形缓冲满了会**静默丢数据**，
如果不计数，表现出来就是"偶尔少一个字节"的诡异 bug。
一个 `volatile uint32_t g_rx_overflow;` 就能把静默失败变成可观测的。
</details>

<details>
<summary>Q3：实测里 `% 60` 没有调用 `__aeabi_uidiv`，是不是说取模也没关系？</summary>

**不是。** 要看清实测的两个层次：

```
$ llvm-nm -u rb_os.o
（空）
```

这个"空"是因为 **`% 60` 的除数 60 是编译期常量**，
clang 把它优化成了**乘法逆元**（魔法数 `0x88888889`）：

```
      46: f648 0389  movw r3, #0x8889
      4e: f6c8 0388  movt r3, #0x8888
      52: fbac 3203  umull r3, r2, r12, r3    ← 乘法
      56: 0953       lsrs r3, r2, #0x5
      58: 011b       lsls r3, r3, #0x4
      5a: eba3 1252  sub.w r2, r3, r2, lsr #5
      60: ebac 0282  sub.w r2, r12, r2, lsl #2  ← 减回去得到余数
```

**指令数对比（实测）**：

| 写法 | 指令数 |
|---|---|
| `& (SIZE-1)`（2 的幂） | **11** |
| `% 60`（常量除数） | **19** |
| `% n`（**运行时变量**） | 一条 `udiv`（M3）；M0 上是 `bl __aeabi_uidiv` |

所以：

1. **2 的幂永远最优**：一条 `and`，11 条指令；
2. 常量取模"能跑但更贵"：多 8 条指令；
3. **运行时取模最贵**：`udiv` 指令，M0 上还会拉进软件除法库
   （[ch09 9.5 实测](../09-uart-serial/9.5-串口HelloWorld.md)：
   M3 有 `udiv`，M0 是 `U __aeabi_uidiv` + `bl`）。

**而且 ISR 里这 8 条指令的差别不是小事**：
115200 下的 ISR 预算是 **8.7 µs/字节**。
72 MHz 下 8 条指令约 0.11 µs——占比不大，
但 921600 下预算只有 1.1 µs，这 8 条就开始咬人了。

**规则**：

```c
#define RB_SIZE 64u        /* 2 的幂，写死 */
uint32_t next = (head + 1u) & (RB_SIZE - 1u);
```

三个好处：
- 一条 `and` 搞定；
- 不依赖编译器的常量优化技巧；
- 大小是宏常量，**可以在编译期断言**：

```c
_Static_assert((RB_SIZE & (RB_SIZE - 1u)) == 0u, "RB_SIZE 必须是 2 的幂");
```

这条断言能防止后人把 `RB_SIZE` 改成 100 然后悄悄变慢
（[ch08 8.12](../08-complex-types/8.12-结构体与嵌入式编程.md) 的同一套思路）。
</details>
