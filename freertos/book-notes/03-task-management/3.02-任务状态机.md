## 这一篇讲什么

任意时刻，一个任务**必然且仅**处于四个状态之一。
状态机是理解所有 RTOS 行为的总纲：调度器做的事本质就是
"在 Ready 集合里挑一个变 Running"。

## 四态与转移

```
                    vTaskSuspend()
        ┌───────────────────────────────────┐
        ▼                                   │
   ┌──────────┐   vTaskResume()    ┌────────┴─────┐
   │Suspended │ ─────────────────► │    Ready     │
   └──────────┘                    └──▲───────┬───┘
        ▲                             │       │ 调度器选中
        │                             │       ▼ （抢占/时间片到）
        │                      解除阻塞 │   ┌─────────┐
        │                             └───┤ Running │
        │ 阻塞式 API：                    │  (在 CPU  │
        │ vTaskDelay /                    │   上执行) │
        │ xQueueReceive(超时)…            └────┬────┘
        │                                    │ 调阻塞式 API
   ┌────┴──────┐                             │
   │  Blocked  │ ◄───────────────────────────┘
   └───────────┘
```

| 状态 | 含义 | 调度器看它吗 |
|---|---|---|
| **Running** | 正在 CPU 上执行（单核任意时刻只有一个） | — |
| **Ready** | 能跑但没轮上（有同/高优先级在跑） | ✅ 选人池 |
| **Blocked** | 在等一个**事件**：延时到期 / 队列有数据 / 信号量被给…… | ❌（事件到了自动回 Ready） |
| **Suspended** | 被 `vTaskSuspend` 显式挂起 | ❌（只有 `vTaskResume` 能救） |

## Blocked vs Suspended：最容易混的一对

| | Blocked | Suspended |
|---|---|---|
| 进的方式 | 任务**自己**调阻塞式 API | 任意任务（包括自己）调 `vTaskSuspend` |
| 出的方式 | **事件**（时间到/数据到）+ 可带超时 | **只能**别的任务调 `vTaskResume` |
| 带超时吗 | 可以（xTicksToWait） | 无超时概念 |
| 典型用途 | 等延时、等队列、等信号量 | 调试期冻结任务、休眠一个完整功能模块 |

一句话：**Blocked 是"等条件"，Suspended 是"被按住"。**

## 关键推论：阻塞是有代价承诺的

任务调 `vTaskDelay(100)` 进 Blocked 时，内核把它从 Ready 名单摘下来，
挂到"延时名单"并记好唤醒 tick——**这期间它对调度器完全隐形，
一个指令都不执行，CPU 占有率是零。**

对照裸机 [19.04](../../../stm32/book-notes/19-systick-and-timer/19.04-三种等待的对比.md)
的三种等待：忙等（while 数循环）是"占着 CPU 等"，
`vTaskDelay` 是"让出 CPU 等"。**这就是 RTOS 让超级循环里
"等传感器 50ms"不再拖垮全局的机制。**

## 与 LDD- 侧对照

| FreeRTOS | Linux 任务状态 |
|---|---|
| Running | TASK_RUNNING（且在 CPU 上） |
| Ready | TASK_RUNNING（在运行队列里） |
| Blocked | TASK_INTERRUPTIBLE / TASK_UNINTERRUPTIBLE（睡眠等事件） |
| Suspended | TASK_STOPPED（SIGSTOP） |

概念几乎一一对应——**RTOS 没有发明新的状态机，只是把 Linux 那套
"睡眠等事件"的思想裁到单片机上**。学两遍记两遍。

## 要点回顾

1. 四态：Running / Ready / Blocked / Suspended；调度器只从 Ready 里挑人。
2. Blocked 等事件可超时；Suspended 只能被别人 resume。
3. 阻塞 = 让出 CPU 的等待，这是 RTOS 解决"等待拖垮全局"的核心机制。

<details>
<summary>Q1：Blocked 的任务超时和事件同时发生怎么办？</summary>

以 API 的返回值区分：`xQueueReceive` 返回 `pdTRUE`（收到了）还是
`pdFALSE`（超时了）。**调用者必须检查返回值**，
不检查就把"超时"当"收到"处理，是队列编程的头号 bug 来源。

</details>

<details>
<summary>Q2：Suspended 的任务被 vTaskDelete 删了，能删吗？</summary>

能。删除不看状态——Suspended 的任务照样删，TCB+栈回收。
反过来不行：**Blocked 的任务没法被"提前唤醒"**
（没有 vTaskWake 这种 API），要么等事件、要么等超时、要么删了它。

</details>
