## 这一篇讲什么

PC 上 `malloc/free` 是日常；裸机篇 [ch13](../../../stm32/book-notes/13-dynamic-memory/README.md)
也见过 `_sbrk` 怎么从链接脚本给的堆里切内存。那为什么 FreeRTOS 要自带分配器，
还一口气给了五个？因为 **malloc 在嵌入式实时语境下有四个硬伤**。

## malloc 的四宗罪

| # | 毛病 | 后果 |
|---|---|---|
| 1 | **不确定耗时** | glibc 的 malloc 要遍历空闲链表、可能合并/分裂块，耗时随堆状态变化——实时系统里"这次调用花多久"必须是已知数 |
| 2 | **碎片化** | 长期分配/释放不同大小的块，堆被切成筛子：总空闲很多、单块都不够，分配开始莫名失败 |
| 3 | **不可重入 / 线程不安全的代价** | newlib 的 malloc 靠锁保证多任务安全，ISR 里调 = 未定义行为 |
| 4 | **失败难察觉** | 返回 NULL 没人检查 → 解引用 → HardFault，现场离事故原点十万八千里 |

## FreeRTOS 的回答：内核不碰你的 malloc

FreeRTOS 内核分配 TCB、栈、队列时**不调用 C 库 malloc**，
而是调用自己的 `pvPortMalloc()`——这个函数由你选编的 `heap_x.c` 提供：

```
xTaskCreate()
   → pvPortMalloc(TCB) + pvPortMalloc(栈)     ← 走 heap_x.c，不走 _sbrk
```

于是四个毛病被逐个拆解：

- **耗时确定**：heap_4 用首次适配 + 相邻块合并，行为简单可分析（不是 O(1)，但可上界）；
- **碎片可控**：选合适的 heap_x（下一篇），或者干脆禁释放（heap_1）；
- **重入安全**：`pvPortMalloc` 内部挂起调度器做临界保护，任务侧随便调；
  （ISR 侧规矩不变：内存分配本来就不是 ISR 该干的活）
- **失败显式**：返回 NULL + 可配 `malloc failed hook`，在钩子函数里 `configASSERT(0)` 当场抓住。

## 与裸机篇 ch13 的对照

| | 裸机（ch13） | FreeRTOS（本章） |
|---|---|---|
| 分配器 | newlib malloc + `_sbrk` | `pvPortMalloc` + heap_x.c |
| 堆从哪来 | 链接脚本 `_end` ~ 栈底之间 | `configTOTAL_HEAP_SIZE` 定死的静态数组 `ucHeap[]` |
| 栈/堆碰撞检查 | 靠自己量 | heap 是编译期定长数组，**物理上不可能撞任务栈** |
| 释放 | free（碎片风险） | 看选哪个 heap_x（下篇） |

注意第三行那个区别：裸机的堆和栈是**同一片 RAM 两头长**，
堆长过头就踩栈；FreeRTOS 的 `ucHeap` 是一个**定长静态数组**，
链接时大小就定死——堆永远长不出数组边界。这是结构性的安全提升。

## 要点回顾

1. malloc 四宗罪：耗时不定、碎片、重入代价、失败难察。
2. FreeRTOS 内核全走 `pvPortMalloc`，由 heap_x.c 提供，与 C 库 malloc 完全脱钩。
3. `ucHeap` 是定长静态数组，堆撞栈这个裸机老大难在结构上消失。

<details>
<summary>Q1：那应用程序里还能用 malloc 吗？</summary>

能，但不推荐混用。混用的坑：malloc 从 `_sbrk` 的区域拿内存，
而链接脚本给不给它留地方、留多少，是你自己的责任；
FreeRTOS 的 ucHeap 又是另一块。两片"堆"都要预算，总量很容易超 RAM。
**规矩：进了 RTOS 的世界，一律 `pvPortMalloc/vPortFree`，让 malloc 失业。**

</details>
