# 5.4 workqueue：Zephyr 的"下半部"，k_work / k_work_delayable

## 这一篇讲什么

workqueue 是 Zephyr 里最像 Linux 内核的概念——
**ISR 里不干活，把活打包成 work item 扔到队列里，
一个专门的线程（workqueue thread）来消费。**
FreeRTOS 里没有内核级对应物，要自己搭"守护任务 + 命令队列"。

## 问题：ISR 里不能干活

裸机篇 [ch10 中断](../../../01-stm32/book-notes/10-interrupts/README.md)
和 LDD- 侧 softirq/tasklet/workqueue 笔记都讲过这个模式：

```
ISR（硬件上下文）：只干最紧急的事（读寄存器、清标志），越快越好
  ↓ 打包 work item
workqueue 线程（线程上下文）：干活（解析、存储、通知），可以阻塞
```

FreeRTOS 的做法是 ISR 里 `xQueueSendFromISR` + 一个专门的任务收队列
——**能用，但每个中断源都要自己搭这套**。
Zephyr 把它做成了内核基础设施：**系统自带一个 workqueue 线程，
你只管 submit work。**

## k_work：一次性工作项

```c
/* 定义 work item + 处理函数 */
void my_work_handler( struct k_work *work );

K_WORK_DEFINE( my_work, my_work_handler );

/* ISR 里：提交，立即返回 */
void USART1_IRQHandler( const struct device *dev, void *user_data )
{
    /* 读寄存器，清中断标志——最紧急的事 */
    k_work_submit( &my_work );   /* 打包扔给 workqueue 线程，立即返回 */
}

/* workqueue 线程里自动调用 */
void my_work_handler( struct k_work *work )
{
    /* 干活：解析数据、写 flash、发通知——可以阻塞 */
}
```

- `K_WORK_DEFINE`：静态定义 work item，编译时确定
- `k_work_submit`：从 ISR 或任何线程提交，**立即返回**
- 处理函数在 **system workqueue 线程**上下文执行——可以调任何内核 API，可以阻塞

## k_work_delayable：可延迟/可周期的工作项

```c
void periodic_handler( struct k_work *work );

K_WORK_DELAYABLE_DEFINE( my_dwork, periodic_handler );

/* 延迟 100ms 后执行一次 */
k_work_schedule( &my_dwork, K_MSEC(100) );

/* 周期性：处理函数里重新调度自己 */
void periodic_handler( struct k_work *work )
{
    do_periodic_work();
    k_work_schedule( &my_dwork, K_MSEC(10) );  /* 10ms 后再来 */
}
```

**对应 FreeRTOS 软件定时器**（[ch05 软件定时器](../../../02-freertos/book-notes/05-software-timers/README.md)）：
`k_work_schedule` ≈ `xTimerStart`，处理函数 ≈ 定时器回调。

| | FreeRTOS 软件定时器 | Zephyr k_work_delayable |
|---|---|---|
| 执行上下文 | 守护任务（一个全局任务） | system workqueue 线程（一个全局线程） |
| 启动 | `xTimerStart` | `k_work_schedule` / `k_work_reschedule` |
| 取消 | `xTimerStop` | `k_work_cancel_delayable` |
| 周期模式 | `xTimerChangePeriod` 自动重载 | 处理函数里手动重新调度 |
| 回调里能阻塞？ | **不能**（会拖住所有定时器） | **不能**（会拖住所有 work） |

**两边同一个坑**：回调/处理函数不能长时间阻塞——
它跑在共享线程里，卡了它等于卡了所有使用这个 workqueue 的人。

## system workqueue vs 自定义 workqueue

Zephyr 系统自带一个 **system workqueue**（内核线程，优先级可配）。
所有 `k_work_submit` 默认都进这个队列。
如果处理函数要干**重活**（解析大数据、写 flash），
会拖住 system workqueue 里其他轻活——此时建自己的 workqueue：

```c
/* 自定义 workqueue：独立线程，独立优先级 */
K_THREAD_STACK_DEFINE( my_wq_stack, 2048 );
struct k_work_q my_wq;

k_work_queue_init( &my_wq );
k_work_queue_start( &my_wq, my_wq_stack,
                    K_THREAD_STACK_SIZEOF( my_wq_stack ),
                    5,              /* 优先级 */
                    NULL );

/* 提交到自定义 workqueue 而不是系统的 */
k_work_submit_to_queue( &my_wq, &my_work );
k_work_schedule_for_queue( &my_wq, &my_dwork, K_MSEC(100) );
```

| | system workqueue | 自定义 workqueue |
|---|---|---|
| 存在 | 内核自带 | 自己建 |
| 优先级 | Kconfig 配 | 启动时指定 |
| 适合 | 轻活（几微秒~几毫秒） | 重活（几十毫秒以上） |
| 风险 | 重活拖住全系统 | 多吃一个线程的栈 |

## 与 FreeRTOS 的完整对照

| 场景 | FreeRTOS | Zephyr |
|---|---|---|
| ISR 交活 | `xQueueSendFromISR` + 自建处理任务 | `k_work_submit`（内核自带） |
| 延迟执行 | 软件定时器 `xTimerStart` | `k_work_schedule` |
| 周期执行 | 软件定时器自动重载 | 处理函数里重新 `k_work_schedule` |
| 取消 | `xTimerStop` | `k_work_cancel_delayable` |
| 重活隔离 | 自建高优先级任务 + 队列 | 自定义 workqueue |

**Zephyr 把 FreeRTOS 里"每个项目自己搭一遍"的模式变成了内核标配。**

## 与 LDD- 侧对照

| Zephyr | Linux 内核 | 说明 |
|---|---|---|
| `k_work` + `k_work_submit` | `struct work_struct` + `schedule_work()` | 一次性工作项 |
| `k_work_delayable` | `struct delayed_work` + `schedule_delayed_work()` | 可延迟工作项 |
| system workqueue | `system_wq`（内核全局 workqueue） | 默认队列 |
| 自定义 workqueue | `alloc_workqueue()` | 独立线程池 |
| 处理函数可阻塞 | workqueue 处理函数可睡眠 | 都是线程上下文 |

**Linux 内核的 workqueue 就是 Zephyr workqueue 的原型**——
API 形状不同，设计思想完全一致。

## 要点回顾

1. `k_work` + `k_work_submit`：ISR 里打包，workqueue 线程里干活——内核级下半部。
2. `k_work_delayable`：可延迟/可周期，对应 FreeRTOS 软件定时器。
3. system workqueue 管轻活，重活建自定义 workqueue 隔离。
4. 处理函数不能长时间阻塞——共享线程，卡了拖一片。
5. 与 Linux 内核 workqueue 同源：`schedule_work()` ↔ `k_work_submit()`。

<details>
<summary>Q1：k_work_submit 重复提交同一个 work item 会怎样？</summary>

如果 work item 还在队列里没被执行，重复 submit **不会重复排队**——
它只执行一次。如果需要"处理完再来一次"，在 handler 里重新 submit。
`k_work_busy_get()` 可以查 work item 当前状态（idle/queued/running）。
这与 Linux 内核 `queue_work` 的行为一致：同一个 work 不会并发执行。

</details>

<details>
<summary>Q2：k_work_delayable 和 k_timer 有什么区别？</summary>

`k_timer` 的回调在 **ISR 上下文**执行（SysTick ISR 里），
不能阻塞、不能调大部分内核 API——只能做极简操作。
`k_work_delayable` 的 handler 在 **线程上下文**（workqueue），
可以阻塞、可以调任何 API。
**选择规则**：回调只是置个标志位用 k_timer；
要干活（哪怕只是打印）用 k_work_delayable。

</details>
