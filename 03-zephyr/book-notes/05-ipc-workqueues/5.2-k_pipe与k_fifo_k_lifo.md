## 这一篇讲什么

k_msgq 传"固定大小消息"，但真实数据不总是齐整的。
UART 收的是**变长字节流**（用 k_pipe），
DMA 缓冲区传的是**指针不是数据**（用 k_fifo/k_lifo）。
Zephyr 按语义拆出三种对象，各管一段。

## k_pipe：字节流管道

```c
K_PIPE_DEFINE( my_pipe, 256, 4 );   /* 容量 256 字节，对齐 4 */

/* 写：可能只写进去一部分 */
size_t written;
k_pipe_put( &my_pipe, tx_buf, 128, &written, 64, K_MSEC(100) );
/*          管道     数据源   想写字节数  实际写了  最少写多少才返回  超时 */

/* 读：同理 */
size_t read_bytes;
k_pipe_get( &my_pipe, rx_buf, 128, &read_bytes, 1, K_FOREVER );
```

与 k_msgq 的关键区别：

| | k_msgq | k_pipe |
|---|---|---|
| 数据单位 | 固定大小消息 | 字节 |
| 一次操作 | 一整条消息（全成或全败） | 可以部分读写 |
| 语义 | "我给你一帧" | "我给你一段流" |
| 典型场景 | 传感器采样帧、命令包 | UART 字节流、日志流 |

`min_xfer` 参数（上面写 64 / 读 1）是"最少传输量"——
管道里凑不够这个数就继续等。写侧设 64 = "要么写够 64 字节要么不写"，
防止碎片化写入。

**FreeRTOS 没有直接对应**。FreeRTOS 的 queue 是消息粒度的，
字节流要么自己封装（每条消息 = 一字节，浪费），要么用
`xStreamBuffer`（FreeRTOS 的 stream buffer，和 k_pipe 语义最接近）。

## k_fifo / k_lifo：传指针，不拷数据

```c
struct my_node {
    sys_snode_t node;       /* 必须放在结构体第一个成员！ */
    uint32_t    data;
    float       value;
};

K_FIFO_DEFINE( my_fifo );

/* 发送方：把节点挂进链表 */
struct my_node *n = alloc_node();
n->data = 42;
k_fifo_put( &my_fifo, n );

/* 接收方：取出节点 */
struct my_node *got = k_fifo_get( &my_fifo, K_FOREVER );
```

**核心区别：不拷贝数据，只传指针（链表节点）。**

| | k_msgq / k_pipe | k_fifo / k_lifo |
|---|---|---|
| 传递内容 | 数据本体（memcpy） | 指针（链表节点地址） |
| 内存开销 | 队列内部存数据 | 队列只存 next 指针 |
| 拷贝次数 | 进一次 + 出一次 | 零拷贝 |
| 所有权 | 随拷贝转移 | 随指针转移——谁拿到节点谁负责 |
| 大小限制 | 单项大小固定 | 节点可以任意大 |

k_lifo 和 k_fifo 用法一样，只是**后进先出**——
FreeRTOS 里没有 lifo（queue 的 SendToFront 插队是特例不是常态）。

## sys_snode_t：侵入式链表的规矩

节点结构体的**第一个成员必须是 `sys_snode_t node`**：

```c
struct my_node {
    sys_snode_t node;   /* ← 必须是第一个！Zephyr 内核强转回结构体用 */
    /* 你的数据... */
};
```

Zephyr 内核操作的是 `sys_snode_t` 单链表节点。取出时内核返回
`sys_snode_t *`，你用 `CONTAINER_OF` 宏转回自己的结构体：

```c
sys_snode_t *snode = k_fifo_get( &my_fifo, K_FOREVER );
struct my_node *n = CONTAINER_OF( snode, struct my_node, node );
```

**这就是 LDD- 侧 `list_head` 的同款设计**——Linux 内核的侵入式链表
（`struct list_head` 嵌在宿主结构体里，`container_of` 反查）。
Zephyr 的 `sys_snode_t` + `CONTAINER_OF` 是完全相同的思想，
见 LDD- 侧内核链表笔记。

## 传指针的所有权问题

k_fifo 传指针 = 所有权问题回来了。
[02-freertos/book-notes 4.4](../../../02-freertos/book-notes/04-queue-management/4.4-传指针的代价与规矩.md)
里的三条铁律原样适用：

1. 节点必须是长寿命存储（堆/静态/内存池）
2. 发送后发送方不能再碰
3. 释放责任写死在设计里

Zephyr 提供了配套的 `k_mem_slab`（固定大小内存池）专门给
k_fifo 节点用——分配/回收都是 O(1)，无碎片：

```c
K_MEM_SLAB_DEFINE( node_pool, sizeof(struct my_node), 16, 4 );

struct my_node *n;
k_mem_slab_alloc( &node_pool, (void **)&n, K_FOREVER );
/* ...填数据，k_fifo_put... */
/* 接收方用完：k_mem_slab_free( &node_pool, (void **)&n ); */
```

## 选型速查

| 场景 | 选什么 | 理由 |
|---|---|---|
| 传感器帧、命令包（固定大小） | `k_msgq` | 消息语义清晰，值拷贝免同步 |
| UART 字节流、日志流 | `k_pipe` | 字节粒度，支持部分读写 |
| DMA 缓冲区、大块数据 | `k_fifo` + `k_mem_slab` | 零拷贝，O(1) 分配回收 |
| 后进先出（栈语义） | `k_lifo` | 特殊场景（undo 栈等） |

## 要点回顾

1. `k_pipe` = 字节流，支持部分读写，FreeRTOS 侧最接近的是 stream buffer。
2. `k_fifo`/`k_lifo` = 传指针（侵入式链表），零拷贝，节点必须 `sys_snode_t` 打头。
3. `CONTAINER_OF` 反查宿主结构体——与 Linux `list_head` + `container_of` 同设计。
4. 传指针的所有权问题用 `k_mem_slab` 内存池解决，O(1) 无碎片。

<details>
<summary>Q1：k_pipe 的 min_xfer 设多少合适？</summary>

写侧设大 = 攒够一批再写（减少拷贝次数，但延迟高）；
设小 = 有空间就写（延迟低，但可能碎片化）。
读侧设 1 = 有数据就返回（实时流）；
设 N = 攒够一帧再处理（解析固定协议头时用）。
UART 场景通常写 min=1 读 min=1，日志场景写 min=64 减少打断。

</details>

<details>
<summary>Q2：k_fifo 能在 ISR 里用吗？</summary>

`k_fifo_put` 可以——它不阻塞（只挂链表），ISR 安全。
`k_fifo_get` 也可以，传 `K_NO_WAIT`。
比 k_msgq 更适合 ISR 场景：不用拷贝数据，只挂一个指针，极快。
DMA 完成中断里 `k_fifo_put` 交出缓冲区是 Zephyr 驱动的标准模式。

</details>
