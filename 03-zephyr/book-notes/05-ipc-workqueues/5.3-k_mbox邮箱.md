## 这一篇讲什么

k_mbox（mailbox）是 Zephyr 里**最重的 IPC 对象**：
消息可以带优先级、可以异步发送（不等人收）、
接收方可以按发送者线程过滤。
功能强，但 API 复杂度高——本篇讲清"什么时候值得用它"。

## 与 k_msgq 的核心差异

```c
/* k_msgq：FIFO，谁先到谁先被收 */
k_msgq_put( &q, &msg, K_FOREVER );

/* k_mbox：可以指定优先级，紧急消息插队 */
struct k_mbox_msg msg = {
    .info = 0,
    .size = sizeof( my_data ),
    .tx_data = &my_data,
    .tx_target_thread = K_ANY,      /* 谁都能收 */
    .priority = 0,                   /* 数值小 = 优先级高 */
};
k_mbox_put( &my_mbox, &msg, K_FOREVER );
```

| 维度 | k_msgq | k_mbox |
|---|---|---|
| 排序 | 严格 FIFO | 可按 priority 排序 |
| 发送方式 | 同步（放完就走） | 可同步可异步 |
| 接收过滤 | 无 | 可按发送者线程过滤 |
| 消息大小 | 固定 | 可变（带 size 字段） |
| 复杂度 | 低 | 高 |
| FreeRTOS 对应 | queue | **无直接对应** |

## 异步发送：发完不等接收

k_mbox 支持**异步发送**——发送方把消息挂进邮箱就走，
接收方什么时候来取都行：

```c
/* 同步：等接收方取走才返回 */
k_mbox_put( &mbox, &msg, K_FOREVER );

/* 异步：挂进去就返回，信号量通知完成 */
K_SEM_DEFINE( send_done, 0, 1 );
msg.tx_block = ( struct k_mem_block ){ 0 };  /* 不用内存池 */
k_mbox_async_put( &mbox, &msg, &send_done );
/* 发送方继续干别的 */
/* 稍后或回调里：k_sem_take( &send_done, K_FOREVER ) 确认已取走 */
```

异步的价值：**高优先级任务不被低优先级接收方拖住**。
FreeRTOS 的队列天然就是这个语义（`xQueueSend` 不等人收），
所以 k_mbox 的异步模式反而更像 FreeRTOS queue——
只是多了优先级排序和过滤。

## 接收过滤：只听特定发送者

```c
/* 只收来自 sensor_thread 的消息 */
struct k_mbox_msg rx_msg;
char rx_buf[64];
k_mbox_get( &my_mbox, &rx_msg, rx_buf, K_FOREVER );
/* rx_msg.info 里有发送者线程 ID、消息大小等元数据 */
```

`tx_target_thread` 字段让发送方指定"只有某个线程能收"，
接收方也可以通过 `rx_source_thread` 过滤"只听某个线程"。
k_msgq 完全没有这个能力——谁 put 谁 get，匿名。

## 什么时候用 k_mbox

**说实话：大多数场景不用。** Zephyr 官方文档自己也说
k_mbox 是"legacy"对象，新代码建议用 k_msgq + 应用层协议。

| 场景 | 建议 |
|---|---|
| 简单 FIFO 消息 | `k_msgq`（5.1） |
| 字节流 | `k_pipe`（5.2） |
| 传指针零拷贝 | `k_fifo`（5.2） |
| 需要消息优先级排序 | `k_mbox`（但先考虑能不能用多个 k_msgq 分级代替） |
| 需要异步发送 | `k_mbox`（或 zbus，见 [ch11](../11-zbus/README.md)） |

**实践建议**：先用 k_msgq，真碰到"紧急消息要插队"再升级 k_mbox。
提前上 k_mbox = 白白增加复杂度。

## 与 FreeRTOS 对照

FreeRTOS **没有 k_mbox 的对应物**。最接近的"优先级消息"做法是：

- 建两个队列（高优/低优），消费端先查高优队列——**应用层分级**
- 或者用 `xQueueSendToFront` 插队（特例不是常态）

Zephyr 的 k_mbox 把这个需求做成了内核对象——功能更强，
但和 Zephyr 其他 IPC 的风格不一致（独有 async、独有 priority、
独有过滤），学习成本高。

## 要点回顾

1. k_mbox = 带优先级 + 异步 + 过滤的"重"邮箱。
2. 大多数场景 k_msgq 够用；k_mbox 是"确认需要优先级排序"时才升级。
3. 异步发送 = 高优先级任务不被接收方拖住，类似 FreeRTOS queue 的默认语义。
4. Zephyr 官方视 k_mbox 为 legacy——新代码优先 k_msgq/zbus。

<details>
<summary>Q1：k_mbox 的 priority 和线程优先级是一回事吗？</summary>

不是。k_mbox 的 `priority` 是**消息**的排序权重（数值小 = 先被取），
与线程优先级（决定谁先跑）完全独立。一个低优先级线程可以发
高优先级消息，反之亦然。消息优先级影响的是"接收方先看到哪条"，
不影响"发送方什么时候跑"。

</details>

<details>
<summary>Q2：k_mbox 和 zbus 都支持异步，选哪个？</summary>

zbus（[ch11](../11-zbus/README.md)）是发布-订阅模式，
天然异步，支持多订阅者——"一个消息多方接收"用 zbus。
k_mbox 是点对点（一个发送一个接收），异步只是可选项。
**新设计用 zbus**，k_mbox 只在维护老代码或确实需要优先级排序时用。

</details>

## 衔接

至此 Zephyr 的"传数据" IPC 讲完了（msgq/pipe/fifo/mbox）。
但有一类需求不是"传数据"而是**"交活"**——ISR 里来了中断，
不能在 ISR 里干活（会拖住中断系统），要把活交给线程上下文做。
FreeRTOS 里这靠 `xQueueSendFromISR` + 专门的处理任务；
Zephyr 给了一个更优雅的方案：workqueue。
下一篇 [5.4 workqueue](5.4-workqueue.md)。
