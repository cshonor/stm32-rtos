## 这一篇讲什么

工具箱里又添一员，选错的代价反而更大了。
这一篇把 ZBus 和 ch05 的队列家族、以及事件（k_event / FreeRTOS 事件组）
摆在一张表上，回答三个问题：**什么规模上 ZBus、什么时候坚持用 msgq、
什么时候连 IPC 都不要**。

## 一张总表

| 需求 | k_msgq | k_event / 事件组 | ZBus | 直接函数调用 |
|---|---|---|---|---|
| 拓扑 | 一对一 | 一对多（仅标志位） | 一对多（带类型化数据） | 同模块内部 |
| 负载 | 固定大小消息 | 32 个位，无数据 | 任意类型（按值） | 任意 |
| 接收上下文 | 接收线程 | 接收线程 | listener 借发布者 / subscriber 自己的 | 调用者 |
| 运行时可插拔消费者 | 否 | 部分 | **是**（add/rm_obs） | 否 |
| RAM 开销 | 一条队列 | 极小 | 通道存储 + 每 subscriber 一条队列 | 零 |
| 理解成本 | 低 | 低 | 中（VDED 时序） | 零 |

## 按规模选型

| 系统形态 | 建议 |
|---|---|
| 2 个模块、单向数据流 | k_msgq，别上总线 |
| "事件发生了"类信号（按键、报警位） | k_event——负载本来就只是个位 |
| 1 份数据 ≥3 个消费者，或消费者会增减 | **ZBus** |
| 跨子系统的松耦合（传感器 → UI/日志/上云） | **ZBus**（生产方不需要知道谁在听） |
| 同一编译单元内的协作 | 直接函数调用，IPC 是浪费 |

一句话：**ZBus 的入场券是"消费者数量 × 变化频率"足够大**。
本仓库基础四实验（[01-hello](../../01-hello/README.md) 起）全是 2 模块规模，
所以本章至今无实验——这是刻意为之，不是遗漏。

## 传感器分发：ZBus 的主场

官方文档钦点的典型场景——一个 IMU 数据源多头消费：

```
                    ┌── listener: 过零检测（轻，借发布线程跑）
imu_thread ──pub──→ imu_chan ──┼── subscriber: ui_thread（10Hz 刷新）
                    │          ├── subscriber: logger_thread（全量记录）
                    │          └── subscriber: uplink_thread（打包上报）
                    └── zbus_chan_read: shell 命令随时读现值
```

这套拓扑用 msgq 写要维护 3 条队列 + 发布者 3 个 put 失败分支；
用 ZBus 发布者只有一行 `zbus_chan_pub`，新增消费者不动发布者。

## 什么时候 ZBus 反而是错的

| 反例 | 为什么 |
|---|---|
| 逐字节流（UART 透传、音频） | 该用 k_pipe（[5.2](../05-ipc-workqueues/5.2-k_pipe与k_fifo_k_lifo.md)）；通道按值拷贝，流式数据放进来又贵又没语义 |
| 大缓冲（图像帧、网络包） | 按值拷贝顶不住；用 net_buf / 指针传递，ZBus 只发"帧就绪"门铃 |
| 严格一对一、要背压卡发布者 | msgq 的"队列满则 put 阻塞"正是你要的；ZBus 的背压隔离反而丢了背压 |
| 只有标志没有数据 | k_event 一个结构体搞定，不需要消息类型和队列 |

## 与 FreeRTOS 生态的对照账

FreeRTOS 用户转 Zephyr 时容易把 ZBus 当成"更好的事件组"——**不是**：

- 事件组 ≈ Zephyr k_event：32 位信号量集合，多任务等待任意位组合；
- ZBus ≈ "内核内置的 pub-sub 框架"：FreeRTOS 里要用 coreMQTT-Agent
  或自研回调表 + 队列才能拼出同构方案。
- 选型逻辑反而一致：**先看拓扑和负载，再看谁的内置工具正好匹配**。

## 要点回顾

1. 选型看三点：拓扑（一对一/一对多）、负载（位/小消息/大块）、消费者是否动态。
2. ZBus 入场券：1 份数据 ≥3 消费者，或跨子系统松耦合；2 模块规模用 msgq。
3. 大块数据别进通道——ZBus 发门铃，数据走管道/指针。
4. ZBus 不是"更好的事件组"：k_event 管标志，ZBus 管带类型数据的广播。

<details>
<summary>Q1：listener 和 workqueue 都能"收通知干活"，怎么分？</summary>

listener 是"消息驱动的回调"，绑定在通道上、随发布发生；
workqueue 是"延迟/卸载执行器"，谁都能 submit。
常见组合正是 [11.1](11.1-通道与三种订阅者.md) 说的：
listener 里只做 `k_work_submit`，把重活卸给系统 workqueue——
一个管"收"，一个管"干"。

</details>

<details>
<summary>Q2：通道太多会不会有性能/内存问题？</summary>

每个通道 = 一份消息存储 + 一个 mutex + 观察者链表，订阅者每个再带一条队列。
几十个小通道在 F103 级 RAM 上依然可行，但**每个 subscriber 的队列深度**
才是大头（深度 × 消息大小）。设计上宁多通道少深度：
按主题切分通道，而不是一个通道塞所有消息类型。

</details>
