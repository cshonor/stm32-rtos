## 这一篇讲什么

VDED = **Virtual Distributed Event Dispatcher**（虚拟分布式事件分发器）。
它是 ZBus 对"一次发布如何送达所有观察者"给出的**时序保证**：
谁在自己的上下文执行、谁借别人的上下文执行、同一条消息各份拷贝
按什么优先级顺序被消费。理解了 VDED，才敢在实时系统里用 ZBus。

## 一次发布的完整旅程

```
发布线程调用 zbus_chan_pub()
        │
        ├─ 1. 消息按值拷贝进通道存储（mutex 保护）
        │
        ├─ 2. 依次执行所有 listener ── 就在发布线程里、同步执行
        │        （按登记优先级从高到低）
        │
        ├─ 3. 消息拷贝进每个 subscriber / msg-subscriber 的队列
        │        （不等待队列有空间消费，超时参数只管 pub 本身）
        │
        └─ 4. 返回；各 subscriber 线程被内核调度
                 优先级最高的 subscriber 最先跑（HLP 规则）
```

要点：**2 和 3 都发生在 pub 调用返回之前**——
listener 是"借发布线程的手"执行的，subscriber 只是收到了入队通知，
真正的消息处理在 subscriber 自己的线程里、之后发生。

## VDED 的三条保证

| 保证 | 内容 | 依赖 |
|---|---|---|
| 顺序性 | 同一通道的两次发布，观察者收到的顺序与发布顺序一致 | 通道内部单份存储 + 各队列 FIFO |
| 优先级序 | 同一次发布，**优先级最高的 subscriber 最先处理**（HLP，Highest Locker Priority） | Zephyr 调度器（[4.3](../04-multithreading/4.3-优先级两个世界.md)） |
| 隔离性 | 慢 subscriber 只堵自己队列，不堵发布者和其他 subscriber | 每 subscriber 独立队列 |

对照裸 msgq 广播写法：发布者挨个 `k_msgq_put`，**任一队列满都会卡住发布者**；
ZBus 把每条队列的背压隔离到各自消费者身上。

## listener 的"借上下文"风险

VDED 第 2 步意味着 listener 的执行**挂在发布线程的优先级和栈上**：

| 后果 | 说明 |
|---|---|
| 优先级传染 | 低优先级发布线程发消息，listener 也以这个低优先级跑 |
| 栈传染 | listener 用的是发布线程的栈，深回调链可能爆栈 |
| 时长传染 | listener 耗时直接加在 pub 调用上，发布者被拖慢 |

因此官方语义对 listener 的定位是"**轻量、快路径、无阻塞**"：
置标志、转发到 workqueue、唤醒 subscriber——
真正的活交给 subscriber 线程按自己的优先级去做。

## 背压：队列满了会发生什么

subscriber 队列（`ZBUS_SUBSCRIBER_DEFINE(name, queue_size)`）满时：

- **该 subscriber 丢消息**（新发布进不去），不影响其他观察者；
- listener 不受影响（同步路径无队列）；
- 可用 `zbus_obs_set_enable` / 运行时观察来动态节流。

对照设计：队列深度 = 容忍的"消费滞后拍数"。
传感器 100Hz 发布、显示线程 10Hz 消费，队列深度 1 就够——
旧帧本就该丢（拿最新值用 `zbus_chan_read` 直接读通道当前值也行）。

## "原书怎么说 / 实际是什么"

| 原书（2024 版）说法 | 实际（Zephyr 3.x 官方文档） |
|---|---|
| VDED 保证"事件按优先级分发" | 完整表述是：listener 在发布上下文按登记优先级执行；subscriber 由各线程**调度器优先级**决定先后——ZBus 自己不改线程优先级 |
| HLP 是 ZBus 实现的优先级继承 | HLP 指"最高优先级 subscriber 优先被调度消费"，靠普通抢占调度实现，不是通道持有锁的继承 |
| pub 总是立即成功 | `zbus_chan_pub` 带 timeout，拿通道 mutex 失败会超时返回错误码 |

## 要点回顾

1. VDED：pub 返回前完成"拷贝进通道 + 同步跑完 listener + 入队所有 subscriber"。
2. listener 借发布线程上下文跑——优先级/栈/时长三重传染，必须快进快出。
3. subscriber 按 Zephyr 调度优先级消费（最高优先级先跑），队列独立、背压隔离。
4. 同一通道消息顺序 = 发布顺序；丢消息只丢队列满的那一个 subscriber。

<details>
<summary>Q1：ISR 里能 zbus_chan_pub 吗？</summary>

可以（官方文档允许，传 K_NO_WAIT）。ISR 上下文执行 listener 更要命——
listener 们全在 ISR 里同步跑完。中断里发布时，listener 列表应极短或为空，
重活一律留给 subscriber 线程。

</details>

<details>
<summary>Q2：想要"拿到消息就处理，不管新不新"，该用 subscriber 还是 zbus_chan_read？</summary>

要"逐条处理不丢帧"用 subscriber（队列缓存每条发布）；
要"只关心最新值"（如 UI 刷新显示当前温度）用
`zbus_chan_read` 直接读通道现值，配合 notify 当门铃，一条队列都不用。

</details>

<details>
<summary>Q3：通道的 mutex 会不会造成优先级反转？</summary>

通道的读写锁（mutex）持锁路径极短（一次 memcpy），
官方设计上靠"持锁时间短"把反转窗口压到可忽略。
真正要防的是 listener 里干长活——那是把短窗口人为拉长。

</details>
