## 这一篇讲什么

VDED = **Virtual Distributed Event Dispatcher**（虚拟分布式事件分发器）。
它是 ZBus 对"一次发布如何送达所有观察者"给出的**时序保证**：
谁在自己的上下文执行、谁借别人的上下文执行、同一条消息各份拷贝
按什么优先级顺序被消费。理解了 VDED，才敢在实时系统里用 ZBus。

## 先用人话说一遍（新手铺垫）

11.1 说了"发布者贴公告、观察者各取所需"，但实时系统里
光知道"送到了"不够，还得知道**什么时候、以谁的优先级、按什么顺序**送到。
VDED 就是 ZBus 对这套时序问题的正式答案——名字唬人，
拆开只是一张"一次发布的办事流程图"。

类比公司发一份紧急通知：老板（发布线程）**先把原件锁进档案柜**
（消息拷进通道，mutex（互斥锁：同一时刻只放一个线程进临界区的锁）保护）；然后**当着老板的面、按职位高低**
念给在场的人听（listener 同步执行——用的是老板的会议室、
老板的时间，念得慢老板就被拖住）；最后**把复印件塞进各部门信箱**
（拷进各 subscriber 队列），散会。各部门谁先看信箱？
按部门级别来（调度器优先级，HLP）；某个部门信箱爆了，
只丢它自己的件，不连累别人（背压隔离）。

三条保证对应三个现实问题的答案：**顺序性**（先发的先到）、
**优先级序**（要紧的消费者先处理）、**隔离性**（慢的消费者不拖累全局）。
写 ZBus 代码时每一条纪律（listener 快进快出、队列深度按滞后容忍度定）
都能从这张流程图上推出来。

| 术语 | 一句话解释 |
|---|---|
| VDED | ZBus 的事件分发模型：规定一次 pub 内部"拷通道→跑 listener→入队"的时序 |
| HLP | 最高锁定者优先：同一次发布，优先级最高的 subscriber 最先被调度处理 |
| 背压 | 消费跟不上时的压力传导问题：ZBus 让它只堵队列满的那个 subscriber |
| 优先级传染 | listener 借发布线程执行导致的副作用：它以发布者的优先级和栈运行 |
| 门铃（notify） | `zbus_chan_notify`：不带数据的纯通知，数据另行共享，通道只负责"提醒" |
| 优先级反转 | 高优先级线程被低优先级线程持有的锁堵住的经典实时问题；通道靠短持锁规避 |

## 一次发布的完整旅程

```
发布线程调用 zbus_chan_pub()
        │
        ├─ 1. 消息按值拷贝进通道存储（mutex 保护）
        │
        ├─ 2. 依次执行所有 listener ── 就在发布线程里、同步执行
        │        （按登记优先级从高到低）
        │
        ├─ 3. 消息拷贝进每个 subscriber / msg-subscriber 的队列
        │        （不等待队列有空间消费，超时参数只管 pub 本身）
        │
        └─ 4. 返回；各 subscriber 线程被内核调度
                 优先级最高的 subscriber 最先跑（HLP 规则）
```

要点：**2 和 3 都发生在 pub 调用返回之前**——
listener 是"借发布线程的手"执行的，subscriber 只是收到了入队通知，
真正的消息处理在 subscriber 自己的线程里、之后发生。

## VDED 的三条保证

| 保证 | 内容 | 依赖 |
|---|---|---|
| 顺序性 | 同一通道的两次发布，观察者收到的顺序与发布顺序一致 | 通道内部单份存储 + 各队列 FIFO（先进先出：先塞进队列的先被取走） |
| 优先级序 | 同一次发布，**优先级最高的 subscriber 最先处理**（HLP，Highest Locker Priority） | Zephyr 调度器（[4.3](../04-multithreading/4.3-优先级两个世界.md)） |
| 隔离性 | 慢 subscriber 只堵自己队列，不堵发布者和其他 subscriber | 每 subscriber 独立队列 |

对照裸 msgq 广播写法：发布者挨个 `k_msgq_put`，**任一队列满都会卡住发布者**；
ZBus 把每条队列的背压隔离到各自消费者身上。

## listener 的"借上下文"风险

VDED 第 2 步意味着 listener 的执行**挂在发布线程的优先级和栈上**：

| 后果 | 说明 |
|---|---|
| 优先级传染 | 低优先级发布线程发消息，listener 也以这个低优先级跑 |
| 栈传染 | listener 用的是发布线程的栈，深回调链可能爆栈 |
| 时长传染 | listener 耗时直接加在 pub 调用上，发布者被拖慢 |

因此官方语义对 listener 的定位是"**轻量、快路径、无阻塞**"：
置标志、转发到 workqueue、唤醒 subscriber——
真正的活交给 subscriber 线程按自己的优先级去做。

## 背压：队列满了会发生什么

subscriber 队列（`ZBUS_SUBSCRIBER_DEFINE(name, queue_size)`）满时：

- **该 subscriber 丢消息**（新发布进不去），不影响其他观察者；
- listener 不受影响（同步路径无队列）；
- 可用 `zbus_obs_set_enable` / 运行时观察来动态节流。

对照设计：队列深度 = 容忍的"消费滞后拍数"。
传感器 100Hz 发布、显示线程 10Hz 消费，队列深度 1 就够——
旧帧本就该丢（拿最新值用 `zbus_chan_read` 直接读通道当前值也行）。

## "原书怎么说 / 实际是什么"

| 原书（2024 版）说法 | 实际（Zephyr 3.x 官方文档） |
|---|---|
| VDED 保证"事件按优先级分发" | 完整表述是：listener 在发布上下文按登记优先级执行；subscriber 由各线程**调度器优先级**决定先后——ZBus 自己不改线程优先级 |
| HLP 是 ZBus 实现的优先级继承 | HLP 指"最高优先级 subscriber 优先被调度消费"，靠普通抢占调度实现，不是通道持有锁的继承 |
| pub 总是立即成功 | `zbus_chan_pub` 带 timeout，拿通道 mutex 失败会超时返回错误码 |

## 要点回顾

1. VDED：pub 返回前完成"拷贝进通道 + 同步跑完 listener + 入队所有 subscriber"。
2. listener 借发布线程上下文跑——优先级/栈/时长三重传染，必须快进快出。
3. subscriber 按 Zephyr 调度优先级消费（最高优先级先跑），队列独立、背压隔离。
4. 同一通道消息顺序 = 发布顺序；丢消息只丢队列满的那一个 subscriber。

<details>
<summary>Q1：ISR 里能 zbus_chan_pub 吗？</summary>

可以（官方文档允许，传 K_NO_WAIT）。ISR（中断服务程序：硬件事件触发、跑在普通线程之外的处理函数）上下文执行 listener 更要命——
listener 们全在 ISR 里同步跑完。中断里发布时，listener 列表应极短或为空，
重活一律留给 subscriber 线程。

</details>

<details>
<summary>Q2：想要"拿到消息就处理，不管新不新"，该用 subscriber 还是 zbus_chan_read？</summary>

要"逐条处理不丢帧"用 subscriber（队列缓存每条发布）；
要"只关心最新值"（如 UI 刷新显示当前温度）用
`zbus_chan_read` 直接读通道现值，配合 notify 当门铃，一条队列都不用。

</details>

<details>
<summary>Q3：通道的 mutex 会不会造成优先级反转？</summary>

通道的读写锁（mutex）持锁路径极短（一次 memcpy），
官方设计上靠"持锁时间短"把反转窗口压到可忽略。
真正要防的是 listener 里干长活——那是把短窗口人为拉长。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| pub 只负责入队，listener 之后异步跑 | 发布完就返回 | pub 返回**之前**：拷进通道 + 同步跑完所有 listener + 入队所有 subscriber |
| HLP 是 ZBus 做的优先级继承 | 听起来像锁继承机制 | 只是普通抢占调度：优先级最高的 subscriber 先被调度，ZBus 不改线程优先级 |
| pub 总是立即成功 | 发个消息还能失败 | `zbus_chan_pub` 带 timeout，拿通道 mutex 失败会超时返回错误码 |
| ISR 里不能发布 | 中断上下文禁 IPC | 可以（传 `K_NO_WAIT`），但所有 listener 全在 ISR 里同步跑完——列表应极短或为空 |

## 代码自测

_注：本节示例按本篇正文语义编写，未在本仓库环境实跑，仿真验证见「验证路径」。_

观察 VDED 时序：listener 同步先于 pub 返回，subscriber 在自己线程后处理。

```c
#include <zephyr/kernel.h>
#include <zephyr/zbus/zbus.h>

struct sensor_data { int temp; int humi; };

ZBUS_CHAN_DEFINE(sensor_chan, struct sensor_data,
                 NULL, NULL, ZBUS_OBSERVERS_EMPTY, ZBUS_MSG_INIT(0, 0));

static void on_sensor(const struct zbus_channel *chan)
{
    printk("1.listener（发布线程上下文，同步）\n");
}
ZBUS_LISTENER_DEFINE(sensor_lis, on_sensor);
ZBUS_SUBSCRIBER_DEFINE(sensor_sub, 4);        /* 4 = 队列深度 */

static void sub_thread(void)
{
    const struct zbus_channel *chan;
    while (!zbus_sub_wait(&sensor_sub, &chan, K_FOREVER)) {
        printk("3.subscriber（自己线程，之后跑）\n");
    }
}
K_THREAD_DEFINE(sub_tid, 1024, sub_thread, NULL, NULL, NULL, 3, 0, 0);

void main(void)
{
    ZBUS_CHAN_ADD_OBS(sensor_chan, sensor_lis, 3);
    ZBUS_CHAN_ADD_OBS(sensor_chan, sensor_sub, 3);

    struct sensor_data d = { .temp = 25, .humi = 60 };
    zbus_chan_pub(&sensor_chan, &d, K_MSEC(10));
    printk("2.pub 已返回（listener 必在此前跑完）\n");
    k_msleep(100);
}
```

**预期现象**：

- 串口顺序严格为 `1.listener` → `2.pub 已返回` → `3.subscriber`；
- subscriber 队列深度调 1、连续 pub 两条而线程不取：只丢它自己的消息，listener 不受影响；
- 把发布挪进 ISR（K_NO_WAIT）：listener 的打印出现在中断上下文。

**验证路径**：`west build -b qemu_cortex_m3 -t run` 看串口输出顺序。

**常见翻车点**：

- 在 listener 里干长活——把通道 mutex 的短窗口人为拉长，诱发优先级反转；
- 队列深度拍脑袋定——应按"容忍的消费滞后拍数"定，旧帧本就该丢。
