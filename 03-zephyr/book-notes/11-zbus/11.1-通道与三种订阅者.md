## 这一篇讲什么

ZBus 是 Zephyr 3.x 引入的**发布-订阅消息总线**：
消息不再从"线程 A 直接塞给线程 B"，而是发布到一个**通道（channel）**，
所有登记在这个通道上的观察者（observer）自动各收一份。
这一篇把三个角色——通道、订阅者、监听器——摆清楚，重点在
**它们的"接收上下文"完全不同**。

## 为什么需要总线：ch05 的痛点

回顾 [ch05](../05-ipc-workqueues/README.md)：k_msgq / k_pipe / k_mbox
全是**点对点**——一个队列一头进一头出。
传感器数据要同时喂给"显示 + 记录 + 上报"三个模块时，用 msgq 的写法：

```
传感器线程 → msgq_display ──→ 显示线程
          ├→ msgq_logger ────→ 记录线程
          └→ msgq_uplink ────→ 上报线程
```

发布者要维护 N 条队列、N 份拷贝、N 个失败分支。
ZBus 把这个拓扑收进内核：**发布者只认识通道，不认识消费者**。

## 三个角色

| 角色 | 是什么 | 在哪接收消息 | 开销 |
|---|---|---|---|
| channel | 静态定义的消息载体，定死消息类型 | —（不执行代码） | 一份消息存储 |
| subscriber | 登记为观察者的**线程** | 自己的线程上下文（队列收） | 一个线程 + 一条队列 |
| listener | 一个**回调函数** | **发布者线程上下文**（同步！） | 极小（无独立栈） |

还有第四种 message subscriber（`ZBUS_MSG_SUBSCRIBER_DEFINE`），
本质是 subscriber 的静态队列化。

## 定义一个通道

```c
struct sensor_data { int temp; int humi; };

ZBUS_CHAN_DEFINE(sensor_chan,            /* 通道名 */
                 struct sensor_data,     /* 消息类型（按值拷贝） */
                 NULL,                   /* validator / user_data */
                 NULL,
                 ZBUS_OBSERVERS_EMPTY,   /* 静态观察者列表 */
                 ZBUS_MSG_INIT(0, 0));   /* 初始值 */
```

观察者可静态登记（`ZBUS_OBSERVERS(...)`）或运行时增删
（`zbus_chan_add_obs` / `zbus_chan_rm_obs`）——"运行时插拔消费者"是 msgq 做不到的。

## 发布与接收

```c
/* 发布：任何线程/ISR 都能发，按值拷贝进通道 */
struct sensor_data d = { .temp = 25, .humi = 60 };
zbus_chan_pub(&sensor_chan, &d, K_MSEC(10));

/* listener：跑在发布者上下文，必须快进快出、禁止阻塞 */
static void on_sensor(const struct zbus_channel *chan)
{
    const struct sensor_data *d = zbus_chan_const_msg(chan);
}
ZBUS_LISTENER_DEFINE(sensor_lis, on_sensor);
ZBUS_CHAN_ADD_OBS(sensor_chan, sensor_lis, 3);  /* 3 = 优先级 */

/* subscriber：线程式接收，可以阻塞处理 */
ZBUS_SUBSCRIBER_DEFINE(sensor_sub, 4);          /* 4 = 队列深度 */
```

发布侧还可用 `zbus_chan_notify` 发"无负载事件"——数据走共享区，通道只当门铃。

## 与 FreeRTOS 的对照（其实对不上）

| FreeRTOS | 能对应吗 | 说明 |
|---|---|---|
| queue | 部分 | 队列本身点对点，ZBus 通道是一对多广播 |
| 事件组 | 部分 | 事件组只有 32 个位、无负载；ZBus 消息带类型化数据 |
| 任务通知 | 不能 | 通知是定向的（指定接收任务），且负载只有 32bit |
| pub-sub 库 | 最接近 | FreeRTOS 主线无内置总线，需 coreMQTT-Agent 之类第三方 |

ZBus 是 Zephyr **内核级内置设施**——相对 FreeRTOS 生态少有的"我有你没有"的 IPC 原语。

## 要点回顾

1. ZBus = 通道（类型化消息载体）+ 观察者；发布者只认通道不认消费者。
2. 三种观察者：listener（回调，跑在**发布者上下文**）、subscriber（线程，自己上下文）、message subscriber（静态队列版 subscriber）。
3. `ZBUS_CHAN_DEFINE` 静态定义 + `zbus_chan_pub` 按值发布；观察者可运行时增删。
4. 解决 ch05 点对点 IPC 的"一份数据多处消费"痛点；FreeRTOS 无直接对应物。

<details>
<summary>Q1：listener 跑在发布者上下文，会不会拖垮发布线程？</summary>

会，这是 listener 的铁律：**回调必须快进快出，禁止阻塞**。
发布线程会**同步依次执行**该通道所有 listener，任何一个慢/阻塞，
发布者和同通道所有接收方一起被拖住。重活应该在 listener 里
`k_work_submit` 转给 workqueue（[5.4 workqueue](../05-ipc-workqueues/5.4-workqueue.md)）。

</details>

<details>
<summary>Q2：消息是按值拷贝的，大消息会不会很贵？</summary>

会。通道内部存储 = 消息大小，发布时拷一份进通道，每个 subscriber 再各拷一份。
上百字节的大块建议改发指针（配合 `zbus_chan_claim` + `zbus_chan_finish`
发布期间原地填充），或走 k_pipe 传块、zbus 只发"门铃"。

</details>
