## 这一篇讲什么

裸机里读写 flash 是"算好地址直接擦写"（对照 [01-stm32 ch11](../../../01-stm32/book-notes/11-linker/README.md)
的地址视角）；文件系统子系统是在这上面加三层抽象。这一篇把三层摆清楚，
再解决选型问题：LittleFS 还是 FAT。

## 三层架构

```
应用代码：fs_open("/lfs/config.txt", ...) / fs_read / fs_write
   │
VFS 层（include/zephyr/fs/fs.h）：统一 API，按挂载点前缀分发
   │
后端：LittleFS（小 flash 专用） 或  FATFS（ChaN 的 ELM FatFs，SD 卡事实标准）
   │
存储驱动：flash 驱动（flash_area） 或  SDMMC/SPI 磁盘驱动
```

对照标准 C 的 stdio（[01-stm32 ch14](../../../01-stm32/book-notes/14-buffered-file-io/README.md)）：
`fs_open/fs_read/fs_write` 和 `fopen/fread/fwrite` 是一一对应的，
只是多了**挂载**这一步——文件路径里的 `/lfs` 前缀必须先挂出来。

## 挂载：一个 fs_mount_t 结构的事

```c
#include <zephyr/fs/fs.h>
#include <zephyr/fs/littlefs.h>

FS_LITTLEFS_DECLARE_DEFAULT_CONFIG(storage);   /* 绑定 devicetree 的 storage_partition */

static struct fs_mount_t lfs_mnt = {
    .type = FS_LITTLEFS,              /* 选后端：FS_LITTLEFS / FS_FATFS */
    .fs_data = &storage,
    .storage_dev = (void *)FIXED_PARTITION_ID(storage_partition),
    .mnt_point = "/lfs",              /* 之后所有 /lfs/... 路径都进 LittleFS */
};

fs_mount(&lfs_mnt);                   /* 失败时常见原因：分区没格式化 */
```

`FIXED_PARTITION_ID(storage_partition)` 是关键：
**文件系统不占整个 flash，只占 devicetree 里划给它的那个分区**，
这就是下一篇 [6.2](6.2-devicetree分区表.md) 的主题。

## LittleFS vs FAT 选型表

| | LittleFS | FAT(FS) |
|---|---|---|
| 设计目标 | 小容量 NOR/NAND flash | 通用块设备，PC 互操作 |
| 掉电安全 | ✅ 写穿日志结构，任意时刻掉电不丢旧数据 | ⬜ 原生不保证（断电可能损坏 FAT 表） |
| 磨损均衡 | ✅ 内建动态磨损均衡 | ⬜ 无（FAT 表集中在固定扇区，热点磨损） |
| RAM/ROM 开销 | 极小（可配到几百字节缓存） | 较大（FAT 缓存、簇管理） |
| PC 可读 | ⬜ 需专用工具 | ✅ SD 卡拔下来插电脑直接读 |
| 典型场景 | 片内/外挂 NOR flash 存配置、日志 | SD 卡存音频/照片/大数据 |

**一句话选型**：flash 上选 LittleFS，SD 卡上选 FAT；
两个都要（外挂 flash 存参数 + SD 卡存数据）就挂两个挂载点，互不干扰。

## 典型用法两则

1. **配置持久化**：不要自己手写 `fs_write` 管参数——
   Zephyr 有 **settings 子系统**（`settings_save/settings_load`），
   后端可选 LittleFS 文件或 NVS（见 [6.3](6.3-磨损均衡与掉电安全.md)），
   键值对形式，掉电安全由后端兜底。
2. **日志落盘**：LOG 子系统有文件系统后端（`CONFIG_LOG_BACKEND_FS`），
   把 `LOG_INF` 的输出追加到 flash 文件，现场复现用的"黑匣子"。

## 书 API 年代差

| 原书怎么说 | 实际是什么（Zephyr 3.x） |
|---|---|
| 早期 Zephyr 的 FS API 挂在 `fs.h` 下且后端只有 FAT | LittleFS 自 2.x 起就是一等公民，是小 flash 场景的默认推荐 |
| 挂载点配置散在 prj.conf 默认值里 | 现行惯例：`FS_LITTLEFS_DECLARE_DEFAULT_CONFIG` + devicetree `storage_partition` 显式绑定 |

## 要点回顾

1. 三层：统一 fs API → LittleFS/FAT 后端 → flash/磁盘驱动；路径前缀按挂载点分发。
2. 挂载核心是 `fs_mount_t` 三要素：后端类型、存储设备（分区 ID）、挂载点。
3. 选型口诀：flash 用 LittleFS（掉电安全+磨损均衡），SD 卡用 FAT（PC 互操作）。

<details>
<summary>Q1：fs_mount 返回 -ENOENT 或挂载失败，第一嫌疑是什么？</summary>

分区从未格式化。LittleFS 挂载时若发现不是合法的 LittleFS 超级块会失败；
开发期常用做法：检测到 `fs_mount` 失败后调 `fs_mkfs(FS_LITTLEFS, ...)` 格式化再挂，
或烧录前用 `littlefs-python` 之类的工具预生成镜像烧进分区。
格式化会清空分区，**别对存着数据的分区无脑 mkfs**。

</details>

<details>
<summary>Q2：一个系统能同时挂 LittleFS 和 FAT 吗？</summary>

能，挂载点互不冲突即可（如 `/lfs` 和 `/SD:`）。
VFS 层按路径最长前缀匹配分发到对应后端。
注意 FAT 的默认挂载点风格是 `/SD:`、`/NAND:` 这类（带冒号），
和 POSIX 风格不同，写路径前先看 prj.conf 里的卷名配置。

</details>
