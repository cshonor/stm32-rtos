## 这一篇讲什么

[6.1](6.1-FS子系统架构.md) 里 `FIXED_PARTITION_ID(storage_partition)` 指向的那块区域
到底从哪来？答案：devicetree 里的 `partitions` 节点。
这一篇讲分区表怎么写、和应用镜像/MCUboot 的关系、代码里怎么引用分区。

## 先用人话说一遍（新手铺垫）

一块 flash 芯片就是一整块地皮：bootloader、应用镜像、升级备件、
用户数据全都要住进去。没有分区表，各家随便占地，
一次 OTA（空中升级：不插线、通过网络远程更新固件）升级就可能把用户数据盖掉——这种事在量产设备上就是事故。

分区表就是**地契**：哪块地归谁、从哪到哪，白纸黑字（devicetree 节点）
写死。经典四块地的格局：门卫室（boot_partition，MCUboot 住）、
现住主楼（slot0，正在跑的应用）、备用楼（slot1，OTA 下载的新镜像）、
仓库（storage，文件系统）。对应关系：升级 = 新镜像先住进备用楼，
验收通过再搬家；仓库放地皮尾部 = 搬家施工不碰用户数据。

两条纪律要提前知道：①地契是**出厂前冻结**级别的设计——
量产后改分区等于把仓库整体平移，里面的货全乱；
②地址可以手算错，但**长度必须按擦除扇区对齐**，
否则 LittleFS 一擦就擦到邻居家。这两条都是"编不过不存在，
出事就是大事"的类型。

| 术语 | 一句话解释 |
|---|---|
| 擦除扇区（sector） | flash 擦除的最小单位（如 4KB）：分区长度必须是它的整数倍 |
| flash map / flash_area | Zephyr 的分区抽象层：把 devicetree 分区节点变成 C 代码可查可写的对象 |
| `FIXED_PARTITION_ID()` | 编译期宏：把分区节点名转成数字 ID，类型安全，取代旧的字符串查找 |
| slot0 / slot1 | OTA 升级的两个镜像槽：slot0 跑当前版本，slot1 接收新版本 |
| MCUboot | Zephyr 生态的标准 bootloader：负责开机校验镜像、执行 slot 交换升级 |

## 分区表长什么样

分区是 flash 控制器节点下的子节点（devicetree 语法细节见
[ch09](../09-devicetree/README.md)，这里只看分区这一处）：

```dts
&flash0 {
    partitions {
        compatible = "fixed-partitions";
        #address-cells = <1>;  #size-cells = <1>;

        boot_partition: partition@0 {              /* 48K 给 bootloader */
            label = "mcuboot";  reg = <0x0 0xC000>;
        };
        slot0_partition: partition@C000 {          /* 应用主槽 */
            label = "image-0";  reg = <0xC000 0x69000>;
        };
        slot1_partition: partition@75000 {         /* 升级备槽 */
            label = "image-1";  reg = <0x75000 0x69000>;
        };
        storage_partition: partition@DE000 {       /* 尾部留给文件系统 */
            label = "storage";  reg = <0xDE000 0x22000>;
        };
    };
};
```

三条铁律：

1. **地址从 0 起算**（相对该 flash 设备的基址）；**reg = <偏移 长度>**。
2. 长度必须按 flash 擦除粒度（sector）对齐——LittleFS 以 sector 为单位擦除，跨半个 sector 就是灾难。
3. 应用镜像链接地址跟着 slot0 走：有 MCUboot 时应用编进 slot0 起始处，构建系统读分区表自动完成。

## Flash map 层：devicetree 到 C 代码的桥

Zephyr 用 **flash map**（flash_area API）把分区节点变成 C 可查的对象：

| devicetree 侧 | C 侧 | 用途 |
|---|---|---|
| `storage_partition` 节点 | `FIXED_PARTITION_ID(storage_partition)` | 编译期转成数字 ID |
| 节点的 reg/label | `flash_area_open(id, &fa)` → `fa->fa_off / fa->fa_size` | 运行时查偏移和大小 |
| —— | `flash_area_read/write/erase(fa, ...)` | 不挂文件系统也能裸读写分区 |

文件系统（LittleFS 后端）、NVS（非易失键值对存储：只存参数/计数器的轻量机制）、settings 的 FCB（环形追加缓冲：专为"只进不出的流水记录"设计）后端、MCUboot 镜像交换，
**全部建立在 flash_area 之上**——分区表是这一切的地基。

## 编译期 vs 运行期引用

```c
/* 编译期：只要 ID（挂载结构体的 storage_dev 字段用） */
.storage_dev = (void *)FIXED_PARTITION_ID(storage_partition),

/* 运行期：要操作分区内容时先 open；fa->fa_off / fa->fa_size 可用 */
const struct flash_area *fa;
flash_area_open(FIXED_PARTITION_ID(storage_partition), &fa);
flash_area_close(fa);
```

## 与 MCUboot 的共存格局

```
[ boot_partition | slot0 | slot1 | storage ]
   MCUboot          正在跑   下载的新镜像   LittleFS/NVS
```

- 升级流程：新镜像写 slot1 → MCUboot 启动时交换 → 应用确认后固化；
  storage 放尾部，**文件系统数据不受 OTA 影响**。
- 无 bootloader 的单镜像项目：slot0 起点就是 flash 基址，storage 仍在尾部——
  **分区表不是 MCUboot 专利，是"划地声明"**。

## 书 API 年代差

| 原书怎么说 | 实际是什么（Zephyr 3.x） |
|---|---|
| 分区曾用 Kconfig/旧 flash_map 头文件加节点 label 字符串查找 | 现行统一 `FIXED_PARTITION_ID()` / `FIXED_PARTITION_OFFSET()` 宏，编译期解析，类型安全 |
| `flash_area_open` 用分区 label 字符串 | label 字符串查询（`FLASH_AREA_ID(label)`）已废弃，一律走 FIXED_PARTITION 宏 |

## 要点回顾

1. 分区表写在 flash 节点的 `partitions` 下：偏移+长度，按擦除扇区对齐。
2. flash map（flash_area API）是 devicetree 分区到 C 代码的桥，文件系统/NVS/MCUboot 都站在它上面。
3. 经典布局 = boot + slot0 + slot1 + storage（尾部）；无 bootloader 也值得写分区表。

<details>
<summary>Q1：改分区表后旧设备上的文件系统数据会怎样？</summary>

storage 分区只要偏移或长度变了，旧数据的相对位置就全乱了——LittleFS 会把
残留数据当乱码，挂载失败或行为异常。**分区表属于"产品出厂前冻结"级别的设计**，
量产后再改等于清盘；OTA 方案里分区表要和 bootloader 一起冻结。

</details>

<details>
<summary>Q2：怎么确认编译出来的应用真的落在 slot0 里？</summary>

看 `build/zephyr/zephyr.dts`（预处理后的完整 devicetree）里分区的最终 reg，
再对照 `zephyr.map` 的 `__rom_region_start` 或 hex 文件起始地址。
链接地址由 devicetree 决定，改分区表后**必须重新 west build** 才生效。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| 分区长度按需求取个整 | 0x10000 好看就用 | 必须按擦除扇区（如 4KB）对齐：LittleFS 以 sector 为单位擦除，跨半个 sector 就擦到邻居家 |
| 改完 dts 直接跑 | 配置改动自动生效 | 链接地址由 devicetree 决定，改分区表后**必须重新 west build**（Q2） |
| 分区表随时可调 | 配置文件而已 | 出厂前冻结级设计：storage 偏移/长度一变，旧设备数据全乱，量产后改 = 清盘（Q1） |
| `flash_area_open` 传 label 字符串 | 书上旧写法 | label 字符串查询已废弃，一律 `FIXED_PARTITION_ID()` 编译期宏，类型安全 |
| 分区表是 MCUboot 专利 | 没 bootloader 不用写 | 单镜像项目也该写：分区表是"划地声明"，防升级/越界写盖掉用户数据 |

## 代码自测

_注：本节代码按 Zephyr API 语义编写，未在本仓库环境实跑，仿真验证见「验证路径」。_

```c
#include <zephyr/kernel.h>
#include <zephyr/storage/flash_map.h>
#include <zephyr/sys/printk.h>

int main(void)
{
    const struct flash_area *fa;
    int rc = flash_area_open(FIXED_PARTITION_ID(storage_partition), &fa);
    if (rc != 0) {
        printk("flash_area_open failed: %d\n", rc);
        return rc;
    }

    printk("storage: off=0x%lx size=0x%lx\n",
           (unsigned long)fa->fa_off, (unsigned long)fa->fa_size);

    uint8_t head[16];
    flash_area_read(fa, 0, head, sizeof(head));   /* 不挂文件系统也能裸读分区 */
    printk("first 4 bytes:");
    for (int i = 0; i < 4; i++) {
        printk(" %02x", head[i]);
    }
    printk("\n");

    flash_area_close(fa);
    return 0;
}
```

**预期现象**：
- 打印的 `off` / `size` 与 dts 里 `storage_partition` 的 `reg = <0xDE000 0x22000>` 完全一致
- 未格式化的分区读回 `ff ff ff ff`（flash 擦除态）
- 挂过 LittleFS 的分区则能读到超级块内容，不再是全 ff

**验证路径**：`west build -b qemu_x86 -t run`（qemu_cortex_m3 无 flash 分区），或带分区表的实机 + 串口。

**常见翻车点**：
- 改了 dts 分区表没重新 west build：打印的还是旧 reg——链接地址由 devicetree 决定（Q2）
- 把 `fa_off` 当绝对地址用：它是**相对该 flash 设备基址**的偏移
- 分区长度不按扇区对齐：后续的 `flash_area_erase` 会波及相邻分区
