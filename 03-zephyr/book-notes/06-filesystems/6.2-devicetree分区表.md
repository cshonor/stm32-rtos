## 分区表长什么样

分区是 flash 控制器节点下的子节点（devicetree 语法细节见
[ch09](../09-devicetree/README.md)，这里只看分区这一处）：

```dts
&flash0 {
    partitions {
        compatible = "fixed-partitions";
        #address-cells = <1>;  #size-cells = <1>;

        boot_partition: partition@0 {              /* 48K 给 bootloader */
            label = "mcuboot";  reg = <0x0 0xC000>;
        };
        slot0_partition: partition@C000 {          /* 应用主槽 */
            label = "image-0";  reg = <0xC000 0x69000>;
        };
        slot1_partition: partition@75000 {         /* 升级备槽 */
            label = "image-1";  reg = <0x75000 0x69000>;
        };
        storage_partition: partition@DE000 {       /* 尾部留给文件系统 */
            label = "storage";  reg = <0xDE000 0x22000>;
        };
    };
};
```

三条铁律：

1. **地址从 0 起算**（相对该 flash 设备的基址）；**reg = <偏移 长度>**。
2. 长度必须按 flash 擦除粒度（sector）对齐——LittleFS 以 sector 为单位擦除，跨半个 sector 就是灾难。
3. 应用镜像链接地址跟着 slot0 走：有 MCUboot 时应用编进 slot0 起始处，构建系统读分区表自动完成。

## Flash map 层：devicetree 到 C 代码的桥

Zephyr 用 **flash map**（flash_area API）把分区节点变成 C 可查的对象：

| devicetree 侧 | C 侧 | 用途 |
|---|---|---|
| `storage_partition` 节点 | `FIXED_PARTITION_ID(storage_partition)` | 编译期转成数字 ID |
| 节点的 reg/label | `flash_area_open(id, &fa)` → `fa->fa_off / fa->fa_size` | 运行时查偏移和大小 |
| —— | `flash_area_read/write/erase(fa, ...)` | 不挂文件系统也能裸读写分区 |

文件系统（LittleFS 后端）、NVS、settings 的 FCB 后端、MCUboot 镜像交换，
**全部建立在 flash_area 之上**——分区表是这一切的地基。

## 编译期 vs 运行期引用

```c
/* 编译期：只要 ID（挂载结构体的 storage_dev 字段用） */
.storage_dev = (void *)FIXED_PARTITION_ID(storage_partition),

/* 运行期：要操作分区内容时先 open；fa->fa_off / fa->fa_size 可用 */
const struct flash_area *fa;
flash_area_open(FIXED_PARTITION_ID(storage_partition), &fa);
flash_area_close(fa);
```

## 与 MCUboot 的共存格局

```
[ boot_partition | slot0 | slot1 | storage ]
   MCUboot          正在跑   下载的新镜像   LittleFS/NVS
```

- 升级流程：新镜像写 slot1 → MCUboot 启动时交换 → 应用确认后固化；
  storage 放尾部，**文件系统数据不受 OTA 影响**。
- 无 bootloader 的单镜像项目：slot0 起点就是 flash 基址，storage 仍在尾部——
  **分区表不是 MCUboot 专利，是"划地声明"**。

## 书 API 年代差

| 原书怎么说 | 实际是什么（Zephyr 3.x） |
|---|---|
| 分区曾用 Kconfig/旧 flash_map 头文件加节点 label 字符串查找 | 现行统一 `FIXED_PARTITION_ID()` / `FIXED_PARTITION_OFFSET()` 宏，编译期解析，类型安全 |
| `flash_area_open` 用分区 label 字符串 | label 字符串查询（`FLASH_AREA_ID(label)`）已废弃，一律走 FIXED_PARTITION 宏 |

## 要点回顾

1. 分区表写在 flash 节点的 `partitions` 下：偏移+长度，按擦除扇区对齐。
2. flash map（flash_area API）是 devicetree 分区到 C 代码的桥，文件系统/NVS/MCUboot 都站在它上面。
3. 经典布局 = boot + slot0 + slot1 + storage（尾部）；无 bootloader 也值得写分区表。

<details>
<summary>Q1：改分区表后旧设备上的文件系统数据会怎样？</summary>

storage 分区只要偏移或长度变了，旧数据的相对位置就全乱了——LittleFS 会把
残留数据当乱码，挂载失败或行为异常。**分区表属于"产品出厂前冻结"级别的设计**，
量产后再改等于清盘；OTA 方案里分区表要和 bootloader 一起冻结。

</details>

<details>
<summary>Q2：怎么确认编译出来的应用真的落在 slot0 里？</summary>

看 `build/zephyr/zephyr.dts`（预处理后的完整 devicetree）里分区的最终 reg，
再对照 `zephyr.map` 的 `__rom_region_start` 或 hex 文件起始地址。
链接地址由 devicetree 决定，改分区表后**必须重新 west build** 才生效。

</details>
