## 这一篇讲什么

NOR flash 的两条物理约束：**写前必须整块擦除、每个块擦写寿命有限**
（典型 10K–100K 次）。在这两条约束下，"朴素地存数据"会同时踩两个坑：
掉电丢数据、热点块被磨穿。LittleFS 的设计就是同时拆掉这两个雷。

## 问题 1：掉电安全

改写 flash 上一个字节的正确流程：读出整块 → 擦除整块 → 写回整块。
擦除后、写回前掉电 = **整块数据全丢**。FAT 类文件系统原地更新 FAT 表
和目录项，掉电窗口正中这个流程。

LittleFS 的解法：**copy-on-write（写时复制）+ 日志结构元数据对（metadata pair）**。

```
改文件内容 → 新数据写到新块，旧块不擦
改目录项   → 元数据追加到 metadata pair 的日志尾部
提交       → 最后写一条 commit 记录；commit 落下才算数
掉电       → 挂载时从日志末尾回放到最后一个有效 commit，中途断的就当没发生
```

关键性质：**任意时刻掉电，文件系统要么回到旧版本，要么前进到新版本，
没有中间态**。这个性质叫 power-loss resilience，是 LittleFS 的头号卖点。

## 问题 2：磨损均衡

日志结构天然有均衡效果——元数据追加写，块写满就换一个。
LittleFS 再加一招：**动态磨损均衡**——块的擦除次数超过阈值时，
把"冷数据"（几乎不改的块）搬去高磨损块，让热数据轮流坐冷板凳。

| | FAT | LittleFS |
|---|---|---|
| 更新方式 | 原地更新（FAT 表/目录项固定位置） | 写时复制 + 日志追加 |
| 掉电后果 | 可能损坏 FAT 表 → 整盘需修复 | 回放日志到最近 commit，最坏丢最后一批未提交数据 |
| 热点块 | FAT 表所在块每次写操作都被擦 | 写入自然轮转 + 动态均衡 |
| 适合擦除寿命 | 不敏感的大容量/可换介质（SD 卡） | 10K 次寿命的小 NOR flash |

## 成本账：天下没有免费的均衡

- **写放大**：小改动引发整块搬迁，吞吐比 FAT 原地写低。
  频繁小写场景（高频日志）要攒批。
- **容量利用**：需要空闲块做轮转，分区建议留出余量；
  LittleFS 有 `CONFIG_FS_LITTLEFS_FC_HEAP_SIZE` 等参数控制元数据缓存。
- **块设备抽象**：LittleFS 层要求知道 `read_size / prog_size / erase_size`，
  Zephyr 的 LittleFS 后端从 flash 驱动自动取，不用手填。

## 比文件系统更轻的两条路

Zephyr 里"掉电安全存数据"有三档方案，按需求选：

| 方案 | 形态 | 适合 |
|---|---|---|
| **NVS**（Non-Volatile Storage） | flash_area 上的键值对，日志结构、掉电安全 | 只存参数/计数器，不需要目录概念 |
| **FCB**（Flash Circular Buffer） | 环形追加日志 | 只进不出的流水记录 |
| **LittleFS 文件** | 完整文件语义 | 多文件、按名字管理、要目录 |

settings 子系统可以架在 NVS 或 LittleFS 之上（[6.1](6.1-FS子系统架构.md)）——
**绝大多数"存配置"需求到 settings 为止，不该直接摸 fs API**。

## 要点回顾

1. flash 两约束：擦除整块、寿命有限 → 掉电丢数据 + 热点磨损两个坑。
2. LittleFS = 写时复制 + 日志提交点：任意掉电回到最近一致状态；追加写天然轮转 + 动态均衡磨平均。
3. 代价是写放大；只存键值对用 NVS/settings，别为几个参数上整套文件系统。

<details>
<summary>Q1：metadata pair 为什么用"一对"块而不是一个？</summary>

互为镜像。写元数据时往 pair 里追加，写满后把存活数据压缩（compact）到
pair 里的另一块——压缩过程本身掉电，旧块还完好，回滚即可。
两块轮换既保证元数据操作的原子性，也让元数据区的擦写次数减半。

</details>

<details>
<summary>Q2：高频记录传感器数据（每秒一条）该用 LittleFS 文件追加吗？</summary>

不该直接每秒 fs_write 小数据——每次都触发 commit 和块管理，写放大严重。
正确姿势：RAM 里攒批（如 4KB 一个 erase block 的量）再落盘，
或者直接用 FCB（它就是为"追加流水"设计的）。
若数据丢几秒无所谓，攒批还能顺带省电（少擦少写）。

</details>
