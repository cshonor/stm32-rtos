## 名字像、语义不同的三个坑

**坑 1：k_sleep vs vTaskDelay 的"期满唤醒"细节。**
两者都是相对时间睡眠，但 Zephyr 的 `k_sleep(K_MSEC(n))` 保证
"至少睡满 n"（向上对齐 tick），FreeRTOS 的 vTaskDelay(n) 是
"睡 n 个 tick 边界之间"，实际可能略少于 n×tick。
做精确周期都不要用相对延时：FreeRTOS 用 vTaskDelayUntil，
Zephyr 用 k_timer（见 [4.4](../04-multithreading/4.4-调度与睡眠.md)）。

**坑 2：k_mutex 不是"二值信号量的马甲"。**
FreeRTOS 里 mutex 和 binary semaphore 实现上很接近（多一个继承）。
Zephyr 的 k_mutex 是**独立对象**：可重入（同线程可多次 lock，
解锁次数要配对）、强制所有权（只能由持有者解锁）、带优先级继承。
k_sem 则没有所有权概念，谁都能 give——别拿 k_sem 当互斥锁用。

**坑 3："queue" 这个词在 Zephyr 里指别的东西。**
Zephyr 内核 API 里叫 queue 的有两个：`k_queue`（**指针**链表，
传引用不传值，和 FreeRTOS queue 语义差很远）和 legacy 的 `k_lifo/k_fifo`。
FreeRTOS queue 的真正对应物是 **k_msgq**（值拷贝 + 环形缓冲 + 双等待名单，
对照 [02-freertos 4.1](../../../02-freertos/book-notes/04-queue-management/4.1-队列是什么.md)）。
选型时先想"传值还是传指针"，再决定 msgq 还是 queue/lifo。

## 读 Zephyr 文档时的速查心法

- 对象名一律 `k_` 前缀 + 下划线小写（k_sem、k_msgq、k_timer）；
- 操作命名多为 `k_<对象>_<动词>`（k_sem_take、k_msgq_put）；
- 超时参数统一是 `k_timeout_t`（K_NO_WAIT / K_FOREVER / K_MSEC(n)），
  全内核一套——比 FreeRTOS 每个对象各写 TickType_t 更一致；
- 找不到对应物时，多半在 k_event / k_poll / k_work 这三个
  "万能胶水"里。

## 要点回顾

1. 语义最近的一对：FreeRTOS queue ↔ Zephyr k_msgq（值拷贝环形缓冲）。
2. 三大坑：相对延时的 tick 对齐差异；k_mutex 可重入+所有权（≠二值信号量）；"queue" 在 Zephyr 指指针链表。
3. 超时统一 `k_timeout_t`；找不到的对应物去 k_event/k_poll/k_work 里找。

<details>
<summary>Q1：为什么 Zephyr 没有 task notification 的直接对应？</summary>

task notification 本质是"挂在线程身上的一格信箱"，用 TCB 内存换速度。
Zephyr 哲学是不给单个对象开"隐藏后门"：等单个事件用 k_sem，
等 32 位事件位用 k_event，等"多个对象谁先就绪"用 k_poll。
功能都覆盖，代价是多一个对象（几十字节）。

</details>

<details>
<summary>Q2：k_queue 传指针，那接收方拿到的内存归谁管？</summary>

归发送方管——k_queue 只搬指针，所有权约定靠应用自己定
（谁分配谁释放，或放回 k_mem_slab）。这正是 k_msgq 存在的理由：
不想管所有权就别传指针，让内核 memcpy。

</details>

## 衔接

词汇换完，剩下最大的一处世界观差异：
**优先级数字的方向，以及负数优先级的存在**。
FreeRTOS 数字越大越优先、没有负数；Zephyr 数字越小越优先、
负数还另有含义。下一篇 [2.2 优先级两个世界](2.2-优先级两个世界.md)。
