## 先用人话说一遍（新手铺垫）

既然机制在 FreeRTOS 那边学过一遍，这一篇为什么不直接跳过？
因为换词汇不是背单词，是**换一套直觉**——你看到 `k_sem` 时脑子里
浮现的那个东西，必须和它真实的行为对上，差一点都不行。

学外语的人知道"假朋友"（false friends）这个词：两个语言里拼写像、
意思却不同的词——比如英语的 gift 在德语里是"毒药"。
换 RTOS 词汇表最大的风险不是"不认识"，而是**自以为认识**。
对应关系：task→thread 这种是纯翻译（真朋友），
`k_queue`、`k_mutex`、`k_sleep` 就是假朋友——名字眼熟，语义有坑，
本篇"三个坑"一节专抓这几个。

所以读这篇的姿势：总表快速过，混个眼熟；
三个坑逐个停下来想清楚——它们就是你未来调试时
"按 FreeRTOS 经验推测、结果被 Zephyr 打脸"的高发地带。

| 术语 | 一句话解释 |
|---|---|
| 优先级继承 | 防优先级反转的机制：低优先级线程持锁时，临时升到等待者（高优先级）的优先级 |
| 可重入 | 同一个线程可以对同一把锁重复加锁（解锁次数须配对），不会自己锁死自己 |
| task notification | FreeRTOS 特有的轻量机制：直接往任务控制块里塞一个值/事件位，不用建对象 |
| `k_timeout_t` | Zephyr 全内核统一的超时类型：`K_NO_WAIT`（不等）/ `K_FOREVER`（死等）/ `K_MSEC(n)`（等 n 毫秒） |
| 值拷贝 vs 传指针 | 队列传数据的两种方式：拷贝 = 数据复制进队列（安全，慢）；传指针 = 只传地址（快，内存归属自己管） |

## 名字像、语义不同的三个坑

**坑 1：k_sleep vs vTaskDelay 的"期满唤醒"细节。**
两者都是相对时间睡眠，但 Zephyr 的 `k_sleep(K_MSEC(n))` 保证
"至少睡满 n"（向上对齐 tick（系统节拍：内核周期性时钟中断的时间单位）），FreeRTOS 的 vTaskDelay(n) 是
"睡 n 个 tick 边界之间"，实际可能略少于 n×tick。
做精确周期都不要用相对延时：FreeRTOS 用 vTaskDelayUntil，
Zephyr 用 k_timer（见 [4.4](../04-multithreading/4.4-调度与睡眠.md)）。

**坑 2：k_mutex 不是"二值信号量的马甲"。**
FreeRTOS 里 mutex 和 binary semaphore 实现上很接近（多一个继承）。
Zephyr 的 k_mutex 是**独立对象**：可重入（同线程可多次 lock，
解锁次数要配对）、强制所有权（只能由持有者解锁）、带优先级继承。
k_sem 则没有所有权概念，谁都能 give——别拿 k_sem 当互斥锁用。

**坑 3："queue" 这个词在 Zephyr 里指别的东西。**
Zephyr 内核 API 里叫 queue 的有两个：`k_queue`（**指针**链表，
传引用不传值，和 FreeRTOS queue 语义差很远）和 legacy 的 `k_lifo/k_fifo`。
FreeRTOS queue 的真正对应物是 **k_msgq**（值拷贝 + 环形缓冲（首尾相接的数组：写指针到尾就绕回头，无需搬动数据） + 双等待名单，
对照 [02-freertos 4.1](../../../02-freertos/book-notes/04-queue-management/4.1-队列是什么.md)）。
选型时先想"传值还是传指针"，再决定 msgq 还是 queue/lifo。

## 读 Zephyr 文档时的速查心法

- 对象名一律 `k_` 前缀 + 下划线小写（k_sem、k_msgq、k_timer）；
- 操作命名多为 `k_<对象>_<动词>`（k_sem_take、k_msgq_put）；
- 超时参数统一是 `k_timeout_t`（K_NO_WAIT / K_FOREVER / K_MSEC(n)），
  全内核一套——比 FreeRTOS 每个对象各写 TickType_t 更一致；
- 找不到对应物时，多半在 k_event / k_poll / k_work 这三个
  "万能胶水"里。

## 要点回顾

1. 语义最近的一对：FreeRTOS queue ↔ Zephyr k_msgq（值拷贝环形缓冲）。
2. 三大坑：相对延时的 tick 对齐差异；k_mutex 可重入+所有权（≠二值信号量）；"queue" 在 Zephyr 指指针链表。
3. 超时统一 `k_timeout_t`；找不到的对应物去 k_event/k_poll/k_work 里找。

<details>
<summary>Q1：为什么 Zephyr 没有 task notification 的直接对应？</summary>

task notification 本质是"挂在线程身上的一格信箱"，用 TCB 内存换速度。
Zephyr 哲学是不给单个对象开"隐藏后门"：等单个事件用 k_sem，
等 32 位事件位用 k_event，等"多个对象谁先就绪"用 k_poll。
功能都覆盖，代价是多一个对象（几十字节）。

</details>

<details>
<summary>Q2：k_queue 传指针，那接收方拿到的内存归谁管？</summary>

归发送方管——k_queue 只搬指针，所有权约定靠应用自己定
（谁分配谁释放，或放回 k_mem_slab）。这正是 k_msgq 存在的理由：
不想管所有权就别传指针，让内核 memcpy（C 标准库的内存拷贝函数：把一段内存原样复制到另一处）。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| k_sleep = vTaskDelay | 都是相对延时，语义一样 | `k_sleep(K_MSEC(n))` 保证**至少睡满 n**（向上对齐 tick）；vTaskDelay 实际可能略少于 n×tick |
| k_mutex 是二值信号量的马甲 | FreeRTOS 里 mutex ≈ binary semaphore 加个继承 | k_mutex 是独立对象：可重入、强制所有权（只能持有者解锁）、带继承；k_sem 谁都能 give |
| "queue" 就是队列 | Zephyr 的 k_queue ≈ FreeRTOS 的 queue | k_queue 是**指针**链表（传引用）；FreeRTOS queue 的真正对应物是 k_msgq（值拷贝 + 环形缓冲） |
| k_queue 传的内存内核管 | 扔进队列就不用管内存了 | k_queue 只搬指针，所有权约定靠应用自己定；不想管所有权就用 k_msgq 让内核 memcpy |

## 衔接

词汇换完，剩下最大的一处世界观差异：
**优先级数字的方向，以及负数优先级的存在**。
FreeRTOS 数字越大越优先、没有负数；Zephyr 数字越小越优先、
负数还另有含义。下一篇 [2.2 优先级两个世界](2.2-优先级两个世界.md)。

## 代码自测

_注：本节代码按 Zephyr API 语义编写，未在本仓库环境实跑，仿真验证见「验证路径」。_

```c
#include <zephyr/kernel.h>

/* k_msgq：值拷贝 + 环形缓冲，FreeRTOS queue 的真正对应物 */
K_MSGQ_DEFINE(my_msgq, sizeof(int), 4, 4);   /* 元素 4 字节，容量 4，4 字节对齐 */

int main(void)
{
    int tx = 42, rx = 0;

    /* 统一超时类型 k_timeout_t：K_NO_WAIT / K_FOREVER / K_MSEC(n) */
    if (k_msgq_put(&my_msgq, &tx, K_NO_WAIT) != 0) {
        printk("队列满\n");
        return 0;
    }
    tx = 99;   /* 改发送方变量——值拷贝，队列里的 42 不受影响 */

    if (k_msgq_get(&my_msgq, &rx, K_FOREVER) == 0) {
        printk("收到 %d（发送方后来改成了 %d）\n", rx, tx);
    }

    /* 读空队列 + 超时 */
    if (k_msgq_get(&my_msgq, &rx, K_MSEC(10)) != 0) {
        printk("10ms 内没货，超时返回\n");
    }
    return 0;
}
```

**预期现象**：

- 打印 `收到 42（发送方后来改成了 99）`——值拷贝语义，发送方改值不影响队列内容；
- 打印 `10ms 内没货，超时返回`——`K_MSEC` 超时生效；
- 若换成 k_queue（指针链表），收到的就是 99——两个"queue"的语义差异一眼可见。

**验证路径**：`west build -b qemu_cortex_m3` 后 QEMU 控制台看输出；Renode 参照 10-renode 章。

**常见翻车点**：

- `K_NO_WAIT` 下队列满时 `k_msgq_put` 返回非 0，不检查返回值就悄悄丢数据；
- 对齐参数（第 4 个参数）写错会触发对齐断言/行为异常，int 填 `4`（或 `sizeof(int)` 的对齐）。
