## 这一篇讲什么

`west build` 跑完，build 目录里躺着的远不止一个 elf。
本篇按"调试时会找谁"的顺序解剖产物地图，
并把它们和 [01-stm32 ch11](../../../01-stm32/book-notes/11-linker/README.md)
学的链接器知识对上号。

## 产物地图

```
build/
├── CMakeCache.txt          ← CMake 配置缓存（板名、工具链路径都在这）
├── build.ninja             ← 实际执行的构建脚本（west build 底下是 ninja）
├── zephyr/
│   ├── zephyr.elf          ← 最终可执行镜像（调试用它）
│   ├── zephyr.hex / .bin   ← 烧录格式（flash 用它）
│   ├── zephyr.map          ← 链接 map：每个符号/段的地址与大小
│   ├── zephyr.dts          ← 合并后的最终 devicetree（板级+overlay 全展开）
│   ├── .config             ← Kconfig 求解结果全量快照
│   ├── include/generated/autoconf.h   ← 配置宏（[3.3](3.3-Kconfig怎么工作.md) 的终点）
│   └── ...（各中间目标文件、生成头文件）
└── ...
```

带 bootloader（如 MCUboot）的构建还会多一个 **merged.hex**
——把 bootloader 和应用的 hex 按各自链接地址拼成一份，
一次烧录齐活。名字即含义：merged = 多个镜像合并。
（本仓 01-hello 为单镜像构建， merged 与否取决于板级默认。）

## 按用途索引：出问题找哪个文件

| 你想知道 | 看哪里 |
|---|---|
| 我开的 CONFIG 生效了吗 | `zephyr/.config`（搜符号名） |
| 代码里 `#ifdef` 走的是哪个分支 | `include/generated/autoconf.h` |
| 我的 overlay 合进去了吗 | `zephyr/zephyr.dts`（搜节点名） |
| 某全局变量/栈被链到哪、占多大 | `zephyr/zephyr.map` |
| Flash/RAM 会不会超 | map 文件尾部统计，或 `west build -t rom_report / ram_report` |
| GDB 调试 | 喂 `zephyr/zephyr.elf`（带符号表） |
| 纯烧录 | `west flash` 自动选 hex/bin，不用手工挑 |

## 与裸机篇的对照：换汤不换药

| 01-stm32 手写 Makefile 的产物 | Zephyr build 目录对应物 |
|---|---|
| main.elf | zephyr/zephyr.elf |
| objcopy 出的 .hex/.bin | zephyr/zephyr.hex / .bin |
| -Wl,-Map 生成的 .map | zephyr/zephyr.map |
| 手写 -D 宏 | autoconf.h（自动生成了，不用 -D） |
| 手写链接脚本 .ld | 由 arch/SoC/dts 组合生成（zephyr 内部） |
| 无对应物 | zephyr.dts、.config、rom_report——平台层多出来的可观测性 |

**终点没变**：还是预处理→编译→汇编→链接那一串，
还是 .text/.rodata/.data/.bss 段布局，还是向量表在起始地址。
裸机篇的链接器知识在这里**全部有效，且是调试 map 文件的前提**。
变化是：链接脚本不再手写，由 devicetree（内存区域定义）+ Kconfig
（如代码重定位选项）共同生成——硬件数据又一次替代了手写代码
（呼应 [1.3](../01-introduction/1.3-板卡与架构.md)）。

## 重构建的三种姿势

```sh
west build -b nucleo_f103rb app        # 增量：改动最小集重编
west build -t clean                    # 清中间产物，保留配置缓存
west build -t pristine                 # 全清：下次构建从零配置开始
```

什么时候必须 pristine：改了板卡目标、改了 CMakeLists 结构、
或遇到"改了 prj.conf 但行为没变"的灵异现象——
配置缓存（CMakeCache.txt）和新输入打架时，pristine 是诚实选项。

## 要点回顾

1. 三份"真相文件"：.config（配置真相）、zephyr.dts（硬件真相）、zephyr.map（内存真相）。
2. 调试喂 elf，烧录用 hex/bin；带 bootloader 时有 merged.hex。
3. 链接本质与裸机篇一致，区别是链接脚本由 DTS+Kconfig 生成。
4. 配置灵异现象先 `west build -t pristine` 再排查。

<details>
<summary>Q1：rom_report 和直接看 map 有什么区别？</summary>

map 是链接器的原始输出（全量、按地址）；
rom_report/ram_report 是 Zephyr 后处理的**按模块/文件聚合视图**
（哪个驱动吃了多少 Flash 一目了然）。裁剪体积时先看 report 找大户，
再回 map 查具体符号。

</details>

<details>
<summary>Q2：zephyr.dts 为什么值得常看？</summary>

它是"构建系统眼中的硬件"的最终形态——板级 dts + 所有 overlay
合并展开后的结果。设备没工作、引脚不对、节点 status 没开，
先在这里确认，比在源文件堆里翻 dtsi 包含链快得多。
ch09 会把它当主力调试工具。

</details>
