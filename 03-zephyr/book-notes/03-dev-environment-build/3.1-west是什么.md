## 这一篇讲什么

west 是 Zephyr 的"大管家"（meta-tool）：源码它克隆、构建它发起、
烧录和调试它代劳。本篇回答两个问题：
**west 为什么存在（它解决的到底是什么问题），
以及日常四条命令（build/flash/debug/menuconfig）底下各是谁在干活。**

## 为什么需要 west：Zephyr 不是一个仓库

[1.2](../01-introduction/1.2-内核vs平台.md) 说过 Zephyr 是平台——
平台的源码天然分裂：内核主线一个仓库，HAL 一个，MCUboot 一个，
TF-M、协议栈、lvgl…… 各是各的仓库。谁来把它们按**正确的版本组合**
摆到正确的目录？这就是 west 的第一职责。

```
zephyr 仓库里的 west.yml（manifest）说：
  需要 modules/hal/stm32 @ 某 commit
  需要 bootloader/mcuboot @ 某 tag
  ……

west init  -m <zephyr仓库> myws   ← 建工作区，克隆 manifest 仓库
west update                       ← 按 west.yml 把所有模块摆到位
```

对照经验：

- 像 git submodule，但 manifest 是**数据文件**，组合/裁剪比重嵌套仓库灵活；
- 像 Python 的 venv + pip，但管的是 C 源码树的版本组合；
- LDD- 侧没有对应物——Linux 内核是单仓库文化，Zephyr 是多仓库文化。

## 日常命令链：west 是壳，别人是芯

| 命令 | west 实际转交给谁 | 干什么 |
|---|---|---|
| `west build -b nucleo_f103rb app` | **CMake + Ninja** | 配置（Kconfig+DTS 展开）并编译 |
| `west flash` | 板卡对应的 runner（openocd / pyocd / jlink / nrfjprog…） | 按 boards/<板>/board.cmake 选定的工具烧录 |
| `west debug` | 同上 + GDB | 起 openocd 等服务端并挂上 gdb |
| `west build -t menuconfig` | CMake → kconfig 前端 | 图形化改配置（[3.3](3.3-Kconfig怎么工作.md)） |

要点：**west 自己几乎什么都不实现**——
构建是 CMake，烧录是 openocd 们，配置是 Kconfig 前端。
west 的价值是"知道每个命令在这个板子上该调用谁、带什么参数"。
这套 runner 机制意味着：换 ST-Link 为 J-Link，命令不变。

## 与本仓 01-stm32 手写 Makefile 的对照

[01-stm32](../../../01-stm32/book-notes/README.md) 里我们手写 Makefile：
arm-none-eabi-gcc 编译、ld 链接、objcopy 出 hex、openocd 烧录——
每一步自己调。west build 干的是**同一串事**，只是：

| 01-stm32 手写 | Zephyr/west |
|---|---|
| Makefile 里列源文件 | CMakeLists.txt 里 `target_sources(app ...)` |
| 手写 -mcpu=cortex-m3 等 flags | 板卡/SoC 的 Kconfig 与 CMake 片段自动注入 |
| 手写链接脚本路径 | 内核按 arch/SoC/dts 生成/选取 |
| openocd -f 手写 cfg | `west flash` 按板级 board.cmake 选 runner |
| 预处理宏自己 -D | Kconfig 生成 autoconf.h（[3.3](3.3-Kconfig怎么工作.md)） |

**编译链接的本质没变**——终点还是
[01-stm32 ch11](../../../01-stm32/book-notes/11-linker/README.md) 学的
段布局和链接脚本；变的是"谁生成这串命令"。
裸机篇学的是原理，这一章学的是**自动化这套原理的工业装置**。

## 原书怎么说 / 实际是什么

| 原书（Eliasz 2024） | 实际（官方文档语义） |
|---|---|
| 以 `west init` 拉完整 zephyrproject 工作区开局 | 仍正确；另可选择只装应用自身 manifest 的"application manifest"模式，工作区更瘦 |
| 烧录示例以特定 runner 为例 | runner 由板级 board.cmake 决定，同一块板可用 `west flash -r <runner>` 临时换 |

## 要点回顾

1. west 是 meta-tool：manifest（west.yml）管多仓库组合，命令扩展管构建/烧录/调试的转发。
2. 它自己不实现：构建=CMake/Ninja，烧录=openocd 系 runner，配置=Kconfig。
3. 与裸机 Makefile 同一串编译链接，只是生成者从"你"变成了"构建系统"。
4. 换调试器/烧录器不改命令——runner 机制把工具差异吸收在板级。

<details>
<summary>Q1：west 和 git submodule 能互相替代吗？</summary>

功能重叠 80%。west 赢在：manifest 可继承（应用可再定义自己的 west.yml
叠加模块）、可选择性检出、与 build/flash 命令一体。
submodule 赢在与 git 原生工具链无缝。Zephyr 选了 west，
你的私有项目两者都行——但用了 Zephyr 就等于默认用 west。

</details>

<details>
<summary>Q2：west update 会动我的源码吗？</summary>

它只检出 manifest 里列的模块仓库到指定版本。
**你自己应用仓库它不动**；但如果你在某个模块仓库里有未提交改动，
update 切版本时会冲突——模块仓库当只读依赖用，改动走 fork + manifest 指向。

</details>
