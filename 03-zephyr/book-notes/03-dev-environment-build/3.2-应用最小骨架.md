## 这一篇讲什么

一个能 `west build` 的 Zephyr 应用，最少只需要**三个文件**。
本篇把骨架摆出来、逐个文件讲职责，再解释构建系统怎么把
"应用 + 板卡 + 内核"三方输入合成一个镜像。

## 最小骨架

```
app/
├── CMakeLists.txt      ← 构建入口：我是谁、我有哪些源文件
├── prj.conf            ← Kconfig 片段：我要哪些内核功能
└── src/
    └── main.c          ← 应用代码
```

可选但常见：`app.overlay`（devicetree overlay，在板级 dts 上改/加硬件描述）、
`boards/nucleo_f103rb.overlay`（只对某板生效，按板名匹配）、
`Kconfig`（应用自定义配置符号，有自定义 CONFIG 才需要）。

## 三个文件逐个看

**CMakeLists.txt**——套路化到可以背：

```cmake
cmake_minimum_required(VERSION 3.20.0)
find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})   # 把内核构建系统拉进来
project(my_app)                                          # 必须在 find_package 之后
target_sources(app PRIVATE src/main.c)                   # 源文件挂到 app 目标
```

三行角色：①找到 Zephyr 的 CMake 包（它定义了 `app` 目标，工具链选择也藏在这里）；
②声明工程；③挂源文件。**顺序不能动**——`project()` 在 find_package 之后是硬要求。

**prj.conf**——Kconfig 片段，逐行 `CONFIG_XXX=y`（如 `CONFIG_GPIO=y`）。
它不是"配置文件被读取"那么简单：这些行会**并入整棵 Kconfig 依赖树**
求解（依赖自动补全、冲突会报错），结果生成 autoconf.h。机制见 [3.3](3.3-Kconfig怎么工作.md)。

**main.c**——唯一没规矩的文件。`main()` 是应用的入口，
但它不是"第一行代码"：内核初始化、静态线程创建都发生在 main 之前
（[4.5 系统线程](../04-multithreading/4.5-系统线程.md)）。

## overlay：改硬件描述不动板级文件

devicetree 的分层（细节归 [ch09](../09-devicetree/README.md)）：

```
SoC dtsi（STM32F103 有什么外设）
   ↓ 被包含
板级 dts（nucleo_f103rb 启用了哪些、引脚怎么接、led0 在哪）
   ↓ 叠加
app.overlay（应用自己的改动：换个引脚、加个传感器节点）
```

overlay 的语法就是 dts 语法，构建时被**合并**到板级树上。
典型动机：板子不变，但你在某个排针上接了块传感器小板——
不为这点事去 fork 板级 dts。这也是"自制板原型期"的偷懒方案
（[1.3 Q1](../01-introduction/1.3-板卡与架构.md)）。

## 构建时的三方合成

```
west build -b nucleo_f103rb app
        │
        ├─ 应用输入：CMakeLists.txt + prj.conf + *.overlay
        ├─ 板卡输入：boards/st/nucleo_f103rb/{Kconfig, defconfig, dts}
        └─ 内核输入：Kconfig 依赖树 + 驱动/子系统源码
        │
        ▼
   CMake 配置阶段：Kconfig 求解 → autoconf.h；DTS 合并 → 生成头文件
        ▼
   Ninja 编译链接 → zephyr.elf（产物解剖见 [3.4](3.4-构建产物解剖.md)）
```

**为什么 Zephyr 工程不该手写顶层 Makefile**：三方输入的合并逻辑
（Kconfig 依赖求解、DTS 包含与 overlay、按配置裁剪编译单元）
全部实现在 Zephyr 的 CMake 模块里。手写 Makefile 等于重写这套逻辑——
裸机篇手写 Makefile 是为了学原理，到了 Zephyr 就别和工业装置较劲。

## 要点回顾

1. 最小骨架三文件：CMakeLists.txt（挂源码）、prj.conf（选功能）、main.c。
2. `find_package(Zephyr ...)` 拉入整个内核构建系统；`project()` 必须在它之后。
3. overlay 在板级 dts 上叠加应用的硬件改动，不动板级文件。
4. 构建 = 应用/板卡/内核三方输入的合成；手写顶层 Makefile 是在重写这套合成逻辑。

<details>
<summary>Q1：多个 .c 文件怎么加？</summary>

`target_sources(app PRIVATE src/a.c src/b.c)` 一行列全，
或分多次调用。子目录有独立 Kconfig/源码组织时，
用 `add_subdirectory()` + 子目录自己的 CMakeLists。

</details>

<details>
<summary>Q2：prj.conf 和 boards/xxx.conf 同时存在，谁赢？</summary>

合并，且**更具体的赢**：应用级 boards/<板>.conf 只对该板生效，
与 prj.conf 冲突时以板级 conf 为准（它更靠近"最终目标"）。
同类优先级还有 defconfig（板卡出厂默认）在最底层。

</details>
