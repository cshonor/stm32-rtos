## 这一篇讲什么

`prj.conf` 里一行 `CONFIG_GPIO=y`，到代码里 `#ifdef CONFIG_GPIO`，
中间隔了一整套 Kconfig 求解过程。本篇把这条链路讲透，
再说 menuconfig 里真正值得看的东西。

## 一条链：从文本行到预处理宏

```
prj.conf ──┐
板级 defconfig ──┼── 合并（prj.conf 覆盖 defconfig）──► .config ──► autoconf.h
Kconfig 依赖树 ──┘        （依赖求解：select/depends on）        （C 头文件）
```

三步各干什么：

1. **合并**：板卡的 defconfig 先铺底（这块板的合理默认），
   prj.conf 在其上覆盖/新增（更具体的板级 conf 优先，见 [3.2](3.2-应用最小骨架.md)）；
2. **求解**：Kconfig 不是简单的 key=value——每个符号有类型（bool/int/string）、
   依赖（`depends on`）和联动（`select`）。你写 `CONFIG_X=y`，
   求解器可能自动带上 Y、Z，也可能因依赖不满足**静默丢弃你的设置**
   （新手最大坑，menuconfig 里可查证）；
3. **生成**：求解结果落到 build 目录的 `.config`（全量快照），
   再转成 `autoconf.h`——每个符号变一个 `#define CONFIG_XXX 1`
   （或数值/字符串），被全内核 #include。

代码侧消费方式：

```c
#include <autoconf.h>   /* 通常由 zephyr 头文件链带入，不用显式写 */
#if defined(CONFIG_GPIO)
/* GPIO 相关代码 */
#endif
#define MY_BUF_SIZE CONFIG_MAIN_STACK_SIZE   /* int 型符号直接当常量用 */
```

## 与 FreeRTOSConfig.h 的对照

| | FreeRTOS | Zephyr |
|---|---|---|
| 配置文件 | FreeRTOSConfig.h（一个头文件） | prj.conf + 分层 conf |
| 符号规模 | 几十个 | **几千个** |
| 依赖关系 | 无（每个宏独立） | 依赖树自动求解 |
| 改法 | 手改头文件 | prj.conf 或 menuconfig |
| 冲突检测 | 编译期 #error 或运行时才发现 | 求解期报 warning/error |

规模差两个数量级——因为 Zephyr 的 Kconfig 不只配内核，
还配驱动、协议栈、子系统（[1.2](../01-introduction/1.2-内核vs平台.md) 全家桶每层都从这里裁剪）。
这正是"平台"的配置面。

## menuconfig 看什么

```sh
west build -t menuconfig
```

值得养成的三个习惯：

1. **按 `/` 搜索符号**：搜符号名即见依赖链，比翻文档快；
2. **看符号的 "Depends on"**：prj.conf 写了却没生效，九成是依赖没满足；
3. **退出保存只影响本次 build 目录**：持久配置必须落回 prj.conf，
   否则 pristine 构建后配置丢失。

## 原书怎么说 / 实际是什么

| 原书（Eliasz 2024） | 实际（官方文档语义） |
|---|---|
| 示例以 `west build -t menuconfig` 进图形界面 | 仍正确；另有 `west build -t guiconfig`（Qt 界面），CI/无图形环境用命令行 conf 文件更稳 |
| 提到直接编辑 build/zephyr/.config 调试 | 可作临时手段，但任何重新配置（cmake 重跑）都可能覆盖它；改 prj.conf 才是正路 |

## 与 LDD- 侧的直通关系

这套机制**就是 Linux 内核的 Kconfig**：
同样的 Kconfig 语言、同样的 menuconfig 界面、同样的
`.config → autoconf.h` 链路。在 Zephyr 里练熟，
LDD- 侧配内核零迁移成本——这是"第二遍学"的最大红利之一
（[1.1](../01-introduction/1.1-Zephyr家谱.md)）。

## 要点回顾

1. 链路：prj.conf + defconfig 合并 → Kconfig 依赖树求解 → .config → autoconf.h。
2. 求解器会 select 联动、会因依赖不满足静默丢弃——写了不生效先查依赖。
3. menuconfig 三板斧：`/` 搜索、看 Depends on、持久化回 prj.conf。
4. 与 Linux 内核同一套机制，技能直通 LDD- 侧。

<details>
<summary>Q1：autoconf.h 里每个符号都有吗，包括没开启的？</summary>

开启的生成 `#define CONFIG_X 1`（或值）；**未开启的不生成**
（早期内核风格会生成 `#undef`，Zephyr 现行是不出现）。
所以代码里要用 `#if defined(CONFIG_X)` / `IS_ENABLED(CONFIG_X)`
判断，不能指望它总有定义。

</details>

<details>
<summary>Q2：怎么给我的应用加自定义 CONFIG 选项？</summary>

在应用目录写 Kconfig 文件定义符号（`config MY_FEATURE` …），
CMakeLists 同级会被构建系统自动拾取（或显式 `KCONFIG_ROOT` 指定）。
然后 prj.conf 里就能 `CONFIG_MY_FEATURE=y`——
和内核符号走完全相同的求解链。

</details>
