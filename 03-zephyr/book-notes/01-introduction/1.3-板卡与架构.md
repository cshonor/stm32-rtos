# 1.3 支持的板卡与架构：为什么"换板不改应用"是设计目标

> 上一篇：[1.2 内核 vs 平台](1.2-内核vs平台.md) ｜ 章导航：[README](README.md)
>

## 这一篇讲什么

Zephyr 主线支持的板卡数以百计、架构覆盖 ARM/x86/RISC-V/Xtensa/ARC 等。
"多"本身不是重点，重点是它把"换板"从**移植工程**压缩成了**一个构建参数**。
本篇讲这件事靠什么机制成立，以及它的边界在哪里。

## 换板的理想形态

```sh
west build -b nucleo_f103rb app     # 编给 F103
west build -b nrf52840dk_nrf52840 app   # 同一份 app，编给 nRF52840
```

应用源码一行不改。之所以可能，是因为应用**从不直接引用硬件**，
只引用 devicetree 里的逻辑名字：

```c
const struct gpio_dt_spec led = GPIO_DT_SPEC_GET(DT_ALIAS(led0), gpios);
/* led0 是哪个口、哪个引脚——由板级 dts 回答，不由应用回答 */
```

硬件差异被三层吸收掉：

| 层 | 负责吸收的差异 | 例子 |
|---|---|---|
| 架构层（arch/） | CPU 核差异 | Cortex-M3 vs RISC-V 的上下文切换、异常入口 |
| SoC/板层（soc/、boards/） | 外设布局差异 | LED 在 PA5（F103）还是 P0.13（nRF52） |
| 驱动模型 | 外设操作差异 | `gpio_pin_set_dt()` 底下走 STM32 还是 Nordic 驱动 |

应用站在三层之上，只看到 `led0` 这个别名。
devicetree 的细节是 [ch09](../09-devicetree/README.md) 的主场，这里先记住结论：
**硬件描述是数据（dts），不是代码——所以换硬件不用改代码。**

## 为什么这是"设计目标"而不是副产品

1. **生态对齐**：厂商想让自己的板子进主线，就必须按驱动模型/devicetree
   规范贡献支持——规范是强制的入口条件（呼应 [1.1](1.1-Zephyr家谱.md) 的治理）；
2. **应用可复用**：samples/ 目录里几百个示例能在大半板卡上直接编过，
   靠的就是别名/统一 API 这层抽象；
3. **测试规模化**：同一份应用逻辑可在 renode/QEMU 模拟目标上跑 CI
   （见 [ch10](../10-renode/README.md)），没有这层抽象做不到。

## "换板不改应用"的诚实边界

| 情况 | 还能不改吗 |
|---|---|
| 应用只用了通用子系统（GPIO/UART/log） | 基本真能不改 |
| 用到板子特有外设（某 SoC 独有的 PWM 模式） | 要动应用或写 overlay |
| 资源差异（目标板 RAM 装不下） | 改 Kconfig 裁剪，应用可能也要瘦身 |
| 协议栈能力差异（目标板无 BLE 射频） | 直接不成立——抽象不能凭空造硬件 |

一句话：**它消灭的是"接线层"的差异，消灭不了"能力层"的差异。**

## 与裸机/FreeRTOS 侧对照

[01-stm32](../../../01-stm32/book-notes/README.md) 里换块板意味着什么？
改 Makefile 的 -mcpu、改引脚宏、改链接脚本、重新对一遍时钟树——
每一项都是代码改动。FreeRTOS 侧同理：内核本身不管硬件，
`FreeRTOSConfig.h` 之外全是板级手工活。

Zephyr 把这些全部收进 boards/<板名>/ 目录（dts + Kconfig + defconfig），
"板卡支持包"从一堆约定俗成的代码，变成了**一份标准化的数据描述**。

| 裸机/FreeRTOS 换板 | Zephyr 换板 |
|---|---|
| 改代码、改 Makefile | 改 `-b` 参数 |
| 引脚定义散落各 .h | 集中在板级 dts |
| 时钟/外设初始化手写 | 驱动模型按 dts 自动初始化 |

## 要点回顾

1. 应用只引用 devicetree 逻辑名（如 `led0`），硬件差异由 arch/SoC/board 三层吸收。
2. "换板不改应用"是设计目标：靠厂商贡献规范 + 统一 API + 可模拟 CI 维持。
3. 边界诚实：消灭接线层差异，消灭不了能力层差异（资源、射频、特有外设）。
4. 对照裸机篇：板级支持从"一堆代码"变成"一份数据（dts）"。

<details>
<summary>Q1：我的自制板子不在支持列表里怎么办？</summary>

写一个自己的 board 目录（dts + Kconfig.defconfig + defconfig），
或在应用里用 overlay 就近改一块现成板子的 dts。
前者是"正式移植"，后者是"原型期偷懒"——overlay 见
[3.2 应用骨架](../03-dev-environment-build/3.2-应用最小骨架.md)。

</details>

<details>
<summary>Q2：几百块板卡的支持，质量都一样吗？</summary>

不一样。支持是厂商和社区贡献的，成熟度参差：Nordic/NXP 主力板
覆盖最全，冷门板可能缺个别驱动。选型时先在官方板卡页查该板的
peripheral 支持表，别假设"在列表里=全功能"。

</details>
