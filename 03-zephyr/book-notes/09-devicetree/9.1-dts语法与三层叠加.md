## 这一篇讲什么

Devicetree 一句话：**把"硬件长什么样"从 C 代码里抽出来写成独立文本，
构建系统读它生成头文件，驱动按它自报家门。** 它源自 Linux（更早是
OpenFirmware），Zephyr 用同一套语法理念，工具链从 dtc 换成自家 Python 实现。

## 为什么需要它：对照 01-stm32 的手写法

在 [01-stm32](../../../01-stm32/book-notes/04-numbers-and-bitops/4.12-用位操作控制内存映射IO寄存器.md)
里点亮 LED：

```c
#define GPIOA_BASE  0x40010800UL   /* 基址：查参考手册；CRH 等寄存器 = BASE + 偏移 */
```

**本质就是"基址 + 偏移"**，换板时这串数字散落在几十个文件里。DT 把它**声明化**：

```
gpioa: gpio@40010800 {
    compatible = "st,stm32-gpio";
    reg = <0x40010800 0x400>;      /* 基址 + 长度：还是那两个数，但只写一次 */
    status = "okay";
};
```

换板 = 换一份 dts，应用代码一行不动。

## 最小语法：节点与四属性

```
/ {                                  /* 根节点 */
    soc {
        spi1: spi@40013000 {         /* "标签: 名字@单元地址" */
            compatible = "st,stm32-spi";   /* 匹配驱动的钥匙 */
            reg = <0x40013000 0x400>;      /* 基址 + 长度 */
            interrupts = <35 5>;           /* IRQ 号 + 优先级 */
            status = "okay";               /* 使能开关 */
        };
    };
};
```

四属性分工：compatible ≈ C 的"类型名"（绑定 binding yaml）；reg ≈ 手写法的 BASE 宏；
interrupts ≈ NVIC 号；status 是编译期 if 0——**`status = "disabled"` 的节点在
构建产物里什么都不留**：SoC dtsi 默认全 disabled，板级 dts 只 okay 实际用到的。

## 三层叠加：.dtsi → 板级 .dts → app.overlay

```
SoC 级 dtsi（芯片手册机器可读版，外设默认 disabled）
  → 板级 dts（#include dtsi；okay 板载外设，写 aliases/chosen）
  → 应用 app.overlay（工程目录，追加新节点/覆盖同名属性）
  → 合并：zephyr.dts → devicetree_generated.h
```

叠加规则：**后写的赢**——overlay 里 `&usart2 { current-speed = <115200>; };`
即覆盖板级定义；`&label` 引用既有节点。

## Zephyr 的两个开关节点：aliases 与 chosen

```
aliases {
    led0 = &green_led_1;        /* 通用名 → 具体节点：应用 DT_ALIAS(led0) */
};
chosen {
    zephyr,console = &usart2;   /* printk/shell 用哪个 UART：内核子系统自己读 */
};
```

samples/basic/blinky 能在几百块板上不改代码编译，全靠 `led0` 约定；
换调试口只改 chosen 一行——Zephyr 可移植性的两个总开关。

## 与 Kconfig 的分工

| | DT | Kconfig |
|---|---|---|
| 回答 | **有什么**（硬件客观存在） | **编什么**（软件功能取舍） |
| 产物 | devicetree_generated.h | autoconf.h |
| 改 UART 波特率 | overlay 改 `current-speed` | 不管 |
| 要不要 UART 驱动/printk | 看 status | CONFIG_SERIAL / CONFIG_PRINTK |

一句话：**DT 描述世界，Kconfig 决定你对世界的态度**——okay 了 spi1 却忘开
CONFIG_SPI=y，驱动照样不进固件。

## 要点回顾

1. Devicetree = 硬件描述声明化：手写"基址+偏移"收敛到一份文本，换板只换 dts。
2. 最小四属性 compatible/reg/interrupts/status；disabled 的节点什么都不留。
3. 三层叠加 dtsi→dts→overlay，后写的赢；产物 devicetree_generated.h。
4. DT 管"有什么"，Kconfig 管"编什么"，两个都要对驱动才真的进固件。

<details>
<summary>Q1：dtc 编译器在 Zephyr 里还用吗？</summary>

主流程**不用**——Zephyr 用自家 Python 库（scripts/dts/）直接解析
dts + binding yaml，生成头文件和合并后的 zephyr.dts；dtc 只在需要 .dtb
二进制 blob 的少数场景出场。这与 Linux（dtc 是刚需）是实际的工具链差异。

</details>

<details>
<summary>Q2：binding yaml 是什么角色？</summary>

每个 compatible 对应一份 bindings yaml，声明该节点允许/必须有哪些属性、
各是什么类型。dts 里写了不允许的属性，**构建期直接报错**——
相当于给 dts 加了 schema 校验，手写寄存器时代这类错误要到运行时才炸。

</details>
