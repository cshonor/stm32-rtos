## 这一篇讲什么

上一篇说 dts 最终变成 `devicetree_generated.h` 里一堆宏。
这一篇讲怎么用**三层读法**把它们捞出来，
以及设备模型怎么把"节点"变成"可调用的 `struct device`"。

## 第一层：拿到节点（node identifier）

| 宏 | 入参 | 适用 |
|---|---|---|
| `DT_ALIAS(led0)` | aliases 里的通用名 | **应用首选**——换板不改代码 |
| `DT_NODELABEL(gpioa)` | 节点标签（`gpioa:`） | 芯片/板上确定存在的东西 |
| `DT_PATH(soc, spi_40013000)` | 完整路径 | 没标签/别名时的兜底 |

三者产出同一种"节点标识" token，拼进后续宏用。
可移植性纪律：**能用 DT_ALIAS 就别用 DT_NODELABEL**——
别名是板级 dts 的"公共接口"，nodelabel 是 SoC 实现细节。

## 第二层：读属性（DT_PROP / DT_REG / DT_IRQ …）

```c
#define SPI1 DT_NODELABEL(spi1)

DT_REG_ADDR(SPI1)              /* 0x40013000 —— 就是 01-stm32 里的 BASE */
DT_PROP(SPI1, clock_frequency) /* 属性名连字符 → 下划线 */
DT_IRQN(SPI1)                  /* 中断号 */
DT_NODE_HAS_STATUS(SPI1, okay) /* 编译期判节点是否使能：1/0 */
```

`DT_NODE_HAS_STATUS` 是写"节点缺席也能编译"的钥匙：

```c
#if DT_NODE_HAS_STATUS(DT_ALIAS(led0), okay)
    /* 有 LED 的板子才编这段 */
#endif
```

## 第三层：复合属性打包（GPIO_DT_SPEC_GET 等）

GPIO 属性不是一个数，而是一组（控制器 + 引脚 + 标志），
`*_DT_SPEC_GET` 一次性打包成结构体：

```c
static const struct gpio_dt_spec led =
    GPIO_DT_SPEC_GET(DT_ALIAS(led0), gpios);
/* led = { .port = <gpioa 设备>, .pin = 5, .dt_flags = GPIO_ACTIVE_HIGH } */

gpio_pin_configure_dt(&led, GPIO_OUTPUT_ACTIVE);
gpio_pin_toggle_dt(&led);
```

这一行宏**依次经过**：DT_ALIAS 定位节点 → 解 gpios 的 phandle 找控制器 →
抽 pin 号和 flags → 填 `gpio_dt_spec`。
同族：`PWM_DT_SPEC_GET`、`SPI_DT_SPEC_GET`、`I2C_DT_SPEC_GET`、`ADC_DT_SPEC_GET`。

## 第四层：节点变设备（DEVICE_DT_GET）

`status="okay"` 且驱动匹配的节点，构建期生成 `struct device`：

```c
const struct device *spi_dev = DEVICE_DT_GET(DT_NODELABEL(spi1));
if (!device_is_ready(spi_dev)) { /* 驱动 init 失败 */ }
```

对照 Linux：`DEVICE_DT_GET` ≈ `of_find_device_by_node`，
但 Zephyr 版**编译期静态生成**、无运行时遍历——
"能静态不动态"的审美，与 [4.2](../04-multithreading/4.2-创建线程两法.md)
说的 `__initcall` 式宏注册同源（驱动侧对称宏是 `DEVICE_DT_INST_DEFINE`）。

## 原书怎么说 / 实际是什么

| 原书怎么说 | 实际是什么（Zephyr 3.x） |
|---|---|
| `DT_GPIO_LABEL(...)` 读控制器名再 `device_get_binding` | 现行 `GPIO_DT_SPEC_GET` 打包 + `gpio_*_dt` 系列，`device_get_binding` 不再是 GPIO 必要步骤 |
| 用 `DT_INST_0_...` 读实例属性 | 语义仍在，但应用层优先别名/nodelabel；`DT_INST` 族留给驱动内部 |

原则：**书里的 DT 宏编译不过，先去官方 Devicetree API 页查现行拼写。**

## 要点回顾

1. 三层读法：定位节点（ALIAS > NODELABEL > PATH）→ 读属性（PROP/REG/IRQ）→ 复合属性 `*_DT_SPEC_GET` 打包。
2. `GPIO_DT_SPEC_GET(DT_ALIAS(led0), gpios)` = 定位别名 → 解 phandle → 填 {port, pin, flags}。
3. okay + 驱动匹配 → 编译期生成 `struct device`，`DEVICE_DT_GET` 取指针。
4. 节点可能缺席时用 `DT_NODE_HAS_STATUS` 编译期分支。

<details>
<summary>Q1：DT_PROP 读不存在的属性会怎样？</summary>

编译期报错——这正是 devicetree 的价值：手写宏时代"地址抄错"运行时炸，
DT 时代"属性缺失"编译期炸。想让属性可缺席，用 `DT_PROP_OR(node, prop, default)`。

</details>

<details>
<summary>Q2：DT 宏为什么全是编译期 token 拼接、不用函数？</summary>

devicetree_generated.h 里全是纯文本 #define，DT 宏族做的是把节点标识
映射到这些名字。**零运行时开销**：DT_REG_ADDR 展开就是立即数，
和手写 `#define SPI1_BASE 0x40013000` 产出的机器码一模一样。

</details>
