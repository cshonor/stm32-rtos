## 这一篇讲什么

收尾篇，干两件事：**① Zephyr dts 与 Linux dts 逐面对照**——
语法同源但工具链、消费方式、运行时机全不同，别把 Linux 的经验直接搬；
**② 回到 01-stm32 的手写寄存器**，说清三种"描述硬件"的方式本质是同一件事的三个抽象层级。

## Zephyr vs Linux：同一语法，两个世界

| 面 | Linux | Zephyr |
|---|---|---|
| 解析工具 | dtc → .dtb 二进制 | 自家 Python 库 → devicetree_generated.h |
| 产物形态 | Flash 里的二进制 blob | C 头文件（纯宏） |
| 解析时机 | **内核启动时**解析 dtb | **编译时**全部展开成宏 |
| 运行时开销 | 有（遍历设备树建 device_node） | **零**——宏展开即立即数 |
| 驱动匹配 | of_match_table 字符串比较 | DT_DRV_COMPAT，编译期绑定 |
| 设备创建 | 运行时 platform_device 注册 | 编译期 DEVICE_DT_INST_DEFINE 静态生成 |
| overlay | 运行时动态叠加（需内核支持） | **编译期**文本叠加，无运行时概念 |
| 删改硬件 | 换 dtb 不重编内核 | 必须重新编译固件 |

一句话：**Linux 把设备树当"运行时数据库"，Zephyr 把它当"代码生成器的输入"。**
同一个 .dts 文件，在两边走向完全相反的路线。
Zephyr 的选择是 MCU 资源约束下的必然——F103 的 20K RAM 养不起
运行时解析器，而编译期展开后 DT_REG_ADDR 就是一个立即数。

## 三种描述硬件的方式：同一事实的三个抽象层级

回到本仓的第一性原理。点亮 PA5 这颗 LED，三个时代各怎么写：

```c
/* 时代一：01-stm32 手写（见 4.12 用位操作控制内存映射IO寄存器） */
#define GPIOA_BSRR (*(volatile uint32_t *)(0x40010800UL + 0x10))
GPIOA_BSRR = (1U << 5);
```

```
/* 时代二：Zephyr dts 声明 */
gpioa: gpio@40010800 {
    compatible = "st,stm32-gpio";
    reg = <0x40010800 0x400>;
    status = "okay";
};
```

```c
/* 时代三：应用只认别名 */
gpio_pin_set_dt(&led, 1);
```

| | 时代一 手写宏 | 时代二 dts | 时代三 别名+API |
|---|---|---|---|
| 硬件事实在哪 | 散落的 #define | 一份 dts 集中声明 | 板级 dts 的 aliases |
| 换板成本 | 全局搜索替换 | 换 dts | **零** |
| 出错时机 | 运行时（地址抄错） | 编译期（binding 校验） | 编译期 |
| 本质 | 基址+偏移 | **还是基址+偏移，只是声明化** | 对声明的引用 |

关键在最后一行：**dts 没有发明任何新东西**——`reg = <0x40010800 0x400>`
里那两个数，和你手写 `#define GPIOA_BASE 0x40010800` 是同一对手册里的数。
改变的是：事实只写一次、编译期校验、消费方与细节解耦。

## 什么时候不必用 dts

dts 不是银弹，本仓场景下要诚实：

- **一次性学习实验**（01-stm32 全部）：手写地址**教学价值更高**——
  你必须亲手查手册、算偏移，才知道 0x40010800 不是魔法数；
- **单板单应用、永不移植**：dts 的抽象税（学语法、查 binding、看产物）可能不划算；
- **调硬件时**：示波器上的问题，最终还是要回落到"基址+偏移+示波器"层面——
  dts 层看不出 PA5 上实际有没有波形。

这就是为什么本仓的顺序是**先 01-stm32 手写，再 03-zephyr 声明**：
不知道 dts 替你封装了什么，dts 出错时你就只能干瞪眼。

## 要点回顾

1. Linux 把 dts 当运行时数据库（dtc + dtb + 启动解析），Zephyr 当代码生成器输入（Python 解析 + 编译期宏展开，零运行时开销）。
2. dts 的 `reg = <基址 长度>` 和手写 BASE 宏是同一事实——dts 只是把它声明化、集中化、编译期校验化。
3. 学习路径上必须先经历手写时代：dts 封装的是"基址+偏移"，不懂封装内容就无法调试。

<details>
<summary>Q1：Zephyr 的 dts 文件能直接拿去给 Linux 用吗？</summary>

语法兼容（都能被 dtc 编译），语义**不能直接移植**：
两边的 binding 命名空间、属性约定（如 Zephyr 的 pinctrl 引用方式、
chosen 节点键名）各有演进。实际工程中同一芯片家族要在两边各维护一套，
厂商（如 ST）会尽量同步，但"一份 dts 两边吃"不是现实。

</details>

<details>
<summary>Q2：devicetree_generated.h 可以手写修改吗？</summary>

不可以也不必要——每次构建重新生成，手改会被覆盖。
想改硬件描述，永远回到源头：改 dtsi/dts/overlay，
然后**看生成产物验证**（build/zephyr/zephyr.dts）。
"生成文件只读"是调试 dts 问题的第一条纪律。

</details>
