## 这一篇讲什么

收尾篇，干两件事：**① Zephyr dts 与 Linux dts 逐面对照**——
语法同源但工具链、消费方式、运行时机全不同，别把 Linux 的经验直接搬；
**② 回到 01-stm32 的手写寄存器**，说清三种"描述硬件"的方式本质是同一件事的三个抽象层级。

## 先用人话说一遍（新手铺垫）

同一份 .dts 语法，Linux 和 Zephyr 的"吃法"完全相反，不理解这一点
就会把一边的经验错搬到另一边。类比同一份菜单的两种餐厅：
**Linux 是现点现做的餐厅**——菜单（dtb）随食客进门才翻开，
厨师现场读、现场配菜（内核启动时解析设备树、动态注册设备）；
灵活，换个菜单不用重盖厨房，但前厅后厨都得养着一批人（运行时开销）。

**Zephyr 是预制菜工厂**——菜单在生产前就被翻译成料理包上的
印刷指令（编译期展开成宏），出厂后没有"读菜单"这个环节：
`DT_REG_ADDR(SPI1)` 展开就是一个数字常量，零运行时开销。
代价是改菜必须回厂重印（改 dts 必须重新编译）。
F103 的 20K RAM 决定了只能选后者——这就是对照表每一行差异的总根源。

本篇下半场的"三个时代"则是本仓的压舱石：手写宏、dts 声明、
别名+API 写的是**同一个硬件事实**，抽象层级逐级上升。
先爬过手写时代再看 dts，你才知道 dts 出错时该往哪层挖。

| 术语 | 一句话解释 |
|---|---|
| dtb | devicetree 的二进制形态：dtc 编译产物，Linux 内核启动时读它 |
| 运行时解析 | Linux 的方式：内核启动过程中遍历设备树、现场创建设备对象 |
| platform_device | Linux 里由设备树节点动态注册出来的设备对象 |
| of_match_table | Linux 驱动里的 compatible 字符串表：内核靠它把节点匹配给驱动 |
| 代码生成器 | Zephyr 的方式：构建期把 dts 翻成 C 宏头文件，编译后无任何"解析"环节 |

## Zephyr vs Linux：同一语法，两个世界

| 面 | Linux | Zephyr |
|---|---|---|
| 解析工具 | dtc → .dtb 二进制 | 自家 Python 库 → devicetree_generated.h |
| 产物形态 | Flash 里的二进制 blob（一整块当原始数据用的二进制，没人再细看内部） | C 头文件（纯宏） |
| 解析时机 | **内核启动时**解析 dtb | **编译时**全部展开成宏 |
| 运行时开销 | 有（遍历设备树建 device_node（Linux 里对应树上每个硬件节点的运行时对象）） | **零**——宏展开即立即数 |
| 驱动匹配 | of_match_table 字符串比较 | DT_DRV_COMPAT，编译期绑定 |
| 设备创建 | 运行时 platform_device 注册 | 编译期 DEVICE_DT_INST_DEFINE 静态生成 |
| overlay | 运行时动态叠加（需内核支持） | **编译期**文本叠加，无运行时概念 |
| 删改硬件 | 换 dtb 不重编内核 | 必须重新编译固件 |

一句话：**Linux 把设备树当"运行时数据库"，Zephyr 把它当"代码生成器的输入"。**
同一个 .dts 文件，在两边走向完全相反的路线。
Zephyr 的选择是 MCU 资源约束下的必然——F103 的 20K RAM 养不起
运行时解析器，而编译期展开后 DT_REG_ADDR 就是一个立即数。

## 三种描述硬件的方式：同一事实的三个抽象层级

回到本仓的第一性原理。点亮 PA5 这颗 LED，三个时代各怎么写：

```c
/* 时代一：01-stm32 手写（见 4.12 用位操作控制内存映射IO寄存器） */
#define GPIOA_BSRR (*(volatile uint32_t *)(0x40010800UL + 0x10))
GPIOA_BSRR = (1U << 5);
```

```
/* 时代二：Zephyr dts 声明 */
gpioa: gpio@40010800 {
    compatible = "st,stm32-gpio";
    reg = <0x40010800 0x400>;
    status = "okay";
};
```

```c
/* 时代三：应用只认别名 */
gpio_pin_set_dt(&led, 1);
```

| | 时代一 手写宏 | 时代二 dts | 时代三 别名+API |
|---|---|---|---|
| 硬件事实在哪 | 散落的 #define | 一份 dts 集中声明 | 板级 dts 的 aliases |
| 换板成本 | 全局搜索替换 | 换 dts | **零** |
| 出错时机 | 运行时（地址抄错） | 编译期（binding 校验） | 编译期 |
| 本质 | 基址+偏移 | **还是基址+偏移，只是声明化** | 对声明的引用 |

关键在最后一行：**dts 没有发明任何新东西**——`reg = <0x40010800 0x400>`
里那两个数，和你手写 `#define GPIOA_BASE 0x40010800` 是同一对手册里的数。
改变的是：事实只写一次、编译期校验、消费方与细节解耦。

## 什么时候不必用 dts

dts 不是银弹，本仓场景下要诚实：

- **一次性学习实验**（01-stm32 全部）：手写地址**教学价值更高**——
  你必须亲手查手册、算偏移，才知道 0x40010800 不是魔法数；
- **单板单应用、永不移植**：dts 的抽象税（学语法、查 binding、看产物）可能不划算；
- **调硬件时**：示波器上的问题，最终还是要回落到"基址+偏移+示波器"层面——
  dts 层看不出 PA5 上实际有没有波形。

这就是为什么本仓的顺序是**先 01-stm32 手写，再 03-zephyr 声明**：
不知道 dts 替你封装了什么，dts 出错时你就只能干瞪眼。

## 要点回顾

1. Linux 把 dts 当运行时数据库（dtc + dtb + 启动解析），Zephyr 当代码生成器输入（Python 解析 + 编译期宏展开，零运行时开销）。
2. dts 的 `reg = <基址 长度>` 和手写 BASE 宏是同一事实——dts 只是把它声明化、集中化、编译期校验化。
3. 学习路径上必须先经历手写时代：dts 封装的是"基址+偏移"，不懂封装内容就无法调试。

<details>
<summary>Q1：Zephyr 的 dts 文件能直接拿去给 Linux 用吗？</summary>

语法兼容（都能被 dtc 编译），语义**不能直接移植**：
两边的 binding 命名空间、属性约定（如 Zephyr 的 pinctrl 引用方式、
chosen 节点键名）各有演进。实际工程中同一芯片家族要在两边各维护一套，
厂商（如 ST（意法半导体：STM32 芯片就是它家的））会尽量同步，但"一份 dts 两边吃"不是现实。

</details>

<details>
<summary>Q2：devicetree_generated.h 可以手写修改吗？</summary>

不可以也不必要——每次构建重新生成，手改会被覆盖。
想改硬件描述，永远回到源头：改 dtsi/dts/overlay，
然后**看生成产物验证**（build/zephyr/zephyr.dts）。
"生成文件只读"是调试 dts 问题的第一条纪律。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| Zephyr 的 dts 直接拿去给 Linux 用 | 同一套语法，理应通用 | 语法兼容、语义不能移植：binding 命名空间与属性约定各有演进 |
| 手改 devicetree_generated.h 快速验证 | 改个头文件试试 | 每次构建重新生成、手改必被覆盖；改硬件永远回 dts 源头 |
| overlay 是运行时叠加 | Linux overlay 运行时动态叠加 | Zephyr 是**编译期**文本叠加，无运行时概念 |
| 换 dts 不用重编 | Linux 换 dtb 不重编内核 | Zephyr 改 dts 必须重新编译固件 |

## 代码自测

_注：本节示例按本篇正文语义编写，未在本仓库环境实跑，仿真验证见「验证路径」。_

用编译期断言证明"三个时代同一事实"：DT 宏展开 = 手写手册数字。

```c
#include <zephyr/kernel.h>
#include <zephyr/devicetree.h>

/* 时代一的手册数字（01-stm32 手写法，见 4.12） */
#define GPIOA_BASE_HANDWRITTEN  0x40010800UL

/* 时代二/三：dts 声明经编译期展开 */
BUILD_ASSERT(DT_REG_ADDR(DT_NODELABEL(gpioa)) == GPIOA_BASE_HANDWRITTEN,
             "dts reg 与手写 BASE 不一致——两个数出自同一本手册");

void main(void)
{
    /* 编过即证明：dts 没发明新东西，只是把手写基址声明化 */
}
```

**预期现象**：

- 构建通过 = `reg = <0x40010800 0x400>` 与手写宏是同一个数，零运行时开销；
- 把断言里的手写值改成 `0x40010900`：编译期立刻炸，不等到运行时；
- `build/zephyr/zephyr.dts` 里 gpioa 节点的 reg 正是这两个数。

**验证路径**：`west build -b nucleo_f103rb`（qemu_cortex_m3 无 stm32 gpioa 节点，此例面向 STM32 板）。

**常见翻车点**：

- 拿这套宏去不存在的节点上断言——节点缺席时先 `DT_NODE_HAS_STATUS` 分支；
- 想"手改 devicetree_generated.h 凑过断言"——下次构建被覆盖，永远改 dts 源头。
