## 这一篇讲什么

BLE 协议栈比 TCP/IP 还厚，但 Zephyr 把它拆成清晰的三层。
搞清楚每层归谁管、层与层之间怎么通话，后面 GATT、广播才有挂的地方。

## 三层划分

```
应用层：你的代码（bt_le_adv_start、GATT service 回调）
   │  Zephyr BLE host API（include/zephyr/bluetooth/）
host 层：GAP（连接管理）/ GATT-ATT（数据模型）/ L2CAP（通道复用）/ SMP（配对加密）
   │  HCI（Host-Controller Interface，标准化命令/事件接口）
controller 层：Link Layer（跳频、时序、包调度）+ PHY（2.4G 射频）
```

**HCI 是整个架构的铰链**：host 以上是纯软件（可移植），
controller 以下贴着射频硬件（厂商专用）。两者可以跑在同一颗芯片，
也可以分两颗芯片用 UART/SPI 连。

## 两种物理部署

| 方案 | 形态 | 例子 |
|---|---|---|
| **单芯片（SoC）** | host + controller 都在一颗 SoC，HCI 是片内函数调用 | nRF52840：Zephyr 的 controller 与 host 编进同一固件 |
| **双芯片（network processor）** | 应用 MCU 跑 host，外挂 BLE 芯片跑 controller，HCI 走 UART（H4）/SPI | 任意 MCU + nRF52 当纯 controller 烧 HCI 固件 |

Zephyr 的独特点：**controller 也是开源的**（`subsys/bluetooth/controller`，
软件实现 Link Layer），不是只有 host 开源。
nRF Connect SDK（Nordic 官方 SDK）就是 Zephyr 下游，
默认 controller 用的就是 Zephyr 这个——"Nordic 全家押 Zephyr"的技术原因。

## host 内部跑在什么线程上

回到 [ch04](../04-multithreading/README.md) 的线程模型，BLE host 里
至少有两类执行上下文：

| 上下文 | 干什么 | 配置项 |
|---|---|---|
| **RX 线程** | 收 HCI 事件/对端数据，向上派发 | `CONFIG_BT_RX_STACK_SIZE` |
| **TX 线程 / BT WQ** | 发送调度与协议栈内部 work | `CONFIG_BT_CTLR_*` / 系统 workqueue |

**回调纪律**（和 [4.4](../04-multithreading/4.4-调度与睡眠.md) 一脉相承）：
GATT 读/写回调、连接回调跑在协议栈线程上下文里，
**不能 k_sleep、不能干重活**——要干活就 k_work_submit 推出去，
否则整个协议栈被你的回调憋死。
RX 线程栈太小是 BLE 项目最常见的翻车点之一，症状是莫名其妙的栈溢出 fatal。

## 配置项速查

```conf
# prj.conf（nRF52 之类有射频的板子）
CONFIG_BT=y                  # host 总开关
CONFIG_BT_PERIPHERAL=y       # 角色：外设（被连方）
CONFIG_BT_CENTRAL=y          # 角色：中心（扫描/发起连接），二选一或都要
CONFIG_BT_CTLR=y             # 用 Zephyr 自带 controller（单芯片时）
```

## 书 API 年代差

| 原书怎么说 | 实际是什么（Zephyr 3.x） |
|---|---|
| 旧文档把 controller 描述为"实验中、功能不全" | 早已成熟，是 nRF Connect SDK 的默认 controller，全功能（含 2M PHY、长距离 coded PHY） |
| `CONFIG_BT_HCI_HOST` 等旧开关组合 | 现行就是 `CONFIG_BT` + 角色宏，构建系统按板子自动选 controller 后端 |

## 要点回顾

1. 三层：应用 / host（GAP·GATT·L2CAP·SMP）/ controller（LL+PHY），HCI 是铰链。
2. 单芯片（nRF52 一芯包办）vs 双芯片（HCI 走 UART）；Zephyr 连 controller 都是开源的。
3. host 有自己的 RX/TX 线程；回调里禁睡眠禁重活，RX 栈别给太小。

<details>
<summary>Q1：F103 想玩 BLE，双芯片方案现实吗？</summary>

技术上可行：拿一块 nRF52832/52840 烧 Zephyr 的 `hci_uart` 样例当纯 controller，
F103 这边 `CONFIG_BT` + HCI 走 UART 即可。但 20K RAM 跑 BLE host 非常勉强
（host 本身就要十几 K 起步），工程上没人这么干。
正确路径：直接用 nRF52 单芯片方案，F103 场景下 BLE 需求交给专用芯片。

</details>

<details>
<summary>Q2：BLE 和经典蓝牙（BR/EDR）在 Zephyr 里是什么关系？</summary>

Zephyr 主线支持 BLE（低功耗）是完整且活跃的；经典蓝牙支持有限且基本停滞，
`CONFIG_BT_BREDR` 存在但生态很小。说"Zephyr 蓝牙"默认就是 BLE。
需要经典蓝牙（如 SPP 串口）的项目一般选 ESP32 的 IDF 而不是 Zephyr。

</details>
