## 这一篇讲什么

手机上的 BLE 调试 App（nRF Connect 等）连上设备后看到的是一棵
"服务 → 特征 → 描述符"树。GATT 就是这棵树的协议，
Zephyr 用一组静态宏把整棵树在编译期声明出来——**没有运行时注册，
服务表就是一段 const 数据**。

## 三层数据模型

| 层 | 是什么 | 类比 |
|---|---|---|
| **Service**（服务） | 一组功能的命名空间，用 UUID 标识 | 一个"对象" |
| **Characteristic**（特征） | 服务里的一个数据点，带属性（read/write/notify） | 对象的"字段" |
| **Descriptor**（描述符） | 特征的元信息，最常见的是 CCC（客户端订阅开关） | 字段的"配置位" |

每个特征有**属性位**：read（手机读你）、write（手机写你）、
**notify/indicate**（你主动推给手机，订阅制）。
notify 是 BLE 数据上报的主力——传感器数据不轮询，有变化就推。

## 用宏声明一个服务

```c
#include <zephyr/bluetooth/gatt.h>

/* 128 位自定义 UUID（厂商自定义服务必须用 128 位，16 位是 SIG 官方的） */
#define MY_SVC_UUID BT_UUID_128_ENCODE(0x12345678, 0x1234, 0x5678, 0x9abc, 0xdef012345678)

static uint8_t sensor_val;                 /* 特征值存这里 */

static ssize_t read_val(struct bt_conn *conn, const struct bt_gatt_attr *attr,
                        void *buf, uint16_t len, uint16_t offset)
{
    return bt_gatt_attr_read(conn, attr, buf, len, offset, &sensor_val, sizeof(sensor_val));
}

static void ccc_changed(const struct bt_gatt_attr *attr, uint16_t value)
{
    /* value == BT_GATT_CCC_NOTIFY 表示手机订阅了 notify */
}

BT_GATT_SERVICE_DEFINE(my_svc,
    BT_GATT_PRIMARY_SERVICE(MY_SVC_UUID),
    BT_GATT_CHARACTERISTIC(BT_UUID_DECLARE_16(0x2A6E),   /* 特征 UUID */
                           BT_GATT_CHRC_READ | BT_GATT_CHRC_NOTIFY,  /* 属性位 */
                           BT_GATT_PERM_READ,                         /* 权限 */
                           read_val, NULL, &sensor_val),              /* 读/写回调+值 */
    BT_GATT_CCC(ccc_changed, BT_GATT_PERM_READ | BT_GATT_PERM_WRITE), /* 订阅开关 */
);
```

三个关键点：

1. `BT_GATT_SERVICE_DEFINE` 展开成一段 **const 属性数组**，
   链接进固件后 host 直接遍历它——宏的层数虽深，产物是纯数据。
2. 每个 characteristic 宏实际生成**多个属性项**（声明 + 值项），
   所以你数代码里的行数和 App 里看到的行数对不上，是正常的。
3. **权限（PERM）和属性位（CHRC）是两回事**：CHRC 告诉手机"这个特征能读"，
   PERM 是 host 侧真正的门禁——两个都要给对。

## 主动推送：notify

```c
sensor_val = read_adc_something();
bt_gatt_notify(NULL, &my_svc.attrs[1], &sensor_val, sizeof(sensor_val));
/* NULL = 发给所有已订阅的连接；attrs 下标对准"值项"那一项 */
```

notify 的纪律回到 [7.1](7.1-BLE栈架构.md) 的线程话题：
它可以在你的应用线程里调，但**回调里（如 ccc_changed）不能干重活**。
推送频率受连接参数限制，这正是下一篇 MTU 与吞吐的主题。

## 书 API 年代差

| 原书怎么说 | 实际是什么（Zephyr 3.x） |
|---|---|
| `BT_GATT_CHARACTERISTIC` 参数为 (uuid, props, perm, read, write, value) | 现行宏签名一致，但增加了 `BT_GATT_CHRC_*` 属性位与加密权限（`BT_GATT_PERM_READ_ENCRYPT`）等组合，配对后才可读写 |
| notify 用 `bt_gatt_notify(NULL, attr, ...)` 直接发 | 签名未变；大数据量推荐 **indicate**（带确认）或先协商大 MTU（见 [7.3](7.3-广播连接与MTU.md)） |

## 要点回顾

1. GATT 树：Service → Characteristic（带 read/write/notify 属性）→ Descriptor（CCC）。
2. Zephyr 用 `BT_GATT_SERVICE_DEFINE` 一族宏在**编译期**生成 const 属性表，无运行时注册。
3. CHRC 属性位管"宣告"，PERM 权限管"门禁"；notify 是上报主力。

<details>
<summary>Q1：bt_gatt_notify 的 attr 下标怎么数？</summary>

属性表按宏展开顺序平铺：PRIMARY_SERVICE 占 1 项，每个 CHARACTERISTIC
占 2 项（声明+值），CCC 占 1 项。上面例子里值项是 attrs[1]。
手写数字下标很脆，工程做法是用 `BT_GATT_SERVICE_DEFINE` 后紧跟定义
枚举常量或取 `bt_gatt_attr_next()` 遍历找 UUID，避免加特征时全体错位。

</details>

<details>
<summary>Q2：手机写数据进来（write 方向）怎么处理？</summary>

给特征加 `BT_GATT_CHRC_WRITE | BT_GATT_PERM_WRITE` 并提供 write 回调：
`ssize_t write_val(conn, attr, buf, len, offset, flags)`，
校验后 memcpy 到自己的变量，返回写入长度。
**回调在协议栈线程里跑**——只搬数据，搬完置标志位让应用线程处理。

</details>
