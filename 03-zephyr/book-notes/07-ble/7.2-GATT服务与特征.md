## 这一篇讲什么

手机上的 BLE 调试 App（nRF Connect 等）连上设备后看到的是一棵
"服务 → 特征 → 描述符"树。GATT 就是这棵树的协议，
Zephyr 用一组静态宏把整棵树在编译期声明出来——**没有运行时注册，
服务表就是一段 const（C 关键字：数据只读、编译后固化不许改写）数据**。

## 先用人话说一遍（新手铺垫）

BLE 设备连上手机后，两边总得先解决一个问题：手机怎么知道
这台设备"有哪些数据、哪些能读、哪些能写"？答案是设备把
自己的能力清单提前公示出来，手机照着清单逐条访问——这张清单就是 GATT 树。

类比一家自助餐厅：菜单（**服务表**）在开门前就印好贴在墙上，
不是顾客来了现写的——对应 Zephyr 的"编译期声明、无运行时注册"。
菜单分**大类**（热菜、凉菜、饮料 = Service），每类下面是**具体菜品**
（= Characteristic，特征），每道菜旁边有小字标注：
"可点"（read）、"可加辣备注"（write）、"出新菜会广播通知会员"
（notify）。那个"会员登记处"就是 **CCC 描述符**——手机不登记，
你 notify 一百次它也收不到。

所以本篇那一坨宏看着唬人，本质只有一个动作：**把菜单排版好，
编译时固化进固件**。host 运行时只是照着这张表逐条答复手机，
没有一个"注册服务"的函数调用。

| 术语 | 一句话解释 |
|---|---|
| GATT 树 | 设备对外公示的数据目录：服务→特征→描述符三层嵌套，手机连上后按树访问 |
| UUID | 服务/特征的全球唯一编号：16 位是蓝牙 SIG 官方分配，自定义必须用 128 位 |
| 特征（Characteristic） | GATT 树里的一个数据点，带"可读/可写/可推送"的属性位 |
| CCC 描述符 | 特征的订阅开关：手机写它表示"订阅 notify"，设备才能主动推数据 |
| notify / indicate | 设备主动向手机推数据的两种方式：notify 不等确认，indicate 逐条等回执 |
| 属性表（attrs） | 宏展开后生成的 const 数组，host 靠遍历它来应答手机的所有 GATT 请求 |

## 三层数据模型

| 层 | 是什么 | 类比 |
|---|---|---|
| **Service**（服务） | 一组功能的命名空间，用 UUID 标识 | 一个"对象" |
| **Characteristic**（特征） | 服务里的一个数据点，带属性（read/write/notify） | 对象的"字段" |
| **Descriptor**（描述符） | 特征的元信息，最常见的是 CCC（客户端订阅开关） | 字段的"配置位" |

每个特征有**属性位**：read（手机读你）、write（手机写你）、
**notify/indicate**（你主动推给手机，订阅制）。
notify 是 BLE 数据上报的主力——传感器数据不轮询，有变化就推。

## 用宏声明一个服务

```c
#include <zephyr/bluetooth/gatt.h>

/* 128 位自定义 UUID（厂商自定义服务必须用 128 位，16 位是 SIG 官方的） */
#define MY_SVC_UUID BT_UUID_128_ENCODE(0x12345678, 0x1234, 0x5678, 0x9abc, 0xdef012345678)

static uint8_t sensor_val;                 /* 特征值存这里 */

static ssize_t read_val(struct bt_conn *conn, const struct bt_gatt_attr *attr,
                        void *buf, uint16_t len, uint16_t offset)
{
    return bt_gatt_attr_read(conn, attr, buf, len, offset, &sensor_val, sizeof(sensor_val));
}

static void ccc_changed(const struct bt_gatt_attr *attr, uint16_t value)
{
    /* value == BT_GATT_CCC_NOTIFY 表示手机订阅了 notify */
}

BT_GATT_SERVICE_DEFINE(my_svc,
    BT_GATT_PRIMARY_SERVICE(MY_SVC_UUID),
    BT_GATT_CHARACTERISTIC(BT_UUID_DECLARE_16(0x2A6E),   /* 特征 UUID */
                           BT_GATT_CHRC_READ | BT_GATT_CHRC_NOTIFY,  /* 属性位 */
                           BT_GATT_PERM_READ,                         /* 权限 */
                           read_val, NULL, &sensor_val),              /* 读/写回调+值 */
    BT_GATT_CCC(ccc_changed, BT_GATT_PERM_READ | BT_GATT_PERM_WRITE), /* 订阅开关 */
);
```

三个关键点：

1. `BT_GATT_SERVICE_DEFINE` 展开成一段 **const 属性数组**，
   链接进固件后 host 直接遍历它——宏的层数虽深，产物是纯数据。
2. 每个 characteristic 宏实际生成**多个属性项**（声明 + 值项），
   所以你数代码里的行数和 App 里看到的行数对不上，是正常的。
3. **权限（PERM）和属性位（CHRC）是两回事**：CHRC 告诉手机"这个特征能读"，
   PERM 是 host 侧真正的门禁——两个都要给对。

## 主动推送：notify

```c
sensor_val = read_adc_something();
bt_gatt_notify(NULL, &my_svc.attrs[1], &sensor_val, sizeof(sensor_val));
/* NULL = 发给所有已订阅的连接；attrs 下标对准"值项"那一项 */
```

notify 的纪律回到 [7.1](7.1-BLE栈架构.md) 的线程话题：
它可以在你的应用线程里调，但**回调里（如 ccc_changed）不能干重活**。
推送频率受连接参数限制，这正是下一篇 MTU 与吞吐的主题。

## 书 API 年代差

| 原书怎么说 | 实际是什么（Zephyr 3.x） |
|---|---|
| `BT_GATT_CHARACTERISTIC` 参数为 (uuid, props, perm, read, write, value) | 现行宏签名一致，但增加了 `BT_GATT_CHRC_*` 属性位与加密权限（`BT_GATT_PERM_READ_ENCRYPT`）等组合，配对后才可读写 |
| notify 用 `bt_gatt_notify(NULL, attr, ...)` 直接发 | 签名未变；大数据量推荐 **indicate**（带确认）或先协商大 MTU（见 [7.3](7.3-广播连接与MTU.md)） |

## 要点回顾

1. GATT 树：Service → Characteristic（带 read/write/notify 属性）→ Descriptor（CCC）。
2. Zephyr 用 `BT_GATT_SERVICE_DEFINE` 一族宏在**编译期**生成 const 属性表，无运行时注册。
3. CHRC 属性位管"宣告"，PERM 权限管"门禁"；notify 是上报主力。

<details>
<summary>Q1：bt_gatt_notify 的 attr 下标怎么数？</summary>

属性表按宏展开顺序平铺：PRIMARY_SERVICE 占 1 项，每个 CHARACTERISTIC
占 2 项（声明+值），CCC 占 1 项。上面例子里值项是 attrs[1]。
手写数字下标很脆，工程做法是用 `BT_GATT_SERVICE_DEFINE` 后紧跟定义
枚举常量或取 `bt_gatt_attr_next()` 遍历找 UUID，避免加特征时全体错位。

</details>

<details>
<summary>Q2：手机写数据进来（write 方向）怎么处理？</summary>

给特征加 `BT_GATT_CHRC_WRITE | BT_GATT_PERM_WRITE` 并提供 write 回调：
`ssize_t write_val(conn, attr, buf, len, offset, flags)`，
校验后 memcpy（C 标准库函数：把一段内存字节原样拷到另一处）到自己的变量，返回写入长度。
**回调在协议栈线程里跑**——只搬数据，搬完置标志位让应用线程处理。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| 属性位给了手机就能读写 | CHRC 宣告了能力 | CHRC 是"宣告"、PERM 是"门禁"，两回事，只给一个手机读写照样被拒 |
| notify 发了手机就能收到 | 推送是单向喊话 | 手机必须先写 CCC 描述符订阅，否则 notify 一百次也收不到 |
| 一个特征 = 属性表一行 | 宏一行对一行 | 每个 CHARACTERISTIC 展开成 2 项（声明+值），CCC 再占 1 项；手写 attrs 下标很脆，加特征全体错位（Q1） |
| 服务要运行时注册 | 其他框架的 register_service() | Zephyr 编译期固化成 const 属性数组，没有任何"注册"调用 |
| 16 位 UUID 随便挑个短的 | 短号好写好看 | 16 位是蓝牙 SIG 官方分配，自定义服务/特征必须用 128 位 UUID |

## 代码自测

_注：本节代码按 Zephyr API 语义编写，未在本仓库环境实跑，仿真验证见「验证路径」。_

```c
#include <zephyr/kernel.h>
#include <zephyr/bluetooth/bluetooth.h>
#include <zephyr/bluetooth/gatt.h>
#include <zephyr/sys/printk.h>

#define MY_SVC_UUID BT_UUID_128_ENCODE(0x12345678, 0x1234, 0x5678, 0x9abc, 0xdef012345678)

static uint8_t sensor_val;
static bool notify_on;

static ssize_t read_val(struct bt_conn *conn, const struct bt_gatt_attr *attr,
                        void *buf, uint16_t len, uint16_t offset)
{
    return bt_gatt_attr_read(conn, attr, buf, len, offset,
                             &sensor_val, sizeof(sensor_val));
}

static ssize_t write_val(struct bt_conn *conn, const struct bt_gatt_attr *attr,
                         const void *buf, uint16_t len, uint16_t offset, uint8_t flags)
{
    sensor_val = *(const uint8_t *)buf;   /* 回调在协议栈线程：只搬数据 */
    return len;
}

static void ccc_changed(const struct bt_gatt_attr *attr, uint16_t value)
{
    notify_on = (value == BT_GATT_CCC_NOTIFY);   /* 手机订阅/退订的开关 */
}

BT_GATT_SERVICE_DEFINE(my_svc,
    BT_GATT_PRIMARY_SERVICE(MY_SVC_UUID),
    BT_GATT_CHARACTERISTIC(BT_UUID_DECLARE_16(0x2A6E),
        BT_GATT_CHRC_READ | BT_GATT_CHRC_WRITE | BT_GATT_CHRC_NOTIFY,
        BT_GATT_PERM_READ | BT_GATT_PERM_WRITE,
        read_val, write_val, &sensor_val),
    BT_GATT_CCC(ccc_changed, BT_GATT_PERM_READ | BT_GATT_PERM_WRITE),
);

int main(void)
{
    bt_enable(NULL);   /* 广播部分见 7.3，这里只看 GATT 树 */

    while (1) {
        k_sleep(K_SECONDS(1));
        sensor_val++;
        if (notify_on) {   /* 没订阅就不发——发了手机也收不到 */
            bt_gatt_notify(NULL, &my_svc.attrs[1], &sensor_val, sizeof(sensor_val));
        }
    }
    return 0;
}
```

**预期现象**：
- nRF Connect 连上后看到服务树：自定义 128 位服务 → 0x2A6E 特征 → CCC 描述符
- 手机读特征：返回每秒递增的 `sensor_val`；手机写 0x5A 后再读：返回 0x5A
- 订阅 CCC 后每秒收到 notify；退订后 `notify_on` 变 false，不再发
- 权限实验：把 `BT_GATT_PERM_WRITE` 删掉，手机写操作被拒——CHRC 与 PERM 两回事

**验证路径**：nRF52 实机 + nRF Connect App（F103 无 BLE，只能仿真 + 主机 BlueZ HCI）。

**常见翻车点**：
- `attrs[1]` 手写数字下标：加/删一个特征后全体错位，工程做法用枚举常量（Q1）
- CHRC 给了 `BT_GATT_CHRC_WRITE` 但 PERM 漏 `BT_GATT_PERM_WRITE`：手机写失败，报错不直观
- write 回调里做解析/存 flash 等重活：那是协议栈线程，搬完数据置标志就走
