## 这一篇讲什么

设备要被手机发现靠**广播**，被发现后建**连接**，连接里传数据的快慢由
**MTU + 连接参数 + PHY** 三个旋钮决定。这一篇把 GAP 的最小模型和
吞吐公式摆清楚。

## GAP：四种角色，记住两个就够

| 角色 | 行为 | 典型设备 |
|---|---|---|
| **Peripheral**（外设） | 发广播、被连接 | 手环、传感器（你的固件通常是这个） |
| **Central**（中心） | 扫描、发起连接 | 手机、网关 |
| Broadcaster / Observer | 只广播不连接 / 只扫描不连接 | beacon、扫码枪 |

广播是 Peripheral 单方面喊话："我在这，我是谁"；
Central 听到后发起连接，之后进入 GATT 的世界（[7.2](7.2-GATT服务与特征.md)）。

## 广播：bt_le_adv_start 一调了之

```c
#include <zephyr/bluetooth/bluetooth.h>

static const struct bt_data ad[] = {
    BT_DATA_BYTES(BT_DATA_FLAGS, BT_LE_AD_GENERAL | BT_LE_AD_NO_BREDR),  /* 通用可发现 */
    BT_DATA_BYTES(BT_DATA_UUID16_ALL, 0x0d, 0x18),                       /* 服务 UUID */
};

bt_enable(NULL);                          /* 初始化 host+controller */
bt_le_adv_start(BT_LE_ADV_CONN_NAME,      /* 预置参数：可连接广播，带设备名 */
                ad, ARRAY_SIZE(ad), NULL, 0);
```

- 广播包只有 **31 字节**有效载荷——塞不下就放 **scan response**（第二包，也是 31 字节）。
- `BT_LE_ADV_CONN_NAME` 这类预置宏展开成 `bt_le_adv_param`（广播间隔、模式）；
  自定义间隔用 `BT_LE_ADV_PARAM()` 宏自己填。
- 广播间隔越短越容易被发现，也越费电——**广播是 BLE 功耗大头之一**。

## 连接参数三件套

连接建立后，双方按固定节奏"约会"交换数据：

| 参数 | 含义 | 影响 |
|---|---|---|
| connection interval | 多久约会一次（7.5ms–4s） | 越小越快越费电 |
| peripheral latency | 外设可以睡过几次约会 | 省电的关键旋钮 |
| supervision timeout | 多久没见到对方算断线 | 断线判定灵敏度 |

吞吐的另一条腿是 **ATT MTU**：默认 23 字节，减去 3 字节 ATT 头，
一次 notify 只能装 20 字节。连接后双方可协商到 247 甚至更大：

```conf
CONFIG_BT_L2CAP_TX_MTU=247
CONFIG_BT_BUF_ACL_RX_SIZE=251     /* controller 侧收包缓冲要跟上调大 */
```

## 吞吐公式（量级估算）

```
吞吐 ≈ MTU_payload × 每连接事件包数 × (1000 / interval_ms)
```

三档提速手段，按代价排序：

1. **加大 MTU**（20 → 244 字节载荷）：纯软件协商，先做。
2. **缩短 connection interval**（100ms → 15ms）：费电换速度。
3. **开 2M PHY**（`CONFIG_BT_CTLR_PHY_2M`，物理层速率翻倍）：
   controller 和手机都要支持，距离近时用。

DLE（Data Length Extension，单包 27 → 251 字节）在现代 Zephyr
controller 上默认开启，和 MTU 是两层的事——**MTU 是协议层的，
DLE 是链路层的，两个都大才有大吞吐**。

## 书 API 年代差

| 原书怎么说 | 实际是什么（Zephyr 3.x） |
|---|---|
| `bt_le_adv_start` 参数结构手填 | 现行惯例用预置宏 `BT_LE_ADV_CONN_NAME` / `BT_LE_ADV_NCONN`，需要定制再 `BT_LE_ADV_PARAM()` |
| 连接参数更新靠手机主导 | 外设可用 `bt_conn_le_param_update()` 主动提议，但**最终拍板权在 central（手机）**，iOS/Android 各有自己的接受范围 |

## 要点回顾

1. GAP 主记两角色：Peripheral 广播被连，Central 扫描发起；广播有效载荷 31 字节。
2. 连接三参数：interval / latency / timeout，吞吐与功耗的对价。
3. 吞吐三招：大 MTU、短 interval、2M PHY；MTU 和 DLE 是两层，都要调。

<details>
<summary>Q1：广播发了但手机扫不到，按什么顺序排查？</summary>

① `bt_enable` 是否成功返回（controller 没起来一切皆空）；
② `bt_le_adv_start` 返回值（常见 -ENOMEM：广播集配置超限）；
③ 广播包里 flags 是否含 `BT_LE_AD_GENERAL`（不可发现模式手机列表不显示）；
④ 用手机调试 App（nRF Connect）而不是系统蓝牙设置页——后者只显示已配对设备。

</details>

<details>
<summary>Q2：notify 发了但手机收不全，是谁的锅？</summary>

先看 MTU：payload 超过 MTU-3 会被协议层拒绝或截断（`bt_gatt_notify` 返回负值）。
再看发送节奏：连续 notify 超过 controller 的 TX buffer 数会失败，
应等 `bt_gatt_notify` 返回成功再发下一条，或用 indicate（逐条确认）。
最后才是连接参数太保守——那是慢，不是丢。

</details>
