## 这一篇讲什么

前两篇把 elf 跑起来了。这一篇讲 Renode 区别于"又黑又硬的真板"的两个超能力：
**Monitor 命令行**（运行时翻看/摆弄整台虚拟机）和
**Robot Framework 集成**（把"固件行为正确"写成可进 CI 的断言）。

## Monitor：一台可以随便翻看的虚拟机

`renode` 不带参数启动进 Monitor 提示符。值得一记的命令族：

```
(monitor) mach create
(monitor) machine LoadPlatformDescription @hello.repl
(machine) sysbus LoadELF @zephyr.elf
# ---- 观测 ----
(machine) sysbus WhatPeripheralAt 0x40004400   # 这个地址上是谁？答：usart2
(machine) sysbus ReadDoubleWord 0x40004400     # 直接读外设寄存器
(machine) gpioPortA GetPinState 5              # PA5 现在高还是低？
# ---- 控制 ----
(machine) pause                     # 整台机器定格
(machine) cpu Step 10               # 单步 10 条指令
(machine) sysbus LogPeripheralAccess usart2 true   # 记录每次 UART 寄存器访问
```

三个洞察：

- `GetPinState` = "**不用示波器的示波器**"——断言"灯亮了"变成断言"PA5 = true"；
- `pause` 是**全局一致暂停**：真板 halt 内核时外设还在跑，Renode 整个世界一起停；
- `LogPeripheralAccess` = 免费的寄存器级逻辑分析仪。

## Robot Framework：把冒烟测试写成断言

```robot
*** Settings ***
Suite Setup     Setup
Suite Teardown  Teardown
Resource        ${RENODEKEYWORDS}

*** Test Cases ***
Hello World 应打印到 UART
    Execute Command           mach create
    Execute Command           machine LoadPlatformDescription @hello.repl
    Execute Command           sysbus LoadELF @zephyr.elf
    Create Terminal Tester    sysbus.usart2

    Execute Command           start
    Wait For Line On Uart     Hello World!    timeout=5
```

跑法：`renode-test hello.robot`。核心关键字：

| 关键字 | 作用 |
|---|---|
| `Create Terminal Tester sysbus.usart2` | 给 UART 输出挂监听器 |
| `Wait For Line On Uart "..." timeout=5` | **核心断言**：5 秒（虚拟时间）内出现该行则 PASS |
| `Execute Command` | 任意 Monitor 命令——.repl/.resc 知识直接复用 |

进阶：`Wait For Pin On GPIO gpioPortA 5`（等 PA5 变高）、
`Write Line To Uart`（往 shell 打命令再断言回显）——
**整个"点灯/按键/shell 交互"验收流程都能无人值守**。

## 为什么这套东西在 CI 里无可替代

```
真板 CI 的麻烦                    Renode + Robot
─────────────────────              ─────────────────────────
板子要占 USB/电源/机位              容器里 renode-test 一条命令
输出靠人眼看/串口抓                 Wait For Line On Uart 断言
"灯亮没亮"要摄像头/示波器          Wait For Pin On GPIO 断言
偶发接触不良 → flaky test           确定性仿真，失败即真失败
```

Zephyr 官方的 twister/`west build -t run` 集成就走这条路，
samples 回归大量跑在 Renode 上。

## 收尾：局限再念一遍

自动化越强，越要忍住"仿真通过 = 万事大吉"的冲动：

- **时序类 bug 仿真抓不住**（虚拟时间，见 [10.1](10.1-Renode与QEMU定位差异.md) 局限表）；
- 外设模型按 datasheet"标准行为"实现——**真芯片的 errata 不在模型里**；
- 断言通过只证明"在模型描述的硬件上行为正确"。

本仓结论照旧：**Renode 做 CI 过滤器，F103 真板做最终验收。**

## 要点回顾

1. Monitor 三神器：`GetPinState`（无示波器看引脚）、`pause`（全局一致暂停）、`LogPeripheralAccess`（免费逻辑分析仪）。
2. Robot 断言核心：`Create Terminal Tester` + `Wait For Line On Uart`，引脚级用 `Wait For Pin On GPIO`。
3. CI 无可替代：确定性 + 可编程断言 + 零硬件库存；但 errata 和时序永远在真板侧。

<details>
<summary>Q1：Robot 测试里的 timeout 是真实秒数吗？</summary>

是虚拟时间——guest 内部时钟。宿主机再慢，"timeout=5" 都按 guest 过 5 秒算，
慢速 CI 容器上测试依然确定；代价同前：度量不了真板时序。

</details>

<details>
<summary>Q2：能把真板串口日志回放给 Renode 当断言基准吗？</summary>

思路成立（黄金日志对比）：真板跑一次存输出，Robot 里逐行 Wait For Line 对齐。
但要给真板日志**去时间戳/去地址噪音**，否则每次运行都不同；
实践上更常见只断言关键行，不做全文 diff。

</details>
