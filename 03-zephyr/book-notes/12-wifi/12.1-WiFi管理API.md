## 这一篇讲什么

Zephyr 的 Wi-Fi 分两层：**管理面**（扫描/连接/断开，走 `wifi_mgmt` API）
和**数据面**（连上之后就是普通网络接口，走 ch08 的 socket）。
本篇只看管理面：API 长什么样、事件从哪个上下文回来。

## 在协议栈里的位置

```
应用
  │  zsock_send/recv …… 数据面（ch08 socket，连上后与 Wi-Fi 无关）
┌─┴──────────────┐
│  wifi_mgmt API │  scan / connect / disconnect / status   ← 本篇
├────────────────┤
│  net_if (L2)   │  接口抽象：ethernet / wifi / ieee802154 一视同仁
├────────────────┤
│  Wi-Fi 驱动    │  原生 SoC 驱动 或 offload 驱动（协处理器）
└────────────────┘
```


关键认知：**Wi-Fi 管理 API 和 socket 层完全解耦**。
连接成功后拿到的是普通 `net_if`，后续代码和以太网版一模一样——
这也是 ch08 先学 socket、本章只补管理面的原因。

## 扫描与连接轮廓

```c
struct net_if *iface = net_if_get_default();
net_mgmt(NET_REQUEST_WIFI_SCAN, iface, NULL, 0);  /* 扫描：异步，结果走事件回调 */

/* 连接：填参数结构，同样异步 */
struct wifi_connect_req_params params = {
    .ssid = (const uint8_t *)"MyAP", .ssid_length = 4,
    .psk = (const uint8_t *)"password", .psk_length = 8,
    .security = WIFI_SECURITY_TYPE_PSK,
    .channel = WIFI_CHANNEL_ANY,
    .mfp = WIFI_MFP_OPTIONAL,
};
net_mgmt(NET_REQUEST_WIFI_CONNECT, iface, &params, sizeof(params));
```

事件回调注册（net_mgmt 事件框架，不是 wifi 专有）：

```c
static struct net_mgmt_event_callback cb;

static void wifi_event_handler(struct net_mgmt_event_callback *cb,
                               uint64_t mgmt_event, struct net_if *iface)
{
    switch (mgmt_event) {
    case NET_EVENT_WIFI_SCAN_RESULT:      /* 扫到一个 AP */ break;
    case NET_EVENT_WIFI_SCAN_DONE:        /* 扫描结束 */   break;
    case NET_EVENT_WIFI_CONNECT_RESULT:   /* 连接成/败 */  break;
    case NET_EVENT_WIFI_DISCONNECT_RESULT:/* 断开 */       break;
    }
}
net_mgmt_init_event_callback(&cb, wifi_event_handler,
                             NET_EVENT_WIFI_SCAN_RESULT |
                             NET_EVENT_WIFI_CONNECT_RESULT |
                             NET_EVENT_WIFI_DISCONNECT_RESULT);
net_mgmt_add_event_callback(&cb);
```

## 事件回调的上下文

`net_mgmt` 事件回调跑在**系统 workqueue 的线程上下文**（不是 ISR，也不是发请求的线程）。三条纪律：

| 纪律 | 原因 |
|---|---|
| 回调里别干长活 | 堵的是系统 workqueue，波及其他子系统（[5.4](../05-ipc-workqueues/5.4-workqueue.md)） |
| 回调与请求线程通信用 k_sem / k_msgq | "等连接结果"= 请求线程 take sem，回调里 give |
| 断开事件随时可能来 | 不只主动 disconnect 才触发，AP 踢人也会来 |

典型骨架：请求线程发 connect → `k_sem_take` → 回调判 status == 0 后 `k_sem_give`（完整代码见 12.3）。

## "原书怎么说 / 实际是什么"

| 原书（2024 版）说法 | 实际（Zephyr 3.x 官方文档） |
|---|---|
| 调 `wifi_mgmt_scan()` / `wifi_mgmt_connect()` 直接函数 | 现行走 `net_mgmt(NET_REQUEST_WIFI_*)` 请求框架，语义相同 |
| 连接是同步调用 | **异步**：请求只是提交，结果走 `NET_EVENT_WIFI_CONNECT_RESULT` 事件 |
| scan 一次性返回 AP 列表 | 逐个 AP 一个 SCAN_RESULT 事件，最后 SCAN_DONE 收尾 |

## 要点回顾

1. Wi-Fi = 管理面（wifi_mgmt / net_mgmt 请求）+ 数据面（普通 net_if + socket），两层解耦。
2. 扫描/连接都是**异步**：发请求，结果走 `NET_EVENT_WIFI_*` 事件。
3. 事件回调跑在系统 workqueue 线程上下文：快进快出，用 sem/msgq 回报结果；连上后一切与 ch08 以太网 socket 同构。

<details>
<summary>Q1：为什么管理 API 要做成异步而不是同步阻塞？</summary>

扫描要数秒、连接要经历认证/关联/DHCP，同步阻塞会把调用线程钉死数秒且
语义僵硬（超时怎么定？）。异步 + 事件让调用方自选等待策略（超时、重试、
并发干别的），代价是状态机要自己维护。

</details>

<details>
<summary>Q2：断线重连谁负责？</summary>

API 层不管。收到 `NET_EVENT_WIFI_DISCONNECT_RESULT` 后应用自己重发 connect。
新版 Zephyr 的 Wi-Fi Network Manager（wifi_nm）可托管自动重连，按需启用。

</details>
