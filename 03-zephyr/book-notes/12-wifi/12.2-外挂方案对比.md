## 这一篇讲什么

F103 自己没有 Wi-Fi，也没有 Ethernet MAC——要联网只有"外挂"一途。
这一篇对比三条路：**ESP32 作 Wi-Fi 协处理器（AT/modem 模式）**、
**直接用原生 Wi-Fi SoC 跑 Zephyr**、以及 F103 平台**现实的替代联网方案**。

## 三条路总览

| 方案 | 拓扑 | Wi-Fi 协议栈在哪 | 应用代码跑在哪 |
|---|---|---|---|
| ESP-AT modem | F103 ──UART──> ESP32（AT 固件） | ESP32 | F103 |
| 原生 Wi-Fi SoC | 单芯片（ESP32 / nRF70 主机等） | SoC 上（Zephyr 驱动） | 同一 SoC |
| offload 协处理器 | 主机 SoC ──SPI/SDIO──> 协处理器 | 协处理器 | 主机（Zephyr） |

Zephyr 驱动模型对三者的抽象：**都注册成一个 net_if**，
上层 wifi_mgmt / socket 代码不变——区别全在 DeviceTree 和 Kconfig
（[ch09](../09-devicetree/README.md) 的活）。

## ESP-AT modem：F103 唯一能走的路

ESP32 刷乐鑫官方 AT 固件，F103 通过 UART 发 AT 指令，
Zephyr 侧由 **modem / esp_at 驱动**把 AT 指令包装成 net_if：

```
F103 应用 ──socket──> Zephyr 网络栈 ──esp_at 驱动──> UART ──AT──> ESP32
                                                                    │ 完整 TCP/IP + Wi-Fi 全在 ESP32 里
```

| 优点 | 代价 |
|---|---|
| F103 应用代码仍是标准 socket | **socket 是 offload 的**（offloaded socket API），不是完整 LwIP 路径，功能子集 |
| ESP32 模块便宜、AT 固件免开发 | UART 带宽是天花板（默认 115200，可提波特率但仍受限） |
| 主控不换，现有 F103 工程直接扩 | 两块芯片两套固件，调试链路变长 |
| | AT 固件版本与 Zephyr 驱动要配套，升级是双份维护 |

注意 Zephyr 里 ESP-AT 走的是 **socket offload** 机制：
`zsock_*` 调用被重定向到 modem 驱动，TCP/IP 栈根本不在 F103 上跑——
所以 netstat、packet capture 这类依赖本地栈的能力会缺。

## 原生 Wi-Fi SoC：把 F103 换掉

ESP32 本身就是 Zephyr 官方支持的 SoC（含 Wi-Fi 驱动）。
"外挂"变成"换主控"：

| 优点 | 代价 |
|---|---|
| 完整 Zephyr 网络栈（LwIP），无 offload 裁剪 | F103 积累的外设代码要移植（外设模型不同） |
| 单芯片，硬件/调试链路最短 | ESP32 的 Zephyr 外设驱动覆盖度不及 STM32 系（逐模块查） |
| Wi-Fi + BLE 同芯片 | 实时性/功耗特性与 STM32 不同，要重评估 |

如果只是"想要 Zephyr + Wi-Fi 的学习/原型环境"，
这条路最顺——官方 sample（`samples/net/wifi`）就是为这类板子写的。

## offload 协处理器：中间路线

主机 SoC（可以是 STM32H7 等）+ 专用 Wi-Fi 协处理器
（如 nRF7002 配套 nRF53/STM32 主机，或 ESP-Hosted 方案的 ESP32），
走 SPI/SDIO。协议栈在协处理器，驱动在主机 Zephyr 里。
性能好于 UART modem，复杂度介于两者之间——**F103 的 SPI 带得动，
但没有现成配套驱动可捡，本仓库不展开**。

## F103 现实的联网替代（不上 Wi-Fi 时）

| 替代 | 说明 |
|---|---|
| W5500（SPI 以太网芯片） | Zephyr 有官方 W5500 驱动，F103 SPI 直挂；完整 LwIP 栈，体验最接近 ch08 教学语义——**本仓库若做联网实验，这是首选** |
| 串口透传到网关 | F103 UART 数据交给常在线网关（树莓派等）转发，F103 端无需网络栈 |
| BLE（ch07 路线） | 同样无硬件前提，先搁置 |

## 要点回顾

1. 三种外挂路径在 Zephyr 里都抽象成 net_if：ESP-AT（UART modem）、原生 SoC、SPI/SDIO 协处理器。
2. ESP-AT 是 F103 唯一保主控的路，代价是 socket offload 功能子集 + UART 带宽天花板。
3. 原生 SoC（ESP32 跑 Zephyr）最顺，但等于换主控、移植外设代码。
4. F103 现实替代：W5500 SPI 以太网（官方驱动、完整栈）优于硬上 Wi-Fi。

<details>
<summary>Q1：socket offload 和完整网络栈差在哪？</summary>

offload 下 zsock_* 被转发给模组执行：TLS、socket 选项、
net_context 高级特性取决于模组固件支持度，本地无法抓包/精细调优。
完整栈（W5500 / 原生 SoC）一切经过 LwIP，行为和 ch08 笔记完全一致。

</details>

<details>
<summary>Q2：ESP32 既能当 modem 又能当主控，同一个 Zephyr 驱动吗？</summary>

不是。modem 模式用 esp_at modem 驱动（挂在 F103 侧）；
ESP32 作主控时用 ESP32 自己的 Wi-Fi 驱动（espressif hal）。
两边代码路径完全不同，只是上层 API 都是 wifi_mgmt + net_if。

</details>
