# 8.3 F103 怎么上网：SPI 网卡 / Wi-Fi 模组 / 4G 模组 / QEMU

## 这一篇讲什么

F103 没有 Ethernet MAC、没有 Wi-Fi，但 Zephyr 网络栈对链路层是中立的
（[8.1](8.1-网络栈架构.md) 的 L2 抽象）。外挂硬件或仿真都能让它上网。
这一篇比较四条路径，给选型一个结论。

## 四条路径总览

| 路径 | 硬件/环境 | TCP/IP 栈在哪 | Zephyr 支持 |
|---|---|---|---|
| **W5500**（SPI） | W5500 模块，SPI 接线 | **芯片内置**（硬件 TCP offload） | ✅ `ethernet w5500` 驱动 |
| **ENC28J60**（SPI） | ENC28J60 模块 | **Zephyr native 栈** | ✅ `eth_enc28j60` 驱动 |
| **ESP-AT**（Wi-Fi 模组） | ESP8266/ESP32 刷 AT 固件，UART 接线 | **模组内置**，Zephyr 走 offloaded socket | ✅ `CONFIG_WIFI_ESP_AT` |
| **4G 模组**（UART） | 移远/SIMCom 等 | 两种：PPP（栈在 Zephyr）或模组内置栈 | ✅ modem 驱动 + `gsm_ppp` / offloaded |
| **QEMU 仿真** | 无硬件 | Zephyr native 栈 | ✅ TAP/SLIP 到主机 |

注意三种根本不同的栈归属：**纯转发**（ENC28J60，只是 MAC+PHY，
IP 栈全靠 Zephyr 自己）、**硬件 offload**（W5500，TCP 状态机在芯片里，
Zephyr 把它模拟成 Ethernet iface）、**AT 指令 offload**（ESP-AT/4G，
连 socket 都是模组的，Zephyr 的 offloaded socket API 做翻译）。

## 逐条点评

**W5500：F103 上最现实的有线路径。**
TCP offload 意味着 Zephyr 侧几乎不占 RAM 做连接缓冲，
20K RAM 的 F103 也跑得动。代价是并发 socket 数被芯片通道数限死（8 个），
且 TLS 仍需自己想办法（offload 只到 TCP）。

**ENC28J60：最便宜但最重。**
它只是 MAC，Zephyr 要跑完整 IP 栈（net_buf 配额见 [8.1](8.1-网络栈架构.md)），
F103 的 RAM 会很紧。学习价值高（协议栈全在你眼皮底下），实用价值一般。

**ESP-AT：Wi-Fi 最省事路径。**
模组内置 TCP/IP + TLS，Zephyr 用 offloaded socket（同样是 zsock_* 调用，
底层翻译成 AT 指令）。**TLS 由模组代劳**——这是小 RAM MCU 上云的
标准答案。代价：AT 翻译层有性能损耗，吞吐量受 UART 波特率封顶。

**4G 模组：两条子路径。**
PPP 模式（`gsm_ppp` 驱动）：模组只做物理链路，Zephyr 自己跑 IP 栈
——RAM 开销大，F103 不现实。模组内置栈 + AT socket：同 ESP-AT 逻辑，
是主流用法。

**QEMU：零硬件验证 socket 代码。**
`qemu_x86` 目标 + 主机 TAP 设备，[8.2](8.2-socket-API与POSIX.md) 的
echo 骨架不用等硬件就能跑通。**先把协议代码在 QEMU 里调对，
再上板子**——这是网络开发的标准工作流。

## devicetree 侧一瞥（W5500 为例）

```dts
&spi1 {
    w5500@0 {
        compatible = "wiznet,w5500";
        reg = <0>;
        spi-max-frequency = <8000000>;
        int-gpios = <&gpiob 5 GPIO_ACTIVE_LOW>;   /* 中断脚 */
        reset-gpios = <&gpiob 6 GPIO_ACTIVE_LOW>;
    };
};
```

配上 `CONFIG_NET_L2_ETHERNET=y` + W5500 驱动配置项，
网络栈就能通过 SPI 认出这块"网卡"——驱动模型与
[ch09](../09-devicetree/README.md) 的 devicetree 机制一脉相承。

## 书 API 年代差

| 原书怎么说 | 实际是什么（Zephyr 3.x） |
|---|---|
| ESP-AT 要手写 UART 收发和 AT 解析 | 现行 `CONFIG_WIFI_ESP_AT` 驱动已成体系，offloaded socket 自动翻译 |
| 4G 只有 PPP 一条路 | modem 子系统重构后，PPP 与 offloaded socket 双路径都可用，按模组能力选 |

## 要点回顾

1. 四路径按"栈在哪"分类：纯转发（ENC28J60）、硬件 offload（W5500）、AT offload（ESP-AT/4G）、仿真（QEMU）。
2. F103 现实选型：有线用 W5500，Wi-Fi/上云用 ESP-AT（TLS 模组代劳）；ENC28J60 只适合学习。
3. 工作流：QEMU 里调通 socket 代码 → 再上板子接真链路。

<details>
<summary>Q1：AT offload 路径下，zsock_socket 返回的 fd 是"真 socket"吗？</summary>

不是本机协议栈的 socket——它是 offloaded socket 层的句柄，
每个 zsock_* 调用被翻译成模组的 AT 指令（如 AT+QISTART）。
对应用透明是设计目标，但**行为细节有差**：错误码映射、并发上限、
DNS 解析都受模组固件约束，移植代码时要在真模组上回归。

</details>

<details>
<summary>Q2：W5500 的"8 个硬件 socket"和 Zephyr 的 socket 数什么关系？</summary>

W5500 驱动把芯片的 8 条通道模拟成一个 Ethernet iface 给 Zephyr 用，
对上层仍是完整 IP 栈的样子（驱动在 L2 层做映射）。
实际上 Zephyr 侧建 TCP 连接，数据走 W5500 的 MACRAW/Socket 模式
——细节随驱动版本演进，选型时以所用 Zephyr 版本的驱动文档为准。

</details>
