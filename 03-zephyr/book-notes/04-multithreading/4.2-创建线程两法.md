## 这一篇讲什么

Zephyr 创建线程有两条官方路径：**运行中动态创建**（`k_thread_create`）
和**编译期静态定义**（`K_THREAD_DEFINE`）。Zephyr 社区审美明显偏后者——
理由和裸机静态分配一脉相承。

## 法一：k_thread_create（动态，参数多但直白）

```c
K_THREAD_STACK_DEFINE(led_stack, 1024);
struct k_thread led_thread_data;
k_tid_t tid;

tid = k_thread_create(&led_thread_data,        /* ① TCB（自己提供存储） */
                      led_stack,               /* ② 栈 */
                      K_THREAD_STACK_SIZEOF(led_stack), /* ③ 栈大小 */
                      vLedEntry,               /* ④ 入口函数 */
                      NULL, NULL, NULL,        /* ⑤ 三个 void* 参数 */
                      5,                       /* ⑥ 优先级（4.3 细讲） */
                      0,                       /* ⑦ 选项（如 K_ESSENTIAL） */
                      K_NO_WAIT);              /* ⑧ 启动延迟 */
```

对照 FreeRTOS `xTaskCreate` 的五个差异点：

| | FreeRTOS xTaskCreate | Zephyr k_thread_create |
|---|---|---|
| TCB 存储 | 内核从 heap 分 | **调用者提供**（static struct k_thread） |
| 栈存储 | 内核从 heap 分 | **调用者提供**（K_THREAD_STACK_DEFINE） |
| 入口参数 | 1 个 void* | 3 个 void* |
| 失败路径 | 返回 pdFAIL（heap 不够） | **编译期就没有失败路径**——存储都是静态的 |
| 启动时机 | 创建即可被调度 | ⑧ 可延迟（K_MSEC(n) 后才就绪） |

注意第二行：**TCB 和栈都由调用者提供存储**，
`k_thread_create` 做的只是"初始化 + 挂进调度器"。
所以它的"动态"只是"运行中调用"，**内存还是静态的**——
真正的动态内存（k_thread_stack_alloc）是另一条不常用的路。

## 法二：K_THREAD_DEFINE（静态，Zephyr 主推）

```c
K_THREAD_DEFINE(led_tid,          /* 线程 id（符号名） */
                1024,             /* 栈大小 */
                vLedEntry,        /* 入口 */
                NULL, NULL, NULL, /* 三个参数 */
                5,                /* 优先级 */
                0,                /* 选项 */
                0);               /* 启动延迟（ms，0=立即） */
```

一行宏，TCB + 栈 + 初始化**全部在编译期完成**——
连 `main` 都没跑，线程就已经在调度器的名单里了。
启动流程：`main` 之前，内核初始化阶段就把所有静态线程建好，
进 `main` 时它们已经在跑了（或被调度）。

**这就是 Zephyr 的审美**：能在编译期定的，绝不留到运行时。
和 devicetree（硬件编译期描述）、Kconfig（功能编译期裁剪）是同一个哲学。

## 怎么选

| 场景 | 选谁 |
|---|---|
| 系统固定线程（传感器、通信、UI） | **K_THREAD_DEFINE**（默认答案） |
| 参数/数量运行时才确定（如按配置起 N 个 worker） | k_thread_create |
| 想 k_thread_join 等它结束 | 都可以（join 用 tid） |

## 选项位（⑦）里值得知道的两个

- `K_ESSENTIAL`：标记为"系统关键线程"，它异常终止会触发内核 fatal error
  （默认线程死掉只死自己）；
- `K_FP_REGS`：线程要用 FPU 时必加（F103 无 FPU；F407 有，到时候要加）。

## 与 LDD- 侧对照

Linux 没有"编译期静态定义线程"的概念——进程/线程都是运行时创建。
Zephyr 的 K_THREAD_DEFINE 更像 Linux 的 `__initcall` 系列宏：
**都是"链接期注册、启动期自动执行"**。这套"宏注册"思想在 Zephyr 里
到处都是（SYS_INIT、DEVICE_DT_DEFINE……），看懂一个看懂一串。

## 要点回顾

1. `k_thread_create`：TCB/栈存储调用者出，"运行中初始化"，无堆无失败路径。
2. `K_THREAD_DEFINE`：编译期全定，Zephyr 主推审美。
3. 静态能定的不动态——与 devicetree/Kconfig 同一哲学。

<details>
<summary>Q1：K_THREAD_DEFINE 的线程在 main 之前就跑了吗？</summary>

确切说：内核初始化（z_cstart → 各 init 级别）完成、调度器启动后，
静态线程按优先级参与调度；`main` 本身也是一个线程（见 [4.5](4.5-系统线程.md)），
谁优先级高谁先跑。所以"在 main 里打第一行日志"之前，
别的线程可能已经输出一堆了——调试时别惊讶。

</details>

<details>
<summary>Q2：启动延迟（K_MSEC(n)）有什么用？</summary>

等硬件就绪：比如某传感器上电后要 100ms 才能通信，
它的服务线程延迟启动就不用自己写"开头睡 100ms"。
也是给 main 线程留"先跑完初始化"的时序手段。

</details>

## 衔接

两法都会问你要"优先级"——而 Zephyr 的优先级体系是全内核最反直觉的部分：
**负数是协作式，非负是抢占式**。下一篇 [4.3 优先级两个世界](4.3-优先级两个世界.md)。
