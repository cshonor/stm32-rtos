## 先用人话说一遍（新手铺垫）

前两篇分别给了"手续怎么办"（12.1 的 API）和"硬件从哪来"（12.2 的路径），
这一篇是把它们拼成完整流水线的最后一步：**点亮哪些开关、
写哪几行代码，才能从编译一路走到 socket 连通**。它是 ch08 的
增量篇——增量只有"链路层握手前传"，其余全是旧知识。

类比开店的完整流程：**Kconfig 清单是装修单**——水电（网络栈）、
营业执照（CONFIG_WIFI）、叫号系统（NET_MGMT_EVENT）一项不能少；
**连接代码是开业当天的手续**——注册叫号器（事件回调）→
递申请（NET_REQUEST_WIFI_CONNECT）→ 坐等叫号（k_sem_take）；
**拿到 IP（DHCP）才算正式开业**——没拿到门牌号就接客（发数据），
客人（socket）必然扑空，这是翻车点表里"连上了但 socket 超时"的全部原因。

记住"异步转同步"这个模式：Wi-Fi 连接天生异步（12.1），
但应用往往想要"连不上就不往下走"——`k_sem_take` 就是把叫号器
变成排队凳的标准写法，这个三段式在任何异步 API 上都通用。

| 术语 | 一句话解释 |
|---|---|
| defconfig | 板级默认配置：每块板自带的 Kconfig 初值，prj.conf 在它基础上叠加 |
| shield | Zephyr 的扩展板配置机制：外接模块（如 Wi-Fi 盾板）的 dts/配置打包复用 |
| DHCP | 自动分配 IP 的协议：连上 Wi-Fi 后靠它拿地址，拿到前 socket 发不出去 |
| `NET_EVENT_IPV4_ADDR_ADD` | "IP 地址到手"事件：开 socket 前推荐等它，避开无地址窗口 |
| 异步转同步 | 用信号量把事件回调包装成阻塞等待的通用模式：回调 give、主线程 take |

## 最小 Kconfig 清单

```conf
# 网络栈（ch08 那一套）
CONFIG_NETWORKING=y
CONFIG_NET_IPV4=y
CONFIG_NET_TCP=y
CONFIG_NET_SOCKETS=y
# Wi-Fi 管理面（12.1）
CONFIG_WIFI=y
CONFIG_NET_MGMT=y
CONFIG_NET_MGMT_EVENT=y
# DHCP：连上后拿 IP（不然得配静态地址）
CONFIG_NET_DHCPV4=y
# 驱动：按硬件路径选（12.2），例如 ESP32 原生或 esp_at modem
```

Wi-Fi 驱动本身通常由板级 defconfig 或 shield 配置带进来，prj.conf 只管上面的协议层开关。

## 最小连接代码

```c
static struct net_mgmt_event_callback wifi_cb;
static K_SEM_DEFINE(connected, 0, 1);

static void on_wifi_event(struct net_mgmt_event_callback *cb,
                          uint64_t evt, struct net_if *iface)
{
    if (evt == NET_EVENT_WIFI_CONNECT_RESULT) {
        const struct wifi_status *s = (const struct wifi_status *)cb->info;
        if (s->status == 0)
            k_sem_give(&connected);      /* 连上了，放主线程走 */
    }
}

void wifi_connect_blocking(void)
{
    struct net_if *iface = net_if_get_default();
    struct wifi_connect_req_params params = {
        .ssid = (const uint8_t *)"MyAP", .ssid_length = 4,
        .psk = (const uint8_t *)"password", .psk_length = 8,
        .security = WIFI_SECURITY_TYPE_PSK,
        .channel = WIFI_CHANNEL_ANY,
    };
    net_mgmt_init_event_callback(&wifi_cb, on_wifi_event,
                                 NET_EVENT_WIFI_CONNECT_RESULT);
    net_mgmt_add_event_callback(&wifi_cb);
    net_mgmt(NET_REQUEST_WIFI_CONNECT, iface, &params, sizeof(params));
    k_sem_take(&connected, K_SECONDS(30));   /* 12.1：异步转同步 */
}
```

连上之后是 ch08 的老朋友，一行不改：

```c
int fd = zsock_socket(AF_INET, SOCK_STREAM, IPPROTO_TCP);
zsock_connect(fd, (struct sockaddr *)&addr, sizeof(addr));
zsock_send(fd, "hello\n", 6, 0);
```

## 与 ch08 的衔接点

| 层 | ch08（以太网语境） | 本章（Wi-Fi 增量） |
|---|---|---|
| 链路就绪 | 插网线 / 链路上电即就绪 | 多一步：scan/connect 异步流程 + 等事件 |
| 拿地址 | DHCPv4 | **同一个** DHCPv4，连上后自动触发 |
| socket 编程 | zsock_* | 完全不变 |
| 新增状态机 | 无 | "未连/连接中/已连/断开重连"要自己维护 |

一句话：**Wi-Fi 给 ch08 加的只有"链路层握手"前传**，socket 层及以上零改动。

## 常见翻车点（官方文档语义整理）

| 症状 | 常见原因 |
|---|---|
| connect 事件回 status != 0 | 密码/安全类型不匹配（PSK vs SAE），或 `ssid_length` 忘了不含 '\0'（C 字符串结尾的隐藏终止字节） |
| 事件回调从不触发 | 漏 `CONFIG_NET_MGMT_EVENT=y` 或没调 `net_mgmt_add_event_callback` |
| 连上了但 socket 超时 | DHCP 没拿到地址就发数据；应再等 IPv4 地址就绪事件 |
| 回调里打印卡死 | 回调跑在系统 workqueue，重活/长日志堵全局（12.1） |

## 要点回顾

1. 最小配置 = ch08 网络栈 + `CONFIG_WIFI`/`NET_MGMT(_EVENT)` + DHCPv4 + 板级驱动。
2. 连接代码三步：注册事件回调 → 发 `NET_REQUEST_WIFI_CONNECT` → sem 等结果。
3. 连上后 socket 代码与 ch08 逐字节相同；本篇配置摘自官方 sample 语义、**未经实测**，硬件到位后以 `samples/net/wifi` 校准。

<details>
<summary>Q1：ssid_length 到底算不算结尾的 '\0'？</summary>

不算。`.ssid` / `.psk` 都是"指针 + 显式长度"，长度是有效字节数
（`"MyAP"` 是 4 不是 5）；多算 1 会把 '\0' 也发进认证流程导致失败。

</details>

<details>
<summary>Q2：DHCP 也要等事件吗？</summary>

推荐等。`NET_EVENT_IPV4_ADDR_ADD`（net_mgmt 的 IPv4 事件组）通知地址就绪后
再开 socket 最稳；连上就用可能撞上"还没拿到 IP"的窗口。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| `ssid_length` 算上结尾 `'\0'` | C 字符串习惯性 +1 | **不算**：长度是有效字节数（`"MyAP"` 是 4），多算 1 会把 '\0' 发进认证流程导致失败 |
| 连上 Wi-Fi 就能发 socket | 连上 = 能通 | 可能还没拿到 IP：推荐等 `NET_EVENT_IPV4_ADDR_ADD` 再开 socket |
| 事件回调不触发是驱动问题 | 怀疑硬件/驱动 | 先查两样：`CONFIG_NET_MGMT_EVENT=y` 和 `net_mgmt_add_event_callback` 漏没漏 |
| 驱动配置全写进 prj.conf | 配置都归 prj.conf 管 | Wi-Fi 驱动通常由板级 defconfig / shield 带入，prj.conf 只管协议层开关 |

## 代码自测

_注：本节示例按本篇正文语义编写，未在本仓库环境实跑，仿真验证见「验证路径」。_

最小流水线：Kconfig 清单 + 异步转同步连接 + socket 发一句 hello。

```conf
# prj.conf
CONFIG_NETWORKING=y
CONFIG_NET_IPV4=y
CONFIG_NET_TCP=y
CONFIG_NET_SOCKETS=y
CONFIG_WIFI=y
CONFIG_NET_MGMT=y
CONFIG_NET_MGMT_EVENT=y
CONFIG_NET_DHCPV4=y
```

```c
#include <zephyr/kernel.h>
#include <zephyr/net/net_if.h>
#include <zephyr/net/net_mgmt.h>
#include <zephyr/net/wifi_mgmt.h>
#include <zephyr/net/socket.h>

static struct net_mgmt_event_callback wifi_cb;
static K_SEM_DEFINE(connected, 0, 1);

static void on_wifi_event(struct net_mgmt_event_callback *cb,
                          uint64_t evt, struct net_if *iface)
{
    if (evt == NET_EVENT_WIFI_CONNECT_RESULT) {
        const struct wifi_status *s = (const struct wifi_status *)cb->info;
        if (s->status == 0)
            k_sem_give(&connected);          /* 连上了，放主线程走 */
    }
}

void main(void)
{
    struct net_if *iface = net_if_get_default();
    struct wifi_connect_req_params params = {
        .ssid = (const uint8_t *)"MyAP", .ssid_length = 4,   /* 不含 '\0' */
        .psk = (const uint8_t *)"password", .psk_length = 8,
        .security = WIFI_SECURITY_TYPE_PSK,
        .channel = WIFI_CHANNEL_ANY,
    };
    net_mgmt_init_event_callback(&wifi_cb, on_wifi_event,
                                 NET_EVENT_WIFI_CONNECT_RESULT);
    net_mgmt_add_event_callback(&wifi_cb);
    net_mgmt(NET_REQUEST_WIFI_CONNECT, iface, &params, sizeof(params));
    if (k_sem_take(&connected, K_SECONDS(30)) != 0)
        return;                              /* 30 秒没连上 */

    int fd = zsock_socket(AF_INET, SOCK_STREAM, IPPROTO_TCP);
    zsock_connect(fd, (struct sockaddr *)&addr, sizeof(addr));
    zsock_send(fd, "hello\n", 6, 0);
}
```

**预期现象**：

- 连接事件回调后 `k_sem_take` 返回 0，socket 发出 `hello\n`；
- `ssid_length` 写成 5：认证失败，事件回 status != 0；
- 漏 `CONFIG_NET_MGMT_EVENT=y`：回调从不触发，30 秒超时返回。

**验证路径**：实机（带 Wi-Fi 的 Zephyr 板）+ 串口，以官方 `samples/net/wifi` 校准。

**常见翻车点**：

- 连上立刻发数据撞上 DHCP 窗口——再等 `NET_EVENT_IPV4_ADDR_ADD` 最稳；
- 回调里打印长日志——跑在系统 workqueue，堵全局。
