## 这一篇讲什么

LED/按钮是"应用自己读属性"，SPI/I2C 是**真驱动链路**：
dts 节点 → compatible → binding → 驱动 → struct device → 总线 API。
这一篇逐环拆开，讲清总线父子关系和 SPI 特有的 cs-gpios。

## 先用人话说一遍（新手铺垫）

9.3 的 LED 是"无驱动"节点——应用自己读属性自己操作，相当于自助。
SPI/I2C 传感器不一样：读写时序、寄存器协议都是现成驱动写好的，
你要做的只是**把你的硬件信息准确登记，让驱动能找到并认领它**。
本篇的"匹配链"就是这条登记—认领流水线。

类比快递入柜：你在 dts 里填的 `compatible = "bosch,bme280"` 是
**包裹上的收件码**——binding yaml 是物业的登记表（查格式合不合法），
驱动里的 `DT_DRV_COMPAT` 是快递员手里的认领清单（对得上才领走），
最后 `struct device` 生成 = 包裹入柜完成，应用 `DEVICE_DT_GET`
凭码取件。**链上任何一环断了，包裹就躺在中转站**——
构建不报错时，按这条链从前往后逐环查，命中率极高。

总线父子关系同理：子节点写在 `&spi1` 里面，意思就是"这颗芯片
挂在 SPI1 这条总线上"——`reg` 在 SPI 里是**片选编号**（第几个片选脚），
在 I2C 里是**从机地址**，因为两条总线"点名"的方式本来就不同：
SPI 靠拉线（一人一管），I2C 靠喊号（广播地址）。

| 术语 | 一句话解释 |
|---|---|
| pinctrl | 引脚复用配置：声明某个外设的 SCK/SDA 等信号落在哪个物理引脚 |
| 片选（CS） | SPI 的"点名线"：主机拉低哪根 CS 就和哪个从机说话 |
| cs-gpios | SPI 控制器节点上的片选 GPIO 数组；子节点 reg = 该数组的下标 |
| `DT_DRV_COMPAT` | 驱动源码里的认领字符串：与 dts 的 compatible 对应（逗号换下划线） |
| `DEVICE_DT_INST_DEFINE` | 驱动侧宏：为每个 okay 的匹配节点在编译期生成一份设备实例 |
| I2C 从机地址 | I2C 总线上设备的 7 位编号，控制器按它寻址，写在子节点 reg 里 |

## 一条完整的匹配链

"在 SPI1 上挂一颗 BME280"的 overlay：

```
&spi1 {
    status = "okay";                    /* ① 先开控制器 */
    pinctrl-0 = <&spi1_sck_pa5 &spi1_miso_pa6 &spi1_mosi_pa7>;  /* ② 引脚复用 */
    pinctrl-names = "default";
    cs-gpios = <&gpioa 4 GPIO_ACTIVE_LOW>;                      /* ③ 片选 */

    bme280@0 {                          /* ④ 子节点：挂在 spi1 总线上 */
        compatible = "bosch,bme280";
        reg = <0>;                      /* SPI 上 reg = 片选索引（第 0 个 cs） */
        spi-max-frequency = <4000000>;
        status = "okay";
    };
};
```

匹配链逐环：

```
compatible = "bosch,bme280"
  → bindings yaml（属性 schema）
  → 驱动里 DT_DRV_COMPAT = bosch_bme280 + CONFIG_BME280=y（9.1 分工表）
  → DEVICE_DT_INST_DEFINE 生成 struct device → 应用 DEVICE_DT_GET 拿指针
```

**compatible 是链上唯一"人写的字符串"**，写错一个字母，
构建期 binding 检查直接报错。

## 总线父子关系：子节点 = "挂在这条总线上"

| | SPI | I2C |
|---|---|---|
| 父节点 | `&spi1`（控制器） | `&i2c1`（控制器） |
| 子节点 `reg` | **片选索引** | **7 位从机地址**（如 `<0x76>`） |
| 节点名后缀 | `bme280@0` | `bme280@76` |
| 寻址谁负责 | 驱动收发前拉对应 cs | 控制器硬件按地址发 START（I2C 的开场信号：宣告一次传输开始） |

I2C 对照写法：

```
&i2c1 {
    status = "okay";
    pinctrl-0 = <&i2c1_scl_pb8 &i2c1_sda_pb9>;
    pinctrl-names = "default";
    bme280@76 { compatible = "bosch,bme280"; reg = <0x76>; status = "okay"; };
};
```

**同一份驱动两种挂法都支持**——驱动对 SPI/I2C 各注册一份 bus ops（总线操作函数集：驱动挂在某条总线上时交出的收发接口），
dts 写在哪条总线下就走哪条通路。传感器换接口，应用代码零改动。

## cs-gpios：SPI 的 Zephyr 特色坑

- 写在**控制器**节点上，是数组（可多路片选）；子节点 `reg = <0>` 指第 0 个；
- 极性（`GPIO_ACTIVE_LOW`）写在 cs-gpios 里，驱动收发时自动拉/放；
- 对照裸机（01-stm32）手写 `GPIOA->BSRR = 1<<4`：DT 时代由驱动按声明自动完成。

应用侧读法：

```c
static const struct spi_dt_spec spi_dev =
    SPI_DT_SPEC_GET(DT_NODELABEL(bme280), SPI_WORD_SET(8) | SPI_TRANSFER_MSB, 0);
spi_write_dt(&spi_dev, &buf);
```

## 原书怎么说 / 实际是什么

| 原书怎么说 | 实际是什么（Zephyr 3.x） |
|---|---|
| 引脚复用写成散装 pinmux 节点 | 现行统一 **pinctrl**：`pinctrl-0` 引用 `pinctrl/soc/` 预定义引脚组 |
| 驱动代码里写死片选 GPIO | 现行强制 cs-gpios 声明在 dts，驱动只读 |
| `spi_write(dev, ...)` 传裸指针 | 推荐 `spi_write_dt(&spec, ...)`，片选/频率由 spec 携带 |

## 要点回顾

1. 匹配链：compatible → binding → DT_DRV_COMPAT → Kconfig → 生成设备——缺一环都点不亮。
2. 子节点挂总线：SPI reg 是片选索引，I2C reg 是 7 位地址；同一驱动可双挂。
3. cs-gpios 写在控制器上、是数组；片选拉放驱动自动完成，告别手写 BSRR。
4. 引脚复用走 pinctrl 预定义引脚组，不再散装 pinmux。

<details>
<summary>Q1：dts 里 okay 了 spi1，设备还是不在？</summary>

按链排查：① 控制器 pinctrl 引脚组；② CONFIG_SPI=y；③ 子节点 compatible 拼写；
④ 传感器 CONFIG_BME280=y。四个开关分属 dts/Kconfig 两边——
"两个都要对，驱动才真的进固件"（9.1）。

</details>

<details>
<summary>Q2：两个同型号传感器怎么写？</summary>

写两个子节点，reg 不同（不同 cs 或不同 I2C 地址），各打各的 nodelabel。
驱动侧 DT_INST_FOREACH_STATUS_OKAY 对每个 okay 实例生成独立 config/data——
**一份驱动代码服务 N 个实例**，这是设备模型对比裸机"一份驱动死磕一个硬件"的核心收益。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| SPI 子节点 `reg` 是地址 | I2C 里 reg 是从机地址，SPI 类比之 | SPI 里 reg 是 **cs-gpios 数组的下标**（片选索引），`reg = <0>` 指第 0 个片选 |
| dts okay 了设备就该在 | okay = 万事俱备 | 按链查四环：pinctrl 引脚组、CONFIG_SPI=y、compatible 拼写、驱动 CONFIG（如 CONFIG_BME280=y） |
| 片选 GPIO 写在驱动代码里 | 裸机习惯 `GPIOA->BSRR = 1<<4` | 现行强制 cs-gpios 声明在控制器节点，驱动收发时自动拉/放 |
| 一份驱动死磕一个硬件 | 裸机一份驱动一个设备 | `DT_INST_FOREACH_STATUS_OKAY`：一份驱动代码服务 N 个 okay 实例 |

## 代码自测

_注：本节示例按本篇正文语义编写，未在本仓库环境实跑，仿真验证见「验证路径」。_

演示完整匹配链：overlay 挂一颗 SPI 传感器，应用 `SPI_DT_SPEC_GET` 收发。

```dts
/* app.overlay */
&spi1 {
    status = "okay";
    pinctrl-0 = <&spi1_sck_pa5 &spi1_miso_pa6 &spi1_mosi_pa7>;
    pinctrl-names = "default";
    cs-gpios = <&gpioa 4 GPIO_ACTIVE_LOW>;   /* 片选数组写在控制器上 */

    bme280@0 {
        compatible = "bosch,bme280";
        reg = <0>;                           /* 片选索引，不是地址 */
        spi-max-frequency = <4000000>;
        status = "okay";
    };
};
```

```c
/* main.c */
static const struct spi_dt_spec spi_dev =
    SPI_DT_SPEC_GET(DT_NODELABEL(bme280),
                    SPI_WORD_SET(8) | SPI_TRANSFER_MSB, 0);

void main(void)
{
    if (!device_is_ready(spi_dev.bus)) {
        return;                 /* 匹配链断环在这里现形 */
    }
    /* buf 为按 SPI API 组织的收发缓冲，片选/频率由 spec 携带 */
    spi_write_dt(&spi_dev, &buf);      /* 片选拉放驱动自动完成 */
}
```

**预期现象**：

- `build/zephyr/zephyr.dts` 里 bme280@0 挂在 spi1 下，cs-gpios 指向 gpioa 4；
- `device_is_ready` 通过、`spi_write_dt` 期间 PA4 被驱动自动拉低再放高；
- 故意写错 compatible 一个字母：编译期 binding 检查直接报错。

**验证路径**：`west build -b nucleo_f103rb`（prj.conf 加 `CONFIG_SPI=y`、`CONFIG_BME280=y`）后烧真板 + 逻辑分析仪看 CS；无硬件时只验证构建与 zephyr.dts 产物。

**常见翻车点**：

- 漏 `pinctrl-0` 引脚组——构建不报错，运行时设备不在；
- `reg` 写成设备地址（I2C 思维）——SPI 的 reg 是 cs-gpios 下标。
