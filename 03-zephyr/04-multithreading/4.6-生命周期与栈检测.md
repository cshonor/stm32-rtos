## 这一篇讲什么

线程的三种死法（正常返回 / abort / 异常）、怎么"等它死"（join）、
以及死后验尸工具（栈水位、栈保护）。收尾 ch04。

## 先用人话说一遍（新手铺垫）

线程的三种死法对应员工的三种离开：**正常离职**（函数 return，
交接清楚，Zephyr 里合法、FreeRTOS 里算事故）、
**被当场开除**（`k_thread_abort`，人走了，但他手里的钥匙、
未还的公章——信号量、互斥量、申请的内存——没人替你收）、
**工伤事故**（除零、越界，全楼拉警报：fatal error，停机待查）。
`k_thread_join` 就是"等他办完离职手续我再走"——
顺便完成结果交接（同步）。

栈溢出的三道防线用"保险丝与体检"理解：MPU 保护和栈哨兵是
**保险丝**——烧断（触发异常）时事故已经发生，作用是防止蔓延；
水位统计是**定期体检**——告诉你"历史最深用到 700 字节"，
让你把 1024 的栈调到合理的余量，事故压根不发生。
新手的常见误区是只配保险丝不做体检，然后把"没烧断"
当成"栈大小配对了"——没烧断只是运气好。

调栈那句"历史最深用量 × 1.5"值得背下来：它把栈大小
从玄学变成了测量题。20K RAM 的 F103 上，每个线程省下的
几百字节都是实打实的预算。

| 术语 | 一句话解释 |
|---|---|
| `k_thread_join` | 阻塞等到目标线程结束（≈ pthread_join（pthread（POSIX 线程：Linux/桌面 C 的标准线程 API）的同款等待函数））：一次性任务的标准收尾 |
| `k_thread_abort` | 强制终止线程：不回收它持有的资源，只当逃生门用 |
| fatal error | 内核级的致命错误处理：默认打印现场停机，可改成记录后看门狗复位 |
| 弱函数（weak） | 可被应用覆盖的默认实现：`k_sys_fatal_error_handler` 就是这种钩子 |
| 悬垂 tid | 指向已死线程的句柄：除 join/查名字外的用法都是未定义行为 |

## 三种死法

| 死法 | 路径 | 善后 |
|---|---|---|
| **正常返回** | 入口函数 return（[4.1](4.1-线程是什么.md)：Zephyr 里合法） | 内核标记 dead，等待 join 或资源回收 |
| **k_thread_abort(tid)** | 别的线程（或自己）强制终止 | 同上；**abort 自己 = 立刻让出 CPU** |
| **异常**（除零/越界/栈溢出触发 MPU（存储保护单元：可给内存划硬件保护区，越界当场触发异常）） | CPU 异常 → 内核 fatal error 处理 | 默认进 `k_fatal_error` → 打印现场停机 |

对照 FreeRTOS：只有"任务调 vTaskDelete"一条死路（且函数返回是事故）。
Zephyr 把"正常结束"扶正，让线程模型更接近 pthread
（pthread 也是 return 正常退出 + pthread_join 收尸）。

## k_thread_join：等它死，顺便同步

```c
k_tid_t t = k_thread_create(...);   /* 或 K_THREAD_DEFINE 的符号名 */
k_thread_join(t, K_FOREVER);        /* 阻塞到 t 结束 */
```

等价于 pthread_join。典型用途："主线程 fork 出计算线程，
join 等结果"——一次性任务的标准模式。
**注意 join 的是 tid，死的线程也能 join**（立刻返回），
但不能 join 自己（死锁，内核会拦）。

abort 的规矩和 FreeRTOS vTaskDelete 同款警告：
**abort 不替你收拾线程自己拿的资源**（信号量、互斥量、申请的内存）。
能设计"正常退出路径"就别用 abort——它只是逃生门。

## 栈溢出：三道防线怎么配

复习 [4.1](4.1-线程是什么.md) 的家底，加上使用姿势：

```conf
# prj.conf
CONFIG_HW_STACK_PROTECTION=y    # 防线1：MPU 栈底保护区，越界当场 MemManage
CONFIG_STACK_SENTINEL=y         # 防线2：栈底魔数，切换时抽查（无 MPU 时的低配）
CONFIG_THREAD_STACK_INFO=y      # 防线3：允许运行时查栈信息
CONFIG_THREAD_RUNTIME_STATS=y   # 配套：水位/CPU 占用统计
```

运行时读水位（开发期调栈大小的正规方法）：

```c
size_t unused;
k_thread_stack_space_get(tid, &unused);
printk("%s 栈剩余 %u 字节\n", k_thread_name_get(tid), unused);
```

**调栈方法论**（与 [freertos 2.3](../../02-freertos/02-heap-memory/2.3-本仓选型heap_4.md)
"先宽后紧"同哲学）：先给宽裕值 → 跑全功能 → 读水位 → 收紧到
"历史最深用量 × 1.5"。防线 1/2 是保险丝，水位统计是调表工具——
**保险丝不能代替调表**。

## 栈大小去哪查（链接期视角）

静态栈（K_THREAD_STACK_DEFINE / K_THREAD_DEFINE）全部落在 `.bss`（程序里"未初始化/清零的全局与静态变量"的段，占 RAM），
`nm zephyr.elf | grep stack`（nm：列出可执行文件符号表的工具）或 map 文件直接可见——
20K RAM 的 F103 上，所有线程栈 + main 栈 + idle 栈 + 中断栈的总账，
**链接期就该算平**，不要等运行时爆炸。

## 要点回顾

1. 三种死法：返回（合法）/ abort（逃生门）/ 异常（fatal）；join 等死并同步。
2. abort 不收资源，能走正常退出就别 abort。
3. 栈保护三道防线 + 水位统计；静态栈让总账链接期可算。

<details>
<summary>Q1：线程死了 tid 还能用吗？</summary>

死了的 tid 可以 join（立即返回）、可以查名字；
但**不能**重新调度它（K_THREAD_DEFINE 的线程死了就是死了，
想"重启"得再 k_thread_create 一个新的，复用同一块栈/TCB 存储）。
悬垂 tid 的其他用法 = 未定义行为，和 FreeRTOS 悬垂句柄同款规矩。

</details>

<details>
<summary>Q2：fatal error 后能自动复位而不是停机吗？</summary>

能，`k_sys_fatal_error_handler` 是可覆盖的弱函数（weak）——
产品里通常改成"记录现场 → 看门狗（一种硬件定时器：程序卡死超时不喂它，它就复位芯片）复位"。
学习阶段保持默认（停机），调试器里看现场比反复复位有用得多。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| abort 后资源自动回收 | 线程终止了，它拿的资源内核会收拾 | `k_thread_abort` **不回收**它持有的信号量/互斥量/申请的内存；能走正常退出就别 abort，它只是逃生门 |
| join 只能等活线程 | 线程都死了还 join 什么 | 死的线程也能 join（立即返回）；但**不能 join 自己**（死锁，内核会拦） |
| 栈没炸 = 大小配对 | 哨兵没报警、MPU 没异常，栈配得刚好 | 保险丝没烧只是运气好；调栈靠水位统计——跑全功能读历史最深用量，×1.5 收紧 |
| 线程死了 tid 继续用 | 句柄还在，拿来操作应该没事 | 死 tid 只能 join/查名字；其他用法 = 未定义行为（悬垂 tid），想"重启"得重新 k_thread_create |
| fatal error 只能停机 | 异常 = 打印现场停机，没得选 | `k_sys_fatal_error_handler` 是可覆盖的弱函数；产品里改成记录现场 + 看门狗复位，学习阶段保持默认 |

## 代码自测

_注：本节代码按 Zephyr API 语义编写，未在本仓库环境实跑，仿真验证见「验证路径」。_

```c
/* prj.conf 需开：CONFIG_THREAD_STACK_INFO=y  CONFIG_THREAD_RUNTIME_STATS=y */
#include <zephyr/kernel.h>

static void calculator(void *a, void *b, void *c)
{
    int *result = a;
    *result = 6 * 7;                       /* 结果走共享变量交接 */
    k_msleep(300);
    printk("calculator 干完，return 走人\n");
}

K_THREAD_STACK_DEFINE(calc_stack, 1024);
static struct k_thread calc_data;

int main(void)
{
    int result = 0;
    k_tid_t tid = k_thread_create(&calc_data, calc_stack,
                                  K_THREAD_STACK_SIZEOF(calc_stack),
                                  calculator, &result, NULL, NULL,
                                  5, 0, K_NO_WAIT);

    k_thread_join(tid, K_FOREVER);         /* 等它死，顺便完成结果交接 */
    printk("join 返回，结果 = %d\n", result);

    size_t unused = 0;
    k_thread_stack_space_get(tid, &unused);   /* 死线程也能查 */
    printk("栈剩余 %u / 1024 字节\n", (unsigned)unused);
    return 0;
}
```

**预期现象**：

- 先打印 `calculator 干完，return 走人`，再打印 `join 返回，结果 = 42`——join 等到正常返回；
- 最后打印栈剩余（预期 900+ 字节，说明 1024 配宽了，可按"历史最深用量 × 1.5"收紧）；
- 全程无 fatal error。

**验证路径**：`west build -b qemu_cortex_m3` 后 `west build -t run`，QEMU 控制台看输出。

**常见翻车点**：

- join 自己 = 死锁（内核会拦）；abort 代替 join 则结果交接和资源都没人管；
- 没开 `CONFIG_THREAD_STACK_INFO` 时 `k_thread_stack_space_get` 拿不到数；
- 线程死了还想用旧 tid"重启"——悬垂 tid 是未定义行为，重新 `k_thread_create` 一个。
