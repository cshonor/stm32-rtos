## 这一篇讲什么

一个能 `west build` 的 Zephyr 应用，最少只需要**三个文件**。
本篇把骨架摆出来、逐个文件讲职责，再解释构建系统怎么把
"应用 + 板卡 + 内核"三方输入合成一个镜像。

## 先用人话说一遍（新手铺垫）

第一次见 Zephyr 工程的人常被文件数量唬住：工作区几百兆，
轮到写应用却只要三个文件。这一篇就是把"你的应用最少要交代什么"
压缩到三张表——少了构建系统不知道怎么组装你，多了是给它添乱。

接着 [1.2](../01-introduction/1.2-内核vs平台.md) 的精装房类比：
搬进精装房（Zephyr 平台）后，你要向物业报备三件事——
**带来哪些家具**（CMakeLists.txt：我的源文件）、
**开通哪些功能**（prj.conf：要 GPIO、要日志，勾选单）、
**实际的生活**（main.c：你的代码）。板级 dts 是原始户型图，
overlay 是**不动承重墙前提下的局部改造单**：
在排针上接了块传感器小板，填张改造单就行，不用重画户型图。

三方合成的图是本篇的眼：你的三张表只是三分之一，
板卡目录和内核各出一份输入，CMake 把三方合并后才开编。
理解"合成"就理解了为什么手写顶层 Makefile 行不通——
你重写不了那个合并逻辑。

| 术语 | 一句话解释 |
|---|---|
| `find_package(Zephyr ...)` | CMake 语句：把 Zephyr 整套构建逻辑拉进你的工程，`project()` 必须排在它后面 |
| `target_sources(app ...)` | CMake 语句：把你的 .c 文件挂到 app 目标上，多文件就列多个 |
| app 目标 | Zephyr 构建系统预定义的编译目标，应用代码统一挂到它名下 |
| dtsi | SoC 级的硬件描述片段：被板级 dts 包含，回答"这颗芯片有什么外设" |

## 最小骨架

```
app/
├── CMakeLists.txt      ← 构建入口：我是谁、我有哪些源文件
├── prj.conf            ← Kconfig 片段：我要哪些内核功能
└── src/
    └── main.c          ← 应用代码
```

可选但常见：`app.overlay`（devicetree overlay，在板级 dts 上改/加硬件描述）、
`boards/nucleo_f103rb.overlay`（只对某板生效，按板名匹配）、
`Kconfig`（应用自定义配置符号，有自定义 CONFIG 才需要）。

## 三个文件逐个看

**CMakeLists.txt**——套路化到可以背：

```cmake
cmake_minimum_required(VERSION 3.20.0)
find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})   # 把内核构建系统拉进来
project(my_app)                                          # 必须在 find_package 之后
target_sources(app PRIVATE src/main.c)                   # 源文件挂到 app 目标
```

三行角色：①找到 Zephyr 的 CMake 包（它定义了 `app` 目标，工具链（编译器、链接器等一整套构建工具的合称）选择也藏在这里）；
②声明工程；③挂源文件。**顺序不能动**——`project()` 在 find_package 之后是硬要求。

**prj.conf**——Kconfig 片段，逐行 `CONFIG_XXX=y`（如 `CONFIG_GPIO=y`）。
它不是"配置文件被读取"那么简单：这些行会**并入整棵 Kconfig 依赖树**
求解（依赖自动补全、冲突会报错），结果生成 autoconf.h。机制见 [3.3](3.3-Kconfig怎么工作.md)。

**main.c**——唯一没规矩的文件。`main()` 是应用的入口，
但它不是"第一行代码"：内核初始化、静态线程创建都发生在 main 之前
（[4.5 系统线程](../04-multithreading/4.5-系统线程.md)）。

## overlay：改硬件描述不动板级文件

devicetree 的分层（细节归 [ch09](../09-devicetree/README.md)）：

```
SoC dtsi（STM32F103 有什么外设）
   ↓ 被包含
板级 dts（nucleo_f103rb 启用了哪些、引脚怎么接、led0 在哪）
   ↓ 叠加
app.overlay（应用自己的改动：换个引脚、加个传感器节点）
```

overlay 的语法就是 dts 语法，构建时被**合并**到板级树上。
典型动机：板子不变，但你在某个排针上接了块传感器小板——
不为这点事去 fork（复制一份仓库/文件到自己名下再改）板级 dts。这也是"自制板原型期"的偷懒方案
（[1.3 Q1](../01-introduction/1.3-板卡与架构.md)）。

## 构建时的三方合成

```
west build -b nucleo_f103rb app
        │
        ├─ 应用输入：CMakeLists.txt + prj.conf + *.overlay
        ├─ 板卡输入：boards/st/nucleo_f103rb/{Kconfig, defconfig, dts}
        └─ 内核输入：Kconfig 依赖树 + 驱动/子系统源码
        │
        ▼
   CMake 配置阶段：Kconfig 求解 → autoconf.h；DTS 合并 → 生成头文件
        ▼
   Ninja 编译链接 → zephyr.elf（产物解剖见 [3.4](3.4-构建产物解剖.md)）
```

**为什么 Zephyr 工程不该手写顶层 Makefile**：三方输入的合并逻辑
（Kconfig 依赖求解、DTS 包含与 overlay、按配置裁剪编译单元（每个 .c 独立编译成一个 .o，称为一个编译单元））
全部实现在 Zephyr 的 CMake 模块里。手写 Makefile 等于重写这套逻辑——
裸机篇手写 Makefile 是为了学原理，到了 Zephyr 就别和工业装置较劲。

## 要点回顾

1. 最小骨架三文件：CMakeLists.txt（挂源码）、prj.conf（选功能）、main.c。
2. `find_package(Zephyr ...)` 拉入整个内核构建系统；`project()` 必须在它之后。
3. overlay 在板级 dts 上叠加应用的硬件改动，不动板级文件。
4. 构建 = 应用/板卡/内核三方输入的合成；手写顶层 Makefile 是在重写这套合成逻辑。

<details>
<summary>Q1：多个 .c 文件怎么加？</summary>

`target_sources(app PRIVATE src/a.c src/b.c)` 一行列全，
或分多次调用。子目录有独立 Kconfig/源码组织时，
用 `add_subdirectory()` + 子目录自己的 CMakeLists。

</details>

<details>
<summary>Q2：prj.conf 和 boards/xxx.conf 同时存在，谁赢？</summary>

合并，且**更具体的赢**：应用级 boards/<板>.conf 只对该板生效，
与 prj.conf 冲突时以板级 conf 为准（它更靠近"最终目标"）。
同类优先级还有 defconfig（板卡出厂默认）在最底层。

</details>

## 坑点速查

| 坑点 | 书 / 常识怎么说 | 实际是什么 |
|---|---|---|
| project() 位置随意 | CMake 工程都是先 project() 再 find_package | **顺序反了**：`find_package(Zephyr ...)` 在前、`project()` 在后是硬要求 |
| prj.conf 只是被读取的配置 | 写一行 `CONFIG_X=y`，构建系统照单执行 | 这些行并入整棵 Kconfig 依赖树求解：依赖自动补全，依赖不满足会被静默丢弃 |
| prj.conf 永远赢 | 应用配置肯定盖过板级配置 | 合并且**更具体的赢**：boards/<板>.conf 与 prj.conf 冲突时以板级 conf 为准 |
| 改硬件要 fork 板级 dts | 排针上接了块传感器小板，得去改板级文件 | 写个 app.overlay 就近叠加即可，不动板级文件 |

## 代码自测

_注：本节代码按 Zephyr API 语义编写，未在本仓库环境实跑，仿真验证见「验证路径」。_

最小骨架三文件，照抄即可编：

```cmake
# CMakeLists.txt —— 顺序是硬要求
cmake_minimum_required(VERSION 3.20.0)
find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})  # 拉入内核构建系统
project(my_app)                                        # 必须在 find_package 之后
target_sources(app PRIVATE src/main.c)                 # 源文件挂到 app 目标
```

```conf
# prj.conf —— 勾选单，并入 Kconfig 依赖树求解
CONFIG_GPIO=y
CONFIG_MAIN_STACK_SIZE=2048
```

```c
/* src/main.c —— main 不是第一行代码：内核初始化、静态线程创建都在它之前 */
#include <zephyr/kernel.h>

int main(void)
{
    printk("skeleton up, main stack = %d\n", CONFIG_MAIN_STACK_SIZE);
    return 0;   /* main 返回合法（4.5 细讲） */
}
```

**预期现象**：

- `west build` 配置阶段无报错，生成 `build/zephyr/zephyr.elf`；
- 控制台打印 `skeleton up, main stack = 2048`——prj.conf 里的值变成了代码里的宏；
- 删掉 prj.conf 的 `CONFIG_MAIN_STACK_SIZE=2048` 重编，打印变回默认 1024——配置链走通。

**验证路径**：`west build -b qemu_cortex_m3 <app目录>` 后 `west build -t run`，QEMU 控制台看输出。

**常见翻车点**：

- `project()` 写到 `find_package` 前面，配置阶段直接报错；
- 源文件放 src/ 却写 `target_sources(app PRIVATE main.c)`，找不到文件；
- 改完 prj.conf 行为没变：先 `west build -t pristine` 再编（3.4 细讲）。
