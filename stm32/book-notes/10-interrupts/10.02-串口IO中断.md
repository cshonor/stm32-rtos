# 10.02 串口 I/O 中断

> 书：第 10 章 中断 · 10.02 串口 I/O 中断（原书 p135–153 区间内）
> 上一篇：[10.01 轮询与中断](10.01-轮询与中断.md) ｜ 下一篇：[10.03 中断例程](10.03-中断例程.md)
> 对应实验：主机侧交叉编译（`--target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding`）

## 书这一节讲什么

一句话：**把串口的接收/发送改成中断驱动**——
使能中断、写 ISR、让 CPU 不再空等。

书讲的是"打开串口中断"。裸机上这里有个**和"漏开时钟"并列的第二号静默失败**：
**中断使能是两道门，漏一个就不进中断，而且不报错。**

## 一、两道门：漏一个静默不进中断

```
外设事件 → [门 1: 外设自己的中断使能位] → NVIC → [门 2: NVIC_ISER] → CPU
```

以 USART1 接收中断为例：

```c
/* 门 1：外设侧（USART1_CR1 的 RXNEIE，bit5） */
USART1_CR1 |= (1u << 5);                       /* RXNEIE：收到字节就触发 */

/* 门 2：NVIC 侧（Cortex-M 的中断使能寄存器） */
#define NVIC_ISER1 (*(volatile uint32_t *)0xE000E104u)
NVIC_ISER1 = (1u << (37u - 32u));              /* USART1 的 IRQn = 37 */
```

**IRQn 怎么算进哪个寄存器**：

```
ISER0: IRQn 0..31    地址 0xE000E100
ISER1: IRQn 32..63   地址 0xE000E104     ← 37 在这里，位 (37-32)=5
ISER2: IRQn 64..95   地址 0xE000E108
```

所以 `NVIC_ISER1 = (1u << 5)`。

⚠ **一定要用 `=` 而不是 `|=`**：

```c
NVIC_ISER1 = (1u << 5);      /* ✅ 写 1 使能，写 0 无效（硬件设计） */
NVIC_ISER1 |= (1u << 5);     /* ⚠ 也能工作，但读-改-写没必要且非原子 */
```

NVIC 的 ISER/ICER 是"**写 1 生效、写 0 无效**"的设计（和
[ch04 4.12](../04-numbers-and-bitops/4.12-用位操作控制内存映射IO寄存器.md) 的 `BSRR` 同一思路），
所以**直接写常量**就行，不需要先读。

| 漏掉 | 现象 | 怎么查 |
|---|---|---|
| 门 1（RXNEIE） | 收到字节了，`SR` 的 RXNE 是 1，但 **NVIC 收不到请求** | 读 `USART1_CR1` bit5 |
| 门 2（NVIC_ISER） | 外设发了请求，但 **CPU 不看** | 读 `NVIC_ISER1` bit5 |
| 两个都漏 | 什么都不发生（最常见） | 两个都读 |

## 二、Cortex-M 特有：ISR 就是普通 C 函数

这是本书这条线上最容易被"通用 C 知识"误导的地方。

| 架构 | ISR 要做什么 | C 里怎么声明 |
|---|---|---|
| AVR / PIC / 8051 / ARM7（传统） | **手动保存寄存器、手动 `RETI`** | `__attribute__((interrupt))` / `__interrupt` |
| **Cortex-M（M0/M3/M4/M7）** | **什么都不用做** | **普通函数** |

原因是 Cortex-M 的中断响应**硬件自动完成**：

```
中断发生
  → 硬件把 8 个寄存器（r0-r3, r12, lr, pc, xpsr）压入当前栈（32 字节）
  → 硬件从向量表取 ISR 地址装进 PC
  → 执行你的 ISR（就是一个普通 C 函数）
  → ISR 用 bx lr 返回（lr 是特殊的 EXC_RETURN 值 0xFFFFFFFx）
  → 硬件自动弹栈恢复，回到被打断的地方
```

ch03 实测的向量表就是这套机制的入口：

```
[ok]   [ 1] 0x08000061 -> Reset_Handler
[ok]   [ 3] 0x080000B5 -> HardFault_Handler  (弱别名 -> Default_Handler)
[ok]   [22] 0x080000B5 -> EXTI0_IRQHandler   (弱别名 -> Default_Handler)
```

## 三、实测：加 `__attribute__((interrupt))` 会怎样？

这是个可以当场测的问题。同一段 ISR，两个版本：

```c
/* 版本 A：普通函数（Cortex-M 正统） */
void USART1_IRQHandler(void){
    if (USART1_SR & RXNE) { g_byte = (uint8_t)USART1_DR; g_flag = 1; }
}
/* 版本 B：加 interrupt 属性 */
__attribute__((interrupt)) void USART1_IRQHandler(void){ ... }
```

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding -Os -c isr.c
$ llvm-objdump -d isr.o
00000000 <USART1_IRQHandler>:              ← 版本 A：13 条指令
       0: f643 0000  movw r0, #0x3800
       4: f2c4 0001  movt r0, #0x4001
       8: 6801       ldr  r1, [r0]
       a: 0689       lsls r1, r1, #0x1a
       c: bf58       it   pl
       e: 4770       bxpl lr
      10: 6840       ldr  r0, [r0, #0x4]
      ...
      28: 4770       bx   lr

$ clang ... -c isr2.c                      ← 版本 B：编译通过，无警告
$ llvm-objdump -d isr2.o
00000000 <USART1_IRQHandler>:              ← 但多了一堆
       0: b5d0       push {r4, r6, r7, lr}   ← ⚠ 多余的压栈
       2: af02       add  r7, sp, #0x8
       4: 466c       mov  r4, sp
       6: f36f 0402  bfc  r4, #0, #3         ← ⚠ 强制 8 字节栈对齐
       a: 46a5       mov  sp, r4
       ...
      32: f1a7 0408  sub.w r4, r7, #0x8
      36: 46a5       mov  sp, r4
      38: bdd0       pop  {r4, r6, r7, pc}   ← ⚠ 多余的弹栈
```

**实测结论**：

1. clang **接受**这个属性（没有警告/报错）——所以你加了也不知道；
2. 它生成了 **多余的 `push`/`pop` + 栈对齐代码**（16 条 vs 13 条指令）；
3. 这些代码在 Cortex-M 上**完全没必要**——硬件已经压好栈了。

⚠ 更糟的是 `pop {..., pc}`：在真正的异常返回里，硬件期望的是
**`bx lr`（lr = EXC_RETURN）** 这个特殊序列来触发异常返回流程。
用普通的 `pop {pc}` 弹栈在某些实现上**不会触发异常返回**——
这属于"能编译、能跑、但语义错"的那类 bug。

**规则：Cortex-M 上 ISR 一律写成普通函数，不加任何属性。**

## 四、USART 的中断标志：读 DR 就清了

USART 的中断标志清除方式是**读写数据寄存器**，比较省心：

| 标志 | 怎么清 |
|---|---|
| **RXNE**（接收寄存器非空） | **读 `DR`** 就清了 |
| **TXE**（发送寄存器空） | **写 `DR`** 就清了 |
| **TC**（发送完成） | 读 SR 再写 DR（软件序列） |

```c
void USART1_IRQHandler(void){
    if (USART1_SR & RXNE) {
        uint8_t c = (uint8_t)USART1_DR;    /* ← 这个读动作本身就清了 RXNE */
        rb_put(&g_rx_rb, c);
    }
}
```

⚠ **但别把这条推广到所有外设**（[10.03 Q2](10.03-中断例程.md) 展开）：
EXTI 是**写 1 清除（w1c）**，写成 `EXTI_PR &= ~(1<<0)` 是错的——
标志清不掉，ISR 无限重入。

## 五、发送中断：和接收不一样

接收中断是"来了就收"；**发送中断要小心"没东西发还一直触发"**：

```c
/* ❌ 常见错误：一使能 TXEIE 就疯狂进中断 */
USART1_CR1 |= (1u << 7);        /* TXEIE：TXE 为 1 就触发 */
/* 结果：发送缓冲空的时候，TXE 一直是 1 → 中断风暴 */

/* ✅ 正确：只在"有数据要发"时打开，发完立刻关掉 */
void uart_start_tx(void){
    if (!rb_empty(&g_tx_rb)) USART1_CR1 |= (1u << 7);    /* 有数据才开 */
}

void USART1_IRQHandler(void){
    if ((USART1_SR & TXE) && (USART1_CR1 & (1u<<7))) {
        uint8_t c;
        if (rb_get(&g_tx_rb, &c) == 0) USART1_DR = c;    /* 写一个字节（清 TXE） */
        else USART1_CR1 &= ~(1u << 7);                    /* 发完了 → 关掉中断 */
    }
    if (USART1_SR & RXNE) { ... }
}
```

**这是新手最常踩的一个坑**：发送中断不像接收中断那样"事件驱动"，
它是**状态驱动**的（"我现在能发"），所以必须**用完就关**。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "使能串口中断" | **两道门**：外设 RXNEIE + NVIC_ISER。漏一个静默不进，和"漏开时钟"并列 |
| "ISR 要加 interrupt 属性" | ❌ Cortex-M 上**不需要**。实测加上会生成多余 `push`/`pop` + `bfc` 栈对齐（16 条 vs 13 条），且 clang **不警告** |
| "`NVIC_ISER \|= bit`" | ISER 是"写 1 生效、写 0 无效"设计，**直接 `=` 就行**，不需要读-改-写 |
| "读 DR 就清了标志" | 对 USART 的 RXNE/TXE 是这样。**别推广到 EXTI（那是 w1c，写 1 清）** |
| "发送中断和接收一样" | ❌ TXE 是**状态驱动**（"能发"），空着时会**中断风暴**。必须"有数据才开、发完就关" |

<details>
<summary>Q1：两道门是什么？漏了怎么查？</summary>

中断请求要穿过两道独立的使能门：

```
外设事件 → [门 1: 外设自己的 IE 位] → NVIC → [门 2: NVIC_ISER] → CPU
```

**门 1 在外设里**（USART1_CR1 的 RXNEIE = bit5）：
决定"这个外设要不要向 NVIC 发请求"。

**门 2 在 NVIC 里**（Cortex-M 的系统控制空间）：
决定"NVIC 收到的请求要不要交给 CPU"。

```c
USART1_CR1 |= (1u << 5);                    /* 门 1 */
NVIC_ISER1  = (1u << (37u - 32u));          /* 门 2：USART1 IRQn=37 → ISER1 bit5 */
```

**漏掉的表现**：

| 漏掉 | 现象 |
|---|---|
| 门 1 | 字节收到了（`SR` 的 RXNE = 1），但 NVIC 那边**没有请求** |
| 门 2 | 外设发了请求，CPU **不看** |
| 两个都漏 | 什么都不发生——**和"代码没写"看起来一样** |

这就是为什么它危险：**失败方式是静默的**。没有编译错误、没有运行时报错、
没有 HardFault——就是"字节收不到"。

**怎么查**：直接读两个寄存器，用调试器：

```
(gdb) x/1xw 0x4001380C       # USART1_CR1：bit5 (RXNEIE) 是否为 1
(gdb) x/1xw 0xE000E104       # NVIC_ISER1：bit5 是否为 1
```

更进一步，读 NVIC 的挂起/活跃寄存器能定位到"请求到哪一步了"：

| 寄存器 | 含义 | 如果它是 1 |
|---|---|---|
| `NVIC_ISPR`（`0xE000E200` 起） | **挂起**（有请求未响应） | 门 1 通了，但 CPU 没响应 → 门 2 没开，或优先级太低 |
| `NVIC_IABR`（`0xE000E300` 起） | **活跃**（正在执行 ISR） | ISR 正在跑（卡住了？） |
| 外设的 `SR` | 事件发生了没 | 为 1 说明硬件侧正常，问题在使能或 NVIC |

**通用规则（对所有外设都成立）**：
**STM32 上任何中断都要开两道门；EXTI 还要第三道（AFIO 的 EXTI 线映射）。**

顺带记一下常用 IRQn（F103）：

| 外设 | IRQn | ISER |
|---|---|---|
| EXTI0 | 6 | ISER0 bit6 |
| EXTI1 | 7 | ISER0 bit7 |
| EXTI15_10 | 40 | ISER1 bit8 |
| USART1 | 37 | ISER1 bit5 |
| USART2 | 38 | ISER1 bit6 |
| SysTick | −1（系统异常，不是外设 IRQ） | 由 `SysTick_CTRL` 的 TICKINT 位控制 |
</details>

<details>
<summary>Q2：为什么 clang 接受 `__attribute__((interrupt))` 却不警告？加了会有什么后果？</summary>

实测（[正文第三节](#三实测加-__attribute__interrupt-会怎样)）：

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding -Os -c isr2.c
（编译通过，零警告）

$ llvm-objdump -d isr2.o
       0: b5d0  push {r4, r6, r7, lr}     ← 多余
       6: f36f 0402  bfc r4, #0, #3       ← 多余：强制 8 字节栈对齐
      38: bdd0  pop  {r4, r6, r7, pc}     ← 多余，而且语义可疑
```

**为什么不警告**：`interrupt` 属性在 clang 里是**架构相关**的。
它对 ARM 的某些目标（比如 ARM32 非 M 系列）有意义，
对 `armv7m` 就退化成"按某种通用规则生成序言/尾声"。
clang 没有专门针对"Cortex-M 不需要这个"做诊断。

**后果有三层，从轻到重**：

**① 代码变大**：13 条指令 → 16 条，多一次 `push`/`pop`（4 个寄存器 = 16 字节栈）。
在一字节 8.7 µs 预算的 ISR 里，这不是零成本。

**② 栈对齐操作（`bfc r4, #0, #3`）**：把 SP 的低 3 位清零（8 字节对齐）。
Cortex-M 上栈本来就由硬件保证对齐（异常入口时 SP 按 8 字节对齐），
这个操作纯属多余。

**③ 最可疑的：`pop {..., pc}`**

正常的 Cortex-M 异常返回是：

```
ISR 结尾执行 bx lr，其中 lr = EXC_RETURN（如 0xFFFFFFF9）
→ 硬件识别 → 触发异常返回序列（弹栈、恢复）
```

而 `pop {r4, r6, r7, pc}` 是**普通的返回**——
它把栈上的值弹进 PC，**不走异常返回流程**。
在某些实现/某些芯片上这会导致：栈没被正确恢复、或者后续中断行为异常。

⚠ 我**没有在真机上验证过第 ③ 条**（这需要实际烧录观察），
它是从"异常返回机制"推出来的风险。但前两条（代码变大、栈对齐多余）是**实测确凿**的。

**结论**：不管第 ③ 条成不成立，前两条已经足够构成"不要加"的理由——
**零收益、确定的代码膨胀**。Cortex-M 上 ISR 就写普通函数。
</details>

<details>
<summary>Q3：发送中断为什么会导致"中断风暴"？怎么正确写？</summary>

因为 **TXE 是状态标志，不是事件标志**。

| 标志 | 性质 | 什么时候为 1 |
|---|---|---|
| **RXNE** | **事件** | 收到一个字节时（读完就变 0） |
| **TXE** | **状态** | **只要 DR 空就一直是 1** |

所以：

```c
USART1_CR1 |= (1u << 7);     /* TXEIE：TXE=1 就请求中断 */
/* 没东西可发时，TXE 恒为 1 → NVIC 持续收到请求 → 中断风暴 */
```

表现：程序看起来"卡死"（其实在以最高频率进出 ISR），
主循环几乎得不到执行时间。

**正确的写法：用完就关**

```c
static ringbuf_t g_tx_rb;

/* 上层要发数据：入队 + 打开发送中断 */
void uart_write(const uint8_t *buf, size_t n){
    while (n--) { if (rb_put(&g_tx_rb, *buf++) != 0) break; }   /* 满了就丢（或等） */
    USART1_CR1 |= (1u << 7);        /* 有数据了 → 开 TXEIE */
}

void USART1_IRQHandler(void){
    /* 发送：检查"中断开着" + "TXE 为 1" */
    if ((USART1_CR1 & (1u << 7)) && (USART1_SR & TXE)) {
        uint8_t c;
        if (rb_get(&g_tx_rb, &c) == 0) {
            USART1_DR = c;              /* 写一个字节（同时清 TXE） */
        } else {
            USART1_CR1 &= ~(1u << 7);   /* 队列空了 → 关掉 TXEIE（关键！） */
        }
    }
    /* 接收：事件驱动，不需要开关 */
    if (USART1_SR & RXNE) {
        rb_put(&g_rx_rb, (uint8_t)USART1_DR);
    }
}
```

三条要点：

1. **ISR 里必须检查 TXEIE 是否开着**——因为 TXE 为 1 时即使没开中断也会进来
   （如果还有别的中断源共用这个 ISR）；
2. **队列空了立刻关 TXEIE**——这是防风暴的关键；
3. **关中断的分支要能被走到**——别写 `if (rb_get(...)==0) DR=c;`
   然后忘了 `else`。

**更简单的替代方案**：如果发送量不大（比如日志），
干脆**用轮询发送 + 中断接收**，别碰 TXEIE。
这是很多量产产品的实际配置，因为它避免了这一整类问题
（[10.01 Q2](10.01-轮询与中断.md)）。

**想收尾时**：关串口/进低功耗前要等 **TC**（不是 TXE），
否则最后一个字节发不出去（[ch09 9.02 Q3](../09-uart-serial/9.02-定义我们的putchar.md)）。
</details>
