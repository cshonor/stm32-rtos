## 书这一节讲什么

写一个最小的 `main()`，编译它，看报错，读懂每一行，最后学会写注释。
书里这一节的程序是**跑在 PC 上**的（`printf("Hello World")`），
到第 3 章才真正上板子。

## 1.3.1 编译程序

书里的命令是 `arm-none-eabi-gcc ...`。我的等价命令：

```bash
$ export PATH=~/micromamba/envs/cdev/bin:$PATH
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb \
        -ffreestanding -fno-builtin -c hello.c -o hello.o
```

**这里有个必踩的坑**：书里的 hello world 用 `printf`，但裸机上 `printf`
根本不存在（见 [00.01](../00-mental-model/00.01-没有OS的C语言.md)）。
所以"第一个程序"在裸机上不能是 hello world，只能先验证**编译通过**，
真正的"输出"要等到 [9.05 串口 Hello World](../09-uart-serial/9.05-串口HelloWorld.md) 才成立。

一个能通过编译、且真的能上板子的最小 `main`：

```c
/* hello.c —— 裸机版"Hello World"：不打印，只让编译器和链接器跑完 */
int main(void)
{
    volatile int i = 0;
    for (;;) { i = i + 1; }     /* 必须有 for(;;)，否则 main 会被当返回处理 */
    return 0;                    /* 永远不会执行到，但要写上 */
}
```

## 1.3.2 犯错（书里最有价值的一节）

书在这一页专门讲"犯错"，这很反常识但非常对。编译器的报错信息是**分层的**，
搞清层与层的关系，排错速度差一个数量级：

| 报错阶段 | 典型信息 | 真正的原因 |
|---|---|---|
| 预处理 | `fatal error: 'xxx.h' file not found` | 头文件路径 / 拼写 |
| 编译 | `error: use of undeclared identifier 'x'` | 语法 / 类型 / 漏声明 |
| 汇编 | `error: unexpected token at start of statement` | 内联汇编或 `.s` 文件方言不对 |
| 链接 | `undefined reference to 'foo'` | **函数存在但没参与链接**（少了 .o 或库顺序不对） |
| 运行 | 什么都不报，板子没反应 / 跑飞进 HardFault | 逻辑或硬件问题，**编译器帮不了你** |

裸机开发最难受的是最后一行：**编译链接全过，板子不动**。
所以从第一天起就要建立"分层确认"的习惯（见 [1.02 Q2](1.02-下载STM32系统工作台.md)）。

## 1.3.3 理解程序

书在这一页逐字解释代码。对裸机来说，真正要理解的是**编译器替你隐式做了什么**：

```c
int main(void) { ... }
```

这一行看起来无害，其实暗含三个假设：程序从 `main` 开始（**假**，
实际从 `Reset_Handler` 开始）、`main` 返回后有人接管（**假**，
裸机上没人接管）、`main` 的参数由运行时准备（**假**，没人准备 `argc/argv`）。

三个假设全不成立，但代码照样能编过——这就是裸机开发的危险之处：
**编译器从不检查"有没有人给你准备运行环境"。**

## 1.3.4 添加注释

书讲注释规范。裸机语境下注释有额外的、更硬的用途：

```c
/* ⚠ 写寄存器的三种语义必须标出来，否则接手的人（包括三个月后的你）会写错 */
GPIOC_BSRR = (1u << 13);        /* W1S：写 1 置位，写 0 无效果 */
EXTI_PR    = (1u << 13);        /* W1C：写 1 清零（写 0 不动） */
u32 sr = USART1_SR;             /* RC：读一次就清标志，不能重复读！ */
```

**寄存器手册里 "W1C / RC / RO" 这类访问语义，比位定义更容易出错，必须在代码里标。**

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| 书用 `printf("Hello World")` 当第一个程序 | 裸机上 `printf` 不存在。这个程序只能验证"编译链通了"，输出要等 ch09 |
| "编译器会告诉你哪里错了" | 只覆盖前四行那类错误。**"板子没反应"这类它一个字都不会说** |
| "`main` 是程序入口" | 裸机上入口是向量表第 1 个字指向的 `Reset_Handler`，`main` 只是被它 `bl` 调用的一个普通函数 |
| "`main` 里 `return 0` 就结束了" | 裸机上没有 `exit`。`main` 返回后程序会跳到**下一条指令**（随机值），标准做法是 `for(;;)` 或 `while(1)` 兜住 |
| "`for(;;)` 和 `while(1)` 一样" | 语义一样。但 `for(;;)` 不含条件表达式，**在 `-Wempty-body` / 静态分析工具下更干净**。本仓库统一用 `for (;;)` |

## 代码自测

<details>
<summary>Q1：为什么裸机的 `main` 必须写成死循环，而 PC 上不需要？</summary>

因为"`main` 返回之后谁接管"这件事，hosted 环境有答案，freestanding 没有。

PC 上 `main` 返回后，`__libc_start_main` 拿到返回值，调 `exit()` → 刷缓冲区 →
`exit_group` 系统调用关掉进程。**这条链是 libc + 内核提供的。**

裸机上这条链完全不存在。`main` 返回时 CPU 执行的是 `Reset_Handler` 里 `bl main`
之后的下一条指令。我们那份 `startup.S` 里下一条恰好是 `b .`（自己跳自己），
所以"看不出来"——但如果你用别的启动文件，下一条可能是随机数据，**行为不确定**。

所以 `for (;;)` 不是风格问题，是**把不确定性变成确定性**。
</details>

<details>
<summary>Q2：写 `volatile int i` 而不写 `int i`，在第一个程序里为什么要紧？</summary>

因为这段代码里 `i` 唯一的作用是"让循环看起来在做点事"。

- 写 `int i`：`-O2` 下编译器发现 `i` 没被读取、循环体无副作用 →
  **整个循环连同 `i` 一起删掉**，`main` 变成空函数。
- 写 `volatile int i`：每次自增都是一次真实的内存写，编译不掉。

第一个程序就用 `volatile`，是为了**第一次就看见"编译器会删代码"这件事**。
这不是理论：本仓库 `ch05` 的空 `while` 实测被 `-Os` 编成了单条 `bx lr`（直接返回）。
</details>
