# 7.02 隐藏变量

> 书：第 7 章 局部变量和函数 · 7.02 隐藏变量（原书 p89–97 区间内）
> 上一篇：[7.01 局部变量](7.01-局部变量.md) ｜ 下一篇：[7.03 函数](7.03-函数.md)
> 对应实验：`--target=armv7m-none-eabi` 交叉编译 + `llvm-nm -u` / `-fstack-usage`

## 书这一节讲什么

一句话：**有些变量你没写，但编译器替你生成了**（hidden variables）。

书举的例子大概是"编译器为表达式的中间结果造的临时变量"。
裸机上这件事的分量完全不同——因为**编译器替你做的每一件事都要在栈、Flash 或时间上记账**，
而且这些开销你从源码里看不见。

## 一、三类隐藏开销（实测可见）

**① 保存 `lr` 和被调用者保存寄存器 → 占栈**

```c
int fact(int n){ return (n<=1) ? 1 : n*fact(n-1); }
```

```
$ clang ... -O0 -c ch07.c && llvm-objdump -d ch07_o0.o
0000006c <fact>:
      6c: b580          push {r7, lr}      ← 8 字节：返回地址 + 帧指针
      6e: b084          sub  sp, #0x10     ← 再 16 字节
      ...
      86: f7ff fffe     bl  0x86           ← 真的调用自己
```

`push {r7, lr}` + `sub sp, #0x10` = **24 字节/帧**，
和 `-O0` 的 `.su` 完全对上（实测 `ch07.c:6:fact 24 static`）。

对照：叶子函数（不调别人的）**不需要保存 `lr`**——
实测 `-Os` 的 `with_locals` 只有 `sub sp, #0x20`，没有 `push`。

**② 大结构体赋值 → 生成 `memcpy` 调用（占 Flash + 栈）**

```c
typedef struct { unsigned a[64]; } big_t;
extern big_t g1, g2;
void f(void){ g1 = g2; }
```

```
$ clang ... -ffreestanding -Os -c memcpy2.c && llvm-nm -u m.o
         U __aeabi_memcpy
         U __aeabi_memcpy4
```

**你没写 `memcpy`，编译器替你调了**——
而且它是未定义符号，链接时找不到就是 `undefined reference`。
（[6.05 字符和字符串](../06-arrays-pointers-strings/6.05-字符和字符串.md) 有完整的补齐清单，
包括 `__aeabi_memset` 参数顺序和标准 `memset` 相反这个坑。）

**③ 软件浮点 → 占 Flash + 大量时间**

M0/M3 没有 FPU，浮点是软件模拟的：

```
U __aeabi_dadd      ← double 加法
U __aeabi_dmul      ← double 乘法
U __aeabi_f2d / __aeabi_d2f   ← 单双精度转换
```

每个都是真实的库函数，会被链接进 Flash，且一次 `double` 乘法要几十条指令。
（[16.07 替代方案](../16-floating-point/16.07-替代方案.md) 展开：实测这些符号会让 `float` 版链接失败。）

## 二、怎么看见隐藏变量

| 手段 | 看到什么 |
|---|---|
| `llvm-nm -u xxx.o` | **未定义符号** = 编译器替你向运行环境要的东西 |
| `-fstack-usage` | 每个函数的单帧大小（含隐藏的寄存器保存） |
| `llvm-objdump -d xxx.o` | `push`/`sub sp` 的实际指令 |
| `llvm-size firmware.elf` | 最终 Flash/RAM 占用（隐藏库函数的 Flash 成本） |

第一条最有用：

```
$ llvm-nm -u memcpy.o
         U __aeabi_memcpy      ← "我需要有人提供这个"
         U __aeabi_memcpy4
```

**裸机工程每次加完代码都该看一眼 `llvm-nm -u`**——
那些 `U` 就是你的 C 运行时该补齐的清单。

## 三、`volatile` 也是一种"隐藏开销"

```c
int leaf(int a, int b){ volatile int t = a + b; return t; }
```

实测 `-Os` 下 `leaf` 的栈用量是 **4 字节**——
不为别的，就因为 `t` 是 `volatile`，**必须有一个真实的栈地址**
（不能被优化成纯寄存器操作）。

```
00000000 <leaf>:            # -Os
       0: b081     sub  sp, #0x4     ← 就为了这个 volatile 变量
       2: 4408     add  r0, r1
       4: 9000     str  r0, [sp]     ← 真的写回内存
       6: 9800     ldr  r0, [sp]     ← 真的读回来
       8: b001     add  sp, #0x4
```

这是"隐藏开销"里最容易被忽略的一类：
**为了调试方便加的 `volatile`，会直接进入栈预算和指令数。**

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "隐藏变量是编译器的小事" | 裸机上是**栈 + Flash + 时间**的三重成本。实测 `fact` 每帧 24 字节、`__aeabi_memcpy` 是未定义符号 |
| "叶子函数和非叶子一样" | 叶子**不用保存 `lr`**（实测 `with_locals` @ -Os 没有 `push`）；非叶子要 8+ 字节 |
| "结构体赋值是几个 mov" | 大了就变成 `memcpy` **调用**（实测 `U __aeabi_memcpy`） |
| "`volatile` 只是防优化" | 它会强制变量**有真实地址**，直接进入栈预算（实测 `leaf` 4 字节就为它） |
| "我没调用的库函数不会进镜像" | `__aeabi_*` 这类编译器生成的调用会。用 `llvm-nm -u` 看 |

## 代码自测

<details>
<summary>Q1：`push {r7, lr}` 是在干什么？为什么有的函数有、有的没有？</summary>

它在**保存返回地址和帧指针**，因为这个函数还要调用别的函数。

`lr`（Link Register, r14）存着"返回给谁"的地址。
如果函数 A 内部调用了 B，那么 `bl B` 这条指令**会覆盖 `lr`**——
A 自己的返回地址就没了。所以 A 必须先把 `lr` 压栈：

```
fact:
    push {r7, lr}     ← 保存（r7 是帧指针，方便调试器回溯）
    ...
    bl   fact         ← 这个 bl 会覆盖 lr，但原来的已经存栈了
    ...
    pop  {r7, pc}     ← 恢复：把存起来的返回地址直接弹进 pc = 返回
```

**叶子函数（不再调用别人）不需要**——因为没人会覆盖它的 `lr`：

```
with_locals:              # -Os，叶子函数
    sub  sp, #0x20        ← 只有局部变量的空间
    ...
    add  sp, #0x20
    bx   lr               ← 直接用 lr 返回，不用压栈
```

实测对照：

| 函数 | 是否叶子 | 有没有 push |
|---|---|---|
| `with_locals` @ -Os | ✅ 是 | ❌ 没有（只有 `sub sp, #0x20`） |
| `fact` @ -O0 | ❌ 否（调自己） | ✅ `push {r7, lr}` |

**工程含义**：深调用链上每个非叶子函数都要多付 8 字节（或更多），
所以"调用深度"和"栈预算"是同一个问题的两面。
另外这也是为什么 `-Os` 的**激进内联**能省栈——内联后就没有调用了，也就不用保存 `lr`。
</details>

<details>
<summary>Q2：我没写 `memcpy`，为什么链接器找我要 `__aeabi_memcpy`？</summary>

因为**编译器会替你生成对它的调用**，只要它觉得"逐字段拷贝不如调库函数"。

实测（`typedef struct { unsigned a[64]; } big_t; void f(void){ g1 = g2; }`）：

```
$ clang ... -ffreestanding -Os -c memcpy2.c
$ llvm-nm -u m.o
         U __aeabi_memcpy
         U __aeabi_memcpy4
```

触发条件：

| 场景 | 会不会生成 |
|---|---|
| 小结构体（几个字）赋值 | 不会——内联成几条 `ldr`/`str` |
| **大结构体（几十字节以上）赋值** | 会（实测 256 字节时生成） |
| 大数组的部分初始化 | 会 |
| 显式 `__builtin_memcpy` | 会 |
| `int a[3] = {1,2,3}`（小数组） | 不会 |

这个符号**时有时无**，所以很容易被当成玄学："我什么都没改，
加了个字段就链接不过了"——其实是结构体越过阈值，编译器改用库调用了。

解决办法：提供一份最小的 C 运行时（[6.05](../06-arrays-pointers-strings/6.05-字符和字符串.md) 有完整清单），
或者**避免大结构体的整体赋值**（改成逐字段拷贝，或显式调用自己的 `memcpy`）。

顺带记住：**`__aeabi_memset(s, n, c)` 的参数顺序和标准 `memset(s, c, n)` 相反**——
照抄标准签名实现会导致"内存被填成了长度值"。
</details>

<details>
<summary>Q3：怎么知道编译器偷偷替我加了什么？</summary>

三条命令，按使用频率排序：

**① `llvm-nm -u xxx.o` —— 看"我要什么"**

```
$ llvm-nm -u memcpy.o
         U __aeabi_memcpy
         U __aeabi_memcpy4
```

`U`（undefined）= 这个文件期待别人提供。裸机上这些就是你的 C 运行时清单。
**加完一批代码跑一次，对比前后差异**——新增的 `U` 就是新引入的隐藏依赖。

**② `-fstack-usage` —— 看"每帧多少栈"**

```
$ clang ... -Os -fstack-usage -c ch07.c && cat ch07_os.su
ch07.c:1:leaf         4    static
ch07.c:2:with_locals  32   static
ch07.c:6:fact          0   static
```

注意 `static` 那列：这里是"栈用量是否静态可知"的意思，
`dynamic` 表示有变长数组（VLA）或 `alloca`，那种情况栈用量**编译期算不出来**——
裸机上**绝对不要用 VLA**（`int a[n]`），它让栈预算彻底失控。

**③ `llvm-size firmware.elf` —— 看"最终多大"**

```
   text    data     bss     dec     hex filename
    296       0       0     296     128 blink.elf
```

每加一个隐藏库函数，Flash（text）就涨一块。
**这三件工具应该放进 `make` 的常规检查里**，每次编译都自动跑。
</details>
