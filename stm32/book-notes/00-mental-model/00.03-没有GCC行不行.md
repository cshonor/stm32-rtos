# 00.03 没有 GCC 行不行？——编译器只是实现，不是标准

> 上一篇：[00.02 操作硬件的三个手段](00.02-操作硬件的三个手段.md)
> 对应实验：`stm32/00-toolchain-clang/`（Mac 上实测通过，产物 296 字节）

## 这一节要解决什么

书第 1 章第一节就是"安装 GCC"。那**不装 GCC 行不行**？

结论：**行。** C 标准规定的是**语言**，不是**实现**。GCC 是符合标准的一种实现，
Clang 是另一种。但"能换"和"能少装"是两件事，得分开说。

## 一、实测：全程零 GNU 交叉工具链

`stm32/00-toolchain-clang` 没装任何 arm-none-eabi 工具链，实测可用：

| 环节 | 传统 GCC 方案 | 本次实测方案 | 为什么能换 |
|---|---|---|---|
| 编译 | `arm-none-eabi-gcc -c` | `clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb` | LLVM 内置 arm 后端 |
| 汇编 | `arm-none-eabi-as` | clang 集成汇编器（默认） | 同上 |
| 链接 | `arm-none-eabi-ld -T linker.ld` | `ld.lld -T linker.ld`（**必须写全 `ld.lld`**） | lld 提供 GNU 风味 |
| 转 bin | `arm-none-eabi-objcopy -O binary` | `llvm-objcopy -O binary` | 功能等价 |
| 反汇编 | `arm-none-eabi-objdump -d` | `llvm-objdump -d` | 功能等价 |
| 段表 / 符号 | readelf / nm | `llvm-readelf` / `llvm-nm` | 功能等价 |

## 二、不能换的是什么

只有两样：

1. **标准** —— `-ffreestanding` + `-nostdlib` 是所有实现的共同语言；
2. **器件手册** —— 地址表、位定义、电气特性，跟编译器厂商无关。

## 二·补：标准到底保证了哪些头文件可用？

上面说「不能换的是**标准**」——那标准对裸机具体承诺了什么？最容易摸到的一块就是
**头文件清单**：标准写死了 freestanding 实现**必须**提供的头文件，清单之外一律「不保证」。

读法要反过来：这是**「工具链欠你的最少保障清单」，不是「你欠工程的必交作业」**——
这些头文件装在编译器自己的安装目录里（clang 是 `lib/clang/<ver>/include/`），
**一个都不 `#include` 也完全合法**，更不用拷一份进工程（拷进去只会自找版本漂移）。

清单逐字引自标准正文 Clause 4：

| 标准 | 纯 freestanding 头文件 | 个数 |
|---|---|---|
| C99（N1256 §4p6） | `float.h` `iso646.h` `limits.h` `stdarg.h` `stdbool.h` `stddef.h` `stdint.h` | **7** |
| C11 = C17（N1570 §4p6） | 上面 7 个 + `stdalign.h` `stdnoreturn.h` | **9** |
| C23（N3220 §4p7） | 上面 9 个 + `stdbit.h` | **10** |

两处容易记错的：

1. **C23 只加了 `stdbit.h`，没有加 `stdckdint.h`。** 不少二手资料把 `stdckdint.h`
   也算进 freestanding——查 N3220 §4p7 原文，清单里**没有**它。
2. **C23 起 freestanding 分了三层**，不再只有一张表：上面 10 个是「完全 freestanding」；
   `string.h`（除 `strcoll`/`strdup`/`strerror`/`strndup`/`strtok`/`strxfrm` 六个函数）
   与 `stdlib.h` 的 `memalignment` 属「部分 freestanding」；定义了
   `__STDC_IEC_60559_BFP__`/`_DFP__` 时 `fenv.h`、`math.h`、`strto*` 才算（有条件）。

**关键辨析：`工具链给的头文件 ≠ 标准保证的头文件`。** 本机 clang 23.1.0 逐个 include 实测：

```sh
clang --target=armv7m-none-eabi -ffreestanding -std=c23 -fsyntax-only probe.c
```

| 结果 | 头文件 |
|---|---|
| ✅ 通过（在标准清单里） | 10 个里的 9 个 |
| ❌ **不通过** | **`stdbit.h`** ← 标准要求给，clang 23.1.0 资源目录里**没有** |
| ⚠️ 通过（**超出**标准清单） | `stdatomic.h` `stdckdint.h`（资源目录里还有 `stdcountof.h` `stddefer.h` 等扩展） |
| ❌ 不通过（hosted 头，理应没有） | `assert.h` `stdio.h` `stdlib.h` `string.h` `math.h` |

所以：**「我这儿能 include 成功」只是这个工具链的实现细节**，既不是标准保证，
也不能当可移植性依据。写可移植的裸机代码，只应依赖标准清单里的头文件——
**能 include ≠ 标准保证**。（工具链侧的完整实测见
[00-toolchain-clang](../../00-toolchain-clang/README.md)。）

## 三、Mac 上的实操结论

`clang --target=armv7m-none-eabi` 直接可用，**不需要装 arm-none-eabi-gcc，
也不需要 Xcode**。一个 micromamba 环境里的 clang 23.1.0 + lld 就够。

顺带一个公开数据点：**STM32CubeIDE 2.1.0 / 2.2.0 起，ST 内置的工具链已经是两套**——
GNU tools for STM32（基于 GCC 14.3.rel1）**和** STARM-Clang 21.1.1。
Arm 自家的 Arm Compiler 6（Keil 用的 `armclang`）官方文档也写明
*"based on LLVM and Clang technology"*；2025 年 Arm 又推了 ATfE
（Arm Toolchain for Embedded），直接用 `clang` + `lld` 取代 `armclang` + `armlink`。

**所以 clang + ld.lld 不是野路子，是 Arm 官方正在走的方向。**

## 坑点（常识怎么说 / 实测是什么）

| 常识怎么说 | 实测是什么 |
|---|---|
| "开发环境要装 arm-none-eabi-gcc" | Mac 上完全不需要。clang 自带 arm 后端，lld 吃 GNU 链接脚本 |
| "用 `ld` 就行" | macOS 的 `/usr/bin/ld` 是 Mach-O 链接器，报 `unknown option: -T`。必须 `ld.lld` |
| "换个编译器要改一堆东西" | 要改的只有：链接脚本里 `ld.lld` 不认的少数伪指令、启动文件里 GNU as 方言。**C 源码基本不用动** |
| "clang 编出来的代码比 GCC 大 / 慢" | 这个我没做过系统对比，**不敢下结论**。Cortex-M 上的 code size 比较要控变量（优化等级、是否 LTO、newlib 版本），我手头没有可信数据 |

## 代码自测

<details>
<summary>Q1：既然换了编译器，为什么启动文件的 `.s` 还能直接用？</summary>

因为 **GNU as 方言 vs Arm 老方言（armasm）** 是**汇编器语法**的差别，不是编译器品牌的差别。
clang 的集成汇编器跟 GCC 一样吃 GNU as 语法，所以：

- `startup.S`（GNU 语法：`.syntax unified`、`.section`、`.word`）→ clang 直接吃；
- `startup.s`（Arm 老语法：`AREA`、`EXPORT`、`DCD`）→ clang 不吃，要转。

实践中踩坑的地方在伪指令细节，不在指令本身。真要跑不通，先看 `.section` 后面那句
属性写得对不对（`%progbits` / `"ax"` 之类）。
</details>

<details>
<summary>Q2：`--target=armv7m-none-eabi` 里三段分别是什么？为什么不用 `-mcpu` 一个参数搞定？</summary>

`--target=` 是 LLVM 的**三元组（triple）**，格式 `<arch>-<vendor>-<os-abi>`：

| 段 | 值 | 含义 |
|---|---|---|
| arch | `armv7m` | 架构 = ARMv7-M（M3/M4/M7 这一族） |
| vendor | `none` | 没有厂商 |
| os-abi | `eabi` | 裸机 EABI（没有 OS） |

而 `-mcpu=cortex-m3` 是**更细的选型**，它决定：具体有哪些指令可用
（M3 没有 DSP 扩展）、默认 CPU 参数、预定义宏。

两者不是重复，**都要给**：triple 决定"用哪套 ABI 和默认库路径"，
`-mcpu` 决定"目标核的指令集细节"。给 triple 不给 `-mcpu` 会用架构默认值，
可能生成 M3 上跑不了的指令。
</details>

<details>
<summary>Q3：那到底什么时候必须用 arm-none-eabi-gcc？</summary>

三种情况，都是"别人给的约束"而不是技术约束：

1. **厂商 SDK 只测过 GCC**：STM32 的 HAL/LL 库、`.ld` 链接脚本、`startup_*.s`
   都是按 GCC 生成的。你换成 clang 也能编，但真要出问题厂商不认。
2. **功能安全认证**：IEC 61508 / ISO 26262 要求工具链有认证证书，
   这跟"编译器好不好"完全无关。要走这条路通常是 Arm Compiler（FuSa 版）或 IAR。
3. **团队/客户指定**：CI 镜像里写死了 `arm-none-eabi-*`，换工具链要走变更流程。

**学习阶段没有这三种约束，所以自由。** 反过来，一旦开始写要交付的固件，
编译器的选择往往不是你能决定的。
</details>

<details>
<summary>Q4：有人说「freestanding 工程必须把那 7 个头文件都拷进源码目录」。错在哪？我在裸机工程里 <code>#include &lt;stdatomic.h&gt;</code> 编译通过，能说明标准保证它可用吗？</summary>

**第一问两处错。** ① 头文件是**工具链自带**的（clang 在 `lib/clang/<ver>/include/`），
不属于工程，拷一份进源码目录反而自找版本漂移；② 数量不是 7 而是随标准变：
C99=7、C11/C17=9、C23=10（见上表原文）。

**第二问：不能。** 标准清单里没有 `stdatomic.h`，clang 照样给了它（实测通过）；
反过来 clang 23.1.0 又**缺**清单里要求的 `stdbit.h`。所以「能 include 成功」只是
**这个工具链的实现细节**，既不是标准保证，也不能作为可移植性依据。要写可移植的裸机代码，
只应依赖标准清单里的头文件。
</details>
