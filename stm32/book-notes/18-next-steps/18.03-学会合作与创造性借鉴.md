## 书这一节讲什么

一句话：**"借鉴"不是复制粘贴——是把别人的技巧**拆出来、
理解它解决什么问题**、然后用到你自己的场景里。**

书强调"合作"与"借鉴"，落到 C 项目上就是两件事：

1. **会拆**（把别人的代码拆成"设计决策 + 权衡"）；
2. **会用**（在自己的约束下重新实现它）。

## 一、⭐ 实测：一个完美的借鉴案例（4 字节学到一条设计原则）

[18.02](18.02-学会阅读.md) 里读到的 libopencm3 `gpio_set`：

```
00000000 <gpio_set>:
       0:      	str	r1, [r0, #0x10]      ← BSRR（偏移 0x10）
       2:      	bx	lr
```

**拆出来的设计决策**：

| 观察 | 拆出的决策 | 为什么 |
|---|---|---|
| 用 `BSRR` 而不是 `ODR` | **置位要原子** | `ODR |= bit` 是读-改-写，多上下文互相覆盖 |
| 只有 2 条指令 | **极简，无分支** | 没有参数校验、没有状态查询 → 调用者负责 |
| 参数是 `(port, pin)` | **不隐藏硬件** | 直接暴露寄存器语义，零抽象成本 |

**用到自己的场景**（本仓库的 `gpio` 模块）：

```c
/* 借鉴 BSRR 的思路：一次写完成置位/清零，不读-改-写 */
#define GPIO_BSRR(port) (*(volatile uint32_t *)((port) + 0x10u))
#define GPIO_BRR(port)  (*(volatile uint32_t *)((port) + 0x14u))

static inline void gpio_set(uint32_t port, unsigned pin) {
    GPIO_BSRR(port) = (1u << pin);          /* 写 1 置位，写 0 无效 */
}
static inline void gpio_clear(uint32_t port, unsigned pin) {
    GPIO_BRR(port) = (1u << pin);           /* 或者 BSRR 的高 16 位 */
}
```

⚠ **注意借鉴不等于照抄**：libopencm3 用函数，本仓库用 `static inline`——
因为本仓库的约束是"Flash 极小 + 只用一种芯片"，**内联比函数调用更划算**。
**这就是"在自己的约束下重新实现"。**

## 三、⚠ "借鉴"的四步检查

```
① 它解决什么问题？（不是"它长什么样"）
② 它付出了什么代价？（没有免费的抽象）
③ 我的约束和它一样吗？（Flash / RAM / 芯片 / 实时性）
④ 我能验证它的效果吗？（实测，不是"听说更好"）
```

⚠ **第④步是区分"借鉴"和"迷信"的关键**：

| 说法 | 实测结果 | 出处 |
|---|---|---|
| "代码宏省代码" | ❌ **28 B vs 28 B**，一样 | [12.03](../12-preprocessor/12.03-代码宏.md) |
| "`--gc-sections` 能瘦身" | ⚠ 单独用**无效**（134/8 → 134/8） | [11.05](../11-linker/11.05-映射文件.md) |
| "用 `float` 比 `double` 快" | ✅ M4F 上真快（`vmul.f32`），M3 上都慢 | [16.01](../16-floating-point/16.01-数字表示.md) |
| "静态库抽取到函数级" | ⚠ **默认是 `.o` 级** | [17.03](../17-modular-programming/17.03-库.md) |
| "库放前面会链接失败" | ⚠ **ld.lld 实测能过且静默** | [17.05](../17-modular-programming/17.05-确定性与不确定性库.md) |

## 四、"合作"在 C 项目里长什么样

C 没有包管理器，合作的方式就是**接口契约**：

| 机制 | 作用 | 出处 |
|---|---|---|
| **头文件** | 契约（我提供什么） | [17.01](../17-modular-programming/17.01-模块设计.md) |
| **`static`** | 边界（我不提供什么） | [17.02](../17-modular-programming/17.02-命名空间.md) |
| **前缀** | 命名空间（避免撞车） | 同上 |
| **弱符号** | 扩展点（你可以覆盖我） | [17.06](../17-modular-programming/17.06-弱符号.md) |
| **静态库** | 交付物（按需抽取） | [17.03](../17-modular-programming/17.03-库.md) |

⚠ **C 的"合作"全靠约定**，没有编译器强制。
所以**纪律比工具重要**——这正是本章放在"后记"里的原因：
技术学完了，剩下的是人的问题。

## 坑点

| 坑 | 原书怎么说 | 实际是什么（实测） |
|---|---|---|
| "借鉴 = 抄过来改改" | 强调"创造性" | ⚠ **要拆出"它解决什么问题"**，否则抄来的抽象在你的约束下是负担 |
| "开源库的写法就是最优" | —— | ⚠ libopencm3 用函数（可移植），本仓库用 `static inline`（省 Flash）——**约束不同，选择不同** |
| "抽象没有成本" | —— | ⚠ 每次间接调用/参数校验都有代价；实测代码宏**不省机器码**（28 B vs 28 B） |
| "大家都这么写" | —— | ⚠ 实测多次推翻课本说法（见第三节表格） |

## 代码自测

<details>
<summary>Q1：借鉴和抄袭的区别在哪？</summary>

**区别在于你有没有拆出"它解决什么问题"。**

以 libopencm3 的 `gpio_set` 为例（实测反汇编）：

```
0:  str r1, [r0, #0x10]     ← BSRR
2:  bx  lr
```

- **抄袭**：把 `gpio_set()` 函数原样搬进你的代码；
- **借鉴**：拆出"**置位要用 BSRR 做单条 32 位写，避免读-改-写**"这条原则，
  然后按**你自己的约束**重新实现：

```c
/* 本仓库：用 static inline（Flash 极小、只用一种芯片，内联比函数调用划算） */
static inline void gpio_set(uint32_t port, unsigned pin) {
    GPIO_BSRR(port) = (1u << pin);
}
```

**判据**：如果原库换了芯片你就不会用了 → 你只是抄了；
如果你能在自己的代码里解释"为什么这么写" → 你是借鉴了。
</details>

<details>
<summary>Q2：怎么判断一个"最佳实践"值不值得照做？</summary>

**实测。** 本仓库踩过几次"听起来对，实测不对"：

| 说法 | 实测 |
|---|---|
| "代码宏省代码" | ❌ **28 B vs 28 B**，一样 |
| "`--gc-sections` 能瘦身" | ⚠ 单独用**完全无效**（134/8 → 134/8），要配 `-ffunction-sections` |
| "静态库抽取到函数级" | ⚠ **默认 `.o` 级**，同一 `.o` 里的 `mul` 会被带进来 |
| "库放前面会链接失败" | ⚠ **ld.lld 实测能过且静默**，要 `--warn-backrefs` 才报 |
| "用 `float` 比 `double` 快" | ✅ 只在**有 FPU** 时成立（M4F 实测 `vmul.f32`）；M3 上都是库调用 |

**四步检查**：

1. 它解决什么问题？
2. 它付出什么代价？
3. 我的约束和它一样吗？
4. **我能实测验证吗？**

第 4 步做不到的话，就标注"未实测"——别当成事实传播。
</details>

<details>
<summary>Q3：C 没有包管理器，"合作"靠什么？</summary>

**靠接口契约 + 约定。** 五件套：

| 机制 | 作用 |
|---|---|
| 头文件 | 契约（我提供什么） |
| `static` | 边界（我不提供什么） |
| 前缀 | 命名空间（避免撞车） |
| 弱符号 | 扩展点（你可以覆盖我的默认实现） |
| 静态库 | 交付物（按需抽取，不浪费 Flash） |

⚠ **全靠约定，编译器不强制**——
所以 [17.02](../17-modular-programming/17.02-命名空间.md) 实测的
"两个 `rx_count` 不加 `static` → `duplicate symbol`"
这种错误只能靠纪律避免。

**这也是为什么第 17 章（模块化）放在技术章节的最后、第 18 章（元建议）之前**：
技术学完了，剩下的是**人的问题**。
</details>
