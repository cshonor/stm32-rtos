## 书这一节讲什么

一句话：**读源码比读教程有用——而"读"不只指读 `.c`，
读编译产物（符号表、反汇编、map 文件）往往更有信息量。**

本仓库已经放好了现成的阅读素材：`third_party/libopencm3`（以及 `_refs/libopencm3-examples`）。

## 一、⚠ 实测：先给一个库"量个体重"

```
$ llvm-ar -t  libopencm3_stm32f1.a | wc -l     → 53 个成员
$ llvm-nm     libopencm3_stm32f1.a | grep -cE '^[0-9a-f]+ [TtDdBbWwRr] '  → 677 个符号
$ ls -lh      libopencm3_stm32f1.a             → 3.0 MB
```

| 指标 | 实测值 | 说明 |
|---|---|---|
| 文件大小 | **3.0 MB** | 但这**不是**你会烧进 Flash 的大小 |
| 成员数 | **53** | 每个成员一个 `.o` |
| 符号数 | **677** | 677 个函数/变量 |

⚠ **3.0 MB ≠ 你的固件会变大 3 MB**——
这正是 [17.3 库](../17-modular-programming/17.3-库.md) 实测的"按需抽取"：
你只用 `gpio_set`，就只有 `gpio.o` 那一个成员进镜像。

**"先量体重"的意义**：知道规模才知道从哪读起。
677 个符号不可能一个个看，**先定位再深入**。

## 二、读源码的四把" Reads 工具"

| 工具 | 回答什么问题 | 命令 |
|---|---|---|
| `llvm-ar -t` | 库里有哪些成员？ | `llvm-ar -t lib.a` |
| `llvm-nm` | 有哪些符号？哪些是全局/本地/弱/未定义？ | `llvm-nm lib.a` |
| `llvm-objdump -d` | 这个函数到底编译成几条指令？ | `llvm-objdump -d --disassemble-symbols=X lib.a` |
| `llvm-size` + map | 它占多少 Flash/RAM？ | `llvm-size -A app.elf` |

## 三、⭐ 实测：读一个函数的反汇编，比读十行文档快

`gpio_set` 在 libopencm3 里的实现（实测反汇编）：

```
$ llvm-objdump -d --no-show-raw-insn --disassemble-symbols=gpio_set libopencm3_stm32f1.a
Disassembly of section .text.gpio_set:

00000000 <gpio_set>:
       0:      	str	r1, [r0, #0x10]
       2:      	bx	lr
```

**两条指令，4 个字节。** 一眼看穿：

- `r0` = GPIO 端口基址，`r1` = 要写的值；
- 偏移 `0x10` = **BSRR 寄存器**（Bit Set/Reset Register）；
- 所以 `gpio_set(port, pin)` 就是**一次 32 位写**，`pin` 那一位写 1 → 置位。

**这一条"读"学到的东西**：

1. **置位/清零是原子的**——BSRR 是"写 1 生效、写 0 无效"，
   不需要"读 ODR → 改位 → 写回"这种**读-改-写**（那在多上下文下会丢更新）；
2. **为什么不用 `|=`**——`ODR |= bit` 是读-改-写，
   中断里和主循环里同时改不同位就会互相覆盖；
3. **代价只有 4 字节 Flash**——比自己写的函数还小。

对照 [ch03](../03-embedded-system-programming/README.md)：
"GPIO 用 BSRR/BRR 而不是 ODR"这条规则，
**看一眼反汇编就彻底懂了**，比读三页文档快。

## 四、读的三个层次

| 层次 | 看什么 | 学到什么 |
|---|---|---|
| **① 接口层**（`.h`） | 函数签名、注释、命名前缀 | 作者想让你怎么用（[17.1](../17-modular-programming/17.1-模块设计.md)） |
| **② 实现层**（`.c`） | 数据结构、边界处理、错误处理 | 作者怎么处理"坏事" |
| **③ 产物层**（`.o` / `.elf`） | 符号表、反汇编、尺寸 | **编译器实际做了什么**——和你以为的可能不一样 |

⚠ **第③层最容易被跳过，也最容易被打脸**：

- 你以为 `static inline` 省空间 → `-O0` 下其实每个 `.c` 一份（[17.1](../17-modular-programming/17.1-模块设计.md) 实测）；
- 你以为代码宏省代码 → 实测 `use_macro` 和 `use_plain` **都是 28 B**（[12.3](../12-preprocessor/12.3-代码宏.md)）；
- 你以为 `-Os` 会保留浮点调用 → 常量折叠让 `__aeabi_fmul` **凭空消失**（[16.7](../16-floating-point/16.7-替代方案.md)）。

## 五、裸机上的阅读顺序建议

```
① 启动文件 / 向量表      （ch03）—— 看懂"上电第一条指令"
② 链接脚本              （ch11）—— 看懂"代码在哪块存储器"
③ 一个最简单的外设驱动   （gpio / uart）—— 看懂"MMIO 怎么访问"
④ 一个带中断的驱动       （exti / timer）—— 看懂"异步怎么同步"
⑤ 一个 RTOS 的调度器      （FreeRTOS tasks.c）—— 看懂"多任务怎么切换"
```

⚠ **别从 RTOS 开始读**——它假设你已经懂 ①~④。

## 坑点

| 坑 | 原书怎么说 | 实际是什么（实测） |
|---|---|---|
| "读源码 = 读 `.c` 文件" | —— | ⚠ **编译产物信息量更大**：实测 `gpio_set` 只有 2 条指令，一眼看穿 BSRR 技巧 |
| "库有 3 MB 就会占 3 MB" | —— | ⚠ 实测 libopencm3_stm32f1.a **3.0 MB**，但按需抽取只进用得上的成员 |
| "文档写的一定对" | —— | ⚠ 反汇编不会撒谎；本仓库多次实测推翻课本说法 |
| "先看 RTOS 比较有用" | —— | ⚠ RTOS 假设你已经懂启动/链接/中断；**按①②③④⑤顺序读** |

## 代码自测

<details>
<summary>Q1：677 个符号的库，我从哪读起？</summary>

先量体重，再定位，最后深入：

```
$ llvm-ar  -t libopencm3_stm32f1.a | wc -l                       → 53 个成员
$ llvm-nm    libopencm3_stm32f1.a | grep -cE '^[0-9a-f]+ ... '   → 677 个符号
$ ls -lh     libopencm3_stm32f1.a                                → 3.0 MB
```

**不要通读**——按"我现在要解决什么问题"来定位：

```bash
llvm-nm lib.a | grep -i gpio          # ① 找到相关符号
llvm-objdump -d --disassemble-symbols=gpio_set lib.a   # ② 看它编译成什么
```

⚠ **3.0 MB 是库的大小，不是你固件的大小**——
[17.3](../17-modular-programming/17.3-库.md) 实测过：
只用 `add` 时 `mul` 完全不进镜像（粒度是 `.o` 级）。
</details>

<details>
<summary>Q2：读反汇编真的有用吗？我又不写汇编。</summary>

**有用——因为反汇编回答的是"编译器到底做了什么"，而这经常和你想的不一样。**

实测例子（libopencm3 的 `gpio_set`）：

```
00000000 <gpio_set>:
       0:  str r1, [r0, #0x10]      ← 一次 32 位写，偏移 0x10
       2:  bx  lr
```

两条指令就让你看懂了三件事：

1. 偏移 `0x10` 是 **BSRR** → 它是"写 1 生效、写 0 无效"的寄存器；
2. 所以置位是**单条.store**，不需要读-改-写 → **天然原子**；
3. 整个函数 **4 字节**，比你自己写的还小。

**"GPIO 要用 BSRR 而不是 ODR |= bit"这条规则，看这一眼就彻底懂了。**

⚠ 反过来，**不读反汇编就不会发现这些打脸的事**：

- `static inline` 在 `-O0` 下每个 `.c` 生成一份（[17.1](../17-modular-programming/17.1-模块设计.md)）；
- 代码宏**不省机器码**（[12.3](../12-preprocessor/12.3-代码宏.md) 实测 28 B vs 28 B）；
- `-Os` 常量折叠让 `__aeabi_fmul` 凭空消失（[16.7](../16-floating-point/16.7-替代方案.md)）。
</details>

<details>
<summary>Q3：读别人的代码，怎么判断好坏？</summary>

按 [17.1](../17-modular-programming/17.1-模块设计.md) 的客观指标 + 三个产物层检查：

```bash
llvm-nm 驱动.o | grep -E ' [TDBCS] '   # ① 泄漏了多少外部符号？（越少越好）
llvm-nm 驱动.o | grep ' U '            # ② 依赖多少外部符号？（越少越独立）
llvm-size -A 驱动.elf                  # ③ 占多少 Flash / RAM？
llvm-objdump -d 驱动.o                 # ④ 关键路径几条指令？
```

实测对照（`leaky.o` 泄漏 **3** 个 vs `clean.o` 只有 **1** 个）。

**坏味道清单**：

- 头文件里有寄存器地址宏（实现细节泄漏）；
- 全局可变状态（`int g_rx_count`）而不是用函数读；
- 内部函数不加 `static`；
- ISR 里做耗时操作（[ch10](../10-interrupts/README.md)）；
- 没有边界检查（裸机上越界是静默的）。
</details>
