## 书这一节讲什么

一句话：**书列了一批开源工具；本篇逐个在本机验证"能不能用、值不值得上"。**

⚠ 结论先行：**书里列的 Cppcheck、Doxygen、Valgrind 在本机都没装**，
但 clang 自带了**零安装的替代品**（静态分析器 + clang-tidy + ASan/UBSan）。

## 二、⭐ 核心实测：三类工具在同一个 bug 上的表现

**样本 A**（`buggy.c`）：未初始化变量 + 符号转换 + **NULL 解引用**

```
编译期 -Wall -Wextra -Wconversion -Wshadow : 2 条
  buggy.c:14:9: variable 'sum' is uninitialized when used here [-Wuninitialized]
  buggy.c:17:17: implicit conversion changes signedness ... [-Wsign-conversion]
clang --analyze                            : ✅ 1 条（NULL 解引用）
  buggy.c:13:18: Array access (from variable 's') results in a null pointer dereference
  [core.NullDereference]  （还给了完整路径：main:27 置 NULL → main:28 传入 → process:13 解引用）
clang-tidy（clang-analyzer-* + bugprone-*） : ✅ 2 条
ASan + UBSan（运行期）                      : ✅ SEGV + 完整调用栈
  buggy.c:13:18: runtime error: load of null pointer of type 'const char'
  ERROR: AddressSanitizer: SEGV on unknown address 0x000000000000
    #0 process buggy.c:13   #1 main buggy.c:28
```

**样本 B**（`buggy2.c`）：栈溢出 + 堆溢出 + **双重释放**（3 个 bug）

```
编译期 -Wall -Wextra -Wconversion -Wshadow : 0 条   ← ⚠ 全开关也是 0
clang --analyze                            : 0 条   ← ⚠
clang-tidy                                 : 0 条   ← ⚠
ASan + UBSan（运行期）                      : ✅ 抓到 stack-buffer-overflow
  ERROR: AddressSanitizer: stack-buffer-overflow ... in process buggy2.c:8
    #0 process buggy2.c:8   #1 main buggy2.c:18
```

### ⚠ 最重要的结论

> **编译期工具（警告 + 静态分析）对"越界 / 双重释放"这类 bug 抓不到——
> 必须靠运行期的 sanitizer。**

| 工具 | 样本 A（NULL 解引用） | 样本 B（越界 + 双重释放） |
|---|---|---|
| 编译期警告全开 | ✅ 2 条（但**不是** NULL 那条） | ❌ **0 条** |
| `clang --analyze` | ✅ **1 条**（精确命中） | ❌ **0 条** |
| `clang-tidy` | ✅ 2 条 | ❌ **0 条** |
| **ASan + UBSan** | ✅ **SEGV + 调用栈** | ✅ **stack-buffer-overflow + 调用栈** |

⚠ 样本 A 里编译期抓到的 2 条是"未初始化"和"符号转换"——
**真正的致命 bug（NULL 解引用）只有静态分析器和 sanitizer 抓到了。**

## 三、⚠ 实测：`scan-build` 在本机跑不通（假阴性）

```
$ scan-build clang -c buggy.c
scan-build: Using '.../clang-23' for static analysis
buggy.c:1:10: fatal error: 'stdio.h' file not found
scan-build: 0 bugs found.          ← ⚠ 假的！它根本没编译成功
scan-build: The analyzer encountered problems on some source files.
```

原因：`xcrun --show-sdk-path` 在本机**返回空**（没装 Xcode CLT），
`scan-build` 拦截编译器后找不到系统头文件路径。

✅ **本机的正确用法**：直接用 `clang --analyze`（实测有效），
绕开 `scan-build` 的编译器拦截。

⚠ **这个坑的价值**：`scan-build` 输出 `0 bugs found` 时**不代表没问题**——
它可能是编译就失败了。**看报告前先确认"Analysis run complete"没有 error。**

## 四、⚠ 实测：`clang-tidy` 默认配置不出结果

```
$ clang-tidy buggy.c -- -Wall
（0 条警告）

$ clang-tidy buggy.c -checks='-*,clang-analyzer-*,bugprone-*'
2 warnings generated.
buggy.c:13:18: warning: Array access ... null pointer dereference [clang-analyzer-core.NullDereference]
buggy.c:17:17: warning: narrowing conversion from 'uint32_t' to 'int' is implementation-defined
                        [bugprone-narrowing-conversions]
```

⚠ **必须显式开 checks**——默认的 checks 在这份代码上是 0 条。

✅ 推荐配置（写进 `.clang-tidy`）：

```yaml
Checks: '-*,clang-analyzer-*,bugprone-*,cert-*,misc-*'
WarningsAsErrors: ''
```

⚠ 另外 `clang-tidy` 会先抱怨 "Could not auto-detect compilation database"——
单文件直接用没问题，工程化最好生成 `compile_commands.json`
（`cmake -DCMAKE_EXPORT_COMPILE_COMMANDS=ON`）。

## 五、每天都在用的四个（零成本、本仓库已在用）

```bash
# ① 编译期：警告开满（成本 0）
clang -Wall -Wextra -Wconversion -Wshadow -Werror ...

# ② 静态分析（成本 0，clang 自带）
clang --analyze -Xclang -analyzer-output=text foo.c
clang-tidy foo.c -checks='-*,clang-analyzer-*,bugprone-*'

# ③ 运行期：sanitizer（主机侧逻辑测试）
clang -O1 -g -fsanitize=address,undefined -o test test.c && ./test

# ④ 资源账本（成本 0，裸机必须持续可见）
clang -fstack-usage -c foo.c && cat foo.su     # 栈
llvm-size -A foo.elf                            # Flash / RAM
```

**④ 实测输出**（本仓库 `make check-stack`）：

```
--- main.su（单位：字节）---
main.c:32:stack_probe	128	static
main.c:47:main	0	static
--- 对照 SRAM 容量 ---
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 20K
```

**④ 另一例**（本次实测 `buggy.c`）：

```
buggy.c:8:process	48	static
buggy.c:26:main	0	static
__text 140    __data 8
```

## 七、按投入产出比排序（建议的上线顺序）

| 顺序 | 工具 | 成本 | 抓什么 |
|---|---|---|---|
| **①** | `-Wall -Wextra -Wconversion -Wshadow -Werror` | **0** | 未初始化、符号转换、类型问题 |
| **②** | `clang --analyze`（零安装） | **0** | NULL 解引用、逻辑路径 bug（**带路径说明**） |
| **③** | `clang-tidy -checks=...` | 低 | ①+② 的超集 + narrowing conversion 等 |
| **④** | **`-fsanitize=address,undefined`** | 低 | ⭐ **越界 / 双重释放 / UB**（编译期抓不到的都在这） |
| **⑤** | `-fstack-usage` + `llvm-size` | **0** | 栈 / Flash / RAM 预算 |
| ⑥ | Cppcheck | 中（要装） | 本机未装，用 ②③ 替代 |
| ⑦ | Doxygen | 中 | 要给别人看时才上 |
| ⑧ | 逻辑分析仪 / 示波器 | 高 | **硬件调试的终极工具**，比任何软件工具都直接 |

⚠ **不要一开始就上**：全套静态分析（误报多，要调规则）、
单元测试框架（小项目开销大于收益）、CI（个人项目先手动）。

⚠ **ASan 的两个已知限制**（[13.4](../13-dynamic-memory/13.4-GCC-AddressSanitizer.md) 实测）：

1. **双重释放只在 `-O0` 能抓到**——`-O1`/`-O2` 下 LLVM 会把 malloc/free 优化掉（实测调用数 3 → 0）；
2. **macOS 上 LSan 不报泄漏**（`detect_leaks=1` 只打印 "checking for leaks"）——
   查泄漏要用 Linux 上的 Valgrind。

## 代码自测

<details>
<summary>Q1：工具这么多，我先上哪个？</summary>

按投入产出比，**前三个零成本**：

**① `-Wall -Wextra -Wconversion -Wshadow -Werror`（成本 0）**

实测样本 A 抓到 2 条（未初始化 + 符号转换）。
这是唯一"写进 Makefile 就再也不用管"的工具。

**② `clang --analyze`（成本 0，clang 自带，不用装 Cppcheck）**

实测抓到**编译期抓不到的** NULL 解引用，还给了完整路径：

```
buggy.c:13:18: warning: Array access results in a null pointer dereference
buggy.c:27:5: note: 's' initialized to a null pointer value
buggy.c:28:28: note: Passing null pointer value via 1st parameter 's'
```

**③ `-fsanitize=address,undefined`（成本低，收益最高）**

实测样本 B：编译期 + 静态分析**都是 0 条**，只有 ASan 抓到：

```
ERROR: AddressSanitizer: stack-buffer-overflow ... in process buggy2.c:8
```

**④ `-fstack-usage` + `llvm-size`（成本 0）** —— 裸机的两个硬约束必须持续可见。

之后再上：Cppcheck（代码上千行后；本机用 ② 替代）、Doxygen（要给别人时）、
逻辑分析仪（调时序时，**硬件调试的终极工具**）。
</details>

<details>
<summary>Q2：`scan-build` 报 0 bugs，是不是我的代码没问题？</summary>

**不一定——本机实测就是假阴性。**

```
$ scan-build clang -c buggy.c
buggy.c:1:10: fatal error: 'stdio.h' file not found
scan-build: 0 bugs found.          ← ⚠ 编译根本没成功
scan-build: The analyzer encountered problems on some source files.
```

原因：`xcrun --show-sdk-path` 在本机**返回空**（没装 Xcode CLT），
`scan-build` 拦截编译器后找不到头文件路径。

✅ **本机的正确做法**：直接用 `clang --analyze`（实测有效），绕开拦截。

⚠ **通用教训**：看到 "0 bugs found" 时，
**先确认没有 `fatal error` / `encountered problems`**——
否则那只是"没编译成功"，不是"没问题"。
</details>

<details>
<summary>Q3：`clang-tidy` 跑出来 0 条，是配置错了吗？</summary>

**很可能是没开 checks。** 实测：

```
$ clang-tidy buggy.c -- -Wall                                  → 0 条
$ clang-tidy buggy.c -checks='-*,clang-analyzer-*,bugprone-*'  → 2 条
   buggy.c:13:18: null pointer dereference [clang-analyzer-core.NullDereference]
   buggy.c:17:17: narrowing conversion ... [bugprone-narrowing-conversions]
```

✅ 推荐在仓库根放一个 `.clang-tidy`：

```yaml
Checks: '-*,clang-analyzer-*,bugprone-*,cert-*,misc-*'
```

⚠ 另外它会先打印 "Could not auto-detect compilation database"——
单文件用没问题；工程化请生成 `compile_commands.json`
（`cmake -DCMAKE_EXPORT_COMPILE_COMMANDS=ON`）。
</details>

<details>
<summary>Q4：ASan/UBSan 有什么抓不到的？</summary>

⚠ **两条实测限制**（[13.4](../13-dynamic-memory/13.4-GCC-AddressSanitizer.md)）：

1. **双重释放只在 `-O0` 抓得到**。
   实测 LLVM IR 里 malloc/free 调用数：`-O0` 是 3、`-O1` 是 **0**——
   优化器把"分配了立刻释放"的死代码删了，ASan 就没东西可查。
   ⇒ **跑 sanitizer 用 `-O1`，但查双重释放要 `-O0`**。

2. **macOS 上 LSan（泄漏检测）不报**。
   实测 `ASAN_OPTIONS=detect_leaks=1:verbosity=1` 只打印 "checking for leaks"，
   没有泄漏报告。⇒ 查泄漏要用 **Linux 上的 Valgrind**（本机未安装）。

⚠ 另外：ASan 是**运行期**工具——**没跑到的代码路径不会报警**。
样本 B 里它在第一个 bug（栈溢出）就崩了，
后面的堆溢出和双重释放**根本没跑到**——
所以"ASan 没报"不等于"后面没问题"。
</details>
