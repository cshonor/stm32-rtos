# 17.5 确定性与不确定性库

> 书：第 17 章 模块化编程 · 17.5 确定性与不确定性库（原书 p227+ 区间内）
> 上一篇：[17.4 ranlib 与库链接](17.4-ranlib与库链接.md) ｜ 下一篇：[17.6 弱符号](17.6-弱符号.md)
> 对应实验：**裸机真链接**（`ld.lld` 23.1.0 + 本仓库 `linker.ld`）

## 书这一节讲什么

一句话：**链接器按命令行从左到右处理，库只在被处理的那一刻起作用——
所以 `-lxxx` 要放最后。但"会不会因此失败"取决于链接器。**

本篇给出 **ld.lld 23.1.0 的实测行为**，它和课本上讲的"GNU ld 单遍扫描"**不一样**。

## 一、单遍扫描的原理

```
维护一个"未解决符号表"
从左到右处理命令行上的每个文件：
  - 遇到 .o：提供的符号 → 已定义；未定义的 → 加入待解决表
  - 遇到 .a：查索引，只抽取"能解决当前待解决表"的成员
```

**关键**：库只在被处理的那一刻起作用。

```
❌ 错序：处理 libmymath.a（待解决表空）→ 没抽取 → 处理 main.o（add 待解决）→ 没库了 → 失败
✅ 对序：处理 main.o（add 待解决）→ 处理 libmymath.a（抽 add.o）→ 解决
```

## 二、⚠ 实测：ld.lld 23.1.0 比课本说的宽容

裸机（`ld.lld` 23.1.0 + `linker.ld`，`bapp.o` 引用 `add`，库是 `libdrv.a`）：

```
=== ① 正确顺序：库在 .o 之后 ===
$ ld.lld -T linker.ld --gc-sections -o ok.elf bvec.o bapp.o -L. -ldrv
   ✅ 链接成功    text 52  data 8  bss 4

=== ② 错误顺序：库在 .o 之前 ===
$ ld.lld -T linker.ld --gc-sections -o bad.elf -L. -ldrv bvec.o bapp.o
   ✅ 链接成功（！）   text 52  data 8  bss 4    ← 大小完全一样
```

**lld 不会失败**，而且**完全静默**（stderr 为空）。

⚠ 但 lld 有专门的诊断开关：

```
=== ②-b 加 --warn-backrefs ===
$ ld.lld -T linker.ld --gc-sections --warn-backrefs -o bad2.elf -L. -ldrv bvec.o bapp.o
   ✅ 链接成功
   ⚠ ld.lld: warning: backward reference detected:
             add in bapp.o refers to ./libdrv.a(badd.o)
```

| 链接器 | 库在 `.o` 之前 | 出处 |
|---|---|---|
| **ld.lld 23.1.0** | ✅ **能过**，默认静默；加 `--warn-backrefs` 才报警 | **本次实测** |
| **macOS ld64** | ✅ **能过**（会重扫） | 旧笔记实测过 |
| GNU ld | ❌ 经典行为是 `undefined reference` | ⚠ **本机没有 GNU ld，未实测** |

⚠ **诚实标注**：本机只有 `ld.lld` 23.1.0 和 macOS `ld64`，
**没有 GNU ld**，所以"GNU ld 会报 undefined reference"是**教科书说法，本机未实测**。

## 三、✅ 正确的做法（不管链接器多宽容）

```bash
# ① 库放最后（推荐，零成本）
clang -o app main.o -L. -lmymath

# ② 循环依赖：用 group 让链接器反复扫
ld.lld -o app.elf bvec.o bapp.o --start-group -L. -ldrv --end-group

# ③ 干脆列两遍（老办法）
ld.lld -o app.elf bvec.o bapp.o -ldrv -ldrv
```

实测 `--start-group` 也能成功，且结果一致：

```
=== ③ 用 group 补救循环依赖 ===
   ✅ --start-group 也能成功    text 52  data 8  bss 4
```

**依赖顺序的规则**（库之间）：

```
若 libA 引用 libB 的符号 → -lA 要在 -lB 前面
（因为处理 -lA 时引入的待解决符号，要由后面的 -lB 解决）
```

## 四、⚠ 真正的"不确定性"：多个库提供同一个符号

这才是最危险的不确定——**不是顺序能不能过，而是"选了谁"**：

| 情况 | 结果 |
|---|---|
| 两个 `.o` 提供同名强符号 | ❌ `duplicate symbol` 报错（[17.2](17.2-命名空间.md) 实测） |
| 两个**库**各有一个同名强符号 | ⚠ **不报错**——谁在前面就抽谁，**后面的库根本不参与** |
| 两个弱定义 | ⚠ 选第一个（[17.6](17.6-弱符号.md) 实测 `board_id() = 0`） |

⚠ **第一种"库版本"尤其阴险**：
`libA.a` 和 `libB.a` 都有一个 `log_init()`，
命令行 `-lA -lB` 时用到 B 的那个——你以为用的是 A。
**而且换一次命令行顺序，行为就变了，且没有警告。**

✅ 对策：

- **前缀纪律**（[17.2](17.2-命名空间.md)）是唯一根本解法；
- 用 `llvm-nm` 检查库里有没有重复符号；
- 链接后 `llvm-nm app.elf | grep 关键符号` 看地址来自哪个成员
  （配合 `--print-map` 能看全貌）。

## 五、⚠ 裸机上的"确定性"还有一层意思

裸机没有动态库，所有符号在链接时定死，
所以**链接产物的确定性 = 可复现构建（reproducible build）**：

| 因素 | 影响 |
|---|---|
| 库的顺序 | 影响抽哪个成员（见上一节） |
| 成员的加入顺序 | 影响最终地址布局 |
| 弱符号的选取 | 影响默认实现还是覆盖 |
| 时间戳 / 路径 | 影响 `.comment` 等段（可用 `-frandom-seed` 等控制） |

⚠ **调试意义**：如果你发现"同样的代码，换个链接顺序行为就变了"，
第一嫌疑就是**多库同名符号**或**弱符号选取**。

## 坑点

| 坑 | 原书怎么说 | 实际是什么（实测） |
|---|---|---|
| "库放前面会 undefined reference" | GNU ld 的经典行为 | ⚠ **ld.lld 23.1.0 实测能过且静默**；要 `--warn-backrefs` 才报 |
| "lld 和 GNU ld 行为一致" | 常说 | ⚠ **不一致**（backward reference 处理不同）；GNU ld 本机未实测 |
| "多个库有同名符号会报错" | —— | ⚠ **不报错**，谁在前面抽谁，**且换顺序行为就变** |
| "`--start-group` 会降低性能" | —— | 会（反复扫），但循环依赖时是唯一干净解法 |
| "库顺序只影响能否链接" | —— | ⚠ 还影响**抽到哪个实现**（多库同名时） |

## 代码自测

<details>
<summary>Q1：为什么库要放在命令行的最后？</summary>

因为链接器**从左到右单遍处理**，库只在被处理的那一刻起作用：

```
处理 libmymath.a：待解决表是空的 → 没有成员被抽取 → 库被完全跳过
处理 main.o：     add 变成待解决 → 但后面没有库了
```

放对顺序：

```
处理 main.o：     add 进入待解决表
处理 libmymath.a：查索引 → 抽 add.o → 解决
```

⚠ **但实测 ld.lld 23.1.0 并没有因此失败**：

```
$ ld.lld -T linker.ld --gc-sections -o bad.elf -L. -ldrv bvec.o bapp.o
   ✅ 链接成功（大小与正确顺序完全一致）
$ ld.lld ... --warn-backrefs ...
   ⚠ warning: backward reference detected: add in bapp.o refers to ./libdrv.a(badd.o)
```

**所以"库放最后"是正确的习惯，但不要指望链接器替你报错。**
建议**在 CI 里常开 `--warn-backrefs`**——否则这类问题会静默潜伏。
</details>

<details>
<summary>Q2：两个库里都有 `log_init()`，会报重复定义吗？</summary>

**不会——这是最阴的一种"不确定性"。**

| 情况 | 结果 |
|---|---|
| 两个 `.o` 提供同名强符号 | ❌ `duplicate symbol`（实测） |
| 两个**库**各有一个同名强符号 | ⚠ **不报错**，谁在命令行前面就抽谁 |

原因：库是**按需抽取**的——`libA.a` 先提供了 `log_init`，
待解决表里就没它了，`libB.a` 根本不会被翻到。

⚠ 后果：**换一次命令行顺序，抽到的实现就变了，而且没有任何警告。**
你以为调的是 A 的 `log_init`，实际是 B 的。

✅ 对策：

1. **前缀纪律**（[17.2](17.2-命名空间.md)）是根本解法：`a_log_init()` / `b_log_init()`；
2. 建库后 `llvm-nm lib*.a | sort | uniq -d` 查重复符号；
3. 链接后 `llvm-nm app.elf | grep log_init` 看地址，配合 map 文件确认来源。
</details>

<details>
<summary>Q3：循环依赖怎么办？</summary>

三个办法，实测都能过：

```bash
# ① 库放最后（能避免大部分情况）
ld.lld -o app.elf bvec.o bapp.o -L. -ldrv

# ② --start-group / --end-group：让链接器反复扫到不再变化
ld.lld -o app.elf bvec.o bapp.o --start-group -L. -ldrv --end-group
   ✅ 实测成功，text 52 data 8 bss 4（与 ① 一致）

# ③ 干脆列两遍（老办法）
ld.lld -o app.elf bvec.o bapp.o -ldrv -ldrv
```

⚠ **② 的代价**：group 里的库会被**反复扫描**直到不再引入新符号，
库大时链接变慢。所以：

- 能用顺序解决就用顺序（零成本）；
- 真有循环依赖（A 用 B 的、B 也用 A 的）再用 group；
- ⚠ **循环依赖本身往往是模块划分有问题**——优先重构，而不是靠 group 兜。
</details>

<details>
<summary>Q4：我怎么知道自己的链接有没有"backward reference"？</summary>

加 `--warn-backrefs`（lld）：

```
$ ld.lld -T linker.ld --gc-sections --warn-backrefs -o app.elf -L. -ldrv bvec.o bapp.o
ld.lld: warning: backward reference detected:
        add in bapp.o refers to ./libdrv.a(badd.o)
```

⚠ **默认不开**，所以要自己加。建议：

- 裸机项目：把 `--warn-backrefs` 写进 Makefile（零成本，能抓到顺序问题）；
- 想更彻底：加 `-Wl,--fatal-warnings` 把它升级成错误；
- ⚠ GNU ld 没有这个选项（它直接报错），所以"移植到 GNU ld 时会突然失败"——
  **这也是为什么要主动检查而不是等它报错**。
</details>
