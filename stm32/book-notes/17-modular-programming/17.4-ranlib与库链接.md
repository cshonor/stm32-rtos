# 17.4 ranlib 与库链接

> 书：第 17 章 模块化编程 · 17.4 ranlib 与库链接（原书 p227+ 区间内）
> 上一篇：[17.3 库](17.3-库.md) ｜ 下一篇：[17.5 确定性与不确定性库](17.5-确定性与不确定性库.md)
> 对应实验：主机侧实测（clang 23.1.0 + macOS `ar` / `llvm-ar` 23.1.0）
> + **裸机真链接**（`ld.lld` 23.1.0 + 本仓库 `linker.ld`）

## 书这一节讲什么

一句话：**`ranlib` 给 `.a` 建符号索引；现代 `ar s` 已经顺带做了，
但"库用什么工具建"在交叉编译时仍然有坑。**

## 一、索引是什么（实测）

```
$ ar rcs libmymath.a add.o mul.o
$ ar -t libmymath.a
__.SYMDEF SORTED      ← 这就是索引
add.o
mul.o
```

`__.SYMDEF`（BSD/macOS 叫法；ELF 侧是 `__.symtab` / `_.symtab`）
是一个"**符号名 → 哪个成员**"的查找表。
没有它，链接器就得**逐个成员解压扫描**——慢，但结果一样。

**历史上的 `ranlib`**：

```bash
ar rc libfoo.a a.o b.o     # 只打包，不建索引
ranlib libfoo.a            # 单独建索引（老式 Unix 必须这步）
```

现代写法 `ar rcs`（`s` = 建索引）或者 `ar s` 已经合并了这一步，
所以 **`ranlib` 一般不用手动跑**。

## 二、⚠ 实测：交叉编译时 macOS 的 `ar` 建不出索引

这是一个本机真实踩到的坑。

```
$ ar rcs libdrv.a badd.o bmul.o       # 成员是 armv7m 的 ELF 目标文件
warning: .../arm64-apple-darwin20.0.0-ranlib: archive library: libdrv.a
         the table of contents is empty
         (no object file members in the library define global symbols)
```

**原因**：macOS 的 `ar`/`ranlib` 按 **Mach-O** 格式去解析成员，
遇到 **ELF** 目标文件就认不出符号，于是索引是空的。

✅ **解决办法：用 LLVM 的 `ar`**（格式无关）：

```bash
llvm-ar rcs libdrv.a badd.o bmul.o
llvm-ar -t libdrv.a
badd.o
bmul.o                      ← ✅ 正常（无警告）
```

| 工具 | 对 ELF 成员建索引 | 备注 |
|---|---|---|
| macOS `ar` / `ranlib` | ⚠ **失败**（警告，索引为空） | 按 Mach-O 解析 |
| **`llvm-ar`** | ✅ 正常 | 格式无关，交叉编译首选 |
| GNU `ar`（Linux） | ✅ 正常 | 本机没有，未实测 |

⚠ **后果**：索引为空时链接**仍然能成功**（lld 会退化成全扫描，慢一些），
所以这个坑很容易被忽略——**直到某天你的库变大了才发现链接变慢**。

## 三、链接命令（实测）

**主机侧**：

```bash
clang -c mymath.c -o mymath.o
ar rcs libmymath.a mymath.o
clang -o app main17.c -L. -lmymath     # ✅ -l 放最后
./app
add(3,4)=7
```

**裸机侧**（本仓库的实际命令形态）：

```bash
clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -Os \
      -ffreestanding -nostdlib -ffunction-sections -fdata-sections \
      -c bvec.c -o bvec.o -c bapp.c -o bapp.o
llvm-ar rcs libdrv.a badd.o bmul.o
ld.lld -T linker.ld --gc-sections -o ok.elf bvec.o bapp.o -L. -ldrv
```

```
   ✅ 链接成功
      text 52   data 8   bss 4   → Flash 60 B
   镜像里的 add/mul: 0800002e T add
```

## 四、⚠ 实测：macOS 的 `ar` 会把 `ranlib` 也换掉

注意上面警告里的路径：

```
/Users/a0000/micromamba/envs/cdev/bin/arm64-apple-darwin20.0.0-ranlib
```

`ar s` 内部是去调 `ranlib` 的，而 micromamba 的 `cdev` 环境里
`ar` 和 `ranlib` 都带 target triple 前缀。
所以**换 `ar` 就是换整套**——用 `llvm-ar` 就同时避开了 `ranlib` 的问题。

## 五、检验库的工具

```bash
llvm-ar -t libxxx.a          # 列出成员（看有没有 __.SYMDEF）
llvm-nm libxxx.a             # 列出每个成员的符号
llvm-nm -s libxxx.a          # 只列索引（armap）
llvm-size libxxx.a           # 各成员大小（部分实现支持）
```

一个"健康"的库应该是：

- `ar -t` 有 `__.SYMDEF`（或 `__.symtab`）；
- `llvm-nm` 能看到每个成员的 `T`/`D` 符号；
- **没有** "table of contents is empty" 警告。

## 坑点

| 坑 | 原书怎么说 | 实际是什么（实测） |
|---|---|---|
| "`ar` 之后还要跑 `ranlib`" | 书 17.4 标题就是这个 | ✅ 现代 `ar rcs`（带 `s`）已包含索引；实测 `ar -t` 能看到 `__.SYMDEF SORTED` |
| "`ar` 是通用的" | 隐含 | ⚠ **macOS `ar` 对 ELF 成员建不出索引**（实测警告），要用 `llvm-ar` |
| "索引为空会链接失败" | —— | ⚠ **不会失败**，只是退化成全扫描（慢）——所以这坑很容易被忽略 |
| "`.a` 就是 zip" | —— | 不完全：它有**符号索引**这个额外结构，且不同平台格式不通用 |

## 代码自测

<details>
<summary>Q1：`ranlib` 现在还需要手动跑吗？</summary>

**基本不需要。** `ar rcs` 里的 **`s`** 就是"建索引"：

```bash
ar rc  libfoo.a a.o b.o     # 只打包
ranlib libfoo.a             # 老式 Unix：单独建索引（书里讲的就是这个）
ar rcs libfoo.a a.o b.o     # ✅ 现代写法，一步到位
```

实测 `ar rcs` 之后：

```
$ ar -t libmymath.a
__.SYMDEF SORTED     ← ✅ 索引已经在了
add.o
mul.o
```

⚠ **真正的坑不是"要不要跑 ranlib"，而是"ar 认不认识你的目标文件格式"**——
见下一题。
</details>

<details>
<summary>Q2：交叉编译建库时，为什么我的 `.a` 会有 "table of contents is empty" 警告？</summary>

因为 **macOS 的 `ar`/`ranlib` 按 Mach-O 解析成员，认不出 ELF**。

实测（成员是 `--target=armv7m-none-eabi` 编出来的 ELF）：

```
$ ar rcs libdrv.a badd.o bmul.o
warning: .../arm64-apple-darwin20.0.0-ranlib: archive library: libdrv.a
         the table of contents is empty
         (no object file members in the library define global symbols)
```

✅ 改用 LLVM 的 `ar`（格式无关）：

```bash
$ llvm-ar rcs libdrv.a badd.o bmul.o
$ llvm-ar -t libdrv.a
badd.o
bmul.o              ← ✅ 无警告
```

⚠ **这个坑很隐蔽**：索引为空时**链接照样成功**
（lld 退化成全扫描），只是变慢。
所以别因为"能编译过"就以为没问题——**看到这条警告就要换 `llvm-ar`**。
</details>

<details>
<summary>Q3：怎么验证一个库是"健康的"？</summary>

三步：

```bash
llvm-ar -t libxxx.a      # ① 有 __.SYMDEF / __.symtab 索引吗？
llvm-nm libxxx.a         # ② 每个成员的 T/D 符号看得到吗？
                         # ③ 建库时有没有 "table of contents is empty" 警告？
```

健康的样子（实测）：

```
$ ar -t libmymath.a
__.SYMDEF SORTED
add.o
mul.o
$ llvm-nm libmymath.a
add.o:
0000000000000000 T _add
mul.o:
0000000000000000 T _mul
```

⚠ 如果 `nm` 输出是空的、或者建库时有警告，
说明索引没建成——**链接会退化成全扫描，库大时明显变慢**。
</details>
