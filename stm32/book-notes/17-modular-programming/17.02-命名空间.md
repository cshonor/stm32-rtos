# 17.02 命名空间

> 书：第 17 章 模块化编程 · 17.02 命名空间（原书 p227+ 区间内）
> 上一篇：[17.01 模块设计](17.01-模块设计.md) ｜ 下一篇：[17.03 库](17.03-库.md)
> 对应实验：主机侧实测（clang 23.1.0 / macOS arm64）

## 书这一节讲什么

一句话：**C 只有一个全局命名空间，`static` + 前缀约定是唯一的防御手段。**

C 没有 `namespace`、`class`、`module` 关键字，
但 Linux 内核、FreeRTOS、Zephyr 这些超大型 C 项目照样组织得很好——
靠的就是本章这套**约定**。

## 一、`static` 到底做了什么（实测）

`static` 在文件作用域只做一件事：**把符号的链接属性从 external 改成 internal**。

| | 不加 `static` | 加 `static` |
|---|---|---|
| `nm` 里的符号 | **大写**（`T` `D` `B` `S`） | **小写**（`t` `d` `b` `s`） |
| 可见范围 | 整个程序（任何 `.o` 都能 `extern` 引用） | 只有本 `.c` |
| 同名冲突 | **链接错误** | 各文件互不影响 |

⚠ **实测：不加 `static` 会直接撞名**

```c
/* dup1.c */ unsigned rx_count = 0;  unsigned f1(void){ return rx_count; }
/* dup2.c */ unsigned rx_count = 0;  unsigned f2(void){ return rx_count; }
```

```
$ clang -O1 -o dup dupmain.c dup1.c dup2.c
duplicate symbol '_rx_count' in:
ld: 1 duplicate symbol for architecture arm64
```

两个模块各自有个"接收计数"，都叫 `rx_count`——**链接直接失败**。
加了 `static` 就各是各的，而且编译器知道没人从外面改它，**优化更激进**。

## 二、⚠ 更隐蔽的坑：意外的外部依赖

```c
/* foo.c */
void helper(void){ /* ... */ }        /* 忘了加 static */

/* bar.c（另一个人写的，三年后） */
extern void helper(void);             /* 咦，有个 helper，用了 */
```

于是 `bar.c` 悄悄依赖了 `foo.c` 的内部实现。
后来有人重构 `foo.c` 删掉 `helper` → `bar.c` 链接失败；
或者更糟：有人改了 `helper` 的语义 → `bar.c` 行为异常，**且没有编译错误**。

## 三、规则

```c
/* gpio.h —— 公开接口，全部带 gpio_ 前缀 */
void     gpio_init(void);
void     gpio_set(unsigned pin);
void     gpio_clear(unsigned pin);
unsigned gpio_read(unsigned pin);

/* gpio.c —— 内部实现，全部 static + 双下划线前缀 */
static void gpio__enable_clock(unsigned port){
    RCC->APB2ENR |= (1u << (2u + port));
}
```

1. **所有不打算给外部用的函数和全局变量，一律 `static`**——
   这不是风格，是**防止符号冲突的唯一手段**；
2. **公开函数统一前缀**（`uart_`、`gpio_`、`rb_`）——**前缀就是 C 的命名空间**；
3. **头文件里只放声明 + 必要的类型**，不放实现（除非 `static inline`）；
4. **头文件必须有 include guard**（[ch12](../12-preprocessor/README.md) 实测撞名会静默吞掉整个头文件）。

| 作用域 | 写法 | 谁可见 |
|---|---|---|
| 文件内 | `static void helper(void)` | 只有本 `.c` |
| 模块内公开 | `gpio_set()` | 所有包含 `gpio.h` 的地方 |
| 全局（危险） | 不带 `static`、也不在头文件里声明 | **所有地方** |

## 四、⚠ 裸机特例：ISR 名字不能加前缀

**中断处理函数名是"硬件约定"的**：
`USART1_IRQHandler`、`SysTick_Handler`、`HardFault_Handler` 必须叫这个名字，
因为**向量表里引用的就是这些符号**（[ch03](../03-embedded-system-programming/README.md) 实测过）。

所以 **ISR 是唯一"必须污染全局命名空间"的地方**——
这也提醒我们：**别的地方更要严格用 `static`**。

⚠ 这也是为什么裸机项目比 PC 项目更需要前缀纪律：
全局命名空间已经被硬件占走了一大块。

## 五、⚠ 实测：碰撞的两种形态

| 情况 | 结果 |
|---|---|
| **两个强定义同名** | ❌ `duplicate symbol '_board_id'`（实测） |
| **一个弱 + 一个强** | ✅ 强覆盖弱，不报错（[17.06](17.06-弱符号.md)） |
| **两个弱定义同名** | ⚠ **不报错，选第一个**（实测 `board_id() = 0`），**不确定** |
| **两个 `static` 同名** | ✅ 各是各的，完全合法 |

实测第二个和第三个：

```
$ clang -O1 -o w2 weak_demo.c override.c && ./w2
board_id() = 103          ← 强定义覆盖弱定义
$ clang -O1 -o w5 weak_demo.c override.c override2.c
duplicate symbol '_board_id'    ← 两个强定义 → 报错
```

## 六、前缀约定的常见形式

| 项目 | 前缀风格 | 例子 |
|---|---|---|
| 本仓库 | `模块_动作` | `uart_init()`、`rb_put()`、`gpio_set()` |
| Linux 内核 | 子系统前缀 | `kmalloc()`、`i2c_transfer()` |
| FreeRTOS | `x` / `v` / `pv` 表返回类型 | `xQueueSend()`、`vTaskDelay()` |
| Zephyr | 子系统前缀 | `gpio_pin_set()`、`k_mutex_lock()` |
| 内部辅助 | **双下划线** | `uart__enable_clock()` |

⚠ **不要用 `_` 开头**：以下划线开头的标识符是**保留给实现**的
（`_start`、`_exit` 这类），自己起的名带下划线前缀有 UB 风险。
用 `模块__` 双下划线放中间/结尾是安全的。

## 坑点

| 坑 | 原书怎么说 | 实际是什么（实测） |
|---|---|---|
| "不加 `static` 也没事" | 一般不强调 | ⚠ 实测两个 `rx_count` → **`duplicate symbol`** 链接失败 |
| "前缀只是命名风格" | 是约定 | ⚠ **C 没有 namespace，前缀就是唯一机制** |
| "`static` 只是限制作用域" | 对 | 还有额外收益：编译器优化更激进（实测 `clean.o` 只剩 1 个外部符号） |
| "ISR 也能加前缀" | —— | ❌ **不能**，向量表里是硬件约定的符号名 |
| "两个弱定义会报错" | —— | ⚠ **不报错**，选第一个（实测 `board_id() = 0`）——**不确定，别依赖** |
| "`_foo` 前缀挺清楚的" | —— | ⚠ 以下划线开头是**保留标识符**，有 UB 风险 |

## 代码自测

<details>
<summary>Q1：`static` 到底做了什么？不加会出什么问题？</summary>

**它把符号的链接属性从 external 改成 internal。**

实测符号表（同一个模块两种写法）：

```
--- leaky.o ---                 --- clean.o ---
T _api_get                      T _api_get
T _helper_sum   ← ⚠ 全局        （无）
S _rx_count     ← ⚠ 全局        b _s_rx_count   ← 小写 = 本地
```

两类问题：

**① 撞名（最直接）**

```c
/* uart.c */ unsigned rx_count;
/* spi.c  */ unsigned rx_count;    /* 也全局 */
```

```
duplicate symbol '_rx_count' in:
ld: 1 duplicate symbol for architecture arm64
```

**② 意外的外部依赖（更隐蔽）**

三年后另一个人 `extern void helper(void);` 用了你漏出去的内部函数，
于是他的模块悄悄依赖你的实现细节——你重构时他就炸，而且**没有编译警告**。

**规则**：不打算给外部用的一律 `static`；公开的放头文件 + 统一前缀。
</details>

<details>
<summary>Q2：为什么 ISR 名字不能加 `uart_` 这样的前缀？</summary>

因为**向量表里引用的符号名是硬件/启动文件约定好的**。

启动文件（或向量表定义）里写的是：

```c
__attribute__((section(".vectors"), used))
unsigned long g_vectors[] = {
    (unsigned long)&_estack,
    (unsigned long)Reset_Handler,
    (unsigned long)NMI_Handler,
    (unsigned long)HardFault_Handler,
    (unsigned long)EXTI0_IRQHandler,      /* ← 就叫这个名字 */
    ...
};
```

这些名字来自 CMSIS 的约定（芯片厂商的头文件里也是这些名字）。
你写成 `uart_EXTI0_IRQHandler`，链接时向量表里的 `EXTI0_IRQHandler` 就没人定义，
会被弱别名兜底成 `Default_Handler`（死循环）——**中断永远进不去你的处理函数**。

⚠ 反过来说：**ISR 是唯一必须污染全局命名空间的地方**，
所以别的地方更要严格 `static`——全局命名空间已经被硬件占走了一大块。
</details>

<details>
<summary>Q3：两个弱定义同名会怎样？两个强定义呢？</summary>

实测四种组合：

| 情况 | 结果 |
|---|---|
| 一个弱，没人覆盖 | ✅ 用弱定义（实测 `board_id() = 0`） |
| **一个弱 + 一个强** | ✅ 强覆盖弱（实测 `board_id() = 103`） |
| **两个弱** | ⚠ **不报错，选第一个**（实测 `board_id() = 0`）→ **不确定，别依赖** |
| **两个强** | ❌ `duplicate symbol '_board_id'` |

**所以模式永远是"一个弱 + 至多一个强"。**

⚠ 两个弱定义"选第一个"是**命令行顺序决定的**，
换个链接器、换个链接顺序就可能变——**这是真正的"不确定性"**
（对应 [17.05](17.05-确定性与不确定性库.md) 讲的链接顺序问题）。
</details>

<details>
<summary>Q4：内部辅助函数用什么命名？`_helper` 可以吗？</summary>

**不要用 `_` 开头。** C 标准保留了一批标识符给实现：

- 所有**以下划线开头**的全局标识符（`_foo`、`_start`）→ 保留；
- 所有**双下划线**在任意位置的（`foo__bar` 其实不违规，但 `__foo` 违规）→ 保留；
- 下划线 + 大写字母（`_Foo`）→ 保留。

✅ 安全的做法：

```c
static void uart__enable_clock(void);    /* 模块名 + 双下划线，放中间 */
static void gpio__write_bsrr(uint32_t v);
```

这样既有前缀（排序时和本模块的函数聚在一起），
又不侵入保留命名空间，还能一眼看出"这是内部的"。
</details>
