## 书这一节讲什么

前五节讲的都是"链接脚本必须怎么写"。11.6 讲的是**链接脚本还能干什么**——
四个已经超出"把程序放对地方"的用法：

| 子节 | 解决什么问题 |
|---|---|
| **"永久"存储的闪存** | 让变量的值**掉电后还留着** |
| **多配置项** | 一堆配置怎么在 Flash 里排版、怎么保证顺序稳定 |
| **定制实例** | 同一份固件，每台设备参数不同（序列号 / 标定值） |
| **固件升级** | bootloader + app 两个程序共存，各自有自己的地址 |

共同点：**都是靠"自定义段 + `MEMORY` 里划区"实现的**。
链接脚本在这里从"必需品"变成"工具"。

## 一、"永久"存储的闪存

### 1.1 原理

Flash 掉电不丢，RAM 掉电就空。
所以想让一个值"永久"，做法是：

> **把它放进一个不会被启动代码初始化的 Flash 段。**

```c
__attribute__((section(".persistent"), used))
const cfg_t g_cfg = { 0xCAFEBABEu, 0u, 0u };
```

链接脚本里给它一个段：

```ld
.persistent : {
    _spersist = .;
    KEEP(*(.persistent*))
    . = ALIGN(4);
    _epersist = .;
} >FLASH
```

### 1.2 实测：它真的落在 Flash 里

```
$ ld.lld -T linker_persist2.ld --gc-sections -Map=persist2.map ...
$ grep -A4 persistent persist2.map
 800007c  800007c        c     4 .persistent
 800007c  800007c        0     1         _spersist = .
 800007c  800007c        c     4         persist.o:(.persistent)
 800007c  800007c        c     1                 g_cfg
 8000088  8000088        0     1         _epersist = .

$ llvm-nm persist2.elf | grep -E "persist|g_cfg"
0801fc0c R _epersist
0801fc00 R g_cfg          ← 'R' = 只读段
0801fc00 R _spersist
```

符号类型是 **`R`（read-only）** —— 确认在 Flash。
对比 `.data` 里的 `g_has_init` 是 **`D`**，`.bss` 里的 `g_tick` 是 **`B`**。

内容字节（`llvm-objdump -s -j .persistent`）：

```
 801fc00 bebafeca 00000000 00000000
         ^^^^^^^^
         0xCAFEBABE（小端）✓
```

### 1.3 ⚠ 实测坑：忘了 `const` 会静默生成"写 Flash"的指令

这是本节最值得记的一个坑。把上面的 `const` 去掉：

```c
__attribute__((section(".persistent"), used))
uint32_t g_counter = 0;        /* ⚠ 没有 const */
int main(void){ g_counter++; ... }
```

**链接器不报错，也不警告**：

```
$ ld.lld -T linker_persist2.ld ... persist_bad.o startup.o -o persist_bad.elf
$                                   ← 静默成功
```

但符号类型和段标志都变了：

```
$ llvm-nm persist_bad.elf | grep g_counter
08000088 D g_counter              ← 'D' 不是 'R'！

$ llvm-readelf -S -W persist_bad.elf | grep -i persist
  [ 3] .persistent  PROGBITS  08000088  000004  ...  WA
                                                     ^^
                                                     可写（W）！
```

地址还是 `0x08000088`（Flash），但段被标成了 **可写**。
生成的代码就真的去写它了：

```
08000010 <main>:
 8000010: movw  r0, #0x88
 8000014: movt  r0, #0x800        ; r0 = 0x08000088
 8000018: ldr   r1, [r0]
 800001a: adds  r1, #0x1
 800001c: str   r1, [r0]          ; ⚠ 往 Flash 地址写！
```

**在真机上这一句的结果**：写操作被 Flash 控制器**忽略**（值不变），
或者触发总线 fault——**取决于芯片，但一定不会像 RAM 那样工作**。

⚠ **关键认知**：`MEMORY { FLASH (rx) ... }` 里的 `(rx)` **只是给人看的提示**，
**lld 不会因为你把一个可写变量放进来就报错**。
属性检查要靠自己（或者加 `ASSERT` 检查段标志——lld 做不了，得靠约定 + code review）。

**所以规则**：

> **放 Flash 段里的东西必须 `const`。**
> 想改它，必须走 Flash 编程流程（擦页 → 编程），不能靠赋值。

### 1.4 写 Flash 不是赋值

| 操作 | RAM 变量 | Flash |
|---|---|---|
| 写 | `x = 5;`（一条 `str`） | 解锁 → 擦除整页 → 编程 → 上锁 |
| 粒度 | 字节 | **页**（F103 = 1 KiB） |
| 次数 | 无限 | **约 10 k 次**（F1 标称） |
| 时间 | 1 周期 | 毫秒级 |

[ch02](../02-ide/README.md) 实测过的这一行就是擦除粒度的直接体现：

```
Warn : Adding extra erase range, 0x08000128 .. 0x080003ff
```

——改 296 字节，代价是擦 1 KiB。

**正确用法**：

1. **读**是普通读（`const` 指针直接读，和读 RAM 一样快，不用解锁）；
2. **写**走 Flash 编程流程 + **磨损均衡**（别每次都写同一页）；
3. 频繁改写的配置**不要**放 Flash（放 RAM，关机前一次性落盘；或者用 EEPROM/FRAM）。

⚠ F103 **没有内部 EEPROM**，所以"永久存储"就是**内部 Flash 的最后一页**
（通常单独划出来当配置区）。

### 1.5 ⚠ 实测坑：把配置区固定在最后一页，会让 `.bin` 变成 130 KB

很自然的一个想法：把配置区钉在最后一页，免得固件升级时被覆盖。

```ld
.persistent 0x0801FC00 : {          /* ← 写死地址 */
    _spersist = .;
    KEEP(*(.persistent*))
    ...
} >FLASH
```

链接成功，地址也对：

```
 801fc00  801fc00        c     4 .persistent
 801fc00  801fc00        c     1                 g_cfg
```

**但是**：

```
$ llvm-objcopy -O binary persist.elf persist.bin && ls -l persist.bin
-rwxr-xr-x  1 a0000  wheel  130060 ... persist.bin
```

对照**不写死地址**（紧跟在 `.text` 后面）的版本：

```
$ llvm-objcopy -O binary persist2.elf persist2.bin && ls -l persist2.bin
-rwxr-xr-x  1 a0000  wheel     136 ... persist2.bin
```

| 布局 | `.bin` 大小 |
|---|---|
| `.persistent` 紧跟 `.text` | **136 B** |
| `.persistent` 钉在 `0x0801FC00` | **130060 B**（956 倍） |

**原因**：`objcopy -O binary` 会把**地址空洞全部填 0**。
`0x0801FC00` 处的段让输出从 `0x08000000` 一直铺到 `0x0801FC0C`：

```
0x0801FC0C = 130060  ✅ 正好等于文件大小
```

**后果**：烧写时间从毫秒级变成秒级，OTA 传输量爆掉。

**三种解法**：

| 解法 | 做法 | 适用 |
|---|---|---|
| ① 连续布局 | 不写死地址，让 `.persistent` 紧跟 `.text` | 配置区不需要独立擦除 |
| ② 分开出 bin | 主固件用 `--remove-section=.persistent`，配置单独 `--only-section` | ✅ **推荐** |
| ③ 生产时分两次烧 | 烧完固件再单独烧配置页 | 出厂标定 |

**解法②的实测**：

```
$ llvm-objcopy -O binary --only-section=.persistent multi.elf cfg.bin
$ ls -l cfg.bin
-rwxr-xr-x  1 a0000  wheel  8 ... cfg.bin      ← 只有 8 字节
```

——8 字节的配置文件，独立于固件烧写。

## 二、多配置项

### 2.1 排版：用 `SORT` 保证顺序稳定

多个配置项各用各的段名：

```c
__attribute__((section(".persistent.factory"), used)) const uint32_t g_factory_sn = 12345u;
__attribute__((section(".persistent.user"),    used)) const uint32_t g_user_baud  = 115200u;
```

链接脚本里用 **`SORT`** 收集：

```ld
.persistent : {
    _spersist = .;
    KEEP(*(SORT(.persistent.*)))     /* ← 按段名排序 */
    . = ALIGN(4);
    _epersist = .;
} >FLASH
```

**实测**：

```
 8000084  8000084        8     4 .persistent
 8000084  8000084        4     4         multi.o:(.persistent.factory)
 8000084  8000084        4     1                 g_factory_sn
 8000088  8000088        4     4         multi.o:(.persistent.user)
 8000088  8000088        4     1                 g_user_baud

$ llvm-objdump -s -j .persistent multi.elf
 8000084 39300000 00c20100
         ^^^^^^^^ ^^^^^^^^
         0x3039=12345  0x0001C200=115200   ✅
```

**为什么必须用 `SORT`**：不排序的话，段的排列顺序取决于
**链接命令行里 `.o` 的顺序**——换一次 Makefile 顺序，配置区布局就变了。
字段地址一变，老设备的配置就全错位（升级后读到垃圾）。

⚠ 更稳的做法是**别靠排序**，直接写死每个字段的地址或用**结构体**：

```c
typedef struct {
    uint32_t magic;      /* 0xCAFEBABE：判断"这段有没有被初始化过" */
    uint32_t version;    /* 布局版本号：升级配置格式时用 */
    uint32_t baud;
    uint32_t reserved;
    uint32_t crc32;      /* 校验：防半写入 / 位翻转 */
} cfg_t;
```

**四个字段各有各的用处**：

| 字段 | 作用 |
|---|---|
| `magic` | 首次上电时识别"没写过"，填默认值 |
| `version` | 固件升级改了配置布局 → 迁移或丢弃旧配置 |
| `reserved` | 预留，避免以后加字段要挪动已有字段 |
| `crc32` | 掉电写一半 → CRC 不匹配 → 用默认值，别用半截数据 |

### 2.2 运行时怎么改配置

因为 `const`，**不能赋值**。要改就得：

1. 把整页读到 RAM（`memcpy`，普通读）；
2. 改 RAM 里的副本；
3. 擦除整页；
4. 编程写回；
5. （可选）读回来校验 CRC。

⚠ **擦除会丢整页**，所以**页里如果有别的数据必须先备份**。
这也是"配置区单独占一页"的理由——**别和代码挤在一页**。

## 三、定制实例（per-device calibration）

**场景**：同一份固件，每台设备的序列号 / 传感器标定值不同。

两种做法，取舍很清楚：

| 做法 | 怎么做 | 优点 | 缺点 |
|---|---|---|---|
| **A. 编译期** | 每台设备编译一次（`-DSN=12345`） | 简单 | ❌ 一万台设备一万份 bin，没法统一发版 |
| **B. 运行期** | 固件统一，出厂时烧配置页 | ✅ 一份固件走天下 | 要写生产烧录工具 |

**B 的实现**（推荐）：

1. 链接脚本里把配置区钉在一个**固定且独立**的地址（最后一页）；
2. 固件里用 `_spersist` 符号访问它；
3. 生产线上用 `objcopy --only-section=.persistent` 抽出配置 bin，单独烧；
4. 固件启动时读 `magic`，不匹配就用默认值 + 报错。

⚠ 结合 1.5 的坑：**主固件的 `.bin` 要用 `--remove-section=.persistent` 去掉配置区**，
否则每台设备都得烧 130 KB。

```make
# 主固件（不含配置区）
llvm-objcopy -O binary --remove-section=.persistent app.elf app.bin
# 配置文件（只有 8 字节）
llvm-objcopy -O binary --only-section=.persistent  app.elf cfg.bin
```

## 四、固件升级（bootloader + app）

### 4.1 核心：app 要"知道自己被放哪了"

Bootloader 放在 `0x08000000`，app 放在后面（比如 `0x08004000`）。
**app 的链接脚本必须把 `FLASH` 的 `ORIGIN` 改掉**：

```ld
/* app 的 linker.ld */
MEMORY {
    FLASH (rx)  : ORIGIN = 0x08004000, LENGTH = 112K   /* ← 不是 0x08000000！ */
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 20K
}
```

**实测**（把 `ORIGIN` 从 `0x08000000` 改成 `0x08004000`，重新链接同一份代码）：

```
$ llvm-nm app.elf | grep -E "Reset_Handler|g_vectors"
08004000 R g_vectors
0800402a T Reset_Handler

$ llvm-objdump -s -j .isr_vector app.elf
 8004000 00500020 2b400008 29400008 29400008
```

对比原始版本：

| 符号 | 原版（0x08000000） | app 版（0x08004000） |
|---|---|---|
| `g_vectors` | `0x08000000` | **`0x08004000`** |
| `Reset_Handler`（nm） | `0x08000012` | **`0x0800402a`** |
| 向量表第 1 项字节 | `13000008` | `2b400008` = **`0x0800402b`** |

⚠ 注意向量表里是 `0x0800402b`（**奇数**，Thumb 位），
`nm` 显示 `0x0800402a`（偶数）——[11.04](11.04-重定位.md) 的老规矩，这里同样成立。

**只改一行 `ORIGIN`，整个程序的所有地址自动平移**——
这就是链接脚本的价值：**不用改一行 C 代码**。

### 4.2 Bootloader 怎么跳过去

```c
typedef void (*fn_t)(void);
uint32_t app_addr = 0x08004000;
uint32_t msp   = *(volatile uint32_t *)(app_addr + 0);   /* 第 0 项：栈顶 */
uint32_t reset = *(volatile uint32_t *)(app_addr + 4);   /* 第 1 项：复位向量 */

__set_MSP(msp);                    /* 换栈 */
((fn_t)reset)();                   /* 跳 */
```

⚠ **三个必须**：

1. **`reset` 已经是奇数**（向量表里带 Thumb 位），**不要再 `| 1`**；
2. 跳转前**关中断**（`cpsid i`）——app 会重新配 NVIC；
3. 跳转前把 **VTOR** 指到 app 的向量表（`SCB->VTOR = 0x08004000`），
   否则 app 的中断还会跳到 bootloader 的表里去。

⚠ F103 的 VTOR **只能在有 `SCB->VTOR` 的情况下改**（Cortex-M3 有，M0 没有）——
M0 要靠把向量表**复制到 RAM 起始**再重映射（另一套机制）。

### 4.3 升级流程里链接脚本要配合的三件事

| 事项 | 做法 |
|---|---|
| app 的起始地址 | `FLASH ORIGIN = 0x08004000` |
| app 的大小上限 | `LENGTH = 112K` + `ASSERT(_etext <= 0x08020000, "app 太大")` |
| 配置区不能被擦 | 配置区放在**最后一页**，升级时**只擦 app 区** |

⚠ **`ASSERT` 在这里特别有用**：把"固件太大装不下"变成**链接期错误**，
而不是烧进去才发现跑飞（[11.02](11.02-链接过程.md) 实测过 `ASSERT` 触发的样子）。

## 五、四个子节的共同套路

回过头看，这四个用法其实是**同一个套路的三步**：

```
① MEMORY 里划一块地         （配置页 / app 区）
② SECTIONS 里建一个自定义段  （.persistent / 整段平移）
③ C 里用 __attribute__((section(...))) 或 extern 符号访问它
```

差别只在"这块地放在哪、要不要写死地址、会不会进 `.bin`"。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实测是什么 |
|---|---|
| "Flash 里的变量加 `const` 就行" | ⚠ **不加 `const` 链接器也不报错**：实测段标志变 `WA`，生成 `str` 往 Flash 写。真机上写被忽略或 fault |
| "`MEMORY` 里的 `(rx)` 会阻止放可写段" | ⚠ **不会**，lld 不检查，`(rx)` 只是提示。实测无警告链接成功 |
| "把配置区钉在最后一页很自然" | ⚠ 会让 `.bin` 从 136 B 变成 **130060 B**（空洞填 0）。要 `--remove-section` 分开出 |
| "多个配置段顺序无所谓" | 顺序取决于 `.o` 命令行顺序 → 用 `SORT` 或结构体固定 |
| "改配置就是赋值" | 要走解锁→擦页→编程→上锁；粒度 1 KiB，寿命约 10 k 次 |
| "bootloader 跳转要 `\| 1`" | ❌ **不要**。向量表里已经是奇数（`2b400008`），再 `\| 1` 就变偶数地址了 |
| "app 要改代码适配地址" | 不用。只改 `ORIGIN` 一行，全程序地址自动平移（实测 `0x08000000`→`0x08004000`） |

## 代码自测

<details>
<summary>Q1：为什么放 Flash 的变量必须加 `const`？不加会怎样？</summary>

**因为不加 `const`，链接器会把它当成"要写的变量"，然后生成写 Flash 的指令——而且一声不响。**

**实测对照**：

```c
/* A：加 const */
__attribute__((section(".persistent"), used)) const cfg_t g_cfg = {...};
/* B：不加 const */
__attribute__((section(".persistent"), used)) uint32_t g_counter = 0;
```

| | A（const） | B（无 const） |
|---|---|---|
| `llvm-nm` 类型 | **`R`** `0801fc00` | **`D`** `08000088` |
| 段标志 | `A`（只读分配） | **`WA`**（**可写**） |
| 链接器反应 | 正常 | **无警告无错误** |
| 生成的代码 | `ldr`（读） | **`str r1, [r0]`**（往 `0x08000088` 写） |

B 的反汇编：

```
08000010 <main>:
 8000010: movw  r0, #0x88
 8000014: movt  r0, #0x800      ; r0 = 0x08000088（Flash 地址）
 8000018: ldr   r1, [r0]
 800001a: adds  r1, #0x1
 800001c: str   r1, [r0]        ; ⚠ 写 Flash
```

**真机上会发生什么**：Flash 控制器在**未解锁**状态下收到写请求，
F1 的行为是**写入被忽略**（值不变，也不报错）。
于是 `g_counter++` 每次读到的都是 0，永远是 1——
**一个"静默失败"的 bug，极难查**。

⚠ **最坑的一点**：`MEMORY { FLASH (rx) : ... }` 里的 `(rx)`
**只是一个注释性质的提示**。实测 lld **不会因为可写段落进 `(rx)` 区域就报错**。
真正的保护只能靠：

1. **约定**：放 Flash 的东西一律 `const`；
2. **code review / CI**：检查自定义段里的符号是不是 `R`
   （`llvm-nm xxx.elf | grep ' D '` 看有没有漏网的）；
3. **运行时**：`magic` 校验（值不对就用默认值）。

**一句话**：`const` 在这里不是"道德劝告"，
是**唯一能让编译器生成读指令而不是写指令的开关**。

<summary>Q2：把配置区固定在最后一页，为什么 `.bin` 会变成 130 KB？怎么解决？</summary>

**因为 `objcopy -O binary` 会把地址空洞全部填 0。**

**实测**：

| 链接脚本写法 | `.persistent` 的 VMA | `.bin` 大小 |
|---|---|---|
| `.persistent : { ... } >FLASH`（连续） | `0x0800007c` | **136 B** |
| `.persistent 0x0801FC00 : { ... } >FLASH`（钉死） | `0x0801fc00` | **130060 B** |

算术对得上：

```
0x0801FC0C（_epersist）= 130060  = persist.bin 的大小 ✅
```

`objcopy -O binary` 的语义是"把 `[最低地址, 最高地址]` 这个区间**按字节铺出来**"，
中间没内容的部分补 0。固件尾部到 `0x0801FC00` 之间空了 ~130 KB，全被填成 0。

**后果**：

- 烧写时间从毫秒级 → 秒级（每 1 KiB 一页，要擦 128 页）；
- OTA 传输量爆掉；
- 更糟的是这些 0 **真的会被烧进 Flash**，把中间区域全写脏。

**三种解法**：

| 解法 | 命令 | 适用 |
|---|---|---|
| ① 连续布局 | 不写死地址 | 配置不需要独立擦除（但会和代码同页，擦配置会擦代码 ⚠） |
| ② **分开出两个 bin** | 见下 | ✅ **推荐** |
| ③ 生产分两次烧 | 先固件后配置 | 出厂标定 |

**解法②的实测**：

```
$ llvm-objcopy -O binary --only-section=.persistent multi.elf cfg.bin
$ ls -l cfg.bin
-rwxr-xr-x  1 a0000  wheel  8 ... cfg.bin       ← 只有 8 字节

$ llvm-objdump -s -j .persistent multi.elf
 8000084 39300000 00c20100
         0x3039=12345   0x0001C200=115200
```

主固件那边配套：

```
$ llvm-objcopy -O binary --remove-section=.persistent app.elf app.bin
```

**推荐组合**：

```
app.bin  = 固件（--remove-section=.persistent）
cfg.bin  = 配置（--only-section=.persistent）
```

这样既能让配置区**独立占一页**（擦配置不会动代码），
又不会让固件 bin 膨胀。

⚠ **还有一点**：即使分成两个 bin，`--only-section` 抽出来的 cfg.bin
**地址信息丢失了**（binary 格式没有地址）。
烧的时候要显式指定地址：

```
openocd> flash write_image cfg.bin 0x0801FC00
```

或者用 `.hex`（Intel HEX 带地址）——`objcopy -O ihex` 保地址。
</details>

<details>
<summary>Q3：bootloader 跳到 app，链接脚本要改什么？`| 1` 还要不要加？</summary>

**链接脚本只改一行**：`FLASH` 的 `ORIGIN`。

```ld
/* app 的 linker.ld */
MEMORY {
    FLASH (rx)  : ORIGIN = 0x08004000, LENGTH = 112K    /* ← 就这一行 */
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 20K
}
```

**实测（同一份 C 代码，只改 ORIGIN）**：

| 符号 | 原版 `0x08000000` | app 版 `0x08004000` |
|---|---|---|
| `g_vectors` | `0x08000000` | **`0x08004000`** |
| `Reset_Handler`（nm） | `0x08000012` | **`0x0800402a`** |
| 向量表第 1 项字节 | `13000008` | **`2b400008`** = `0x0800402b` |

**连一行 C 代码都不用改**——所有绝对地址由链接器整体平移。
这就是"链接脚本是地址的唯一权威"的直接体现。

---

**`| 1` 要不要加？——不要。**

向量表里存的**已经是带 Thumb 位的值**：

```
 8004000 00500020 2b400008 29400008 29400008
                  ^^^^^^^^
                  = 0x0800402b   ← 奇数，已经有 Thumb 位了
```

所以直接当函数指针用就行：

```c
uint32_t app_addr = 0x08004000;
uint32_t msp   = *(volatile uint32_t *)(app_addr + 0);
uint32_t reset = *(volatile uint32_t *)(app_addr + 4);   /* 0x0800402b */

__set_MSP(msp);
SCB->VTOR = app_addr;        /* ⚠ 别忘了 */
((void(*)(void))reset)();    /* ✅ 直接用，不要 | 1 */
```

⚠ **如果手贱加了 `| 1`**：`0x0800402b | 1 = 0x0800402b`（不变，因为已经是奇数）。
但如果代码里写成 `(uint32_t)Reset_Handler_Symbol | 1` 而那个符号
**是从 `nm` 抄来的偶数地址** `0x0800402a`，那加 1 才是对的。

**判断标准只有一个**：**看内存里的字节，别看 `nm` 的输出**。

- 从**向量表内存**里读出来的 → **已经带 Thumb 位，不要再加**；
- 从 **`llvm-nm`**（llvm 会清 bit0）抄来的偶数地址 → **要 `| 1`**。

---

**跳转前必须做的三件事**：

| # | 做什么 | 为什么 |
|---|---|---|
| 1 | **`SCB->VTOR = app_addr`** | 不改的话，app 的中断还会跳到 bootloader 的向量表 |
| 2 | **关中断**（`cpsid i`） | app 会重新配 NVIC；跳转途中来一个中断 = 用半初始化的栈 |
| 3 | **`__set_MSP(msp)`** | app 有自己的栈顶（向量表第 0 项），必须用它的 |

⚠ **Cortex-M0 没有 `SCB->VTOR`**（M0 的 VTOR 是可选的，多数 M0 芯片没有）。
M0 上要重映射向量表，只能把 app 的向量表**复制到 RAM 起始**（`0x20000000`）
再配 `SYSCFG_CFGR1` 做内存重映射——**另一套完全不同的机制**。
</details>

<details>
<summary>Q4：配置区为什么要放 `magic` / `version` / `crc` 三个字段？</summary>

因为 Flash 配置区会遇到三种"数据不对"的情况，各需要一个字段来兜。

**实测的坏配置会长这样**（就是 1.2 里那个）：

```
 801fc00 bebafeca 00000000 00000000
         ^^^^^^^^ ^^^^^^^^ ^^^^^^^^
         magic=0xCAFEBABE  boot_count=0  crc=0
```

**三个字段各自防什么**：

| 字段 | 防的场景 | 不做会怎样 |
|---|---|---|
| **`magic`** | **首次上电**：Flash 是 `0xFF...FF`（擦除态）或全是垃圾 | 把 `0xFFFFFFFF` 当配置读 → 波特率 = 4 G，程序直接跑飞 |
| **`version`** | **固件升级改了配置布局**（加字段 / 改字段含义） | 新固件按新布局解释老数据 → 字段错位，读到别人的值 |
| **`crc32`** | **写一半掉电**（擦页后只写了前几个字） | magic 对、version 对，但数据是半截的 → 用半截数据跑 |

**代码长这样**：

```c
static cfg_t g_cfg_ram;                     /* RAM 里的可写副本 */

void cfg_load(void) {
    const cfg_t *p = (const cfg_t *)_spersist;   /* 链接器给的地址 */
    if (p->magic != CFG_MAGIC) { g_cfg_ram = cfg_default(); return; }   /* ① */
    if (p->version != CFG_VERSION) { g_cfg_ram = cfg_default(); return; } /* ② */
    if (crc32(p, sizeof(*p) - 4) != p->crc32) { g_cfg_ram = cfg_default(); return; } /* ③ */
    g_cfg_ram = *p;                          /* 拷到 RAM，之后都在 RAM 里改 */
}
```

**为什么读出来要拷到 RAM**：Flash 里的 `const` 不能写。
运行期改的是 RAM 副本，改完再整页写回。

⚠ **两个细节**：

1. **`crc32` 只算到 `crc32` 字段之前**（`sizeof(*p) - 4`）——
   不能把 CRC 字段本身算进去。
2. **`version` 不匹配时的策略要选**：
   - 保守：丢弃，用默认值（用户配置丢了，但不会跑飞）；
   - 友好：写迁移代码（老 version → 新 version 逐字段搬）。
   **出厂后改布局一定要有迁移逻辑**，否则老设备一升级就"恢复出厂设置"。

**还有第四个字段值得加**：`reserved`。

```c
typedef struct {
    uint32_t magic;
    uint32_t version;
    uint32_t baud;
    uint32_t reserved;      /* ← 预留 */
    uint32_t crc32;
} cfg_t;
```

加字段时**用掉 `reserved` 而不是追加到末尾**——
这样**结构体大小不变**，老配置还能通过 CRC（否则 `sizeof` 变了，CRC 一定不匹配）。
</details>
