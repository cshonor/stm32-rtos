# 11.4 重定位

> 书：第 11 章 链接器 · 11.4 重定位（原书 p154–173 区间内）
> 上一篇：[11.3 链接器定义的符号](11.3-链接器定义的符号.md) ｜ 下一篇：[11.5 映射文件](11.5-映射文件.md)
> 对应实验：map 文件 vs `llvm-nm` vs `llvm-objdump -s -j .isr_vector`（Thumb 位三方对照实测）

## 书这一节讲什么

一句话：**把 `.o` 里"还不知道最终地址"的引用，填成最终地址**。

`Reset_Handler` 在 `startup.o` 里的地址是 0（`.o` 不知道会被放到哪），
但向量表里必须填 `0x08000013`。
这个"把 0 变成 0x08000013"的过程就是重定位。

## 一、⚠ 实测：三个工具给出三个不同的地址

这是本章最能"打脸常识"的一组实测。同一个 `Reset_Handler`：

```
① map 文件（ld.lld -Map=）：
 8000010  8000010        0     1                 $t
 8000011  8000011        2     1                 Default_Handler
 8000013  8000013       58     1                 Reset_Handler
 800006d  800006d       18     1                 main

② llvm-nm -n：
08000010 00000002 T Default_Handler
08000012 00000058 T Reset_Handler
0800006c 00000018 T main

③ 向量表的原始字节（llvm-objdump -s -j .isr_vector）：
 8000000  00500020 13000008 11000008 11000008
                    ^^^^^^^^ ^^^^^^^^
                    = 0x08000013  = 0x08000011
```

| 来源 | `Reset_Handler` | 奇偶 |
|---|---|---|
| map 文件 | `0x08000013` | **奇** |
| `llvm-nm` | `0x08000012` | 偶 |
| **向量表里的实际字节** | **`0x08000013`** | **奇** |

**结论**：

- **map 文件和向量表里的是"原始符号值"**（带 Thumb 位）；
- **`llvm-nm` / `llvm-objdump -t` 显示时把 Thumb 位清掉了**（为了让你读得舒服）。

⚠ 这个差别会咬人：
你在 `nm` 里看到 `0x08000012`，去 gdb 里 `x/1xw 0x08000012` **看的是错误的地址**
（真正的代码在 `0x08000012`，但**作为函数指针**它的值是 `0x08000013`）。
反之想手工构造函数指针时，必须 `| 1`
（[ch08 8.14 Q3](../08-complex-types/8.14-函数指针与typedef.md)）。

**验证向量表第 0 项**：`00500020` 小端 = **`0x20005000`** = `_estack` ✓
（[ch03 实测](../03-embedded-system-programming/README.md) 真机读到 `msp = 0x20004f80`）。

## 二、重定位的三类

| 类型 | 例子 | 链接器做什么 |
|---|---|---|
| **绝对地址** | 向量表里的函数指针、`&g_has_init` | 直接填最终地址（+ Thumb 位） |
| **相对跳转** | `bl main`（PC 相对） | 算偏移（目标 − 当前位置） |
| **数据引用** | `ldr r0, [pc, #0x30]`（常量池） | 把常量池放在附近，填偏移 |

看实测的 `Reset_Handler` 反汇编（ch03 的）：

```
800006c: ldr r1, [pc, #0x30]   ; 从常量池取 _sidata = 0x08000084
800006e: ldr r2, [pc, #0x34]   ; 取 _sdata  = 0x20000000
8000074: ldr r4, [r1], #4      ; 从 Flash 读
8000078: str r4, [r2], #4      ; 往 RAM 写
```

`[pc, #0x30]` 是**相对 PC 的偏移**——链接器决定把常量池放哪，然后填偏移。
这就是为什么 `.o` 里这些指令的立即数是"待定"的。

## 三、ARM 的映射符号：`$t` / `$d`

map 文件里能看到这些怪符号：

```
 8000010  8000010        0     1                 $t
 8000011  8000011        2     1                 Default_Handler
 8000013  8000013       58     1                 Reset_Handler
 800009c  800009c        0     1                 $d
```

| 符号 | 含义 |
|---|---|
| **`$t`** | 从这里开始是 **Thumb 指令** |
| **`$d`** | 从这里开始是 **数据**（常量池、`litpool`） |
| `$a` | 从这里开始是 ARM 指令（32 位，Cortex-M 上没有） |

ARM ELF 用它们告诉反汇编器"这段字节是什么"——
因为 ARM/Thumb 混合时，同一串字节可以解释成指令也可以解释成数据。

**实践意义**：看反汇编时遇到 `$d` 后面跟着 `.word 0x08000084` 这类东西，
**不要当成指令**——那是常量池，是 `ldr rX, [pc, #imm]` 要读的数据。

Cortex-M 只跑 Thumb，所以你只会看到 `$t` 和 `$d`。

## 四、Thumb 位：为什么函数地址是奇数

这是重定位里最需要单独记住的一条。

Cortex-M **只执行 Thumb 指令集**（没有 ARM 状态）。硬件规定：
**跳转时目标地址的最低位为 1 表示 Thumb 代码**。

所以：

- 函数 `Reset_Handler` 的真实入口：`0x08000012`；
- 但作为**函数指针**它的值是 `0x08000013`；
- 向量表里填的是 `0x08000013`（实测字节 `13000008`）。

**ELF 层面的实现**：Thumb 函数的符号 `st_value` 就是奇数（bit0 = 1）。
链接器重定位时直接把这个值填进向量表。
`llvm-nm` 显示时**主动清掉了 bit0**，所以你看到偶数。

⚠ 这个"清掉"是 **llvm 系工具的行为**；
GNU 的 `arm-none-eabi-nm` 传统上**显示奇数**。
所以在两套工具间切换时会看到"地址差 1"——**不是 bug，是 Thumb 位**。

**什么时候会踩到**：

| 场景 | 注意 |
|---|---|
| 手写地址常量当函数指针 | 必须 `\| 1`（[ch08 8.14](../08-complex-types/8.14-函数指针与typedef.md)） |
| 在 gdb 里 `x/1xw <函数地址>` | 看清掉 Thumb 位后的地址（`nm` 给的就是） |
| 从向量表读地址做跳转（bootloader） | 表里已经是奇数，**别再 +1，也别对齐掉** |
| 地址做算术（比如算偏移） | 先 `addr & ~1u`，算完再 `\| 1` |

## 五、怎么看重定位表

```
$ llvm-readelf -r startup.o          # 看 .o 里的重定位项
$ llvm-readelf -R blink.elf          # 看最终的重定位（裸机通常为空）
```

裸机的最终 ELF 一般**没有动态重定位**（没有 loader），
所有地址在链接时就定死了——这也是"裸机是静态链接的极致"这个说法的由来。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实测是什么 |
|---|---|
| "重定位就是把 0 换成最终地址" | 对，但**函数地址还要 +1（Thumb 位）**。实测向量表填 `0x08000013`，`nm` 显示 `0x08000012` |
| "`nm` 显示的就是地址" | ⚠ llvm 系**清掉了 Thumb 位**。三个来源实测：map `0x08000013` / nm `0x08000012` / 向量表 `0x08000013` |
| "函数地址是偶数" | 真实入口是偶数，但**作为函数指针的值是奇数** |
| "反汇编里全是指令" | `$d` 后面是**常量池**（数据），不是指令 |
| "链接完还会有重定位" | 裸机的最终 ELF 一般没有（静态定死） |

## 代码自测

<details>
<summary>Q1：为什么 `llvm-nm` 和 map 文件里的地址差 1？</summary>

因为 **Thumb 位的处理方式不同**。

实测三方对照（同一个 `Reset_Handler`）：

```
map 文件：        0x08000013    ← 奇
llvm-nm：         0x08000012    ← 偶
向量表实际字节：   0x08000013    ← 奇（13000008，小端）
```

**底层事实**：

- ELF 里 Thumb 函数的 `st_value` **包含 bit0 = 1**（这是 ARM ELF 规范）；
- 链接器重定位时把这个值**原样**填进向量表 → `0x08000013`；
- `llvm-nm` / `llvm-objdump -t` **显示时清掉 bit0**，让你看到"真实入口地址" `0x08000012`。

所以：

| 用途 | 该用哪个 |
|---|---|
| 在 gdb 里看代码（`x/10i 0x08000012`） | **偶数**（nm 给的那个） |
| 构造函数指针 / 填向量表 | **奇数**（map / 让编译器自动处理） |
| 计算"这个函数多大" | 两者都行（size 字段不受影响） |

⚠ **GNU 工具的行为不同**：
`arm-none-eabi-nm` 传统上**显示奇数**（不清除 bit0）。
所以在 GNU 和 LLVM 工具链之间切换时，同一份 ELF 会看到差 1 的地址——
**这不是 bug，也不是链接错了，就是 Thumb 位的显示差异。**

**验证方法**（最可靠）：直接看向量表的字节。

```
$ llvm-objdump -s -j .isr_vector blink.elf
 8000000  00500020 13000008 11000008 11000008
```

`13000008` 小端 = `0x08000013` —— **这就是硬件真正会读到的值**。

**规则**：
**想知道"硬件会怎么用这个地址"，就看内存里的字节；
想知道"代码在哪"，就用 nm 给的地址。两者差 1 是正常的。**
</details>

<details>
<summary>Q2：`$t` 和 `$d` 是什么？为什么 map 里有一堆这种符号？</summary>

它们是 ARM ELF 的**映射符号（mapping symbol）**，用来告诉工具"从这里开始的字节是什么"。

| 符号 | 含义 |
|---|---|
| **`$t`** | 从这里开始是 **Thumb 指令** |
| **`$d`** | 从这里开始是 **数据**（常量池 / literal pool） |
| `$a` | 从这里开始是 **ARM 指令**（32 位；Cortex-M 上没有） |

**为什么需要**：ARM 有 ARM（32 位）和 Thumb（16 位）两套指令集，
同一串字节用哪套解释**结果完全不同**。
而且代码段里会混着数据（常量池）——
`ldr r0, [pc, #0x30]` 要读的那 4 个字节就躺在指令流中间。

反汇编器如果不知道"这一段是数据"，就会把常量池当成指令翻译，
输出一堆毫无意义的指令。

**实测 map 里看到的**：

```
 8000010  8000010        0     1                 $t              ← 开始是 Thumb 指令
 8000011  8000011        2     1                 Default_Handler
 8000013  8000013       58     1                 Reset_Handler
 800009c  800009c        0     1                 $d              ← 开始是数据（常量池）
```

注意 `$t` / `$d` 的 **size 是 0**——它们不是"东西"，是"标记"。

**实践意义**：

1. **看反汇编时**：遇到 `$d` 后面的 `.word 0x08000084`，
   **不要当成指令**。那是 `ldr rX, [pc, #imm]` 要读的常量。
   实测 ch03 的搬运循环里就有这种：
   ```
   800006c: ldr r1, [pc, #0x30]     ; 读常量池里的 _sidata
   ...
   $d:
   80000a0: .word 0x08000084        ; ← 这就是 _sidata
   ```

2. **Cortex-M 上只会看到 `$t` 和 `$d`**：
   因为只跑 Thumb，不会有 `$a`。
   如果看到 `$a`，说明目标配错了（编译出了 ARM 指令）。

3. **它们不占空间**：size = 0，纯粹是元数据。

**一句话**：`$t`/`$d` 是"这段字节怎么解释"的标注，
看反汇编时认得它们，就不会被常量池骗。
</details>

<details>
<summary>Q3：重定位有哪几类？裸机上哪一类最容易出问题？</summary>

三类，按出问题概率排：

| 类型 | 例子 | 链接器做什么 | 出问题概率 |
|---|---|---|---|
| **绝对地址** | 向量表里的函数指针、`&g_has_init` | 填最终地址（**+ Thumb 位**） | ⚠ **最高**（Thumb 位） |
| **相对跳转** | `bl main`（PC 相对） | 算偏移 | 低（编译器算，不会错） |
| **数据引用** | `ldr r0, [pc, #0x30]` | 把常量池放附近，填偏移 | 低 |

**绝对地址为什么最容易出问题**：

实测的向量表字节：

```
 8000000  00500020 13000008 11000008 11000008
          │        │        └─ Default_Handler = 0x08000011
          │        └─ Reset_Handler = 0x08000013
          └─ _estack = 0x20005000（这个是纯数据，没有 Thumb 位）
```

注意对比：

- **`_estack`（数据指针）= `0x20005000`，偶数**——它是栈地址，不是代码，不带 Thumb 位；
- **`Reset_Handler`（函数指针）= `0x08000013`，奇数**——它是代码，带 Thumb 位。

**同一个向量表里，两种指针的"最低位"含义不同**。
这就是最容易出错的地方：

```c
/* ❌ 手写向量表时容易写成 */
const uint32_t vectors[] = {
    (uint32_t)&_estack,          /* 0x20005000 ✅ 数据，偶数 */
    (uint32_t)Reset_Handler,     /* ✅ 编译器自动 +1 */
    (uint32_t)0x08000100,        /* ❌ 手写常量忘了 | 1 */
};
```

**相对跳转和常量池为什么安全**：
它们是编译器生成的，偏移由链接器精确计算，你插不了手。
唯一会出问题的是"跳转距离超出范围"（比如代码超过几十 KB 而用了 16 位分支），
但链接器会**报错**（`relocation out of range`），不会静默出错。

**所以结论**：
**重定位里唯一需要你操心的是"手写绝对地址"，尤其是函数指针的 Thumb 位。**
其余的交给工具链。
</details>
