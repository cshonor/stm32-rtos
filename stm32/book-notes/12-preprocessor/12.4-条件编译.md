# 12.4 条件编译

> 书：第 12 章 预处理器 · 12.4 条件编译（原书 p174–185 区间内）
> 上一篇：[12.3 代码宏](12.3-代码宏.md) ｜ 下一篇：[12.5 定义符号的位置](12.5-定义符号的位置.md)
> 对应实验：`#if` vs `#ifdef` 三态实测、头文件守卫重名实测、`#error` 板子选择实测、`NDEBUG` 对体积的影响实测

## 书这一节讲什么

一句话：**`#if` / `#ifdef` / `#elif` / `#else` / `#endif`——让一部分代码"根本不进编译器"。**

书上讲条件编译偏"调试开关"。但在嵌入式里它最大的价值是：
**一套代码适配多块板子 / 多个芯片。**

本篇把四个用法**都跑出实测**：
`#if` vs `#ifdef` 的差别、头文件守卫重名的后果、`#error` 怎么卡住误配置、
`NDEBUG` 到底能省多少 Flash。

## 一、裸机上最正经的用途：一套代码多块板子

```c
/* board.h */
#if defined(BOARD_NUCLEO_F103RB)
#  define LED_PORT         GPIOA
#  define LED_PIN          5
#  define LED_ACTIVE_HIGH  1
#  define USARTx           USART1
#  define PCLK2_HZ         8000000u        /* 上电默认 HSI */
#elif defined(BOARD_F407_DISCOVERY)
#  define LED_PORT         GPIOF
#  define LED_PIN          9
#  define LED_ACTIVE_HIGH  0               /* 低电平点亮 */
#  define USARTx           USART1
#  define PCLK2_HZ         84000000u
#else
#  error "未指定板子：请 -DBOARD_NUCLEO_F103RB 或 -DBOARD_F407_DISCOVERY"
#endif
```

配合 [12.6](12.6-命令行定义的符号.md) 的 `-D`：

```
$ clang ... -DBOARD_F407_DISCOVERY ...
```

### 1.1 实测：`#error` 会真的卡住

```
$ clang -fsyntax-only board.c          ← 忘了给 -D
board.c:6:4: error: "未指定板子：请 -DBOARD_NUCLEO_F103RB 或 -DBOARD_F407_DISCOVERY"
    6 | #  error "未指定板子：请 -DBOARD_NUCLEO_F103RB 或 -DBOARD_F407_DISCOVERY"
      |    ^
board.c:8:11: error: use of undeclared identifier 'LED_PIN'
2 errors generated.

$ clang -E -P -DBOARD_F407_DISCOVERY board.c
int pin = 9;                            ← ✅
```

⚠ **注意 `#error` 之后还会报第二个错**（`LED_PIN` 未定义）——
这是正常的：预处理器**不会停**，`#error` 只是打一条错误，后面的代码照样处理。
所以看 `#error` 的报错要**看第一条**。

**价值**：`#error` 把"忘了选板子"从
"编译出一堆莫名其妙的错"变成**一句人话**。
这是条件编译最划算的用法之一。

## 二、`#if` vs `#ifdef`：三态实测（最容易混淆的一对）

```c
#ifdef FOO
#  define A 1
#else
#  define A 0
#endif

#if FOO
#  define B 1
#else
#  define B 0
#endif
```

**实测三种情况**：

| 编译选项 | `A`（`#ifdef FOO`） | `B`（`#if FOO`） |
|---|---|---|
| 无 `-D` | `0` | `0` |
| **`-DFOO=0`** | **`1`** ⚠ | `0` |
| `-DFOO` | `1` | `1` |

```
$ clang -E -P iv.c                # 无 -D
0=0
0=0
$ clang -E -P -DFOO=0 iv.c        # ⚠ 关键
1=1                               # #ifdef：定义了就算（哪怕值是 0）
0=0                               # #if：值是 0 就是假
$ clang -E -P -DFOO iv.c
1=1
1=1
```

**规则**：

| 写法 | 判断什么 | 未定义时 |
|---|---|---|
| `#ifdef FOO` | **有没有定义过**（不看值） | 假 |
| `#if defined(FOO)` | 同上（更灵活，可组合） | 假 |
| `#if FOO` | **值是不是非 0** | 当作 **0** ⚠ |

⚠ **最坑的组合**是 `-DFOO=0` + `#ifdef FOO`：
你在命令行明确写了"关掉这个功能"（`=0`），
结果 `#ifdef` 认为它**开着**。

**本仓库的取向**：

> **功能开关一律用 `#if CONFIG_XXX`（值判断）或 `#if defined(...)`，
> 不要混用 `#ifdef`。**

```c
#if defined(BOARD_F103) && (LOG_LEVEL >= 2)     /* ✅ 可组合，语义明确 */
#ifdef BOARD_F103 && LOG_LEVEL >= 2             /* ❌ 语法错误：#ifdef 只能跟一个标识符 */
```

`#if defined()` 能写复合条件，`#ifdef` **不能**——这也是选它的理由。

## 三、用法②：头文件守卫（⚠ 实测重名会静默吞掉整个头文件）

```c
#ifndef CONFIG_H
#define CONFIG_H
/* ... 头文件内容 ... */
#endif
```

**实测：两个头文件用了同一个守卫名**

```c
/* a.h */  #ifndef CONFIG_H / #define CONFIG_H / #define FROM_A 1 / #endif
/* b.h */  #ifndef CONFIG_H / #define CONFIG_H / #define FROM_B 1 / #endif
/* main */ #include "a.h"  #include "b.h"
```

```
$ clang -E -P -I. guard.c
1=1
FROM_B=FROM_B            ← ⚠ FROM_B 没被替换！b.h 的内容被整段跳过了
```

**原因**：`a.h` 已经定义了 `CONFIG_H`，
所以 `#include "b.h"` 时守卫判断为"已包含" → **整个 b.h 被跳过**。

**真实编译时的症状**：

```
$ clang -fsyntax-only -I. guard2.c
guard2.c:3:9: error: use of undeclared identifier 'FROM_B'
    3 | int x = FROM_B;
      |         ^~~~~~
1 error generated.
```

——报错在**使用处**，而不是在头文件里，
而且**没有任何"头文件被跳过"的提示**。
表现为"明明 `#include` 了，却说没定义"，极难查。

⚠ **`CONFIG_H` 这种通用名最容易撞**。

**三条对策**：

| 对策 | 做法 | 备注 |
|---|---|---|
| ① 守卫名带路径/模块前缀 | `BOARD_CONFIG_H`、`DRV_UART_REG_H` | ✅ 简单有效 |
| ② 用 `#pragma once` | 一行，不会重名 | ⚠ 非标准（但 GCC/Clang/MSVC 全支持） |
| ③ 加 UUID 后缀 | `CONFIG_H_9F3A2B` | 有些生成器这么做 |

⚠ **`#pragma once` 的坑**：它靠**文件 inode/路径**判断，
同一个文件通过不同路径（软链接、两份拷贝）包含时**会失效**。
本仓库用**①（带前缀的守卫名）**。

## 四、用法③：日志分级（实测能省多少 Flash）

```c
#if LOG_LEVEL >= 2
#  define LOG_D(fmt, ...) printf("[D] " fmt "\n", __VA_ARGS__)
#else
#  define LOG_D(fmt, ...) ((void)0)
#endif
```

这类"发布版裁掉调试代码"的用法，省的是**真金白银的 Flash**。

**实测（Cortex-M3，`-Os`，一个 assert 的代价）**：

```c
extern void __assert_func(const char *f, int l, const char *fn, const char *e);
#ifdef NDEBUG
#  define assert(e) ((void)0)
#else
#  define assert(e) ((e) ? (void)0 : __assert_func(__FILE__, __LINE__, __func__, #e))
#endif
volatile uint32_t g;
int main(void){ g = 1; assert(g == 2); return 0; }
```

| | 无 `NDEBUG` | **`-DNDEBUG`** |
|---|---|---|
| `.text` | **86 B** | **24 B**（省 62 B） |
| 未定义符号 | `U __assert_func` | **无** |
| `.rodata` 字符串 | `"asrt4.c\0main\0g == 2\0"`（17 B） | **无** |

```
$ llvm-size asrt4.o        # 无 NDEBUG
   text	   data	    bss
     86	      0	      4
$ llvm-size asrt4.o        # -DNDEBUG
   text	   data	    bss
     24	      0	      4

$ llvm-objdump -s -j .rodata.str1.1 asrt4.o     # 无 NDEBUG
 0000 61737274 342e6300 6d61696e 0067203d  asrt4.c.main.g =
 0010 3d203200                             = 2.
```

⚠ **一个 assert 就 62 字节**。原因有三：

1. 判断分支 + 失败路径的调用代码；
2. **`.rodata` 里的三个字符串**：`__FILE__`（文件名）、`__func__`（函数名）、`#e`（表达式原文）；
3. `__FILE__` 的**完整路径**如果很长，字符串本身就几十字节。

**所以裸机上日志/断言的成本不是"代码"，主要是 `__FILE__` 字符串。**
想省 Flash 又想保留断言，可以：

```c
#define assert(e) ((e) ? (void)0 : __assert_func(__LINE__))   /* 只传行号，不传文件名 */
```

## 五、用法④：⚠ `assert` 在裸机上没有 stderr

这是书上讲不到、但裸机必踩的坑。

**PC 上**：`assert` 失败 → 打印到 stderr → `abort()`。
**裸机上**：**没有 stderr，也没有 `abort()`**。

**实测（交叉编译到 armv7m）**：

```
$ clang --target=armv7m-none-eabi ... -c asrt2.c -o asrt2.o
$ llvm-nm -u asrt2.o
         U __assert_func              ← 未定义！没人实现它

$ ld.lld -T linker.ld -e main asrt2.o -o asrt2.elf
ld.lld: error: undefined symbol: __assert_func
>>> referenced by asrt2.c
>>>               asrt2.o:(main)
```

⚠ 顺带一个**交叉编译的现实问题**：

```
$ clang --target=armv7m-none-eabi ... -c asrt.c
asrt.c:2:10: fatal error: 'assert.h' file not found
```

——**交叉目标没有配套的 libc 头文件**（本仓库只用 clang + ld.lld，没装 newlib）。
主机侧能找到 `assert.h`，交叉侧找不到。

（主机侧实测 `assert.h` 的 `assert` 会引入 `___assert_rtn`：
`llvm-nm -u asrt_host.o` → `U ___assert_rtn`。）

**裸机上的三条出路**：

| 出路 | 做法 |
|---|---|
| ① **自己实现 `__assert_func`** | 点亮 LED + 死循环 / 从 UART 打印 |
| ② **全部关掉**（`-DNDEBUG`） | 发布版常用，实测省 62 B/处 |
| ③ **用自己的宏** | `#define ASSERT(e) do{ if(!(e)) fail_blink(__LINE__); }while(0)` |

**①的参考实现**：

```c
void __assert_func(const char *f, int l, const char *fn, const char *e){
    (void)f; (void)fn;
    uart1_puts("ASSERT failed: line ");
    uart1_put_uint(l);
    uart1_puts(": ");
    uart1_puts(e);            /* 表达式原文，#e 给的 */
    gpio_led_on();
    for (;;) { __asm__ volatile("wfi"); }
}
```

⚠ **别让 assert 失败后继续跑**——
断言失败说明"不该发生的事发生了"，
继续跑只会让状态更乱。死循环 + LED 是裸机上最合适的反应。

## 六、另外两个标准用法

| 用法 | 写法 | 目的 |
|---|---|---|
| 头文件守卫 | `#ifndef X_H` / `#define X_H` / `#endif` | 防重复包含（见第三节的坑） |
| 平台适配 | `#if defined(__arm__)` / `#elif defined(__x86_64__)` | 一份代码跨架构 |

⚠ **`#if` 里能用的只有"宏"和"整型常量"**——
`const` 变量、`enum` 常量、**都进不去**（预处理器看不到它们）。
这是 [12.1](12.1-简单宏.md) Q2 讲的那条的直接后果。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实测是什么 |
|---|---|
| "`#ifdef` 和 `#if` 差不多" | ⚠ **`-DFOO=0` 时完全不同**：`#ifdef FOO` → **1**，`#if FOO` → **0** |
| "头文件守卫随手写" | ⚠ 重名会**静默吞掉整个头文件**。实测两个 `CONFIG_H` → `FROM_B=FROM_B`（未替换），报错在使用处 |
| "`#error` 会让预处理停下" | ❌ 不会。实测 `#error` 之后**继续报第二个错**（`LED_PIN` 未定义）。要看第一条 |
| "`assert` 失败会打印" | 裸机**没有 stderr**。实测交叉编译 → `U __assert_func` → **链接失败** |
| "日志宏省不了多少" | 实测一个 `assert` = **62 字节**（86 → 24），主要是 `__FILE__` 字符串 |
| "`#if` 里能写复合条件" | ✅ 但要用 `#if defined(A) && ...`；`#ifdef A && B` 是**语法错误** |

## 代码自测

<details>
<summary>Q1：`-DFOO=0` 和 `#ifdef FOO` 为什么是"开着"？</summary>

**因为 `#ifdef` 只看"有没有定义过"，不看值。**

**实测三态对照**：

```c
#ifdef FOO
#  define A 1
#else
#  define A 0
#endif
#if FOO
#  define B 1
#else
#  define B 0
#endif
```

| 编译选项 | `A`（`#ifdef FOO`） | `B`（`#if FOO`） |
|---|---|---|
| 无 `-D` | `0` | `0` |
| **`-DFOO=0`** | **`1`** ⚠ | `0` |
| `-DFOO` | `1` | `1` |

`A=1` 展开出来是 `1`，预处理器把 `A` 替换成 1，所以输出 `1=1`。

**为什么危险**：

```c
/* 你想关掉某个功能，很自然地写 */
$ clang -DFEATURE_DMA=0 ...

/* 而代码里写的是 */
#ifdef FEATURE_DMA
    dma_init();          /* ⚠ 照样被编进去！你以为关了，其实开着 */
#endif
```

——**编译成功、运行出错、且很难想到是因为 `-D` 的值被忽略了。**

**三条规则**：

**① 判断"功能开关"用 `#if`，不用 `#ifdef`**：

```c
#if FEATURE_DMA              /* ✅ 值为 0 就是关 */
```

**② 只判断"有没有定义"时才用 `#ifdef` / `#if defined()`**：

```c
#if defined(BOARD_F103)      /* ✅ 语义明确：只看有没有 */
```

**③ 复合条件只能用 `#if defined()`**：

```c
#if defined(BOARD_F103) && (LOG_LEVEL >= 2)     /* ✅ */
#ifdef BOARD_F103 && LOG_LEVEL >= 2             /* ❌ 语法错误 */
```

`#ifdef` 后面**只能跟一个标识符**，不能写表达式。

**还有一个变体值得知道**：`#if FOO` 在 `FOO` **未定义**时当作 **0**，
**不会报错**（这是 C 标准规定的）。
所以 `#if LOG_LEVEL >= 2` 在忘了 `-DLOG_LEVEL` 时**静默变成 `#if 0 >= 2`**，
日志被裁掉——**不报错，但功能没了**。

对策：配合 `#error` 强制要求定义：

```c
#ifndef LOG_LEVEL
#  error "必须定义 LOG_LEVEL（如 -DLOG_LEVEL=2）"
#endif
```
</details>

<details>
<summary>Q2：头文件守卫重名会发生什么？为什么报错位置那么奇怪？</summary>

**后包含的头文件会被整段静默跳过，报错出现在"使用处"而不是头文件里。**

**实测**：

```c
/* a.h */
#ifndef CONFIG_H
#define CONFIG_H
#define FROM_A 1
#endif

/* b.h */
#ifndef CONFIG_H      /* ⚠ 和 a.h 用了同一个名字 */
#define CONFIG_H
#define FROM_B 1
#endif

/* main.c */
#include "a.h"
#include "b.h"
int x = FROM_B;
```

```
$ clang -E -P -I. guard.c
1=1
FROM_B=FROM_B          ← ⚠ FROM_B 没被替换，说明 b.h 的内容根本没进来

$ clang -fsyntax-only -I. guard2.c
guard2.c:3:9: error: use of undeclared identifier 'FROM_B'
    3 | int x = FROM_B;
      |         ^~~~~~
1 error generated.
```

**为什么会这样**：

1. `#include "a.h"` → `CONFIG_H` 未定义 → 定义它 → 放进 `FROM_A`；
2. `#include "b.h"` → `CONFIG_H` **已定义** → `#ifndef` 为假 → **整个 b.h 被跳过**；
3. `FROM_B` 从来没被定义过；
4. 用到它的地方报"未声明标识符"。

**报错为什么在使用处**：
预处理器只是**不把 b.h 的内容插进来**，它不做任何检查。
编译器看到的 `main.c` 里就没有 `FROM_B` 这个宏，
`int x = FROM_B;` 里的 `FROM_B` 被当成**一个未声明的变量名**。

**症状总结**：**"我明明 include 了，为什么说没定义？"**
——99% 是守卫重名。

**三条对策**：

| 对策 | 做法 | 评价 |
|---|---|---|
| ① **守卫名带模块前缀** | `BOARD_CONFIG_H`、`DRV_UART_REG_H` | ✅ **本仓库用这个** |
| ② `#pragma once` | 一行搞定，不会重名 | ⚠ 非标准；靠文件路径判断，**软链接/双拷贝会失效** |
| ③ 加随机后缀 | `CONFIG_H_9F3A2B` | 代码生成器常用，手写时不必要 |

**①的命名规则**：

```
<模块或路径>_<文件名>_H
BOARD_CONFIG_H         ← board/config.h
DRV_UART_REG_H         ← drv/uart_reg.h
```

⚠ **`CONFIG_H`、`COMMON_H`、`UTIL_H`、`DEFS_H` 是重灾区**——
这些名字几乎每个项目都会有人用。

**顺带：为什么不用 `#pragma once`？**

它靠**文件身份**（inode / 规范化路径）判断，
所以这些情况会失效：

- 同一个文件通过**软链接**和**真实路径**各包含一次；
- 构建系统把头文件**复制**到两个目录；
- 某些网络文件系统上 inode 不稳定。

裸机项目通常目录结构简单，`#pragma once` 实际不会出问题；
但**守卫名是 C 标准的、行为完全可预测的**，本仓库优先用它。
</details>

<details>
<summary>Q3：`assert` 在裸机上为什么链接失败？该怎么办？</summary>

**因为 `assert` 展开后调用一个没人实现的函数，且裸机没有 stderr。**

**实测（交叉编译到 armv7m-none-eabi）**：

```c
extern void __assert_func(const char *f, int l, const char *fn, const char *e);
#define assert(e) ((e) ? (void)0 : __assert_func(__FILE__, __LINE__, __func__, #e))
int main(void){ g = 1; assert(g == 2); return 0; }
```

```
$ llvm-nm -u asrt2.o
         U __assert_func               ← 未定义符号

$ ld.lld -T linker.ld -e main asrt2.o -o asrt2.elf
ld.lld: error: undefined symbol: __assert_func
>>> referenced by asrt2.c
>>>               asrt2.o:(main)
```

**在 PC 上这不会失败**，因为 libc 提供了 `__assert_func`（Linux 上是 `__assert_fail`，
macOS 上是 `___assert_rtn`——实测主机侧 `llvm-nm -u asrt_host.o` 输出 `U ___assert_rtn`）。
**裸机上没有 libc，所以没人实现它。**

⚠ **还有一个交叉编译的现实问题**（本仓库实测）：

```
$ clang --target=armv7m-none-eabi ... -c asrt.c
asrt.c:2:10: fatal error: 'assert.h' file not found
```

——**交叉目标没有配套的 libc 头文件**。
本仓库只用 clang + ld.lld，没装 newlib，所以 `<assert.h>` / `<string.h>` 都找不到。
主机侧（有系统头文件）能找到，交叉侧不行。

**三条出路**：

**① 自己实现 `__assert_func`（推荐）**：

```c
void __assert_func(const char *f, int l, const char *fn, const char *e){
    (void)f; (void)fn;
    uart1_puts("ASSERT: line "); uart1_put_uint(l);
    uart1_puts(" expr: ");       uart1_puts(e); uart1_puts("\r\n");
    gpio_led_on();
    for (;;) __asm__ volatile("wfi");      /* 不要继续跑 */
}
```

⚠ **一定要死循环**——断言失败说明状态已经不可信，
继续跑只会产生更难查的二次故障。

**② 发布版全部关掉（`-DNDEBUG`）**：

实测省得很多：

| | 无 `NDEBUG` | `-DNDEBUG` |
|---|---|---|
| `.text` | 86 B | **24 B** |
| `.rodata` | `"asrt4.c\0main\0g == 2\0"` | 无 |
| 未定义符号 | `U __assert_func` | 无 |

**一个 assert 就 62 字节**——主要花在 `__FILE__` 字符串上。

**③ 用自己的宏**（最可控）：

```c
#define ASSERT(e) do { if (!(e)) fail_blink(__LINE__); } while (0)
```

⚠ **`do { } while(0)` 是必须的**（[12.3](12.3-代码宏.md) 提过）——
否则 `if (x) ASSERT(a); else ...` 会挂错 `else`。

**关于体积的补充说明**：

如果既想保留断言又想省 Flash，可以**不传文件名**：

```c
#define assert(e) ((e) ? (void)0 : __assert_func(__LINE__))
```

——省掉 `__FILE__` 和 `__func__` 两个字符串，
代价是失败时不知道是哪个文件的哪一行（只知道行号）。
在只有一个源文件的 lab 里这够用，在正式项目里不建议。

⚠ **`__FILE__` 通常是编译时的完整路径**，
比如 `/Users/xxx/project/src/main.c`，那就是 30+ 字节。
用 `-ffile-prefix-map=` 或 Makefile 里用相对路径能压掉这部分。
