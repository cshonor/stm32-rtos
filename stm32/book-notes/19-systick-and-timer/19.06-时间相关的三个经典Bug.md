## 书这一节讲什么

书里没有。**时间相关的 bug 有三个共同点：能编译、能链接、能跑，
只是"某些时刻"会错**——所以它们往往上线几周甚至几个月才暴露。

本节把三个经典 bug 摆在一起看，每个都给实测证据。

## 一、三大经典 Bug 一览

| Bug | 原因 | 对策 |
|---|---|---|
| **延时差 9 倍** | 以为 72 MHz 实际 8 MHz（忘了配 PLL） | 时钟配置完成后**打印/测量确认** |
| **49.7 天后失效** | `uint32_t` 毫秒计数回绕（2^32 ms ≈ 49.7 天） | 用 `(int32_t)(a-b)` 比较法（[19.03](19.03-g_ms与回绕安全的时间比较.md)） |
| **ISR 里读 millis 读到一半** | `uint64_t` 计数在 32 位机上非原子 | 用 `uint32_t` + 回绕安全比较；或读时关中断 |

前两个的实测数据已经在 [19.02](19.02-配置成1ms心跳.md) 和 [19.03](19.03-g_ms与回绕安全的时间比较.md) 给出，
本节补**第三个的实测**，再加一个"时间用对了能解决什么问题"的正例：**按键去抖**。

## 二、⭐ 实测：`uint64_t` 毫秒计数真的会读到"半新半旧"

`atomic.c` 交叉编译到 Cortex-M3（`-Os`）的反汇编：

```
read32（4 条 /  8 B）: ... ldr  r0, [r0]              ← 一条指令读完，原子
read64（4 条 /  8 B）: ... ldm  r0, {r0, r1}          ← 一次读两个寄存器
tick32（6 条 / 12 B）: ... ldr r1,[r0] ; adds r1,#1 ; str r1,[r0]
tick64（7 条 / 14 B）: ... ldrd r1, r2, [r0]
                           adds r1, #0x1
                           adc  r2, r2, #0x0
                           strd r1, r2, [r0]          ← 读-改-写，非原子
```

⚠ **`tick64` 是四条指令的读-改-写序列**。主循环若在 `ldrd` 之后、`strd` 之前
被 SysTick 打断，就拿到"低 32 位已加、高 32 位没加"的半新值。

最要命的是**进位那一瞬间**：`0x00000000_FFFFFFFF` → `0x00000001_00000000`。
读到一半就是 `0x00000000_00000000`——**时间瞬间倒退 49.7 天**。
任何"超时判据"都会立刻失效，而这类现象一年可能只出现一次。

⚠ 补充一个容易忽略的点：`read64` 在本机编成了**单条 `ldm`**，
看起来是原子的——**但这只是本次 `-Os` 下的巧合**。
`-O0` 下它是 `ldrd`（也还行），但换成别的优化级别或别的编译器就可能拆成两条 `ldr`。
**不能依赖代码生成碰巧是原子的**，要在类型层面就避免。

## 三、⭐ 实测：按键去抖——时间去对了能省掉 4 次误触发

主机侧模拟（`deb.c`，模型：`t=10..13 ms` 抖动 4 ms，`t=14..99` 稳定按下，`t=100` 松开）：

```
== ① 不去抖：直接读电平 ==
  t= 11 ms  电平 0->1  ❌ 一次按下产生多次跳变
  t= 12 ms  电平 1->0  ❌ 一次按下产生多次跳变
  t= 13 ms  电平 0->1  ❌ 一次按下产生多次跳变
  t=100 ms  电平 1->0  ❌ 一次按下产生多次跳变
  共 4 次跳变（真实应该只有 2 次：按下 + 松开）

== ② 20 ms 去抖（非阻塞判据）==
  t= 33 ms  ✅ 确认按下（已稳定 20 ms）
  t=100 ms  ✅ 确认松开
  共 2 次有效事件（真实 = 2）
```

**一次真实按键，不去抖会被识别成 4 次跳变**（按下 3 次 + 松开 1 次）。
这就是"按一下键，计数加了 3"的根源——**ch05 的按键实验迟早会遇到**。

去抖状态机用的判据仍然是 `(int32_t)(g_ms - t0) >= 20`，
**和 [19.03](19.03-g_ms与回绕安全的时间比较.md) 完全同一个写法**——
一套判据，处处能用。

⚠ **诚实标注**：以上是**主机侧模拟**（`raw_level()` 是我编的抖动模型），
**不是真机按键波形**。真实机械按键的抖动时长通常 5~20 ms、波形更乱，
但结论（不去抖会重复计数）不变。

## 四、Bug 排查顺序（时间异常时的检查清单）

```
① 时钟真的是我以为的那个频率吗？      → 差 9 倍 / 差 8 倍
② 比较时间用的是 (int32_t)(a-b) 吗？  → 49.7 天后失效
③ 计数器是 64 位吗？ISR 里在改它吗？  → 读到半新半旧
④ ISR 真的在固件里吗？                → 向量表没写 → --gc-sections 删掉（19.03）
⑤ 计时器溢出周期够长吗？              → µs 计数只有 71.58 分钟
```

⚠ 第 ④ 条是 [19.03](19.03-g_ms与回绕安全的时间比较.md) 的发现，
它比①②③都更早发生（上电就崩），但**症状容易被误判成"时钟没配好"**。

## 坑点

| 坑 | 原书怎么说 | 实际是什么（实测） |
|---|---|---|
| "`uint64_t` 毫秒更保险，不会溢出" | 书里没讲 | ❌ 实测 `tick64` 是 `ldrd/adds/adc/strd` **四条指令的非原子序列**，进位瞬间读到半值 → **时间倒退 49.7 天** |
| "`read64` 编译成一条 `ldm`，所以是原子的" | —— | ⚠ 只是**本次 `-Os` 的巧合**；不能依赖代码生成，要在**类型层面**避免 |
| "按一下键就是一次" | ch05 用忙等去抖 | ❌ 实测不去抖**一次按下产生 4 次跳变**（t=11/12/13/100） |
| "去抖要阻塞 20 ms" | —— | ⚠ 阻塞期间主循环停摆；实测的非阻塞状态机**同样得到 2 次正确事件** |
| "毫秒计数用 `uint32_t` 会溢出" | —— | ⚠ 会（**49.7 天**），但用 `(int32_t)(a-b)` 就**完全安全**（[19.03](19.03-g_ms与回绕安全的时间比较.md)） |
| "微秒也能用 `uint32_t`" | —— | ❌ 实测 **71.58 分钟**就回绕 |

## 代码自测

<details>
<summary>Q1：为什么"进位那一刻"最危险？</summary>

因为**只有那一刻，高低 32 位会同时变化**，而读到的半新值在时间轴上是"灾难性"的。

```
g_ms64 = 0x00000000_FFFFFFFF       （即将进位）
ISR 执行:  ldrd r1, r2, [r0]       ← 读到 r1=0xFFFFFFFF, r2=0x00000000
           adds r1, #1             ← r1 = 0x00000000, 产生进位
           adc  r2, r2, #0         ← r2 = 0x00000001
      ⚠ 若此刻被主循环打断：主循环读到低=0xFFFFFFFF, 高=0x00000000
           strd r1, r2, [r0]       ← 写回 0x00000001_00000000
```

主循环拿到的两种坏值：

| 打断时机 | 读到的值 | 后果 |
|---|---|---|
| `adds` 之后、`adc` 之前 | `0x00000000_FFFFFFFF`（低已加，高没加） | 比真实值**小 1**，问题不大 |
| `strd` 只写了一半 | `0x00000001_FFFFFFFF` 或 `0x00000000_00000000` | **时间倒退 / 前进 49.7 天** |

⚠ **"时间倒退"的破坏力远大于"时间快一点"**：
所有 `time_after_eq(now, deadline)` 都会瞬间变成"还没到"，
于是**所有定时任务同时停摆**，直到 49.7 天后才恢复。
表现出来就是"设备每隔很久会莫名死机一次，重启就好"。

**结论**：裸机上**就用 `uint32_t` 毫秒**（[19.03](19.03-g_ms与回绕安全的时间比较.md) 的
回绕安全比较已经解决了 49.7 天的问题）。64 位换来的是**更麻烦的原子性问题**，不划算。
</details>

<details>
<summary>Q2：真的必须用 64 位时，怎么安全地读？</summary>

三种办法，代价递增：

**① 关中断读（最直接）**

```c
uint64_t read_ms64_safe(void){
    uint32_t primask = __get_PRIMASK();
    __disable_irq();
    uint64_t v = g_ms64;
    if (!primask) __enable_irq();     /* 只在原本开着时才恢复 */
    return v;
}
```

⚠ 代价：**引入中断延迟抖动**。关中断期间所有中断都不能响应，
对于 1 kHz 心跳影响不大，但对 100 μs 级采样就是灾难。
**临界区越短越好**。

**② 双读校验（不关中断）**

```c
uint64_t read_ms64_double(void){
    uint64_t a, b;
    do { a = g_ms64; b = g_ms64; } while (a != b);
    return b;
}
```

原理：如果两次读到一致，说明中间没有发生"写了一半"。
⚠ **有活锁风险**：如果 ISR 频率极高，可能一直读不到一致值。
但 1 kHz 心跳下读两次只要几微秒，实际不会有事。

**③ 用低 32 位 + 进位标志（最巧）**

```c
volatile uint32_t g_ms_lo;        /* ISR 里加 */
volatile uint32_t g_ms_hi;        /* ISR 里只在 lo 回绕时加 */
```

让 ISR 只在低 32 位真正回绕时才动高 32 位。
主循环先读 hi、再读 lo、再读一次 hi——若两次 hi 一致就安全。
这是 Linux 内核 `jiffies_64` 在 32 位平台上的经典做法
（配合 `seqlock`）。

**推荐**：**① 或 ②，或者干脆退回 `uint32_t`**。
裸机上大部分时候，正确答案是"**用 32 位就好**"。
</details>

<details>
<summary>Q3：去抖状态机为什么要三个状态？两个够吗？</summary>

**两个不够**，因为要去抖就必然有"看到了但还没确认"这个中间态。

| 状态 | 含义 |
|---|---|
| `ST_IDLE` | 电平为 0，等待按下 |
| `ST_MAYBE` | 电平变 1 了，但**还没稳定够 20 ms**，不确定 |
| `ST_DOWN` | 已稳定 20 ms，确认按下 |

只有两个状态（`IDLE` / `DOWN`）的话，
"电平变 1"就必须**立刻**认定为按下——那就完全没去抖了。
实测里不去抖的版本就是这么错的（4 次跳变）。

⚠ **第三个状态的真正价值是"能反悔"**：

```c
case ST_MAYBE:
    if (!cur) { st = ST_IDLE; }      /* ⭐ 抖回去了，撤销 */
    else if ((int32_t)(g_ms - t0) >= 20) { st = ST_DOWN; ... }
```

抖动期间电平会来回跳，`ST_MAYBE` 让你**随时可以退回 `ST_IDLE` 重新计时**。
实测里 `t=10..13 ms` 抖了 4 ms，就是被这条撤销掉的——
所以最终 `t=33 ms` 才确认按下（`10 + 20 = 30`，加上模型里的对齐差）。

**这个三态模式是通用的**——不只是按键：

- 串口帧结束判定（收到字符 → MAYBE → 3 字符时间无数据 → 确认帧结束）
- 传感器稳定判定（读数变化 → MAYBE → 稳定 N ms → 确认新值）
- 电源稳定判定（电压越阈 → MAYBE → 稳定 → 确认掉电）

**凡是"要观察一段时间才能下结论"的逻辑，都是这个三态机。**
