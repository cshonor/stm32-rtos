# 19.3 g_ms 与回绕安全的时间比较

> 上一篇：[19.2 配置成 1 ms 心跳](19.2-配置成1ms心跳.md) ｜ 下一篇：[19.4 三种等待的对比](19.4-三种等待的对比.md)

## 书这一节讲什么

书里没有。**有了 1 ms 心跳之后，怎么用才是关键。**

核心就一句话：**不要"等"，要"问"。**
主循环每次转过来问一句"到点了吗"，而不是站着等。

而"到点了吗"这句问话有个正确写法和个错误写法，
**错误写法要连跑 49.7 天才会暴露**——这是嵌入式最经典的 bug 之一。

## 一、millis() 与"问"的写法

```c
uint32_t millis(void){ return g_ms; }              /* ISR 和主循环都读 */

/* 非阻塞延时判据（关键：不是"等"，是"问"） */
static uint32_t s_next;
void loop(void){
    if ((int32_t)(millis() - s_next) >= 0) {       /* ← 回绕安全的写法 */
        s_next = millis() + 500u;
        led_toggle();
    }
    do_other_work();                                /* 这行不会被阻塞 */
}
```

**`(int32_t)(millis() - s_next) >= 0` 是回绕安全的**，
靠的是 ch04 讲过的 unsigned 回绕。写成 `millis() >= s_next` 在 `s_next` 回绕后会错。

## 二、⭐ 实测：两种写法在回绕点上的分歧

本机跑的 `wrap` 程序（clang 23.1.0 编译后运行）实测输出：

```
== ① 正常情况（未回绕）==
  next=1000   now=990     now>=next:0   (int32)(now-next)>=0:0
  next=1000   now=1000    now>=next:1   (int32)(now-next)>=0:1
  next=1000   now=1010    now>=next:1   (int32)(now-next)>=0:1

== ② ⚠ 回绕情况（next 接近 2^32）==
  next=4294967280 now=4294967280  now>=next:1   (int32)(now-next)>=0:1   差值=0 ms
  next=4294967280 now=4294967288  now>=next:1   (int32)(now-next)>=0:1   差值=8 ms
  next=4294967280 now=0           now>=next:0   (int32)(now-next)>=0:1   差值=16 ms
  next=4294967280 now=16          now>=next:0   (int32)(now-next)>=0:1   差值=32 ms
  ⚠ now=0x00000010 时实际已过去 32 ms，但 now>=next 判为假 → 永远不触发
```

`next = 0xFFFFFFF0`、`now = 0x00000010` 时：
**实际已过 32 ms，朴素写法判"没到"，而且从此 `now` 再也追不上 `next`（除非再等 49.7 天）。**

回绕时间换算（同一程序实测打印）：

```
uint32_t 毫秒计数回绕 = 2^32 ms = 49.7 天
uint32_t 微秒计数回绕 = 2^32 us = 71.58 分钟
uint64_t 纳秒计数回绕 = 2^64 ns = 584.5 年
(int32_t) 能安全比较的最大跨度 = 2^31 ms = 24.86 天
```

⚠ 注意**微秒计数只有 71.58 分钟就回绕**——
用 `uint32_t` 存微秒，一个多小时就出事。

## 三、⭐⭐ 实测：向量表里不写 SysTick_Handler，ISR 会被整个 gc 掉

这是本次实验**最值钱的一个发现**。同样的 `app_tick2.c`，
只改向量表项数（16 项含 SysTick vs 2 项不含），`--gc-sections` 链接结果：

```
=== 向量表 16 项（第 15 项指向 SysTick_Handler）===
   text    data     bss     dec     hex
    124       0       8     132      84
--- 保留下来的符号 ---
08000050 0000002a T Reset_Handler
08000040 00000010 T SysTick_Handler     ← ✅ 在
20000004 00000004 B g_led
20000000 00000004 B g_ms
08000000 00000040 T g_vectors

=== 向量表 2 项（只有 SP + Reset_Handler）===
   text    data     bss     dec     hex
     52       0       8      60      3c
--- 保留下来的符号 ---
08000008 0000002a T Reset_Handler
20000004 00000004 B g_led
20000000 00000004 B g_ms
08000000 00000008 T g_vectors
                                       ← ❌ SysTick_Handler 消失了
```

**ISR 代码被 `--gc-sections` 当成"没人引用的死代码"删掉了。**

后果：SysTick 中断照样会触发，NVIC 按向量表取出第 15 项，
取到的是 `0`（或残留值），**PC 跳到非法地址 → HardFault**。
而 `g_ms` 的符号还在（因为主循环引用了它），
所以**链接不报错、`size` 看着也正常，只有上电跑起来才崩**。

差值拆解：`124 − 52 = 72` 字节 = 向量表扩容 `64 − 8 = 56` 字节 + ISR 本体 16 字节。

## 四、⭐ 实测：ISR 与判据各编出几条指令

```
08000040 <SysTick_Handler>:                  ← 16 字节，6 条指令
 8000040: movw r0, #0x0
 8000044: movt r0, #0x2000                   ← r0 = &g_ms
 8000048: ldr  r1, [r0]
 800004a: adds r1, #0x1
 800004c: str  r1, [r0]                      ← g_ms++
 800004e: bx   lr
```

主循环里的回绕安全判据，**被内联后只剩 2 条指令**（`Reset_Handler` 反汇编节选）：

```
 8000064: ldr  r3, [r0]                      ← now = g_ms（volatile，真的去读内存）
 8000066: subs r3, r3, r2                    ← now - next
 8000068: bmi  0x8000064                     ← 负数（还没到）就回跳继续轮询
 ...
 800006e: add.w r2, r2, #0x1f4               ← next = now + 500（0x1F4）
```

**`subs` + `bmi` 两条指令**——回绕安全判据**零额外成本**，
和普通无符号比较生成的指令数完全一样。所以"怕慢就用朴素写法"是错的：
**正确写法一分钱都不多花。**

## 坑点

| 坑 | 原书怎么说 | 实际是什么（实测） |
|---|---|---|
| "`millis() >= next` 就行了" | 书里没讲 | ❌ 实测 `next=0xFFFFFFF0, now=0x10` 时判为**假**（实际已过 32 ms）→ 永远不触发 |
| "用 `uint32_t` 存毫秒会溢出" | —— | ⚠ 会（**49.7 天**），但**只要用 `(int32_t)(a-b)` 比较就完全安全**（回绕是定义好的，ch04） |
| "微秒也能用 `uint32_t`" | —— | ❌ 实测 **71.58 分钟**就回绕，比毫秒危险 1000 倍 |
| "ISR 写了就一定在固件里" | —— | ❌⭐ **向量表 2 项时 `SysTick_Handler` 被 `--gc-sections` 整个删掉**（text 124 → 52）；链接**不报错**，上电才 HardFault |
| "回绕安全写法更费指令" | —— | ❌ 实测内联后就是 **`subs` + `bmi` 两条**，和朴素写法同价 |
| "ISR 里多做点事没关系" | —— | ⚠ 实测 ISR 本体 16 B / 6 条指令；**ISR 应该只做"加一"这种事** |

## 代码自测

<details>
<summary>Q1：为什么 `(int32_t)(a - b) >= 0` 是回绕安全的？</summary>

因为 **unsigned 减法回绕是定义良好的**（ch04 实测 `UINT_MAX+1 = 0`），
而且我们关心的量是**差值**，不是绝对值。

设 `a = millis()`、`b = next`。`a - b` 的 32 位无符号结果，
**正好等于"a 领先 b 多少"，即使 a 或 b 已经回绕过。**

用 8 位简化（回绕点 256）：

```
b = 250, a = 3        （a 已回绕过一次，实际领先 9）
a - b = 3 - 250 = -247 → 无符号回绕 → 256 - 247 = 9   ✅ 正确的"领先量"
(int8_t)9 = 9 > 0     → "到达了"      ✅

b = 250, a = 240      （a 还没到，还差 10）
a - b = 240 - 250 = -10 → 无符号回绕 → 246
(int8_t)246 = -10 < 0 → "还没到"      ✅
```

**为什么转成有符号**：把 32 位无符号差值重新解释成 `int32_t`，
正数 = 领先（到达），负数 = 落后（没到）。
只要"领先量"不超过 `INT32_MAX`（实测 **24.86 天的毫秒数**），判断就正确。

**限制**：如果 `next = millis() + 40天`，超过 24.86 天就不可靠了。
超时判据通常远小于这个量级，所以实际永远够用。
</details>

<details>
<summary>Q2：为什么 ISR 会被 --gc-sections 删掉？我明明写了它啊。</summary>

因为 `--gc-sections` 的判据是**"有没有人引用它"**，而向量表是唯一该引用它的地方。

链接器从**入口点**（`Reset_Handler`）出发做可达性分析：
`Reset_Handler` 用了 `g_ms`、`g_led`，所以这两个保留；
但**没有任何代码调用 `SysTick_Handler`**——它是被**硬件**通过向量表调用的，
链接器不知道这件事。

所以：

- **向量表 16 项**（第 15 项 = `&SysTick_Handler`）→ 向量表引用了它 → 保留 ✅
- **向量表 2 项** → 没人引用 → **整个 `.text.SysTick_Handler` section 被删** ❌

实测证据就是 text 从 **124 → 52**，符号表里 `SysTick_Handler` 凭空消失。

**为什么这么危险**：

1. 链接**不报任何错**（ISR 不是 undefined，它就是被删了）；
2. `g_ms` 还在（主循环引用了），所以 `nm` 看着"该功能齐全"；
3. `size` 还会**变小**，看起来像"优化得不错"；
4. 只有上电、SysTick 第一次触发时才 HardFault——**而且是间歇性的、难以复现的**。

**对策**（三选一，推荐第一个）：

```c
/* ① 向量表里写全（推荐）——用的是 16 项那套 */
__attribute__((section(".vectors"), used))
unsigned long g_vectors[16] = { ..., (unsigned long)SysTick_Handler };

/* ② 给 ISR 加 used 属性——保住代码，但向量表没指向它，照样进不去 */
__attribute__((used)) void SysTick_Handler(void){ g_ms++; }

/* ③ 关掉 --gc-sections——不推荐，会带上大量死代码 */
```

⚠ **注意 ② 是个陷阱**：`used` 只保证"代码不被删"，
**不保证"中断能进得来"**。中断能不能进来，完全取决于向量表里写没写。
真正要修的是向量表，不是加 `used`。
</details>

<details>
<summary>Q3：g_ms 在 ISR 里加一、在主循环里读，会不会读到"半新半旧"？</summary>

**32 位不会，64 位会。** 这是本节最容易被忽略的一条。

Cortex-M3 上 32 位对齐读写是**单条指令**，天然原子。实测反汇编：

```
read32（4 条 / 8 B）: movw r0,#0x0 ; movt r0,#0x0 ; ldr r0,[r0] ; bx lr
                                                    ↑ 一次 ldr 读完，打断不了

tick32（6 条 / 12 B）: ... ldr r1,[r0] ; adds r1,#0x1 ; str r1,[r0] ...
```

⚠ 但 **`uint64_t` 就不是原子了**。同样是实测（`-Os`）：

```
read64（4 条 / 8 B）:  ... ldm  r0, {r0, r1}        ← 一条指令读两个寄存器
tick64（7 条 / 14 B）: ... ldrd r1, r2, [r0]
                           adds r1, #0x1
                           adc  r2, r2, #0x0
                           strd r1, r2, [r0]        ← 读-改-写，非原子
```

`tick64` 是**四条指令的读-改-写序列**。如果主循环在 `ldrd` 之后、
`strd` 之前被 SysTick 打断，就会读到"低 32 位已加、高 32 位没加"的半新值。

⚠ 更要命的是**进位那一刻**：`0x00000000_FFFFFFFF` → `0x00000001_00000000`。
读到一半就是 `0x00000000_00000000`，**时间瞬间倒退 49.7 天**。

**对策**（任选）：

| 方案 | 代价 |
|---|---|
| 坚持用 `uint32_t` + 回绕安全比较（本节主线） | **零代价**，49.7 天回绕用 `(int32_t)(a-b)` 化解 |
| 读之前关中断、读完开中断 | 每次读几条指令的临界区，**会引入中断延迟抖动** |
| 拆成两个 `volatile uint32_t`（高/低）分别读 | 仍有窗口，只是小一点 |

**结论**：裸机上**就用 `uint32_t` 毫秒**，别用 64 位。
本节 Q1 的回绕安全比较已经把 49.7 天的问题解决了，
64 位带来的是**更麻烦的原子性问题**，得不偿失。
</details>
