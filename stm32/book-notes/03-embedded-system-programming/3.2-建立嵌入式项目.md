## 书这一节讲什么

书里是在 IDE（System Workbench）里点 **File → New → C Project**，选芯片型号，
向导自动生成一个能编译的空工程。这一节的价值不在"点什么按钮"，
而在**向导生成的那堆东西到底是什么**。

一句话概括本节要建立的认知：

> **嵌入式项目比 PC 项目多出来的部分，全部是"操作系统原本替你做的事"。**

## 一、向导生成的东西，翻译成文件就是三样

在 IDE 里点向导，你会看到一堆项目和一堆文件。把它们按**职责**归类，只有三样是裸机特有的：

| 文件 / 设置 | 干的事 | 在 PC 上谁提供 |
|---|---|---|
| **启动文件**（`startup_*.s` 或 `.c`） | 定义向量表；复位后把 `.data` 从 Flash 搬到 RAM、把 `.bss` 清零，然后调 `main` | **C 运行库的 `crt1.o`**（`Scrt1.o` / `crti.o` …） |
| **链接脚本**（`*.ld`） | 告诉链接器：Flash 从哪到哪、RAM 从哪到哪、哪个段放哪个地址 | **编译器内置的默认脚本**（`ld --verbose` 能看到） |
| **编译选项**（`-ffreestanding`、`-nostdlib`、`--target=...`） | 告诉编译器"别假设有 libc、没有 OS、目标架构是这个" | 不用管，默认就是 hosted + 本机架构 |

**PC 上这三样是"默认就有"，裸机上这三样是"不写就没有"。**

这也是为什么 PC 上写 C 从来不关心"栈顶在哪" —— 内核在 `execve` 的时候帮你设好了；
而裸机上，栈顶是**向量表的第 0 个字**，你不写就没人写（见 [3.3](3.3-你的第一个嵌入式程序.md)）。

## 二、我这边：不用向导，手写

本仓库的路线是 clang + ld.lld + make，没有 IDE 向导。等价的"建立项目"就是建这么几个文件：

```console
$ mkdir stm32/03-gpio-blink && cd stm32/03-gpio-blink
$ ls
main.c          # 应用：点灯
portprobe.c     # 探针程序（可选，见实验 README §5）
startup.S       # 启动文件：向量表 + Reset_Handler
linker.ld       # 链接脚本：Flash/RAM 布局
Makefile        # 构建规则
```

`startup.S` 和 `linker.ld` 是从 [`stm32/01-bare-metal`](../../01-bare-metal/README.md) 继承的
（那里已经逐行拆解过）。这里只强调**向导帮你做了什么、以及为什么你该自己写一遍**：

| 向导帮你做的 | 为什么值得自己写一遍 |
|---|---|
| 生成 `startup_stm32f103xb.s`（几百行，含全部中断向量） | 不写一遍就永远不知道"上电后前两条指令读的是哪两个地址" |
| 生成 `STM32F103RBTx_FLASH.ld`（片段式、条件很多） | 不写一遍就不知道 `.data` 的 VMA 和 LMA 为什么不同（见 [3.5](3.5-探索项目文件.md)） |
| 填好一堆编译/链接选项 | 不拆一遍就不知道哪个选项在解决哪个问题（比如 `-ffreestanding` 到底关掉了什么） |

> **不是说向导不好**——生产项目就该用向导（人不可能记住所有向量名和内存布局）。
> 但在**学的阶段**，向导的成本是"你觉得这一切都是天经地义的"。

## 三、实测：从零到能跑，最少需要什么

本仓库 `03-gpio-blink` 的完整构建过程（实测）：

```console
$ export PATH=/Users/a0000/micromamba/envs/cdev/bin:$PATH
$ make
clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb \
      -ffreestanding -fno-builtin -fno-common -Wall -Wextra -Os -g \
      -ffunction-sections -fdata-sections \
      -fno-unwind-tables -fno-asynchronous-unwind-tables \
      -c main.c -o main.o
ld.lld -T linker.ld --gc-sections -Map=blink_gpio.map -o blink_gpio.elf startup_s.o main.o
llvm-objcopy -O binary blink_gpio.elf blink_gpio.bin
```

**只有两个"自己的"输入**：`linker.ld`（地图）和 `startup.S`（起床流程）。
其余全是编译器/链接器的事。

每个编译选项在解决什么问题：

| 选项 | 解决什么 | 不加会怎样 |
|---|---|---|
| `--target=armv7m-none-eabi` | 目标是 ARMv7-M，无操作系统 | 默认编 x86，链接直接失败 |
| `-mcpu=cortex-m3 -mthumb` | 具体内核 + 只生成 Thumb 指令 | 用错内核 → 非法指令 |
| `-ffreestanding` | 声明"没有 libc/OS"，禁止把代码优化成库调用 | 编译器可能把循环优化成 `memset`，而你没有 `memset` → **链接期 undefined symbol** |
| `-fno-builtin` | 连"内建函数识别"也关掉 | 结构体赋值仍可能变成 `memcpy` 调用 |
| `-fno-common` | 关掉老 C 的"暂定定义"（多个 `.o` 里的同名言明变量会合并） | 变量定义重复时静默合并，难查 |
| `-ffunction-sections -fdata-sections` + `--gc-sections` | 没被引用的函数/数据不进 Flash | 整个库都会被拉进来 |
| `-fno-unwind-tables -fno-asynchronous-unwind-tables` | 试图去掉 `.ARM.exidx` | 每个函数多 8 字节（LLVM 上仍去不干净，链接脚本里还得 `/DISCARD/`） |

**其中最容易被忽略、也最容易咬人的是 `-ffreestanding`。**
实测对照（`stm32/01-bare-metal`）：

```console
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -Os -c 一个结构体赋值.c
$ llvm-objdump -d ...
      bl  memcpy          ← 编译器替你调了个库函数，而裸机上没有它
```

加上 `-ffreestanding -fno-builtin` 后，编译器会自己展开成 `ldr/str` 序列。

## 四、链接期会替你守着什么

裸机项目有个 PC 项目没有的好处：**内存是有限的、地址是固定的**，所以很多错误能在链接期抓到。
本仓库的 `linker.ld` 里就写了两条断言：

```ld
ASSERT(_svector == ORIGIN(FLASH), "向量表不在 Flash 首地址：硬件取不到 MSP/PC")
ASSERT(_evector - _svector >= 64, "向量表不足 16 个字：系统异常都放不下")
```

实测：**故意把链接脚本里的 `KEEP(*(.isr_vector))` 删掉**（`linker-nokeep.ld`），
`--gc-sections` 会认为向量表"没人引用"，直接把它扔掉，镜像开头变成代码指令：

```console
$ diff <(od -An -tx4 -N16 blink_asm.bin)  <(od -An -tx4 -N16 nokeep.bin)
正常版 : 20005000 08000061 080000b5 080000b5     ← 第 1 个字是栈顶
nokeep : 480e2101 6048480d 2102480d 490c4a0d     ← 变成指令了，一上电就挂
```

**这类"链接期断言"是裸机独有的保险**，PC 上你写不出这种断言——
因为 PC 上你不知道自己的代码会被加载到哪。

同一个思路的延伸（书里 11 章会正式讲）：

```c
_Static_assert(sizeof(uint32_t) == 4, "");                    /* 编译期 */
_Static_assert(offsetof(GPIO_TypeDef, BSRR) == 0x10, "");      /* 编译期：寄存器布局对不对 */
ASSERT(. <= ORIGIN(FLASH) + LENGTH(FLASH), "FLASH overflow!")  /* 链接期 */
```

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| 书 3.2：用 IDE 向导建项目 | 向导生成启动文件和链接脚本 —— **而这两样恰恰是最该自己写一遍的**。本仓库手写，`01-bare-metal` 已逐行拆过 |
| "新建工程 = 选芯片型号" | 选型号实际是在选三样东西：**编译目标**（armv7m）、**内存布局**（Flash/RAM 起始与长度）、**寄存器定义头文件**。IDE 帮你填了，但三者是独立的 |
| "`-ffreestanding` 是个细节选项" | 不加它，编译器可能把你的循环/结构体赋值变成 `memcpy`/`memset` 调用，裸机上直接**链接失败**。这是最容易踩的一个 |
| "`.o` 文件里地址都是 0，说明编译出错了" | 不是错。`.o` 里的地址是**待定的**，由链接器按链接脚本填（这叫重定位）。所以"段大小"从 `.o` 就能看，但"段地址"必须链接后才知道 |
| "项目里文件越少越好" | 裸机项目的"最少"是：**1 个启动文件 + 1 个链接脚本 + 1 个以上 `.c` + 1 个 Makefile**。少任何一个都跑不起来（除非用 IDE 的默认值，但那只是把文件藏起来了） |
| "Makefile 是构建工具的事，跟裸机无关" | 裸机 Makefile 里藏着知识：哪些选项是必须的（`-ffreestanding`）、哪些是优化（`--gc-sections`）、哪些是补救（`DISCARD .ARM.exidx`）。**看不懂 Makefile 就等于看不懂构建过程** |

## 代码自测

<details>
<summary>Q1：为什么裸机需要启动文件，PC 上却从来没见过它？</summary>

因为 PC 上有**操作系统**，裸机上没有。精确地说，是有人替你做了同一件事：

| 要做的事 | PC（Linux） | 裸机 STM32 |
|---|---|---|
| 设栈指针 | 内核在 `execve` 时设好 `rsp` | **向量表第 0 个字**，硬件在复位时装进 MSP |
| 把有初值的全局变量放到内存 | 内核按 ELF 的 `PT_LOAD` 段映射（页本来就有内容） | `Reset_Handler` 里的循环，把 Flash 里的模板拷到 RAM |
| 把无初值的全局变量清零 | 内核给新页，物理页本来就是 0 | `Reset_Handler` 里的循环 |
| 调用 `main` | `__libc_start_main` → `main` | `bl main` |
| `main` 返回后干什么 | `exit()`，回收资源 | **没有"返回"这回事**，得写死循环 |

PC 上这件事由 `crt1.o`（C runtime startup）干，它由 `gcc` 自动链接进去，
所以你从来没见过它。你可以自己看看它存在：

```console
$ gcc -v hello.c 2>&1 | tail -3
 /usr/lib/.../Scrt1.o /usr/lib/.../crti.o ... -lc ... /usr/lib/.../crtn.o
                  ↑ 这就是"启动文件"
$ objdump -d /usr/lib/x86_64-linux-gnu/Scrt1.o | head -20   # 能看到 _start
```

**所以"写启动文件"这件事，你一直都在用别人的成果，只是现在要自己写。**

</details>

<details>
<summary>Q2：`--gc-sections` 会不会把我要的东西误删？</summary>

会，而且最常被误删的就是**向量表**。理由是它的可达性分析方式：

链接器从"入口点"（`ENTRY()` 指定的符号）出发，沿调用关系标记所有可达代码/数据，
没被标记的就被丢掉。而**向量表是数据段，没有任何代码 `call` 它** ——
从链接器角度看，它就是一堆没人引用的 32 位整数。

所以必须显式保命：

```ld
KEEP(*(.isr_vector))     /* KEEP 的意思是：哪怕没人引用，也留下 */
```

同理需要 `KEEP` 的还有：

| 段/符号 | 为什么会被误删 |
|---|---|
| `.isr_vector` | 只有硬件"引用"它，链接器看不见 |
| 中断服务函数（如果只出现在向量表里） | 同上 |
| `__attribute__((section(".noinit")))` 的启动标记 | 如果还没被 main 用到 |
| 用 `asm` 或函数指针表调用的函数 | 静态分析看不到调用关系 |
| 某些初始化构造函数表（`.init_array`） | 在裸机上通常没用，但如果 RTOS 用了就要保 |

本仓库的实测：删掉 `KEEP` 后镜像开头从 `20005000`（栈顶）变成 `480e2101`（指令），
**一上电就挂**。这类错误在主机侧很难发现（编译链接都不报错），
所以要靠 `ASSERT` 断言 + 回读向量表来兜底。

</details>

<details>
<summary>Q3：`.o` 里的段地址全是 0，为什么还能看段大小？</summary>

因为**大小是确定的，位置不是**。

编译一个 `.c` 时，编译器知道你写了几个全局变量、每个多大，所以它能算出
`.text` 有 280 字节、`.bss` 有 16 字节。但它**不知道**这些东西最后会被放到哪个地址 ——
那取决于链接脚本（甚至可以链接到完全不同的地址空间）。

所以 `.o` 里每个段的 `addr = 0`，同时带着一张**重定位表**：

```console
$ llvm-readelf -r main.o          # 看重定位表
Relocation section '.rel.text.main':
  Offset    Info    Type        Sym. Value  Sym. Name
  00000010  ...     R_ARM_MOVW  00000000     RCC_APB2ENR
```

它的意思是："`.text` 的第 0x10 个字节处有个 32 位立即数，它应该等于
`RCC_APB2ENR` 的最终地址（现在还不知道）"。

链接器的工作就是：**确定每个符号的最终地址（分配）→ 把重定位表里的占位值填上（重定位）**。
`ld.lld -Map=` 生成的 map 文件，就是这次分配的全过程记录。

**实践含义**：一个符号在 `.o` 里"地址是 0"完全正常；
如果你发现链接后的 `.map` 里某个段挤出内存了，那才是真问题（链接器还会用 `ASSERT` 报错）。

</details>

<details>
<summary>Q4：Makefile 里那些选项，哪些是"必须有"，哪些是"最好有"？</summary>

分三档，判据是**不加会怎样**：

**必须有**（不加就跑不起来）：

```
--target=armv7m-none-eabi        # 不指定就编成本机架构
-mcpu=cortex-m3 -mthumb          # 内核与指令集
-ffreestanding                   # 不加会被优化成 memcpy/memset → 链接失败
-T linker.ld                     # 不指定链接脚本 → 用默认的，布局全错
```

**最好有**（不加能跑，但会白占空间 / 埋坑）：

```
-ffunction-sections -fdata-sections + --gc-sections   # 省 Flash
-ffreestanding 配套的 -fno-builtin                     # 更彻底地禁止库调用
-fno-common                                            # 避免暂定定义的静默合并
-fno-unwind-tables                                     # 省掉 .ARM.exidx
-Wall -Wextra                                          # 编译期抓 bug
-g                                                     # 调试信息（gdb 要用）
-Os                                                    # 尺寸优先（也可 -O2）
```

**看情况**：

```
-nostdlib        # 完全不要标准库。用了 --sysroot + newlib 时不能加
-fshort-enums    # 结构体里 enum 用最小宽度 —— 会影响结构体布局，要小心
-LTO             # 链接期优化，能显著减体积，但调试变难
```

**一个判断技巧**：拿这些选项做"二分删除"——删掉一个，看构建是否失败、
看 `.bin` 变大多少、看反汇编变了什么。**本仓库的 `01-bare-metal` 和 `03-gpio-blink`
都留着 `-ffreestanding` 的对照实验**，可以直接跑。

</details>

<details>
<summary>Q5：向导生成的启动文件有几百行，我手写的凭什么够用？</summary>

够用，因为**两种用途不同**：

| | 向导生成的 | 本仓库手写的 |
|---|---|---|
| 长度 | 300–600 行 | 约 200 行（含大量注释） |
| 向量表项数 | **全部**外设中断（F103 有 60 个 IRQ） | 前 16 个系统异常 + 少量外设 IRQ |
| 每个中断入口 | 都是独立的 `xxx_IRQHandler` | **弱符号统一别名到 `Default_Handler`** |
| 适合 | 产品（谁都可能给你加中断） | 学习 + 只用少数外设的小程序 |

关键在那个**弱符号别名**技巧：

```asm
.weak   NMI_Handler
.thumb_set NMI_Handler, Default_Handler     /* 没人实现就落到默认处理 */
```

这样向量表里的每一项都有名字、都能被覆盖，但**不需要每个都写实现**。
实测向量表前 24 个字里有 20 个都指向同一个地址 `0x080000B4`（`Default_Handler`）——
这就是弱符号在起作用。

代价：**未处理的中断不会报错，只会静静地跑到 `Default_Handler` 里死循环**。
所以本仓库的 `Default_Handler` 里故意写了"记录现场然后死循环"，
方便调试器抓（比直接 `b .` 友好）。

用外设中断时（比如 EXTI0），只要在 C 里定义同名函数即可覆盖：

```c
void EXTI0_IRQHandler(void) { /* 名字对上了就自动生效，不需要改启动文件 */ }
```

**这也是 §3.4 和 ch10 会反复提到的机制：启动文件提供"弱默认"，应用层提供"强实现"。**

</details>
