## 书这一节讲什么

从这一节开始，代码不再跑在你自己的电脑上，而是跑到一块**独立的板子**上。书里选的是
**NUCLEO-F030R8**（ST 的 Nucleo-64 系列，MCU 是 STM32F030R8T6，Cortex-M0）。
这一节干两件事：

1. **3.1.1 对开发板进行编程和调试** —— 认识板载的那个调试器，以及它怎么把程序送进芯片；
2. **3.1.2 配置开发板** —— 跳线、供电、按键，让它进入"可以被编程"的状态。

> 下面的正题是我的实测，不是对原书内容的复述。凡涉及"书里具体怎么写"的地方，

## 一、我手上的板子不是书里那块——差在哪

| 项 | 书：NUCLEO-F030R8 | 我：NUCLEO-F103RB | 影响 |
|---|---|---|---|
| MCU | STM32F030R8T6 | STM32F103RBT6 | 见下 |
| 内核 | **Cortex-M0**（ARMv6-M） | **Cortex-M3**（ARMv7-M） | 编译目标 `armv6m` → `armv7m`；M3 多了硬件除法、`bic`/`orr` 单指令位操作等 |
| 主频 | 48 MHz | 72 MHz（但复位后跑 **HSI 8 MHz**，没配 PLL） | 延时常数完全不同 |
| Flash / RAM | 64 KB / 8 KB | **128 KB / 20 KB** | 链接脚本 `LENGTH` 不同 |
| 封装 / 引脚数 | LQFP64 | LQFP64 | 一样 |
| GPIO 配置寄存器 | `MODER`/`OTYPER`/`OSPEEDR`/`PUPDR`，每脚 2 位 | `CRL`/`CRH`，每脚 **4 位**（CNF+MODE） | **唯一真正要改代码的地方** |
| GPIO 时钟使能 | `RCC_AHBENR` 的 IOPAEN | `RCC_APB2ENR` 的 IOPAEN (bit2) | 寄存器名 + 位号都不同 |
| 用户 LED | PA5 | PA5 | **一样，代码可直接照搬** |
| 板载调试器 | ST-Link/V2-1 | ST-Link/V2-1 | 一样 |

**结论：可以照着书学。** 差异集中在两个寄存器，其余（向量表、启动流程、链接脚本、
`BSRR` 的原子性、`.data`/`.bss` 处理）都是 ARM 内核 + C 语言层面的通用知识。

> 有意思的是：**F1 那种"一个引脚挤 4 个位"的老式布局，反而更适合作为第一块板子**——
> 它会把"读-改-写不原子"这个坑直接摆到你面前（见 [3.3.2](3.3-你的第一个嵌入式程序.md)）。

## 二、实测：怎么确认板子"活着"

在写任何代码之前，先确认调试器能连上芯片。这一步比"灯亮不亮"更早、更可信。

```console
$ export PATH=/Users/a0000/micromamba/envs/cdev/bin:$PATH
$ ~/.local/xpack-openocd-0.12.0-7/bin/openocd -f ../02-libopencm3/openocd/f103rb.cfg \
    -c "init" -c "shutdown"

Info : STLINK V2J28M18 (API v2) VID:PID 0483:374B      ← 调试器固件版本 + USB ID
Info : Target voltage: 3.239841                          ← 板上 3.3V 轨实测电压（供电正常）
Info : SWD DPIDR 0x1ba01477                              ← ★ Cortex-M 内核的"身份证"
Info : [stm32f1x.cpu] Cortex-M3 r1p1 processor detected  ← 内核型号 + 修订版
Info : [stm32f1x.cpu] target has 6 breakpoints, 4 watchpoints  ← 硬件断点/观察点数量
Info : device id = 0x20036410                            ← ★ ST 的芯片 ID
Info : flash size = 128 KiB                              ← ★ Flash 容量
```

三个星号就是"板子活着"的硬证据，它们比灯亮不亮可靠得多：

| 观测 | 值 | 它证明了什么 |
|---|---|---|
| `SWD DPIDR` | `0x1ba01477` | 内核的调试端口能应答 —— **芯片上电了、时钟在跑、SWD 线通了** |
| `device id` | `0x20036410` | 低 12 位 `0x410` = ST 的 **medium-density** 系列（F103x8/B） |
| `flash size` | `128 KiB` | 对应 **F103RB**（若是 C8 会是 64 KiB）—— 直接验证了板子型号 |

> **为什么这个顺序很重要**：灯不亮的原因有一百种（引脚配错、时钟没开、
> LED 极性搞反、跳线断开、程序根本没烧进去……）。
> 而"调试器连不上芯片"只有几种原因（没供电、SWD 断线、芯片锁死）。
> **先排除少的那种，再查多的那种**，这是嵌入式排障的第一原则。

## 三、`DPIDR` 和 `device id` 这两个数怎么读

**`0x1ba01477`（DPIDR, Debug Port ID Register）** —— 这是 ARM 定义的，不是 ST 定义的：

| 位域 | 值 | 含义 |
|---|---|---|
| `[31:24]` | `0x1b` | 修订号 |
| `[23:17]` | `0x0d` → 实际看 `[23:20]`=`0x1`, `[19:16]`=`0x0` | 不是关键 |
| `[15:12]` PARTNO | `0xba0` | JTAG-DP 还是 SW-DP（`0xBA0` = **SW-DP**） |
| `[11:1]` | | |
| `[0]` | `1` | DP 版本 |

实际用的时候不需要逐位拆 —— 记住**"能打印出 DPIDR 就是 SWD 通信成功"**就够了。
真正的用处是对比：如果换一块板子打印出别的值，说明内核变了（比如 M0+ 是 `0x0bc11477`）。

**`0x20036410`** —— 这是 ST 的 device ID（在 `DBGMCU_IDCODE` 寄存器里，地址 `0xE0042000`）：

```c
/* 你自己的程序里也能读，读到的应该和调试器报的一致 */
#define DBGMCU_IDCODE (*(volatile uint32_t *)0xE0042000u)
/* 实测本板：低 12 位 = 0x410，高 16 位 = 0x2003（修订号），整体 = 0x20036410 */
```

| DEV_ID (低 12 位) | 系列 |
|---|---|
| `0x410` | F103 medium-density（x8/xB，64/128 KB Flash） ← **本板** |
| `0x414` | F103 high-density（xC/xD/xE） |
| `0x418` | F103 connectivity line（含 CAN/ETH/USB OTG） |
| `0x440` | F030x8 / F05x |

**这个技巧值得记住**：板子上丝印模糊、或者拿到一块来源不明的板子时，
读一次 `DBGMCU_IDCODE` 就知道它到底是什么芯片 —— 比翻原理图快。

## 四、3.1.2「配置开发板」：Nucleo-64 其实不用怎么配

书里的"配置开发板"是给那些"裸芯片 + 外接调试器 + 需要跳线选供电"的学习板写的。
**Nucleo-64 这块板子把这一步几乎消灭了**，因为它板上集成了一整套：

| 板载资源 | 实测 / 说明 |
|---|---|
| ST-Link/V2-1 调试器 | 板子左半边那块 STM32F103C8（**是的，板载调试器自己也是一颗 STM32**），出厂已烧好固件 |
| 供电 | 直接用 USB，**不需要外接电源**；`Target voltage: 3.239841` 是实测值 |
| 目标电压 | 3.3 V，由调试器侧通过跳线供给 |
| 复位按键 B2 | 板上黑色小按钮（不是蓝色的 B1） |
| 用户按键 B1 | 蓝色按钮 → **PC13**（见 §5 实测） |
| 用户 LED LD2 | 绿色 → **PA5** |
| LD1 / LD3 / LD4 | 分别是 USB 通信灯 / 电源灯 / 过流灯 |
| CN2（ST morpho）/ CN5·CN6·CN7·CN8（Arduino 兼容） | 把所有引脚引出来 |
| SB 跳线（solder bridge） | 板上 0Ω 电阻式跳线，用来切断 LED/按键与引脚的连接 |

**唯一需要留意的一类"配置"**：如果你想让某个引脚做别的事，而它正好被 LED、按键或调试口占着，
就得动 SB 跳线（要动烙铁）。比如 PA13/PA14/PA15 被 SWD 占用，
想当普通 GPIO 用就必须先在软件里关闭 JTAG（见 §5 的复位值实测）。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| 书 3.1：用 NUCLEO-F030R8 | 我手上只有 F103RB。差异只有 **GPIO 配置寄存器布局**（`MODER` 2 位 vs `CRL` 4 位）和**时钟使能位号**，照学没问题；编译目标从 `armv6m` 改 `armv7m` |
| "配置开发板 = 插对跳线、选对供电" | Nucleo-64 板载 ST-Link 自带供电和烧录通道，**跳线基本不用动**。实测插上 USB 就能连 |
| "看灯亮就知道程序跑起来了" | 灯不亮的成因太多（引脚/时钟/极性/跳线/没烧进去）。**先用调试器读 `DPIDR`/`device id`**，这一步把范围缩小到"通信是否正常" |
| "板子型号看丝印" | 丝印会看不清，而且 F103 的 C8/B 封装相同、只见 Flash 大小不同。**读 `DBGMCU_IDCODE`（0xE0042000）** 最可靠 |
| "Nucleo 板就是一块 MCU" | 板上至少**两颗** MCU：目标芯片 + ST-Link 自己那颗（F103C8）。所以板子上会看到两个 USB 设备描述 |
| "PA13/PA14/PA15 是普通 GPIO" | 复位后它们被 SWD/JTAG 占用，且复位值不是标准的 `0x44444444`（实测 `GPIOA_CRH = 0x88844444`）。要用得先关 JTAG |
| "macOS 上装驱动很折腾" | 实测 macOS 免驱：`STLINK V2J28M18 ... VID:PID 0483:374B` 直接出来 |

## 代码自测

<details>
<summary>Q1：调试器报的 `Cortex-M3 r1p1` 里，"r1p1" 是什么意思？</summary>

`rXpY` = **revision X, patch Y**（修订号 r1、补丁号 p1）。

这个信息来自内核自己的识别寄存器（`CPUID`，地址 `0xE000ED00`）：
`CPUID[19:16]` 是 variant（r1 里的 1），`CPUID[3:0]` 是 revision（p1 里的 1）。

有什么用？**errata（芯片勘误）**。ARM 和 ST 都会发布"某个修订版存在某个 bug"的文档，
有些坑必须靠软件规避（比如某些早期的 M3 在特定指令序列下有异常行为）。
做产品做久了会发现：**同一个型号、不同批次的芯片，行为可能不一样**，
`r1p1` 就是区分它们的依据。

（顺带：`CPUID[15:4]` = `0xC23` 表示 Cortex-M3，`0xC24` 是 M4，`0xC20` 是 M0。
所以从 CPUID 也能反推内核型号。）

</details>

<details>
<summary>Q2：为什么板子上要放两颗 MCU？ST-Link 自己为什么用 F103C8？</summary>

因为**调试器和被调试的芯片必须是两个独立的东西**。

调试的本质是：通过 SWD 两根线（SWCLK/SWDIO）去读写目标芯片的内存和寄存器。
如果调试器就是目标芯片自己，那它得"自己调试自己"——
芯片在复位、在跑中断、在 HardFault 的时候，那份调试逻辑也会跟着一起乱。

所以需要一颗**独立的小 MCU**，它：

1. 跑一份固件，向 PC 侧伪装成 USB 设备；
2. 从 USB 收命令（"读 0x4001080C"、"在这行下个断点"）；
3. 把它翻译成 SWD 时序，打到目标芯片上。

用 F103C8 是因为它够便宜、够快（72 MHz）、Flash/RAM 够固件用、
ST 自己有大量库存。这也是为什么**板载 ST-Link 本身是可以被升级/被刷坏的**——
你刷坏了调试器，目标芯片再好也连不上（当然，还有 SWD 引脚可以外接一个调试器救回来）。

一个实践含义：**Nucleo 板上那个"USB"口坏了不代表 MCU 坏了**。
反过来也成立——MCU 锁死了，ST-Link 还是活着的（可以 `-c "stm32f1x unlock 0"` 救）。

</details>

<details>
<summary>Q3：`Target voltage: 3.239841` 有什么可看的？</summary>

它量的是**目标芯片的 VDD 轨**，不是 USB 的 5V。两个用处：

1. **确认供电正常**。如果读到 0 V 或很飘，说明目标侧没供电（跳线被拔了、
   或者板子只插了不含数据的 USB 线）——这时后面的烧录必然失败，
   但报错信息会是"No target found"，容易往"线坏了"方向查。
2. **确认没有掉压**。3.239841 而不是理想 3.300 是正常的（LDO 精度 + 负载），
   但如果掉到 2.8 V 以下，Flash 烧写可能就开始随机失败——
   **这类问题在 USB 供电不足（用了劣质线/集线器）时很典型**。

还有个数：**这个值精确到小数点后 6 位，但它不是那么可信**。它来自 ST-Link 里的 ADC，
精度有限。它的用途是"看数量级和趋势"，不是当万用表。

</details>

<details>
<summary>Q4：书里用 F030R8，如果我也买一块，是不是就能一字不差地照抄？</summary>

**代码可以照抄，但有三处必然要改**，而且都是"改了才跑得动"的：

| 处 | F030R8（书） | 说明 |
|---|---|---|
| 编译目标 | `--target=armv6m-none-eabi -mcpu=cortex-m0` | 内核变了，指令集就变了 |
| GPIO 引脚配置 | `GPIOA_MODER`，每脚 2 位 | 一行的写法不同 |
| 时钟使能 | `RCC_AHBENR` bit17 | 寄存器名 + 位号不同 |

另外两处"不改也能跑，但结论会错"：

- **主频**：F030 默认从 HSI 8 MHz 起（PLL 可到 48），F103 默认也是 HSI 8 MHz（可到 72）。
  两者**复位后都是 8 MHz**，但书里如果假设 48 MHz 来算延时常数，抄过来就不对。
- **Flash/RAM 容量**：链接脚本里的 `LENGTH` 必须按自己的板子改。

一个更省事的做法（本仓库在做）：**同一份 C 代码，用宏区分寄存器布局**，
换板子只改头文件。这也是 CMSIS 头文件（`stm32f103xb.h`）在干的事——
书里第 4 章开始会用 `<stdint.h>` 定义类型，到后面自然会走到"用统一的名字屏蔽芯片差异"。

</details>

<details>
<summary>Q5：为什么排障要"先查连不上，再查灯不亮"？</summary>

因为**两者的可能性数量差了几个数量级**。

| 症状 | 可能原因 | 数量级 |
|---|---|---|
| 调试器连不上 | 没供电 / SWD 断线 / 芯片被读保护锁死 / 时钟被配坏导致 SWD 死掉 | 几种 |
| 灯不亮 | 引脚配错、时钟没开、LED 极性反、SB 跳线断开、程序没烧进去、程序卡在 HardFault、延时太短看起来像常亮、板子型号不同…… | 十几种，且互相掩盖 |

**排障的正确姿势是"从上往下切"**：先证明最底层（硬件连接）没问题，
再往上走。每一步都用"能明确回答是/否"的证据，而不是"看起来好像"：

```
芯片上电？     ← Target voltage 有值
SWD 通？       ← 能打印 DPIDR
是什么芯片？   ← device id / flash size
程序在跑？     ← 能 halt 且 pc 在 Flash 范围里（0x08000xxx）
跑对了吗？     ← 回读检测点变量 / 向量表
最后才看现象   ← 灯
```

**本仓库所有的实测都遵循这个顺序**。这也是为什么 `make probe`
（只读、halt、回读状态）比"看灯"更重要 —— 它是那个"能明确回答是/否"的证据。

</details>
