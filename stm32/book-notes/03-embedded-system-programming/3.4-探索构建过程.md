## 书这一节讲什么

在 IDE 里点 Build，Console 面板会刷出一大段输出。大多数人会习惯性地往下滚，
看到 `Build Finished` 就关掉。书这一节要做的就是**停下来读那一段**：

- 编译了哪些源文件？（`.c` / `.S`）
- 每个源文件变成了什么？（`.o`）
- 最后合成了什么？（`.elf`，再转成 `.bin`）
- 中间那个 `.map` 是什么？

一句话：**IDE 没做什么神秘的事，它只是在替你跑命令。**

**就这么三行命令。**（`startup_s.o` 那次编译因为已经存在被 make 跳过了，

## 一条语句从源文件到 Flash 的完整路程

```
main.c ──clang -c──→ main.o ─┐
                             ├──ld.lld -T linker.ld──→ blink_gpio.elf
startup.S ─clang -c→ startup_s.o ─┘                         │
                                                            ├─llvm-objcopy─→ blink_gpio.bin ──→ Flash
                                                            ├───── -Map ──→ blink_gpio.map
                                                            └─ -fstack-usage→ main.su
```

四个产物，四种用途，**一个都不能混**：

| 产物 | 大小（实测） | 给谁用 | 能不能烧 |
|---|---|---|---|
| `main.o` | 3728 B | 链接器 | ❌ 地址全是 0，没有向量表 |
| `startup_s.o` | 3036 B | 链接器 | ❌ 同上 |
| `blink_gpio.elf` | 134856 B | **gdb**（要符号、要段表、要 DWARF） | ⚠ 能，但没人这么干 |
| `blink_gpio.bin` | **376 B** | **烧录器**（openocd `program`） | ✅ 就是最终镜像 |
| `blink_gpio.map` | 5687 B | 你（查"这个符号放哪了"） | —— 纯文本报告 |
| `main.su` | 1 行 | 你（查栈用量） | —— 纯文本报告 |

> **`.elf` 13 万字节，真正烧进去的只有 376 字节**——这个对比第一次看到会有点意外。
> 多出来的全是**调试信息（DWARF）和符号表**，它们**不会**进 Flash
> （`llvm-objcopy -O binary` 只搬 `PROGBITS` 段的内容）。
> 这也是为什么"烧录用 `.bin`、调试用 `.elf`"——两个文件根本是给两拨人看的。

## 三个优化等级，`.text` 差多少（实测）

同一个 `main.c`，只改优化级别：

| 优化 | `.text` 大小 | 相对 `-O0` |
|---|---|---|
| `-O0` | **198 字节** | 基准 |
| `-Os`（本实验用） | **190 字节** | −8 字节（−4%） |
| `-O2` | **190 字节** | −8 字节（−4%） |

**这个结果反直觉**：很多人以为 `-O0` 编出来的代码会大好几倍。这里只差 4%。

原因：**这个程序太小了**，一共就几十条语句，绝大部分"体积"来自
- 寄存器地址的构造（`movw` + `movt` 两条固定开销）
- 向量表本身（96 字节，优化无关）
- `.ARM.attributes` 之类的元数据

> 所以"优化等级能省多少 Flash"**必须按真实工程去量**，不能拿玩具程序的比例外推。
> 等你有一份几千行的工程，`-O0 → -Os` 差 30%~50% 都很正常。
> `-ffunction-sections -fdata-sections` + `--gc-sections` 的收益同理：小工程里接近 0，
> 大工程里能砍掉一堆没人调用的库函数。

## 每个 `.o` 里的地址都是 0 —— 重定位的起点

这是[第 1 章 1.5](../01-hello-world/1.5-编译器在幕后的工作方式.md)实测过的结论，这里再点一次，
因为它是"为什么必须有链接器"的核心答案：

```console
$ llvm-readelf -S main.o
  [ 1] .text    PROGBITS  00000000 000040 0000xx     ← 地址是 0
  ...
```

因为编译器**不知道**这份代码最终会放在 Flash 的哪里：

- 编译 `main.c` 的时候，编译器甚至不知道会跟谁一起链接；
- `main()` 里调的 `delay()` 在哪？**不知道**（可能在另一个 `.o` 里）；
- 所以 `.o` 里留下的是**占位**：一个"待填"的符号引用。

链接器做的事就是把这些占位全部填成真地址 —— **这就是重定位（relocation）**。
书在第 11 章专门讲它，这里先记住"**`.o` 里的地址不是最终地址**"。

## 链接器顺手做的三件事

```console
$ make symbols | head -8
08000000 R _svector            ← 向量表起点（linker.ld 定义的符号）
08000000 R g_vectors
08000060 T Reset_Handler       ← 启动代码（startup.S 提供）
08000060 R _evector            ← 向量表终点 = .isr_vector 长度 0x60 = 96 字节 ✅
080000b4 W BusFault_Handler    ← 全是弱符号，全指向同一个地址……
080000b4 W DebugMon_Handler
080000b4 T Default_Handler     ← ……就是 Default_Handler
080000b8 T main                ← 我们的 main（main.o 提供）
```

三件事：

1. **分配地址**：把 `.isr_vector` 放在 `0x08000000`（Flash 首地址）——
   因为 Cortex-M 复位时硬件**固定从那里取** MSP 和 Reset_Handler。
2. **解析符号**：`main` 在 `main.o` 里，`Reset_Handler` 在 `startup_s.o` 里，
   链接器把它们拉进同一个地址空间。
3. **填占位**：`Reset_Handler` 里那句 `bl main` 的目标地址，就是这里定下来的 `0x080000b8`。

**副产品一个很好用的技巧**：`_evector - _svector = 0x60 = 96`，
正好等于 `llvm-size` 报的 `.isr_vector` 大小 96。
**两个独立来源对上了 —— 这就是交叉验证。**

另外注意 `0x080000b4` 那一堆 `W`（weak）：**向量表里所有没实现的中断，
都指向同一个 `Default_Handler`**。它们的大小是 0 —— 链接器把它们**合并**了，
不占额外空间。（ch10 会看到"怎么把某个 IRQ 从 `Default_Handler` 换掉"。）

## 栈用量也能在构建阶段量出来（`-fstack-usage`）

裸机**没有守卫页**（不像 Linux 有 4KB guard page），栈溢出了不会报 `SIGSEGV`，
而是**悄悄踩掉旁边的变量**。所以栈用量必须自己量。

```console
$ make check-stack
main.c:68:main	8	static
```

读法：`main` 函数**静态栈用量 8 字节**。

为什么只有 8 字节？因为 `-Os` 下：

- `main` 里没有数组、没有大的局部变量；
- 只有保存的 `r4`/`r5`/`lr` 那几个寄存器（编译器为了用 callee-saved 寄存器压栈）；
- `delay` 被内联了，它自己那部分也算进来了。

> **`static`** 这个词表示"编译期就能算出来的固定用量"。
> 如果用了 VLA（变长数组）或 `alloca`，这里会写 `dynamic`，那就只能靠人工估了。
> 好的做法是**把每个函数的栈用量加起来**，和 RAM 里给栈留的空间比 ——
> 本板 20K RAM，栈从 `0x20005000` 往下长，实测 MSP 在 `0x20004ff8`（用了 8 字节，对得上）。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实测是什么 |
|---|---|
| "IDE 帮你构建，你不用管细节" | 构建就是**三行命令**（compile × N、link、objcopy）。IDE 只是替你敲，顺便把参数拉长 |
| "编译出来的可执行文件就是要烧的文件" | `.elf` 134856 B、`.bin` **376 B**。多出的全是 DWARF + 符号表，**不进 Flash** |
| "优化等级越高代码越小" | 玩具程序上 `-O0` 198 → `-Os` 190，**只差 4%**。比例必须按真实工程量，不能外推 |
| "`.o` 里已经有地址了" | `.o` 里起始地址是 **0**，全是占位。地址是链接器分配的（这就是重定位） |
| "构建就是把源码合起来" | 链接器还顺手干了三件事：分配地址、解析符号、填占位。而且还**合并**了未实现的中断处理函数（全是弱符号，都指向 `Default_Handler`） |
| "栈溢出会崩" | 裸机没有守卫页，**溢出就静默踩内存**。只能靠 `-fstack-usage` + 人工加总 |
| "改了头文件不用重编，反正头文件不产生代码" | `make` 的依赖里**没有加头文件**（本目录 Makefile 就是简化版）。写工程必须上 `-MMD -MP` 自动依赖，否则你改了 `.h` 而 make 不重编 —— 症状是"改了没生效"，极难查 |
| "构建产物都该提交进 git" | `.o`/`.elf`/`.bin`/`.map`/`.su` **全是产物**，不进 git。`.gitignore` 里要写死（见 [3.5](3.5-探索项目文件.md)） |

## 代码自测

<details>
<summary>Q1：为什么 `.elf` 十三万字节，`.bin` 只有 376 字节？</summary>

因为 **`.bin` 不是"更小的 `.elf`"，而是"要被写进 Flash 的字节流"**。

`llvm-objcopy -O binary` 的语义是：把 ELF 里**所有 `PROGBITS` 类型的段按地址排序，
中间空洞用 0 填满，拼成一条连续的字节流**。

`.elf` 里那些"多出来"的东西分成几类，**没有一类属于"要写进 Flash 的内容"**：

| 内容 | 在 ELF 里的形式 | 会进 `.bin` 吗 |
|---|---|---|
| 机器码 `.text` | `PROGBITS`，有内容 | ✅ |
| 向量表 `.isr_vector` | `PROGBITS`，有内容 | ✅ |
| `.data` 初值 | `PROGBITS`（本次 0 字节） | ✅（有的话） |
| `.bss` / `.noinit` | **`NOBITS`** —— 只有地址范围，没有内容 | ❌ |
| 符号表 `.symtab` | 非分配段（无地址） | ❌ |
| 调试信息 `.debug_*` | 非分配段 | ❌ |
| 段/节名字符串表 | 非分配段 | ❌ |

**逐条算一遍**（实测）：

```
.isr_vector(96) + .text(280) + .data(0) = 376  ← 与 blink_gpio.bin 完全一致 ✅
```

`.debug_*` 是 `-g` 带来的，**十多万字节全在这里**。`-g` 不写进芯片，
但它是"能把 gdb 定到 `main.c:38`"的唯一原因（[3.6](3.6-调试应用程序.md)）。

**所以永远别用 `.elf` 的大小判断"程序占多少 Flash"，用 `.bin` 或 `llvm-size`。**

</details>

<details>
<summary>Q2：为什么小程序的 `-O0` 和 `-Os` 只差 4%？</summary>

因为**固定开销压倒了优化收益**。

一份 Cortex-M 程序的最小体积由这些东西构成，它们**与优化等级无关**：

- **向量表**：96 字节（本实验 4 个字的实际内容 + 一堆 `Default_Handler` 别名）
- **启动代码**：搬 `.data`、清 `.bss`、`bl main` —— 十几条指令，没法再省
- **地址构造**：STM32 的外设在 `0x4001xxxx` 这种地址，一条 `movw` 装不下，
  必须 `movw` + `movt` 两条。这个开销**每条外设访问都要付**
- **`.ARM.attributes`**：37 字节元数据

`-O0` 到 `-Os` 能省的是"多余的寄存器搬来搬去、多余的分支"。
本实验里 `main` 一共就那么几条语句，`-O0` 下也没多少冗余可省。

**实践含义**：

| 场景 | 该怎么做 |
|---|---|
| 学习 / 调试阶段 | 用 `-O0` 或 `-Og`，**因为优化会打乱单步的顺序**（[3.7](3.7-逐步执行程序.md)会实测这个坑） |
| 发布 / 体积紧张 | `-Os` + `-ffunction-sections -fdata-sections` + `--gc-sections` |
| 想量化收益 | **必须拿自己的工程量**，别信任何"能省 XX%"的通用说法 |

顺带一个常被忽略的点：**优化等级会影响 `volatile` 之外的一切**。
本实验的 `delay()` 用了 `volatile` 参数才活下来，
换成 `-O0` 反而不需要它 —— **"能跑"不等于"写对了"**，
只有 `-Os`/`-O2` 下还能跑的代码才算过。

</details>

<details>
<summary>Q3：构建产物里哪些该进 git？</summary>

一条判据：**能不能由源文件重新生成**。

| 文件 | 进 git？ | 理由 |
|---|---|---|
| `main.c` / `portprobe.c` / `startup.S` / `linker.ld` / `Makefile` | ✅ 必须 | 源 |
| `README.md` | ✅ 必须 | 实测记录（是本仓库的核心价值） |
| `*.o` | ❌ | 编译产物 |
| `*.elf` | ❌ | 链接产物，且 **134 KB / 每次改动都变** |
| `*.bin` | ❌ | 产物（但**发布固件时例外**：要归档 Release 的 `.bin` + 校验和） |
| `*.map` | ❌ | 产物。但**做体积审计时值得临时留一份** |
| `*.su` | ❌ | 产物 |
| `.vscode/launch.json` | ⚠ 看情况 | **不是产物**，是调试配置，团队共享有价值。本仓库当前忽略了它（因为里面带 `$HOME` 绝对路径）—— 推荐改用 `${env:HOME}` 后提交，见 [3.5](3.5-探索项目文件.md) |
| `.vscode/*` 里的 `compile_commands.json` | ❌ | 产物（由 `-MJ` 或 `bear` 生成） |

`--gc-sections` 那条还有个陷阱：**`.map` 是产物，但它是唯一能回答
"为什么这个函数没进 Flash"的文件**。所以体积优化期间，
建议把 `.map` 一起提交，改完再撤。

本仓库的做法：`stm32/` 下的每个实验目录**只提交源 + Makefile + README**，
`.gitignore` 统一在根：`*.o *.elf *.bin *.map *.su`。

</details>

<details>
<summary>Q4：为什么 `make` 第一次跑和第二次跑的输出不一样？</summary>

第一次会看到**两条编译命令**（`startup.S` + `main.c`），第二次只看到一条。这是 make
的**增量构建**在起作用：它按"文件修改时间"判断目标是否比依赖旧，旧的就跳过。

```console
# 第一次
clang ... -c startup.S -o startup_s.o
clang ... -c main.c    -o main.o
ld.lld -T linker.ld ... -o blink_gpio.elf

# 第二次（什么都没改）
make: Nothing to be done for 'all'.
```

**好处**：大工程改一个文件不用全编。
**代价**：**依赖关系必须写对，否则会出现"改了不重编"**。

本目录 Makefile 的 `.o` 依赖只有 `.c`，**没有头文件**：

```make
%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@
```

现在 `main.c` 没有自己的 `.h` 所以没事。一旦你拆出 `gpio.h`，
改了它 make **不会重编** —— 你会看到"新代码没生效"，然后开始怀疑工具链。

**正确做法**（工程必做）：

```make
CFLAGS += -MMD -MP          # 生成 .d 依赖文件
-include $(OBJS:.o=.d)      # 让 make 读进来
```

`-MMD` 让 clang 在编译时顺手写一份"这个 `.o` 依赖哪些头文件"，
make 读了它就能正确判断。**这是从玩具 Makefile 到工程 Makefile 的分水岭。**

</details>

<details>
<summary>Q5：`make` 报 "Nothing to be done"，但我明明改了 `linker.ld`？</summary>

先看本目录的依赖写得对不对 —— **`linker.ld` 是写进依赖里的**：

```make
$(TARGET).elf: startup_s.o main.o linker.ld
	$(LD) $(LDFLAGS) -Map=$(TARGET).map -o $@ startup_s.o main.o
```

这样改 `linker.ld` 会触发重链接。**但很多教程的 Makefile 漏了这一项**：

```make
$(TARGET).elf: $(OBJS)                 # ❌ 少了 linker.ld
	$(LD) $(LDFLAGS) -T linker.ld -o $@ $(OBJS)
```

症状就是"我改了链接脚本，Flash 布局没变"。

**排查三步**：

```console
$ make -d | grep -i linker.ld          # 看 make 是怎么判断这个依赖的
$ touch *.c && make                    # 强制全编一次，看是不是时间戳问题
$ make -B                              # 无条件重编所有目标（忽略时间戳）
```

`make -B` 是这类问题的**通用杀手锏**：先把"时间戳/依赖"这个变量排除掉，
如果 `-B` 之后正常了，那问题 100% 在依赖声明，不在工具链。

**顺带**：这也是为什么"把产物提交进 git"会埋雷 —— git checkout 出来的文件
时间戳全是 `checkout` 那一刻，make 的增量判断会完全失效（全都要重编，
或者更糟：在错误的时机认为"不用编"）。

</details>
