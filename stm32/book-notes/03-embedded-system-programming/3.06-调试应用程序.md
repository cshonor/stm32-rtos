> 书里是"点 Debug 按钮"。本篇讲它背后是**两个进程**：
> `openocd`（GDB server）+ `arm-none-eabi-gdb`（客户端）——**分清楚这两个，调试就不神秘了。**

## 书这一节讲什么

书在 IDE 里点的那颗 **Debug 按钮**（不是 Run），干了四件事：

1. 把程序烧进 Flash；
2. 启动一个"调试服务"，通过 ST-Link 和芯片说话；
3. 启动一个调试器客户端，连上那个服务；
4. 让芯片停在**第一条语句**，把 IDE 切到 Debug 透视图。

在 IDE 里这四步是一瞬间的事，所以"调试"看起来像个整体。**但它其实是四个独立环节**，
拆开之后你会发现：**每一环你都能自己跑，而且能更细地控制。**

## 我们的等价物：两个终端

```console
# 终端 A —— 调试服务（它同时是烧录器和 GDB server）
$ ~/.local/xpack-openocd-0.12.0-7/bin/openocd -f ../02-libopencm3/openocd/f103rb.cfg
...
Info : stm32f1x.cpu: hardware has 6 breakpoints, 4 watchpoints      ← ★ 记住这个数字
Info : starting gdb server for stm32f1x.cpu on 3333
Info : Listening on port 3333 for gdb connections

# 终端 B —— 调试客户端
$ ~/.local/arm-gnu-toolchain-14.2.rel1-darwin-arm64-arm-none-eabi/bin/arm-none-eabi-gdb blink_gpio.elf
(gdb) target remote localhost:3333
(gdb) monitor reset halt
(gdb) break main
(gdb) continue
```

**`monitor` 开头的是"给 openocd 的话"，不是给 gdb 的。** 这是最容易混的一点：

| 命令 | 谁执行 | 例子 |
|---|---|---|
| `break` / `next` / `print` / `x` | **gdb**（在 gdb 这边处理） | `break main` |
| `monitor xxx` | **openocd**（转发给调试服务） | `monitor reset halt`、`monitor flash info 0` |

gdb 通过 `qRcmd` 包把 `monitor` 后面的东西转发给 openocd，openocd 执行完再把输出回传。
**所以 `monitor` 能看到的东西比 gdb 多**（Flash 信息、时钟状态、ST-Link 版本都在那边）。

## 实测：连接的那一瞬间，芯片在哪？

`target remote` 一建立连接，gdb 就会**先让芯片停下来**，然后报告它停在哪：

```console
$ arm-none-eabi-gdb -batch blink_gpio.elf -ex "target remote localhost:3333" ...
0x08000156 in delay (n=41648) at main.c:64
64	        __asm__ volatile("nop");
[stm32f1x.cpu] halted due to debug-request, current mode: Thread
xPSR: 0x01000000 pc: 0x08000060 msp: 0x20005000
```

两行信息，来源不同：

| 行 | 谁说的 | 含义 |
|---|---|---|
| `0x08000156 in delay (n=41648) at main.c:64` | **gdb** | 用 DWARF 把 PC 翻译成"源码第 64 行，参数 n=41648" |
| `[stm32f1x.cpu] halted due to debug-request...` | **openocd** | 芯片被调试请求停住，并报出它自己的 PC/MSP |

**"调试器能连上一个正在运行的程序，并告诉你它跑到哪了"**——这件事在 PC 上也成立，
但嵌入式有个额外好处：**SWD 是硬件层面的访问，即使程序跑飞、HardFault、
甚至把时钟配错导致 CPU 卡死，调试器照样能连上去**。这是"排障逃逸舱"。

## 实测：断点命中与「硬件断点」

```console
(gdb) break main
Breakpoint 1 at 0x80000ba: file main.c, line 70.
Note: automatically using hardware breakpoints for read-only addresses.

(gdb) continue
Breakpoint 1, main () at main.c:70
70	    boot_stage = 1;
```

三行输出，三个知识点：

**① `0x80000ba` 是 `main.c:70` 对应的机器码地址。**
这个"行号 → 地址"的映射**来自 DWARF 调试信息**（[3.05](3.05-探索项目文件.md) 里
让 `.elf` 膨胀到 13 万字节的元凶）。**这就是 `-g` 的意义**：
不加 `-g`，`.elf` 会小很多，但 gdb 只能给你地址，不能给你源码行。

**② `Note: automatically using hardware breakpoints for read-only addresses.`**
这句提示**极其重要**，也是嵌入式调试和 PC 调试最大的差异之一：

| | PC（Linux / macOS） | 裸机（Flash 上的程序） |
|---|---|---|
| 断点怎么实现 | **软件断点**：把目标指令的首字节改成 `int3`/`brk` | ❌ **做不到**——Flash **不可写** |
| 用什么 | 改内存 | **硬件断点**（CPU 内的地址比较器） |
| 数量 | 不限 | **有限**：`hardware has 6 breakpoints, 4 watchpoints` |

openocd 在启动时就把这个数字报出来了（见上面终端 A 的 `Info` 行）。
**6 个**——Cortex-M3 的 FPB（Flash Patch and Breakpoint）单元就这么多。
所以**裸机调试不能像 PC 那样随便打 20 个断点**，超过 6 个就会
`Cannot insert breakpoint` 或者悄悄改成"单步 + 判断"（极慢）。

**③ 断点停在 `boot_stage = 1;` 这一行，是"还没执行"。**
gdb 的语义：停在某行 = 该行的代码**尚未执行**。所以此时读 `boot_stage`
拿到的还是上一次运行留下的值（见下面"坑点"）。

## 实测：`bt` 只有一帧（不是 bug）

```console
(gdb) bt
#0  main () at main.c:70
```

**只有一个栈帧** —— 按理说应该是 `#0 main` + `#1 Reset_Handler`（因为启动代码 `bl main` 调用了它）。

原因：`bt` 需要**栈展开（unwinding）**信息才能找到"调用者在哪"：

- PC 上：编译器生成 `.eh_frame` / `.ARM.exidx`，记录了"这一帧多大、返回地址存在哪"；
- 裸机：本实验的 Makefile **显式关掉了它**：
  ```make
  -fno-unwind-tables -fno-asynchronous-unwind-tables     ← 为了省 Flash（见 3.3.4 的 .ARM.exidx 实测）
  ```
- 汇编写的 `startup.S` 也没有 `.cfi` 指令。

于是 gdb 只能报当前帧。**想看"谁调用的我"，就得用汇编级手段**：

```console
(gdb) info registers lr          # lr 里存着返回地址
lr             0x800009b         # → 0x0800009a 之后，正是 Reset_Handler 里 bl main 的下一条
(gdb) info symbol 0x800009b      # （如果符号表覆盖到）会告诉你它在哪个函数
```

顺带：`lr = 0x800009b` 的**最低位是 1** —— 这是 Thumb 状态位（Cortex-M 只支持 Thumb，
所以所有函数地址的最低位在寄存器里恒为 1，`0x800009a | 1`）。
看到 `0x...9b` 这种"奇数地址"不要以为错了，**正常的**。

## ★ 实测的大坑：`monitor reset halt` 之后，gdb 的寄存器视图是**陈旧的**

这是本篇最有价值的发现，因为它会让你**看到错误的数据却毫不自知**。

```console
(gdb) monitor reset halt
[stm32f1x.cpu] halted due to debug-request, current mode: Thread
xPSR: 0x01000000 pc: 0x08000060 msp: 0x20005000     ← openocd 说：PC=0x08000060, MSP=0x20005000

(gdb) info registers pc sp
pc             0x800014c           0x800014c <main+148>   ← ❌ gdb 说：PC 在 main 里！
sp             0x20004ff8          0x20004ff8             ← ❌ MSP 也是旧值
```

**两边矛盾。谁对？openocd 对。**

原因：`monitor` 命令是**绕过 gdb 直接发给 openocd** 的，gdb **不知道**芯片状态变了，
它只是把 `info registers` 显示成**上次读到的缓存**。CM3 复位后 PC 应该 = `0x08000060`
（`Reset_Handler` 首条），MSP = `0x20005000`（RAM 顶）。openocd 是对的。

### 两种修正姿势（都实测过）

```console
# 姿势 1：执行一条指令（副作用是 gdb 被迫重新读寄存器）
(gdb) stepi
Reset_Handler () at startup.S:82
82	    movs    r1, #1
(gdb) info registers pc sp
pc             0x8000062           0x8000062 <Reset_Handler+2>   ← ✅ 刷新了（已执行一条）
sp             0x20005000          0x20005000

# 姿势 2：显式刷新寄存器缓存（推荐，无副作用）
(gdb) monitor reset halt
(gdb) maintenance flush register-cache
(gdb) info registers pc sp
pc             0x8000060           0x8000060 <Reset_Handler>     ← ✅ 精确：复位后的真值
sp             0x20005000          0x20005000
```

> **`maintenance flush register-cache`** 是 gdb 的"维护命令"（`maintenance` 前缀表示
> 不承诺接口稳定，但一直在用）。**只要用了 `monitor` 命令改变了目标状态，
> 就该跟一条这个**，否则后面所有 `info registers` 都是骗你的。

**同一类坑还有**：`monitor reset halt` 之后立刻读**外设寄存器**（`x/6xw 0x40010800`）
—— 这个反而是**对的**，因为 `x` 是直接读内存，不走缓存。
实测同一时刻读出来是复位值：

```console
0x40010800:	0x44444444	0x88844444	0x00000000	0x0000a000
0x40010810:	0x00000000	0x00000000
0x40021018:	0x00000000        ← 时钟还没开
```

**所以：`x` 读内存可信，`info registers` 要警惕缓存。** 记住这一条能省几个小时的困惑。

## ★ 用 gdb 从零点亮一颗 LED（四步实测）

上一节 3.3.3 里我们"用调试器 `mww` 点灯"是**在程序已经跑起来、时钟已开**的前提下做的。
那如果**完全不给程序机会**，从复位状态出发，能不能用调试器把灯点亮？

**能，但要按顺序：**

```console
# 步骤 1：开 GPIOA 时钟（这一步不做，后面全废 —— 见下）
(gdb) set {unsigned int}0x40021018 = 0x4
(gdb) x/1xw 0x40021018
0x40021018:	0x00000004        ✅ 写进去了

# 步骤 2：把 PA5 配成推挽输出
(gdb) set {unsigned int}0x40010800 = 0x44244444
(gdb) x/1xw 0x40010800
0x40010800:	0x44244444        ✅

# 步骤 3：写 BSRR 置位 PA5
(gdb) set {unsigned int}0x40010810 = 0x20
(gdb) x/1xw 0x4001080c
0x4001080c:	0x0000a020        ✅ bit5 = 1 → LED 亮

# 步骤 4：写 BRR 复位
(gdb) set {unsigned int}0x40010814 = 0x20
(gdb) x/1xw 0x4001080c
0x4001080c:	0x0000a000        ✅ bit5 = 0 → LED 灭
```

### 反面对照：跳过步骤 1 会怎样（这是同一次实验的另一半）

同一套操作，**唯独漏掉"开时钟"那一步**：

```console
(gdb) set {unsigned int}0x40010810 = 0x20      # 直接写 BSRR 置位
(gdb) x/1xw 0x4001080c
0x4001080c:	0x0000a000                          ❌ bit5 还是 0，灯没亮
(gdb) set {unsigned int}0x40010814 = 0x20      # 再写 BRR
(gdb) x/1xw 0x4001080c
0x4001080c:	0x0000a000                          ❌ 依然 0
```

**为什么？因为此时 `RCC_APB2ENR = 0`（复位值），GPIOA 的时钟是关的。**

这条实测补上了 3.3 的一个缺口，也修正了一个流行说法：

> **"调试器直接写寄存器就能点灯"这个说法，有一个隐藏前提：外设时钟必须是开的。**

而且它给出了一个**极强的证据**：连**调试器通过 SWD 直接写总线**都写不进去，
说明"时钟没开 → 寄存器不可访问"**不是软件层面的检查，是硬件层面的时钟门控**
（时钟断了，寄存器单元的存储/译码逻辑就不工作）。

**实践含义（排障顺序）**：

```
灯不亮
├─ 用调试器写 BSRR 试试
│   ├─ 灯亮  → 硬件通路 OK，问题在代码（配置写错/被覆盖/没跑到）
│   └─ 灯不亮 → 先查 RCC_APB2ENR 的 bit2！
│              ├─ = 0 → 忘了开时钟（或时钟树配错）
│              └─ = 1 → 再查引脚配置 / SB 跳线 / LED 焊反
```

## 断点、观察点、`monitor` 常用命令速查

```console
# ---- gdb 侧 ----
break main                  # 断点（行号 / 函数名 / 文件:行）
break main.c:101 if blink_count > 5    # 条件断点（每次命中都要"停-判-走"，慢，但省硬件断点）
info breakpoints            # 看断点列表 / 命中次数
delete 1                    # 删 1 号断点
disable 2 / enable 2        # 临时关掉/打开
tbreak main                 # 只命中一次的临时断点
watch blink_count           # 观察点（值变化时停）★ 但只有 4 个硬件 watchpoint
print /x crl_after_config   # 看变量（十六进制）
x/6xw 0x40010800            # 看一段内存（6 个字，十六进制字，地址递增）
info registers r0 r1 pc     # 看寄存器
info symbol 0x800009b       # 反查"这个地址属于哪个符号"
list 68,80                  # 看源码
info line main.c:70         # 反查"这一行对应哪个地址"（和 break 的输出对得上）

# ---- monitor 侧（发给 openocd）----
monitor reset halt          # 复位并停住
monitor reset run           # 复位并自由运行
monitor halt                # 只停住，不复位
monitor flash info 0        # Flash 分区信息（扇区大小/保护状态）
monitor mdw 0x08000000 4    # 直接读内存（openocd 侧，输出更原始）
monitor mww 0x40010810 0x20 # 直接写内存
monitor reset init          # 复位并执行初始化脚本（比 reset halt 更完整）
```

> **`watch` 值得单独提醒**：openocd 报的 `4 watchpoints` 是**硬件数量**。
> 你打第 5 个 `watch` 时 gdb 会退化成"单步 + 每次比较"（极慢，且 `next` 会变得像卡住）。
> **在裸机上，能用 `print` 解决的就别用 `watch`。** 这也是为什么本仓库的
> `main.c` 要埋那么多 `volatile` 观测点变量 —— **它们是"用内存换调试资源"**，
> 一条 `x/6xw 0x20000000` 就把 6 个变量的当前值全看到了，一个断点都不占。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "点 Debug 就会停在你想要的地方" | Debug 按钮只是**建连接 + 烧录 + 附加上去**。它停下时的位置是"当前 PC"，不一定是 `main` |
| "断点就是断点，随便打" | Flash 只读 → 只能用**硬件断点**，`hardware has 6 breakpoints, 4 watchpoints`（openocd 启动时自己报了）。超了会退化或用不了 |
| "`monitor reset halt` 之后寄存器就是复位值" | **openocd 那边是**，**gdb 的 `info registers` 是陈旧缓存**。实测 PC 显示 `main+148`，真值是 `Reset_Handler`。必须跟 `maintenance flush register-cache`（或一条 `stepi`） |
| "`x`（读内存）和 `info registers` 一样可信" | `x` 每次都真去读总线（可信）；`info registers` 走 gdb 自己的缓存（可能陈旧）。**`monitor` 改过状态后尤其要警惕** |
| "`bt` 应该能看到从 Reset_Handler 调过来的完整栈" | 裸机上通常**只有一帧**。`-fno-unwind-tables` + 汇编无 `.cfi` → 没有栈展开信息。要看调用者只能用 `lr` |
| "寄存器里的地址应该是偶数" | Thumb 状态下函数指针**最低位恒为 1**（`lr = 0x800009b`）。这是状态位，不是错误 |
| "调试器直接写寄存器就能点灯" | **前提是外设时钟已开**。实测时钟关着时，SWD 写 BSRR 完全无效（ODR 保持 `0x0000a000`）→ 这是硬件时钟门控，不是软件检查 |
| "调试会影响程序运行，测出来的时间不准" | 对。**halt 期间计时器/外设仍在跑**，但你的软件不跑。所以"halt 一下再 resume"会破坏任何时间敏感的逻辑（这也是后面用 SysTick 计时更可靠的原因之一） |
| "`print` 看变量最保险" | 前提是**变量真的在内存里**。被优化进寄存器的变量 `print` 会说 `<optimized out>`，看到这个别怀疑调试器，去降优化等级或给变量加 `volatile` |

## 代码自测

<details>
<summary>Q1：为什么 Flash 上的程序不能用软件断点？</summary>

软件断点的实现是**把目标地址的指令首字节替换成一个"陷入"指令**
（x86 是 `0xCC`/`int3`，ARM 是 `bkpt`），CPU 执行到那里就触发异常，
调试器接管、显示状态、恢复原字节、继续。

这在 RAM 里的程序上完美工作。但**Flash 上不行**：

| 问题 | 说明 |
|---|---|
| Flash 不能按字节写 | 只能**擦整页**（F1 是 1 KiB）再重写整页 |
| 擦一页 = 断点命中一次就擦一次 | 几十毫秒起，Flash 寿命也受不了（F1 保证约 1 万次擦写） |
| 断点命中后要立刻恢复 | 做不到 —— 擦写期间目标指令不在，程序自己都跑不了 |

于是芯片厂商给了硬件方案：**FPB（Flash Patch and Breakpoint）单元** ——
一组"地址比较器 + 影子指令"，在**取指阶段**就把命中的地址替换成 `bkpt`。
对 Flash 零写入，速度也快。

代价就是**数量有限**：

```
Info : stm32f1x.cpu: hardware has 6 breakpoints, 4 watchpoints
```

**6 个断点 / 4 个观察点**（Cortex-M3 的规格）。F1 上还有 2 个"指令比较器"用于 patch，
但 openocd 报的是可用的断点数量。

**实践引申**：

- **6 个够用，但要省着用**。打完记得 `delete`，否则下次调试会莫名
  "断点插不进去"。
- **条件断点会吃掉"隐形的慢"**：gdb 的实现是"每次命中都停下来判断条件"，
  在一个每秒几十万次的循环里条件断点 ⇒ 等于单步执行。
  **这是"程序在调试器里慢得像死了"的第一号原因。**
- **更好的办法是"用内存换断点"**：本实验在 `main.c` 里埋的 `volatile` 观测点变量
  （`crl_after_config` / `odr_after_set` / `blink_count` / `boot_stage`），
  一个断点都不用，一条 `x/6xw 0x20000000` 就能看到 6 个变量的值。

</details>

<details>
<summary>Q2：`monitor reset halt` 和 `monitor reset run` 到底做了什么？</summary>

`reset` 是**给芯片的复位信号**（openocd 通过调试口触发，等价于按了板上的 RESET 键）。
后面的 `halt` / `run` 决定"复位之后马上做什么"：

| 命令 | 动作 |
|---|---|
| `monitor reset halt` | 复位 → **停在复位向量**（PC = `Reset_Handler` 首条，MSP = RAM 顶） |
| `monitor reset run` | 复位 → **立刻放它跑**（等于拔插一下电源） |
| `monitor reset init` | 复位 → 停下 → **执行 openocd 的初始化脚本**（配时钟、初始化 Flash 控制器等） |

**`reset halt` 之后，"停在复位向量"就一定能停住吗？** 不一定 —— 这里有个真实的坑：

```
reset halt 发出 → 复位信号解除 → 芯片开始取指执行
                                    ↑
                              调试器要在这之前把 halt 请求送到，才能停住
```

理论上有个竞态窗口。实际上 CM3 的调试单元在复位后会先进入 halt 状态（除非被配置成
"不复位时不停"），所以通常可靠。**但如果你在 `main` 里就把时钟配错、或者把
调试引脚（PA13/PA14）重配成了普通 GPIO —— 那就再也连不上了**，
此时只能按住板上的 RESET 键 + `monitor reset halt` 抢那几百毫秒。

**顺带解释一个现象**：为什么 `reset halt` 后立刻 `x/1xw 0x40021018` 得到 0？
因为**复位是把所有外设寄存器恢复默认值**，而外设时钟默认全关。
每次 `reset halt` 都等于"回到一无所知的出厂状态"——
所以调试脚本里**每次 reset 之后都要重新配一遍**，不能指望上次的配置还在。

</details>

<details>
<summary>Q3：`break main.c:70` 和 `break main` 有什么区别？</summary>

`break main` 断在**函数入口**（prologue 之后第一条有意义的指令），
`break file:line` 断在**那一行对应的第一条指令**。

在 `-Os` 下这个区别会咬人，因为**行号和指令不再是直线对应**：

```console
(gdb) break main
Breakpoint 1 at 0x80000ba: file main.c, line 70.     ← main 的第一条代码落在 70 行
```

更麻烦的是：**优化会把多行合并到一段指令**，或者**把一行的代码拆到两个分支**。
实测本实验的 `next` 序列，行号是**跳着走**的：

```
77 → 79 → 80 → 96 → 93 → 96 → 94        ← 不是 70,77,79,80,93,94,96 的顺序
```

那是编译器重排 + 指令/行号映射的结果。**看起来像"gdb 乱跳"。**

三个应对办法：

| 办法 | 命令 | 说明 |
|---|---|---|
| 降优化 | `make CFLAGS="-O0 -g"` | **学习阶段首选**：`-O0` 下行号基本是直线，单步不会晕 |
| 看汇编 | `disassemble /r main` 或 `layout asm` | 不跟 C 行号走，直接跟指令 —— **最可信** |
| 用函数名断点 | `break delay` | 比行号稳定（但内联后就没了，见 [3.07](3.07-逐步执行程序.md)） |

**本实验的 Makefile 用的是 `-Os`** —— 因为要演示"真实工程会遇到的麻烦"。
你日常调试时建议切到 `-O0 -g`，只在**性能/体积问题**上回到 `-Os`。

</details>

<details>
<summary>Q4：`info symbol 0x800009b` 这种反查有什么用？</summary>

有用，而且常常是**唯一出路**。典型场景：

**场景 1：HardFault 之后看是谁挂的**

```
(gdb) info registers pc lr
lr    0x0800014d        ← 挂之前调用的最后一个函数地址
(gdb) info symbol 0x0800014c
delay + 12 in section .text     ← 原来是 delay 里出的问题
```

**场景 2：看 `lr` 判断"谁调用的我"**（`bt` 只有一帧时的替代方案，
见本篇「实测：`bt` 只有一帧」）。

**场景 3：核对链接脚本布局**

```
(gdb) info symbol 0x08000178
_sidata in section .isr_vector? no —— 它会告诉你这个地址落在哪个段
```

**为什么这个技能在裸机上比在 PC 上更重要**：PC 上你有 `/proc/self/maps`、
有 core dump、有 ASan 报告；**裸机上唯一的结构化信息就是符号表 + `.map` 文件**。
所以本仓库一条纪律：

> **任何"地址 ↔ 名字"的困惑，都先用 `info symbol` 和 `.map` 查，
> 再考虑去读反汇编。**

顺带一个小技巧：`info symbol` 的输入不要求精确地址。
给 `0x800009b`（Thumb 位=1 的奇数地址）也能正常工作，gdb 会自己掩掉最低位。

</details>

<details>
<summary>Q5：为什么"用调试器点灯"这件事本身值得写一篇笔记？</summary>

因为它把**整条链路的两端都摊开了**，而且**每一步都可以独立验证**。

一个完整的点灯链路是：

```
C 代码 → 编译 → 链接 → 烧录 → 芯片执行 → 寄存器写入 → 引脚电平 → LED 亮
   ↑                                                              ↑
   └──────────── Ｘ 这里出问题怎么办？───────────────────────────┘
```

出问题时，你在两端之间**没有中点**，只能猜。"用调试器点灯"就在中间插了一排检查点：

```
① 调试器写 APB2ENR    → 读回 = 4？        否则：地址错 / 芯片型号不对
② 调试器写 CRL        → 读回 = 0x44244444？ 否则：时钟没开（先做①）
③ 调试器写 BSRR       → 读回 ODR.bit5 = 1？ 否则：引脚被别的东西占着 / 硬件问题
④ 灯亮了？
   ├─ 亮 → 硬件通路完全 OK，问题 100% 在**代码**（没跑到/写错/被覆盖）
   └─ 不亮 → 问题 100% 在**硬件/电路**（SB 跳线、LED 极性、焊接）
```

**这一套二分法能把"灯不亮"从"什么都有可能"压缩到"两类之一"。**

而且这次的实测还给了一个**意外收获**：跳过步骤 ① 时，
**连调试器都写不进去**。这反过来证明了一件重要的事：

> **"必须先开时钟"不是一句经验规则，而是有硬件机制支撑的硬约束。**

如果只记住"要先开时钟"（一句口诀），你会在 F4/L4 上被 BusFault 打脸
（那边未使能时钟的访问直接进异常）。如果记住了**机制**（时钟门控切断了寄存器的访问），
你就能预测新芯片的行为、知道该往哪查。

**这就是本仓库坚持"每个结论都要有实测支撑"的原因** ——
口诀会过期，机制不会。

</details>
