# 16.7 替代方案

> 书：第 16 章 浮点数 · 16.7 替代方案（原书 p219+ 区间内）
> 上一篇：[16.6 次正规数](16.6-次正规数.md) ｜ 下一篇：[第 17 章 模块化编程](../17-modular-programming/README.md)
> 对应实验：主机侧实测 + **交叉编译真链接**
> （`--target=armv7m-none-eabi -mcpu=cortex-m3` + `ld.lld` + 本仓库 `linker.ld`）

## 书这一节讲什么

一句话：**在没有 FPU 的 MCU 上，浮点的正解是"整数 / 定点数"。**

本篇给出**裸机真链接的实测数据**：同样是 `a*b+c`，
整数版和 Q16.16 定点版**链接成功**，
`float` 版和 `double` 版**链接失败**——因为它们需要额外的软浮点库。

## 一、⚠ 核心实测：M3 上链接一个 `a*b+c`

四个版本的 `Reset_Handler` 都做同一件事（`volatile` 输入，防止被 `-Os` 常量折叠），
用本仓库的 `stm32/00-toolchain-clang/linker.ld` 真链接：

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -Os \
        -ffreestanding -nostdlib ... -c app_X.c
$ ld.lld -T linker.ld --gc-sections -o app_X.elf vec.o app_X.o
```

| 版本 | `.o` 里的未定义符号 | 链接结果 | Flash（text+data） |
|---|---|---|---|
| **整数** `int a*b+c` | 无 | ✅ **成功** | **56 + 12 = 68 B** |
| **Q16.16 定点** | 无 | ✅ **成功** | **64 + 12 = 76 B** |
| **`float`** | `__aeabi_fmul` `__aeabi_fadd` | ❌ **失败** | —— |
| **`double`** | `__aeabi_dmul` `__aeabi_dadd` | ❌ **失败** | —— |

```
ld.lld: error: undefined symbol: __aeabi_fmul
>>> referenced by app_f.c
>>>               app_f.o:(Reset_Handler)

ld.lld: error: undefined symbol: __aeabi_dmul
>>> referenced by app_d.c
>>>               app_d.o:(Reset_Handler)
```

⚠ **诚实说明**：链接失败是因为**本机没有 armv7m 的 compiler-rt builtins**
（`lib/clang/23/lib/` 下只有 `*osx*` 版本），
不是"浮点不能用"。但它**证明了一件重要的事**：

> **浮点需要额外的运行时库，整数和定点不需要。**
> 那些 `__aeabi_f*`/`__aeabi_d*` 函数加起来是**几 KB 的 Flash**，
> 在 64 KB Flash 的 F103C8 上不是小数目。

**定点版只比整数版多 8 字节**（64 vs 56）——
因为 M3 有 `smull`（32×32→64 位乘法）指令，Q16.16 的乘法几乎是免费的。

## 二、Q16.16 定点数（实测）

```
$ ./q
Q16.16 范围: -32768.0000 ~ 32768.0000   分辨率 0.0000152588
float  1.5*2.25+0.5  = 3.8750000000
Q16.16              = 3.8750000000   (位模式 0x0003e000)
误差 = 0.0000000000
```

| 项 | 实测值 |
|---|---|
| 范围 | **±32768.0** |
| 分辨率 | **1/65536 = 1.5258789e-05** |
| `1.5 × 2.25 + 0.5` | 和 float **完全一致**（`3.875`） |
| 乘法位模式 | `0x0003e000` |

```c
typedef int32_t q16_t;
#define Q16_SHIFT 16
#define Q16_FROM_FLOAT(f) ((q16_t)((f) * 65536.0f))
#define Q16_TO_FLOAT(q)   ((float)(q) / 65536.0f)
#define Q16_FROM_INT(i)   ((q16_t)(i) << 16)
#define Q16_TO_INT(q)     ((q16_t)(q) >> 16)

static inline q16_t q16_add(q16_t a, q16_t b) { return a + b; }   /* 就是整数加！*/
static inline q16_t q16_sub(q16_t a, q16_t b) { return a - b; }
static inline q16_t q16_mul(q16_t a, q16_t b) {
    return (q16_t)(((int64_t)a * (int64_t)b) >> Q16_SHIFT);       /* ⚠ 必须 64 位中间 */
}
static inline q16_t q16_div(q16_t a, q16_t b) {
    return (q16_t)(((int64_t)a << Q16_SHIFT) / b);                /* ⚠ 先左移再除 */
}
```

**两个易错点**：

1. **乘法必须 64 位中间值**。两个 Q16.16 相乘，中间是 Q32.32，
   32 位上直接溢出。⚠ 但在 M0/M3 上 `int64_t` 也是软件的——
   **所以乘法才是定点的真正成本，加减完全免费**（实测：定点版比整数版只多 8 B）。
2. **除法要先左移再除**：`(a << 16) / b`，否则精度全丢。

## 三、⚠ 实测：Q16.16 也会溢出

```
⚠ 300.0 * 300.0 (Q16.16) = 24464.0000   ← 溢出（正确值 90000）
```

`300 × 300 = 90000 > 32768`，**超出 int32_t 范围直接回绕**。
⚠ 而且和 float 溢出成 `inf` 不同，**定点溢出是"回绕成另一个合法值"**——
比 inf 更难发现。

✅ 对策：算之前先估算范围；必要时用 Q8.24（范围小、精度高）或
`int64_t` 做中间值。

## 四、⚠ 实测：定点 vs 浮点的累加误差

```
累加 5000000 次（每次 +0.001）：
  float   结果 = 4897.391602  （真值 5000.000000）
  Q16.16  结果 = 4959.106445
```

两者都有误差，但**性质完全不同**：

| | `float` | Q16.16 |
|---|---|---|
| 实测结果 | **4897.391602** | **4959.106445** |
| 误差 | −102.6（**−2.05%**） | −40.9（**−0.82%**） |
| 误差来源 | `0.001f` 本身不精确 + 逐次舍入 | **步长取整**：用了 `65/65536 = 0.00099182` 而不是 `0.001` |
| 可预测吗 | ❌ 依赖舍入序列 | ✅ **完全可算**：`5000 × 65/65536 = 4959.1` |
| 能修正吗 | 要 Kahan | ✅ 用 `66`（`65.536` 的舍入）或补偿 |

**这一条比"哪个更准"更重要**：

> **定点误差是确定的、可分析的、可复现的；
> 浮点误差是随舍入序列漂移的。**
> 硬实时系统要的是**可预测**，不只是"平均更准"。

⚠ **诚实说明**：这个对比里 Q16 用了 `65` 作为 `0.001` 的定点值，
本身就有 −0.8% 的系统偏差；换成 `66` 会偏正。
**定点的精度取决于你选的步长**，这是设计者必须自己算的账。

## 五、⚠ 实测：`printf("%f")` 有多贵

```
$ ./pf
snprintf("%.2f")   : 186 ns/次 → "23.45"
snprintf 整数拆分   : 100 ns/次 → "23.450"
```

**格式化浮点比整数拆分慢约 1.9 倍**（主机侧实测，已有 FPU 和硬件除法）。

⚠ 在裸机上差距会**大得多**：`%f` 需要
① 软浮点库 + ② 十进制格式化库，两项都要链接进来。
[ch09](../09-uart-serial/README.md) 实测过 `mini_printf` 只有 **340 B**——
正是因为它**不含 `%f`**。

✅ 裸机的打印方式（整数拆分，不用 `%f`）：

```c
void print_temp(int32_t mC) {          /* 毫摄氏度：23450 = 23.450 ℃ */
    int ip = mC / 1000, fp = mC % 1000;
    if (fp < 0) fp = -fp;
    mini_printf("%d.%03d C\r\n", ip, fp);
}
```

## 六、决策表（本仓库的取向）

| 场景 | 方案 | 依据 |
|---|---|---|
| 温度、电压、电流等物理量 | **整数 + 单位后缀**（`temp_mC`、`volt_mV`） | 无误差、无库依赖 |
| PID 控制、滤波 | **Q16.16 定点** | 确定性；实测比整数版只多 8 B |
| 显示 | **整数拆分**（不用 `%f`） | 实测 186 vs 100 ns；裸机上差更多 |
| 协议传输 | **定点整数** | 跨平台无歧义（[16.1](16.1-数字表示.md)） |
| 时间戳 / 计数 | **`uint32_t`/`uint64_t`** | ⚠ `float` 在 1e7 处 ULP=1（[16.3](16.3-精度位数.md)） |
| 真需要大动态范围 | `float`（确认有 FPU） | 定点的 ±32768 不够 |

**按芯片的决策**：

| 芯片 | FPU | 建议 |
|---|---|---|
| **Cortex-M0 / M0+**（F030R8） | **无** | **能不用就不用** |
| **Cortex-M3**（F103RB） | **无** | 同上（[16.1](16.1-数字表示.md) 实测 `U __aeabi_fmul`） |
| **Cortex-M4F / M7（单精度）** | **有** | `float` 硬件加速；⚠ **`double` 仍是软件** |
| Cortex-M7（双精度版） | 有 | `double` 也快 |

⚠ **即使有 FPU，也要注意三条**：

1. **FPU 默认关闭**：M4F 上要设 `SCB->CPACR |= (3<<20)|(3<<22)`，
   否则用浮点 → **UsageFault（NOCP）**；
2. **中断帧变大**：用 FPU 后中断要多压浮点上下文（M4 上约 68 字节，对齐后 136），
   栈预算要加（[ch07](../07-stack-frame-functions/README.md)）；
3. **`double` 在单精度 FPU 上仍是软件**（实测未定义符号仍在）。

## 七、主机侧的对照（有 FPU 是什么感觉）

实测算术吞吐（Apple Silicon，`-O2`，1e8 次循环）：

```
int    a*b+c : 0.238 ns/次
float  a*b+c : 1.176 ns/次
double a*b+c : 0.938 ns/次
int    a/b   : 0.626 ns/次
float  a/b   : 0.940 ns/次
double a/b   : 0.939 ns/次
```

**全部在 1 ns 量级**——这就是"有 FPU"的样子：
`float` 和 `double` 几乎一样快，和整数同一个量级。

⚠ 对比 M3：**同样的 `a*b+c` 是 `__aeabi_fmul` 库函数调用**，
量级差几百到上千倍。
（M3 上的具体周期数**本机未实测**——需要板子和软浮点库，
且本机没有 armv7m 的 builtins，见第一节。）

## 代码自测

<details>
<summary>Q1：同样是 `a*b+c`，为什么 `float` 版链接失败而 Q16.16 版能链接？</summary>

因为 **`float` 需要软浮点库，定点只需要整数指令**。实测：

```
整数版   .o 未定义符号: （空）        → ✅ 链接成功，Flash 68 B
Q16.16版 .o 未定义符号: （空）        → ✅ 链接成功，Flash 76 B
float版  .o 未定义符号: __aeabi_fmul __aeabi_fadd  → ❌ undefined symbol: __aeabi_fmul
double版 .o 未定义符号: __aeabi_dmul __aeabi_dadd  → ❌ undefined symbol: __aeabi_dmul
```

⚠ **注意**：这次失败的直接原因是**本机没有 armv7m 的 compiler-rt builtins**，
不是"浮点不能用"。但它证明了核心事实：

> **浮点运算依赖额外的运行时库（几 KB Flash），整数/定点不依赖。**

而 Q16.16 定点版只比整数版多 **8 字节**——
因为 M3 有 `smull` 指令（32×32→64），乘法几乎是免费的。
**这就是"替代方案"的全部意义。**
</details>

<details>
<summary>Q2：Q16.16 的乘法为什么要 `int64_t` 中转？</summary>

因为两个 Q16.16 相乘，中间结果是 **Q32.32**（32 位整数 + 32 位小数），
在 `int32_t` 里**必然溢出**。

```c
static inline q16_t q16_mul(q16_t a, q16_t b) {
    return (q16_t)(((int64_t)a * (int64_t)b) >> 16);   /* ⚠ 必须 64 位 */
}
```

⚠ 但在 **M0/M3 上 `int64_t` 运算也是软件的**（要 `__aeabi_lmul` 之类的辅助函数）。
所以：

- **加减法**：就是整数加减，**完全免费**（实测定点版比整数版只多 8 B）；
- **乘法**：才是定点的真正成本——但仍然比软浮点便宜得多；
- **除法**：`(a << 16) / b`，⚠ 先左移再除，否则精度全丢。

**实用建议**：能重构成"先乘后加"（MAC）的算法尽量用加法和移位，
把乘法次数降到最少。
</details>

<details>
<summary>Q3：定点数的溢出和 `float` 溢出成 `inf` 有什么不同？哪个更危险？</summary>

**定点更危险，因为它不产生"异常值"，而是产生"另一个合法值"。**

实测：

```
⚠ 300.0 * 300.0 (Q16.16) = 24464.0000   ← 正确值 90000，回绕成 24464
```

| | 浮点溢出 | 定点溢出 |
|---|---|---|
| 结果 | `inf`（[16.4](16.4-无穷大.md) 实测） | **回绕成另一个合法数**（实测 24464） |
| 能检测吗 | ✅ `x > FLT_MAX` | ❌ 结果看起来"正常" |
| 后续 | inf 会继续传播 / 变 NaN | **静默错误值，直接进控制回路** |

✅ 对策：

1. **设计阶段估算范围**：Q16.16 只有 ±32768，中间结果也算进去；
2. **乘法用 `int64_t` 中间值**并检查结果是否超 `int32_t` 范围；
3. 必要时换格式：Q8.24（范围 ±128、精度更高）或 Q24.8（范围 ±8388608）。
</details>

<details>
<summary>Q4：M4F 有 FPU，我直接把 `double` 改成 `float` 就够了吗？</summary>

**改类型是第一步，还要做三件事。**

实测 M4F 的未定义符号（`armv7em -mfloat-abi=hard -mfpu=fpv4-sp-d16`）：

```
U __aeabi_dadd  U __aeabi_dmul  U __aeabi_ddiv   ← ⚠ double 还是软件
```

`float` 的三个 `__aeabi_f*` 已经消失（反汇编是 `vmul.f32` / `vdiv.f32`），
但 `double` 的三个还在——**M4F 只有单精度 FPU**。

另外三件必须做的事：

1. **使能 FPU**：`SCB->CPACR |= (3UL<<20) | (3UL<<22); __DSB(); __ISB();`
   否则用浮点 → **UsageFault（NOCP）**。⚠ **裸机启动代码里没人替你做**。
2. **加大栈预算**：用了 FPU 后中断帧要多压浮点上下文（M4 上约 68 字节，
   对齐后可能 136），见 [ch07](../07-stack-frame-functions/README.md)。
3. **别用 `%f`**：实测 `snprintf("%.2f")` 比整数拆分慢 **1.9 倍**
   （186 vs 100 ns），裸机上还要额外链接格式化库。

**最省事的做法仍然是用整数**——整数不需要使能任何东西，
不影响中断帧，也不需要任何库。
</details>
