## 书这一节讲什么

一句话：**Valgrind 是一个"不用重新编译就能查内存错误"的工具。**

书上讲它的 `memcheck` 工具怎么用、输出怎么读。
本篇补上书里没讲的两件事：

1. **Valgrind 和 ASan 的机制差别**（决定了各自能查什么、代价多大）；
2. **本机的现实情况**（见下——**我没法在这台机器上跑它**）。

## 二、Valgrind 是怎么工作的（和 ASan 的关键差别）

| | **Valgrind** | **AddressSanitizer** |
|---|---|---|
| **机制** | **二进制翻译**（运行时把机器码翻译成 IR，再插桩） | **编译期插桩**（clang 在生成代码时就插入检查） |
| **要不要重新编译** | ❌ **不用**（直接跑原来的可执行文件） | ✅ 要（`-fsanitize=address` 重新编译） |
| **要不要源码** | 不用（但要 `-g` 才有行号） | 不用（但要 `-g` 才有行号） |
| **速度** | **慢 20–50 倍**（公开的经验值，**未实测**） | **慢 2 倍左右**（公开的经验值，**未实测**） |
| **能查什么** | 越界、UAF、双重释放、**泄漏**、未初始化读 | 越界、UAF、双重释放、泄漏（LSan） |
| **独有优势** | ✅ **未初始化内存读**（ASan 查不了） | ✅ 快；能在生产构建里跑 |
| **能跑在板子上** | ❌ 不能（要 OS + 大量资源） | ❌ 不能（要 libc + shadow memory） |

⚠ **"未初始化内存读"是 Valgrind 的独门绝技**：

```c
int x;                 /* 未初始化 */
if (x > 0) ...         /* Valgrind: "Conditional jump depends on uninitialised value" */
```

ASan **查不了**这个（它只管地址合法性，不管值有没有初始化）。
这是"两个都装上"的理由。

## 三、书上的用法（命令与输出解读）

```sh
# 基本用法
valgrind --tool=memcheck ./app

# 完整查泄漏（推荐）
valgrind --tool=memcheck --leak-check=full --show-leak-kinds=all ./app

# 追"未初始化读"的来源
valgrind --tool=memcheck --track-origins=yes ./app
```

**输出怎么读**（书上的典型例子，⚠ **非本机实测**）：

```
==12345== Invalid write of size 4
==12345==    at 0x1091B6: main (ch13.c:8)
==12345==  Address 0x4a54068 is 0 bytes after a block of size 40 alloc'd
==12345==    at 0x483B7F3: malloc (vg_replace_malloc.c:307)
==12345==    by 0x10918F: main (ch13.c:4)
```

和 ASan 的信息**几乎一一对应**：

| Valgrind 说 | ASan 说 | 含义 |
|---|---|---|
| `Invalid write of size 4` | `WRITE of size 4` | 写了 4 字节 |
| `Address ... is 0 bytes after a block of size 40` | `is located 0 bytes after 40-byte region` | 越界到末尾后 0 字节处 |
| `at 0x1091B6: main (ch13.c:8)` | `#0 ... in main ch13.c:8` | 出错行 |
| `by 0x10918F: main (ch13.c:4)` | `#1 ... in main ch13.c:4` | 分配点 |

——**两者给出的是同一套信息**，只是"怎么拿到"不同
（Valgrind 靠运行时翻译，ASan 靠编译期插桩）。

**泄漏报告**（⚠ 非本机实测）：

```
==12345== LEAK SUMMARY:
==12345==    definitely lost: 1,024 bytes in 1 blocks
==12345==    indirectly lost: 0 bytes in 0 blocks
==12345==    possibly lost: 0 bytes in 0 blocks
==12345==    still reachable: 0 bytes in 0 blocks
```

| 分类 | 含义 | 要管吗 |
|---|---|---|
| **definitely lost** | 指针彻底丢了，回收不了 | ✅ **必须修** |
| **indirectly lost** | 因为父块丢失而连带丢失 | ✅ 修了父块就没了 |
| **possibly lost** | 指针还在但指向块中间（链式结构常见） | ⚠ 看情况 |
| **still reachable** | 退出时还持有指针（比如全局缓存） | ❌ 通常不用管 |

## 五、怎么选：Valgrind 还是 ASan？

| 场景 | 选 |
|---|---|
| **日常开发、跑测试** | **ASan**（快，能一直开着） |
| 怀疑**未初始化读** | **Valgrind**（ASan 查不了） |
| **不能重新编译**（只有二进制） | **Valgrind** |
| 想查**泄漏**且 ASan 的 LSan 不给力 | **Valgrind**（见下） |
| CI 里跑 | **ASan**（快；Valgrind 太慢） |

⚠ **关于泄漏检测的一个实测发现**：
在本机 macOS arm64 上，**ASan 的 LeakSanitizer 不报泄漏**——
实测 `ASAN_OPTIONS=detect_leaks=1` 只打出
`LeakSanitizer: checking for leaks`，**没有报出那块明确泄漏的 1024 字节**。

所以：**如果你的主要需求是查泄漏，且你在 macOS 上，
Valgrind（在 Linux 上跑）比 ASan 的 LSan 更可靠。**
这正好是"两个都要会"的理由。

## 六、⚠ Valgrind 的三个常见"假警报"

书上大概不会提，但用起来一定会碰到：

| 现象 | 原因 | 处理 |
|---|---|---|
| 报告系统库里的错误 | 你只关心自己的代码 | `--suppressions=` 加载抑制文件 |
| `still reachable` 一大堆 | 程序退出时没清理全局缓存 | 通常不用管（或 `--show-leak-kinds=definite`） |
| 报"uninitialised value"但代码看着没问题 | 可能是**结构体填充字节**（padding）被整体拷贝 | 用 `memset` 初始化整个结构体，或忽略 |

⚠ **第二条在嵌入式模拟代码里特别常见**：
全局的驱动结构体、缓存池，退出时当然还"可达"。
**别为了消除这些警告去写清理代码**——那是给工具看，不是给用户看。

## 代码自测

<details>
<summary>Q1：Valgrind 和 AddressSanitizer 到底差在哪？什么时候必须用 Valgrind？</summary>

**核心差别在"插桩的时机"**，这决定了两者的一切差异。

| | **Valgrind** | **AddressSanitizer** |
|---|---|---|
| 机制 | **运行时二进制翻译**：把已编译的机器码翻译成 IR，插桩后再执行 | **编译期插桩**：clang 生成代码时就插入检查 |
| 要不要重新编译 | ❌ **不用** | ✅ 要（`-fsanitize=address`） |
| 速度 | 慢（公开经验值 20–50 倍，⚠ **未实测**） | 快（公开经验值约 2 倍，⚠ **未实测**） |
| 独有能力 | ✅ **未初始化内存读** | ✅ 快到能常开 |
| 能查栈/全局越界 | 有限 | ✅ 能（`-fsanitize=address` 覆盖栈和全局） |

**机制差异带来的实际后果**：

**① "不用重新编译"是 Valgrind 的最大便利**

```sh
valgrind ./release_binary        # 直接跑现成的二进制
```

适合：拿不到源码的第三方库、已经编译好的发布版、构建流程改不动的老项目。

**② "未初始化读"是 Valgrind 的独门绝技**

```c
struct { int a; char b; } s;     /* 有 3 字节填充 */
...
if (s.a > 0) ...                 /* s.a 从未赋值 */
```

Valgrind：

```
Conditional jump or move depends on uninitialised value(s)
```

**ASan 完全查不了这个**——它只检查"访问的地址合不合法"，
不检查"读到的值有没有被初始化过"。

⚠ 这个坑在嵌入式模拟代码里特别常见：
从硬件读回来的结构体、没 `memset` 的局部缓冲区、
用了 `malloc` 而不是 `calloc` 的数组。

**③ ASan 快到能"一直开着"**

这就是它成为首选的理由：
**日常开发的每一次编译都带上 `-fsanitize=address`，
成本可以接受，收益是每次运行都在检错**。
Valgrind 慢到只能在"专门跑一次"时用。

---

**所以：什么时候必须用 Valgrind？**

| 场景 | 理由 |
|---|---|
| **怀疑未初始化读** | ASan 查不了 |
| **不能重新编译**（只有二进制） | ASan 要求重新编译 |
| **查泄漏且 LSan 不给力** | ⚠ 实测：本机 macOS arm64 上 ASan 的 LSan **不报泄漏**（只打出 `checking for leaks`），而 Valgrind 在 Linux 上可靠 |
| 想看**更细的内存画像** | Valgrind 有 `massif`（堆剖面）、`cachegrind`（缓存分析）、`helgrind`（竞态）等工具集 |

⚠ **Valgrind 不只是 memcheck**，它是一整套工具：

```sh
valgrind --tool=memcheck   ./app    # 内存错误（本节）
valgrind --tool=massif     ./app    # 堆使用剖面（谁在什么时候占了多少）
valgrind --tool=cachegrind ./app    # 缓存命中分析
valgrind --tool=helgrind   ./app    # 数据竞争（多线程）
```

——`massif` 在"RAM 够不够"这个问题上特别有用，
正好对应 [ch11](../11-linker/README.md) 讲的静态预算思路。

**一句话**：
> **ASan 是日常用的（快、常开），Valgrind 是专门排查用的（慢、但查得更全）。
> 两个都要会，别二选一。**
</details>

<details>
<summary>Q2：泄漏报告里的四类（definitely / indirectly / possibly / still reachable）分别要不要修？</summary>

**只有前两类必须修。**

**分类的含义**（⚠ 以下是工具文档的标准定义，**非本机实测**）：

| 分类 | 含义 | 要修吗 |
|---|---|---|
| **definitely lost** | **没有任何指针指向它了**，彻底回收不了 | ✅ **必须修** |
| **indirectly lost** | 因为**父块**丢失而连带丢失（比如丢了一个链表的头指针，后面所有节点都间接丢了） | ✅ 修了父块就没了 |
| **possibly lost** | 还有指针，但**指向块的中间**而不是开头（链表、树这类"内部指针"结构常见） | ⚠ 看情况 |
| **still reachable** | 退出时**仍然有指针指向它**（全局缓存、单例、注册表） | ❌ **通常不用修** |

**为什么 `still reachable` 不用修**：

```c
static cache_t g_cache;      /* 全局缓存，程序活着时一直要用 */
int main(void){ cache_init(&g_cache); ... return 0; }
```

程序退出时 `g_cache` 还"可达"，**但那不是泄漏**——
进程一退出，操作系统会把整个地址空间收回去。
为了消除这条警告去写 `cache_destroy(&g_cache)`，
是**给工具看的代码，不是给用户看的**。

⚠ **嵌入式模拟代码里这条特别常见**：

- 全局的驱动句柄；
- 静态注册的回调表；
- RTOS 的任务控制块。

都会在退出时报 `still reachable`。**别理它们**，
用 `--show-leak-kinds=definite,indirect` 把噪音滤掉：

```sh
valgrind --leak-check=full --show-leak-kinds=definite,indirect ./app
```

**`possibly lost` 怎么判断**：

典型场景——链表节点：

```c
node_t *p = ...;              /* 指向某个节点 */
/* 头指针丢了，但某个地方还存着指向中间节点的指针 */
```

工具不确定"这个中间指针算不算还持有整块"，所以判 `possibly`。

**判断方法**：看这个指针是不是**你代码里的真实引用**。
如果是（比如你确实在用某个节点），修复头指针即可；
如果不是（那个指针也是垃圾），就是真的泄漏。

**优先级的实操建议**：

1. **先修 `definitely lost`**（这是真漏）；
2. `indirectly lost` 通常**修了父块自动消失**；
3. `possibly lost` 逐个看；
4. `still reachable` **加过滤参数忽略**。

⚠ **一个重要的提醒**：
在**长期运行的嵌入式设备**上，
`still reachable` 的语义会变——
因为设备**不会退出**，那些"退出时还持有"的内存
会一直占着。如果它们是**无界增长**的（比如一个只增不减的日志缓存），
那就是**真泄漏**。

**所以判断标准不是"退出时可达吗"，而是"它会无界增长吗"。**
在裸机上，后者才是要命的。
</details>

<details>
<summary>Q3：为什么裸机上没有内存检错工具？那怎么办？</summary>

**因为所有内存检错工具都需要"操作系统 + 大量额外内存"，裸机两样都没有。**

**工具的资源需求**：

| 工具 | 需要什么 | 裸机有吗 |
|---|---|---|
| **Valgrind** | OS（进程、mmap）、二进制翻译运行时、比被测程序多几倍的内存 | ❌ 全没有 |
| **ASan** | libc（`malloc` 拦截）、**shadow memory**（每 8 字节应用内存配 1 字节影子，即 +12.5%）、运行时库 | ❌ 全没有 |

⚠ **ASan 的 shadow memory 开销看起来不大（1/8），
但它的 redzone 和 quarantine 让实际开销远大于此**——
公开经验值是"内存开销 2–3 倍"（**未实测**）。
在 20 KB RAM 的 F103RB 上，**根本放不下**。

**那怎么办？四条现实的路**：

**① 在主机上把逻辑跑一遍（最重要）**

这是本章全部内容的落点：
把**不依赖硬件的算法逻辑**（链表操作、协议解析、状态机）
抽出来，在主机上编译 + 开 ASan 跑一遍。

```
裸机代码               主机测试
─────────────────────────────────
list_push()      →     clang -fsanitize=address + 单元测试
protocol_parse() →     同上
ring_buffer()    →     同上（ch10 的 rb_put/rb_get 就是这么验的）
```

[ch10](../10-interrupts/10.04-用缓冲区提速.md) 里环形缓冲的行为验证
（`put ok=63 full_reject=137 head=63 tail=0`）就是这么做的——
**主机侧跑出真数字，再搬到裸机上**。

**② 静态分析（编译器警告开满）**

```make
CFLAGS += -Wall -Wextra -Werror
CFLAGS += -Wshadow -Wconversion -Wdouble-promotion
CFLAGS += -fanalyzer          # GCC 的静态分析器（clang 用 scan-build）
```

⚠ clang 的静态分析：

```sh
scan-build clang ...          # 或者 clang --analyze
```

实测有效范围有限（查不出运行时才暴露的问题），
但**零成本**，应当常开。

**③ 自己写带检查的分配器**

裸机上的内存池能做主机侧 malloc 做不到的事：

```c
void pool_free(void *p){
    /* 范围检查：野指针变成静默忽略，而不是内存破坏 */
    if ((uintptr_t)b < (uintptr_t)g_pool ||
        (uintptr_t)b >= (uintptr_t)(g_pool + POOL_BLOCKS)) return;
    b->used = 0;
}
```

实测这个带检查的 `pool_free` 只要 **30 字节**
（[13.01](13.01-基本堆分配和释放.md)）。

还能加：

| 检查 | 做法 |
|---|---|
| **magic 字段** | 块头放 `0xA5A5A5A5`，`free` 时校验，能抓"重复释放"和"野指针" |
| **双 magic（头尾）** | 块尾也放，能抓"写越界" |
| **填充模式** | 分配时填 `0xCD`，释放时填 `0xDD`，一眼看出"用过没" |
| **分配计数** | `g_alloc_count` / `g_free_count`，不匹配就是漏了 |

——这就是"裸机版的 Valgrind"，几十行代码，
代价是**每个块多几个字节**。

**④ 填充模式查栈溢出**

[ch11](../11-linker/11.05-映射文件.md) 讲过：
上电后把栈区填成 `0xDEADBEEF`，跑一段时间后从栈顶往下扫，
找第一个不等于填充值的地址 = 栈曾经到过的最低点。

**同类思路也能用在内存池上**。

**一句话总结**：

> **裸机上没有工具，所以纪律要提前到设计阶段：
> 静态分配（可预测）+ 内存池（可检查）+ 主机侧跑逻辑（可用 ASan）。**
> 这三条加起来，覆盖率比"在板子上调试"高得多。
