# 13.2 链表

> 书：第 13 章 动态内存 · 13.2 链表（原书 p186+ 区间内）
> 上一篇：[13.1 基本堆分配和释放](13.1-基本堆分配和释放.md) ｜ 下一篇：[13.3 Valgrind](13.3-Valgrind.md)
> 对应实验：主机侧实测（1000 节点静态池 vs `malloc` 链表，内存占用与连续性对照）

## 书这一节讲什么

一句话：**链表 = 用指针把不连续的节点串起来**，插入删除 O(1)，不需要连续内存。

书上讲的是主机侧的 `malloc` 版链表。本篇补上两件书里没讲的事：

1. **实测：动态链表比静态池多占多少内存、节点有多"散"**；
2. **裸机上的替代：静态节点池 + 索引链表**（不用指针，用数组下标）。

## 一、书上的写法（malloc 版）

```c
typedef struct node { int val; struct node *next; } node_t;

node_t *list_push(node_t *head, int v){
    node_t *n = malloc(sizeof(*n));
    if (!n) return head;            /* ⚠ 别忘了检查 */
    n->val = v;
    n->next = head;
    return n;
}

void list_free(node_t *head){
    while (head) { node_t *t = head->next; free(head); head = t; }
}
```

⚠ 两个必写的检查，书上容易一笔带过：

| 检查 | 不做的后果 |
|---|---|
| `if (!n) return head;` | 分配失败 → `n->val = v` **空指针写** → 裸机 HardFault |
| `list_free` 里先存 `next` 再 `free` | `free(head)` 之后读 `head->next` = **use-after-free** |

## 二、⚠ 实测：动态链表的真实代价

**1000 个节点的对照**（主机侧，64 位）：

```
静态池  1000 节点：16000 B（= 1000 × sizeof=16，连续）
动态    1000 节点：地址跨度 18176 B（min 0x149604210 .. max 0x149608910）
  → 每节点实际占 18.2 B（含分配器开销与不对齐）

节点地址连续性（前 8 个的间距）：
  -624 -2048 16 2176 16 96 16 16
  → 有负数 = 不连续（来自不同的 size-class 区域）
```

| 指标 | 静态池 | `malloc` 链表 |
|---|---|---|
| 每节点占用 | **16.0 B** | **18.2 B**（+14%） |
| 地址连续 | ✅ 是 | ❌ **否**（间距出现 −2048、+2176） |
| 总量可预测 | ✅ 编译期确定 | ❌ 取决于分配器 |

⚠ **"间距出现负数"意味着节点在内存里是跳着放的**——
macOS 的 malloc 从不同 size-class 区域交错分配。
**后果是缓存局部性极差**：遍历链表时每次访问都是**缓存未命中**。

在有缓存的 Cortex-M7（有 I/D-Cache）上这会明显拖慢遍历；
在 F103（无缓存）上影响小，但**"不连续"本身仍然是个隐患**：
出问题时要 dump 内存看链表，节点散在各处，人工核对很痛苦。

### 2.1 malloc_good_size：小块的实际开销

```
malloc_good_size(1)   = 16 B     ← 要 1 字节给 16 字节
malloc_good_size(8)   = 16 B
malloc_good_size(16)  = 16 B
malloc_good_size(24)  = 32 B     ← ⚠ 要 24 给 32
```

⚠ **要 24 字节给 32 字节**——33% 的浪费。
链表节点如果做成 24 字节（`int val` + 指针 + 一个字段），
每个节点**白白浪费 8 字节**。

**这是个实用的设计约束**：
> 设计节点大小时，查一下 `malloc_good_size()`，
> 让 `sizeof(node_t)` 落在分配器的"整数档"上（16/32/48/64…）。

## 三、裸机上的替代：静态节点池 + 索引链表

```c
/* 不用指针，用数组下标当"指针" */
#define MAX_NODES 32
#define NULL_IDX  (-1)
typedef struct { int val; int next; } node_t;    /* next = -1 表示 NULL */
static node_t g_nodes[MAX_NODES];
static int g_free_head = 0;      /* 空闲链表头 */
static int g_used_head = -1;     /* 已用链表头 */
```

**四个好处**：

| 好处 | 说明 |
|---|---|
| **位置固定** | 全在 `.bss`，[ch11 的 map 文件](../11-linker/11.5-映射文件.md)能算出总量 |
| **无碎片** | 节点大小固定，和内存池同理 |
| **可序列化** | 整块 `g_nodes` 能直接发到上位机调试（指针做不到） |
| **可放进 Flash 的常量表** | 初始拓扑能用 `const` 数组表达 |

⚠ **关于"省 RAM"**：
在 **32 位**的 Cortex-M 上，`int` 下标和指针**都是 4 字节**，
所以"用下标省内存"**不成立**——
这条好处只在有 64 位主机的模拟代码里才成立。

真正的理由是**前三条**（固定、可序列化、可预测），不是省 RAM。

### 3.1 用 `int16_t` 下标才是真的省

节点数 ≤ 32767 时：

```c
typedef struct { int32_t val; int16_t next; } node_t;   /* 6 字节 → 对齐后 8 字节 */
```

对比指针版 `int32_t val + node_t *next` = **8 字节**（32 位）→ 一样。
但对比 **64 位主机上的模拟代码**（指针 8 字节）：8 字节 vs 16 字节，**省一半**。

⚠ 在 32 位裸机上省不了。别为了"据说省内存"去做复杂的下标转换——
**可读性优先**，除非你确实在 64 位环境下跑模拟。

## 四、链表 vs 数组：什么时候该用哪个

| 需求 | 选 | 理由 |
|---|---|---|
| 频繁在**中间**插入删除 | **链表** | O(1)（数组要搬 O(n)） |
| 频繁**按下标访问** | **数组** | O(1)（链表要 O(n) 遍历） |
| 数量固定、已知上界 | **静态数组 / 节点池** | 可预测，无碎片 |
| 元素很大，搬移昂贵 | **链表** | 只改指针 |
| 要遍历做统计 | **数组** | 缓存局部性好（实测第二节的 −2048/+2176 间距） |
| 裸机、实时 | **静态节点池** | 无 malloc，耗时有界 |

⚠ **"链表灵活所以多用"是个常见误解**。
实测表明：链表在**内存占用**（+14%）、**缓存局部性**（间距负值）、
**可调试性**（节点散落）三方面都更差。
它只在"中间插入删除频繁"这一件事上赢。

**裸机上的默认选择应该是静态数组或节点池**，
只有真的需要"中间频繁插入删除"时才上链表。

## 五、双向链表与"头节点"技巧

书上讲单向链表。两个实用补充：

| 技巧 | 作用 |
|---|---|
| **带头节点（sentinel）** | 空表和非空表用同一套代码，不用 `if (head == NULL)` 特判 |
| **双向链表** | 删除任意节点 O(1)（单向要找前驱，O(n)） |

**双向链表在裸机上的代价**：每个节点多一个指针（+4 字节）。
32 个节点多 128 字节——通常划算（换来 O(1) 删除）。

⚠ **双向链表最容易错的地方**：插入/删除时**四个指针的修改顺序**。
建议画图标好 1/2/3/4 步，或者用"先连新的、再断旧的"这个顺序。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实测是什么 |
|---|---|
| "链表节点散落没关系" | ⚠ 实测间距出现 **−2048 / +2176**，节点在内存里跳着放 → 缓存局部性差 |
| "链表省内存" | ❌ 实测每节点 **18.2 B** vs 静态池 **16.0 B**（+14%） |
| "用数组下标代替指针能省 RAM" | ⚠ **32 位裸机上不成立**（`int` 和指针都是 4 B）。真正的理由是"固定 / 可序列化 / 可预测" |
| "链表插入删除快" | 只在**中间**插入删除成立。尾部追加要遍历到尾（O(n)），除非维护尾指针 |
| "`malloc` 一个 24 B 的节点就占 24 B" | ❌ `malloc_good_size(24)` = **32 B**，浪费 33% |
| "链表比数组灵活，多用" | ⚠ 实测在内存、缓存、可调试性三方面都更差。只在"中间频繁插删"时赢 |

## 代码自测

<details>
<summary>Q1：`malloc` 出来的链表节点，实际占多少内存？</summary>

**比 `sizeof(node_t)` 多，而且节点不连续。**

**实测（主机侧，1000 个节点）**：

```
静态池  1000 节点：16000 B（= 1000 × sizeof=16，连续）
动态    1000 节点：地址跨度 18176 B
  → 每节点实际占 18.2 B

节点地址连续性（前 8 个的间距）：
  -624 -2048 16 2176 16 96 16 16
```

**两个数字各说明一件事**：

**① 每节点 18.2 B vs 16.0 B（+14%）**

多出来的是**分配器的每块开销**（chunk header、对齐填充）。
`sizeof(node_t)` = 16 B（`int` 4 + 指针 8 + 对齐填充 4），
但分配器实际划走的更多。

⚠ **这个比例在小节点上更夸张**。查 `malloc_good_size()`：

```
malloc_good_size(1)   = 16 B     ← 要 1 给 16，浪费 94%
malloc_good_size(8)   = 16 B
malloc_good_size(16)  = 16 B     ← 刚好
malloc_good_size(24)  = 32 B     ← ⚠ 要 24 给 32，浪费 33%
```

**设计建议**：
让 `sizeof(node_t)` 落在 **16 / 32 / 48 / 64** 这些档位上。
一个 24 字节的节点**不如扩成 32 字节划算**（反正都要付 32）。

**② 间距出现负数和 ±2048（不连续）**

```
  -624 -2048 16 2176 16 96 16 16
   ↑     ↑
   往回跳了
```

malloc 从不同 size-class 区域交错分配，所以**相邻两次分配的地址可能相差很远**。

**后果**：

| 影响 | 说明 |
|---|---|
| **缓存局部性差** | 遍历链表时几乎每次都是缓存未命中 |
| **Cortex-M7**（有 cache） | 遍历明显变慢 |
| **F103**（无 cache） | 性能影响小，但**可调试性变差** |

**"可调试性变差"这条在裸机上更实际**：
出问题想 dump 内存看链表时，节点散在各处，
你没法"打印从 0x20000000 开始的 16000 字节"就看到全貌。
而**静态池可以**——这也是 [ch11](../11-linker/11.5-映射文件.md)
"用 map 文件找符号地址"能直接用在静态池上的原因。

**一句话**：
> **链表的代价不是"多几个字节"，而是"失去可预测性和局部性"。
> 在裸机上，后者往往比前者贵得多。**
</details>

<details>
<summary>Q2：裸机上的"静态节点池 + 索引链表"真的更好吗？</summary>

**在"可预测性"上明显更好；在"省内存"上，32 位裸机上没有优势。**

**写法**：

```c
#define MAX_NODES 32
#define NULL_IDX  (-1)
typedef struct { int val; int next; } node_t;    /* next 是下标，不是指针 */
static node_t g_nodes[MAX_NODES];
static int g_free_head = 0;
static int g_used_head = -1;
```

**真正的好处（三条，都要实测/可验证）**：

| 好处 | 为什么重要 |
|---|---|
| **① 位置固定** | 全在 `.bss`，**map 文件里能查到 `g_nodes` 的地址和大小**，gdb 里 `x/64xw &g_nodes` 一眼看全 |
| **② 无碎片、耗时有界** | 和内存池同理（[13.1](13.1-基本堆分配和释放.md) 实测 `pool_alloc` 40 B、零依赖） |
| **③ 可整块序列化** | 调试时把 `g_nodes` 整个发到上位机。**指针版做不到**（指针值在另一台机器上没意义） |

**③在裸机调试里特别实用**：

```c
void dump_nodes(void){
    uart1_puts("idx val next\n");
    for (int i = 0; i < MAX_NODES; i++)
        uart1_printf("%3d %3d %3d\n", i, g_nodes[i].val, g_nodes[i].next);
}
```

——32 个节点全打出来，一眼看出链表哪里接错了。
指针版你得追着指针跑，还可能跑到野地址直接 HardFault。

**⚠ 但"省 RAM"这条是错的**：

| 平台 | `int` 下标 | 指针 | 谁省 |
|---|---|---|---|
| **32 位 Cortex-M** | 4 B | 4 B | **一样** |
| 64 位主机（模拟代码） | 4 B | 8 B | 下标省一半 |

**在 F103 上两者都是 4 字节**。
所以别为了"据说省内存"去做下标转换——**可读性反而变差了**
（`g_nodes[p].next` 不如 `p->next` 直观）。

**什么时候下标版真的省**：

```c
typedef struct { int32_t val; int16_t next; } node_t;   /* 节点数 ≤ 32767 */
```

`int16_t` 下标 → 节点 8 字节（对齐后）vs 指针版 8 字节——**还是一样**。
省不了。**除非你在 64 位环境下跑模拟。**

**所以判断标准**：

> **用静态节点池的理由是"固定 / 无碎片 / 可调试"，不是"省内存"。**
> 如果你的节点数量固定、有明确上界，就该用静态池；
> 如果想要"看起来省内存"而改用下标，那是误解题。

⚠ **还有一个静态池的硬约束**：**节点数上界必须编译期确定**。
如果需求是"来多少收多少，上界未知"，
那就只能动态分配（或者明确拒绝超限——嵌入式里通常选后者，返回错误）。
</details>

<details>
<summary>Q3：链表最容易出的 bug 是什么？怎么防？</summary>

**四类，按出现频率排。**

**① 忘了检查 `malloc` 返回 NULL**

```c
node_t *n = malloc(sizeof(*n));
n->val = v;            /* ⚠ 分配失败 → 空指针写 */
```

裸机上没有 `malloc`（[13.1](13.1-基本堆分配和释放.md) 实测链接失败），
但在有 RTOS 堆的环境里，`malloc` 失败是**真实可能**的。

```c
if (!n) return head;   /* 或者返回错误码 */
```

⚠ **在 Cortex-M 上写地址 0 附近**不一定 HardFault——
`0x00000000` 是 aliased 到 Flash 起始的，写它会被忽略，
**静默失败**，比崩溃更难查。

**② `free` 之后读 `next`（use-after-free）**

```c
void list_free(node_t *h){
    while (h) { free(h); h = h->next; }     /* ❌ free 之后读 h->next */
}
```

**必须先存 `next` 再 `free`**：

```c
void list_free(node_t *h){
    while (h) { node_t *t = h->next; free(h); h = t; }   /* ✅ */
}
```

实测 ASan 抓这个：

```
==44211==ERROR: AddressSanitizer: heap-use-after-free on address 0x602000000970
    #0 0x0001041cfcd4 in main uaf.c:3
SUMMARY: AddressSanitizer: heap-use-after-free uaf.c:3 in main
```

**③ 双重释放（double free）**

```c
free(p); free(p);        /* ⚠ 破坏分配器的空闲链表 */
```

实测 ASan（`-O0` 下能抓到）：

```
==44256==ERROR: AddressSanitizer: attempting double-free on 0x602000000970
    #1 0x000102a93e94 in main dbl.c:2
SUMMARY: AddressSanitizer: double-free dbl.c:2 in main
==44256==ABORTING
```

⚠ **注意**：同一份代码在 **`-O1`/`-O2` 下 ASan 抓不到**——
实测 `-O1` 的 LLVM IR 里 `malloc`/`free` 调用数是 **0**
（优化器把整个 `malloc/free` 对当死代码删掉了）。
详见 [13.4](13.4-GCC-AddressSanitizer.md)。

**对策**：`free(p); p = NULL;`——`free(NULL)` 是安全的空操作。
（但对**多个指针指向同一块**的情况无效，那要靠所有权约定。）

**④ 遍历时改了链表（迭代器失效）**

```c
for (node_t *p = head; p; p = p->next)
    if (p->val == x) list_remove(&head, p);    /* ⚠ p 已经被 free 了，p->next 是 UAF */
```

**对策**：和②一样，**先存 `next` 再处理**：

```c
for (node_t *p = head; p; ) {
    node_t *t = p->next;
    if (p->val == x) list_remove(&head, p);
    p = t;
}
```

---

**通用的三条防线**：

| 防线 | 做法 |
|---|---|
| ① **开 sanitizer 跑一遍** | ASan 实测能抓 ①②（[13.4](13.4-GCC-AddressSanitizer.md)） |
| ② **所有权约定写进注释** | "这个函数接管 `p` 的所有权，调用者不要再 `free`" |
| ③ **裸机上用静态池** | 池的 `free` 能做**范围检查**（[13.1](13.1-基本堆分配和释放.md) 实测 `pool_free` 30 B），把野指针变成静默忽略而不是内存破坏 |
</details>
