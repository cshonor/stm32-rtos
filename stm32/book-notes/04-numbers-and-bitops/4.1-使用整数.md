# 4.1 使用整数

> 书：第 4 章 数字和变量 · 4.1 使用整数（原书 p44–64 区间内）
> 下一篇：[4.2 声明变量](4.2-声明变量.md)
> 对应实验：主机侧 clang 23.1.0（macOS arm64）+ `--target=armv7m-none-eabi` 交叉校验

## 书这一节讲什么

一句话：**C 程序里最常用的是整数**，而整数在代码里有四种写法——十进制、十六进制、
八进制、（C23 起）二进制。书在这里只是告诉你"这些都能写"，没有展开陷阱。

但裸机上这一节有个书里没明说的分层：**整数在裸机代码里承担三种完全不同的角色**，
写错后缀或进制，出错的方式各不相同。

## 一、整数的三种角色（书里混在一起讲，裸机必须分开）

| 角色 | 例子 | 位模式有没有外部含义 | 写错会怎样 |
|---|---|---|---|
| **数量** | `for (int i = 0; i < 10; i++)`、延时计数 | 没有 | 算错了，逻辑不对，但不会伤硬件 |
| **地址** | `0x40010800`（GPIOA 基址） | 有（芯片手册定义） | 写到一个不存在的地址 → HardFault 或静默无效 |
| **位模式 / 掩码** | `(1u << 5)`、`0xFu << 20` | 有（寄存器位定义） | 改错引脚、覆盖别人的配置 |

判据一句话：**"这个数的位模式是不是芯片手册定义的？"**
是 → 用 `uint32_t` + `u` 后缀 + 十六进制；不是 → `int` 随便用。

## 二、四种进制，实测

```c
/* lit.c */
printf("064  = %d (八进制陷阱)\n", 064);
printf("0x64 = %d\n", 0x64);
printf("64   = %d\n", 64);
```

```
$ clang -o lit lit.c && ./lit
064  = 52 (八进制陷阱)
0x64 = 100
64   = 64
```

**`064` 不是 64，是 52。** 这个坑在裸机上的典型发作场景是写引脚号或位号：
`1u << 064` 会把第 52 位移出去（`uint32_t` 下是 UB，实测见 [4.9 溢出](4.9-溢出.md)），
结果通常是 0——你想开的那个引脚根本没开，灯不亮，且没有任何报错。

二进制字面量是 **C23** 才进标准的（GCC/clang 早就有扩展）：

```
$ clang -std=c23 -o bin_c23 bin.c && ./bin_c23
0b1010 = 10
$ clang -std=c11 -pedantic -o bin_c11 bin.c
bin.c:2:41: warning: binary integer literals are a C23 extension [-Wc23-extensions]
```

裸机代码里 `0b` 其实很好用（写寄存器配置时一眼能看出哪几位是 1），
但它会让 `-std=c11 -pedantic` 的工程报警告——工程里统一口径比好看更重要。

## 三、后缀：`u` 和 `l` 不是装饰

| 写法 | 类型 | 裸机该不该用 |
|---|---|---|
| `1` | `int` | 数量场景可以 |
| `1u` | `unsigned int` | **位操作的默认写法** |
| `1ul` | `unsigned long` | ⚠ `long` 宽度跨平台不一致（Mac 8 / Cortex-M 4），别用 |
| `1ull` | `unsigned long long` | 64 位计数才用，Cortex-M 上要两条指令 |

为什么位操作必须带 `u`：

- `1 << 31` 对 `int` 是**未定义行为**（把 1 移进符号位）；
- `1u << 31` 是**定义良好**的 `0x80000000`。

实测：`~0u = 0xffffffff`、`1u << 31 = 0x80000000`（[4.10 补码](4.10-有符号整数的补码表示.md)有展开）。

## 四、裸机里的整数长什么样（对照感）

书里这一节举的都是 PC 上的算术例子。同一件事在裸机上是这个画风：

```c
/* 数量：延时计数 */
for (volatile uint32_t i = 0; i < 800000u; i++) { }

/* 地址：寄存器 */
#define GPIOA_BASE 0x40010800u

/* 位模式：开 PA5 的时钟 + 配置 + 置位 */
#define RCC_APB2ENR (*(volatile uint32_t *)0x40021018u)
RCC_APB2ENR |= (1u << 2);          /* 数量 2 是"位号"，值 4 才是"掩码" */
```

注意最后一行：**`2` 是位号（属"数量"语义），`(1u << 2)` 才是位模式。**
把"位号"和"掩码"混用是裸机最常见的低级错误之一——
`RCC_APB2ENR |= 2` 恰好等于 `|= (1u<<1)`，开的是**另一个外设的时钟**。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "整数就是整数" | 裸机上整数有**数量 / 地址 / 位模式**三种角色，写错角色不会报错，只会静默改错硬件 |
| "`064` 就是 64" | 实测 `064 = 52`，前导 0 是八进制。位号/引脚号写成 `064` 会移出界 |
| "后缀加不加无所谓" | `1 << 31` 是 UB，`1u << 31` 是定义良好的 `0x80000000` |
| "`0b1010` 是标准 C" | C23 才进标准；`-std=c11 -pedantic` 下是 `[-Wc23-extensions]` 警告（实测） |
| "整数运算在哪个平台都一样" | 宽度不一样：Mac `long`=8、Cortex-M `long`=4（实测见 [4.5](4.5-整数的大小和表示.md)） |

## 代码自测

<details>
<summary>Q1：为什么裸机代码里写寄存器几乎不用十进制？</summary>

因为寄存器值不是"数量"，是**一组开关**。

`GPIOA_CRL` 的 bit 20–23 决定 PA5 是输入还是输出、什么速率。
这个值写成十进制 `1048576` 你完全看不出它管哪个引脚；
写成十六进制 `0x00100000` 至少能数出"第 20 位"；
写成 `0x1u << 20` 才是自解释的。

所以裸机的写法顺序是：**先造掩码，再写值**——

```c
GPIOA_CRL = (GPIOA_CRL & ~(0xFu << 20)) | (0x1u << 20);   /* 清 4 位再置 1 */
```

十进制在这里没有任何表达力优势，反而掩盖了"哪几位被改"这个唯一重要的信息。
</details>

<details>
<summary>Q2：`0b1010` 这种二进制写法，工程里到底该不该用？</summary>

看你的 `-std=` 口径。

- **能用的场合**：`-std=c23`（或 gnu 系默认宽松模式）下 `0b` 是标准写法，
  写寄存器配置位时可读性最好，实测 `0b1010 = 10`。
- **不能用的场合**：工程锁了 `-std=c11 -pedantic`，实测会报
  `binary integer literals are a C23 extension`。

折中做法（很多裸机项目采用）：**用十六进制 + 注释**，或者干脆用 `(1u<<n)` 的或运算拼：

```c
#define CFG ( (1u << 20) | (1u << 22) )   /* 自解释，且与 C 版本无关 */
```

这比 `0b` 更稳，因为位号直接出现在代码里，跟手册的位号一一对应。
</details>

<details>
<summary>Q3：位号（bit number）和掩码（mask）弄混，会发生什么？</summary>

静默地改错硬件。举个真实的：

```c
RCC_APB2ENR |= (1u << 2);   /* 正确：bit2 = IOPAEN，开 GPIOA 时钟 */
RCC_APB2ENR |= 2;           /* 错误：值 2 = bit1 = AFIOEN，开的是 AFIO */
```

两句编译都能过，运行都不报错。区别是：第一句之后 GPIOA 能工作，
第二句之后 GPIOA 的时钟没开——**在 STM32F1 上访问未开时钟的外设寄存器，
读回的是 0，写进去也不生效**，表现为"灯死活不亮，但代码看着完全正确"。

防护手段只有一个：**永远写 `(1u << n)`，绝不写裸数字。**
配合 [4.12](4.12-用位操作控制内存映射IO寄存器.md) 里的 `BIT(n)` 宏更稳。
</details>
