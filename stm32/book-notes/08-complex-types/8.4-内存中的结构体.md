# 8.4 内存中的结构体

> 书：第 8 章 复杂数据类型 · 8.4 内存中的结构体（原书 p98–118 区间内）
> 上一篇：[8.3 结构体](8.3-结构体.md) ｜ 下一篇：[8.5 访问未对齐数据](8.5-访问未对齐数据.md)
> 对应实验：主机侧 clang 23.1.0（`-O2`）+ `--target=armv7m-none-eabi` 交叉 `_Static_assert`

## 书这一节讲什么

一句话：**结构体在内存里是"按成员顺序排列 + 为满足对齐插填充"**。

这是本章最值钱的一节之一：PC 上"浪费几个字节"无所谓，
**裸机上布局错了就是写错寄存器。**

## 一、实测：同样的成员，换个顺序差 4 字节

```c
struct S1 { char a; int b; char c; };   /* 交错 */
struct S2 { int  b; char a; char c; };  /* 同样成员，换个顺序 */
struct P  { char a; int b; } __attribute__((packed));
```

```
$ clang -O2 -o st st.c && ./st
S1: size=12 off(a)=0 off(b)=4 off(c)=8
S2: size=8  off(b)=0 off(a)=4 off(c)=5
packed P: size=5 off(a)=0 off(b)=1
```

**Cortex-M3 上也是同样的数字**（编译期断言验证）：

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding -c st_arm.c
_Static_assert(sizeof(struct S1) == 12, "S1");    ← 通过
_Static_assert(sizeof(struct S2) == 8,  "S2");    ← 通过
_Static_assert(sizeof(struct P)  == 5,  "P");     ← 通过
_Static_assert(offsetof(struct S1, b) == 4, "");  ← 通过
```

## 二、`S1` 的布局画出来

```
S1（12 字节，成员实际只占 6 字节）：
  偏移 0:      a (char, 1 字节)
  偏移 1..3:   【填充 3 字节】 ← int b 必须 4 字节对齐，不能放偏移 1
  偏移 4..7:   b (int)
  偏移 8:      c (char, 1 字节)
  偏移 9..11:  【尾部填充 3 字节】 ← 保证数组里下一个元素的 b 仍然对齐
  ─────────────
  总计 12 字节（6 字节是填充，占 50%）
```

规则只有两条：

1. **每个成员必须落在"自身对齐值"的整数倍地址上**（`int` 要 4 字节对齐）；
2. **结构体总大小是最大成员对齐值的整数倍**（否则数组第二个元素就错位了）。

`S2` 把 `int` 放最前面，`a`、`c` 两个 char 紧跟着占 4..5，
尾部填充只需 2 字节 → 总共 8。

**经验**：成员按"对齐值从大到小"排列，通常最省空间。

## 三、`packed`：省空间，但代价大

```c
struct P { char a; int b; } __attribute__((packed));   /* size=5，b 在偏移 1 */
```

`b` 在偏移 1 —— **未对齐的 32 位访问**。后果见 [8.5](8.5-访问未对齐数据.md)：

| 内核 | 未对齐 32 位访问 |
|---|---|
| **Cortex-M0 / M0+** | ❌ **HardFault** |
| Cortex-M3 / M4 | 支持（慢，且不保证原子） |
| x86 / arm64 | 无感 |

所以：

- **寄存器结构体绝不能加 `packed`**（它本来就该是自然对齐的 `uint32_t` 序列）；
- 协议解析要用 `packed` 时，**只用来算偏移，不直接解引用**
  （改用按字节拼装，见 [8.5](8.5-访问未对齐数据.md)）。

## 四、裸机上为什么这一节致命

如果你手写的寄存器结构体布局与手册**差一个字节**：

```c
/* 假设成员顺序写错了：ODR 和 IDR 写反 */
typedef struct { volatile uint32_t CRL, CRH, ODR, IDR, ... } wrong_t;
```

那么 `GPIOA->IDR` 实际访问的是 `ODR` 的地址——
**读引脚读成了读输出寄存器**，值看起来"很像对的"（都是 0/1），
于是 bug 能潜伏很久。

防护只有一条：**每个寄存器结构体都配 `_Static_assert(offsetof(...))`**（[8.3](8.3-结构体.md) Q2）。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "结构体大小 = 成员大小之和" | ❌ 实测 `S1{char,int,char}` = **12**，成员只占 6（50% 是填充） |
| "成员顺序随便排" | 顺序直接决定大小：实测 `S1`=12 vs `S2`=8 |
| "`packed` 省空间，多用" | M0/M0+ 上会**未对齐访问 HardFault**；M3 慢。寄存器结构体禁用 |
| "对齐规则各平台一样" | 基本一样，但**不能假设**：用 `_Static_assert` 钉死你要的数字 |
| "尾部填充无所谓" | 它影响 `sizeof`，进而影响数组/缓冲区的大小计算 |

## 代码自测

<details>
<summary>Q1：为什么 `struct S1 {char,int,char}` 是 12 而 `S2 {int,char,char}` 是 8？</summary>

因为**对齐要求在每个成员之间插入了填充字节**。实测（Mac 和 Cortex-M3 都是这个数）：

```
S1: size=12  off(a)=0 off(b)=4 off(c)=8
S2: size=8   off(b)=0 off(a)=4 off(c)=5
```

`S1` 的布局：

```
0:      a (1 字节)
1..3:   填充 3 字节     ← b 是 int，必须 4 字节对齐，不能放偏移 1
4..7:   b
8:      c (1 字节)
9..11:  尾部填充 3 字节  ← 保证 S1[1].b 依然对齐到 4
──────────
12 字节
```

`S2`（`int` 在前）：

```
0..3:   b
4:      a
5:      c
6..7:   尾部填充 2 字节  ← 总大小必须是 4（最大对齐值）的倍数
──────────
8 字节
```

规律：**把对齐要求大的成员放前面，填充就少。**
需要省 RAM 时（裸机永远需要），按"对齐值降序"排列成员：

```c
struct good { uint32_t a; uint16_t b; uint8_t c; uint8_t d; };   /* 8 字节，无浪费 */
struct bad  { uint8_t c; uint32_t a; uint8_t d; uint16_t b; };   /* 12 字节 */
```

不过要注意：**寄存器结构体的成员顺序必须按手册，不能为了省空间重排**——
那里"正确"压倒一切（这类结构体也不占 RAM，它映射的是 MMIO 地址）。
</details>

<details>
<summary>Q2：`packed` 到底能不能用？</summary>

能用，但要分清**两种用途**：

**用途 A：映射寄存器块 → ❌ 禁用 `packed`**

寄存器块本来就是自然对齐的 32 位序列，`packed` 只会帮倒忙
（可能让编译器生成字节访问，而 32 位寄存器**必须**用 32 位访问）。

**用途 B：描述协议帧格式 → ✅ 可以，但别直接解引用**

```c
typedef struct { uint8_t sync; uint32_t len; uint16_t crc; }
    __attribute__((packed)) frame_t;

/* ❌ 别这样：rx_buf 可能不对齐，M0 上直接 HardFault */
frame_t *f = (frame_t *)rx_buf;
uint32_t n = f->len;

/* ✅ 用 offsetof 算偏移 + 按字节读取 */
size_t off_len = offsetof(frame_t, len);        /* packed 布局的偏移是正确的 */
uint32_t n = read_le32(rx_buf + off_len);       /* 任何对齐都安全 */
```

这样既拿到了 `packed` 的"布局可计算"的好处，又避开了未对齐访问。

**用途 C：省 RAM 的大型数据结构 → ⚠ 谨慎**

省了 RAM，但每次访问未对齐成员都要多条指令（M3）或 HardFault（M0）。
20 KB RAM 上，通常"按对齐值排序成员"比 `packed` 更划算（省得差不多，没有副作用）。
</details>

<details>
<summary>Q3：怎么验证我手写的寄存器结构体布局是对的？</summary>

三层验证，从编译期到运行期：

**① 编译期：`offsetof` + `_Static_assert`（必须做）**

```c
#include <stddef.h>
_Static_assert(offsetof(GPIO_TypeDef, CRL)  == 0x00u, "");
_Static_assert(offsetof(GPIO_TypeDef, IDR)  == 0x08u, "");
_Static_assert(offsetof(GPIO_TypeDef, BSRR) == 0x10u, "");
_Static_assert(sizeof(GPIO_TypeDef)         == 0x1Cu, "");
```

改定义的那一刻如果不符，编译直接失败并给出期望值——零成本、100% 覆盖。

**② 打印出来核对（调试期一次）**

```c
printf("off(BSRR)=%zu size=%zu\n", offsetof(GPIO_TypeDef, BSRR), sizeof(GPIO_TypeDef));
```

和手册的 "Register map" 表逐行对照。有串口后（[9.5 串口 Hello World](../09-uart-serial/9.5-串口HelloWorld.md)）很容易做。

**③ 真机验证（最有说服力）**

用调试器读寄存器的**实际地址**，和你通过结构体访问的地址对比：

```
(gdb) p/x &GPIOA->BSRR
$1 = 0x40010810          ← 应该等于手册里的 GPIOA_BSRR 地址
```

或者写个自检：往 `BSRR` 写值，然后从**裸地址**读回，看是否一致。

一句话：**编译期断言是主力，它把"和手册对不上"变成编译错误；
真机验证只在第一次移植新芯片时做一次。**
</details>
