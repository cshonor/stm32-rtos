# 8.07 结构体赋值

> 书：第 8 章 复杂数据类型 · 8.07 结构体赋值（原书 p98–118 区间内）
> 上一篇：[8.06 结构体初始化](8.06-结构体初始化.md) ｜ 下一篇：[8.08 结构体指针](8.08-结构体指针.md)
> 对应实验：`--target=armv7m-none-eabi -ffreestanding`（`-O0` / `-Os` / `-O2` 三档 + `llvm-nm -u`）

## 书这一节讲什么

一句话：**结构体可以用 `=` 整体赋值**：`a = b;` 会逐成员拷贝。

书把它当作方便的语法。裸机上它的代价是**真实的**：
大结构体的赋值会变成 `memcpy` 调用，占 Flash、占栈、花时间。

## 一、实测：编译器什么时候生成 `memcpy`

```c
typedef struct { unsigned a[64]; } big_t;      /* 256 字节 */
extern big_t g1, g2;
void f(void){ g1 = g2; }
void h(unsigned char *d, const unsigned char *s, unsigned n){ __builtin_memcpy(d, s, n); }
```

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding -Os -c memcpy2.c
$ llvm-nm -u m.o
         U __aeabi_memcpy
         U __aeabi_memcpy4

（-O0 / -Os / -O2 三档都会生成，实测）
```

而**小结构体不生成**——编译器内联成几条 `ldr`/`str`：

```c
typedef struct { unsigned a[2]; } small_t;     /* 8 字节 */
extern small_t s1, s2;
void g(void){ s1 = s2; }     /* 无 U 符号，内联展开 */
```

**判据**：成员的字节数少（通常 ≤ 16 字节）→ 内联；多 → 调 `memcpy`。

## 二、`memcpy` 调用的三个代价

| 代价 | 说明 |
|---|---|
| **Flash** | `__aeabi_memcpy` 被链接进来，占几百字节 |
| **栈** | 调用本身要一帧（虽然小） |
| **时间** | 函数调用 + 循环拷贝，比内联的几条 `ldr/str` 慢 |
| **额外坑** | `__aeabi_memset(s, n, c)` 参数顺序和标准 `memset(s, c, n)` **相反** |

最后一条是纯粹的坑（[6.05](../06-arrays-pointers-strings/6.05-字符和字符串.md)）：
照抄标准签名实现会导致"内存被填成了长度值"。

## 三、裸机上的替代写法

**① 大结构体：用指针传递，别拷贝**

```c
/* ❌ 按值传/返回大结构体 */
void handle(big_t pkt);
big_t make(void);

/* ✅ 传指针 */
void handle(const big_t *pkt);
void make(big_t *out);
```

**② 需要拷贝时显式调用，别隐式**

```c
memcpy(&dst, &src, sizeof dst);       /* 意图明确，且你能看到它 */
```

**③ 寄存器结构体：绝不整体赋值**（[8.06](8.06-结构体初始化.md) Q3）

```c
GPIOA->CRL &= ~(0xFu << 20);          /* 逐字段、位操作 */
```

## 四、赋值的"逐成员"语义与 `volatile`

```c
typedef struct { volatile uint32_t a, b; } regs_t;
regs_t *p = ...;
*p = (regs_t){ .a = 1, .b = 2 };      /* 依次写 a、b —— 两次硬件写 */
```

对 MMIO 结构体来说，**赋值 = 依次写每个寄存器**，中间没有原子性保证。
这也是寄存器结构体不该整体赋值的原因之一。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "结构体赋值很方便" | 大结构体变成 `memcpy` 调用（实测 `U __aeabi_memcpy`，三档优化都有） |
| "`a = b` 是原子的" | 不是。逐成员/逐字节拷贝，可被打断 |
| "赋值很便宜" | 大结构体：函数调用 + 循环，比内联慢 |
| "不写 `memcpy` 就不用管" | 编译器会隐式生成（实测） |
| "MMIO 结构体也能整体赋值" | ❌ 会写到锁定位/保留位（[8.06](8.06-结构体初始化.md)） |

## 代码自测

<details>
<summary>Q1：为什么"我没写 memcpy，链接器却找我要 `__aeabi_memcpy`"？</summary>

因为**编译器替你生成了对它的调用**。

实测（`typedef struct { unsigned a[64]; } big_t; void f(void){ g1 = g2; }`）：

```
$ clang ... -ffreestanding -Os -c memcpy2.c && llvm-nm -u m.o
         U __aeabi_memcpy
         U __aeabi_memcpy4
```

触发条件只有一个：**拷贝的数据量大到"内联展开不划算"**。
小结构体（≤ 几个字）被内联成 `ldr`/`str` 序列，不产生符号。

这个"阈值"是编译器的内部决策，所以表现为**时有时无**：
"我什么都没改，加了个字段就链接不过了"——
其实是结构体越过阈值，编译器改用库调用了。

应对方式二选一：

**A. 提供实现**（裸机最小 C 运行时的一部分）：

```c
void *memcpy(void *d, const void *s, size_t n){ /* 字节/字循环 */ }
void __aeabi_memcpy (void *d, const void *s, size_t n){ memcpy(d, s, n); }
void __aeabi_memcpy4(void *d, const void *s, size_t n){ memcpy(d, s, n); }
void __aeabi_memset (void *s, size_t n, int c){ memset(s, c, n); }  /* ← 参数顺序相反 */
```

**B. 避免大结构体的整体赋值/传参**：改成传指针，
或者用 `for` 循环逐字段拷贝（这样你能在代码里看见代价）。

推荐 **B**：裸机上"隐式的大块内存操作"都应该变成显式的。
</details>

<details>
<summary>Q2：结构体赋值是原子的吗？中断来了会怎样？</summary>

**不是原子的**——它是逐成员（甚至逐字节）的拷贝。

```c
typedef struct { uint32_t a; uint32_t b; uint16_t c; } state_t;
volatile state_t g_state;

/* 主循环里 */
g_state = new_state;     /* 写 a → 写 b → 写 c，三步 */

/* ISR 里 */
uint32_t x = g_state.a;  /* 可能读到"新 a + 旧 b"的混合状态 */
```

后果：ISR 读到"半新半旧"的数据（**撕裂读**，torn read）。
如果 `a` 和 `b` 有内在一致性要求（比如"长度"和"校验和"），就会出错。

三种解法：

**① 临界区**（最简单）

```c
__disable_irq();  g_state = s;  __enable_irq();     /* 写期间关中断 */
```

**② 双缓冲 + 原子切换**

```c
static state_t buf[2];
static volatile uint8_t active;      /* 0 或 1 */

/* 写：先写"不活跃"的那份，再切换指针 */
state_t *inactive = &buf[active ^ 1];
*inactive = s;
active ^= 1;                          /* 一条字节写 = 原子 */
```

**③ 序列号（seqlock 思路）**

```c
typedef struct { uint32_t seq; state_t s; } guarded_t;
/* 写：seq++(奇) → 写 s → seq++(偶)
   读：读 seq，若为奇就重试 */
```

裸机上最常用的是 ①（临界区）——
除非数据结构很大或 ISR 很频繁（关中断太久会影响实时性），那就用 ②。
</details>

<details>
<summary>Q3：`a = b` 和 `memcpy(&a, &b, sizeof a)` 有区别吗？</summary>

语义上基本等价（都是逐字节拷贝），但有三点差别：

**① 类型检查**
`a = b` 要求 `a` 和 `b` **同类型**（编译器会检查）；
`memcpy` 只看地址和字节数，**类型不匹配也不报错**。

```c
struct A { int x; } a;  struct B { int y; } b;
a = b;                            /* ❌ 编译错误：类型不匹配（好事） */
memcpy(&a, &b, sizeof a);         /* ✅ 编译通过，但语义可疑 */
```

**② 填充字节（padding）**
`a = b` 允许编译器**只拷贝有效成员**（填充内容未定义）；
`memcpy` 会拷贝**包括填充在内的所有字节**。

这在比较操作上有实际影响：

```c
memcmp(&a, &b, sizeof a) == 0      /* ❌ 不可靠：填充字节可能是垃圾值 */
```

所以**结构体不要用 `memcmp` 比较**，要逐成员比（[8.04](8.04-内存中的结构体.md) 讲过填充）。

**③ 生成的代码**
小结构体：两者都被内联；
大结构体：`a = b` 可能生成 `__aeabi_memcpy` 调用（实测），
`memcpy` 也是——但**至少你在代码里看得见**。

裸机上的建议：

| 场景 | 用 |
|---|---|
| 同类型、小结构体 | `a = b`（清楚、有类型检查） |
| 需要"看得见的拷贝" | `memcpy`（意图显式） |
| **MMIO 结构体** | **都别用** ——逐个字段位操作 |
</details>
