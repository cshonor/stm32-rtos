# 8.14 函数指针与 typedef

> 书：第 8 章 复杂数据类型 · 8.14 函数指针与 typedef（原书 p98–118 区间内）
> 上一篇：[8.13 typedef](8.13-typedef.md) ｜ 下一篇：[8.15 typedef 和 struct](8.15-typedef和struct.md)
> 对应实验：主机侧（函数地址/`sizeof`）+ Cortex-M 交叉（`-O0` / `-Os` 反汇编对照）

## 书这一节讲什么

一句话：**函数指针要用 `typedef` 命名**，否则声明没人看得懂。

这是 `typedef` **唯一不可替代**的场景。
而在裸机上，函数指针的重要性比 PC 上高得多——
**Cortex-M 的向量表本身就是一个函数指针数组**。

## 一、为什么非 typedef 不可

```c
/* 不 typedef：一个"接受函数指针、返回函数指针"的声明 */
void (*(*signal(int, void (*)(int)))(int))(int);

/* typedef 之后 */
typedef void (*sighandler_t)(int);
sighandler_t signal(int, sighandler_t);
```

第一行不是段子——它是 POSIX `signal` 的真实声明。
**裸机上会写出同类的东西**：回调注册表、驱动操作表、状态机的转移表。

```c
typedef void (*uart_rx_cb_t)(const uint8_t *buf, unsigned len, void *ctx);
typedef int  (*dev_read_t)(void *dev, uint8_t *dst, unsigned n);
```

## 二、实测：函数指针就是函数的入口地址

```c
int add(int a,int b){return a+b;}
int sub(int a,int b){return a-b;}
typedef int (*binop_t)(int,int);
binop_t fp = add;
printf("fp=%p add=%p fp(3,4)=%d\n", (void*)fp, (void*)add, fp(3,4));
fp = sub;
printf("after fp=sub: fp(3,4)=%d sizeof(fp)=%zu\n", fp(3,4), sizeof(fp));
```

```
$ clang -O2 -o pr pr.c && ./pr
fp=0x100d1be44 add=0x100d1be44 fp(3,4)=7
after fp=sub: fp(3,4)=-1 sizeof(fp)=8
```

两个结论：

1. **`fp` 打印出来的值和 `add` 的地址完全相同**——函数指针没有额外间接层，
   它就是入口地址本身；
2. 改指向 `sub` 之后，同一个调用点 `fp(3,4)` 得到 `-1`——
   **这就是"运行时多态"的全部机制**；
3. `sizeof(fp)=8` 是 Mac/arm64 的指针大小（Cortex-M 上是 4）。

## 三、实测：间接调用生成的是 `blx`，直接调用是 `bl`

```c
int via_fp(binop_t f, int x, int y){ return f(x, y); }
int direct(int x, int y){ return add(x, y); }
```

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding -O0 -c sp2.c
000000a0 <via_fp>:
      a0: b580    push {r7, lr}
      a2: b084    sub  sp, #0x10
      ...
      b0: 4790    blx  r2              ← 间接调用：寄存器里存地址
      b2: b004    add  sp, #0x10
      b4: bd80    pop  {r7, pc}

$ ... -Os -c sp2.c
00000016 <via_fp>:
      16: 4603    mov  r3, r0
      18: 4608    mov  r0, r1
      1a: 4611    mov  r1, r2
      1c: 4718    bx   r3             ← 尾调用：直接跳过去，连 lr 都不压

0000001e <direct>:                    ← direct 被内联了
      1e: 4408    add  r0, r1
      20: 4770    bx   lr
```

对照：

| 调用方式 | `-O0` | `-Os` |
|---|---|---|
| 直接调用 `add(x,y)` | `bl add` | **被内联**，一条 `add r0,r1` |
| 通过函数指针 `f(x,y)` | `blx r2` | `bx r3`（尾调用） |

**代价很实在**：

1. **间接调用无法内联**——编译器不知道 `f` 指向谁；
2. 多一次寄存器装载 + `blx`（比 `bl` 稍慢）；
3. **压栈**：`-O0` 下 `via_fp` 栈用量 24 B（`.su` 实测），而 `direct` 是 16 B。

## 四、裸机上的三个用途

**① 向量表（本质就是函数指针数组）**

```c
typedef void (*isr_t)(void);
__attribute__((section(".isr_vector"), used))
static const isr_t vector_table[] = {
    (isr_t)(&_estack),      /* 0: 初始 SP */
    reset_handler,          /* 1: Reset */
    nmi_handler,            /* 2: NMI */
    hardfault_handler,      /* 3: HardFault */
    ...
};
```

ch03 实测过向量表前几项的内容——**它们就是函数入口地址**
（而且是带 Thumb 位的，见下）。

**② 驱动 / 设备表（同一套接口，换板子只换表）**

```c
typedef struct {
    void (*init)(void);
    int  (*read)(uint8_t *dst, unsigned n);
    int  (*write)(const uint8_t *src, unsigned n);
} dev_ops_t;

static const dev_ops_t uart0_ops = { uart0_init, uart0_read, uart0_write };
static const dev_ops_t usb_ops   = { usb_init,   usb_read,   usb_write   };

const dev_ops_t *g_dev = &uart0_ops;     /* 换介质：改这一行 */
g_dev->write(buf, n);
```

这就是裸机上的"面向对象"——[17.1 模块设计](../17-modular-programming/17.1-模块设计.md) 会展开。
**Linux 的 `struct file_operations` 就是这套东西的终极形态。**

**③ 回调（ISR 通知上层）**

```c
typedef void (*uart_rx_cb_t)(const uint8_t *buf, unsigned len, void *ctx);

static uart_rx_cb_t g_rx_cb;
static void *g_rx_ctx;

void uart_set_rx_callback(uart_rx_cb_t cb, void *ctx){ g_rx_cb = cb; g_rx_ctx = ctx; }

/* ISR 里：
   if (g_rx_cb) g_rx_cb(frame, len, g_rx_ctx);   ← ch10：回调里不能做耗时的事 */
```

## 五、⚠ Cortex-M 的两个坑

**① Thumb 位**

Cortex-M 只执行 Thumb 指令集，函数指针的**最低位必须是 1**。
正常取函数地址时编译器会处理好（实测 `fp` 的值和 `add` 的地址一致，
打印出来的地址已经带了 Thumb 位）。

但**手写地址常量当函数指针**就会踩坑：

```c
isr_t h = (isr_t)0x08000100;     /* ❌ 最低位是 0 → 触发 HardFault（试图切 ARM 状态） */
isr_t h = (isr_t)0x08000101;     /* ✅ +1 */
```

ch03 实测的向量表项就是 `+1` 的（`0x080000B5` 这种奇数地址）——
**那个奇数不是巧合，是 Thumb 位。**

**② 空指针必须检查**

```c
if (g_rx_cb) g_rx_cb(buf, len, ctx);    /* 没注册的回调 = 跳到 0 地址 */
```

Flash 里的向量表也一样：如果某一项是 0 且那个中断发生了，
CPU 会跳到 0 地址——**现象是 HardFault，而不是"没反应"**。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "函数指针有个间接层" | 实测 `fp` 打印值 **== `add` 的地址**，就是入口地址本身 |
| "函数指针调用和直接调用差不多快" | 实测 `-O0` 下间接是 `blx r2`、**无法内联**；直接调用 `-Os` 被内联成一条 `add` |
| "函数指针不占栈" | 实测 `-O0` `.su`：`via_fp` 24 B vs `direct` 16 B |
| "函数地址就是地址" | Cortex-M 上**最低位必须是 1（Thumb 位）**。手写常量要 `+1`（ch03 实测向量表项是奇数） |
| "回调没注册时调用会没事" | 跳到地址 0 → **HardFault**。必须 `if (cb)` |
| "typedef 只是好看" | 对函数指针而言**不是**：`void (*(*signal(int, void(*)(int)))(int))(int)` 没人看得懂 |

## 代码自测

<details>
<summary>Q1：函数指针在裸机上有什么不可替代的用途？</summary>

三个，按重要性：

**① 向量表（这是硬件要求的，不是可选的设计）**

Cortex-M 复位后从 `0x00000000`（或重映射到 `0x08000000`）读两张表项：
初始 SP 和 Reset 入口，之后每个异常都按索引跳到表里存的地址。
**那张表就是一个函数指针数组。**

```c
typedef void (*isr_t)(void);
__attribute__((section(".isr_vector"), used))
static const isr_t vector_table[] = { (isr_t)&_estack, reset_handler, nmi_handler, ... };
```

ch03 实测过表里的内容——`0x080000B5` 这样的**奇数**地址，
最低位 1 就是 Thumb 位（见 Q3）。

**② 驱动 / 设备操作表（换硬件只换表）**

```c
typedef struct {
    void (*init)(void);
    int  (*read)(uint8_t *dst, unsigned n);
    int  (*write)(const uint8_t *src, unsigned n);
} dev_ops_t;

const dev_ops_t *g_dev = &uart0_ops;    /* 换成 USB：只改这一行 */
g_dev->write(buf, n);
```

上层代码再也看不到 `USART1->DR` 这种具体寄存器。
这既是**可移植性**，也是**可测试性**（主机上塞一个 mock 表就能跑单元测试）。

**③ 回调（ISR 通知上层）**

```c
typedef void (*uart_rx_cb_t)(const uint8_t *buf, unsigned len, void *ctx);
void uart_set_rx_callback(uart_rx_cb_t cb, void *ctx);
/* ISR: if (g_rx_cb) g_rx_cb(frame, len, g_rx_ctx); */
```

这个模式的价值是把**"硬件层"和"业务层"解耦**：
`uart.c` 不需要知道收到一帧之后要干什么。

⚠ 注意：回调是在**中断上下文**执行的，
所以里面不能 `printf`、不能加锁、不能做耗时的事（[10.3 中断例程](../10-interrupts/10.3-中断例程.md)）。
</details>

<details>
<summary>Q2：函数指针调用的代价有多大？值得为此放弃抽象吗？</summary>

实测数据说话：

```
-O0：via_fp  → blx r2（间接调用，栈 24 B）
     direct  → 内联/直接调用（栈 16 B）
-Os：via_fp  → bx r3（尾调用，栈 0 B）
     direct  → 被内联成一条 add r0, r1
```

代价有三项：

| 项 | 直接调用 | 函数指针 |
|---|---|---|
| 能否内联 | ✅ 能（实测 `-Os` 下 `direct` 被完全内联） | ❌ **不能**（编译器不知道指向谁） |
| 指令 | `bl` | `blx`（多一次寄存器装载） |
| 栈（`-O0`） | 16 B | 24 B |

**值不值？分场景：**

| 场景 | 结论 |
|---|---|
| 向量表 | **硬件要求**，没得选 |
| 驱动操作表（每次 I/O 调一次） | **值得**。I/O 本身是毫秒/微秒级，一条 `blx` 是纳秒级 |
| 回调（每帧一次） | **值得**，同上 |
| 每字节都调一次的函数指针（比如 `putc`） | ❌ 不值。热路径上要么内联、要么直接调 |
| 中断里的高频路径 | ⚠ 谨慎。中断要求快，间接调用的额外开销占比会变高 |

**工程判据**：看调用频率。
- **每事件/每帧/每包**调一次 → 用函数指针，可读性和可移植性的收益远大于几纳秒；
- **每字节/每像素**调一次 → 别用，改成宏或直接调用。

**另外别忽略一个反向收益**：函数指针让驱动可以被**替换成 mock**，
从而能在主机上跑单元测试。这个收益在裸机项目里往往比那几纳秒重要得多。
</details>

<details>
<summary>Q3：Cortex-M 上函数指针为什么要 "+1"？什么时候会踩到？</summary>

因为 **Thumb 位**。

Cortex-M 只支持 Thumb 指令集（没有 ARM 状态）。
硬件规定：**跳转时目标地址的最低位为 1 表示 Thumb 代码**。
（最低位是 0 意味着"切到 ARM 状态"，而 Cortex-M 没有这个状态 → **HardFault / 用法错误**。）

关键点：**这一位是地址的一部分，不是对齐位。**
函数实际入口在偶数地址 `0x08000100`，但函数指针的值是 `0x08000101`。

**什么时候编译器帮你处理**：

```c
isr_t h = reset_handler;       /* ✅ 编译器自动置位 */
```

实测 `fp` 打印出来和 `add` 的地址完全一致——取函数地址时编译器会带上 Thumb 位。

**什么时候会踩坑——手写地址常量**：

```c
isr_t h = (isr_t)0x08000100;   /* ❌ 最低位 0 → 跳过去就 HardFault */
isr_t h = (isr_t)0x08000101;   /* ✅ */
```

典型现场：

1. **手写向量表**（ch03 实测的表项是 `0x080000B5` 这种奇数——就是这个位）；
2. **bootloader 跳转到 APP**：
   ```c
   uint32_t app_entry = *(volatile uint32_t *)(APP_BASE + 4);   /* 从 APP 向量表读，已带 Thumb 位 */
   ((isr_t)app_entry)();          /* ✅ 别自己再 +1，也别把它对齐掉 */
   ```
3. **从调试器/日志里抄地址**——日志打印的地址通常已带 Thumb 位，
   再 `+1` 就错了。

**规则**：

- 从**函数**取地址 → 编译器处理，别管；
- 从**向量表**读地址 → 表里本来就带位，别改；
- **手写常量** → 必须 `| 1`；
- 做地址运算前先**清掉**最低位：`addr & ~1u`，算完再 `| 1`。

一个记忆点：**在 Cortex-M 上看到奇数地址，先想到 Thumb 位，不要当成"地址错了"。**
</details>
