# 8.8 结构体指针

> 书：第 8 章 复杂数据类型 · 8.8 结构体指针（原书 p98–118 区间内）
> 上一篇：[8.7 结构体赋值](8.7-结构体赋值.md) ｜ 下一篇：[8.9 结构命名](8.9-结构命名.md)
> 对应实验：`--target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding`（`-O0` / `-Os` / `-O2` + `-fstack-usage`）

## 书这一节讲什么

一句话：**用指针访问结构体成员要写 `p->m`，它是 `(*p).m` 的语法糖**。

书讲到这里基本是"语法课"。但在裸机上这一节有两件必须钉死的事：

1. **`->` 是零成本的**——不是"稍微方便一点"，是**生成完全相同的机器码**；
2. **结构体传参必须传指针**——传值的代价在 `-O0` 下是**栈用量的 28 倍**（实测 112 B vs 4 B）。

## 一、实测：`->`、`(*p).`、裸地址三种写法机器码完全相同

```c
typedef struct { volatile uint32_t CRL, CRH, IDR, ODR, BSRR, BRR, LCKR; } GPIO_TypeDef;
#define GPIOA ((GPIO_TypeDef *)0x40010800u)

void via_arrow (void){ GPIOA->BSRR = (1u<<5); }        /* ① 结构体指针 */
void via_deref (void){ (*GPIOA).BSRR = (1u<<5); }      /* ② 解引用再取成员 */
void via_offset(void){ *(volatile uint32_t *)(0x40010800u + 0x10u) = (1u<<5); }  /* ③ 裸地址 */
```

```
$ clang --target=armv7m-none-eabi -mcpu=cortex-m3 -mthumb -ffreestanding -Os -c sp.c
$ llvm-objdump -d sp_Os.o
00000000 <via_arrow>:
       0: f640 0010     movw  r0, #0x810
       4: f2c4 0001     movt  r0, #0x4001
       8: 2120          movs  r1, #0x20
       a: 6001          str   r1, [r0]
       c: 4770          bx    lr
0000000e <via_deref>:
       e: f640 0010     movw  r0, #0x810        ← 一模一样
      12: f2c4 0001     movt  r0, #0x4001
      16: 2120          movs  r1, #0x20
      18: 6001          str   r1, [r0]
      1a: 4770          bx    lr
0000001c <via_offset>:
      1c: f640 0010     movw  r0, #0x810        ← 还是一模一样
      ...
```

`-O0` / `-Os` / `-O2` 三档都是这个结果。

**结论：三种写法在机器层面没有区别，`->` 纯粹是给人看的。**
编译器在编译期就把"基址 0x40010800 + 成员偏移 0x10"算成了常量 `0x40010810`，
然后 `movw/movt` 装进寄存器、一条 `str` 写出去。

所以选 `->` 的理由**只有可读性和可校验性**（见 [8.12](8.12-结构体与嵌入式编程.md)），
不存在任何性能顾虑——这是本节能给出的最有价值的结论。

## 二、实测：结构体传值 vs 传指针（栈用量差 28 倍）

```c
typedef struct { uint32_t v[16]; } huge_t;            /* 64 字节 */
uint32_t huge_by_value(huge_t s)      { return s.v[0] + s.v[15]; }
uint32_t huge_by_ptr(const huge_t *s) { return s->v[0] + s->v[15]; }
```

```
$ clang ... -fstack-usage -c sp2.c
== -O0 ==
sp2.c:4:huge_by_value   112   static      ← 112 字节
sp2.c:5:huge_by_ptr       4   static      ←   4 字节
== -Os ==
sp2.c:4:huge_by_value     0   static
sp2.c:5:huge_by_ptr       0   static
```

`-O0` 下传值版的栈用量是传指针版的 **28 倍**。看反汇编就知道钱花在哪：

```
00000000 <huge_by_value>:                 -O0
       0: e92d 4ff0     push.w {r4-r11, lr}       ← 9 个寄存器，36 字节
       4: b093          sub    sp, #0x4c          ← 再开 76 字节
       6: 9002          str    r0, [sp, #0x8]
       ...（共约 40 条指令，把 16 个成员从调用者的栈区搬到自己的栈帧）
      6a: b013          add    sp, #0x4c
      6c: e8bd 8ff0     pop.w  {r4-r11, pc}

00000070 <huge_by_ptr>:                   -O0
      70: b081          sub    sp, #0x4           ← 4 字节
      72: 9000          str    r0, [sp]
      74: 9900          ldr    r1, [sp]
      76: 6808          ldr    r0, [r1]
      78: 6bc9          ldr    r1, [r1, #0x3c]    ← 直接用偏移 0x3c
      7a: 4408          add    r0, r1
      7c: b001          add    sp, #0x4
      7e: 4770          bx     lr                 ← 7 条指令
```

`-Os` 下两边都是 0——**但别高兴太早**：

```
00000000 <huge_by_value>:                 -Os
       0: 990b          ldr    r1, [sp, #0x2c]    ← 从"调用者的栈"读，不是自己的帧
       2: 4408          add    r0, r1
       4: 4770          bx     lr
```

`0` 只是因为**调用者**替它把 64 字节复制到了栈上（AAPCS：超过 4 个字的结构体通过内存传递）。
栈照样被吃掉 64 字节，只是账记在了调用者头上——`-fstack-usage` 看不见。

**这就是裸机上最危险的错觉**：`.su` 报 0，你以为不要钱，
实际上每次调用都在栈上搬 64 字节。

## 三、小结构体（≤ 16 字节）走寄存器，可以传值

```c
typedef struct { uint32_t a,b,c,d; } big_t;          /* 16 字节 = 4 个字 */
uint32_t by_value(big_t s)      { return s.a+s.b+s.c+s.d; }
uint32_t by_ptr(const big_t *s) { return s->a+s->b+s->c+s->d; }
```

```
-Os：
0000002a <by_value>:
      2a: 4408   add r0, r1      ← 4 个成员分别装在 r0..r3，不需要栈
      2c: 4410   add r0, r2
      2e: 4418   add r0, r3
      30: 4770   bx  lr

00000032 <by_ptr>:
      32: e890 000e  ldm.w r0, {r1, r2, r3}   ← 一条多寄存器加载
      36: 68c0       ldr   r0, [r0, #0xc]
      38: 4411   add r1, r2
      3a: 4419   add r1, r3
      3c: 4408   add r0, r1
      3e: 4770   bx  lr
```

AAPCS 规定前 4 个字用 `r0..r3` 传。所以：

| 结构体大小 | 传值代价 | 建议 |
|---|---|---|
| ≤ 16 字节（4 字） | 寄存器传递，几乎免费 | 传值可以，代码更好读 |
| > 16 字节 | **走栈 + 内存拷贝** | **必须传指针** |

## 四、裸机上的硬规则

```c
/* ✅ 寄存器块：永远传基址指针（而且通常是编译期常量，连传都不用传） */
#define GPIOA ((GPIO_TypeDef *)0x40010800u)
GPIOA->BSRR = ...;

/* ✅ 大结构体：const 指针，明确表达"我不改" */
void uart_send(const uart_cfg_t *cfg, const uint8_t *buf, size_t n);

/* ❌ 别这么写：64 字节的拷贝发生在栈上，栈只有 20 KB */
uart_cfg_t make_cfg(void);        /* 返回大结构体：调用者栈上开临时对象 */
uart_send(make_cfg(), buf, n);
```

三条规则：

1. **> 16 字节的结构体一律传 `const *`**；
2. **不要让函数返回大结构体**（临时对象落在调用者栈上，`.su` 里看不到）；
3. **`->` 随便用，它是免费的**（实测三种写法机器码一致）。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实际是什么 |
|---|---|
| "`p->m` 是 `(*p).m` 的简写" | 实测**机器码完全相同**，三种写法（含裸地址）在 `-O0/-Os/-O2` 下都编译成 `movw/movt/str` |
| "传值更安全（不会改到外面）" | 代价实测：64 字节结构体在 `-O0` 下栈用量 **112 B**（传指针 4 B），约 40 条指令 |
| "`.su` 报 0 就是不要钱" | `-Os` 下 `huge_by_value` 报 0，但**调用者**在栈上替它复制了 64 字节——账记在别人头上 |
| "结构体传参和传指针差不多" | 小结构体（≤16 B）走 `r0..r3` 确实差不多；大结构体差 28 倍栈 + 40 条指令 |
| "寄存器地址用宏还是用指针都一样" | 机器层面一样，**但只有结构体写法能用 `_Static_assert` 校验偏移**（见 [8.12](8.12-结构体与嵌入式编程.md)） |

## 代码自测

<details>
<summary>Q1：既然 `->` 和裸地址生成的机器码一样，为什么还要用结构体映射寄存器？</summary>

**机器码一样，但"错的时候"完全不一样。**

裸地址写法：

```c
*(volatile uint32_t *)(0x40010800u + 0x10u) = (1u << 5);
```

这里 `0x10` 和 `0x40010800` 都是**我手抄手册的魔数**。
抄错了会怎样？——灯不亮。然后你花两小时查硬件。

结构体写法：

```c
typedef struct { volatile uint32_t CRL, CRH, IDR, ODR, BSRR, BRR, LCKR; } GPIO_TypeDef;
#define GPIOA ((GPIO_TypeDef *)0x40010800u)
_Static_assert(offsetof(GPIO_TypeDef, BSRR) == 0x10, "与 RM0008 不符");
GPIOA->BSRR = (1u << 5);
```

偏移抄错会怎样？——**编译不过**。实测故意把 `0x10` 写成 `0x14`：

```
gpio_bad.c:10:16: error: static assertion failed due to requirement
              '__builtin_offsetof(GPIO_TypeDef, BSRR) == 20': BSRR
gpio_bad.c:10:45: note: expression evaluates to '16 == 20'
```

编译器直接告诉你：**实际是 16，你写的是 20**。

这就是差别：同样的机器码，一个把错误推迟到"灯不亮"，
另一个把错误提前到"编译失败"。**在裸机上，能把检查从运行时提前到编译期，永远是赚的。**

另外两个附带好处：

- **可读性**：`GPIOA->BSRR` 一眼看出是哪个外设哪个寄存器；裸地址要读者自己算；
- **可移植**：换芯片只改结构体定义和基址宏，业务代码一行不动。
</details>

<details>
<summary>Q2：什么时候可以传值，什么时候必须传指针？给个判据。</summary>

按 **16 字节（4 个字）** 划线，这是 AAPCS 规定的寄存器传参上限：

| 大小 | 传值 | 传指针 |
|---|---|---|
| ≤ 16 B | ✅ 走 `r0..r3`，几乎免费 | 也行 |
| > 16 B | ❌ 走栈 + 内存拷贝 | ✅ 必须 |

实测数据（`-O0`，Cortex-M3）：

| 函数 | 结构体大小 | 栈用量 | 指令数 |
|---|---|---|---|
| `huge_by_value` | 64 B | **112 B** | ~40 |
| `huge_by_ptr` | 64 B（指针 4 B） | 4 B | 7 |
| `by_value` | 16 B | 12 B | — |
| `by_ptr` | 16 B | 4 B | 5 |

**裸机上的额外判据**（比性能更重要）：

1. **栈只有 20 KB，且溢出无报错**。传值把大对象放到栈上，
   而 `.su` 在 `-Os` 下还看不见（账记在调用者头上）——这是双重风险。
2. **传 `const *` 能表达"我不改"**，比传值的"我改的是副本"更便宜（4 B vs 64 B）。
3. **要改就传 `*`**，别用"传值 + 返回新值"（两次拷贝）。

一句话：**小结构体（≤4 字）传值没问题，大的一律 `const *` / `*`。
寄存器块压根不用传——它是编译期常量指针。**
</details>

<details>
<summary>Q3：`-Os` 下 `.su` 报 0，是不是说明优化后就没成本了？</summary>

**不是，这是最容易骗人的一处。**

实测：

```
== -O0 ==
sp2.c:4:huge_by_value   112   static
== -Os ==
sp2.c:4:huge_by_value     0   static
```

看 `-Os` 的反汇编：

```
00000000 <huge_by_value>:
       0: 990b   ldr r1, [sp, #0x2c]     ← 从 sp 读！说明数据确实在栈上
       2: 4408   add r0, r1
       4: 4770   bx lr
```

它读 `[sp, #0x2c]`——**参数就在栈上**。只是这 64 字节是**调用者**提前放好的，
所以 `huge_by_value` 自己的帧里不需要再开空间，`.su` 就报 0。

换句话说：

- `-O0`：被调用者自己开 112 字节帧，把参数搬进来；
- `-Os`：调用者把 64 字节放在自己的栈区，被调用者直接读。

**总成本没有消失，只是换了个地方记账。**

工程上的启示：

1. **不要只看单个函数的 `.su`**，尤其是开了优化之后。
   要看整条调用链，或者直接看链接期的栈余量（[11.5 映射文件](../11-linker/11.5-映射文件.md)）。
2. **传大结构体时，成本在调用点**，而调用点可能在一个很深的调用链上——
   那里往往才是栈最紧的地方。
3. 想要确定的答案：用 `-O0` 跑一遍 `.su` 看上界，
   再用 `-Os` 看优化后的实际值，两个数都要看。

**规则：看到 `.su` 报 0，先确认参数是不是大的——是的话，那个 0 是假象。**
</details>
