# A.3 做错会怎样

> 书：附录「项目创建清单」（原书 p243）
> 上一篇：[A.2 清单每步的实测数据](A.2-清单每步的实测数据.md)
> 对应实验：本次**逐条实测**（每个"做错的版本"都真的编/链了一遍，记录真实输出）

## 书这一节讲什么

**一篇"失败模式对照表"。**
[A.1](A.1-项目创建清单.md) 给清单、[A.2](A.2-清单每步的实测数据.md) 给正确路径的实测，
本篇给**每一步做错时的真实后果**。

为什么值得单独一篇？因为实测下来**大部分错误都不报错**：

| 做错的事 | 链接器的反应 |
|---|---|
| 漏 `ENTRY(Reset_Handler)` | 一条 **warning** |
| 漏 `KEEP(*(.vectors))` | **静默** |
| 向量表不写 ISR | **静默** |
| 不搬 `.data` / 不清 `.bss` | **静默** |
| 漏 `-mthumb` | **静默**（而且实测无影响） |
| 漏 `-mcpu=cortex-m3` | **静默**（编译通过） |

**六条里五条是静默的。** 这就是清单这类笔记存在的理由。

## 一、⭐ 失败①：链接脚本 `.vectors` 漏 `KEEP`

```ld
.vectors : { *(.vectors) } > FLASH      /* ❌ 少了 KEEP */
```

实测结果：

```
g_vectors 还在吗: ❌被删
ELF 入口: Entry point address: 0x8000001      ← ⚠ 基线是 0x8000015
尺寸: 206 B（基线 226）                        ← 少了 20 B
```

**整个向量表被 `--gc-sections` 删掉了**（16 B 表 + 4 B 差异）。

后果链：

1. `--gc-sections` 从 `ENTRY` 出发做可达性分析，**向量表没人"调用"**——
   它是被硬件读的，链接器不知道；
2. 向量表一删，`Reset_Handler` 就被放到了 `0x08000000`（Flash 最开头）；
3. 于是 `0x08000000` 处放的是**指令而不是 SP**——
   上电后 `SP = 那条指令的值`，**第一条 `push` 就飞了**。

⚠ **最阴险的一点**：entry 变成 `0x8000001` 看起来"很正常"（奇数、在 Flash 里），
尺寸还**变小了 20 B**，像"优化得不错"。只有上电才知道是坏的。

✅ **对策**：`KEEP(*(.vectors))`。本仓库 `Makefile` 里有 `check-nokeep` 目标专门查这个。

## 二、失败②：漏 `ENTRY(Reset_Handler)`

```
ld.lld: warning: cannot find entry symbol _start; not setting start address
  Entry point address: 0x0                    ← ⚠
```

加上之后（同一份脚本、同样的 `.o`）：

```
  （无警告）
  Entry point address: 0x8000015              ← ✅
```

⚠ 这是六条里**唯一会说话的一条**，但只给 warning。
`.bin` 照样能用（芯片不看 ELF 头），所以很容易被忽略——
直到你用调试器下断点，发现断不到 `Reset_Handler`。

## 三、失败③：向量表不写 ISR → ISR 被 gc

`main.c` 里写了 `SysTick_Handler`，但向量表只有 4 项（没写第 15 项）：

```
08000010 T Default_Handler
08000014 T Reset_Handler
0800006c T main
→ SysTick_Handler 是否被 gc：已被删除         ← ❌
```

和 [19.3](../19-systick-and-timer/19.3-g_ms与回绕安全的时间比较.md) 是同一个坑
（那里测得 text 124 → 52，差值 72 B = 向量表 56 B + ISR 16 B）。

✅ **对策**：向量表写全 16 项（至少把要用的 ISR 都写进去）。
⚠ `__attribute__((used))` **救不了**——它只保住代码，不保住"中断能进来"。

## 四、失败④：`Reset_Handler` 不搬 `.data` / 不清 `.bss`

```c
void Reset_Handler(void){ main(); for(;;){} }     /* ❌ 少了两步 */
```

实测：

```
链接：成功
   text    data     bss     dec     hex
     72      20       8     100      64
20000000 00000004 D g_init      ← 初值 0x1234 存在 Flash 的 _sidata 处
20000004 00000004 B g_zero
20000008 00000004 B g_out
```

**链接完全通过，符号表也完全正常。**
但上电后 `g_init` 读到的**不是 `0x1234`**，而是 RAM 的上电随机值；
`g_zero` 也**不是 0**。

⚠ **诚实标注**：本机无真机，**"读到随机值"是机制推导，不是我量出来的**。
实测到的是"链接成功、符号位置正确、没有任何告警"这一层。

✅ **对策**：`Reset_Handler` 里三步不能少（搬 `.data` → 清 `.bss` → `main()`）。

## 五、⚠ 实测推翻常识：漏 `-mthumb` / 漏 `-mcpu` 都没事

这两条我原本以为会报错，实测结果相反：

| 漏掉的 flag | 实测结果 |
|---|---|
| `-mthumb` | **编译通过**（exit 0），反汇编仍是 `b/movw/movt` 等 **Thumb 2 字节指令** |
| `-mcpu=cortex-m3` | **编译通过**（exit 0），无任何警告 |

```
漏 -mthumb 的反汇编（仍是 Thumb）：
       0: e7fe          b  0x0 <Default_Handler>   @ imm = #-0x4
       2: f240 0000     movw  r0, #0x0
       6: f240 0100     movw  r1, #0x0
```

原因：`--target=armv7m-none-eabi` **这个 triple 本身已经隐含 Thumb**
（ARMv7-M 架构只支持 Thumb 指令集，没有 ARM 状态）。

⚠ **但别因此就不写**：

1. 换成 `--target=armv7em-none-eabi`（M4F）或其他架构时，隐含假设会变；
2. 别人读你的 `Makefile` 时，**显式写出来是自文档**；
3. `-mcpu` 影响的是**指令调度与可用指令集**（如 M4 的 DSP 扩展），
   漏了会退化到通用默认，可能悄悄变慢——**这次实测没报错，不代表没代价**。

## 六、汇总对照表

| # | 做错 | 链接器说 | 实测数字 | 上电后 |
|---|---|---|---|---|
| ① | `.vectors` 漏 `KEEP` | 静默 | 226 → **206 B**，入口 `0x8000001` | SP = 指令值，一 `push` 就飞 |
| ② | 漏 `ENTRY` | **warning** | 入口 **0x0**（正常 `0x8000015`） | `.bin` 能用，调试器断不到 |
| ③ | 向量表不写 ISR | 静默 | ISR 符号消失（19.3：124→52） | 中断触发 → HardFault |
| ④ | 不搬 `.data`/不清 `.bss` | 静默 | 链接成功，符号正常 | 全局初值是 RAM 随机值 |
| ⑤ | 漏 `-mthumb` | 静默 | 编译通过，**仍是 Thumb**（triple 隐含） | ⚠ 本次无影响，但不代表通用 |
| ⑥ | 漏 `-mcpu` | 静默 | 编译通过 | 可能悄悄退化指令调度 |

## 坑点

| 坑 | 原书怎么说 | 实际是什么（实测） |
|---|---|---|
| "链接能过就说明配置对了" | —— | ❌ 实测 **6 种错误里 5 种静默通过** |
| "尺寸变小总是好事" | —— | ⚠ 实测漏 `KEEP` 时 **226 → 206 B**，其实是**向量表被删了** |
| "漏 `-mthumb` 会编出 ARM 指令" | —— | ❌ 实测 `armv7m-none-eabi` **隐含 Thumb**，漏了也没事（但别依赖） |
| "漏 `-mcpu` 会报错" | —— | ❌ 实测 **exit=0**，静默 |
| "加 `used` 能保住 ISR" | —— | ⚠ 只保住代码，**中断照样进不来**（要修向量表） |
| "链接器会提醒我漏了什么" | 附录给清单 | ❌ 实测只有漏 `ENTRY` 给了一条 **warning** |

## 代码自测

<details>
<summary>Q1：为什么"尺寸变小"反而要警惕？</summary>

因为**删掉有用的东西也会变小**，而链接器不会告诉你删的是什么。

实测三组数字：

| 情况 | 尺寸 | 性质 |
|---|---|---|
| 基线（正确） | 226 B | —— |
| 漏 `KEEP`（向量表被删） | **206 B** | ❌ 坏了 |
| `/DISCARD/` 掉 `.ARM.exidx`（有意为之） | **210 B** | ✅ 有意的取舍 |

**两次都是"变小"，一次是 bug、一次是优化。**

⚠ 而且 206 比 210 **还小**——如果只看"谁更小"，
坏掉的那个版本会赢。这就是为什么**尺寸不能单独当指标**。

**正确的做法**：尺寸变化时要**同时看符号表**：

```sh
llvm-size app.elf                          # 尺寸
llvm-nm app.elf | grep -E 'g_vectors|Handler'   # 关键符号还在吗
llvm-readelf -h app.elf | grep -i entry    # 入口对吗
```

三个都对得上，"变小"才是优化。

**引申**：本仓库的纪律是**每个数字都要有出处**（[18.1](../18-next-steps/18.1-学会写作.md)）。
尺寸这种"单一数字"尤其危险——
它看起来精确、可比较，但**完全没有告诉你变的是什么**。
</details>

<details>
<summary>Q2：漏 KEEP 时，为什么入口变成了 0x8000001 而不是 0x0？</summary>

因为 `ENTRY(Reset_Handler)` **还在**，只是 `Reset_Handler` 的地挪了。

```
正确（有 KEEP）：
  0x08000000  .vectors   16 B   ← SP=0x20005000, Reset=0x08000015
  0x08000010  .text            ← Reset_Handler 在这里
  → ENTRY(Reset_Handler) = 0x08000014 | 1 = 0x8000015   ✅

漏 KEEP（向量表被删）：
  0x08000000  .text            ← Reset_Handler 被挤到了最开头
  → ENTRY(Reset_Handler) = 0x08000000 | 1 = 0x8000001   ⚠
```

**入口地址本身"看起来合法"**：奇数（Thumb 标志 ✅）、在 Flash 里 ✅。
所以它通过了所有"格式检查"——只有**语义**是错的：
`0x08000000` 应该是 **SP** 的位置，现在放了代码。

⚠ 这正是本篇的核心教训：**裸机上"格式对"和"语义对"是两回事**。

| 检查 | 漏 KEEP 的版本 | 结论 |
|---|---|---|
| 入口是奇数？ | ✅ `0x8000001` | 格式对 |
| 入口在 Flash？ | ✅ | 格式对 |
| `0x08000000` 处是 SP？ | ❌ 是代码 | **语义错** |
| 向量表存在？ | ❌ 被删了 | **语义错** |

✅ 所以校验脚本**不能只查入口**，必须查**向量表前两项的语义**
（见 [A.2](A.2-清单每步的实测数据.md) 第三节）。
</details>

<details>
<summary>Q3：这六条里哪条最危险？</summary>

**第 ① 条（漏 `KEEP`）和第 ③ 条（向量表不写 ISR）并列。**

判据三条：**多晚被发现 × 多难定位 × 后果多严重**。

| # | 何时暴露 | 定位难度 | 后果 |
|---|---|---|---|
| ① 漏 `KEEP` | **上电第一条指令** | 难（入口看起来合法） | 完全不启动 |
| ② 漏 `ENTRY` | 调试时（`.bin` 能跑） | **容易**（有 warning） | 只影响调试 |
| ③ 向量表不写 ISR | **中断第一次触发** | ⭐ 最难（间歇性） | HardFault，且可能跑一阵才崩 |
| ④ 不搬 `.data` | 用到全局变量时 | 中（值随机，不像 bug 像玄学） | 逻辑错误，不是崩溃 |
| ⑤ 漏 `-mthumb` | **不会暴露**（本次无影响） | —— | 无 |
| ⑥ 漏 `-mcpu` | 可能永远不暴露 | —— | 可能悄悄变慢 |

**③ 最阴险**：程序能正常跑起来、主循环正常、LED 正常闪，
直到某个中断第一次触发——**如果那个中断很罕见（比如 1 小时一次）**，
你会得到一个"偶尔死机"的设备，而且**没有任何线索指向 ISR**。

**① 最彻底**：直接不启动，但因为它暴露得早（上电就不动），
反而比 ③ 好定位——至少你知道"根本没跑起来"。

⚠ **共同点**：两者都是 **`--gc-sections` 删了不该删的东西**。
所以本篇给的唯一硬建议是：

> **每次链完，用 `llvm-nm` 确认 `g_vectors` 和所有 ISR 都还在。**
> 花 5 秒，能挡住最贵的两个坑。
</details>
