# 15.3 二进制模式

> 书：第 15 章 命令行参数和原始 I/O · 15.3 二进制模式（原书 p212+ 区间内）
> 上一篇：[15.2 原始 I/O](15.2-原始IO.md) ｜ 下一篇：[15.4 ioctl](15.4-ioctl.md)
> 对应实验：主机侧实测（clang 23.1.0 / macOS arm64）— `O_BINARY` 是否存在、
> `\n` 是否被翻译、`\r` 是否被吞、`0x00` 二进制块

## 书这一节讲什么

一句话：**"二进制模式"是 stdio（`fopen` 的 `"b"`）的概念；
原始 I/O（`open/read/write`）天生就是二进制的，根本没有这个开关。**

`fopen` 要写 `"rb"` / `"wb"`，`open` **不用**——
因为 raw I/O 从设计上就不做任何字节翻译。
本篇把这件事**测出来**，并补上"二进制数据里含 `0x00`"这个真正的坑。

## 一、⚠ 实测：`O_BINARY` 在 POSIX 上根本不存在

```c
#ifdef O_BINARY
    printf("O_BINARY 已定义 = 0x%x\n", (unsigned)O_BINARY);
#else
    printf("O_BINARY 未定义（POSIX 无此标志）\n");
#endif
```

```
$ ./bm
O_BINARY 未定义（POSIX 无此标志）
O_TEXT 未定义
```

——所以**在 macOS / Linux 上，`open()` 里写 `O_BINARY` 连编译都过不去**
（除非你自己 `#define O_BINARY 0` 做跨平台垫片，Windows 上才置为真实值）。

| 平台 | `fopen` 需要 `"b"` 吗 | `open` 需要 `O_BINARY` 吗 | `\n` 会被翻译吗 |
|---|---|---|---|
| Linux / macOS（POSIX） | 写了无害，**无实际区别** | ❌ **根本没有这个宏** | ❌ 不翻译 |
| Windows（MSVC/mingw） | ⚠ **必须写**，否则 `\n`→`\r\n` | ⚠ 需要 `_O_BINARY` / `_setmode` | ✅ 会翻译 |

## 二、⚠ 实测：`\n` 一个字节进、一个字节出

同一串 `"a\nb\n"`（4 字节），两种写法的磁盘结果：

```
raw   open()+write()  -> 磁盘 4 字节: 61 0a 62 0a
stdio fopen("w")      -> 磁盘 4 字节: 61 0a 62 0a
```

```
$ od -An -tx1 bm.bin
 61  0a  62  0a
$ od -An -tx1 bm.txt
 61  0a  62  0a
```

**完全一样**——POSIX 下 `"w"` 和 `"wb"` 产出逐字节相同，
源码里 2 个 `\n`，磁盘上就是 2 个 `0x0a`，**没有多出 `0x0d`**。
文件大小都是 4 字节。

⚠ **这条只在 POSIX 上成立。** 同一段代码在 Windows 上用 `"w"` 写，
磁盘会是 `61 0d 0a 62 0d 0a`（6 字节）——这就是为什么**跨平台代码必须写 `"wb"`**：
写上它在 POSIX 上是 no-op，不写它在 Windows 上是 bug。

## 三、⚠ 实测：反向也一样，读的时候不吞 `\r`

造一个手工二进制文件 `x 0d 0a y`（4 字节，注意它是 raw `write` 写进去的）：

```
源文件 x 0d 0a y（4 字节），"r" 读出 4 字节: 78 0d 0a 79
```

**4 字节进、4 字节出，`0x0d` 原封不动。**
在 Windows 上用 `"r"`（文本模式）读同一个文件，会得到 3 字节（`0d 0a` 折叠成 `\n`）——
这就是为什么读 PNG / 固件镜像 / 任何二进制文件时，**模式字符串必须带 `b`**。

**结论**：POSIX 上你感觉不到区别，是因为系统不翻译；
Windows 上你感觉不到区别，是因为**你侥幸写了 `b`**。
**不要靠"我这边跑着没问题"来判断模式字符串对不对。**

## 四、raw I/O 为什么不需要"二进制模式"

因为翻译发生在 **stdio 层**（`FILE*` 的缓冲区进出时），
而 `open/read/write` **压根不经过那一层**：

```
fprintf/fwrite ──► stdio 缓冲（这里有 t/b 差异）──► write() ──► 内核
write()        ───────────────────────────────────────────────► 内核
```

所以：

- ✅ **用 raw I/O 就自动是二进制语义**，不需要、也不可能指定模式；
- ⚠ 反过来，`read` 出来的字节**完全按原样**给你——
  包括 Windows 上文件里真实存在的 `\r\n`，得你自己处理。

## 五、⚠ 真正的坑：二进制数据里的 `0x00`

这才是"二进制模式"最容易翻车的地方——**不是模式字符串，而是你顺手用了字符串工具**。

```
$ ./bm2
write(fd, blk, 8) 返回值 = 8
read 全量: 8 字节 = 01 00 ff 41 42 00 7f 80
strlen(blk)   = 1   <-- ⚠ 只数到第一个 0x00
printf %s     = []  <-- ⚠ 打印到第一个 0x00 为止
fread(r,1,8)  = 8 字节 = 01 00 ff 41 42 00 7f 80
```

`blk[8] = {01 00 ff 41 42 00 7f 80}` 一共 8 字节，里面有 **2 个 `0x00`**：

| 工具 | 结果 | 原因 |
|---|---|---|
| `write(fd, blk, 8)` | **8** | ✅ 显式给长度，不看内容 |
| `read(fd, r, 8)` | **8** | ✅ 同上 |
| `fread(r, 1, 8, f)` | **8** | ✅ 按字节计数 |
| `strlen(blk)` | **1** | ⚠ 遇到 `0x00` 就停 |
| `printf("%s")` | **空** | ⚠ 同上 |

**规则**：二进制数据**永远**用"缓冲区指针 + 显式长度"，
不要用 `strlen` / `strcpy` / `%s` 去推断长度。
[ch14](../14-buffered-file-io/14.5-二进制IO.md) 讲 `fwrite` 结构体填充时已经踩过一次同类问题。

## 六、⚠ `fread` 的返回值是"项数"，不是"字节数"

```
$ ./bm2
fread(r,4,2)  = 2 项（8 字节文件正好 2 项）
fread(r,4,3)  = 2 项（短项返回 2，不是 8）
```

`fread(ptr, size, nmemb, f)` 返回的是**完整读入的 `size` 大小的项数**。
文件只有 8 字节时 `fread(r,4,3)` 返回 **2**，你**不能**把它当字节数用。

✅ **推荐的写法**：永远让 `size=1`，返回值就是字节数。

```c
size_t got = fread(buf, 1, sizeof buf, f);   /* got == 字节数，语义唯一 */
```

## 七、裸机映射：UART 上只有"字节流"，没有模式概念

裸机的串口是**纯字节通道**——发 `0x0A` 就是 `0x0A`，没有任何层会替你加 `\r`：

| PC 概念 | 裸机对应 | 说明 |
|---|---|---|
| 文本/二进制模式 | **不存在** | 只有 `uart1_putc(uint8_t)` |
| `0x00` 特殊吗 | **不特殊** | 就是一个字节，照样发出去 |
| `\n` → `\r\n` | **要自己加** | 终端（minicom/screen）需要 `0x0D 0x0A`，你必须在 `putc('\n')` 时手动补 `\r` |

```c
void uart1_putc(uint8_t c) {
    if (c == '\n') uart1_putc('\r');      /* ⚠ 手动补 CR，没有系统帮你做 */
    while (!(USART1->SR & USART_SR_TXE)) ;
    USART1->DR = c;
}
```

——**这条正好是"文本模式"在 PC 上由 libc 替你做的事。**
在 PC 上你嫌它多事（`t`/`b` 之争），在裸机上你得自己补上它。

## 坑点

| 坑 | 原书怎么说 | 实际是什么（实测） |
|---|---|---|
| `O_BINARY` 到处都能用 | 只提了二进制模式 | ❌ **POSIX 上未定义**（`./bm` 实测），只有 Windows 有 |
| `"w"` 和 `"wb"` 有区别 | Windows 语境下有 | POSIX 上**逐字节相同**（`61 0a 62 0a` vs `61 0a 62 0a`） |
| 文本模式读会吞 `\r` | Windows 会 | POSIX 上**不吞**（4 字节进 4 字节出：`78 0d 0a 79`） |
| `strlen` 能量二进制长度 | 没提 | ⚠ **不能**：`8` 字节块测出 `1` |
| `fread` 返回字节数 | 没强调 | ⚠ **返回项数**：`fread(r,4,3)` → `2` |
| raw I/O 需要二进制模式 | —— | ❌ 不需要，raw 天生二进制（不经过 stdio 翻译层） |

## 代码自测

<details>
<summary>Q1：这段代码在 Linux 上能编译吗？</summary>

```c
int fd = open("x.bin", O_WRONLY | O_CREAT | O_BINARY, 0644);
```

**不能。** 实测 `O_BINARY 未定义（POSIX 无此标志）`，
编译期 `O_BINARY` 是未声明标识符 → 报错。

正确写法（跨平台）：

```c
#ifndef O_BINARY
#define O_BINARY 0          /* POSIX 上是 0，加上等于没加 */
#endif
int fd = open("x.bin", O_WRONLY | O_CREAT | O_BINARY, 0644);
```

——这也是为什么**跨平台项目里 `O_BINARY` 垫片是标准操作**。
</details>

<details>
<summary>Q2：`fread(buf, 4, 3, f)` 在只有 8 字节的文件上返回什么？你想读 12 字节，实际拿到几个字节？</summary>

返回 **2**（项数，实测）。实际拿到 **8 字节**（2 项 × 4 字节）。

文件只剩一个不完整的第 3 项时，`fread` **不会**把残缺的那一半塞进缓冲区，
它返回已完整读入的项数，**末尾不足一项的部分留在流里**。

推荐改成 `fread(buf, 1, 12, f)`，此时返回 **8**——直接就是字节数，不会算错。
</details>

<details>
<summary>Q3：收到 8 字节串口帧 `01 00 ff 41 42 00 7f 80`，用 `printf("%s", frame)` 打印为什么什么都看不到？</summary>

因为 `frame[1]` 就是 `0x00`，`%s` 遇到第一个 `0x00` 就认为字符串结束 → 打印空（实测 `printf %s = []`）。

✅ 正确做法：按长度转十六进制打印

```c
for (size_t i = 0; i < len; i++) printf("%02x ", frame[i]);
```

——**二进制帧永远带长度，不要用 NUL 结尾的字符串语义。**
（对比 [ch09](../09-uart-serial/README.md) 里"打印收到的字节"的习惯写法。）
</details>

<details>
<summary>Q4：裸机上 `uart1_putc('\n')` 后，终端上光标回到行首了吗？</summary>

**没有。** 实测结论：裸机 UART 是纯字节通道，没有任何层把 `\n` 翻译成 `\r\n`。
终端（minicom / screen / PuTTY）收到单独的 `0x0A`（LF）通常**只换行不回车**，
表现为"阶梯状"输出：

```
第一行
     第二行
           第三行
```

必须在驱动里手动补 `0x0D`：

```c
if (c == '\n') uart1_putc('\r');
```

——**这正是 PC 上"文本模式"替你干的活。**
PC 上它是可开关的翻译，裸机上它是你必须手写的一行。
</details>
