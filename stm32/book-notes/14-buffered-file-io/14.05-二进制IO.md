# 14.05 二进制 I/O

> 书：第 14 章 缓冲文件 I/O · 14.05 二进制 I/O（原书 p202–211 区间内）
> 上一篇：[14.04 打开文件](14.04-打开文件.md) ｜ 下一篇：[14.06 缓冲与刷新](14.06-缓冲与刷新.md)
> 对应实验：主机侧实测（clang 23.1.0 / macOS arm64）— 文本/二进制大小对照、
> **结构体填充字节实测**（12 B vs 7 B）、小端字节序实测

## 书这一节讲什么

一句话：**`fwrite` / `fread` 直接读写原始字节，不做任何转换。**

书上讲 `fwrite(&x, sizeof x, 1, f)` 这种用法。本篇补上书里**没讲但会咬人**的两件事：

1. **⚠ 直接 `fwrite` 一个结构体会把填充字节也写进去**（实测 12 B vs 7 B）；
2. **⚠ 二进制格式依赖字节序**（`40 42 0f 00` 在小端上才等于 1000000）。

## 一、实测：同一个 `int 1000000`，两种存法

```c
int v = 1000000;
FILE *fb = fopen("v.bin","wb"); fwrite(&v, sizeof v, 1, fb); fclose(fb);
FILE *ft = fopen("v.txt","w");  fprintf(ft, "%d", v);        fclose(ft);
```

```
$ ./tb
同一个 int 1000000：二进制 4 字节 / 文本 7 字节
$ ls -l v.bin v.txt
4 v.bin
7 v.txt
$ od -An -tx1 v.bin
 40  42  0f  00
$ cat v.txt
1000000
```

| | 二进制 | 文本 |
|---|---|---|
| 大小 | **4 字节** | **7 字节** |
| 内容 | `40 42 0f 00` | `1000000` |
| 优点 | 精确、快、**可逆** | 可读、可 diff、可手改 |
| 缺点 | 不可读、**依赖字节序/对齐** | 慢、大、**有精度问题**（浮点） |

⚠ **`0x000F4240 = 1000000`**。文件里是 `40 42 0f 00`——
**最低有效字节在最前面**，这是**小端**（little-endian）。
Cortex-M 也是小端（[ch08](../08-complex-types/8.10-联合体.md) 实测
`u.i = 0x12345678 → b[0] = 0x78`）。

## 二、⚠ 实测坑①：`fwrite` 一个结构体会把填充字节也写进去

这是本节最重要的一条，有实测数字。

```c
typedef struct { uint8_t flag; uint32_t value; uint16_t code; } rec_t;
typedef struct { uint8_t flag; uint32_t value; uint16_t code; } __attribute__((packed)) rec_p_t;

rec_t   r = { 1, 0x11223344u, 0x5566 };
rec_p_t p = { 1, 0x11223344u, 0x5566 };
fwrite(&r, sizeof r, 1, f);      /* 自然对齐 */
fwrite(&p, sizeof p, 1, f);      /* packed */
```

**实测**：

```
rec_t    sizeof=12  offsetof(flag)=0 offset(value)=4 offset(code)=8
rec_p_t  sizeof=7（packed，无填充）

自然对齐 fwrite：12 字节 → 01 00 00 00 44 33 22 11 66 55 00 00
packed   fwrite：7 字节 → 01 44 33 22 11 66 55

$ ls -l r_nat.bin r_pkd.bin
12 r_nat.bin
7  r_pkd.bin
```

**拆解自然对齐的那 12 字节**：

```
01          00 00 00       44 33 22 11     66 55      00 00
└flag(1)┘  └填充(3)┘      └value(4)┘     └code(2)┘  └尾部填充(2)┘
```

⚠ **12 字节里有 5 字节是填充**（3 + 2），**占比 42%**。
这些字节被**真的写进了文件**。

**三个后果**：

| 后果 | 说明 |
|---|---|
| **文件变大** | 12 B vs 7 B（实测），数据量大时差异巨大 |
| **填充字节的值不确定** | ⚠ C 标准说填充字节的值是**未指定的**。实测里是 `00`，但**不保证**——换编译器/优化级可能变 |
| **格式不兼容** | 编译器改了对齐规则 → 老文件读不出来 |

⚠ **"填充字节值不确定"是最阴的一条**：
同样的代码，两次运行写出的文件**可能不一样**
（填充位置残留了上一次的栈内容），
于是**校验和不稳定**，你会以为"数据被破坏了"。

**对策（三选一）**：

| 方案 | 做法 | 适用 |
|---|---|---|
| **① 逐字段序列化**（✅ 推荐） | 手工 `fwrite` 每个字段，或按字节组装 | 跨平台、跨版本 |
| **② `packed` 结构体** | `__attribute__((packed))` | ⚠ 要小心非对齐访问（M0 HardFault） |
| **③ 加编译期断言** | `_Static_assert(sizeof(rec_t) == 12, ...)` | 至少保证不变 |

**①的写法**：

```c
static void put_u32(uint8_t *b, uint32_t v){ b[0]=v; b[1]=v>>8; b[2]=v>>16; b[3]=v>>24; }
static void put_u16(uint8_t *b, uint16_t v){ b[0]=v; b[1]=v>>8; }

void rec_serialize(uint8_t out[7], const rec_t *r){
    out[0] = r->flag;
    put_u32(out + 1, r->value);
    put_u16(out + 5, r->code);
}
```

——**字节序写死为小端**（或写死为大端），
**文件格式不再依赖编译器和 CPU**。

⚠ **`packed` 的代价**（[ch08](../08-complex-types/8.12-结构体与嵌入式编程.md)）：
`packed` 之后 `value` 落在偏移 1，**不是 4 的倍数** →
在 **Cortex-M0 上非对齐访问直接 HardFault**。
**别为了省 5 字节去冒这个险**，除非你确实需要紧凑格式并且用逐字节访问。

## 三、⚠ 实测坑②：二进制格式依赖字节序

`v.bin` 里是 `40 42 0f 00`：

| 机器 | 读出来是多少 |
|---|---|
| **小端**（x86、arm64、Cortex-M） | **1000000** ✅ |
| 大端（某些 MIPS、网络字节序） | `0x40420F00` = **1078089472** ❌ |

⚠ **网络协议规定用大端**（network byte order），
所以如果你在写网络报文，要**显式转换**：

```c
#include <arpa/inet.h>
uint32_t n = htonl(v);        /* host → network（大端） */
uint32_t h = ntohl(n);        /* network → host */
```

裸机上没有 `arpa/inet.h`，自己写：

```c
static uint32_t swap32(uint32_t x){
    return ((x & 0xFF) << 24) | ((x & 0xFF00) << 8) |
           ((x >> 8) & 0xFF00) | ((x >> 24) & 0xFF);
}
uint32_t to_be(uint32_t x){        /* 转成大端 */
#if defined(__BYTE_ORDER__) && (__BYTE_ORDER__ == __ORDER_BIG_ENDIAN__)
    return x;
#else
    return swap32(x);
#endif
}
```

## 四、`fwrite` / `fread` 的正确用法（返回值）

```c
size_t fwrite(const void *ptr, size_t size, size_t nmemb, FILE *f);
size_t fread (void *ptr, size_t size, size_t nmemb, FILE *f);
```

⚠ **返回值是"成功读写的【项数】"，不是字节数**。

```c
rec_t r;
size_t n = fwrite(&r, sizeof r, 1, f);
if (n != 1) { /* ⚠ 没写完！ */ }
```

**两个参数的坑**：

```c
fwrite(buf, 1, 100, f);       /* 写 100 项 × 1 字节 = 100 字节 */
fwrite(buf, 100, 1, f);       /* 写 1 项 × 100 字节 = 100 字节 */
```

两者**总字节数一样**，但**返回值含义不同**：

| 调用 | 写了一半（50 字节）时返回 |
|---|---|
| `fwrite(buf, 1, 100, f)` | **50**（50 个 1 字节项） |
| `fwrite(buf, 100, 1, f)` | **0**（0 个 100 字节项！） |

⚠ **第二种写法下，你无法区分"一个都没写"和"写了一部分"**——
因为只要没写满 100 字节，返回值就是 0。

**规则**：

> **`size` 用 1，`nmemb` 用总字节数。**
> 这样返回值 = 实际读写的字节数，语义最清晰。

```c
size_t n = fwrite(buf, 1, nbytes, f);      /* ✅ */
if (n != nbytes) { /* 处理短写 */ }
```

## 五、文本 vs 二进制：什么时候选哪个

| 场景 | 选 | 理由 |
|---|---|---|
| **配置文件**（给人改） | **文本** | 可用编辑器改、可进 git diff |
| **固件镜像** | **二进制** | 必须逐字节精确 |
| **协议报文** | **二进制** | 带宽/存储效率，且要精确 |
| **日志** | **文本** | 人要读 |
| **高频采样数据** | **二进制** | 实测 4 B vs 7 B（**省 43%**） |
| **跨机器传输** | **二进制 + 显式字节序** | 文本也可以，但要处理编码 |

⚠ **浮点不要用文本存**：

```c
double x = 0.1;
fprintf(f, "%.17g", x);       /* ✅ 需要 17 位有效数字才能无损往返 */
fprintf(f, "%f", x);          /* ❌ 0.100000 —— 丢精度 */
```

而二进制 `fwrite(&x, sizeof x, 1, f)` 是**逐字节精确**的。

## 六、裸机上的"二进制 I/O"

书上的 `fwrite` 在裸机上没有（没文件系统），
但**"按原始字节收发"这件事天天在做**：

| PC | 裸机 |
|---|---|
| `fwrite(&v, 4, 1, f)` | `uart1_send_bytes((uint8_t*)&v, 4)` |
| `fread(&v, 4, 1, f)` | 从环形缓冲里取 4 字节再拼 |
| 文件格式 | **协议帧格式** |
| 字节序 | 串口/网口的字节序（通常小端，网络大端） |

⚠ **裸机协议设计的三条纪律**（都来自本节的实测教训）：

1. **显式定义字节序**（别依赖 CPU）；
2. **不要直接 `memcpy` 结构体**（填充字节会进报文，实测 12 vs 7）；
3. **加长度 + CRC**（对应"检查 `fwrite` 返回值"）。

**典型的帧格式**：

```
| magic(2) | len(2) | payload(len) | crc32(4) |
```

——`magic` 对应 [ch11](../11-linker/11.06-高级用法.md) 配置区里的 `magic` 字段，
`crc32` 对应那里的 CRC，**思路完全一样**。

## 坑点（书 / 常识怎么说 / 实际是什么）

| 书 / 常识怎么说 | 实测是什么 |
|---|---|
| "`fwrite(&s, sizeof s, 1, f)` 很方便" | ⚠ **把填充字节也写进去了**。实测 `rec_t` 12 B vs `packed` 7 B，**5 字节是填充（42%）** |
| "填充字节都是 0" | ⚠ C 标准说填充字节的值**未指定**。实测这次是 `00`，**不保证下次也是** |
| "二进制文件可移植" | ⚠ 依赖**字节序**。`40 42 0f 00` 只在小端上是 1000000 |
| "`fwrite` 返回值是字节数" | ❌ 是**项数**。`fwrite(buf,100,1,f)` 写一半时返回 **0**，无法判断写了多少 |
| "`packed` 能省空间" | 能（实测 12→7），但 `value` 落在偏移 1 → **Cortex-M0 上 HardFault** |
| "二进制比文本省" | ✅ 实测 `int 1000000`：4 B vs 7 B（省 43%）。但**浮点用文本要 17 位才无损** |

<details>
<summary>Q1：为什么不能直接 `fwrite` 一个结构体？实测差多少？</summary>

**因为 `fwrite` 写的是 `sizeof(struct)` 个字节，包括**填充字节**。**

**实测**：

```c
typedef struct { uint8_t flag; uint32_t value; uint16_t code; } rec_t;
typedef struct { uint8_t flag; uint32_t value; uint16_t code; } __attribute__((packed)) rec_p_t;
```

```
rec_t    sizeof=12  offsetof(flag)=0 offset(value)=4 offset(code)=8
rec_p_t  sizeof=7（packed，无填充）

自然对齐 fwrite：12 字节 → 01 00 00 00 44 33 22 11 66 55 00 00
packed   fwrite：7 字节 → 01 44 33 22 11 66 55

文件大小：12 r_nat.bin / 7 r_pkd.bin
```

**那 12 字节里有什么**：

```
01          00 00 00       44 33 22 11     66 55      00 00
└flag(1)┘  └填充(3)┘      └value(4)┘     └code(2)┘  └尾部填充(2)┘
            ↑ 让 value 对齐到 4                ↑ 让整个结构体对齐到 4
```

**5 字节填充 / 12 字节 = 42% 是废的。**

---

**三个具体后果**：

**① 文件变大**（12 vs 7，数据量大时差异可观）

**② ⚠ 填充字节的值不确定（最阴的一条）**

C 标准说填充字节的值是 **unspecified（未指定）**。
实测这次是 `00`，但：

- 换编译器可能变；
- 换优化级可能变；
- **同一程序两次运行都可能变**（填充位置残留上次用过的栈内容）。

后果：**同样的输入，两次运行写出的文件校验和不同**，
你会以为"数据被破坏了"，其实是填充字节在变。

**③ 格式不兼容**

编译器改了对齐规则（比如换到 64 位平台、加了字段），
老文件就读不出来了——**而你看不出来**，因为 sizeof 一样。

---

**三条对策**：

**① 逐字段序列化（✅ 最推荐）**

```c
static void put_u32(uint8_t *b, uint32_t v){ b[0]=v; b[1]=v>>8; b[2]=v>>16; b[3]=v>>24; }
static uint32_t get_u32(const uint8_t *b){ return b[0] | (b[1]<<8) | ((uint32_t)b[2]<<16) | ((uint32_t)b[3]<<24); }

void rec_serialize(uint8_t out[7], const rec_t *r){
    out[0] = r->flag;
    put_u32(out + 1, r->value);
    put_u16(out + 5, r->code);
}
```

- **字节序写死**（这里是小端）；
- **没有填充**；
- **改结构体不会破坏格式**（只要序列化函数跟着改）。

**② `packed`（⚠ 要小心）**

```c
typedef struct {...} __attribute__((packed)) rec_p_t;    /* 实测 sizeof=7 */
```

省了 5 字节，但 `value` 落在**偏移 1**——**不是 4 的倍数**。

| 内核 | 访问 `p.value` 会怎样 |
|---|---|
| **Cortex-M0** | **HardFault**（不支持非对齐访问） |
| Cortex-M3/M4 | 能跑，慢，且**非原子** |

所以 `packed` 适合**只做"存储格式"、不做"内存访问"**的场景：
写的时候逐字节填，读的时候逐字节取，不直接访问字段。

**③ 至少加编译期断言**

```c
_Static_assert(sizeof(rec_t) == 12, "rec_t 布局变了，文件格式不兼容！");
```

——不能消除填充，但**能在格式变化时立刻报错**，
而不是等到用户发现"老文件读不出来了"。
</details>

<summary>Q2：`fwrite` 的返回值到底怎么判断？两种调用写法差在哪？</summary>

**返回值是"成功写入的【项数】"，不是字节数。**

```c
size_t fwrite(const void *ptr, size_t size, size_t nmemb, FILE *f);
```

**两种写法对比**（都是写 100 字节）：

```c
fwrite(buf, 1, 100, f);       /* 100 项 × 1 字节 */
fwrite(buf, 100, 1, f);       /* 1 项 × 100 字节 */
```

| | 全部成功 | 只写了 50 字节 |
|---|---|---|
| `fwrite(buf, 1, 100, f)` | 返回 **100** | 返回 **50** ✅ 知道写了多少 |
| `fwrite(buf, 100, 1, f)` | 返回 **1** | 返回 **0** ❌ 无法区分"一点没写"和"写了一半" |

⚠ **第二种写法下，你只能知道"没写完整"，但不知道写了多少**——
**无法做断点续传、无法做部分重试**。

**规则**：

> **`size` 写 1，`nmemb` 写总字节数。
> 这样返回值 = 实际字节数，语义最清晰。**

```c
size_t want = 100;
size_t n = fwrite(buf, 1, want, f);
if (n != want) {
    /* 短写（short write）：磁盘满了 / 网络断了 / 被打断 */
    fprintf(stderr, "只写了 %zu / %zu 字节\n", n, want);
}
```

---

**`fread` 同理，而且有个额外的坑：短读不一定是错误**

```c
size_t n = fread(buf, 1, want, f);
if (n != want) {
    if (feof(f))  { /* 到文件尾了 —— 正常，不是错误 */ }
    if (ferror(f)) { /* 真的出错了 */ }
}
```

⚠ **读文件时"读到的比想要的少"通常是正常的**（文件就这么大），
所以 `fread` 之后要**用 `feof` / `ferror` 区分**，不能一律当错误处理。

**写文件时"写的比想要的少"几乎总是错误**（磁盘满、配额、断网），
所以 `fwrite` 短写一定要当错误处理。

---

**⚠ 最容易忘的一步：`fclose` 也要检查**

```c
fwrite(buf, 1, n, f);          /* 返回 n —— "成功" */
fclose(f);                     /* ⚠ 这里可能失败：缓冲区没刷出去 */
```

[14.04](14.04-打开文件.md) 详细讲过：
**`fwrite` "成功"只意味着数据进了用户态缓冲区，
`fclose` 刷新时才发现磁盘满了。**

```c
if (fclose(f) == EOF) {
    fprintf(stderr, "关闭失败（数据可能没写完）: %s\n", strerror(errno));
}
```

**顺序很重要**：

```c
/* ✅ 正确顺序 */
size_t n = fwrite(...);
if (n != want) { ...; }
if (fclose(f) == EOF) { ...; }        /* 最后检查关闭 */

/* ❌ 错误：fclose 之后再用 f */
fclose(f);
ferror(f);                            /* ⚠ f 已经是悬空的了 */
```
</details>

<details>
<summary>Q3：二进制文件的字节序问题怎么彻底解决？</summary>

**唯一可靠的办法：在格式里写死字节序，存取时显式转换。**

**问题实测**：

```
$ od -An -tx1 v.bin
 40  42  0f  00          ← 1000000 = 0x000F4240 的小端表示
```

| 机器 | `fread` 出来是多少 |
|---|---|
| 小端（x86 / arm64 / **Cortex-M**） | **1000000** ✅ |
| 大端（部分 MIPS / 网络字节序） | `0x40420F00` = **1078089472** ❌ |

**为什么会发生**：
`fwrite(&v, 4, 1, f)` 就是 `memcpy`——
**把内存里的 4 个字节原样写到文件**。
内存里的排列取决于 CPU 的字节序。

---

**解决方案：显式序列化（不依赖 CPU）**

```c
/* 写死为小端（Cortex-M 的原生字节序，也省一次转换） */
static void put_u32_le(uint8_t *b, uint32_t v){
    b[0] = (uint8_t)(v      );
    b[1] = (uint8_t)(v >>  8);
    b[2] = (uint8_t)(v >> 16);
    b[3] = (uint8_t)(v >> 24);
}
static uint32_t get_u32_le(const uint8_t *b){
    return (uint32_t)b[0]        | ((uint32_t)b[1] <<  8) |
           ((uint32_t)b[2] << 16)| ((uint32_t)b[3] << 24);
}
```

**这样写的好处**：

- **任何 CPU 上结果一样**（字节序由代码决定，不由 CPU 决定）；
- **没有填充字节**（配合 [Q1](14.05-二进制IO.md) 的逐字段序列化）；
- 代码量极小（几十字节），裸机上也放得下。

---

**如果要的是大端（网络字节序）**：

PC 上：

```c
#include <arpa/inet.h>
uint32_t n = htonl(v);      /* host to network（大端） */
uint32_t h = ntohl(n);      /* network to host */
uint16_t ns = htons(s);     /* 16 位版本 */
```

**裸机上没有 `arpa/inet.h`**（[ch12](../12-preprocessor/12.04-条件编译.md) 实测过交叉编译找不到 libc 头文件），
自己写：

```c
static uint32_t swap32(uint32_t x){
    return ((x & 0x000000FFu) << 24) | ((x & 0x0000FF00u) <<  8) |
           ((x & 0x00FF0000u) >>  8) | ((x & 0xFF000000u) >> 24);
}
```

⚠ **要不要 swap 取决于本机字节序**，可以用编译器宏判断：

```c
#if defined(__BYTE_ORDER__) && (__BYTE_ORDER__ == __ORDER_BIG_ENDIAN__)
#  define to_le32(x) swap32(x)
#  define to_le32(x) (x)
#else
#  define to_le32(x) (x)
#endif
```

或者**更稳的做法——完全不判断，直接按字节组装**（上面的 `put_u32_le`）：
**它在大端和小端机器上都产生小端结果**，
因为它是"逐字节赋值"，不涉及内存布局。

---

**三个实用建议**：

**① 帧格式里别放"裸结构体"**

```
❌ | rec_t(12 字节，含填充，字节序随 CPU) |
✅ | flag(1) | value(4,LE) | code(2,LE) |     ← 共 7 字节，格式写死
```

**② 加一个 magic / 版本字段**

[ch11](../11-linker/11.06-高级用法.md) 的 Flash 配置区设计里
`magic` / `version` / `crc32` 三个字段，
**同样的思路也能用在文件格式上**：

```
| magic(2) | version(1) | len(2,LE) | payload | crc32(4,LE) |
```

`version` 让你以后能改格式而不破坏老文件。

**③ 在另一台机器上测一次**

⚠ 字节序 bug 的诡异之处：**在你的机器上 100% 正常**。
要发现它，要么在另一架构的机器上跑一遍
（比如 Raspberry Pi 是 ARM 小端，可以和某些大端设备对照），
要么**写单元测试，用固定的字节序列做断言**：

```c
uint8_t buf[4];
put_u32_le(buf, 1000000);
assert(buf[0] == 0x40 && buf[1] == 0x42 && buf[2] == 0x0F && buf[3] == 0x00);
```

——**这个断言在任何 CPU 上都成立**，因为它测的是"格式"，不是"内存布局"。
